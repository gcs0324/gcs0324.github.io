Message Backlog · 消息积压
面试这样说

消息积压的根本原因就是生产速度远大于消费速度，我一般从三个层面去分析：是消费者挂了、消费逻辑太慢，还是突发流量打进来了。

紧急预案是先扩容消费者实例，Kafka 一个 Partition 只能对应 Consumer Group 里的一个消费者，所以要同时扩 Partition 数。如果积压量极大，我们会建临时 Topic，把原 Topic 的消息先用一个轻量 Consumer 快速转发进去，临时 Topic 开 10 倍分区数，再拉起大量 Consumer 并行消费。

非核心消息可以选择降级——比如日志类、统计类消息积压了就直接丢弃，优先保核心链路。

长期来看要复盘：批量拉取调大 max.poll.records、消费端异步化、或者从业务上做流量整形。

消息积压 — 临时 Topic 扩容分流方案
PLAN-A
紧急扩容处理流程
1
告警触发 — 定位积压原因
监控 消费者 Lag（consumer_lag），看是所有分区均匀积压（流量暴增）还是个别分区（消费者挂了）。
同时看消费者进程 CPU / GC 情况，排除消费逻辑耗时暴涨。
2
扩容消费者 + 扩分区
增加 Consumer Group 实例数。若实例数已 = Partition 数，先扩 Partition（注意：分区数只能增不能减，key 路由会变，需业务评估）。
黄金比例：Consumer 实例数 = Partition 数，充分并行。
# 动态增加分区（慎用，会影响 key 路由） kafka-topics.sh --alter --topic your_topic \ --partitions 30 --bootstrap-server broker:9092
3
极端积压 — 临时 Topic 分流
原 Topic 积压 1000 万条，建 临时 Topic（30 分区），用一个专门的转发 Consumer 快速把消息搬过去（只转发不处理），再起 30 个消费者并行消费临时 Topic，积压消化后下线临时资源。
原 Topic (3分区) ──→ 转发Consumer ──→ 临时Topic (30分区) └──→ 30 个 Consumer 并行消费
4
降级处理非核心消息
区分消息优先级。日志、埋点等非核心消息积压时直接 丢弃或延迟消费，保证订单、支付等核心 Topic 的资源。
5
事后优化
调大 max.poll.records 批量拉取；消费侧引入内存队列 + 线程池异步处理；评估是否需要拆 Topic、做流量整形（令牌桶限速生产方）。
常见根因
为什么会积压
优先排查这几点
  • 消费者实例挂了，Lag 急速上涨
  • 下游依赖慢（DB 慢查询、RPC 超时）
  • 消息体过大，反序列化耗时高
  • GC 停顿导致 poll 间隔超 session.timeout
  • 突发流量，生产侧没有限速
预防手段
降低积压概率
长期架构改进
  • 监控 Lag，提前预警（阈值 = 5min 消费量）
  • 消费者批量拉取 + 异步线程池处理
  • 生产侧限速（令牌桶），削峰填谷
  • 按消息优先级设独立 Topic
  • 定期演练扩容流程，保留临时扩容脚本
Message Durability · 消息不丢
面试这样说

消息不丢需要从三个阶段分别保证：生产者发送阶段、Broker 存储阶段、消费者处理阶段。每个阶段都有可能丢。

生产者阶段：把 acks 设成 all（-1），这样 Leader 和所有 ISR 副本都写入后才返回成功。同时开启 enable.idempotence，重试时不会重复写入。

Broker 阶段：副本数设 3，min.insync.replicas 设 2，这样只要有两个副本在线就能保证数据不丢。还要关掉 unclean.leader.election，防止落后的副本当选 Leader 造成数据回退。

消费者阶段：把 enable.auto.commit 关掉，改成手动提交 offset。业务处理完成后再 commit，防止"拿到消息但没处理完就提交了 offset"这种情况导致消息丢失。

① PRODUCER
生产者阶段
  • acks=all 等待所有 ISR 确认
  • retries=MAX 失败自动重试
  • 幂等Producer 重试不重复
  • 同步发送 核心消息用 get() 阻塞
② BROKER
Broker 存储阶段
  • replication.factor=3 三副本，允许 1 台宕机
  • min.insync.replicas=2 acks=all 时至少 2 个副本写入才算成功（1 Leader + 1 Follower），防 Leader 单点
  • 关闭 unclean 选举防数据回退
  • 刷盘策略 重要场景同步刷盘
③ CONSUMER
消费者阶段
  • 关闭自动提交 offset
  • 业务处理完再 commit
  • 异常时不 commit，触发重新消费
  • 结合幂等处理重复投递
消息不丢 — 三阶段失效点与防护措施
PRODUCER CONFIG
生产者不丢消息核心配置
1
acks=all — 强确认
Leader 收到消息后，等待所有 ISR（In-Sync Replica）副本全部写入才返回 ACK。若 ISR 中有副本宕机，写入会失败而非静默丢失。
props.put("acks", "all"); props.put("retries", Integer.MAX_VALUE); props.put("enable.idempotence", true); // 幂等Producer，防重试导致重复 props.put("max.in.flight.requests.per.connection", 5);
2
核心消息同步等待确认
支付、订单等核心业务用 Future.get() 阻塞等待，确认写入成功再返回给上游。异步回调适合日志类消息。
RecordMetadata meta = producer.send(record).get(); // 阻塞等确认 // 失败抛异常，业务层捕获后告警 / 重试 / 写补偿表
3
事务消息（RocketMQ 方案）
本地数据库操作和消息发送需要原子性时，用 RocketMQ 事务消息。半事务消息 → 执行本地事务 → commit/rollback，Broker 定时回查保证最终一致。
// RocketMQ 事务消息流程 发送半事务消息(PREPARED) → 执行本地事务(扣库存/更新订单) → commit → Broker 投递消费者 → rollback → Broker 删除消息 → 超时未响应 → Broker 回查本地事务状态
BROKER CONFIG
Broker 存储层不丢消息核心配置
1
replication.factor=3 — 三副本冗余
每个 Partition 在 3 台 Broker 上各存一份。允许 1 台 Broker 宕机数据不丢，是生产环境的最低标准。
# 创建 Topic 时指定（也可在 Broker 全局默认配置） kafka-topics.sh --create --topic order-topic \ --partitions 8 --replication-factor 3 \ --bootstrap-server broker:9092
2
min.insync.replicas=2 — 写入最小确认副本数
配合 acks=all 使用。含义：acks=all 发送的消息，至少需要 2 个副本（含 Leader）写入成功，才向 Producer 返回 ACK。
即 Leader 写入 + 至少 1 个 Follower 同步完成。若当前 ISR 副本数 < 2，Broker 直接拒绝写入（抛 NotEnoughReplicasException），而不是悄悄丢失数据。
# server.properties（Broker 全局） min.insync.replicas=2 # 含义：3 副本中允许 1 个 Follower 落后/宕机； # 若 2 个 Follower 同时宕机，ISR 只剩 Leader(1个) < 2， # 此时 acks=all 的写入会被拒绝，保护数据不丢。
3
unclean.leader.election.enable=false — 禁止脏选举
当 ISR 中所有副本都宕机，Kafka 默认会等待 ISR 恢复。若开启 unclean 选举，落后的非 ISR 副本会被强行选为 Leader，直接导致已确认的消息丢失（数据回退）。生产环境必须关闭。
# server.properties unclean.leader.election.enable=false // 默认 false（Kafka 0.11+） # 关闭后：ISR 全宕 → 宁可分区不可用，也不用落后副本服务 # 开启后：ISR 全宕 → 选落后副本，可用性高但数据可能丢失
4
log.flush — 刷盘策略（可选加强）
Kafka 默认依赖 OS pagecache 异步刷盘，极端断电可能丢最近未落盘的消息。金融级场景可配置同步刷盘，但会显著降低吞吐，通常用三副本+UPS电源代替同步刷盘。
# 每写入 1 条消息强制 fsync（性能代价极大，慎用） log.flush.interval.messages=1 # 推荐：依赖副本冗余保证持久性，不做同步刷盘
CONSUMER CONFIG
消费者手动提交 offset
1
关闭自动提交
自动提交会在 poll 后的后台定时提交，消息拿到了但业务还没处理完就提交了 offset，此时消费者崩溃就永久丢失这条消息。
props.put("enable.auto.commit", false);
2
处理完业务逻辑后再提交
业务处理成功后才调用 commitSync()。异常时不提交，下次 poll 会重新消费（需业务幂等兜底）。
ConsumerRecords<K,V> records = consumer.poll(Duration.ofMillis(100)); for (ConsumerRecord<K,V> record : records) { process(record); // 先处理业务 } consumer.commitSync(); // 全部处理完再提交
3
失败重试 + 死信队列
处理失败的消息进入重试队列，重试 N 次仍失败则投入死信队列（DLQ），人工介入或异步补偿，彻底避免消息静默丢失。
注意

消息不丢 vs 消息不重：二者是对立的。acks=all + 重试会导致重复投递，手动提交 offset + 处理失败重试也会重复。所以「消息不丢」必须配合「消费幂等」一起做，不能只解决一端。

Idempotency · 幂等
面试这样说

幂等分两层讲：生产者幂等和消费者幂等。

生产者幂等是 Kafka 原生支持的，开启 enable.idempotence=true，每个 Producer 启动时 Broker 分配一个 PID，每条消息带序列号，Broker 用「PID + Partition + SeqNo」去重，同一条消息重试多少次都只写一条。但注意这只在单 Partition 单会话内有效，Producer 重启后 PID 会变，要全局精确一次需要用 Kafka 事务。

消费者幂等是业务层的事，Kafka 本身不负责。常见方案是：给每条消息带一个全局唯一 ID，消费前先用 Redis SETNX 或数据库唯一索引查一下有没有消费过，处理完再标记。我们线上用的是消息 ID + 数据库唯一索引兜底 + Redis 快速过滤的组合方案。

PRODUCER
Kafka 原生幂等 — PID + Sequence Number
1
开启幂等 Producer
enable.idempotence=true，Broker 为每个 Producer 分配唯一 PID，每条消息附带单调递增 Sequence Number。
2
Broker 去重
Broker 对每个 PID + Partition 维护最近写入的 SeqNo 滑动窗口（默认 5 条），SeqNo 重复或乱序的消息直接丢弃，向 Producer 返回成功响应。
// Broker 内部去重逻辑（简化） if (seqNo == lastSeqNo[pid][partition] + 1) { write(message); // 正常写入 } else if (seqNo <= lastSeqNo[pid][partition]) { return ACK; // 重复，幂等丢弃 } else { throw OutOfOrderSequenceException; // 乱序，报错 }
3
跨 Session 精确一次 — 事务 API
Producer 重启后 PID 会变，单靠幂等 Producer 无法跨会话去重。需用 Kafka 事务（transactional.id）绑定固定逻辑 ID，实现跨重启的精确一次语义。
props.put("transactional.id", "order-producer-1"); // 固定逻辑 ID，重启不变 producer.initTransactions(); producer.beginTransaction(); producer.send(new ProducerRecord<>("order-topic", orderId, payload)); producer.commitTransaction(); // 原子提交，失败可 abortTransaction()
CONSUMER
业务层幂等方案 — 三道防线
1
全局唯一消息 ID
生产端给每条消息打上全局唯一 ID（雪花算法 / UUID），消费端以此 ID 为去重 Key。核心前提：没有唯一 ID，后续所有去重策略都无从建立。
2
第一道防线 — Redis SETNX 快速过滤
消费前先执行 SETNX msgId 1 EX 300，返回 0 说明已消费，直接跳过，避免后续业务逻辑和 DB 操作。绝大多数重复请求在这里被拦截，性能最好。
Boolean isNew = redis.setIfAbsent("idempotent:msg:" + msgId, "1", 5, TimeUnit.MINUTES); if (Boolean.FALSE.equals(isNew)) { log.info("重复消息，跳过: {}", msgId); return; // 已消费，幂等退出 } doProcess(msg); // 首次消费，执行业务
3
第二道防线 — DB 唯一索引兜底
业务表或消费日志表对 msg_id 加唯一索引，INSERT IGNORE 即使 Redis 故障或 TTL 过期也能保证不重复写入，是最终的强一致性保障。
-- 消费日志表（唯一索引保障） INSERT IGNORE INTO msg_consume_log(msg_id, topic, created_at) VALUES (?, ?, NOW()); -- 重复插入自动忽略，影响行数=0 即为重复 -- 或：幂等 UPDATE（利用业务状态） UPDATE orders SET status = 'PAID', paid_at = NOW() WHERE order_id = ? AND status = 'UNPAID'; -- WHERE 自然幂等
4
第三道防线 — 状态机 + 乐观锁
业务状态有合法流转路径（未支付 → 已支付 → 已发货），重复消费「支付成功」消息时，WHERE status='UNPAID' 自然不命中，受影响行数为 0，天然幂等。结合乐观锁（version 字段）还能防并发竞争。
int affected = orderDao.updateStatus(orderId, "PAID", "UNPAID"); // 乐观锁 if (affected == 0) { log.warn("状态流转失败，可能是重复消费: orderId={}", orderId); return; // 幂等退出，不报错 }
方案适用场景优点缺点
Redis SETNX 高并发、消息量大 毫秒级过滤，性能好 Redis 故障时降级，需 TTL 管理
DB 唯一索引 对数据一致性要求高 强一致，无额外依赖 写 DB 有压力，高并发下锁竞争
状态机检查 有状态流转的业务 业务语义清晰，零额外存储 需设计好状态机，不适用无状态消息
Kafka 事务 Kafka→Kafka 流处理 原生精确一次语义 性能损耗大，配置复杂
大厂实践

美团、字节等大厂通常用 Redis 快过滤 + DB 唯一索引兜底的双重方案：Redis 负责 99% 的重复过滤（性能），DB 唯一索引负责 Redis 故障或 TTL 过期后的最终一致性（正确性）。二者缺一不可。

Ordered Consumption · 顺序消费
面试这样说

Kafka 的顺序保证是 Partition 级别的，同一个 Partition 内消息是有序的，不同 Partition 之间无序。所以要实现业务顺序消费，核心思路是把同一业务 key 的消息路由到同一个 Partition。

生产侧：发消息时指定 key（比如 orderId），Kafka 默认 Partitioner 会对 key 取 hash 再取模，保证同一个 key 永远进同一个 Partition。

消费侧：一个 Partition 在 Consumer Group 里只能被一个 Consumer 消费，这是 Kafka 保证的。但消费者内部如果用多线程处理，就可能乱序。所以要么单线程消费，要么做一层内存有序队列——按 key 再 hash 到不同线程，同一 key 的消息始终由同一线程处理。

全局有序（所有消息都有序）只能用单 Partition，但吞吐量会大幅下降，实际业务很少这么做。绝大多数场景只需要局部有序，按 orderId、userId 这类 key 分 Partition 就够了。

顺序消费 — key → Partition → Consumer → 线程 路由全链路
DESIGN
局部有序完整方案
1
生产者：按业务 key 路由到固定 Partition
发消息时带上业务 key（orderId / userId），Kafka 默认 DefaultPartitioner 对 key 做 murmur2 hash 取模，相同 key 永远进相同 Partition。
ProducerRecord<String, String> record = new ProducerRecord<>("order-topic", orderId, payload); // orderId 作为 key，相同订单消息落同一 Partition producer.send(record);
2
Kafka 保证：同 Partition 只分配给一个 Consumer
Consumer Group 内，Partition 的分配是互斥的，同一 Partition 不会同时被两个消费者消费（Rebalance 期间短暂例外）。Partition 内消息按写入顺序投递。
Topic: order-topic (Partitions: 0 ~ 7) Consumer Group: order-service Consumer-A → Partition [0, 1] Consumer-B → Partition [2, 3] Consumer-C → Partition [4, 5, 6, 7] // 同一 Partition 内严格有序
3
消费者内部：同 key 路由同一线程
单 Partition 单线程消费，吞吐够了就不用多线程。若需提升吞吐，对 key 再 hash 分发到有序内存队列 + 固定线程，保证同 key 的消息由同一线程串行执行。
// 消费者内部按 key hash 到不同线程 int threadIdx = Math.abs(orderId.hashCode() % threadPool.size()); threadQueues[threadIdx].offer(record); // 同 orderId → 同队列 → 同线程
4
Rebalance 期间的有序保证
Rebalance 时 Partition 会在 Consumer 间重新分配，期间可能短暂乱序或重复投递。
处理方式：① 消费者实现 ConsumerRebalanceListener，rebalance 前 commitSync 当前进度；② 结合幂等，重复消费的消息不产生副作用。
全局有序
单 Partition
所有消息严格有序，吞吐受限
  • Topic 只设 1 个 Partition
  • Consumer Group 只有 1 个消费者有效
  • 吞吐量 = 单 Partition 上限（约百 MB/s）
  • 适合：数据库 binlog 同步、配置变更广播
  • 不适合：高并发订单、用户行为流
局部有序（推荐）
按业务 key 分 Partition
同 key 有序，高吞吐，生产主流方案
  • N 个 Partition，同 key → 同 Partition
  • 吞吐 = N 倍单 Partition（水平扩展）
  • 适合：订单状态流转、用户操作序列
  • 注意：扩 Partition 后 key 路由会变，需滚动迁移
  • 热点 key 可能导致 Partition 不均，需监控
常见误区

扩 Partition 会破坏有序性：增加 Partition 数后，同一 key 的 hash 取模结果变了，历史消息在旧 Partition，新消息在新 Partition，导致乱序。线上操作前要评估影响，通常需要等旧 Partition 消费完再扩，或通过业务层 rebalance key 路由策略。

Election · 集群选举机制
面试这样说

Kafka 的"选举"其实有两层，面试前最好先弄清楚哪层，或者直接开口就说"Kafka 里有两种选举，我分开说"。

Controller 选举——选的是"集群协调者"，整个集群只有一个 Active Controller。ZK 模式下，所有 Broker 抢着在 ZooKeeper 里创建 /controller 临时节点，先到先得。Controller 宕机后要等 ZK session 超时（默认 18s）节点才消失，然后重新抢，整个过程秒级。KRaft 模式改用 Raft 投票，毫秒级完成，还彻底去掉了 ZooKeeper 依赖。

Partition Leader 选举——选的是"某个分区由谁处理读写"，这才是真正影响我们代码的部分。某台 Broker 宕了，Controller 立刻遍历它上面所有的 Leader 分区，每个分区从 ISR（同步副本列表）里选第一个存活的副本做新 Leader。ISR 里的副本保证数据没有落后，所以不会丢消息。如果 ISR 全空，就看 unclean.leader.election.enable——false 保数据但分区 offline，true 保可用但可能丢消息。

最容易被追问的一个点：两种选举是独立触发的。普通 Broker 挂了，只有 Partition Leader 选举；Controller 所在的 Broker 宕机才有 Controller 选举，如果它同时持有 Leader 分区，就是先选出新 Controller、再由新 Controller 补选 Partition Leader，顺序发生，不是同时。

CONTROLLER
Controller 选举 — ZK 模式 vs KRaft 模式
1
Controller 的职责（先背下来，是后续所有问题的基础）
集群中有且只有一个 Active Controller，它做三件事：
① Partition Leader 选举——哪台 Broker 挂了，由 Controller 触发受影响分区重选 Leader
② Broker 上下线感知——监控所有 Broker 存活，挂了立刻感知并处理
③ 元数据管理——维护分区副本分配、Leader 信息，并广播给所有 Broker

注意：Controller 本身也只是一个普通 Broker 兼了这个"管理员角色"（ZK 模式），所以它挂了，既要重新选 Controller，也可能要重选 Partition Leader。
2
ZK 模式：临时节点抢占（5步）
理解原理比背步骤重要，核心是 ZooKeeper 临时节点的特性——谁创建了它谁就是 Controller，创建者连接断了节点自动消失。
① 正常状态：ZK 中存在 /controller 节点，由当前 Controller 持有 内容：{"brokerid": 2, "epoch": 5, ...} 所有 Broker 对该节点注册 Watcher 监听 ② Controller（Broker-2）宕机 → 与 ZK 的 TCP 连接断开 → ZK 等待 session.timeout（默认 18s）确认超时 → 自动删除 /controller 临时节点 ③ 所有 Broker 收到 Watcher 通知：/controller 节点没了！ ④ 抢占注册（原子操作，先到先得） Broker-0：create /controller → 成功 ✓ → 新 Controller，epoch=6 Broker-1：create /controller → NodeExistsException → 注册 Watcher 等待 ⑤ 新 Controller（Broker-0）从 ZK 读取全量集群元数据，开始工作 // 总耗时 ≈ ZK session 超时时间（最长 18s）+ 选举时间 ≈ 秒级
面试追问："为什么要等 18s？" — ZK session 超时是 ZK 为了区分"网络短暂抖动"和"节点真的挂了"的保护机制，不能缩太短否则误判，不能设太长否则影响可用性。
3
KRaft 模式：Raft 投票（Kafka 3.3+ GA）
KRaft 用 Raft 共识协议替代 ZK，有几个独立的 Controller 节点组成 Quorum（仲裁组，通常 3 或 5 个）：
正常状态： Active Controller = Raft Leader，其余 = Raft Follower Active Controller 定期向 Follower 发 Raft 心跳 元数据写入 __cluster_metadata 内部 Topic（Raft Log） Active Controller 宕机： Follower 检测到心跳超时（毫秒级，远小于 ZK session 超时） → 自增 term（类比 ZK 的 epoch） → 发送 RequestVote 给其他 Controller 节点 → 先拿到多数票（n/2 + 1）的节点当选 Active Controller // 耗时：毫秒级 ✓ 无 ZK session 超时等待
关键改进：① 去掉 ZK 外部依赖；② Failover 秒级 → 毫秒级；③ Partition 上限从 ~20 万提升至百万级（ZK 的性能瓶颈消失了）。生产部署推荐 Isolated 模式，Controller 节点专用、不承载业务 Partition，这样 Controller 宕机完全不影响 Partition Leader，影响面最小。
PARTITION LEADER
Partition Leader 选举 — 影响代码的核心机制
1
触发条件与完整流程（5步）
任意持有 Leader 分区的 Broker 宕机，Controller 立刻触发：
Step 1 Controller 感知 Broker-2 下线 ZK 模式：/brokers/ids/2 临时节点消失 KRaft：Raft 心跳超时标记下线 Step 2 找出所有 Leader 在 Broker-2 上的 Partition Step 3 对每个 Partition，查 ISR 列表，去掉 Broker-2， 选剩余 ISR 中第一个存活节点为新 Leader P0: ISR=[0,1,2] → 去掉2 → 选 Broker-0 ✓ Step 4 Leader Epoch + 1，写元数据（ZK 节点 or Raft Log） Step 5 广播 LeaderAndIsrRequest → 所有 Broker 更新缓存 Producer/Consumer 下次刷新 Metadata 路由到新 Leader
关键：只从 ISR 里选。ISR 中的副本保证数据与 Leader 完全同步（没有落后超过 replica.lag.time.max.ms），所以选 ISR 中的节点就不会丢失已提交的消息。
2
Unclean Leader Election — 一道高频追问
问题场景：某分区的 ISR 全挂了，只有落后很多的 out-of-sync 副本活着，要不要让它当 Leader？
unclean.leader.election.enable = false // 默认，推荐 // ISR 全空 → 该分区持续 offline，拒绝读写 // 优点：已提交数据绝对不丢（CP 选择） // 代价：分区不可用，Producer 收到 NotEnoughReplicasException unclean.leader.election.enable = true // 让 out-of-sync 副本当 Leader → 分区恢复可用 // 代价：该副本落后的那部分消息（HW 到旧 Leader LEO 之间）永久丢失（AP 选择） // 适合：日志/埋点等可接受少量丢失的业务
面试答法：这是可用性（AP）vs 数据完整性（CP）的经典取舍。金融/订单类业务选 false，宁可短暂不可用也不能丢消息；日志类业务可以接受 true。
3
Leader Epoch — 为什么需要它（理解比背更重要）
0.11 之前，Follower 重启后按 HW（High Watermark） 截断日志。这会造成两个 Bug：

• 数据丢失：Follower 截断到 HW，随后成为新 Leader，旧 Leader 在 HW 之后写的消息就消失了
• 数据不一致：两个副本先后宕机再恢复，同一 offset 可能存了不同内容（日志"分叉"）

0.11 引入 Leader Epoch 修复：每次 Leader 切换 epoch 自增。Follower 重启不再盲目截断到 HW，而是先问新 Leader "epoch N 结束在哪个 offset"，按精确位置截断。
Follower 重启 → 发送 OffsetsForLeaderEpoch(epoch=5) 新 Leader → 回复 endOffset=100 Follower → 将 log 精确截断到 offset 100，然后从 101 继续同步 // 不再依赖 HW，epoch 给每次 Leader 切换打上精确边界
4
选举期间你的代码会发生什么
Leader 选举过程中，该分区短暂没有 Leader，Producer 和 Consumer 请求会收到 NotLeaderOrFollowerException。配置正确则客户端完全自动恢复：
// Producer 配置（保证选举期间自动重试不丢消息） props.put("retries", Integer.MAX_VALUE); props.put("delivery.timeout.ms", "120000"); // 总兜底 2min props.put("retry.backoff.ms", "200"); // 重试间隔 200ms props.put("enable.idempotence", "true"); // 幂等，重试不重复 // Consumer 自动刷新 Metadata，找到新 Leader 继续消费，无需特殊处理 // KRaft 模式 Failover 毫秒级，客户端通常感知不到；ZK 模式秒级，重试几次即可恢复
