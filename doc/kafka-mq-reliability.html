Message Backlog · 消息积压
面试这样说

消息积压的根本原因就是生产速度远大于消费速度，我一般从三个层面去分析：是消费者挂了、消费逻辑太慢，还是突发流量打进来了。

紧急预案是先扩容消费者实例，Kafka 一个 Partition 只能对应 Consumer Group 里的一个消费者，所以要同时扩 Partition 数。如果积压量极大，我们会建临时 Topic，把原 Topic 的消息先用一个轻量 Consumer 快速转发进去，临时 Topic 开 10 倍分区数，再拉起大量 Consumer 并行消费。

非核心消息可以选择降级——比如日志类、统计类消息积压了就直接丢弃，优先保核心链路。

长期来看要复盘：批量拉取调大 max.poll.records、消费端异步化、或者从业务上做流量整形。

消息积压 — 临时 Topic 扩容分流方案
PLAN-A
紧急扩容处理流程
1
告警触发 — 定位积压原因
监控 消费者 Lag（consumer_lag），看是所有分区均匀积压（流量暴增）还是个别分区（消费者挂了）。
同时看消费者进程 CPU / GC 情况，排除消费逻辑耗时暴涨。
2
扩容消费者 + 扩分区
增加 Consumer Group 实例数。若实例数已 = Partition 数，先扩 Partition（注意：分区数只能增不能减，key 路由会变，需业务评估）。
黄金比例：Consumer 实例数 = Partition 数，充分并行。
# 动态增加分区（慎用，会影响 key 路由） kafka-topics.sh --alter --topic your_topic \ --partitions 30 --bootstrap-server broker:9092
3
极端积压 — 临时 Topic 分流
原 Topic 积压 1000 万条，建 临时 Topic（30 分区），用一个专门的转发 Consumer 快速把消息搬过去（只转发不处理），再起 30 个消费者并行消费临时 Topic，积压消化后下线临时资源。
原 Topic (3分区) ──→ 转发Consumer ──→ 临时Topic (30分区) └──→ 30 个 Consumer 并行消费
4
降级处理非核心消息
区分消息优先级。日志、埋点等非核心消息积压时直接 丢弃或延迟消费，保证订单、支付等核心 Topic 的资源。
5
事后优化
调大 max.poll.records 批量拉取；消费侧引入内存队列 + 线程池异步处理；评估是否需要拆 Topic、做流量整形（令牌桶限速生产方）。
常见根因
为什么会积压
优先排查这几点
  • 消费者实例挂了，Lag 急速上涨
  • 下游依赖慢（DB 慢查询、RPC 超时）
  • 消息体过大，反序列化耗时高
  • GC 停顿导致 poll 间隔超 session.timeout
  • 突发流量，生产侧没有限速
预防手段
降低积压概率
长期架构改进
  • 监控 Lag，提前预警（阈值 = 5min 消费量）
  • 消费者批量拉取 + 异步线程池处理
  • 生产侧限速（令牌桶），削峰填谷
  • 按消息优先级设独立 Topic
  • 定期演练扩容流程，保留临时扩容脚本
Message Durability · 消息不丢
面试这样说

消息不丢需要从三个阶段分别保证：生产者发送阶段、Broker 存储阶段、消费者处理阶段。每个阶段都有可能丢。

生产者阶段：把 acks 设成 all（-1），这样 Leader 和所有 ISR 副本都写入后才返回成功。同时开启 enable.idempotence，重试时不会重复写入。

Broker 阶段：副本数设 3，min.insync.replicas 设 2，这样只要有两个副本在线就能保证数据不丢。还要关掉 unclean.leader.election，防止落后的副本当选 Leader 造成数据回退。

消费者阶段：把 enable.auto.commit 关掉，改成手动提交 offset。业务处理完成后再 commit，防止"拿到消息但没处理完就提交了 offset"这种情况导致消息丢失。

① PRODUCER
生产者阶段
  • acks=all 等待所有 ISR 确认
  • retries=MAX 失败自动重试
  • 幂等Producer 重试不重复
  • 同步发送 核心消息用 get() 阻塞
② BROKER
Broker 存储阶段
  • replication.factor=3 三副本
  • min.insync.replicas=2
  • 关闭 unclean 选举防数据回退
  • 刷盘策略 重要场景同步刷盘
③ CONSUMER
消费者阶段
  • 关闭自动提交 offset
  • 业务处理完再 commit
  • 异常时不 commit，触发重新消费
  • 结合幂等处理重复投递
消息不丢 — 三阶段失效点与防护措施
PRODUCER CONFIG
生产者不丢消息核心配置
1
acks=all — 强确认
Leader 收到消息后，等待所有 ISR（In-Sync Replica）副本全部写入才返回 ACK。若 ISR 中有副本宕机，写入会失败而非静默丢失。
props.put("acks", "all"); props.put("retries", Integer.MAX_VALUE); props.put("enable.idempotence", true); // 幂等Producer，防重试导致重复 props.put("max.in.flight.requests.per.connection", 5);
2
核心消息同步等待确认
支付、订单等核心业务用 Future.get() 阻塞等待，确认写入成功再返回给上游。异步回调适合日志类消息。
RecordMetadata meta = producer.send(record).get(); // 阻塞等确认 // 失败抛异常，业务层捕获后告警 / 重试 / 写补偿表
3
事务消息（RocketMQ 方案）
本地数据库操作和消息发送需要原子性时，用 RocketMQ 事务消息。半事务消息 → 执行本地事务 → commit/rollback，Broker 定时回查保证最终一致。
// RocketMQ 事务消息流程 发送半事务消息(PREPARED) → 执行本地事务(扣库存/更新订单) → commit → Broker 投递消费者 → rollback → Broker 删除消息 → 超时未响应 → Broker 回查本地事务状态
CONSUMER CONFIG
消费者手动提交 offset
1
关闭自动提交
自动提交会在 poll 后的后台定时提交，消息拿到了但业务还没处理完就提交了 offset，此时消费者崩溃就永久丢失这条消息。
props.put("enable.auto.commit", false);
2
处理完业务逻辑后再提交
业务处理成功后才调用 commitSync()。异常时不提交，下次 poll 会重新消费（需业务幂等兜底）。
ConsumerRecords<K,V> records = consumer.poll(Duration.ofMillis(100)); for (ConsumerRecord<K,V> record : records) { process(record); // 先处理业务 } consumer.commitSync(); // 全部处理完再提交
3
失败重试 + 死信队列
处理失败的消息进入重试队列，重试 N 次仍失败则投入死信队列（DLQ），人工介入或异步补偿，彻底避免消息静默丢失。
注意

消息不丢 vs 消息不重：二者是对立的。acks=all + 重试会导致重复投递，手动提交 offset + 处理失败重试也会重复。所以「消息不丢」必须配合「消费幂等」一起做，不能只解决一端。

Idempotency · 幂等
面试这样说

幂等分两层讲：生产者幂等和消费者幂等。

生产者幂等是 Kafka 原生支持的，开启 enable.idempotence=true，每个 Producer 启动时 Broker 分配一个 PID，每条消息带序列号，Broker 用「PID + Partition + SeqNo」去重，同一条消息重试多少次都只写一条。但注意这只在单 Partition 单会话内有效，Producer 重启后 PID 会变，要全局精确一次需要用 Kafka 事务。

消费者幂等是业务层的事，Kafka 本身不负责。常见方案是：给每条消息带一个全局唯一 ID，消费前先用 Redis SETNX 或数据库唯一索引查一下有没有消费过，处理完再标记。我们线上用的是消息 ID + 数据库唯一索引兜底 + Redis 快速过滤的组合方案。

PRODUCER
Kafka 原生幂等
1
开启幂等 Producer
enable.idempotence=true，Broker 为每个 Producer 分配唯一 PID，每条消息附带单调递增 Sequence Number。
2
Broker 去重
Broker 对每个 PID + Partition 维护最近写入的 SeqNo 窗口，重复消息被直接丢弃不写入，返回成功响应。
3
跨 Session 精确一次 — 事务 API
Producer 重启 PID 变化，需用 Kafka 事务（transactional.id）实现跨会话精确一次语义。
props.put("transactional.id", "order-producer-1"); producer.initTransactions(); producer.beginTransaction(); producer.send(record); producer.commitTransaction();
CONSUMER
业务层幂等方案
1
全局唯一消息 ID
生产端给每条消息打上全局唯一 ID（雪花算法 / UUID），消费端用此 ID 做去重 Key。
2
Redis SETNX 快速过滤
消费前先 SETNX msgId 1 EX 300，返回 0 说明已消费，直接跳过。Redis 做第一道快速拦截。
Boolean ok = redis.setIfAbsent("msg:" + msgId, "1", 5, MINUTES); if (!ok) return; // 已消费，跳过 doProcess(msg);
3
DB 唯一索引兜底
业务表对 msg_id 加唯一索引，INSERT IGNORE 或 ON DUPLICATE KEY UPDATE，从存储层保证不重复写入。
INSERT IGNORE INTO order_consume_log(msg_id, ...) VALUES(?, ...); -- 或：幂等 UPDATE UPDATE orders SET status=2 WHERE id=? AND status=1;
4
状态机 + 乐观锁
订单状态有合法流转路径（未支付→已支付→已发货），重复消费「支付成功」消息时，WHERE status=未支付 自然不命中，天然幂等。
方案适用场景优点缺点
Redis SETNX 高并发、消息量大 毫秒级过滤，性能好 Redis 故障时降级，需 TTL 管理
DB 唯一索引 对数据一致性要求高 强一致，无额外依赖 写 DB 有压力，高并发下锁竞争
状态机检查 有状态流转的业务 业务语义清晰，零额外存储 需设计好状态机，不适用无状态消息
Kafka 事务 Kafka→Kafka 流处理 原生精确一次语义 性能损耗大，配置复杂
大厂实践

美团、字节等大厂通常用 Redis 快过滤 + DB 唯一索引兜底的双重方案：Redis 负责 99% 的重复过滤（性能），DB 唯一索引负责 Redis 故障或 TTL 过期后的最终一致性（正确性）。二者缺一不可。

Ordered Consumption · 顺序消费
面试这样说

Kafka 的顺序保证是 Partition 级别的，同一个 Partition 内消息是有序的，不同 Partition 之间无序。所以要实现业务顺序消费，核心思路是把同一业务 key 的消息路由到同一个 Partition。

生产侧：发消息时指定 key（比如 orderId），Kafka 默认 Partitioner 会对 key 取 hash 再取模，保证同一个 key 永远进同一个 Partition。

消费侧：一个 Partition 在 Consumer Group 里只能被一个 Consumer 消费，这是 Kafka 保证的。但消费者内部如果用多线程处理，就可能乱序。所以要么单线程消费，要么做一层内存有序队列——按 key 再 hash 到不同线程，同一 key 的消息始终由同一线程处理。

全局有序（所有消息都有序）只能用单 Partition，但吞吐量会大幅下降，实际业务很少这么做。绝大多数场景只需要局部有序，按 orderId、userId 这类 key 分 Partition 就够了。

顺序消费 — key → Partition → Consumer → 线程 路由全链路
DESIGN
局部有序完整方案
1
生产者：按业务 key 路由到固定 Partition
发消息时带上业务 key（orderId / userId），Kafka 默认 DefaultPartitioner 对 key 做 murmur2 hash 取模，相同 key 永远进相同 Partition。
ProducerRecord<String, String> record = new ProducerRecord<>("order-topic", orderId, payload); // orderId 作为 key，相同订单消息落同一 Partition producer.send(record);
2
Kafka 保证：同 Partition 只分配给一个 Consumer
Consumer Group 内，Partition 的分配是互斥的，同一 Partition 不会同时被两个消费者消费（Rebalance 期间短暂例外）。Partition 内消息按写入顺序投递。
Topic: order-topic (Partitions: 0 ~ 7) Consumer Group: order-service Consumer-A → Partition [0, 1] Consumer-B → Partition [2, 3] Consumer-C → Partition [4, 5, 6, 7] // 同一 Partition 内严格有序
3
消费者内部：同 key 路由同一线程
单 Partition 单线程消费，吞吐够了就不用多线程。若需提升吞吐，对 key 再 hash 分发到有序内存队列 + 固定线程，保证同 key 的消息由同一线程串行执行。
// 消费者内部按 key hash 到不同线程 int threadIdx = Math.abs(orderId.hashCode() % threadPool.size()); threadQueues[threadIdx].offer(record); // 同 orderId → 同队列 → 同线程
4
Rebalance 期间的有序保证
Rebalance 时 Partition 会在 Consumer 间重新分配，期间可能短暂乱序或重复投递。
处理方式：① 消费者实现 ConsumerRebalanceListener，rebalance 前 commitSync 当前进度；② 结合幂等，重复消费的消息不产生副作用。
全局有序
单 Partition
所有消息严格有序，吞吐受限
  • Topic 只设 1 个 Partition
  • Consumer Group 只有 1 个消费者有效
  • 吞吐量 = 单 Partition 上限（约百 MB/s）
  • 适合：数据库 binlog 同步、配置变更广播
  • 不适合：高并发订单、用户行为流
局部有序（推荐）
按业务 key 分 Partition
同 key 有序，高吞吐，生产主流方案
  • N 个 Partition，同 key → 同 Partition
  • 吞吐 = N 倍单 Partition（水平扩展）
  • 适合：订单状态流转、用户操作序列
  • 注意：扩 Partition 后 key 路由会变，需滚动迁移
  • 热点 key 可能导致 Partition 不均，需监控
常见误区

扩 Partition 会破坏有序性：增加 Partition 数后，同一 key 的 hash 取模结果变了，历史消息在旧 Partition，新消息在新 Partition，导致乱序。线上操作前要评估影响，通常需要等旧 Partition 消费完再扩，或通过业务层 rebalance key 路由策略。
