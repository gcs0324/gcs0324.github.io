§1 先区分“顺序约束”和“共享冲突”

同步

多个进程因合作而需要按某个先后顺序推进。例如“生产一个数据项”必须早于“消费这个数据项”。

互斥

多个进程不能同时进入访问同一临界资源的代码区。例如修改共享队列的头尾指针时必须串行。

判断法

先问“我等的是某个条件/数量吗？”——用计数信号量；再问“条件满足后，共享结构能否多人同时修改？”——不能就再用互斥信号量。

§2 P/V 的含义与放置顺序

P(S) / wait(S)

请求一个 S 所代表的资源或通行许可。若当前不可用，记录型信号量会让进程阻塞并进入 S 的等待队列。

V(S) / signal(S)

归还一个资源或发出一次条件已成立的通知。若 S 上有阻塞进程，唤醒其中一个，被唤醒者先进就绪队列。

易错

P/V 必须是原子操作，但“P 之后的整段业务代码”并不自动成为原子操作。互斥是靠其他进程在临界区前也执行同一个 P(mutex) 实现的。

§3 生产者-消费者：三个信号量分别管什么
教程例题 · N 个缓冲格的完整 P/V 设计
有 N=5 个缓冲格，多个生产者向队列放数据，多个消费者取数据。写信号量初值和操作顺序，并说明为什么这样写。
1empty=5 表示初始有 5 个空格；full=0 表示初始没有可消费数据；mutex=1 表示队列结构同时只能被一个进程修改。
2生产者先在自己的私有区域生成数据，然后 P(empty)：它需要一个空格，缓冲区满时应在占用互斥锁之前等待。
3获得空格后再 P(mutex)，把数据写入队列并修改尾指针。这一小段才是临界区。
4写入后先 V(mutex) 离开临界区，再 V(full) 把“可消费数据”增加 1，必要时唤醒消费者。
5消费者对称地先 P(full) 等数据，再 P(mutex) 修改队列，取出后 V(mutex)、V(empty)。真正处理数据应放在锁外，减少占锁时间。
semaphore empty = 5, full = 0, mutex = 1; producer: consumer: item = produce(); P(full); // 先等一个已用格 P(empty); // 先等一个空格 P(mutex); // 再锁队列 P(mutex); // 再锁队列 item = remove(); insert(item); V(mutex); // 先放锁 V(mutex); // 先放锁 V(empty); // 归还空格 V(full); // 公布多一个数据 consume(item);
6检查守恒关系：任意时刻 empty + full = 5，且 mutex 只保护队列修改。若把生产者写成先 P(mutex) 再 P(empty)，缓冲区满时生产者会抱着 mutex 等 empty，消费者又需 mutex 才能取数据，形成死锁。
核心顺序：先申请数量资源，再申请互斥锁；先释放互斥锁，再公布新的资源数量。
短场景 · 读者优先为什么可能让写者饥饿
第一个读者 P(rw)，最后一个读者 V(rw)，其他读者可并发读。若读者持续到达，会发生什么？
1只要读者数 readcount 始终大于 0，“最后一个读者”就还没出现，rw 不会被释放。
2写者在 P(rw) 处持续等待，就是写者饥饿。解决要加入公平排队或写优先机制，不是随意调换两个 V 操作。
读者优先保证读吞吐，但不保证写者有限等待。题目要求“公平”时必须改设计。
§4 死锁的四个必要条件和处理策略

四个条件

  • 互斥：资源不能同时共享使用。
  • 请求并保持：已持有资源时继续等新资源。
  • 不可剥夺：资源只能由持有者主动释放。
  • 循环等待：存在闭环等待链。

四类处理思路

  • 预防：事先破坏四条件之一。
  • 避免：不必破坏条件，每次分配前保证仍处安全状态。
  • 检测与解除：允许发生，定期检测后撤销/抢占。
  • 忽略：发生极少时交给人工处理。
预防方法破坏条件代价
一次申请所有资源请求并保持资源利用率低，也可能饥饿
允许剥夺某些资源不可剥夺只适合可安全恢复的资源
所有进程按资源编号递增申请循环等待限制程序灵活性
§5 银行家算法：安全状态不等于所有进程立即完成
教程例题 · 完整安全性检查
系统有 A/B/C 三类资源，Available=(3,3,2)。已知 Allocation 和 Max 如下，判断当前状态是否安全。
进程AllocationMaxNeed = Max - Allocation
P0(0,1,0)(7,5,3)(7,4,3)
P1(2,0,0)(3,2,2)(1,2,2)
P2(3,0,2)(9,0,2)(6,0,0)
P3(2,1,1)(2,2,2)(0,1,1)
P4(0,0,2)(4,3,3)(4,3,1)
1先逐项算 Need = Max - Allocation。安全性检查的问题是：现有的 Work 能否先满足某个进程全部剩余需求，让它完成并归还已占有资源。
2初始 Work=(3,3,2)。P1 的 Need=(1,2,2) 每一维都 ≤ Work，所以可先完成 P1。它完成后归还 Allocation=(2,0,0)，新 Work=(5,3,2)。
3现在 P3 的 Need=(0,1,1) ≤ (5,3,2)，完成并归还 (2,1,1)，Work=(7,4,3)。
4P4 的 Need=(4,3,1) ≤ (7,4,3)，完成后归还 (0,0,2)，Work=(7,4,5)。
5P0 的 Need=(7,4,3) ≤ (7,4,5)，完成后归还 (0,1,0)，Work=(7,5,5)。
6P2 的 Need=(6,0,0) ≤ (7,5,5)，完成后归还 (3,0,2)，Work=(10,5,7)。全部进程都能依次完成。
安全序列之一：P1 → P3 → P4 → P0 → P2，因此当前状态安全。最终 Work=(10,5,7) 等于系统总资源，可作为反向检查。
不等于死锁

“当前没找到安全序列”表示不安全，不表示此刻已经死锁；它表示未来存在进入死锁的可能。银行家算法通过拒绝某些分配保持安全状态。

§6 速记、易错与考试型练习

拿分清单

  • P 是申请/等待，V 是释放/通知。
  • 先 P 数量资源，再 P 互斥锁，避免抱锁等条件。
  • 不同资源类型的 P 顺序可导致死锁；V 顺序多影响并发度。
  • 安全序列是“可以这样完成”，不是实际调度顺序。
  • 不安全不等于已死锁。

C 类不深挖

  • 某个内核的读写锁源码。
  • 复杂无锁数据结构与 ABA 问题。
  • 分布式死锁检测算法。
  • 实时系统优先级继承实现细节。
考试型练习 · 哲学家如何破坏循环等待
5 名哲学家都先取左筷再取右筷可能死锁。如果规定奇数号先取左筷，偶数号先取右筷，为什么能避免原来的死锁？
1全员同方向取筷时，可形成 P0 等 P1、P1 等 P2…P4 等 P0 的闭环。
2奇偶号改为相反顺序后，相邻哲学家会竞争同一根作为“第一根”的筷子，至少有人在未持有任何筷子时等待。
3因此不能出现“每人都持有一根并等下一根”的完整循环等待链。
该方案通过打破统一的环形申请顺序，破坏循环等待。
