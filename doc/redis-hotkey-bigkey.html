SDS · Simple Dynamic String
面试这样说

Redis 没有直接用 C 语言的字符串，而是自己封装了一个 SDS。C 字符串有几个明显的缺陷。

第一，O(1) 获取长度。C 字符串获取长度要遍历到 \0 才行，是 O(N) 的，SDS 在头部直接记录了 len，O(1) 就能拿到。

第二，二进制安全。C 字符串遇到 \0 就认为字符串结束了，SDS 用 len 来判断边界，可以存图片、序列化对象这类任意二进制数据。

第三，内存预分配。字符串小于 1MB 时扩容多分配一倍空间，大于等于 1MB 时多分配 1MB。缩短时不立即释放，记录进 free 留给下次用。频繁修改时 realloc 次数大幅减少。

第四，自动选头部宽度。根据长度自动选 sdshdr5 / 8 / 16 / 32 / 64，短字符串头部几乎零浪费。

// SDS 结构（简化） struct sdshdr { int len; // 已用长度 — O(1) 获取 int free; // 剩余空间 — 惰性释放 char buf[]; // 实际数据 — 二进制安全 };
优势
相比 C 字符串
四个核心改进
  • O(1) 获取长度，无需遍历
  • 二进制安全，可存任意数据
  • 预分配+惰性释放，减少 realloc
  • 自动选头宽，短字符串省内存
预分配规则
扩容策略
修改时触发
  • 新长度 < 1MB：额外多分配同等大小
  • 新长度 ≥ 1MB：额外多分配 1MB
  • 缩短时：不释放，记入 free 字段
  • 下次扩容优先用 free，避免 realloc
Skiplist · 跳跃表
面试这样说

跳跃表是 Redis Sorted Set 在数据量大时用的底层结构，可以理解成一个多层的有序链表。

最底层是完整的有序链表，上面的层是逐渐稀疏的索引，每个节点随机决定自己能到达哪一层，晋升概率是 25%，最多 32 层。查找从最高层开始，快速定位大概范围，然后逐层向下收窄，平均复杂度 O(log N)。

最大优势是范围查询特别方便。找到起始位置后直接沿底层链表顺序往后走，ZRANGE、ZRANGEBYSCORE 都是这个原理。红黑树做范围查询需要中序遍历，实现复杂很多。

ZSet 里跳跃表和 hashtable 是双索引并存的。跳跃表负责按 score 排序，支持范围查询；hashtable 负责 member→score 映射，让 ZSCORE 达到 O(1)。两个结构共享 member 字符串指针，不重复存储数据。

Quicklist · 快速列表
面试这样说

quicklist 是 Redis List 大规模时的底层结构，本质是双向链表加 listpack 的组合。

纯链表的问题是每个节点单独分配内存，碎片多，CPU 缓存命中率低。纯数组（旧版 ziplist）有连锁更新问题——每个 entry 存前驱长度，修改一个元素可能导致后续所有 entry 级联重分配，最坏 O(N²)。

quicklist 的思路是把链表每个节点换成一个 listpack 页，默认每页最多 128 个元素，页内连续内存，页之间链表连接。listpack 改为每个 entry 只记录自身长度，修改互不影响，彻底解决连锁更新。

还支持对中间节点做 LZF 压缩，两端不压缩保证热点访问速度，中间冷数据压缩节省内存，用 list-compress-depth 控制。

head ←→ [listpack页] ←→ [listpack页] ←→ [listpack页] ←→ tail ↓ ↓ ↓ 连续内存 连续内存 连续内存 ≤128 elem ≤128 elem ≤128 elem (可 LZF 压缩中间节点，两端不压缩)
解决的问题
两全其美
链表 + 数组各取所长
  • 链表碎片多 → listpack 连续内存，缓存友好
  • ziplist 连锁更新 → entry 只存自身长度，互不影响
  • 头尾仍然 O(1)，LPUSH/RPOP 不移动其他数据
  • 中间节点 LZF 压缩，冷数据省内存
三者对比
SDS / Skiplist / Quicklist
核心思路
  • SDS：记元数据+预分配，解决字符串基础问题
  • Skiplist：多层索引以空间换时间，范围查询快
  • Quicklist：链表分段+连续内存，两个问题一起解
  • 共同点：用额外结构/元数据换性能
热Key · Hot Key
面试这样说

热 Key 就是某个 Key 被大量请求集中访问，导致它所在的 Redis 节点 CPU 或带宽被打满，影响整个节点上其他 Key 的正常访问。典型场景是秒杀活动的商品详情、微博热搜、春节红包等。

DETECT
先定位热 Key
1
redis-cli --hotkeys
Redis 4.0+ 内置统计，需开启 maxmemory-policy allkeys-lfu
redis-cli --hotkeys
2
实时 monitor（慎用生产）
有性能损耗，仅用于紧急排查
redis-cli monitor | grep -i "get\|set"
3
SDK 客户端埋点（推荐）
在请求链路上统计各 Key 频次，无性能损耗，大厂标配
SOLUTION
解决方案（由浅入深）
①
本地缓存（最有效）
请求先打本地 JVM 缓存（Caffeine），设 3~5s 短 TTL。对 Redis 的请求量能降 90%+。缺点是各机器数据可能不一致，适合商品详情、配置项等对实时性要求不高的场景。
Cache<String, Object> localCache = Caffeine.newBuilder() .expireAfterWrite(5, TimeUnit.SECONDS) .maximumSize(1000) .build(); Object val = localCache.get(key, k -> redisTemplate.opsForValue().get(k));
②
Key 拆分复制（读多写少）
复制成 N 份分散到不同节点，读时随机取一份。写时同步更新所有副本。Redis Cluster 下不同 Key 落不同 slot，自然分散。
// 写：复制 N 份 for (int i = 0; i < N; i++) redis.set("hot_key_" + i, value); // 读：随机选一份 String key = "hot_key_" + ThreadLocalRandom.current().nextInt(N);
③
异步预热 + 定时刷新
对可预测的热点（大促前商品、榜单）提前加载到本地缓存，后台线程定时刷新，避免高峰时集中击打 Redis。
④
限流 + 降级兜底
超过阈值直接返回默认值或上次缓存值，防止 Redis 被打挂。
if (!rateLimiter.tryAcquire()) return defaultValue; // 降级 return redis.get(key);
场景推荐方案
读多写少（商品、配置）本地缓存 + 短 TTL
秒杀 / 活动热点Key 拆分复制 + 本地缓存
实时排行榜读写分离 + 多从库
突发不可预测流量限流 + 降级兜底
大Key · Big Key
面试这样说

大 Key 是指 Value 体积很大，或者集合类型里元素数量非常多，比如一个 Hash 里几十万个字段，或者一个 String 的 Value 有几十 MB。

危害
三个核心问题
  • 读写慢阻塞：Redis 单线程，读几十 MB 可能耗时几十 ms，期间其他命令全被阻塞
  • DEL 危险：直接删除大 Key 会阻塞主线程，生产事故的常见来源
  • 带宽撑满：大 Value 传输占用大量网络带宽，影响同机其他服务
解决思路
化整为零
  • 拆分：String 分片为多个小 Key，Hash 按模分桶
  • 压缩：gzip / snappy 压缩 Value，JSON 文本压缩比可达 5~10x
  • UNLINK 异步删除：4.0+ 必用，内存回收放后台线程
  • 对象卸载：大 Value 存 OSS/S3，Redis 只存 URL
DELETE
大 Key 安全删除流程
1
String 类型 → 直接 UNLINK
UNLINK big_key # 异步删除，不阻塞主线程（禁用 DEL）
2
Hash / Set / ZSet → 先分批清成员，再 UNLINK
# 用 HSCAN 分批删成员，每批 sleep 一下，低峰期执行 cursor = 0 loop: cursor, fields = HSCAN big_hash cursor COUNT 100 if fields: HDEL big_hash fields if cursor == 0: break UNLINK big_hash
3
扫描工具定期治理
redis-cli --bigkeys # 快速扫描 rdb -c memory dump.rdb # RDB 离线深度分析
⚠ 生产规范

删大 Key 一律用 UNLINK 代替 DEL，这是踩过事故之后沉淀下来的硬规范。4.0 以下版本需手动分批 SCAN 删除。

大厂生产实战方案
字节跳动
热Key 自动探测系统
✦
SDK 埋点 → 旁路统计服务 → 自动本地化。Client SDK 上报每个 Key 的访问频次，超过阈值自动触发本地缓存预热，业务方完全无感知。核心思路：不依赖人发现问题，让系统自动发现自动解决。
美团
Squirrel 客户端 + Proxy 双层
✦
Redis 客户端（Squirrel）层拦截热 Key，自动本地缓存几百毫秒。DBProxy 层做热 Key 读写分离路由，打到多个从节点。应急手段：热 Key 所在分片单独迁移到高配机器。
阿里 Tair
内核层 + Proxy 透明缓存
✦
Tair 内核直接支持热 Key 统计（OBJECT FREQ key），无需客户端埋点。支持 Proxy 本地缓存，热 Key 数据缓存在 Proxy 节点，根本不走后端 Redis。Proxy 是集中的，不存在多机数据不一致问题。
滴滴实案
司机实时位置大 Key 拆分
✦
全量司机位置存单个 Geo Key，几十万成员，读取把带宽打满。按城市+区域二级拆分：driver:geo:{cityId}:{gridId}，每格只存周边司机。数据量从几十万降到几百，读取只查周边格子。
趋势

大厂的方向是把能力下沉到基础设施层，业务方无感知。字节在 SDK 层自动探测，阿里在 Proxy 层透明缓存，美团 SDK + Proxy 双层防护。大 Key 的治理重心也从"出问题救火"转向代码 Review 阶段卡写法、上线前扫描预防。

京东 Hotkey 框架
面试这样说

京东把这套东西开源了，叫 hotkey，思路和字节类似但实现细节清晰，可以直接拆开讲。

最巧妙的两点：一是用一致性哈希把同一个 Key 的流量聚合到同一个 Worker，解决分布式环境下统计不准的问题；二是用 Etcd Watch 做广播，Worker 不需要维护 Client 连接，架构非常干净。

业务应用（内嵌 Client SDK） ↓ 上报 key 访问频次（异步批量，本地滑动窗口攒批） Worker 集群（一致性哈希，同一 Key → 同一 Worker，聚合统计） ↓ 发现热 Key，写入 Etcd 集群 ↓ Watch 推送通知（所有 Client 自动收到） 业务应用（Client SDK） → 本地 Caffeine 缓存该 Key 的 Value
FLOW
四步核心流程
1
Client 本地滑动窗口统计，异步批量上报
SDK 拦截每次 Redis 访问，本地用滑动窗口计数，攒一批再异步发给 Worker，不阻塞主线程，业务无感知。
2
Worker 一致性哈希聚合，判断是否热 Key
Client 用一致性哈希把同一个 Key 的数据打到同一个 Worker，避免统计分散不准。Worker 聚合所有应用实例数据，滑动窗口判断是否超阈值。单机看不到热点，聚合后热 Key 就暴露了。
3
写入 Etcd → Watch 广播所有 Client
Worker 发现热 Key 后写入 Etcd。所有 Client 都 Watch 着 Etcd，自动收到推送后立刻本地缓存该 Key。Worker 不需要维护 Client 连接，解耦干净。
4
热 Key TTL 到期 → 清除本地缓存，回归正常
Etcd 记录过期后，Client 收到通知清除本地缓存，恢复正常走 Redis 流程。Value 由 Client 自己第一次访问时去 Redis 取，Worker 不需要知道 Value 内容，职责单一。

一句话

热 Key 核心思路是分散访问压力，本地缓存和 Key 拆分是最常用手段；大 Key 核心思路是化整为零，拆分+压缩，删除必用 UNLINK。两者本质都是单点压力过大，解法都是分而治之。京东 hotkey 是这套思路的标准工程实现，用一致性哈希+Etcd Watch 把探测和通知做成了基础设施。
