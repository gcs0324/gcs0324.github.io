01Prompt 基础
Prompt 的本质

Prompt就是你发给大语言模型（LLM）的输入文本。它不是什么高深的概念——你每次和 ChatGPT 对话时输入的内容就是 Prompt。

从技术角度看，LLM 的本质是一个"下一个 Token 预测器"。给定一串 Token 序列，它会计算下一个 Token 的概率分布。Prompt 就是这个 Token 序列的起点，它决定了模型从哪个方向"续写"。

  • 输入一段自然语言文本（可以包含指令、问题、上下文、示例等）
  • 输出LLM 基于这段输入生成的续写内容
  • 关键点Prompt 的措辞、结构、顺序会直接影响生成结果的质量。同一问题换一种问法，输出可能完全不同
为什么叫"Engineering"：Prompt Engineering 不是简单地"跟 AI 聊天"，而是一套系统化的工程方法论——通过设计、测试、迭代 Prompt 来稳定地获得高质量输出。
好 Prompt 的特征

一个高质量的 Prompt 通常具备以下特征：

  • 明确（Specific）告诉模型具体要做什么，不要模糊。"帮我写个接口"不如"帮我写一个 REST API，GET /api/users/{id}，返回 UserDTO，包含 id、name、email 三个字段"
  • 结构化（Structured）用分隔符、编号、标题组织内容，让模型清楚地识别指令、上下文、输入和输出要求
  • 有约束（Constrained）明确输出格式、长度、语言、风格等限制。"用 Java 编写，使用 Spring Boot 3.x，输出纯代码不要解释"
  • 有示例（Exemplified）给出 1-3 个输入输出示例，让模型理解你想要的模式（即 Few-shot）
  • 分步骤（Step-by-step）复杂任务拆成小步骤，让模型逐步推理，而不是一步到位
记忆口诀：好 Prompt = 明确目标 + 充分上下文 + 输出约束 + 示例参考。
02常用模式
指令型 / 角色型 / 情境型

实际开发中，Prompt 往往是多种模式的组合。以下是最常见的三种基础模式：

模式写法示例适用场景
指令型直接告诉模型做什么，加约束条件"将以下 SQL 转为 MyBatis XML 映射，保留所有注释"格式转换、代码生成、文本处理
角色型先设定模型的角色/身份，再提要求"你是一位有 10 年经验的 Java 架构师，请审查以下代码的设计问题"需要专业判断的场景（代码审查、方案设计）
情境型先描述背景信息，再提出问题"我们团队正在将单体应用拆分为微服务。当前系统是 Spring Boot 单体，数据库是 MySQL。请给出分步拆分方案"需要理解业务上下文的复杂决策

实际使用中，最常见的组合是：角色 + 指令 + 情境。例如："你是一位资深 DBA（角色），请分析以下 SQL 查询慢的原因（指令），当前数据量约 5000 万行，使用 MySQL 8.0（情境）"。

常见误区：不要给模型设定不可能的角色（"你是一个数据库引擎"），也不要给角色设定无意义的属性（"你是一个友善的、幽默的、戴眼镜的工程师"）。角色设定的目的是引导模型调用正确的知识领域，不是"讲故事"。
03系统提示词
System Prompt 设计

System Prompt（系统提示词）是预设在对话开始前的"全局指令"，对整个对话生效。它不会出现在用户的消息历史中，但会一直影响模型的输出风格和行为。

System Prompt 通常包含以下几个部分：

  • 角色定义你是谁，负责什么。例如："你是一个 Java 技术文档助手，专注于 Spring Boot 和中间件领域"
  • 行为规范应该做什么、不应该做什么。例如："回答时使用中文，技术术语保留英文原文；如果不确定答案，说'我不确定'而不是编造"
  • 输出格式回答的结构和风格。例如："回答分为三个部分：问题分析 → 解决方案 → 注意事项。每个部分不超过 3 段"
  • 知识边界明确模型的知识范围。例如："你只负责回答 Spring 相关问题，遇到非 Spring 问题请引导用户咨询对应专家"

一个完整的 System Prompt 示例：

你是团队的 Java 技术助手。你的职责是帮助开发者解决 Spring Boot、
MyBatis、Kafka、Redis 相关的技术问题。

规则：
1. 回答使用中文，技术术语保留英文
2. 代码示例使用 Java 17 + Spring Boot 3.x 语法
3. 回答结构：问题分析 → 解决方案（含代码）→ 注意事项
4. 如果问题超出你的知识范围，诚实告知并建议咨询方向
5. 遇到安全相关的代码（SQL 拼接、密钥硬编码），必须指出风险
设计原则：System Prompt 应该简洁、明确、可测试。避免写一大堆"你应该博学多才、充满智慧"之类的空话——这些对模型行为没有实质影响。重点放在具体的输出格式、行为约束和知识边界上。
04Few-shot 与 CoT
Few-shot / Chain-of-Thought / Self-Consistency

以下是三种经过验证的、能显著提升 LLM 输出质量的 Prompt 技术：

  • Few-shot（少样本学习）在 Prompt 中给出 2-5 个输入输出示例，让模型"照葫芦画瓢"。比如让模型做情感分析，先给出 3 条标注好的样例，模型就能学会你的标注标准。比 Zero-shot（不给示例）准确率通常高 10-30%
  • Chain-of-Thought（CoT，思维链）要求模型在回答前先展示推理过程。加一句"请一步步思考"或"Let's think step by step"，模型会先输出推理步骤，再给出最终答案。对于数学、逻辑、复杂推理任务效果显著
  • Self-Consistency（自我一致性）让同一个 Prompt 被模型执行多次（温度 > 0），取多数投票的结果。比如同一个问题问 5 次，如果 3 次以上答案相同，就采纳该答案。适合需要高可靠性的决策场景

一个结合了 Few-shot 和 CoT 的 Prompt 示例：

请判断以下代码是否存在 SQL 注入风险。

示例 1：
代码：String sql = "SELECT * FROM users WHERE id = '" + userId + "'";
分析：直接拼接用户输入到 SQL 中，存在 SQL 注入风险。
结论：有风险

示例 2：
代码：String sql = "SELECT * FROM users WHERE id = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, userId);
分析：使用 PreparedStatement 参数化查询，用户输入不会被解析为 SQL。
结论：无风险

现在请分析：
代码：{user_code}
分析：（请一步步思考）
面试常考：CoT 的核心价值在于"把隐性推理显性化"——强制模型输出中间步骤，既提高了最终答案的准确性，也让用户可以检查推理过程是否合理。这在需要可解释性的场景（金融、医疗）中尤为重要。
05模板管理
Prompt 模板化与版本管理

在生产环境中，Prompt 不应该硬编码在代码里。模板化和版本管理是工程化的基本要求。

  • 模板化把 Prompt 中的变量部分用占位符代替，运行时动态填充。例如 你是一个{role}助手，请回答关于{topic}的问题。Spring AI 提供了 PromptTemplate 类支持变量替换
  • 版本管理每次修改 Prompt 都应该记录版本号、修改原因、A/B 测试结果。建议用 Git 管理 Prompt 文件，或者使用 Prompt 管理平台（如 LangSmith、PromptFlow）
  • 环境隔离不同环境（开发/测试/生产）使用不同的 Prompt 版本。测试环境可以用更激进的 Prompt（比如更严格的输出格式），生产环境用更稳健的版本
  • 灰度发布新 Prompt 上线前，先在小流量上测试。比如将 5% 的用户流量切到新 Prompt，对比关键指标后再决定是否全量
最佳实践：Prompt 应该像代码一样管理——用 Git 做版本控制，用 CI/CD 做自动化测试，用 A/B 测试做效果验证。每次修改都写清楚"改了什么、为什么改、预期效果"。
06评估与迭代
Prompt A/B 测试与评估指标

Prompt 的优化不是靠直觉，而是靠数据。以下是评估和迭代的标准流程：

评估维度：

  • 准确性（Accuracy）生成的回答是否正确。可以人工标注一批测试用例，计算正确率
  • 相关性（Relevance）回答是否紧扣问题，没有跑题或答非所问
  • 完整性（Completeness）回答是否覆盖了问题的所有方面，没有遗漏关键信息
  • 格式合规（Format Compliance）回答是否符合要求的输出格式（JSON、Markdown、纯文本等）
  • 响应时间（Latency）Prompt 越长，LLM 推理越慢。需要在质量和速度之间找平衡

A/B 测试流程：

  • 准备测试集收集 50-200 条典型问题，覆盖不同场景和难度
  • 对比版本同一个测试集分别跑 Prompt A 和 Prompt B
  • 打分对比可以用 LLM-as-Judge（让另一个 LLM 给回答打分）或人工打分
  • 统计显著性样本量足够大时，用统计检验确认差异不是随机波动
常用工具：LangSmith（LangChain 官方平台，支持 Prompt 版本管理和评估）、PromptLayer（Prompt 日志和版本管理）、Braintrust（端到端 AI 评估平台）。Java 项目也可以自己搭一套基于 JUnit + LLM API 的评估框架。
