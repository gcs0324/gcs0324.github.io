01ACID 与隔离级别
ACID 在 InnoDB 中的实现
Atomicity 原子性
事务内所有操作要么全部成功，要么全部回滚。
实现：undo log。事务回滚时按 undo log 逆向执行，把每条记录恢复到修改前的状态。
Consistency 一致性
事务执行前后，数据满足所有完整性约束（外键、唯一性、业务规则）。
实现：数据库约束 + 原子性 + 隔离性共同保证。一致性是目标，其余三者是手段。
Isolation 隔离性
并发事务互不干扰，一个事务的中间状态对其他事务不可见。
实现：MVCC（快照读无锁隔离）+ 锁机制（当前读串行化）。
Durability 持久性
提交的事务永久保存，即使系统崩溃也不丢失。
实现：redo log + 两阶段提交。WAL 保证事务提交时数据变更已落盘。
四个隔离级别与对应问题
隔离级别脏读不可重复读幻读实现方式适用
READ UNCOMMITTED✗ 有✗ 有✗ 有无特殊控制几乎不用
READ COMMITTED（RC）✅ 无✗ 有✗ 有每次 SELECT 生成新 ReadView互联网常用（Oracle 默认）
REPEATABLE READ（RR）✅ 无✅ 无⚠ 快照读无，当前读可能有事务首次 SELECT 生成 ReadView + Gap LockMySQL 默认
SERIALIZABLE✅ 无✅ 无✅ 无所有 SELECT 加 S 锁，完全串行极少使用

三类并发问题的定义：

  • 脏读读到另一个事务未提交的修改，对方回滚后数据就不存在了
  • 不可重复读同一事务内两次读同一行，结果不同（另一事务中途提交了修改）
  • 幻读同一事务内两次按条件查询，第二次多出（或少了）一些行（另一事务中途插入/删除了数据）
生产环境是用 RC 还是 RR，是一个选型判断。RC：锁粒度更小（无 Gap Lock），并发更高，binlog 必须用 ROW 格式（STATEMENT 格式在 RC 下主从复制可能不一致）。RR：MySQL 默认，MVCC 避免不可重复读，Gap Lock 大幅减少（但不完全消除）幻读，binlog 三种格式均可。
02MVCC 版本链
ReadView 四个字段

MVCC 的核心是 ReadView（读视图），每次快照读时创建（或复用）。ReadView 用来判断哪个数据版本对当前事务可见。

字段含义
m_ids创建 ReadView 时所有活跃（已开始但未提交）事务的 ID 列表
min_trx_idm_ids 中的最小值，即最老的活跃事务 ID
max_trx_id创建 ReadView 时下一个将分配的事务 ID（= 当前最大已分配 trx_id + 1）
creator_trx_id创建此 ReadView 的当前事务自身 ID
版本可见性四条规则

对一行记录，其 DB_TRX_ID 为写入该版本的事务 ID。判断是否对当前 ReadView 可见：

  • 规则1DB_TRX_ID == creator_trx_id → 可见（自己写的，自己能读）
  • 规则2DB_TRX_ID < min_trx_id → 可见（该版本由更早已提交的事务写入）
  • 规则3DB_TRX_ID >= max_trx_id → 不可见（该版本在 ReadView 创建后才开始的事务写入，还未提交或不在视野里）
  • 规则4min_trx_id <= DB_TRX_ID < max_trx_id：
      — 若 DB_TRX_ID in m_ids → 不可见（创建 ReadView 时仍活跃，未提交）
      — 若 DB_TRX_ID not in m_ids → 可见（在该范围内但已提交）

不可见时，沿 DB_ROLL_PTR 找上一个版本，对每个版本重复上述四条规则，直到找到可见版本或版本链结尾（该行对当前事务不存在）。

03快照读 vs 当前读
哪些操作是快照读，哪些是当前读
快照读（Snapshot Read）
读 undo log 版本链，不加锁，基于 MVCC ReadView 判断可见性。

触发语句：普通 SELECT（不带 FOR UPDATE / LOCK IN SHARE MODE）

性能极好，并发无锁。
当前读（Current Read）
读最新提交版本，加锁阻止其他事务并发修改。

触发语句：
· SELECT ... FOR UPDATE（X 锁）
· SELECT ... LOCK IN SHARE MODE（S 锁）
· UPDATE / DELETE / INSERT（隐式 X 锁）
· INSERT ... ON DUPLICATE KEY UPDATE
RR 下幻读是否完全解决

不完全解决。分两种情况：

  • 纯快照读同一事务内多次 SELECT，MVCC 保证读到相同快照，不会出现幻行 → 无幻读
  • 纯当前读UPDATE / SELECT FOR UPDATE 加 Next-Key Lock，锁住已有行和间隙，阻止其他事务在该范围内插入 → 无幻读
  • 快照读后当前读混用先 SELECT（快照读，不加锁），另一事务 INSERT + COMMIT，再 UPDATE（当前读，能看到新行）→ 出现幻读
-- 幻读场景复现（RR 隔离级别）
-- 事务 A:
BEGIN;
SELECT * FROM orders WHERE user_id=1;   -- 快照读，得到 2 行，不加锁

-- 事务 B（此时插入并提交）:
INSERT INTO orders(user_id,amount) VALUES(1,100); COMMIT;

-- 事务 A 继续：
UPDATE orders SET status=1 WHERE user_id=1;  -- 当前读，能看到 B 插入的行，更新了 3 行！
SELECT * FROM orders WHERE user_id=1;         -- 快照读，现在也能看到 3 行（因为 A 自己修改了 B 的行）

根本原因：当前读修改了 B 插入的行后，该行的 DB_TRX_ID 变成了 A 的事务 ID（creator_trx_id），满足规则1，快照读也变得可见了。

防范措施：业务中需要"读后写"的场景，SELECT 就应该用 SELECT ... FOR UPDATE（当前读），而不是普通 SELECT，这样从一开始就加了 Next-Key Lock，阻止并发插入。
04锁的分类体系
表级意向锁（IS / IX）

意向锁（Intention Lock）是 InnoDB 自动加的表级锁，用来快速判断表上是否有行级锁，避免全表扫描。不与行级锁冲突，只与表级 S/X 锁冲突。

  • IS意向共享锁：事务要对某些行加 S 锁时，先在表上加 IS 锁
  • IX意向排他锁：事务要对某些行加 X 锁时，先在表上加 IX 锁
请求 \ 持有S（表锁）X（表锁）ISIX
S（表锁）✅ 兼容❌ 冲突✅ 兼容❌ 冲突
X（表锁）❌ 冲突❌ 冲突❌ 冲突❌ 冲突
IS✅ 兼容❌ 冲突✅ 兼容✅ 兼容
IX❌ 冲突❌ 冲突✅ 兼容✅ 兼容

实际意义：执行 ALTER TABLE（需表级 X 锁）时，若表上存在 IX 锁（有行级写锁），ALTER 会等待所有行级锁释放。这就是为什么大事务 + 大表 DDL 容易造成长时间锁等待。

行级锁三种类型
前提：以下三种行锁均为 InnoDB 在索引项上加锁，而不是在行数据上。若 WHERE 条件没有走索引，InnoDB 会升级为表锁（锁住所有行的索引项）。
Record Lock（记录锁）
锁住索引树上的单个叶节点（一条具体记录）。

触发：精确匹配，如 WHERE id=5
作用：阻止其他事务修改/删除该行
RC 和 RR 都有
Gap Lock（间隙锁）
锁住两个索引值之间的开区间间隙，阻止在此间隙内插入新记录。

例：id 有值 (3, 7)，Gap Lock 锁住 (3, 7) 区间
作用：防止幻读（阻止在该间隙 INSERT）
仅 RR 级别才有，RC 不加 Gap Lock
Next-Key Lock（临键锁）= Record Lock + Gap Lock
锁住一个索引值及其左侧的间隙（左开右闭区间）。InnoDB 的默认行锁类型。

例：id 有值 (1, 3, 7, 10)，对 id=7 的 Next-Key Lock 锁住 (3, 7]
范围查询时会加多个相邻 Next-Key Lock。如 WHERE id > 3 会锁住 (3,7]、(7,10]、(10,+∞)

设计目标：防止幻读——既锁住已有行，又锁住前面的间隙阻止插入
Insert Intention Lock（插入意向锁）
INSERT 时设置的一种特殊 Gap Lock，声明"我要在某个间隙内插入记录"。
多个事务可以同时持有同一间隙的不同位置的插入意向锁（互不冲突），但会被 Gap Lock 阻塞。
这是 INSERT 被阻塞时的锁类型。
RC 与 RR 加锁行为对比
场景RCRR
WHERE id=5（精确匹配，行存在）Record Lock on id=5Record Lock on id=5
WHERE id=5（行不存在）无锁（不存在就没有）Gap Lock on 包含5的间隙
WHERE id > 3（范围查询）仅对扫描到的已有行加 Record Lock对范围内的行和间隙加 Next-Key Lock
WHERE name='张三'（无索引）锁全表所有行的 Record Lock（等同表锁）锁全表所有行和间隙的 Next-Key Lock

RC 没有 Gap Lock，并发能力更强，但可能出现幻读。高并发 OLTP 场景很多团队选择 RC，配合 ROW 格式 binlog。

05死锁检测与处理
死锁经典场景
-- 事务 A                          -- 事务 B
BEGIN;                             BEGIN;
UPDATE t SET v=1 WHERE id=1;  -- 锁 id=1
                               UPDATE t SET v=2 WHERE id=2;  -- 锁 id=2
UPDATE t SET v=3 WHERE id=2;  -- 等待 B 释放 id=2
                               UPDATE t SET v=4 WHERE id=1;  -- 等待 A 释放 id=1
-- A 等 B，B 等 A → 死锁

死锁的本质：多个事务以不同顺序请求同一组资源，形成循环等待。

死锁检测：wait-for graph

InnoDB 维护一张等待图（wait-for graph）：节点是事务，有向边表示"A 在等待 B 持有的锁"。周期性检测图中是否存在有向环，有环即死锁。

检测到死锁后，InnoDB 选择代价最小的事务（通常是 undo log 最少、影响行最少的那个）作为受害者，主动回滚该事务，释放锁，让其他事务继续执行。

innodb_deadlock_detect   = ON    -- 死锁检测开关，默认开。高并发时检测本身有 O(n²) 开销
innodb_lock_wait_timeout = 50    -- 锁等待超时（秒），超时后报错回滚当前语句（非整个事务）
高并发场景下 innodb_deadlock_detect 的开销。当有大量线程并发等待同一把锁时（如秒杀扣减库存），每加入一个新等待者都要扫描等待图，复杂度 O(n²)，可能产生严重 CPU 消耗。极端高并发场景可考虑关闭死锁检测，改为依赖 lock_wait_timeout 超时回滚，但需要业务层做好重试。

关键信息：lock_mode X locks rec but not gap（Record Lock）vs lock_mode X locks gap before rec（Gap Lock）vs lock_mode X（Next-Key Lock）。

避免死锁的工程实践
  • ①固定加锁顺序：多个事务操作同一组行时，约定按相同顺序加锁（如按 id 从小到大），消灭循环等待
  • ②缩短事务：事务尽量短，持锁时间越短，与其他事务冲突的概率越低
  • ③批量操作改为小批次：大 UPDATE 一次锁大量行，改为分批执行
  • ④索引优化：避免走全表扫描（等于锁全表），确保 WHERE 条件命中索引
  • ⑤业务层重试：捕获 1213 Deadlock found 错误，自动重试事务
06binlog 格式
binlog 与事务隔离级别的关联

binlog 格式的选择与事务隔离级别密切相关：

  • RC + STATEMENT主从可能不一致——RC 下同一 SQL 在主从执行时看到的行不同（RC 没有 Gap Lock，允许幻读），MySQL 会报错并禁止在 RC 下使用 STATEMENT 格式。
  • RC + ROW安全，主流互联网选择：RC 锁粒度小、并发高，ROW 格式保证主从行级完全一致。
  • RR + 任意格式均安全，RR 的 Gap Lock 在语句级别保证一致性。

07事务常见大坑
长事务——最常见的生产隐患

长事务指持续时间很长（分钟级甚至小时级）的事务。主要危害：

  • undo log 膨胀长事务的 ReadView 持续存在，Purge Thread 无法清理该事务开始后产生的所有旧版本，undo tablespace 持续增长，可能占用数 GB 空间
  • 锁资源占用长事务持有的行锁、间隙锁长时间不释放，其他事务等待锁超时，QPS 下降
  • 主从延迟从库需要完整执行 binlog 里的事务，长事务的 binlog 很大，加剧主从延迟
-- 找出超过 60 秒的事务
SELECT trx_id, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_sec,
       trx_mysql_thread_id, trx_query
FROM information_schema.INNODB_TRX
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60
ORDER BY duration_sec DESC;
隐式事务自动提交

MySQL 默认 autocommit=ON，每条 SQL 是独立事务自动提交。容易踩的坑：

  • DDL 自动提交ALTER TABLE、CREATE INDEX、TRUNCATE 等 DDL 语句会隐式提交当前事务，然后执行 DDL。在事务中执行 DDL 会意外提交之前的 DML，这是无法回滚 DDL 的根本原因。
  • BEGIN 陷阱连续执行两个 BEGIN，第二个 BEGIN 会隐式提交第一个事务。ORM 框架通常能处理好，但裸 JDBC 需注意。
  • autocommit 关闭某些框架会 SET autocommit=0，此后每条 SQL 都是事务的一部分，必须手动 COMMIT，忘了 COMMIT 就是长事务。
大事务——写入量过大的事务

单次事务修改数万行（如 DELETE FROM t WHERE create_time < '2023-01-01'，删除百万行）：

  • →undo log 单次生成量大，回滚代价极高
  • →占用大量 Lock 资源，行锁和 Gap Lock 覆盖大范围，阻塞其他事务
  • →binlog 单个事务过大（ROW 格式下尤其明显），主从延迟剧增

正确做法：分批小事务执行。

-- 替代大批量 DELETE
DELETE FROM t WHERE create_time < '2023-01-01' LIMIT 1000;  -- 循环执行，每次 1000 行
-- 或使用 pt-archiver 工具，支持限速、主从延迟感知、安全归档
事务使用 Checklist：
① 事务尽量短，持锁时间越短越好
② SELECT FOR UPDATE（当前读）比普通 SELECT 更安全的"读后写"场景
③ 批量 DML 拆成小批次，每批 1000~5000 行为宜
④ 定期监控长事务（information_schema.INNODB_TRX）
⑤ RC 隔离级别 + ROW binlog 是互联网业务的主流选择
