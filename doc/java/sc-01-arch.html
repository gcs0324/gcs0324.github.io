01单体架构 vs 微服务架构
为什么需要微服务？单体的痛点

单体架构（Monolith）把所有业务模块打成一个 WAR/JAR 部署，早期简单易用，但随着业务增长会暴露出一系列问题：

单体架构的痛点
· 部署耦合：改一个模块要重新部署整个应用，发布风险高
· 扩容粗粒度：只有订单模块高峰，却要扩整个应用
· 技术栈固化：全局只能用一套语言/框架
· 团队瓶颈：代码库庞大，多团队改同一仓库冲突频繁
· 可用性连带：一个模块 OOM 拖垮整个进程
微服务的收益
· 独立部署：各服务独立发布，互不影响
· 精细扩容：哪个服务有压力就扩哪个
· 技术异构：各服务可选不同语言/框架
· 故障隔离：一个服务挂了不影响其他服务
· 团队自治：按业务域划分团队，各自负责
微服务的代价——不是银弹

微服务解决了单体的扩展性问题，但引入了新的复杂度：

  • 分布式复杂度网络调用代替本地调用，延迟变高、失败概率增加，需要超时/重试/熔断等机制
  • 分布式事务跨服务修改数据无法用数据库本地事务，需要 Seata/TCC/Saga 等复杂方案
  • 运维复杂度部署几十个微服务需要 CI/CD、容器化（Docker/K8s）、统一日志、链路追踪等配套设施
  • 服务间通信服务发现、负载均衡、接口版本管理都需要额外设计
微服务不是默认选项。团队规模小、业务还不复杂时，单体 + 模块化分层是更好的选择。微服务适合：团队 20 人以上、服务模块 QPS/资源需求差异大、发布频率高且希望独立发布的场景。
02Spring Cloud 组件全景图
Spring Cloud 是一个微服务工具集，而不是单一框架

Spring Cloud 本身是一组规范（接口 + 抽象），各功能领域有多套可替换的实现。理解这一点比记住每个组件名字更重要。

04服务调用完整链路
从客户端请求到服务响应的完整路径

理解这条链路，是调优 Spring Cloud 应用的基础。每个环节都可能成为性能瓶颈或故障点。

①
客户端发请求 → Gateway 路由匹配
客户端请求到达 Spring Cloud Gateway。Gateway 按路由规则匹配（Path/Header/Method），在全局 Filter 链中依次处理：认证（JWT 解析）→ 鉴权 → 限流（Redis 令牌桶）→ 请求日志。路由匹配成功后，从 Nacos 注册中心获取目标服务实例列表。
②
Gateway 负载均衡 → 目标服务实例
Gateway 集成 Spring Cloud LoadBalancer，从服务实例列表中按策略（轮询/权重）选择一个实例，转发请求。如果目标实例不可达，LoadBalancer 会剔除该实例并重试其他实例（重试次数由配置控制）。
③
服务内部处理 → Feign 调用下游服务
请求到达目标服务（如 order-service）后，正常处理业务逻辑。若需要调用其他服务（如 user-service），通过 OpenFeign 发起 HTTP 调用。Feign 自动从 Nacos 查找 user-service 实例，LoadBalancer 选择实例，Sentinel 检查是否限流/熔断，通过则发起 HTTP 请求。
④
Sentinel 限流 & 熔断保护
每次服务调用经过 Sentinel 的 SlotChain（责任链）：统计 QPS/并发数 → 检查流控规则 → 检查熔断规则（错误率/慢调用比例）。触发限流 → 抛出 FlowException；触发熔断 → 抛出 DegradeException，进入 fallback 降级逻辑。
⑤
SkyWalking 透明链路追踪
SkyWalking Agent（Java Agent 字节码增强）在每次服务调用时自动注入 Trace ID，通过 HTTP Header（sw8）传递到下游服务。全链路的调用时序、每个 Span 的耗时、异常信息都会异步上报到 SkyWalking OAP，不影响业务逻辑。
⑥
结果返回 → Gateway 响应过滤
下游服务响应经 Gateway 后置 Filter 处理（如添加响应头、统一响应格式）后返回客户端。Gateway 记录完整请求日志（请求耗时、响应状态码、目标实例 IP）。
05核心设计原则
微服务拆分的六个原则
单一职责
每个服务只负责一个业务域（用户、订单、库存）。一个服务出现需要频繁修改不相关功能的情况，说明职责不清晰，应该继续拆分。
高内聚低耦合
服务内部的功能紧密相关（高内聚），服务之间仅通过定义清晰的 API 交互（低耦合）。避免服务间直接操作对方数据库。
围绕业务域
按 DDD（领域驱动设计）的限界上下文划分，而不是按技术层（DAO/Service/Controller）拆分。技术层拆分会导致大量网络调用。
数据库隔离
每个微服务独享自己的数据库（Database per Service）。多服务共享数据库是微服务的反模式，会导致耦合和数据库成为单点瓶颈。
服务自治
每个服务能独立部署、独立扩容、独立失败。依赖第三方服务时，要做好降级：对方不可用时，用降级数据返回，而不是让自己也挂掉。
接口向后兼容
服务升级时 API 不能破坏已有消费方。新增字段用默认值；废弃字段先标注 @Deprecated 保留一个版本再删除；主版本不兼容时新建接口路径（/v2/）。
Spring Cloud Alibaba 是国内生产环境的主流选择。Nacos（注册 + 配置）+ Gateway + OpenFeign + Sentinel + Seata 的组合，覆盖了微服务的全部核心需求，且都有阿里巴巴在超大规模场景下的验证。文档中文友好，社区活跃。
