01服务雪崩与容错设计
服务雪崩：一个服务慢，拖垮所有服务

在微服务调用链 A → B → C → D 中，如果 D 响应变慢，C 等待 D 的线程被阻塞，C 的线程池耗尽，C 变慢，B 等待 C 的线程耗尽，B 变慢……最终整个系统级联崩溃，这就是服务雪崩（Cascading Failure）。

根本原因：微服务调用是跨网络的，网络调用比本地调用慢 N 倍，且随时可能超时、失败。

三种容错手段：

超时（Timeout）
调用下游服务设置超时时间，超时直接失败，避免线程无限等待。是最基本的容错手段，所有 Feign 调用都必须设置超时。
熔断（Circuit Breaker）
当下游服务错误率超过阈值，触发熔断，后续请求直接走降级逻辑，不再真正调用下游，避免大量线程阻塞。等一段时间后尝试半开（Half-Open）。
限流（Rate Limiting）
限制进入服务的请求 QPS/并发数，把超出能力范围的请求拒绝在外，防止系统过载。不是等服务崩了才保护，而是提前防止崩溃。
02Sentinel 架构原理
Sentinel 的核心：资源（Resource）+ 规则（Rule）

Sentinel 把保护的对象抽象为资源（Resource），可以是一个接口方法、一个 Feign 调用、一个 URL，也可以是任意代码块。对资源配置规则，Sentinel 在调用资源时检查规则并执行对应动作。

Sentinel 的 SlotChain（责任链）是核心执行引擎，每次资源调用都要经过所有 Slot：

  • NodeSelectorSlot构建资源调用树（哪个接口被哪个接口调用），用于流量统计
  • StatisticSlot统计实时数据（QPS、并发线程数、响应时间、错误率），滑动窗口计数
  • FlowSlot检查流控规则，超出则拒绝（抛 FlowException）
  • DegradeSlot检查熔断规则，触发熔断则抛 DegradeException
  • AuthoritySlot黑白名单检查
  • SystemSlot系统自适应保护（CPU 使用率、系统负载等）
Sentinel Dashboard 动态规则推送

规则不写死在代码里，而是通过 Sentinel Dashboard 下发，并持久化到 Nacos，服务重启后规则仍然有效：


spring:
  cloud:
    sentinel:
      transport:
        dashboard: localhost:8080       # Sentinel Dashboard 地址
      datasource:
        flow-rules:                    # 流控规则数据源
          nacos:
            server-addr: localhost:8848
            namespace: prod-namespace-id
            group-id: SENTINEL_GROUP
            data-id: order-service-flow-rules
            data-type: json
            rule-type: flow
03流量控制规则
流控规则四个维度
维度选项说明
阈值类型QPS / 并发线程数QPS：每秒请求数；线程数：当前正在处理该资源的线程数
流控模式直接 / 关联 / 链路直接：达阈值就限流；关联：关联资源超阈值时限流本资源；链路：只统计指定入口的流量
流控效果快速失败 / Warm Up / 排队等待见下方详解
针对来源default / 指定调用方只限流特定调用方（如只限流 order-service 对 user-service 的调用）

三种流控效果：

快速失败（默认）
超过阈值立即抛出 FlowException，直接失败。适合对延迟敏感的场景，不接受排队等待。
Warm Up（冷启动）
系统启动初期容量低，流量阈值从 阈值/冷加载因子（默认3） 开始，经过预热时长逐步达到设定阈值。防止启动瞬间流量打垮冷机器。
排队等待
超过 QPS 阈值的请求排队等待而不是立即失败，按匀速速率处理。需设置最大等待时间，超出等待时间才失败。适合流量整形/削峰填谷。
04熔断降级规则
三种熔断策略
慢调用比例
统计时间窗口内，响应时间超过阈值（RT）的请求比例达到设定比例，触发熔断。

例：最大 RT=500ms，比例阈值=50%，窗口=10s → 10秒内50%请求超过500ms，熔断。
异常比例
统计时间窗口内，异常请求数占总请求数的比例超过阈值，触发熔断。

例：异常比例阈值=50%，窗口=10s → 10秒内50%以上请求抛异常，熔断。
异常数
统计时间窗口内，异常总数超过阈值，触发熔断。

适合绝对数量控制（而非比例），例如流量很低时，5个异常就应触发熔断。

Fallback 降级实现（整合 OpenFeign）
// 1. Feign 接口定义 fallback
@FeignClient(name = "user-service", fallback = UserFeignFallback.class)
public interface UserFeignClient {
    @GetMapping("/user/{id}")
    UserDTO getUserById(@PathVariable Long id);
}

// 2. 实现 fallback（降级逻辑）
@Component
public class UserFeignFallback implements UserFeignClient {
    @Override
    public UserDTO getUserById(Long id) {
        // 降级：返回默认值，不抛异常
        return UserDTO.builder()
            .id(id)
            .name("未知用户")    // 降级数据
            .build();
    }
}

// 3. 若需要获取异常信息，用 FallbackFactory
@Component
public class UserFeignFallbackFactory implements FallbackFactory<UserFeignClient> {
    @Override
    public UserFeignClient create(Throwable cause) {
        log.error("user-service 调用失败: {}", cause.getMessage());
        return id -> UserDTO.builder().id(id).name("未知用户").build();
    }
}

// application.yml
feign:
  sentinel:
    enabled: true   # 开启 Sentinel 对 Feign 的支持
05Seata 分布式事务
为什么需要 Seata？本地事务解决不了跨服务问题

电商下单场景：order-service 创建订单 + stock-service 扣减库存 + account-service 扣减余额，三个操作分属三个服务、三个数据库，数据库本地事务无法跨数据库保证原子性。如果创建订单成功但扣库存失败，就产生数据不一致。

Seata 是阿里开源的分布式事务框架，支持四种模式：

四种事务模式对比
模式原理侵入性适用场景
AT 模式（默认）自动分析 SQL，生成前镜像/后镜像（undo_log），全局事务失败时自动回滚低（只加 @GlobalTransactional）数据库操作场景，大多数电商业务
TCC 模式业务自己实现 Try / Confirm / Cancel 三个方法，Seata 框架编排高（要实现三个方法）对性能要求高，无法依赖 undo_log 的场景
Saga 模式长事务，每步操作有对应补偿操作，失败时逆向补偿高长流程业务（保险理赔、供应链）
XA 模式基于数据库的 XA 协议，两阶段提交低需要强一致性，支持 XA 的数据库
AT 模式原理详解

AT 模式是 Seata 的默认模式，对业务代码几乎无侵入：只需在入口方法加 @GlobalTransactional，Seata 自动处理所有事务协调。

三个角色：

  • TC（Transaction Coordinator）事务协调者，即 Seata Server，维护全局事务状态，负责全局提交/回滚的决策
  • TM（Transaction Manager）事务管理者，即业务发起方（加了 @GlobalTransactional 的服务），向 TC 注册全局事务、发起提交/回滚
  • RM（Resource Manager）资源管理者，即参与事务的各个服务，向 TC 注册分支事务，执行本地事务后上报结果
// order-service：事务发起方
@GlobalTransactional(timeoutMills = 30000, name = "create-order-tx")
public void createOrder(OrderDTO dto) {
    // 1. 创建订单（本地事务）
    orderMapper.insert(Order.from(dto));

    // 2. 扣减库存（Feign 调用 stock-service）
    stockFeignClient.deduct(dto.getStockId(), dto.getCount());

    // 3. 扣减余额（Feign 调用 account-service）
    accountFeignClient.deduct(dto.getUserId(), dto.getAmount());
    // 以上任一步失败，Seata 自动回滚全部操作
}

AT 模式的回滚机制：Seata 的 DataSourceProxy 拦截所有 SQL，执行前记录"前镜像"（数据原始值），执行后记录"后镜像"（新值），存入 undo_log 表。全局事务失败时，TC 通知各 RM 用 undo_log 生成逆向 SQL 并执行回滚。

AT 模式的全局锁机制可能导致性能问题。AT 模式在全局事务期间对修改的行加全局锁（写入 lock_table），其他全局事务修改同一行时需等待。高并发场景下全局锁竞争可能成为瓶颈，此时应考虑 TCC 模式。
06链路追踪 SkyWalking
为什么需要链路追踪

一次用户请求经过 Gateway → order-service → user-service → stock-service，如果响应慢或报错，靠日志很难定位是哪个服务出了问题（日志分散在各个服务）。

链路追踪的核心思路：给每次请求分配一个全局唯一的 Trace ID，所有服务处理这个请求时都带上这个 Trace ID 记录日志，就能把分散在各服务的日志串成一条完整的调用链。

SkyWalking 核心概念
Trace（链路）
一次完整请求的全局标识，由全局唯一的 Trace ID 标识。一个 Trace 包含多个 Span。
Span（操作单元）
Trace 中的一个原子操作，记录操作的开始时间、结束时间、操作名、结果（成功/失败）。Span 之间有父子关系，形成树状结构。
Agent（探针）
Java Agent 字节码增强，通过 JVM 参数挂载：-javaagent:/skywalking/agent.jar，无需修改代码，自动采集 HTTP/Feign/JDBC/Redis 等调用信息。
OAP（分析平台）
SkyWalking 后端服务，接收 Agent 上报的数据，存储到 Elasticsearch，提供查询 API。默认 gRPC 端口 11800，HTTP 端口 12800。
SkyWalking Agent 接入与自定义追踪
# 启动时挂载 Agent（无需改代码）
java -javaagent:/opt/skywalking/agent/skywalking-agent.jar \
     -Dskywalking.agent.service_name=order-service \
     -Dskywalking.collector.backend_service=oap-server:11800 \
     -jar order-service.jar

# 或在 Dockerfile/K8s 中配置
ENV JAVA_TOOL_OPTIONS="-javaagent:/skywalking/skywalking-agent.jar"
ENV SW_AGENT_NAME="order-service"
ENV SW_AGENT_COLLECTOR_BACKEND_SERVICES="oap:11800"
// 自定义追踪（标注关键业务方法）
import org.apache.skywalking.apm.toolkit.trace.Trace;
import org.apache.skywalking.apm.toolkit.trace.Tag;

@Service
public class OrderService {

    @Trace(operationName = "createOrder")
    @Tag(key = "orderId", value = "returnedObj.id")
    public Order createOrder(OrderDTO dto) {
        // 业务逻辑...
    }

    // 在任意位置添加自定义信息到当前 Span
    public void doSomething() {
        ActiveSpan.tag("userId", userId.toString());
        ActiveSpan.error("出现错误了");
    }
}
可靠性建设 Checklist：
① 所有 Feign 调用设置超时（connectTimeout + readTimeout）
② 关键服务接口配置 Sentinel 流控规则，防止被打垮
③ Feign 调用下游服务时配置 fallback，下游挂了不影响自己
④ 跨服务写操作使用 Seata @GlobalTransactional 保证数据一致
⑤ 接入 SkyWalking，确保每个服务都能被链路追踪覆盖
⑥ 所有服务日志输出 TraceId（SkyWalking 自动注入到 MDC，配置 logback 打印即可）
