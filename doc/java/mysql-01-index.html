01B+树索引结构
为什么 InnoDB 选 B+树

索引的本质是预先把数据排好，让查找从 O(n) 变成 O(log n)。但在数据库场景下，核心矛盾不是 CPU 比较次数，而是磁盘 IO 次数——每次 IO 读一个 16 KB 的页，IO 层数越少，查询越快。衡量树形索引的关键指标是树高，树高由扇出（branching factor）决定：一个节点能放多少个 key+pointer。

数据结构100 万行时树高范围查询为什么不选
红黑树≈ 20 层（log₂ 1M）中序遍历，需跨节点回溯层高太大，20 次 IO
B树（B-树）≈ 3~4 层数据在内部节点，范围扫要回溯父节点非叶存数据占空间，扇出比 B+树低；范围扫回溯成本高
HashO(1) 点查完全不支持无序，不支持 > / < / BETWEEN / ORDER BY / LIKE 前缀
B+树≈ 3 层（log₁₁₇₀ 1M）叶节点双向链表，顺序扫——（最优解）

B树 vs B+树的关键差异：B树的非叶节点也存真实行数据，每个节点能放的 key 数因此减少，扇出降低，层高增加。B+树非叶节点只存 key + 指针，一个 16 KB 的页能放约 1170 个指针（key≈8 字节 + pointer≈6 字节 = 14 字节，16384 ÷ 14 ≈ 1170）。叶节点存实际行数据（假设行均 1 KB，每页约 16 行），三层即可覆盖 1170 × 1170 × 16 ≈ 2200 万行，最多 3 次 IO 定位任意一行。

B+树三层结构 — 千万行数据最多 3 次 IO
叶节点之间通过双向链表连接（图中蓝色箭头）。范围查询找到起始叶节点后，顺序扫链表即可，无需再从根节点向下遍历。这是 B+树比 B树更适合 BETWEEN、ORDER BY、LIMIT 扫描的根本原因。
02聚簇索引 vs 非聚簇索引
聚簇索引（Clustered Index）

聚簇索引不是一种额外的索引，而是一种数据存储方式：行数据和主键索引共用同一棵 B+树，叶节点直接存完整行数据。InnoDB 的主键就是聚簇索引，物理上行数据按主键顺序紧密排列在磁盘上。

主键确定规则（优先级从高到低）：

  • ①有显式 PRIMARY KEY → 用它
  • ②没有主键，找第一个非空唯一索引（NOT NULL UNIQUE）→ 用它
  • ③都没有 → InnoDB 自动生成隐藏的 6 字节 DB_ROW_ID 作为聚簇索引列，用户不可见
二级索引（Secondary Index）与回表代价

InnoDB 所有非主键索引都是二级索引。二级索引的叶节点存储的是索引列值 + 主键值，不包含其他列。查询不在索引中的列时，需要两次 B+树遍历：

①
走二级索引 B+树
按 WHERE 条件在二级索引上定位到满足条件的叶节点，读取主键值。每命中一行，得到一个主键。
②
回表（Table Lookup）
拿主键值重新在聚簇索引 B+树上再走一次，才能拿到完整行。每行需要一次独立的 B+树遍历，随机 IO。

回表的 IO 是随机的（主键值散落在磁盘各处），命中行数越多，随机 IO 越多。当回表代价超过全表顺序扫描的代价时，优化器会主动放弃二级索引走全表扫描——这就是有时候明明加了索引却不走的原因之一。

MyISAM 没有聚簇索引。MyISAM 的数据文件（.MYD）和索引文件（.MYI）分离，所有索引——包括主键索引——的叶节点存的都是行的物理地址（文件偏移量），数据按插入顺序堆放（堆表）。因此 MyISAM 的主键查询和普通索引查询性能差不多，都需要一次地址寻址，不存在"主键天然覆盖行数据"的优势。
03覆盖索引
用索引消灭回表

如果一条查询所需的所有列都包含在某个索引里（索引的 key 列 + 二级索引叶节点里自带的主键列），就不需要回表，直接在索引叶节点就能拿到完整结果，这叫覆盖索引（Covering Index）。

EXPLAIN 中 Extra: Using index 就是覆盖索引命中的信号，表示"从索引就拿到了所有需要的数据，没有回表"。

-- 表结构：orders(id PK, user_id, status, amount, created_at)
-- 索引：idx_user_status(user_id, status)

-- ❌ 需要回表：amount 不在索引里
SELECT user_id, status, amount FROM orders WHERE user_id = 100;

-- ✅ 覆盖索引：只查 user_id + status，均在索引叶节点里
SELECT user_id, status FROM orders WHERE user_id = 100;

-- ✅ 也是覆盖索引：id 是主键，二级索引叶节点里自带
SELECT id, user_id, status FROM orders WHERE user_id = 100;
覆盖索引的工程价值

高频查询路径上，把 SELECT 需要的列追加进联合索引，是消灭回表最直接的手段。代价是索引变大、写入维护成本增加，需要权衡：

  • ✓追加列区分度低、列宽小（如 status、is_deleted）→ 代价小，收益大，值得追加
  • ✗追加列是 TEXT/BLOB 类型或宽度很大 → 索引页膨胀，不值得
count(*) 也能走覆盖索引。执行 SELECT count(*) FROM orders WHERE status=1 时，如果 status 上有索引，优化器只需扫描索引叶节点计数，不需要读行数据。EXPLAIN 会显示 Extra: Using index，IO 大幅减少。
04联合索引与最左前缀
最左前缀的底层原因

联合索引 (a, b, c) 在 B+树中的排序规则是：先按 a 排，a 相同按 b 排，b 相同按 c 排。这个规则决定了索引的可用性：

  • ✅WHERE a=1：a 有全局序，可以二分定位
  • ✅WHERE a=1 AND b=2：a 等值后，b 在该 a 子集内有序，可以继续定位
  • ✅WHERE a=1 AND b>2：a 等值后，b 做范围扫，c 在此范围内无全局序，c 的过滤交给 ICP
  • ❌WHERE b=2：跳过 a，b 在全局无序，无法用索引定位
  • ❌WHERE a=1 AND c=3（跳过 b）：a 等值后，c 在 b 不确定下无序，c 无法索引定位

关键推论：范围条件（> / < / BETWEEN / LIKE 'x%'）之后的列失去索引过滤能力，但仍可通过 ICP 在引擎层过滤（见第 07 节）。

MySQL 8.0 Skip Scan（跳跃扫描）

8.0 新增优化：当联合索引第一列区分度极低（如 gender 只有 M/F），查询只过滤后续列时，优化器可枚举第一列的所有值，对每个值做子范围扫描，从而"绕过"最左前缀限制。

-- 索引：(gender, age)，gender 只有 M/F
-- 8.0 Skip Scan：等价于 gender='M' AND age>25 UNION gender='F' AND age>25
SELECT * FROM users WHERE age > 25;

-- EXPLAIN FORMAT=JSON 中可以看到：
-- "using_index_for_skip_scan": true
Skip Scan 只在第一列区分度极低（值少）且第一列没有等值条件时才划算。若第一列有几十种值，枚举成本反而高于全表扫描，优化器会自动放弃 Skip Scan。
05ORDER BY 与索引排序
ORDER BY 什么时候走索引

ORDER BY 能走索引的本质条件：在 WHERE 等值条件固定了索引前缀列之后，ORDER BY 的列恰好是索引中的下一列（且方向一致），这样排序列在固定前缀下已经是有序的，无需额外排序。

SQL 模式索引结果原因
WHERE a=1 ORDER BY b(a,b)✅ 走索引，无 filesorta 等值固定后，b 在该子集内天然有序
WHERE a=1 ORDER BY b,c(a,b,c)✅ 走索引，无 filesorta 等值后，(b,c) 联合有序
WHERE a=1 AND b=2 ORDER BY c(a,b,c)✅ 走索引，无 filesort(a,b) 均等值，c 有序
WHERE a>1 ORDER BY b(a,b)❌ filesorta 是范围条件，b 在不同 a 值间无全局序
WHERE a=1 ORDER BY b DESC,c ASC(a,b,c)❌ filesort（8.0前）b/c 方向不一致，单向索引无法满足
WHERE a=1 ORDER BY b DESC,c ASC(a, b DESC, c ASC)✅ 走索引（8.0+）8.0 支持建降序索引，方向与查询匹配
ORDER BY RAND()—❌ 永不走索引函数结果不可预排序，无法映射到 B+树
ORDER BY a LIMIT 10(a)✅/❌ 视选择性LIMIT 小、需回表行少时走索引；返回比例高时优化器选全表扫
filesort 两种算法

ORDER BY 不能走索引时，MySQL 对结果集做内存（或磁盘）排序，称为 filesort（名字有点误导，不一定真写文件）。有两种算法：

双路排序（Two-Pass Sort）

① 读 row pointer + 排序列 → sort_buffer
② 在 sort_buffer 内排好序
③ 按 row pointer 回表，再读剩余列

两次磁盘读取；sort_buffer 只需存少量数据，适合行宽很大的场景。

单路排序（Single-Pass Sort）

① 一次把 SELECT 需要的所有列读入 sort_buffer
② 在 sort_buffer 内直接排序，排完直接输出

一次磁盘读取；但 sort_buffer 需装下所有列，占内存更多。

MySQL 默认优先单路排序。当待排数据量超过 sort_buffer_size（默认 256 KB）时，会把已排好的片段溢写到磁盘，最后做多路归并，产生真正的文件 IO，这才是性能杀手。

-- 调整（会话级别，不要设太大，是每个连接独占的内存）
SET SESSION sort_buffer_size = 4 * 1024 * 1024;  -- 4 MB

-- 查看排序是否用了磁盘临时文件
SHOW STATUS LIKE 'Sort_merge_passes';  -- > 0 说明发生了磁盘归并
Using filesort 不代表性能差。结果集只有几十行时，filesort 在内存里瞬间完成，完全可以接受。真正危险的是 Extra: Using temporary; Using filesort——需要先建内存/磁盘临时表再排序，常见于 GROUP BY 和 ORDER BY 是不同列的场景。这才是需要重点优化的信号。
06索引失效场景
让索引失效的常见写法
🔴
对索引列使用函数或运算
WHERE YEAR(created_at) = 2024 → ❌ 全表扫描
WHERE DATE_FORMAT(created_at, '%Y') = '2024' → ❌
改写：WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01' → ✅

WHERE id + 1 = 101 → ❌ 改为 WHERE id = 100 → ✅

原因：函数/运算改变了列的实际值，B+树按原始值排序，找不到计算后的值。
🔴
隐式类型转换（高频坑）
phone VARCHAR(20) 列：WHERE phone = 13812345678（传了整型）→ ❌
MySQL 需要把 phone 列每行都 CAST 成数字再比较，相当于对索引列套了函数，全表扫描。

注意方向：id INT，WHERE id = '100'（传了字符串）→ ✅ 字符串 '100' 转成整数 100，对参数转换，不是对列转换，索引仍有效。

记忆口诀：转换加在列上 → 失效；转换加在参数上 → 有效。
🔴
LIKE 前导通配符
WHERE name LIKE '%张%' → ❌ 前导 % 无法确定 B+树起始位置，全扫
WHERE name LIKE '张%' → ✅ 确定前缀 '张'，可以在 B+树定位到第一个"张"开头的节点后顺序扫

如果业务必须做全模糊搜索，考虑 Elasticsearch 全文检索，或 MySQL FULLTEXT 索引（仅适合文本内容搜索，不支持精确 SQL 过滤）。
🔴
OR 连接中有非索引列
WHERE id = 1 OR name = '张三'：id 有索引、name 没有 → ❌ 整体全表扫描
因为满足 name='张三' 的行散落全表，必须扫全表，加上 id 的条件也没有意义。

两列都有索引时，MySQL 可能 Index Merge（OR 合并两个索引结果），但稳定性差，建议改写：
SELECT ... WHERE id=1 UNION SELECT ... WHERE name='张三'
🟡
NOT IN / NOT EXISTS / !=（否定条件）
否定条件无法利用索引有序性定位一个区间，通常走全表扫描。
例外：数据量极少 + 主键/唯一索引时，优化器可能走 index range scan。不可依赖，需 EXPLAIN 验证。

改写思路：NOT IN (1,2,3) 可改为 LEFT JOIN ... IS NULL 的排除写法，有时能利用索引。
🟡
索引区分度太低，优化器主动放弃
status 只有 0/1 两个值，99% 的行 status=0。走索引 + 回表的代价 > 全表顺序扫描的代价，优化器自动选择全表扫描，即使索引存在。

强制走索引：SELECT ... FROM t FORCE INDEX(idx_status) WHERE status=0，但通常没有意义。
真正的解决方案：重新设计索引（如把 status 放入联合索引的非首位），或接受全表扫描并优化表大小。
🟡
字符集或 Collation 不匹配（JOIN 时的坑）
两张表 JOIN，关联列类型相同但字符集不同（如一张 utf8，一张 utf8mb4），MySQL 需要做隐式转换，被转换的那侧无法走索引。

排查：SHOW CREATE TABLE 确认字符集一致；生产环境统一使用 utf8mb4 + utf8mb4_unicode_ci。
07索引下推 ICP
Index Condition Pushdown（MySQL 5.6+）

ICP 解决的问题场景：联合索引 (name, age)，查询 WHERE name LIKE '张%' AND age > 20。

name 前缀匹配能用索引定位到第一个"张"开头的节点，但 age 是范围列后的条件，在 B+树层无法过滤。5.6 之前：先按 name 命中的所有叶节点一一回表，拿完整行后再在 Server 层过滤 age。如果 name LIKE '张%' 命中 10000 行但 age>20 只有 100 行，就产生了 9900 次无效回表。

5.6+ ICP：把 age>20 的过滤条件下推到存储引擎层，在拿到二级索引叶节点后先检查 age（叶节点里包含 age），只有 age>20 的行才回表，直接把回表从 10000 次降为 100 次。

ICP 对比 — 有无索引下推的 IO 路径
EXPLAIN 中 Extra: Using index condition 表示 ICP 生效。ICP 默认开启，可用 SET optimizer_switch='index_condition_pushdown=off' 关闭。ICP 只对二级索引有效，聚簇索引的叶节点已包含所有列，没有"下推"的必要。
08MRR 优化
Multi-Range Read — 随机 IO → 顺序 IO

二级索引按索引列有序排列，但叶节点里的主键值是乱序的。例如按 status 索引命中了 user_id 为 9012、43、7831、201 的行，按命中顺序回表就是 4 次随机 IO，物理上在磁盘各处跳来跳去。

MRR 的优化思路：

①
收集主键
先扫描二级索引，把范围内所有主键值收集到 read_rnd_buffer 中，不立即回表。
②
按主键排序
对 buffer 中的主键值排序，变成 43 → 201 → 7831 → 9012 的顺序（接近物理页顺序）。
③
批量顺序回表
按排序后的主键顺序批量读聚簇索引，IO 变成近似顺序读，磁盘寻道次数大幅减少。
-- 查看 MRR 开关状态
SELECT @@optimizer_switch\G
-- 含 "mrr=on,mrr_cost_based=on" → 开启，成本划算时自动启用

-- EXPLAIN 中 Extra: Using MRR 表示生效

-- 调整每次收集多少主键（默认 256KB）
SET SESSION read_rnd_buffer_size = 4 * 1024 * 1024;
MRR + BKA（Batched Key Access）联合优化 JOIN。BKA 把驱动表每批次产生的关联列值收集起来，以 MRR 方式访问被驱动表的索引，把 JOIN 的随机 IO 变成批量顺序 IO。需要单独开启：SET optimizer_switch='batched_key_access=on'，并同时确保 MRR 开启。
09页分裂与索引碎片
自增主键 vs UUID 的写放大问题

InnoDB 每个 B+树叶节点是一个 16 KB 的页，满页插入新行时会触发页分裂（Page Split）：把当前页大约一半的记录移到新分配的页，然后更新父节点的指针。

自增主键（推荐）

新行永远插到最后一页。当前页写满后直接申请新页追加，不触发分裂，IO 顺序，页填充率接近 100%。

UUID / 随机主键（慎用）

新行插入位置随机，大概率命中已满的中间页，频繁触发页分裂：写放大（每次分裂写两页 + 更新父节点）、碎片化（分裂后平均填充率约 50%）、缓存失效（热数据不集中，Buffer Pool 命中率下降）。

100 万次随机主键写入，页分裂可能产生额外 50% 以上的页数，相同数据需要更多 IO 才能扫描完。

碎片整理方案
-- 查看碎片率
SELECT table_name,
       ROUND(data_length/1024/1024, 1) AS data_MB,
       ROUND(data_free/1024/1024, 1)   AS free_MB,
       ROUND(data_free/(data_length+data_free)*100, 1) AS frag_pct
FROM information_schema.TABLES
WHERE table_schema = 'your_db' AND engine = 'InnoDB'
ORDER BY data_free DESC LIMIT 20;
方案原理是否锁表适用场景
OPTIMIZE TABLE t重建表 + 索引，回收碎片空间是（MDL 写锁）小表，停机窗口
ALTER TABLE t ENGINE=InnoDB触发 Online DDL 重建否（5.6+ Online DDL）中等大小表
pt-online-schema-change影子表 + 增量同步 + rename否超大表，生产环境
gh-ost基于 binlog 的无触发器迁移否超大表，主从复制环境
页分裂无法完全杜绝，但可以缓解。如果业务必须用全局唯一 ID，优先选雪花 ID（趋势递增，毫秒级有序）或 UUID v7（时间戳有序），而不是 UUID v4（完全随机）。趋势递增的 ID 写入模式接近自增，页分裂频率与自增主键相当。
10索引设计实战
选列：区分度优先

区分度（Selectivity）= 不重复值数量 / 总行数，越接近 1 说明该列越适合做索引。

-- 计算各列区分度
SELECT
  COUNT(DISTINCT status)  / COUNT(*) AS sel_status,   -- 结果约 0.00003，极低
  COUNT(DISTINCT user_id) / COUNT(*) AS sel_user,     -- 结果约 0.3，可以
  COUNT(DISTINCT phone)   / COUNT(*) AS sel_phone     -- 结果约 0.999，非常适合
FROM orders;

-- 经验值：Selectivity > 0.1 才值得单独建索引

区分度低的列（如 status、gender）不适合单独建索引，但可以作为联合索引的非首位列（查询有等值条件时仍能利用）。

联合索引列顺序设计三原则
  • ①等值列放前，范围列放后：(user_id, created_at) 比 (created_at, user_id) 更好——user_id 等值固定后，created_at 才有序，才能做范围扫。
  • ②高区分度列放前：在满足①的前提下，区分度高的列放在前面，过滤效果好，减少扫描行数。
  • ③覆盖查询的列追到末尾：把 SELECT 里频繁出现但不在 WHERE 中的列追加到联合索引末尾，消灭回表。代价是索引变宽，评估 write 开销是否可接受。
-- 典型设计案例：订单查询
-- 查询：WHERE user_id=? AND status=? ORDER BY created_at DESC LIMIT 20
-- 同时需要返回 order_no（不在 WHERE 里）

-- 推荐索引：(user_id, status, created_at, order_no)
--   user_id 等值，status 等值，created_at 有序 → ORDER BY 不需要 filesort
--   order_no 追加尾部 → 覆盖索引，不需要回表
ALTER TABLE orders ADD INDEX idx_user_status_time_no
  (user_id, status, created_at, order_no);
前缀索引 — 处理长字符串
-- 找到合适的前缀长度：区分度接近全列时就够了
SELECT
  COUNT(DISTINCT LEFT(email, 8))  / COUNT(*) AS p8,
  COUNT(DISTINCT LEFT(email, 12)) / COUNT(*) AS p12,
  COUNT(DISTINCT LEFT(email, 16)) / COUNT(*) AS p16,
  COUNT(DISTINCT email)           / COUNT(*) AS full
FROM users;
-- 若 p12 ≈ full，取 12 即可

ALTER TABLE users ADD INDEX idx_email(email(12));

前缀索引的缺点：不能用于覆盖索引（叶节点存的是截断值，不是完整值，查询还是要回表）；也不能用于 ORDER BY 排序（截断值和完整值排序结果可能不同）。

索引维护：清理冗余与未使用的索引
-- 查找冗余索引（前缀覆盖关系）
SELECT * FROM sys.schema_redundant_indexes
WHERE table_schema = 'your_db';

-- 查找从未被使用的索引（MySQL 5.7+，基于 performance_schema）
SELECT * FROM sys.schema_unused_indexes
WHERE object_schema = 'your_db';

-- 查看索引使用统计
SELECT index_name, rows_selected, rows_inserted, rows_updated, rows_deleted
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE object_schema = 'your_db' AND object_name = 'orders';

每个多余的索引在 INSERT / UPDATE / DELETE 时都需要额外维护一棵 B+树，大表高并发写入时代价显著。定期清理冗余和未使用的索引是 DBA 的基本工作。

索引设计 Checklist
① 先梳理高频查询，再针对性建索引（而不是先建索引再看效果）
② WHERE / JOIN ON / ORDER BY 列优先考虑，等值列在前，范围列在后
③ 必要时在索引末尾追加列消灭回表
④ 字符串列评估区分度，考虑前缀索引
⑤ 主键用自增整型或趋势递增 ID，避免随机 UUID
⑥ EXPLAIN 验证：type 列至少达到 range，最好 ref 或 eq_ref
⑦ 定期用 sys.schema_unused_indexes 清理无效索引
