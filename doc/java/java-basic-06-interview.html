Q1 Java 面向对象三大特性是什么？各自的含义？ 高频▼
面试官视角

考查对 OOP 核心概念的理解，是基础中的基础。结合代码或实际例子解释更佳，能说出"多态条件"和"成员变量不多态"是加分项。

参考回答
  • 封装将数据和操作封装在类中，通过 private/protected/public 控制访问权限，隐藏实现细节，降低耦合。比如 JavaBean 的 getter/setter。
  • 继承子类复用父类代码（extends），支持代码重用，体现 is-a 关系。Java 只支持单继承，但可实现多接口。
  • 多态同一类型引用，指向不同子类对象时表现出不同行为（动态绑定）。编译期看左边类型，运行期看实际对象类型（虚方法表）。多态三条件：继承 + 重写 + 父类引用指向子类对象。
注意：成员变量不存在多态，访问的是引用类型的变量；只有方法调用才动态绑定。

Q2 接口和抽象类的区别？各自适用场景？ 高频重点▼
面试官视角

考查设计能力，希望听到 is-a vs can-do、代码复用 vs 行为契约的本质区别，而不只是语法差异的罗列。

参考回答
维度抽象类接口
构造器有无
成员变量可有实例变量只有 public static final 常量
方法可有具体方法JDK8+ 可有 default/static 方法
继承限制单继承可实现多个接口
设计语义is-a，代码复用（模板方法）can-do，行为契约（依赖倒置）

选择原则：有代码复用需求且有明确 is-a 关系 → 抽象类；只需行为约束且可能多实现 → 接口。Spring 的 AbstractBeanFactory 是抽象类，Comparable / Serializable 是接口。

Q3 方法重写（Override）和重载（Overload）的区别？ 高频▼
面试官视角

基础题，考查是否清楚编译期 vs 运行期绑定的本质，以及不能重写 static/final/private 的原因。

参考回答
  • 重写发生在子父类之间，方法签名（名+参数列表）完全相同，返回类型可协变，访问权限 ≥ 父类，运行时动态绑定（多态基础）。不能重写 static/final/private 方法。
  • 重载同一类中，方法名相同但参数列表不同（类型/数量/顺序），编译期静态绑定，返回类型和访问权限无要求。
// 重写：运行时决定调用哪个
Animal a = new Dog(); a.speak(); // 调用 Dog.speak()

// 重载：编译时决定调用哪个
void print(int i) {}
void print(String s) {}  // 参数类型不同，编译器区分
Q4 多态的底层实现原理是什么？虚方法表如何工作？ 重点▼
面试官视角

深挖底层，考查对 JVM 虚方法表机制的理解，能说出 invokevirtual 和 invokeinterface 的候选人层次明显更高。

参考回答

Java 多态通过 虚方法表（vtable） 实现：

  • ①每个类在类加载时建立虚方法表，存储可重写方法的实际入口地址
  • ②子类方法表从父类继承，如果重写则替换对应入口；未重写则指向父类方法
  • ③JVM 通过 invokevirtual 指令，根据实际对象类型查虚方法表，找到正确方法入口
  • ④接口调用用 invokeinterface，无固定偏移量，需遍历接口表，效率略低

Q5 为什么重写 equals() 必须同时重写 hashCode()？ 高频重点▼
面试官视角

基础中的重点，直接关系到 HashMap/HashSet 的正确使用。能说出"先比 hashCode 定桶，再 equals 比较"的候选人更优秀。

参考回答

契约：equals 相等的对象，hashCode 必须相等（反之不要求）。

原因：HashMap/HashSet 先比 hashCode 定桶，再 equals 比较对象。如果只重写 equals 不重写 hashCode，两个逻辑相等的对象哈希值不同，落入不同桶，导致 HashMap 找不到已存对象，Set 出现重复元素。

// 反例：不重写 hashCode
User u1 = new User(1L, "Alice");
User u2 = new User(1L, "Alice");
u1.equals(u2) == true;          // 重写了 equals 相等
set.add(u1); set.contains(u2);  // ❌ 可能返回 false！hashCode 不同落入不同桶

Q6 String 为什么设计成不可变？有什么好处？ 高频▼
面试官视角

考查对不可变对象设计优势的理解，顺带可延伸到字符串常量池，以及 StringBuilder vs StringBuffer 的选择。

参考回答

设计：内部 byte[]（JDK9+）/ char[]（JDK8）被 private final 修饰，且类本身是 final，防止子类破坏不变性。

  • ①字符串常量池：不可变才能安全共享同一对象，节省内存。"abc" == "abc" 为 true
  • ②哈希缓存：hashCode 只计算一次（懒计算后缓存），HashMap key 性能好
  • ③线程安全：不可变对象天然线程安全，无需同步
  • ④安全性：类路径、网络连接等 String 参数不可被修改，防止安全漏洞

  │

Q10 HashMap 扩容机制？JDK7 多线程死循环问题？ 重点▼
面试官视角

深入考查扩容细节和线程安全问题，体现对底层的掌握深度。能说出"头插法导致环形链表"是核心得分点。

参考回答

JDK8 扩容优化：扩容为 2 倍时，元素新索引只有两种情况：原位置不变（高位为 0），或原位置 + oldCap（高位为 1）。无需重新计算 hash，效率高。

JDK7 死循环：JDK7 用头插法，多线程并发扩容时，链表节点的 next 指针形成环，导致 get() 死循环（CPU 100%）。JDK8 改为尾插法解决，但 HashMap 仍然线程不安全（多线程 put 可能数据丢失），生产必须用 ConcurrentHashMap。

常见误区：很多人以为 JDK8 解决了线程安全问题，实际上只是解决了死循环，并发 put 仍然会丢数据。
Q11 如何用 LinkedHashMap 实现 LRU 缓存？ 重点▼
面试官视角

LRU 是面试高频算法题，考查对 LinkedHashMap 访问顺序模式的理解，能直接写出代码是最好的展示。

参考回答
class LRUCache<K,V> extends LinkedHashMap<K,V> {
    private final int capacity;
    LRUCache(int cap) {
        super(cap, 0.75f, true);  // accessOrder=true：访问时移到链表尾部
        this.capacity = cap;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K,V> eldest) {
        return size() > capacity;  // 超容量时删除链表头（最久未访问）
    }
}
LRUCache<Integer,Integer> cache = new LRUCache<>(3);
cache.put(1,1); cache.put(2,2); cache.put(3,3);
cache.get(1);   // 1 变为最近访问（移到尾部）
cache.put(4,4); // 容量满，删除最久未访问的 2
Q12 什么是 fail-fast 机制？如何在迭代时安全删除元素？ 高频▼
面试官视角

考查集合迭代陷阱的理解，实际开发中的常见 Bug。for-each 循环内直接 remove 会抛异常这个经历很多人都有。

参考回答

fail-fast 通过 modCount 记录集合结构修改次数。迭代器每次 next() 时检查 modCount == expectedModCount，不一致抛 ConcurrentModificationException。

安全删除的三种方式：

  • ①Iterator.remove()（会同步 expectedModCount，最安全）
  • ②list.removeIf(predicate)（JDK8，推荐，最简洁）
  • ③遍历副本或使用 CopyOnWriteArrayList（fail-safe，读写不共享数组）
Q13 ConcurrentHashMap 在 JDK7 和 JDK8 中的区别？ 高频重点▼
面试官视角

并发集合是面试必考点，JDK7 Segment 分段锁 vs JDK8 CAS+synchronized 的演进体现对锁粒度优化的理解。

参考回答
  • JDK7分段锁（Segment），每个 Segment 继承 ReentrantLock，锁粒度为 Segment（默认 16 个），最大并发度为 16。
  • JDK8取消 Segment，改用 CAS + synchronized，锁粒度细化到每个桶的头节点。put 时若桶为空用 CAS 插入，否则 synchronized 锁头节点，并发度大幅提升（接近 O(1) 锁操作）。
  • size()用 LongAdder 思想的 CounterCell 数组，分散计数，减少 CAS 竞争，解决高并发下 size 统计的性能问题。

Q15 Java 泛型的类型擦除是什么？有什么限制？ 高频重点▼
面试官视角

泛型是中高级 Java 必考题，类型擦除是很多框架实现的基础，能说出 TypeReference 的原理是加分项。

参考回答

Java 泛型是"伪泛型"：编译后类型参数被擦除，替换为 Object（无界）或上界类型，编译器自动插入强制类型转换。

限制：

  • ①不能 new T() / new T[]（运行时不知道类型）
  • ②不能 instanceof List<String>（擦除后都是 List）
  • ③静态成员不能使用类泛型参数

运行时获取泛型：通过匿名子类 + getGenericSuperclass() 获取 ParameterizedType（Jackson、Gson 的 TypeReference 原理）。

Q16 什么是 PECS 原则？上界和下界通配符的区别？ 重点▼
参考回答

PECS：Producer Extends，Consumer Super。

  • ? extends T（上界）：可读不可写，用于生产者（读取数据来处理），如 Collections.sort(List<? extends Comparable>)
  • ? super T（下界）：可写不可读（只能读为 Object），用于消费者（写入数据），如 Collection.addAll(Collection<? super E>)
// Collections.copy 同时用了两种
public static <T> void copy(List<? super T> dest, List<? extends T> src)
//                               消费者(写入)            生产者(读取)
Q17 反射的原理是什么？性能影响如何？ 高频▼
面试官视角

框架基础，考查对反射性能代价的认知，以及实际使用中如何优化（缓存 Method 对象）。

参考回答

反射通过 JVM 运行时的类元数据（存于方法区/Metaspace）访问类的结构（字段、方法、构造器）。

性能影响（约慢 1-2 个数量级）：

  • ①需要检查访问权限（setAccessible(true) 可绕过，但有安全风险）
  • ②参数装箱/拆箱、数组包装开销
  • ③无法被 JIT 内联优化

优化：缓存 Method/Field 对象，避免重复 getDeclaredMethod。Spring、MyBatis 大量使用反射但都有缓存机制。

Q19 注解的原理是什么？@Retention 三个级别的区别？ 重点▼
参考回答

注解本质是特殊接口（extends Annotation），通过反射在运行时读取（RUNTIME 级）或在编译时处理（SOURCE/CLASS 级，APT）。

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)  // 运行时保留，可通过反射读取
public @interface Log {
    String value() default "";
}
// 运行时读取
if (method.isAnnotationPresent(Log.class)) {
    String v = method.getAnnotation(Log.class).value();
}
  • SOURCE编译后丢弃，用于代码生成（Lombok @Data）
  • CLASS保留在 class 文件，运行时不可读，用于字节码工具（默认）
  • RUNTIME运行时保留，可通过反射读取（Spring @Transactional、@Autowired）

Q22 try-with-resources 是什么？finally 中 return 有什么问题？ 重点▼
面试官视角

实际编程规范题，考查资源管理和异常抑制机制。finally return 吞异常是很多人不知道的陷阱。

参考回答

try-with-resources（JDK7）：实现 AutoCloseable 的资源自动关闭，编译器生成 finally 块，并通过 addSuppressed() 保留 close() 中的异常（不丢失原始异常）。

try (InputStream in = new FileInputStream("f");
     Connection conn = dataSource.getConnection()) {
    // 使用资源，自动按声明逆序关闭
} // 等价于带 addSuppressed 的 finally 块

finally return 陷阱：finally 中的 return 会覆盖 try 中的 return，甚至吞掉 try 块中的异常，强烈不建议在 finally 中使用 return。

面试陷阱：try{ return 1; } finally{ return 2; } 最终返回 2，try 块的 return 被覆盖。

NIO: Thread ──轮询──> Selector ──就绪──> Channel read
AIO: Thread ──注册──> OS ──完成回调──> Handler
  • BIO同步阻塞，一连接一线程，C10K 问题（1万并发=1万线程），简单但不可扩展
  • NIO同步非阻塞，多路复用，单线程处理多连接（Selector），Netty 基于此实现
  • AIO异步非阻塞，注册回调，OS 完成后通知。Linux 基于 epoll 模拟，Windows 原生 IOCP

Q27 Stream 流的惰性求值是什么？并行流有哪些注意事项？ 高频▼
参考回答

惰性求值：中间操作（filter/map/sorted）不立即执行，只在终结操作（collect/forEach/count）触发时，构建执行管道一次性处理数据，可进行短路优化（如 findFirst 找到后不继续处理）。

并行流注意事项：

  • ①使用 ForkJoinPool.commonPool()，与整个 JVM 共享，会影响其他并行操作
  • ②数据量小时线程开销反而更慢（通常 10000+ 元素才有收益）
  • ③操作必须无副作用，避免共享变量（使用 Collectors.toList() 是安全的）
  • ④流只能消费一次，重复终止操作抛 IllegalStateException
Q28 Optional 的正确使用方式？不应该用在哪些场合？ 重点▼

Q29 JDK8 新时间 API 为什么要替代 Date/Calendar？ 高频▼
参考回答

Date/Calendar 的问题：Date 可变，线程不安全；Calendar API 繁琐，月份从 0 开始（1月=0）；SimpleDateFormat 非线程安全，多线程需 ThreadLocal 包装。

java.time 的优势（JSR-310）：

  • ①不可变，天然线程安全，DateTimeFormatter 可静态常量共享
  • ②API 清晰：LocalDate（日期）/ LocalDateTime（日期时间）/ Instant（时间戳）/ ZonedDateTime（带时区）/ Duration（时间段）
  • ③更好的时区支持（ZoneId.of("Asia/Shanghai")）
Q30 Record 类是什么？和普通类有什么区别？ 重点▼
面试官视角

JDK16 正式特性，体现对现代 Java 的了解。能说出 Record 的限制（不能 extends 普通类）是加分项。

参考回答

Record（JDK16 正式）：不可变数据载体，自动生成构造器、accessor 方法（无 get 前缀）、equals、hashCode、toString。

record Point(int x, int y) {}
// 等价于一个不可变类，字段 private final
Point p = new Point(3, 4);
p.x();  // 访问器，不是 getX()

// 限制：不能 extends 类（隐式继承 java.lang.Record），可实现接口
// 不能有实例字段（只有 record 组件），但可有静态字段和自定义方法

适用：DTO、Value Object、API 响应对象，配合 Sealed 类实现代数数据类型。

Q31 JDK21 的虚拟线程是什么？解决了什么问题？有什么限制？ 高频重点▼
面试官视角

JDK21 最重要特性，体现对 Java 发展趋势的了解。能说出"synchronized 块中阻塞会 pin 住平台线程"是加分项。

参考回答

虚拟线程（Project Loom）：JVM 管理的轻量级线程，多对多映射到平台线程（OS 线程）。

  • 解决问题BIO 一连接一线程无法扩展（C10K），NIO 编程模型复杂。虚拟线程阻塞时自动卸载平台线程，不占用 OS 线程，可创建百万级并发。
  • 使用方式Thread.ofVirtual().start(task) 或 Executors.newVirtualThreadPerTaskExecutor()
  • 限制不适合 CPU 密集型任务；synchronized 块中阻塞会 pin 住平台线程（推荐改用 ReentrantLock）；Spring Boot 3.2+ 可自动为 Tomcat 启用虚拟线程。
Q32 接口 default 方法解决了什么问题？多 default 方法冲突如何处理？ 重点▼
参考回答

解决问题：Java 集合接口升级（如 Collection.stream()、List.sort()）时，若不加 default 则所有已有实现类都需修改，破坏向后兼容性。JDK8 通过 default 方法实现接口的非破坏性演进。

冲突处理（优先级规则）：

  • 1类或父类的具体方法（最高优先级）
  • 2子接口的 default 方法（接口继承层次越深越优先）
  • 3多个接口的 default 方法平级冲突 → 实现类必须显式重写，否则编译报错
interface A { default void hi() { /* A */ } }
interface B { default void hi() { /* B */ } }
class C implements A, B {
    @Override public void hi() { A.super.hi(); }  // 必须显式选择
}
