01Spring 事务抽象
PlatformTransactionManager

Spring 定义了统一的事务管理接口 PlatformTransactionManager，屏蔽底层不同数据访问技术的事务实现差异：

public interface PlatformTransactionManager {
    // 开启事务（根据 TransactionDefinition 定义传播行为/隔离级别等）
    TransactionStatus getTransaction(TransactionDefinition definition);
    // 提交事务
    void commit(TransactionStatus status);
    // 回滚事务
    void rollback(TransactionStatus status);
}

ReactiveTransactionManager响应式编程（R2DBC）

04@Transactional 详解
常用属性速查
@Transactional(
    propagation = Propagation.REQUIRED,       // 传播行为
    isolation = Isolation.DEFAULT,            // 隔离级别
    timeout = 30,                             // 超时时间（秒），-1 表示永不超时
    readOnly = false,                         // 只读优化
    rollbackFor = Exception.class,            // 触发回滚的异常类型
    noRollbackFor = BusinessException.class   // 不触发回滚的异常类型
)
默认行为：不指定 rollbackFor 时，只对 RuntimeException 和 Error 回滚，checked 异常（如 IOException）不回滚。建议显式配置 rollbackFor = Exception.class。
05@Transactional 失效场景
7 种常见失效场景
失效①
方法非 public
Spring AOP 基于代理，无法拦截非 public 方法（CGLIB 子类覆盖限制）。解决：改为 public。
失效②
同类自调用（this.method()）
this 指向原始对象，绕过代理。解决：注入自身代理或用 AopContext.currentProxy()。
失效③
异常被 catch 吞掉
try-catch 内没有 rethrow，事务感知不到异常，正常提交。解决：catch 后重新抛出或手动调用 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()。
失效④
异常类型不匹配
默认只回滚 RuntimeException 和 Error，抛 checked 异常不回滚。解决：配置 rollbackFor = Exception.class。
失效⑤
多线程操作
事务上下文绑定在 ThreadLocal，子线程无法继承父线程的事务，子线程操作不在事务内。
失效⑥
数据库引擎不支持事务
MySQL MyISAM 不支持事务，InnoDB 才支持。检查建表语句的 ENGINE 设置。
失效⑦
传播行为配置问题
如配置了 PROPAGATION_NOT_SUPPORTED（挂起当前事务）或调用方未开启事务而被调用方使用了 MANDATORY。
06编程式事务
TransactionTemplate 使用

声明式事务是方法级别的粗粒度控制，编程式事务可精确到代码块：

@Autowired
private TransactionTemplate transactionTemplate;

public void batchProcess(List<Item> items) {
    for (Item item : items) {
        // 每条数据独立事务，互不影响
        transactionTemplate.execute(status -> {
            try {
                itemDao.save(item);
                return null;
            } catch (Exception e) {
                status.setRollbackOnly(); // 手动标记回滚
                log.error("item {} 处理失败", item.getId());
                return null;
            }
        });
    }
}

适用场景：循环体内细粒度事务控制、根据运行时条件动态决定是否开事务、只有方法中几行代码需要事务保护。

08TransactionSynchronizationManager
TSM 是什么 & 工具方法速查

TransactionSynchronizationManager（TSM） 是 Spring 事务体系的 ThreadLocal 存储中枢，所有事务管理器在开启 / 提交 / 回滚事务时都通过 TSM 读写当前线程的事务上下文。

ThreadLocal 存储内容：

字段作用
resources（Map）DataSource → Connection 映射，保证同一事务内复用同一连接
synchronizations（Set）注册的 TransactionSynchronization 回调集合
currentTransactionName当前事务名（格式 类名.方法名），用于日志 / APM 监控
currentTransactionReadOnly是否只读事务，读写分离路由的核心判断依据
currentTransactionIsolationLevel当前隔离级别（Connection.TRANSACTION_* 常量值）
actualTransactionActive当前线程是否真正激活了物理事务

常用静态工具方法：

方法返回值说明
isActualTransactionActive()boolean是否有物理事务激活，注册回调前必须先判断
isSynchronizationActive()boolean同步上下文是否激活（弱于上面：SUPPORTS 传播下有差异）
isCurrentTransactionReadOnly()boolean是否只读事务，AbstractRoutingDataSource 路由从库时常用
getCurrentTransactionName()String获取当前事务名，用于日志追踪
getCurrentTransactionIsolationLevel()Integer获取当前隔离级别
getResource(key) / hasResource(key)Object / boolean读取 / 判断线程绑定的资源（多数据源场景）
bindResource(key,val) / unbindResource(key)void / Object手动绑定 / 解绑资源（框架级用法，业务代码慎用）
TransactionSynchronization 回调接口 & 注册写法

通过 TSM.registerSynchronization() 向当前事务注册生命周期回调：

回调方法触发时机典型用途
beforeCommit(readOnly)提交前（数据已修改，未提交）额外校验、flush 缓存到 DB
beforeCompletion()提交或回滚之前（含异常场景）关闭资源、释放锁
afterCommit()事务成功提交后发 MQ 消息、清除 Redis 缓存、发邮件
afterCompletion(status)事务完成后（提交 / 回滚均触发）
status: 0=committed 1=rolled_back 2=unknown		统一清理资源、失败告警
// Spring 5.3+：TransactionSynchronization 接口方法均有 default 空实现
// 直接匿名实现，只重写需要的方法即可
if (TransactionSynchronizationManager.isActualTransactionActive()) {
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                // 事务已成功提交，消息不会误发
                mqProducer.sendOrderCreated(order);
            }

            @Override
            public void afterCompletion(int status) {
                if (status == STATUS_ROLLED_BACK) {
                    log.warn("Order {} rolled back, MQ not sent", order.getId());
                }
            }
        }
    );
}
⚠ 前提：registerSynchronization() 必须在激活的事务上下文中调用，否则抛 IllegalStateException。始终先用 isActualTransactionActive() 判断，或确保调用方带有 @Transactional。
afterCommit() 操作 DB 的正确姿势 & 与 @TransactionalEventListener 对比

afterCommit() 执行时原事务已关闭，直接调用默认传播行为（REQUIRED）的 Service 方法会以无事务方式执行，是高频踩坑点：

场景结果风险
调用 @Transactional（REQUIRED）方法 无事务可加入，非事务执行 危险 SQL 无保护，异常不回滚
调用 REQUIRES_NEW 方法 开启全新独立事务 安全 推荐，注意新事务异常处理
用 @Async 切换线程 子线程无事务上下文，自行开事务 安全 异步场景首选 
// ✗ 危险：REQUIRED 方法在 afterCommit 中实际无事务保护
public void afterCommit() {
    auditService.log(order);  // @Transactional(REQUIRED) — 无事务！
}

// ✓ 方案一：显式用 REQUIRES_NEW 开新事务
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void log(Order order) { ... }

// ✓ 方案二：@Async 切新线程，线程内自行开事务
public void afterCommit() {
    asyncService.doAfterCommit(order); // 子线程：@Async + @Transactional
}
⚠ ThreadLocal 不跨线程：@Async 切换后，子线程 isActualTransactionActive() 必然为 false，不要期望子线程能访问父线程的事务上下文。

TSM 手动注册 vs @TransactionalEventListener：

维度TSM.registerSynchronization()@TransactionalEventListener
代码量匿名类，稍繁琐注解声明，极简
与业务耦合回调写在 Service 方法内Listener 与 Service 完全解耦
无事务 fallback自行判断 isActualTransactionActive()有 fallbackExecution 参数
