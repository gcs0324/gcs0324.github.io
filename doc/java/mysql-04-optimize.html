01EXPLAIN 全字段精读
type 列 — 访问类型（最重要的字段）

type 列描述 MySQL 找到行的方式，性能从好到差排列。生产环境目标：至少达到 range，最好 ref 或 eq_ref。ALL 必须优化。

system
表只有一行数据（系统表）。特殊情况，几乎不出现在业务表中。
const
主键或唯一索引等值查询，最多返回一行。优化器将结果视为常量。
例：WHERE id = 5（id 是主键）
eq_ref
JOIN 时被驱动表用主键/唯一索引等值查找，每个驱动表行最多匹配一行。最优的 JOIN 类型。
例：FROM a JOIN b ON a.id = b.id（b.id 是主键）
ref
非唯一索引等值查询，可能返回多行。
例：WHERE user_id = 100（user_id 有普通索引，非唯一）
range
索引范围扫描。> / < / BETWEEN / IN / LIKE 'x%' 等。
索引有效，只扫描一段范围，可接受。
index
全索引扫描（扫整棵二级索引树）。虽走了索引，但扫描量大。常见于覆盖索引但没有 WHERE 条件。
比 ALL 好（只扫索引不读行数据），但仍需关注。
ALL
全表扫描。最差。扫描所有行，IO 和 CPU 最高。必须优化：检查 WHERE 条件是否能加索引或改写。
key_len — 索引使用长度计算

key_len 显示优化器实际用到的索引长度（字节），可以判断联合索引用了几列。

数据类型key_len 计算示例
INT NOT NULL44
INT NULL4 + 1（null 标志位）5
BIGINT NOT NULL88
VARCHAR(n) NOT NULL, utf8mb4n × 4 + 2（长度字节）VARCHAR(50) → 202
VARCHAR(n) NULL, utf8mb4n × 4 + 2 + 1VARCHAR(50) → 203
CHAR(n) NOT NULL, utf8mb4n × 4CHAR(10) → 40
DATETIME NOT NULL5（5.6.4+ 精简格式）5
-- 联合索引 (user_id BIGINT NOT NULL, status TINYINT NOT NULL)
-- 如果 key_len=8 → 只用了 user_id
-- 如果 key_len=9 → 用了 user_id + status
-- 可以判断 WHERE 条件有没有用到后续列

②

# 输出按响应时间总量排序的 TOP SQL，附带调用次数、平均/最大耗时、示例 SQL

③

对问题 SQL 执行 EXPLAIN（或 EXPLAIN FORMAT=JSON 获取代价信息），重点检查：type 是否 ALL、有没有 Using temporary/filesort、key 是否正确。
④
针对性优化
— 缺索引 → 加索引（注意等值在前、范围在后、覆盖查询列）

03JOIN 优化
Nested Loop Join（NLJ）— 最常见的 JOIN 算法

MySQL 最基本的 JOIN 算法：从驱动表取一行，到被驱动表用索引查匹配行，逐行循环。

-- 驱动表：orders（WHERE 条件过滤后小结果集）
-- 被驱动表：order_items（大表，需要在 order_id 上有索引）
SELECT o.*, oi.product_id
FROM orders o
JOIN order_items oi ON o.id = oi.order_id   -- oi.order_id 必须有索引！
WHERE o.user_id = 100;

NLJ 的时间复杂度 = 驱动表扫描行数 × 被驱动表每次查找代价。被驱动表有索引时，每次查找是 O(log n)；无索引时退化为全表扫描，极慢。

被驱动表的 JOIN 列必须有索引。没有索引时，EXPLAIN 会显示 Using join buffer (Block Nested Loop)，MySQL 把驱动表放入 join_buffer（默认 256KB），与被驱动表做笛卡尔积过滤，IO 量 = 驱动表行数 × 被驱动表行数，百万级数据下几乎不可接受。
Hash Join（MySQL 8.0.18+）

8.0.18 引入 Hash Join：把小表（驱动表）的 JOIN 列构建 Hash 表放入内存，然后扫描大表（被驱动表）逐行用 Hash 查找匹配。

  • 适用被驱动表无法使用索引的等值 JOIN，此时 Hash Join 比 BNL 快得多
  • 限制只支持等值 JOIN（=）；Hash 表需放入内存（join_buffer_size），超出则落磁盘
  • 识别EXPLAIN Extra: Using join buffer (Hash join)

即使有 Hash Join，也应尽量给 JOIN 列加索引，NLJ + 索引的效率在大多数场景仍优于 Hash Join。

驱动表选择与优化原则
  • 小表驱动大表过滤后行数少的表作为驱动表，减少循环次数。MySQL 优化器通常能自动选择，但统计信息不准时可能选错。
  • IN vs EXISTSIN (SELECT ... FROM small_table) ≈ 小表驱动，适合子查询结果集小；EXISTS (SELECT 1 FROM large_table WHERE ...) ≈ 大表驱动，适合外表结果集小。两者的实际性能取决于子查询结果集大小，需 EXPLAIN 验证。
  • STRAIGHT_JOIN强制左边的表作为驱动表：SELECT ... FROM a STRAIGHT_JOIN b ON ...。优化器选错驱动表时使用。
  • 减少 JOIN 层数多表 JOIN 超过 3 张时，优化器选择执行顺序的组合数指数增长（n! 复杂度），建议业务层拆分为多次查询。
04分页优化
LIMIT offset 的代价

SELECT * FROM orders ORDER BY id LIMIT 100000, 20 看起来只返回 20 行，但 MySQL 实际上要扫描前 100020 行，丢弃前 100000 行，只返回后 20 行。随着 offset 增大，扫描量线性增长，到第 10 万页时已经极慢。

-- 验证：两条语句扫描行数相差 100000 倍
EXPLAIN SELECT * FROM orders LIMIT 20;            -- rows ≈ 20
EXPLAIN SELECT * FROM orders LIMIT 100000, 20;    -- rows ≈ 100020
三种优化方案
方案1
延迟关联（Deferred Join / Late Row Lookup）
先用子查询在覆盖索引上快速拿到目标页的主键 ID，再用主键回表取完整数据。
核心思路：把"扫描+回表"拆成"扫描（覆盖索引，快）+ 小批量回表（按 ID，精准）"。 
-- 原查询（慢）
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;

-- 延迟关联（快）
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 20) AS t
ON o.id = t.id;
效果：子查询只扫索引（覆盖索引，Using index），不回表；JOIN 只用 20 次精准主键查找。
方案2
游标分页（Cursor Pagination / Seek Method）
记录上一页最后一行的 ID（或排序列值），下一页用 WHERE id > last_id LIMIT 20。
完全消灭 offset 扫描，无论翻到第几页，扫描量恒定为 20 行。 
-- 第一页
SELECT id, user_id, amount FROM orders WHERE user_id=1 ORDER BY id LIMIT 20;
-- 假设最后一行 id = 1500

-- 下一页（使用游标，O(1) 定位）
SELECT id, user_id, amount FROM orders
WHERE user_id=1 AND id > 1500 ORDER BY id LIMIT 20;
限制：不支持随机跳页（无法直接跳到第 5000 页）；排序列必须有索引且唯一（或组合唯一）。适合"下拉加载更多"交互。
方案3
业务层约束最大页数
强制限制用户最多翻到第 N 页（如第 200 页），超出返回空结果或提示"请细化搜索条件"。
适合搜索场景，用户很少会真的翻到第 1000 页，产品设计上直接规避深分页。
05count 优化
count(*) vs count(1) vs count(id) vs count(非空列)
写法行为性能
count(*)统计所有行，包括 NULL 行；InnoDB 优化器会选最小的索引（或主键）扫描，不读行数据最优（MySQL 专门优化）
count(1)与 count(*) 完全等价，MySQL 8.0 优化器处理方式相同与 count(*) 相同
count(id)（主键）统计主键非 NULL 的行数；主键不可能为 NULL，等价于 count(*)，但需要读主键列值稍逊于 count(*)
count(非主键列)统计该列非 NULL 的行数；若列可为 NULL，结果可能小于总行数；需读该列值判断是否 NULL最慢，需判断 NULL

结论：统一用 count(*)，可读性好，且 MySQL 专门优化。

为什么 InnoDB count(*) 比 MyISAM 慢

MyISAM 在表的元数据中记录了总行数，SELECT count(*) FROM t（无 WHERE 条件）直接返回，O(1)。

InnoDB 不记录总行数（因为 MVCC：不同事务看到的行数可能不同），必须扫描一遍才能得到当前事务视图下的行数。优化器选最小的二级索引扫描（比主键索引小），但仍是 O(n)。

-- InnoDB 大表 count(*) 的替代方案：
-- 1. 缓存行数（Redis INCR/DECR，写入时+1，删除时-1）
-- 2. 单独维护计数表（事务内同时更新业务表和计数表，保证原子性）
-- 3. 业务允许近似值时：SHOW TABLE STATUS LIKE 'orders' → Rows 列（估算值）
-- 4. information_schema.TABLES.TABLE_ROWS（同上，估算）
06主从复制
异步复制流程
MySQL 主从复制三个核心线程
三种复制模式
异步复制（默认）
主库提交事务后立即返回客户端，不等待从库确认。

风险：主库崩溃后，未同步到从库的事务丢失，主从数据不一致。
半同步复制
主库提交后，等待至少一个从库确认收到 binlog（写入 relay log 即可，不等 SQL Thread 执行），再返回。

保证至少一份副本有数据，主库崩溃不丢事务，但增加提交延迟约 1 个 RTT。
GTID 复制（推荐）
每个事务有全局唯一 ID（GTID = server_uuid:seq_no）。从库通过 GTID 自动定位同步位点，主从切换无需手动指定 binlog 文件和位置，大幅简化运维。

MySQL 5.6+ 推荐使用。
主从延迟排查与优化
-- 查看从库延迟
SHOW SLAVE STATUS\G
-- 关注 Seconds_Behind_Master（SQL Thread 落后主库的秒数）
-- 若 Seconds_Behind_Master 持续增大，说明 SQL Thread 回放速度跟不上

-- 常见原因：
-- 1. 主库有大事务（单个 binlog event 很大，SQL Thread 回放慢）
-- 2. 主库并发写入高，从库单线程 SQL Thread 追不上（5.6 以前）
-- 3. 从库服务器性能差（CPU/IO 不足）
优化手段说明
并行复制（MTS）5.6+ 多线程 SQL Thread，按库（5.6）或按事务组（5.7 LOGICAL_CLOCK）并行回放。设置 slave_parallel_workers=8
半同步 + 并行复制组合使用，既保证不丢数据，又加快从库追赶速度
从库使用 SSDIO 是回放瓶颈时，换 SSD 直接见效
拆分大事务根本方案，避免主库产生大事务 binlog event
读写分离中间件感知延迟ShardingSphere / MyCat 等中间件可读取 Seconds_Behind_Master，延迟超阈值时自动路由到主库
07分库分表
垂直拆分 vs 水平拆分
垂直分库（按业务）
把不同业务模块的表拆到不同数据库实例（用户库、订单库、商品库）。

解决：单实例连接数/并发上限；不同业务独立扩容。
问题：跨库 JOIN 消失，需应用层聚合；分布式事务问题。
水平分表（按数据量）
同一张表按 sharding key 分散到多个表/库（orders_0、orders_1…orders_n）。

解决：单表数据量超过 2000 万行后的性能问题。
问题：跨分片查询、全局唯一 ID、分布式事务。
Sharding Key 选择原则
  • ①业务最常用的查询维度：订单按 user_id 分片（绝大多数查询都带 user_id）；日志按时间分片（按月查询）
  • ②数据分布均匀：避免 hotspot——如果按 user_id hash 分片，热门用户集中在少数分片会导致不均
  • ③尽量不改：sharding key 一旦确定很难修改，修改需要迁移所有数据
  • ④避免跨分片查询：选择能覆盖 80% 以上查询的维度作为 sharding key
全局唯一 ID 方案
方案实现优点缺点
UUID v4随机 128 位实现简单随机写，页分裂严重；太长（36 字符）
数据库自增（号段模式）每次取一段 ID（如 1000 个）缓存本地趋势递增，无页分裂依赖 DB，需单独维护 ID 生成服务
雪花 ID（推荐）64 位 = 时间戳 41 + 机器 ID 10 + 序列 12趋势递增，高并发（约 400 万/秒/节点），无 DB 依赖时钟回拨问题（需处理）
UUID v7前 48 位是毫秒时间戳，保证时序有序有序，标准化，无需部署 ID 服务128 位仍然较长
分库分表的难题
  • 跨分片查询涉及多个分片的 ORDER BY / GROUP BY / JOIN，需要中间件（ShardingSphere / Vitess）在内存中聚合，代价极高，建议业务设计时尽量避免
  • 分布式事务跨分片写操作无法用本地事务保证原子性，需引入 2PC / Saga / TCC 等方案，复杂度大增
  • 数据迁移从单库迁移到分库分表，需要双写 + 数据校验 + 切流，通常需要 2~4 周停机窗口（或在线迁移方案）
  • 扩容再分片分片数固定后扩容需要重新 rehash，建议一开始就按足够多分片（如 1024），每个物理库承载多个逻辑分片，扩容时只需迁移逻辑分片

读写分离注意事项
  • 主从延迟导致读到旧数据写操作后立刻读，可能路由到有延迟的从库，读到写前的数据。解决：写后读策略路由到主库；或用 select ... master_bind；或 ProxySQL 的会话黏性
  • 事务内读必须走主库事务内的读操作必须路由到主库，否则读到的数据与事务的写操作不一致
  • 中间件选型ProxySQL（轻量，规则灵活）/ ShardingSphere-Proxy（功能全，分库分表 + 读写分离）/ MyCat

工具原理锁表时间适用场景

性能调优思路总结：
① 慢查询 → EXPLAIN → 索引优化是第一优先级（80% 的慢查询是索引问题）
② 大偏移分页 → 游标分页或延迟关联
③ count(*) 大表 → 缓存计数，接受近似值
