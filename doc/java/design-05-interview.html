Q1 单例模式有哪几种实现方式？各自的优缺点？ 高频重点 ▾
考察点

单例是最高频的设计模式题，重点考查 DCL 和静态内部类实现，能说清线程安全原理加分。

参考回答
实现方式线程安全懒加载推荐度
饿汉式（static final）✅ JVM 类加载❌✅ 简单首选
静态内部类✅ JVM 类加载✅⭐ 最推荐
DCL 双重检查✅（必须加 volatile）✅✅ 复杂场景
枚举✅❌✅ 防反射/序列化破坏
懒汉式（synchronized）✅✅❌ 每次加锁性能差
// ⭐ 静态内部类：JVM 类加载保证线程安全 + 懒加载，推荐
public class Singleton {
    private Singleton() {}
    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}

Holder 类只有在第一次调用 getInstance() 时才被加载，JVM 保证类加载的线程安全性，无需额外同步。

Q2 DCL 单例为什么需要 volatile？不加会有什么问题？ 高频重点 ▾
考察点

并发 + 设计模式综合题，考查指令重排序和 happens-before 的深层理解。

参考回答

new Singleton() 非原子操作，JIT 编译后分三步：① 分配内存 → ② 初始化对象 → ③ 将引用指向内存。CPU/JIT 可能重排序为 ①③②。

// 问题场景（不加 volatile）
instance = new Singleton(); // 可能重排序为 ①③②

Thread A: ①分配内存 → ③引用指向内存（instance != null）→ ②初始化...
Thread B: 第一次 check: instance != null → 直接返回半初始化对象 → NPE!

volatile 在写操作后插入 StoreLoad 内存屏障，禁止 ② 和 ③ 的重排序，保证对象完全初始化后引用才对其他线程可见。

  • ▸ volatile 写 happens-before volatile 读
  • ▸ 保证可见性（写后其他线程立即看到新值），但不保证原子性

Q3 工厂方法模式和抽象工厂模式的区别？ 高频 ▾
考察点

两种模式经常混淆，核心区分是"一种产品"vs"产品族"。

参考回答
// 工厂方法：一种产品，子类决定实例化哪个类
interface AnimalFactory { Animal create(); }
class DogFactory implements AnimalFactory { Animal create() { return new Dog(); } }

// 抽象工厂：一族相关产品
interface UIFactory {
    Button createButton();   // 产品1
    Checkbox createCheckbox(); // 产品2
}
class LightUIFactory implements UIFactory { /* 浅色系全套 */ }
class DarkUIFactory  implements UIFactory { /* 深色系全套 */ }
  • ▸ 工厂方法：解决"如何创建一个对象"，通过继承扩展，Spring BeanFactory 是典型
  • ▸ 抽象工厂：解决"如何创建一族相关对象"，切换工厂可整体替换产品族
  • ▸ 抽象工厂增加新产品类型（如 TextField）需修改所有工厂接口，违背开闭原则；但增加新产品族（如新主题）无需修改

Q4 建造者模式解决了什么问题？和构造器有什么区别？ 高频 ▾
考察点

实践型问题，Lombok @Builder 到处在用，考查背后设计思想的理解。

参考回答

解决问题：构造参数 > 4 个时，重叠构造器难以维护；JavaBean 的 setter 方式无法创建不可变对象，且对象可能处于不一致中间状态。

// ❌ 重叠构造器（参数多就噩梦）
new User("Alice", 25, "a@b.com", "Beijing", "13800138000");

// ✅ Builder 模式（参数名即方法名，不可变，可选参数清晰）
User user = User.builder()
    .name("Alice").age(25).email("a@b.com")
    .build(); // 一次性构建，对象不可变

适用场景：参数多且有可选项、需要不可变对象、同一构建过程需要生成不同表示（HTML/PDF 报告）。

Q5 浅拷贝和深拷贝的区别？如何实现深拷贝？ 高频 ▾
考察点

基础题，常结合 BeanUtils.copyProperties 一起考，需说明各方案的副作用。

参考回答
// 浅拷贝：新对象与原对象共享引用类型字段（同一内存地址）
A orig = new A(new B()); A copy = orig.clone();
copy.b.value = 99; // orig.b.value 也变成 99！

// 深拷贝方案1：序列化（最简单，对象需 Serializable）
A deep = SerializationUtils.clone(orig);

// 深拷贝方案2：JSON 转换（transient 字段丢失）
A deep = JSON.parseObject(JSON.toJSONString(orig), A.class);

// 深拷贝方案3：手写 clone()（繁琐但准确）

BeanUtils.copyProperties()：浅拷贝，只复制基本类型值和引用，引用类型字段仍然共享。生产中使用需注意。

Q9 门面模式和中介者模式的区别？ 重点 ▾
考察点

两种"简化交互"的模式，需要明确区分单向简化 vs 多对多协调。

参考回答
  • ▸ 门面（Facade）：为复杂子系统提供简单入口，单向（外部→子系统），子系统不知道门面存在。如 JdbcTemplate 封装 JDBC，SLF4J 封装日志框架。
  • ▸ 中介者（Mediator）：集中管理对象间的多对多通信，各对象只与中介者通信。如 Spring MVC DispatcherServlet（Handler 们不直接通信）、MQ 消息代理、聊天室服务器。

核心区别：门面是单向的简化层；中介者是协调双向复杂交互的中心节点。

Q10 享元模式的原理？Java 中哪些地方用到了？ 高频 ▾
考察点

常通过 Integer 缓存考查，体现对内存优化和对象复用的理解。

参考回答

享元模式：共享细粒度对象，区分内部状态（共享，不变）和外部状态（不共享，按需传入）。

  • ▸ Integer 缓存：-128~127 范围内的 Integer 对象由 IntegerCache 缓存复用，Integer.valueOf(100) == Integer.valueOf(100) 为 true
  • ▸ 字符串常量池：相同字面量共享同一 String 对象
  • ▸ 数据库连接池/线程池：复用 Connection/Thread 对象，最重要的享元实践
  • ▸ Spring 单例 Bean：IoC 容器作为享元工厂
Q11 桥接模式解决了什么问题？举例说明 ▾
考察点

相对较难的模式，考查对多维度变化导致类爆炸问题的设计处理。

参考回答

桥接模式解决多维度变化的类爆炸问题：用组合替代继承，将抽象与实现分离，使两个维度可独立扩展。

// 形状 + 颜色两个维度，不用桥接需要 RedCircle/BlueCircle/RedSquare/BlueSquare...
abstract class Shape {
    protected Color color;  // 桥接点（组合而非继承）
    abstract void draw();
}
// 扩展形状：只需新增 Shape 子类
// 扩展颜色：只需新增 Color 实现，互不影响

JDBC 是最佳实例：DriverManager（抽象）+ Driver 接口，MySQLDriver/OracleDriver（实现）独立变化，应用代码面向 JDBC API 无需修改。

Q12 策略模式如何消除大量 if-else？结合 Spring 说明 高频重点 ▾
考察点

最实用的设计模式题，Spring Map 注入是最优雅的落地方案，能写出完整代码加分。

参考回答
// ❌ 传统 if-else（每次新增支付方式都要改）
if ("alipay".equals(type)) { ... }
else if ("wechat".equals(type)) { ... }

// ✅ 策略 + Spring Map 注入（零 if-else，开闭原则）
interface PayStrategy { PayResult pay(PayRequest req); }

@Component("alipay")  class AliPayStrategy  implements PayStrategy { ... }
@Component("wechat")  class WechatPayStrategy implements PayStrategy { ... }

@Service
public class PayService {
    @Autowired
    private Map<String, PayStrategy> strategies; // Spring 自动注入，key=BeanName

    public PayResult pay(String type, PayRequest req) {
        return Optional.ofNullable(strategies.get(type))
            .orElseThrow(() -> new UnsupportedPayTypeException(type))
            .pay(req);
    }
    // 新增支付方式：只需新增 @Component，不改 PayService
}

Q13 责任链模式的应用？Spring Security 的 Filter 链如何工作？ 高频重点 ▾
考察点

责任链是框架底层高频模式，能结合 Spring Security/Dubbo 具体说明更加分。

参考回答

责任链：请求沿处理者链传递，每个处理者决定处理或向下传递，解耦请求发送者与接收者。

// Spring Security Filter 链
SecurityFilterChain:
  UsernamePasswordAuthenticationFilter
    → BasicAuthenticationFilter
    → AuthorizationFilter
    → ExceptionTranslationFilter
    → ...

// 每个 Filter 通过 chain.doFilter() 向下传递
public void doFilter(ServletRequest req, ServletResponse resp, FilterChain chain) {
    // 前置处理（认证/鉴权）
    chain.doFilter(req, resp); // 传递给下一个 Filter
    // 后置处理
}
  • ▸ 新增功能只需插入新 Filter，不修改已有 Filter（开闭原则）
  • ▸ 同类应用：Dubbo Filter 链、Netty ChannelPipeline、MyBatis Interceptor

Q15 模板方法模式和策略模式如何选择？ 重点 ▾
考察点

两种消除代码重复的模式，考查对选型的判断：继承 vs 组合。

参考回答
  • ▸ 模板方法：继承，父类定义算法骨架（不变），子类覆盖特定步骤（可变）。扩展点固定，编译时确定。JdbcTemplate、RestTemplate 是典型。
  • ▸ 策略：组合，整个算法可互换。运行时动态选择，更灵活。

选择原则：算法整体不变、只有某几步不同 → 模板方法；整个算法都可能不同 → 策略。

记忆口诀：模板方法 = 骨架固定，步骤可变（继承）；策略 = 整体可换（组合）

Q17 状态模式和策略模式的区别？订单状态机如何实现？ 重点 ▾
考察点

工程实践题，订单状态流转是常见业务场景，能设计状态机说明有实践经验。

    void ship(Order o)   { throw new InvalidStateException(); } // 禁止

// 状态转换图：待付款 → 已付款 → 已发货 → 已完成
//                  ↘ 已取消

04 设计原则 Q19–Q23
Q19 SOLID 原则分别是什么？结合 Spring 举例 高频重点 ▾
考察点

设计能力的核心题，能结合实际框架举例的候选人远比背定义的优秀。

参考回答
  • S 单一职责：一个类只有一个改变的原因。Controller 处理 HTTP、Service 处理业务、DAO 访问数据。
  • O 开闭原则：对扩展开放，对修改关闭。Spring AOP 用代理扩展功能不修改业务代码；策略模式新增策略不改 Context。
  • L 里氏替换：子类可替换父类。重写方法不应缩窄父类的语义（不能抛更多异常）。
  • I 接口隔离：接口细分，不强迫实现用不到的方法。Spring BeanFactory vs ApplicationContext（后者扩展前者）。
  • D 依赖倒置：高层不依赖低层，都依赖抽象。@Autowired UserService 注入接口而非实现，IoC 容器的核心。

Q21 依赖倒置原则（DIP）、IoC、DI 三者的关系？ 高频 ▾
考察点

IoC/DI 基础题，三个概念层次不同，考查清晰区分的能力。

参考回答
  • ▸ DIP（原则）：高层不依赖低层，都依赖抽象——"依赖接口，而非实现"
  • ▸ IoC（思想）：将对象创建的控制权从调用方反转给容器/框架
  • ▸ DI（实现）：IoC 的具体方式，容器将依赖"注入"给使用者（构造器/setter/@Autowired）

关系链：DIP 是设计原则 → IoC 是实现 DIP 的思想 → DI 是 IoC 的实现手段。Spring 通过 DI 实现 IoC，从而满足 DIP。

Q22 里氏替换原则（LSP）如何避免违反？ 重点 ▾
考察点

LSP 最容易被忽视，正方形继承长方形是经典反例，考查对继承语义的深刻理解。

参考回答

经典违反案例：正方形（Square）继承长方形（Rectangle），设置宽度时同时改高度，导致 Rectangle 的行为在子类中不一致，使用 Rectangle 的代码会产生意外结果。

  • ▸ 子类重写方法不应抛出比父类更宽泛的异常
  • ▸ 子类方法的前置条件（输入约束）不应比父类更严
  • ▸ 子类方法的后置条件（输出约束）不应比父类更宽
  • ▸ is-a 要从行为语义判断，不能只看结构（正方形几何上是长方形，但行为不满足 LSP）
Q23 继承 vs 组合，什么时候优先使用组合？ 高频 ▾
考察点

"优先组合而非继承"是 GoF 核心原则，考查对继承滥用问题的认识。

参考回答
  • ▸ 继承的问题：破坏封装（子类依赖父类实现细节）、继承体系脆弱（父类修改影响所有子类）、Java 单继承限制
  • ▸ 组合的优势：运行时动态替换实现、不依赖父类内部、更灵活的复用

选择规则：只有满足严格 is-a 关系且子类需要重用父类实现时才用继承；否则优先组合（has-a）。策略模式、装饰器模式都是以组合代替继承的典型。

Q24 CAP 定理是什么？ZooKeeper 和 Eureka 各选了什么？ 高频重点 ▾
考察点

参考回答
         Consistency（一致性）
               △
              /|\
             / | \
        CP  /  |  \ （CA 在分布式中不存在）
           /   |   \
          /    |    \
         /─────────── \
Partition Tolerance ── Availability（可用性）
（分区容忍性，必须保证）

CP：ZooKeeper、etcd         → 一致性 > 可用性，分区期间拒绝服务

固定窗口时间窗口内计数，超过则拒绝实现简单边界突刺（窗口切换瞬间2倍流量）简单粗粒度限流

Q27 分库分表的策略？如何选择分片键？ 高频重点 ▾
考察点

大数据量经典解决方案，分片键选择是关键，能说出跨库查询问题加分。

参考回答
  • ▸ 垂直分库：按业务模块拆（用户库/订单库/商品库），降低耦合
  • ▸ 水平分表：同库多表，如 order_0~order_31，按 user_id % 32 路由
  • ▸ 水平分库：数据拆到不同实例，解决连接数/IO 瓶颈

分片键原则：① 分布均匀（避免热点），② 与业务主要查询维度一致（按 user_id 分就要携带 user_id 查），③ 尽量不跨库 JOIN。推荐 user_id 或订单 ID，避免 status 等低基数字段。

跨库问题：分库后 JOIN、事务、分页都需要在应用层处理，评估改造成本再决定是否分库。
Q28 分布式 ID 的常见方案？雪花算法的原理和缺陷？ 高频 ▾
考察点

分布式基础题，雪花算法 64bit 结构必须能讲清楚，时钟回拨问题是加分项。

参考回答
Snowflake 64-bit 结构：
┌─────┬──────────────────────────┬───────────────┬──────────────┐
│ 1bit│        41bit             │    10bit      │    12bit     │
│符号位│  时间戳（毫秒，相对纪元）  │  机器ID(5+5)  │  序列号      │
└─────┴──────────────────────────┴───────────────┴──────────────┘
可用 69 年，每毫秒每机器生成 4096 个，趋势递增（B+Tree 友好）
  • ▸ UUID：无序，不适合 B+Tree 索引，128bit 太长
  • ▸ DB 自增：单点，性能瓶颈
  • ▸ Redis INCR：高性能，但需持久化，多机器分 step
  • ▸ 雪花算法：趋势递增，高性能，缺陷：时钟回拨导致 ID 重复
  • ▸ 美团 Leaf：号段模式 + 雪花双模，解决时钟回拨（用 NTP 对时 + 等待/报警策略）

Q31 消息队列解决了哪些问题？如何保证消息不丢失？ 高频 ▾
考察点

MQ 是微服务核心中间件，使用场景和三段可靠性是必考点。

参考回答

MQ 解决的问题：解耦（发布者不关心消费者）、异步（提高响应速度）、削峰（缓冲流量洪峰）

消息不丢失三个环节：

  • Producer 同步发送 + ACK 确认，失败重试（消息幂等）；RocketMQ 事务消息
  • Broker 消息持久化（刷盘 sync/async），主从复制（最小 ISR > 1）
  • Consumer 手动 ACK，业务处理完后再 commit offset；失败重试 + 死信队列兜底
Q32 高可用系统设计有哪些核心手段？ 高频重点 ▾
考察点

综合系统设计能力的收尾题，考查整体架构视野，能串联多个技术点加分。

参考回答

高可用 = 减少故障时间（MTTR↓）+ 降低故障概率（MTBF↑）

  • ▸ 冗余：主从/集群，无单点故障（SPOF），自动 Failover
  • ▸ 限流：保护下游，拒绝超额请求而非让系统雪崩
  • ▸ 熔断：错误率超阈值自动熔断，半开探测恢复（Resilience4j/Sentinel）
  • ▸ 降级：核心链路保障，非核心功能返回兜底数据
  • ▸ 超时 + 重试：快速失败，幂等重试，避免线程积压
  • ▸ 异步解耦：MQ 削峰，断开强依赖链路
  • ▸ 多机房/异地多活：单机房容灾，就近访问
  • ▸ 可观测性：Metrics（Prometheus）+ Logging（ELK）+ Tracing（SkyWalking）快速定位故障
