01 · 核心概念
  • Topic / Partition — 逻辑分组与物理分区，水平扩展的基础
  • Broker / Cluster — 节点与集群，Leader Partition 分散均衡
  • Producer / Consumer / Consumer Group — 三者关系与并行消费模型
  • Offset — 消费位置的唯一标识，存于 __consumer_offsets
02 · 消息存储原理
  • LogSegment — .log / .index / .timeindex 三文件结构
  • 稀疏索引 — 每隔 log.index.interval.bytes 记一条，二分查找定位
  • 顺序写 + Page Cache — 为什么 Kafka 吞吐量远超随机写数据库
  • 零拷贝 sendfile() — DMA 直接传输，跳过用户态拷贝
03 · 副本机制 ISR/HW/LEO
  • AR / ISR / OSR — 全副本集合 / 同步副本集合 / 落后副本集合
  • HW（High Watermark） — 消费者可见的最大 Offset，由 ISR 最小 LEO 决定
  • LEO（Log End Offset） — 每个副本自己的末尾 Offset
  • HW 推进流程 · min.insync.replicas 与可用性权衡
04 · Controller 与元数据
  • Kafka Controller — 集群大脑，负责 Partition Leader 选举、ISR 变更
  • Controller 选举 — ZooKeeper 模式下的临时节点抢占机制
  • KRaft 模式（Kafka 3.x） — 内置 Raft 协议替代 ZooKeeper，去除外部依赖
  • KRaft vs ZooKeeper 模式对比 · 迁移路径
05 · 消息压缩与批量
  • 压缩算法 — GZIP / Snappy / LZ4 / ZSTD 吞吐 vs 压缩比对比
  • 批量发送 — batch.size + linger.ms 对延迟与吞吐的影响
  • Producer 端压缩 vs Broker 端重压缩 · 消费者解压缩
CH 02 Producer 深度解析 kafka-02-producer.html DONE 打开 →
01 · 发送全流程
  • 拦截器 → 序列化器 → 分区器 → RecordAccumulator
  • Sender 线程 — 从 Accumulator 取批次，发给 NetworkClient
  • NetworkClient — 基于 NIO Selector 管理 TCP 连接池
  • 整体链路时序图 · 同步发送 vs 异步发送 vs 发后即忘
02 · 分区策略
  • 无 Key — 粘性分区（Sticky） — 2.4+ 默认，凑满一批再换分区
  • 有 Key — murmur2 哈希取模 — 相同 Key 必落同一 Partition
  • 自定义分区器 — 实现 Partitioner 接口，按业务规则路由
  • 分区数设计原则 · 扩分区后 Key 路由一致性问题
03 · acks 与可靠性配置
  • acks=0 — 不等确认，最高吞吐，可能丢消息
  • acks=1 — Leader 写入即确认，Leader 宕机可能丢
  • acks=all/-1 — 等所有 ISR 写入，最可靠
  • retries + retry.backoff.ms + delivery.timeout.ms 三参数联动
04 · 幂等 Producer
  • enable.idempotence=true — 单分区内去重，精确一次
  • ProducerID + SequenceNumber — Broker 端去重机制
  • 局限：仅保证单 Partition、单会话内幂等；跨分区需事务
05 · 事务 Producer（Exactly-Once）
  • transactional.id — 跨 Session 的唯一标识
  • initTransactions() → beginTransaction() → send() → commitTransaction()
  • 事务协调器 — __transaction_state Topic 存储事务日志
  • 读隔离级别：isolation.level=read_committed 消费端过滤未提交消息
  • Kafka Stream Exactly-Once 语义的底层实现原理
CH 03 Consumer 深度解析 kafka-03-consumer.html DONE 打开 →
01 · 消费流程
  • subscribe() / assign() — 自动分配 vs 手动指定 Partition
  • poll() 心跳机制 — poll 超时与 max.poll.interval.ms 的关系
  • Fetcher — 预取数据，fetch.min.bytes / fetch.max.wait.ms
  • Pull 模式设计的优势：消费者控制消费速率，避免 Push 过载
02 · Rebalance 机制
  • 触发条件 — 成员加入/退出、订阅变更、Partition 数变更、心跳超时
  • GroupCoordinator — 由 Broker 承担，管理组成员与 Offset
  • JoinGroup + SyncGroup 协议 — 两阶段 Rebalance 流程
  • Eager（停止消费）vs Cooperative（增量） — 协作式 Rebalance 避免全停
  • 减少 Rebalance 的实践：session.timeout.ms / heartbeat.interval.ms / max.poll.interval.ms 调优
03 · Offset 提交策略
  • 自动提交 — enable.auto.commit=true，可能重复消费或丢失
  • 手动同步提交 — commitSync()，处理完再提交，at-least-once
  • 手动异步提交 — commitAsync(callback)，高吞吐，失败需处理
  • 精确位置提交 — commitSync(offsets) 按 Partition 精细控制
  • 三种语义：at-most-once / at-least-once / exactly-once
04 · 分区分配策略
  • RangeAssignor — 按范围分配，可能不均匀（默认）
  • RoundRobinAssignor — 轮询分配，要求订阅相同 Topic
  • StickyAssignor — 尽量保持上次分配，减少 Rebalance 迁移量
  • CooperativeStickyAssignor — 协作式 + 粘性，Kafka 2.4+ 推荐
05 · 消费监控与调优
  • Consumer Lag — Lag = HW - CurrentOffset，积压监控核心指标
  • JMX 指标 · kafka-consumer-groups.sh --describe
  • max.poll.records — 单次 poll 最大记录数，控制处理批量
  • 多线程消费模式：单线程 poll + 线程池处理 vs 多 Consumer 实例
CH 04 消息可靠性保障 kafka-04-reliable.html DONE 打开 →
01 · 消息不丢失
  • 生产者侧 — acks=all + retries + min.insync.replicas≥2
  • Broker 侧 — unclean.leader.election.enable=false，禁止落后副本成 Leader
  • 消费者侧 — 处理完业务再手动提交 Offset，避免先提交后处理失败
  • 三端联动的最强可靠性配置清单
02 · 幂等消费（不重复）
  • 业务层幂等 — 数据库唯一键 / Redis SETNX / 状态机判断
  • 消息 ID 去重 — 消费前查 Redis/DB 是否已处理，处理后记录
  • 幂等 vs 去重的区别：幂等是操作本身可重入，去重是过滤重复消息
  • 分布式场景下的幂等令牌（Idempotency Key）设计
03 · 消息顺序消费
  • 全局顺序 — 1 个 Partition，1 个 Consumer，吞吐量受限
  • 局部顺序 — 相同业务 Key（如订单 ID）哈希到同一 Partition
  • Consumer 单线程消费保序 vs 多线程消费乱序问题
  • Partition 内有序，Partition 间无序的本质原因
04 · 消息积压处理
  • 紧急扩容 — 临时增加 Consumer 实例（不超过 Partition 数）
  • 新建 Topic 扩分区 — 原 Topic 停写，消费后转发到多分区 Topic
  • 批量消费 — 增大 max.poll.records，批量入库减少 IO 次数
  • 积压原因排查 · 消费速率 vs 生产速率的监控方法
05 · 消息延迟与回溯
  • 延迟消息 — Kafka 原生不支持，方案：时间轮 / 延迟 Topic 分级
  • 消息回溯 — seek(partition, offset) 手动重置消费位置
  • --reset-offsets — 命令行按时间戳或 Offset 重置消费组
  • Dead Letter Topic — 多次重试失败后转入死信队列，人工介入
