01主内存与工作内存
JMM 抽象模型

JMM（Java Memory Model）定义了线程与主内存之间的抽象关系：所有共享变量存储在主内存，每个线程有自己的工作内存（寄存器/Cache 的抽象），线程只能操作工作内存中变量的副本，不能直接读写主内存。

区域位置存储内容作用
主内存（Main Memory）堆内存（逻辑概念）所有共享变量（实例字段、静态字段）线程间数据共享的唯一来源
工作内存（Working Memory）CPU 缓存/寄存器主内存变量的副本线程的私有工作区，操作更快

线程对变量的操作必须在工作内存中进行，写完后再刷回主内存，读时先从主内存加载到工作内存。正是这种缓存导致了可见性问题。

8 种原子内存操作
操作作用域说明
lock主内存将变量标记为线程独占
unlock主内存释放独占锁定
read主内存→工作内存从主内存读取变量值（与 load 配合）
load工作内存将 read 的值放入工作内存副本
use工作内存→执行引擎线程读取工作内存变量，传给执行引擎
assign执行引擎→工作内存执行引擎赋值给工作内存变量
store工作内存→主内存将工作内存变量值传给主内存（与 write 配合）
write主内存将 store 的值写入主内存变量
02并发三大特性
原子性 · 可见性 · 有序性
特性含义保证方式
原子性（Atomicity）操作不可被中断，要么全执行要么全不执行synchronized、Lock、Atomic 原子类
可见性（Visibility）一个线程修改共享变量后，其他线程能立即看到最新值volatile、synchronized、final
有序性（Ordering）程序执行顺序按代码顺序，不受指令重排影响volatile（禁止重排）、happens-before 规则
i++ 的原子性问题：i++ 看似一条语句，实则三步：① 读取 i 值 ② 加 1 ③ 写回。多线程下可能两个线程都读到旧值，导致结果比预期少。解决：AtomicInteger.getAndIncrement() 或 synchronized。
03happens-before 原则
8 条 happens-before 规则

如果操作 A happens-before 操作 B，则 A 的结果对 B 可见，且 A 的执行顺序在 B 之前。JMM 通过以下规则定义可见性保证：

规则 1
程序顺序规则
同一线程内，前面的操作 happens-before 后续操作
规则 2
监视器锁规则
unlock 操作 happens-before 后续对同一锁的 lock 操作
规则 3
volatile 变量规则
volatile 写操作 happens-before 后续对该变量的读操作
规则 4
线程启动规则
Thread.start() happens-before 被启动线程的每个操作
规则 5
线程终止规则
线程所有操作 happens-before 其他线程检测到该线程终止（join()/isAlive()）
规则 6
线程中断规则
interrupt() happens-before 被中断线程检测到中断
规则 7
对象终结规则
对象构造函数结束 happens-before finalize() 开始
规则 8
传递性规则
A happens-before B，B happens-before C，则 A happens-before C
04volatile 关键字
两个核心语义
  • ①可见性：对 volatile 变量的写操作会立即刷新到主内存；其他线程读 volatile 变量时会先使工作内存副本失效，强制从主内存重新读取。底层通过 lock 前缀指令实现，触发 MESI 缓存一致性协议
  • ②禁止指令重排序：编译器和处理器不能对 volatile 变量的读写进行重排序。通过在 volatile 写前插入 StoreStore 屏障、写后插入 StoreLoad 屏障，读前插入 LoadLoad 屏障、读后插入 LoadStore 屏障实现
volatile 不保证原子性：volatile int i; i++; 仍然是非原子的三步操作。需要原子性请用 AtomicInteger 或 synchronized。
volatile 适用场景
  • ✅状态标志：volatile boolean running = true; 线程间停止信号
  • ✅双重检查锁定（DCL）：单例模式中防止半初始化对象逃逸
  • ✅独立观察：周期性发布数据，订阅者只需读最新值（无需原子性）
  • ❌不适用：复合操作（check-then-act、read-modify-write），需要 Atomic 类或 synchronized
05指令重排序
三种重排序
类型发生阶段说明
编译器重排序编译期JIT 编译器在不改变单线程语义前提下调整语句顺序
处理器重排序运行期CPU 乱序执行（Out-of-Order Execution），流水线优化
内存系统重排序运行期Store Buffer、Invalidate Queue 导致写操作延迟可见

as-if-serial 语义：在单线程内，重排序后的执行结果与顺序执行结果相同（编译器和CPU的底线保证）。但多线程下 as-if-serial 无法保证跨线程可见性，因此需要 JMM 的 happens-before 规则。

06DCL 双重检查锁定单例
为什么需要 volatile
// ❌ 错误写法：没有 volatile，可能返回半初始化对象
public class Singleton {
    private static Singleton instance;
    public static Singleton getInstance() {
        if (instance == null) {               // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {       // 第二次检查
                    instance = new Singleton(); // ← 问题所在
                }
            }
        }
        return instance;
    }
}

// ✅ 正确写法：加 volatile
private static volatile Singleton instance;

instance = new Singleton() 实际分三步：① 分配内存 ② 初始化对象 ③ 将引用指向内存。指令重排可能变成 ①③②，另一线程此时读到 instance 非 null，但对象未初始化完成（半初始化对象）。volatile 禁止 ②③ 重排，解决此问题。

07内存屏障
4 种内存屏障
屏障类型说明作用
LoadLoadLoad1; LoadLoad; Load2Load1 数据装载完成前，Load2 不能执行
StoreStoreStore1; StoreStore; Store2Store1 数据对其他处理器可见后，Store2 才能执行
LoadStoreLoad1; LoadStore; Store2Load1 数据装载完成前，Store2 不能刷出
StoreLoadStore1; StoreLoad; Load2Store1 数据对所有处理器可见后，Load2 才能执行。开销最大，是全能屏障

volatile 写操作：前插 StoreStore，后插 StoreLoad；volatile 读操作：后插 LoadLoad 和 LoadStore。
