01同步辅助工具
CountDownLatch vs CyclicBarrier vs Semaphore
工具核心语义可重用典型场景
CountDownLatch等待 N 个操作完成（count→0 唤醒等待者）❌ 一次性等待所有子任务完成后汇总；服务启动完成信号
CyclicBarrierN 个线程互相等待，全部到达栅栏后一起继续✅ 自动重置多线程分批计算，每批结束同步；并行模拟
Semaphore控制同时访问资源的线程数（许可证机制）✅连接池/限流（最多 N 个并发）
使用示例
// CountDownLatch：等待 3 个子任务都完成
CountDownLatch latch = new CountDownLatch(3);
for (int i = 0; i < 3; i++) {
    executor.submit(() -> {
        try { doWork(); }
        finally { latch.countDown(); } // 每完成一个 -1
    });
}
latch.await(); // 阻塞直到 count=0

// CyclicBarrier：3 个线程同步到达再继续
CyclicBarrier barrier = new CyclicBarrier(3, () ->
    System.out.println("所有线程到达，开始下一阶段"));
// 各线程调用 barrier.await() 等待

// Semaphore：最多 5 个线程同时访问数据库
Semaphore sem = new Semaphore(5);
sem.acquire();  // 获取许可，无则阻塞
try { dbOperation(); }
finally { sem.release(); } // 释放许可
02原子类与 CAS
CAS（Compare And Swap）原理

CAS 是一条 CPU 原子指令（x86 的 cmpxchg），包含三个操作数：内存地址 V、期望值 A、新值 B。只有当 V 的值等于 A 时，才将 V 更新为 B，整个过程原子不可中断。

// AtomicInteger 的 compareAndSet 底层
// 通过 Unsafe.compareAndSwapInt() 调用硬件 CAS 指令
atomicInt.compareAndSet(expected, newValue);

CAS 的三个问题：

  • ①ABA 问题：值从 A→B→A，CAS 无法感知。解决：AtomicStampedReference（带版本号）或 AtomicMarkableReference
  • ②循环开销：竞争激烈时 CAS 一直失败，CPU 空转。解决：退避策略，或换用 LongAdder
  • ③只能保证单变量：无法同时保证多个变量的原子性。解决：AtomicReference 封装对象，或 synchronized
LongAdder vs AtomicLong
维度AtomicLongLongAdder（JDK 8+）
实现单 volatile long + CASCell 数组分散热点 + base 值
高并发性能CAS 竞争激烈，性能下降分段累加，性能显著更好
读取精度任意时刻精确sum() 时才汇总，瞬时值不精确
内存占用小略大（Cell 数组）
适用低并发、需精确读取高并发计数（如统计 QPS）

03ConcurrentHashMap
JDK 7 vs JDK 8 实现对比
维度JDK 7（分段锁）JDK 8（CAS + synchronized）
数据结构Segment 数组 + HashEntry 链表Node 数组 + 链表/红黑树
锁粒度Segment 级别（默认 16 个 Segment）Node 级别（每个桶头结点一把锁）
并发度固定 16（Segment 数量）动态，最大等于数组长度
扩容段内扩容多线程协同扩容（transfer）
查询全程无锁（volatile 保证可见性）全程无锁（volatile Node）
put 流程lock() 锁段，然后操作CAS 插入空桶；桶非空时 synchronized 锁头结点
树化阈值不支持链表长度≥8 且数组≥64 时转红黑树
JDK 8 put() 流程
1. key/value 不能为 null（否则抛 NPE）
2. 计算 hash（spread 扰动函数）
3. 循环 CAS 直到成功：
   a. 数组未初始化 → initTable()
   b. 目标桶为 null → CAS 直接插入 Node（无锁）
   c. 桶头结点 hash=MOVED(-1) → 协助扩容（helpTransfer）
   d. 桶非空 → synchronized(头结点) {
      链表：遍历找相同key更新，或尾插
      红黑树：调用 TreeBin.putTreeVal()
   }
4. 链表长度 >= 8 时尝试树化（treeifyBin）
5. addCount() 更新 size，检查是否需要扩容

05CopyOnWriteArrayList
写时复制原理

读操作无锁（直接读 volatile 数组）；写操作加 ReentrantLock，复制一份新数组，在新数组上修改，完成后将引用指向新数组：

// 写操作（add 为例）
public boolean add(E e) {
    synchronized (lock) {
        Object[] elements = getArray();
        int len = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1); // 复制
        newElements[len] = e;
        setArray(newElements); // volatile 写，对所有读线程立即可见
        return true;
    }
}
  • 优点读操作完全无锁，适合读多写少场景
  • 缺点①写时复制内存开销大（数据量大时 GC 压力大）
  • 缺点②弱一致性：读操作读到的是快照，写完成前无法看到新数据
  • 场景配置列表、黑白名单、观察者列表（读多写极少）
06CompletableFuture
核心方法速查
方法说明
supplyAsync(supplier, executor)异步执行有返回值任务
runAsync(runnable, executor)异步执行无返回值任务
thenApply(fn)上一步结果 → 转换（同步）
thenApplyAsync(fn)上一步结果 → 转换（异步）
thenCompose(fn)扁平化嵌套 CF（flatMap）
thenCombine(cf, fn)两个 CF 都完成后合并结果
thenAccept(consumer)消费结果，无返回值
exceptionally(fn)异常处理，返回默认值
handle(fn)处理正常值和异常（二合一）
allOf(cfs...)等待所有 CF 完成
anyOf(cfs...)任意一个 CF 完成即返回
实战示例：并行查询聚合
ExecutorService executor = Executors.newFixedThreadPool(3);

// 并行发起 3 个查询
CompletableFuture<User> userCF =
    CompletableFuture.supplyAsync(() -> userService.get(uid), executor);
CompletableFuture<Order> orderCF =
    CompletableFuture.supplyAsync(() -> orderService.get(uid), executor);
CompletableFuture<Points> pointsCF =
    CompletableFuture.supplyAsync(() -> pointsService.get(uid), executor);

// 等待全部完成（allOf 返回 CF<Void>）
CompletableFuture.allOf(userCF, orderCF, pointsCF).join();

// 聚合结果
UserVO vo = new UserVO(userCF.join(), orderCF.join(), pointsCF.join());

// 异常处理
CompletableFuture<String> safe = cf
    .exceptionally(e -> {
        log.error("查询失败", e);
        return "default";
    })
    .thenApply(result -> "prefix_" + result);
默认线程池陷阱：不传 executor 时使用 ForkJoinPool.commonPool()，该线程池是全局共享的，可能被并行流、其他任务占用，生产环境应始终传入自定义线程池。
