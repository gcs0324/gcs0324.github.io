01分布式系统的核心问题
为什么分布式系统难

单机程序的世界里，函数调用要么成功要么失败，进程内变量随时可读，时钟全局唯一。分布式系统打破了这三件事：调用可能部分成功、数据可能读到旧值、时钟可能每台机器都不同。

  • ①网络不可靠：丢包、延迟、抖动、分区都是常态。一次 RPC 超时，你无法判断"对方没收到"还是"对方收到了但回包丢了"
  • ②节点会故障：磁盘损坏、进程崩溃、机器断电、机房断网。任何时刻都要假设某些节点正在死
  • ③时钟不同步：每台机器的本地时钟有漂移，NTP 同步也只能压到毫秒级。"先后顺序"无法用墙上时间判断
  • ④消息可能乱序：两条消息先后发出，可能后发的先到。TCP 只保证同一连接内有序，跨连接、跨节点都不保证
  • ⑤没有真正的全局视图：任何节点看到的都是"延迟的、局部的、过期的"快照，全局一致状态需要付出昂贵的协调代价
分布式 8 大谬误（Fallacies of Distributed Computing）

Sun 公司 1994 年总结的 8 条新手最容易踩的"想当然"。每一条都对应着一类典型的线上事故。

谬误 1
网络是可靠的
→ 任何远程调用都要考虑超时、重试、降级
谬误 2
延迟为零
→ 跨机房调用动辄几十毫秒，N+1 查询会被放大
谬误 3
带宽无限
→ 大对象传输、全表 dump 会打爆链路
谬误 4
网络是安全的
→ 内网也要 TLS、鉴权、最小权限
谬误 5
拓扑不会变
→ 扩缩容、迁移随时在发生，IP 不能写死
谬误 6
只有一个管理员
→ 配置变更要有版本和审计，否则人祸难追
谬误 7
传输成本为零
→ 序列化、压缩、跨机房流量都有真金白银的开销
谬误 8
网络是同构的
→ 不同语言、不同协议、不同版本共存，兼容性必须设计
02CAP 定理
C / A / P 的精确含义

CAP 是 Eric Brewer 在 2000 年提出的论断：一个分布式系统不可能同时满足以下三个性质中的全部三个，最多只能满足两个。

字母含义口语解释
C — Consistency一致性（强一致 / 线性一致）所有节点在同一时刻看到相同的数据。任意时刻读到的都是最近一次成功写入的值
A — Availability可用性非故障节点收到的每个请求都能在合理时间内返回非错误响应（不要求是最新数据）
P — Partition tolerance分区容忍性当网络发生分区（部分节点之间通信中断）时，系统仍能继续工作
CAP 的核心不是"三选二"，而是"P 是必选项"。在真实分布式环境里，网络分区一定会发生，所以 P 不能放弃。真正的取舍是：分区发生时，选 C 还是选 A。CA 系统等于"不允许分区"，那就是单机数据库，不算分布式。
CAP 三角 — P 必选，真实取舍是 CP 还是 AP
CP 系统与 AP 系统的取舍

当分区发生时（比如 5 节点集群被切成 3+2 两部分），CP 与 AP 走的是完全相反的路。

选择分区时的行为代表系统适用场景
CP（保 C 弃 A）少数派分区拒绝服务或转只读，多数派继续读写但仍要走共识。宁可返回错误，也不返回旧数据ZooKeeper、etcd、HBase、Consul、Nacos（CP 模式）配置中心、注册中心、分布式锁、领导选举
AP（保 A 弃 C）所有分区都继续服务，可能返回旧数据，事后通过最终一致性收敛Eureka、Cassandra、DynamoDB、Redis Cluster、Nacos（AP 模式）商品详情、社交动态、推荐内容、监控数据
常见误读纠正：
① MySQL 主从架构不是 CP 也不是 AP，是"CA 加事后补救"。真分区时主从都还在跑，但数据可能丢。
② ZooKeeper 严格来说是顺序一致而非线性一致，但分区时少数派直接不可用，属于 CP 阵营。
③ "CAP 只能三选二"是网络上最常见的过度简化，面试时要能说清"P 是必选"这一层。
03BASE 理论
BASE 是什么

BASE 是 eBay 工程师提出的、对 CAP 中"AP 一侧"的工程落地总结。核心思想是：放弃 ACID 那种"强一致"的执念，换取整体的可用性和可伸缩性。

  • BBasically Available（基本可用）：允许损失部分可用性。比如响应时间从 200ms 退化到 2s、降级返回兜底数据、限流拒绝部分流量，但核心功能不挂
  • SSoft state（软状态）：允许系统存在"中间状态"，即数据副本之间可以短暂不一致。比如订单刚下完，物流系统看到的还是空
  • EEventually consistent（最终一致）：经过一段时间的同步（通常是秒级到分钟级），所有副本最终会收敛到一致状态，但不保证任何时刻都一致
BASE 与 ACID 的取舍
维度ACID（强一致）BASE（最终一致）
一致性强一致：写完立即对所有人可见最终一致：可能短暂看到旧值
可用性故障时宁可不可用故障时降级但保持响应
性能跨节点锁与协调开销大异步复制，吞吐高
扩展性难水平扩展（受协调瓶颈）天然水平扩展
典型场景银行转账、库存扣减商品浏览、评论、统计
实际系统几乎都是"局部 ACID + 全局 BASE"：单库内用事务保证强一致，跨库跨服务用消息/补偿走最终一致。完全选边的系统很少。
04一致性模型谱系
从最强到最弱

"一致性"这个词在分布式语境里有十几种精细划分，从强到弱大致排成一个谱系。掌握其中 4~5 个关键档位就够应付绝大多数面试。

等级名称含义
最强线性一致（Linearizable）所有操作看起来像在一个全局时钟下原子地、按真实时间顺序执行。读必然读到最新写入
强顺序一致（Sequential）所有节点看到的操作顺序一致，但不要求与真实时间一致。ZooKeeper 提供的是顺序一致
中因果一致（Causal）有因果关系的操作（A 引发 B）所有节点看到顺序一致；无因果关系的操作顺序无要求
弱读己之写（Read-your-writes）用户读到的内容一定包含自己之前写过的（避免发完朋友圈刷不到自己）
弱单调读（Monotonic Read）同一用户连续读，时间上不会"穿越"——已经读到 v2，不会再读到 v1
最弱最终一致（Eventual）停止写入后，经过足够长时间，所有副本最终会一致。中间任意时刻都可能不一致
区分线性一致 vs 顺序一致的小例子：A 在 10:00 写 x=1，B 在 10:01 读 x。线性一致要求 B 必读到 1；顺序一致只要求"所有节点都先看到写、再看到读"这个顺序，但具体时间可以滞后——B 可能读到 0，只要全集群都还没看到这次写。
05Paxos 共识算法
Paxos 解决的问题

多个节点对"一个值"达成一致 —— 听起来简单，但要在节点会崩、消息会丢、网络会乱序的条件下做到，需要严密的协议保证。Paxos 由 Leslie Lamport 在 1990 年提出，是所有现代共识算法的鼻祖。

Proposer 提议者
发起提案（包含一个值），驱动决议过程
Acceptor 接受者
对提案投票，存储被接受的提案。多数派同意即视为达成共识
Learner 学习者
不参与决议，只学习已达成的最终结果
Basic Paxos 两阶段流程
1
Prepare 阶段（提议）
Proposer 选一个全局唯一递增的提案编号 N，向所有 Acceptor 发送 Prepare(N)。Acceptor 收到后，若 N 比自己见过的所有编号都大，则承诺"不再接受编号 < N 的提案"，并回复自己已接受过的最大编号提案（如果有）
2
Accept 阶段（接受）
Proposer 收到多数派 Acceptor 的回复后，从回复里挑出"已接受的最大编号提案"对应的值 v（如果都没接受过，就用自己想提的值）。然后向所有 Acceptor 发 Accept(N, v)。Acceptor 收到后，若 N ≥ 自己承诺的最小编号，就接受并持久化
3
达成共识
当一个提案被多数派 Acceptor 接受，这个值就被"chosen"，所有 Learner 最终都会学到这个值
活锁问题：两个 Proposer 反复用更高的 N 抢占，可能导致谁都无法 Accept 成功。Multi-Paxos 通过选举唯一 Leader 来规避这个问题。
Multi-Paxos 与工程难点

Basic Paxos 只能对单个值达成一致。实际系统需要对"一连串值"达成一致（即复制日志），这就是 Multi-Paxos：选一个 Leader 一直当 Proposer，跳过每次的 Prepare 阶段，性能大幅提升。

  • ▸Paxos 论文只给了核心证明，没给完整工程实现，导致每家公司"实现的 Paxos 都长得不一样"
  • ▸Leader 选举、日志补洞、配置变更等细节都需要自己设计
  • ▸正是因为难懂难落地，才催生了后来"为了易懂而设计"的 Raft
06Raft 共识算法
Raft 的设计目标：可理解性

Raft 由 Diego Ongaro 在 2014 年提出，明确以"比 Paxos 更易理解"为目标，把共识问题拆成三个相对独立的子问题：Leader 选举、日志复制、安全性。etcd、TiKV、Consul、CockroachDB 都用 Raft。

Leader 领导者
同一 term 内唯一，负责接收客户端请求并复制日志到 Follower
Follower 跟随者
被动接收 Leader 的日志和心跳，不主动发请求
Candidate 候选者
选举期间的临时角色，赢得多数票即变成 Leader
Leader 选举流程

Raft 把时间切成不定长的任期（term），每个 term 开头是一次选举。term 是一个全局递增的整数，用来区分新旧 Leader。

1
心跳超时
Follower 在随机选举超时（通常 150~300ms）内没收到 Leader 心跳，转为 Candidate，term + 1，给自己投一票
2
拉票
向其他所有节点发送 RequestVote RPC，附带自己的 term 和最新日志的 (term, index)
3
投票规则（Election Restriction）
收到 RequestVote 的节点：① 本 term 还没投过票；② 候选人的日志至少和自己一样新（按 last log term，相同则比 last log index）。两条都满足才投赞成票
4
赢得多数 → 变 Leader
收到多数派赞成票，立刻成为 Leader，开始发送心跳压制其他 Candidate。如果同时多人参选导致票被瓜分，等待下一次随机超时再选
随机超时的妙处：每个 Follower 的超时时间在区间内随机，几乎不可能多个节点同时变成 Candidate，从而避免脑裂式的票数瓜分。这是 Raft 简化设计的关键技巧。
Raft 节点状态机 — Follower / Candidate / Leader 三态流转
日志复制流程
1
客户端写入 Leader
Leader 把命令追加到本地日志（未提交状态），并行向所有 Follower 发送 AppendEntries RPC
2
Follower 写入本地日志
Follower 写入成功后回 ACK。Leader 维护每个 Follower 的 matchIndex（已匹配到的日志位置）
3
多数派确认 → 提交
当某条日志被多数派写入，Leader 推进 commitIndex，应用到状态机，返回客户端成功。下次心跳带上新的 commitIndex，Follower 也跟着应用
Log Matching 性质：如果两个日志在某个 (term, index) 位置上的条目相同，那这两个日志在该位置之前的所有条目都相同。Leader 通过 AppendEntries 携带的 prevLogIndex/prevLogTerm 强制 Follower 与自己对齐，不一致就向前回退直到找到匹配点。
配置变更（Joint Consensus）

集群从"3 节点"扩到"5 节点"的过程中，新旧节点集合可能各自选出一个 Leader 导致脑裂。Raft 用联合共识解决：先进入"新+旧都生效"的中间状态（任何决议都需要新旧两个多数派同时同意），再切到只用新配置。这样保证任意时刻不会有两个独立的多数派。

07ZAB 协议
ZAB 是什么

ZAB（ZooKeeper Atomic Broadcast）是 ZooKeeper 专用的原子广播协议。本质上和 Multi-Paxos / Raft 解决同一类问题，但有两个特色：① 为主备模型量身定制；② 支持崩溃恢复后的快速日志补全。

阶段动作说明
① Leader Election选主通过 epoch（类似 Raft 的 term）比较 + zxid（事务 ID）比较，选出日志最新的节点当 Leader
② Discovery + Sync数据同步新 Leader 收集多数派 Follower 的最高 zxid，把缺失的事务推送给落后的节点，让所有 Follower 与自己对齐
③ Broadcast原子广播对外服务阶段。Leader 把每个写请求封装成 proposal，两阶段提交：先广播给 Follower（写本地日志），收到多数派 ACK 后再广播 COMMIT
ZAB 与 Raft 的核心异同
维度ZABRaft
提交方式两阶段：propose + commit一阶段：AppendEntries 携带 commitIndex 顺带提交
选主标准zxid 最大者优先(last log term, last log index) 字典序最大者优先（本质相同）
日志同步选主后专门的 Sync 阶段，把缺失事务补齐持续运行中通过 AppendEntries 自动回退到匹配点
读一致性默认本地读（顺序一致）；要强一致需 sync() + 读默认走 Leader 读（线性一致）；优化可走 ReadIndex / Lease Read
典型实现ZooKeeperetcd、TiKV、Consul、CockroachDB
08Gossip 协议
Gossip 是什么

Gossip 是"流言传播式"的最终一致性协议：每个节点周期性地随机挑几个邻居交换状态，几轮之后整个集群都会收到。它不追求强一致，但天然适合大规模、动态、去中心化的集群。

  • ▸反熵（Anti-entropy）：周期性地比对全量状态差异并修复。慢但能保证最终一致，适合后台修复
  • ▸谣言传播（Rumor mongering）：只传播"新消息"，传几轮就停。快但可能丢，适合事件通知
  • ▸收敛速度：N 个节点理论上 O(log N) 轮就能全部收到一条消息
典型应用：
• Cassandra / DynamoDB：节点间交换成员状态、心跳
• Consul：基于 Serf 库做服务发现的成员管理
• Redis Cluster：16384 个 slot 的归属、节点 fail 状态都靠 Gossip 传播
• 区块链：交易和区块的全网广播
09拜占庭容错（BFT）
拜占庭将军问题

Paxos / Raft / ZAB 都属于CFT（Crash Fault Tolerance）：只能容忍节点宕机，但假设所有活着的节点都"诚实"。如果有节点作恶（发假消息、发不同消息给不同人），CFT 协议就会失效。

BFT（Byzantine Fault Tolerance）解决的就是这个问题：在最多 f 个节点作恶的情况下，仍能让其他诚实节点达成一致。理论上需要总节点数 ≥ 3f + 1。

对比CFTBFT
故障模型节点会宕机/网络丢包，但不撒谎节点可能任意作恶
节点数要求≥ 2f + 1 容忍 f 个故障≥ 3f + 1 容忍 f 个作恶
性能高，常用低，消息复杂度 O(n²)
典型场景公司内网集群公链、跨组织联盟链
代表算法Paxos、Raft、ZABPBFT、HotStuff、Tendermint
日常工作中接触的中间件（ZK / etcd / Kafka / Redis）几乎全是 CFT。BFT 只在区块链、跨机构联盟系统里需要 —— 面试能点到"什么是拜占庭问题，CFT 和 BFT 区别"基本够用，深挖 PBFT 流程是加分项。
