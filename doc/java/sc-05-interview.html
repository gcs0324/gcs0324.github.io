Q1 微服务和单体架构各自适合什么场景？什么时候应该做微服务拆分？ 高频 ▾
考察点

考察对微服务价值和代价的理性认识，能说出"不是所有系统都适合微服务"是成熟工程师的体现。

参考回答

微服务不是银弹，选型要看实际情况：

  • 适合单体团队人数少（<10人）、业务还在探索期、QPS 低、功能模块没有明显差异化扩容需求。此时单体开发快、部署简单、调试方便，微服务的收益远小于引入的复杂度。
  • 适合微服务团队规模较大（20人以上）、各模块发布频率和资源需求差异明显（如订单服务 QPS 高需要扩容，用户服务低）、需要技术栈灵活性、故障隔离要求高的场景。

拆分时机判断：当单体出现以下信号时，可以考虑拆分：1）频繁发布冲突（多团队改同一仓库）；2）某模块性能瓶颈需要独立扩容；3）不同模块对技术栈有不同要求；4）系统规模导致构建/启动速度不可接受。

拆分原则：按业务域（DDD 限界上下文）拆分，每个服务独享数据库，不要按技术层（DAO/Service/Controller）拆分。

Q3 Nacos 注册中心的原理是什么？服务是如何注册和发现的？ 高频重点 ▾
考察点

注册中心原理是微服务必问，能说清注册/心跳/推送/本地缓存四个环节是完整回答。

参考回答

分四个阶段：

  • ① 服务注册服务启动时，客户端（Nacos SDK）向 Nacos Server 发送 HTTP 请求，把自己的 IP、端口、服务名、集群名注册到注册中心。
  • ② 心跳保活客户端每 5 秒向 Nacos 发一次心跳。Nacos 15 秒未收到心跳标记实例为不健康，30 秒删除实例（临时实例/AP 模式）。
  • ③ 服务发现消费方启动时订阅目标服务，本地缓存实例列表。Nacos 2.x 通过 gRPC 长连接主动推送实例变更（毫秒级），同时消费方每 30 秒定时拉取一次兜底。
  • ④ 调用时OpenFeign/LoadBalancer 从本地缓存取实例列表，按负载均衡策略选一个实例直接发 HTTP 请求（不经过 Nacos）。

Nacos 的数据模型：Namespace（环境隔离）→ Group（业务分组）→ Service（服务名）→ Cluster（机房）→ Instance（具体实例）。

Q4 Nacos 的 AP 模式和 CP 模式有什么区别？如何选择？ 高频重点 ▾
考察点

AP/CP 是 CAP 定理的落地，能结合 Nacos 临时实例/永久实例说清区别是加分项。

参考回答

Nacos 独特之处在于同一集群内可以同时支持 AP 和 CP，按实例类型区分：

  • AP 模式（临时实例，默认）使用自研 Distro 协议（最终一致性）。服务实例宕机后，Nacos 在心跳超时后自动删除，其他节点仍然可以正常注册和发现服务（优先可用性）。Spring Boot 微服务默认用此模式（ephemeral: true）。
  • CP 模式（永久实例）使用 Raft 协议（强一致性）。Leader 宕机时，整个集群暂停写操作（新注册/注销），直到选出新 Leader，但已有服务列表仍可读。适合需要强一致性的场景（ephemeral: false）。

选择建议：Spring Cloud 微服务选 AP（默认），服务上下线高频，允许短暂不一致（最终会同步），可用性更重要。需要强一致的场景（如底层 DNS 服务注册）选 CP。

Q6 Nacos 配置中心的动态刷新是如何实现的？@RefreshScope 的原理是什么？ 高频 ▾
考察点

配置动态刷新是生产环境常用特性，能说清 @RefreshScope 的原理（Bean 重建）是加分项。

参考回答

动态刷新的全流程：

  • ① 监听Nacos 客户端通过长轮询（每 30 秒）向 Nacos Server 检查配置是否变更，Nacos Server 有变更时提前返回响应（Long Polling），客户端立即感知
  • ② 拉取客户端收到变更通知后，重新拉取最新配置内容
  • ③ 发布事件Nacos SDK 发布 RefreshEvent 到 Spring 的事件总线
  • ④ 刷新上下文Spring 的 ContextRefresher 监听到 RefreshEvent，重新加载 Environment，刷新所有 @RefreshScope 标注的 Bean

@RefreshScope 原理：被标注的 Bean 实际上是一个代理对象（Scoped Proxy）。每次访问该 Bean 的方法时，代理会检查 Bean 是否被标记为"需要刷新"。刷新事件触发后，代理会销毁旧的 Bean 实例，下次访问时重新创建（重新注入配置属性）。

@Bean
@RefreshScope   // 缺少这个注解，配置变更后不会生效
public SomeService someService(@Value("${some.config}") String config) {
    return new SomeService(config);
}

Q7 注册中心挂了，服务还能正常互相调用吗？ 高频 ▾
考察点

这是考察对注册中心和客户端缓存理解的经典题，很多人不知道"缓存还在、可以继续调用"。

参考回答

已有的服务调用不受影响，但有限制。

原因：消费方本地有实例列表的缓存（内存中）。注册中心挂了之后：

  • 已有调用继续正常工作，消费方从本地缓存取实例列表，继续发请求，完全不依赖注册中心
  • 新实例注册新服务实例无法注册，注册中心挂了无法接收注册请求
  • 实例下线感知注册中心挂了期间，某个实例宕机后消费方无法感知（Nacos 不能推送变更），会继续调用已宕机的实例，导致请求失败（需要重试/熔断兜底）
  • 配置刷新Nacos 配置中心也无法推送配置变更，但已有配置不受影响

结论：注册中心挂了对正在运行的服务影响有限，但新服务无法接入、故障实例无法快速剔除。所以生产 Nacos 需要集群部署（3 节点）保证高可用。

Q8 服务实例如何优雅下线？怎么防止流量丢失？ 重点 ▾
考察点

优雅下线是生产运维必备，考察对整个发布流程的理解。

参考回答

服务下线如果处理不当，会导致请求发到正在关闭的实例，返回连接拒绝或处理到一半的错误。优雅下线分三步：

  • ① 摘除流量先通知注册中心（Nacos）下线该实例，Nacos 推送变更给所有消费方，消费方更新本地缓存不再路由到这个实例。等待一个推送传播周期（约 2~5 秒）。
  • ② 等待处理中的请求实例继续处理已经到达的请求，等待所有正在处理的请求完成（Spring Boot Graceful Shutdown，配置 server.shutdown=graceful，超时时间 30s）。
  • ③ 关闭进程所有请求处理完毕后，正常关闭 JVM 进程，释放数据库连接、消息队列连接等资源。
server:
  shutdown: graceful   # 开启优雅关闭（Spring Boot 2.3+）
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s   # 等待处理中请求最多 30 秒

消费方侧：配置重试（Retry Filter / Feign 重试），即使遇到瞬间连接失败，能自动切换到其他健康实例重试。

Q9 Spring Cloud Gateway 和 Zuul 有什么区别？Gateway 为什么性能更好？ 高频 ▾
考察点

框架选型对比，核心是理解同步 Servlet 和异步 Reactor 的本质区别。

参考回答

核心区别在于线程模型：

  • Zuul 1.x基于 Servlet，同步阻塞模型。每个请求占用一个线程，线程等待 IO 时阻塞。高并发下线程数快速耗尽，吞吐受限于线程池大小。
  • Gateway基于 Spring WebFlux + Project Reactor + Netty，全异步非阻塞。少量线程（CPU 核数 × 2）用事件循环处理大量并发请求。IO 等待时线程不阻塞，立即处理其他请求。理论上吞吐是 Zuul 的几倍。

另一个区别：Gateway 天然集成 Spring Cloud 生态（负载均衡、Sentinel、Nacos），而 Zuul 2.x 虽然也改成异步，但 Spring 官方未集成，实际上 Zuul 在 Spring Cloud 生态中已经没有位置了。

注意：Gateway 基于响应式编程，Filter 中不能有同步阻塞操作（如同步调 Redis、DB），必须用 Mono/Flux API，否则会阻塞事件循环线程，反而变慢。

Q10 Gateway 一次请求的处理流程是什么？Pre Filter 和 Post Filter 的执行顺序？ 高频重点 ▾
考察点

Gateway Filter 链的执行顺序是面试必问，Pre/Post 是同一 Filter 的两个阶段，很多人答错。

参考回答

Gateway 处理流程：请求 → HttpWebHandlerAdapter → DispatcherHandler → RoutePredicateHandlerMapping → FilteringWebHandler（Filter 链）→ 目标服务 → Filter 链（逆向）→ 响应

Filter 链的执行顺序：

  • Pre 阶段按 @Order 从小到大（优先级高到低）依次执行各 Filter 的 chain.filter(exchange) 之前的逻辑。典型：认证 → 限流 → 日志记录请求
  • 转发请求最终的 NettyRoutingFilter 把请求转发到目标服务
  • Post 阶段目标服务响应后，Filter 链逆向（Order 从大到小）执行 chain.filter(exchange) 之后的逻辑。典型：添加响应 Header → 记录响应日志
// Pre Filter + Post Filter 在同一个 filter 方法里
public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
    // === Pre 阶段 ===
    long startTime = System.currentTimeMillis();

    return chain.filter(exchange).then(Mono.fromRunnable(() -> {
        // === Post 阶段（请求完成后执行）===
        long elapsed = System.currentTimeMillis() - startTime;
        log.info("请求耗时: {}ms", elapsed);
    }));
}

Q11 Gateway 如何做统一认证鉴权？JWT 放在哪里验证？ 高频 ▾
考察点

认证鉴权是每家公司都有的需求，能给出完整的 JWT 在网关验证的方案是工程实践加分点。

参考回答

推荐在 Gateway 层做统一认证，而不是每个微服务都做，避免重复代码：

  • 认证（Authentication）在 Gateway 的全局 Filter（最高优先级）中解析请求的 Authorization: Bearer <jwt>，用公钥验证签名，解析用户 ID、角色等信息，把用户信息写入 Header（如 X-User-Id）传给下游服务。下游服务直接从 Header 读取，不再验证 Token。
  • 鉴权（Authorization）粗粒度权限（角色判断：是否是管理员）可以在 Gateway Filter 中做；细粒度权限（是否有权访问某个业务资源）必须在业务服务内部做（Gateway 不了解业务语义）。
  • 白名单登录、注册等不需要认证的接口在 Filter 中配置白名单放行。

Token 刷新：JWT 通常有较短的过期时间（15 分钟~2 小时），配合 Refresh Token（存 Redis，较长过期）实现无感刷新。

Q12 OpenFeign 的底层原理是什么？它和 RestTemplate 有什么区别？ 高频重点 ▾
考察点

Feign 底层使用动态代理是必答点，能说出整合 LoadBalancer 和 Sentinel 的过程是加分项。

参考回答

OpenFeign 核心是JDK 动态代理：

  • ①Spring Boot 启动扫描 @FeignClient 接口，为每个接口创建 JDK 动态代理，注册到 Spring 容器
  • ②调用 Feign 接口方法时，代理的 invoke 方法执行，解析方法上的注解（@GetMapping 等）构建 HTTP 请求
  • ③通过 Spring Cloud LoadBalancer 从 Nacos 获取目标服务实例列表，按负载均衡策略选一个 IP:Port
  • ④经过 Sentinel 检查（流控/熔断规则），通过则用 HTTP Client（默认 JDK，推荐 OkHttp3）发起真实请求
  • ⑤响应 JSON 由 Jackson 反序列化为返回类型，异常情况进入 fallback

与 RestTemplate 的区别：RestTemplate 需要手动拼 URL、手动序列化/反序列化、手动处理异常；Feign 只需写接口声明，代码更简洁，且原生整合 LoadBalancer、Sentinel，无需额外配置。

Q13 Feign 调用超时如何配置？超时和重试有什么需要注意的？ 高频 ▾
考察点

超时和重试配置是生产必备，能说出非幂等接口不能随意配重试是加分项。

参考回答
spring:
  cloud:
    openfeign:
      client:
        config:
          default:              # 全局默认配置
            connect-timeout: 2000   # 连接超时 2 秒
            read-timeout: 5000      # 读超时 5 秒
          user-service:         # 针对 user-service 单独配置

  • GET 可以重试查询类接口是幂等的，失败后重试另一个实例不会有副作用。配置 Feign 的 Retryer 或 Gateway 的 Retry Filter。

Q14 Spring Cloud 的客户端负载均衡有哪些策略？和服务端负载均衡有什么区别？ 高频 ▾
考察点

客户端负载均衡是 Spring Cloud 区别于传统架构的重要特性，能说清客户端 vs 服务端的区别是基础。

参考回答

客户端 vs 服务端负载均衡：

  • 服务端负载均衡（Nginx/SLB）请求先到负载均衡服务器，由它转发到后端实例。消费方只知道负载均衡的 IP，不知道后端实例列表。引入了一个中间节点，有额外网络 RTT。
  • 客户端负载均衡（LoadBalancer）消费方本地持有实例列表，自己选一个实例直接调用。没有中间节点，延迟更低，且可以实现更灵活的策略（如同集群优先）。

Spring Cloud LoadBalancer 内置策略：

  • 轮询（默认）RoundRobinLoadBalancer，依次轮流选实例，适合实例配置相同的场景
  • 随机RandomLoadBalancer，随机选一个
  • Nacos 权重NacosLoadBalancer（引入 spring-cloud-starter-alibaba-nacos-discovery），按 Nacos 控制台配置的实例权重分流，权重 0 = 不接收流量（优雅下线）

Q15 微服务如何实现灰度发布（金丝雀发布）？ 重点 ▾
考察点

灰度发布是生产必备的发布策略，能给出两种方案（权重/Header 定向）是工程实践能力的体现。

参考回答

灰度发布让新版本先接收少量流量，验证功能和性能，逐步扩大比例。两种常见方案：

  • 方案1：比例分流Gateway 使用 Weight 断言，旧版本实例注册为 old-group（权重90），新版本实例注册为 new-group（权重10），90% 流量走旧版本，10% 走新版本。通过调整权重逐步放量。
  • 方案2：Header 定向灰度Gateway 根据请求 Header（如 X-Version: v2 或 Cookie 中的灰度标识）将特定用户路由到新版本实例。适合内测用户、员工验证场景，精确控制灰度人群。
  • 方案3：Nacos 实例元数据新版本实例在 Nacos 注册时打标签（metadata: {version: v2}），自定义 LoadBalancer 根据请求上下文（ThreadLocal 传递的灰度标）选择对应版本实例，实现全链路灰度（Gateway → 服务 A → 服务 B 都走新版本）。

Q16 微服务间调用如何传递认证信息（Token/Header）？ 高频 ▾
考察点

服务间传递 Token 是实际开发高频场景，Feign 拦截器是标准解法。

参考回答

Gateway 解析 Token 后把用户信息写入 Header（如 X-User-Id），下游服务通过 Feign 调用其他服务时，需要把这些 Header 透传过去。

最优雅的方式是实现 Feign 的 RequestInterceptor：

@Component
public class FeignTokenInterceptor implements RequestInterceptor {

    @Override
    public void apply(RequestTemplate template) {
        // 从当前请求的 Header 中取出用户 ID，附加到 Feign 请求
        ServletRequestAttributes attrs = (ServletRequestAttributes)
            RequestContextHolder.getRequestAttributes();
        if (attrs != null) {
            HttpServletRequest request = attrs.getRequest();
            String userId = request.getHeader("X-User-Id");
            if (userId != null) {
                template.header("X-User-Id", userId);
            }
            // 也可以传递 Token 本身（如果下游服务需要鉴权）
            String token = request.getHeader("Authorization");
            if (token != null) {
                template.header("Authorization", token);
            }
        }
    }
}

注意：如果是异步调用（CompletableFuture），RequestContextHolder 是基于 ThreadLocal 的，需要手动传递到子线程（RequestContextHolder.setRequestAttributes(attrs, true)）。

Q17 什么是服务雪崩？如何防止？ 高频重点 ▾
考察点

服务雪崩是微服务最核心的稳定性问题，能给出超时+熔断+限流三层防御是完整回答。

参考回答

服务雪崩：在调用链 A→B→C 中，C 响应变慢，B 等待 C 的线程阻塞，线程池耗尽，B 无法处理新请求，A 等待 B 的线程也阻塞……最终整个系统级联崩溃。

三层防御体系：

  • 超时所有远程调用必须设置超时时间（connectTimeout + readTimeout），避免线程无限等待。这是最基础的防御，成本最低。
  • 熔断通过 Sentinel 监控调用的错误率/慢调用比例，超过阈值触发熔断，后续请求直接走 fallback 降级，不再真正调用下游。避免大量线程阻塞在下游。经过熔断时间窗口后尝试恢复（Half-Open）。
  • 限流通过 Sentinel 对入口 QPS/并发数限流，把超出系统承载能力的请求提前拒绝，防止过载。

此外，仓壁模式（Bulkhead）：为不同下游服务分配独立线程池，一个下游慢不影响其他下游的线程资源。Sentinel 的并发线程数限制可以实现类似效果。

Q18 Sentinel 的限流算法有哪些？滑动窗口和令牌桶有什么区别？ 高频重点 ▾
考察点

四种限流算法的原理和适用场景是算法 + 工程双重考点，高频出现。

参考回答
算法原理优点缺点适用
固定窗口统计固定时间窗口（如1秒）内的请求数，超阈值拒绝实现简单窗口边界突刺（两个窗口交界处可能2倍流量通过）精度要求不高
滑动窗口（Sentinel默认）把时间窗口分成多个小格，统计最近N格的总请求数，平滑统计解决边界突刺实现较复杂，内存占用略多精确流控（Sentinel 默认）

漏桶请求先进桶，桶以固定速率漏出处理，桶满则拒绝强制匀速输出，保护下游不允许突发，响应时间增加流量整形，均匀输出

Q19 Sentinel 熔断有哪三种策略？各自的触发条件是什么？ 高频 ▾
考察点

三种熔断策略的触发条件和适用场景是必答内容。

参考回答
  • 慢调用比例在统计时间窗口内，响应时间超过设定 RT（如 500ms）的请求比例超过阈值（如 50%），且请求数达到最小触发数，触发熔断。适合下游服务响应变慢的场景。
  • 异常比例在统计时间窗口内，异常请求数占总请求数的比例超过阈值（如 50%），且请求数达到最小触发数，触发熔断。适合下游大量报错的场景。
  • 异常数在统计时间窗口内，异常总数超过设定阈值，触发熔断。不按比例，是绝对数量控制。适合流量很低时（比例计算不准），几个异常就应该熔断的场景。

熔断后进入 OPEN 状态，经过熔断时间窗口（如 10 秒）后变为 HALF-OPEN，放行一个探测请求：成功则恢复（CLOSED），失败则继续熔断（OPEN）。

Q21 熔断器的三种状态（Closed/Open/Half-Open）是如何转换的？ 高频 ▾
考察点

熔断器状态机是必答题，是最常见的面试考点之一。

参考回答
  • CLOSED（关闭）正常状态，请求正常通过，Sentinel 实时统计指标（错误率/慢调用比例）
  • CLOSED → OPEN统计窗口内，指标超过熔断阈值 → 触发熔断，进入 OPEN 状态
  • OPEN（断开）熔断状态，所有请求直接拒绝（走 fallback），不发起真实调用，保护下游
  • OPEN → HALF-OPEN经过熔断时间窗口（熔断持续时间），进入 HALF-OPEN 状态
  • HALF-OPEN（半开）放行一个探测请求：若成功 → CLOSED（恢复正常）；若失败 → 重新 OPEN（继续熔断）

核心设计思路：OPEN 状态防止雪崩（不再请求下游），HALF-OPEN 实现自动恢复（不需要人工介入）。熔断时间窗口设置要合理：太短频繁切换 OPEN/HALF-OPEN，太长恢复太慢影响可用性。

Q22 Sentinel 的 Fallback 降级怎么实现？和限流拒绝怎么区分处理？ 重点 ▾
考察点

Fallback 实现和异常区分是开发中实际会遇到的问题，能说清 FlowException/DegradeException 和业务异常的区别是加分点。

参考回答

两种方式：

方式1：OpenFeign + Sentinel（推荐）

@FeignClient(name = "user-service",
             fallbackFactory = UserFallbackFactory.class)
public interface UserFeignClient {
    @GetMapping("/user/{id}")
    UserDTO getUser(@PathVariable Long id);
}

@Component
public class UserFallbackFactory implements FallbackFactory<UserFeignClient> {
    @Override
    public UserFeignClient create(Throwable cause) {
        if (cause instanceof FlowException) {
            log.warn("user-service 被限流");
        } else if (cause instanceof DegradeException) {
            log.warn("user-service 触发熔断");
        } else {
            log.error("user-service 调用异常", cause);
        }
        // 返回降级数据
        return id -> UserDTO.defaultUser(id);
    }
}

方式2：@SentinelResource 注解

@SentinelResource(value = "getUserById",
                  blockHandler = "handleBlock",  // 限流/熔断处理
                  fallback = "handleFallback")    // 其他异常处理
public UserDTO getUserById(Long id) { ... }

// 限流/熔断时调用（必须是同类的静态或非静态方法，参数加 BlockException）
public UserDTO handleBlock(Long id, BlockException e) {
    return UserDTO.defaultUser(id);
}

// 业务异常时调用
public UserDTO handleFallback(Long id, Throwable t) {
    return UserDTO.defaultUser(id);
}

Q24 什么是热点参数限流？适合什么场景？ 重点 ▾
考察点

热点参数限流是 Sentinel 的特色功能，能给出秒杀商品的具体场景是工程实践的体现。

参考回答

热点参数限流：对同一接口，针对某个参数的特定值单独限流，而不是对整个接口 QPS 统一限流。

典型场景：秒杀商品查询接口 GET /product/{productId}。秒杀开始时，某几个热门商品（如 productId = 100, 200）的 QPS 极高，而普通商品 QPS 很低。

热点参数限流：对 productId = 100 单独限流 5000 QPS，对 productId = 200 单独限流 3000 QPS，对其他 productId 默认限流 200 QPS。精确控制，不影响普通商品的正常访问。

Q25 微服务中为什么需要分布式事务？本地事务为什么解决不了？ 高频重点 ▾
考察点

理解分布式事务的必要性是回答 Seata 等方案的基础，能给出具体场景是加分项。

参考回答

本地事务（数据库 ACID 事务）只能保证单个数据库内的原子性。微服务每个服务有独立的数据库，跨服务的操作分散在不同数据库，数据库事务管理器无法跨越数据库边界。

典型场景：电商下单 = 创建订单（order_db）+ 扣减库存（stock_db）+ 扣减余额（account_db）。三个操作在三个数据库：

  • →订单创建成功，库存扣减成功，扣余额时账户不足失败 → 库存被扣了但订单应该回滚 → 数据不一致
  • →订单创建成功，扣库存时网络超时（不知道成功还是失败）→ 是重试还是回滚？无法判断

解决方案：Seata（强一致）/ 消息最终一致性（本地消息表 + MQ）/ TCC（柔性事务）。选哪种取决于业务对一致性的要求和对性能的权衡。

Q26 Seata AT 模式的原理是什么？如何实现回滚？ 高频重点 ▾
考察点

AT 模式是 Seata 最常用的模式，能说清 TC/TM/RM 三角色和 undo_log 回滚机制是必答内容。

参考回答

三个角色：

  • TC（Transaction Coordinator）Seata Server，维护全局事务状态，收集所有 RM 的分支事务结果，决定全局提交或回滚
  • TM（Transaction Manager）事务发起方（加了 @GlobalTransactional 的服务），向 TC 注册全局事务，最终触发提交/回滚
  • RM（Resource Manager）各参与服务，向 TC 注册分支事务，执行本地事务，上报结果

AT 模式两阶段：

  • Phase 1各服务执行本地事务前，Seata 的 DataSourceProxy 解析 SQL，查询前镜像（before image），执行 SQL，查询后镜像（after image），将前后镜像写入 undo_log 表，提交本地事务，向 TC 注册分支事务
  • Phase 2（提交）所有分支成功，TC 通知各 RM 异步删除 undo_log，全局提交完成
  • Phase 2（回滚）任一分支失败，TC 通知各 RM 用 undo_log 生成逆向 SQL（将数据恢复为 before image）执行，回滚本地事务，删除 undo_log

Q27 Seata 的 AT、TCC、Saga 三种模式怎么选？ 高频 ▾
考察点

三种模式的选型判断是实战能力的体现，核心是侵入性 vs 性能的权衡。

参考回答
模式侵入性性能一致性适用场景
AT（默认）极低（只加注解）中（有全局锁）最终一致普通数据库操作，大多数业务场景
TCC高（实现 Try/Confirm/Cancel）高（无全局锁）最终一致性能要求高，可以容忍代码侵入
Saga高（实现补偿逻辑）高最终一致长流程业务，跨组织事务

  • 长流程选 Saga业务步骤多（5步以上）且每步耗时长，AT 长时间持有全局锁不合适，Saga 每步操作后立即提交，有失败再触发补偿。

Q28 不用 Seata，如何保证跨服务的数据最终一致性？ 高频重点 ▾
考察点

消息最终一致性是比 Seata 更轻量的方案，在很多场景下是更好的选择，能说清本地消息表模式是高分回答。

参考回答

最常用的方案是消息最终一致性（本地消息表 + 消息队列）：

  • ① 本地事务在同一数据库事务中，写业务数据 + 写消息表（message_outbox），保证两者原子性
  • ② 轮询发送独立的消息发送线程/定时任务，扫描 message_outbox 中未发送的消息，发送到 MQ，发送成功后更新状态为"已发送"
  • ③ 消费者处理下游服务消费 MQ 消息，执行对应业务操作，需要保证幂等（消息可能重复投递）
  • ④ 失败重试发送失败或消费失败，MQ 重试机制保证最终投递成功

适用场景：对一致性要求是"最终一致"（允许秒级延迟），而不是"强一致"（立即一致）。如订单支付成功后通知发货系统、积分系统，不需要实时强一致，用消息异步解耦更合适。

优点 vs Seata：无分布式事务的性能开销，系统解耦，吞吐更高。
缺点：有延迟，不能保证立即一致，业务逻辑要处理幂等。

Q29 微服务链路追踪是如何实现的？Trace ID 如何在服务间传递？ 高频 ▾

参考回答

微服务部署几十个实例，日志分散在各服务器上，必须用日志聚合方案统一查询。主流方案：

  • 采集每个服务节点部署 Filebeat（Sidecar 或 DaemonSet），采集服务日志文件，发送到 Logstash 或直接到 Elasticsearch
  • 处理Logstash 解析日志格式（JSON 或正则提取），提取 TraceId、ServiceName、Level 等字段
  • 存储结构化日志存入 Elasticsearch，按天/周索引管理，设置 ILM 策略自动清理旧数据
  • 查询通过 Kibana 按 TraceId 查全链路日志，按 ServiceName 查特定服务，按 Level=ERROR 查错误日志

最佳实践：日志使用 JSON 格式输出，包含 traceId、service、level、timestamp、message 字段，Elasticsearch 自动解析，无需 Logstash 额外处理。

Q31 微服务接口升级时如何保证向后兼容？ 重点 ▾
考察点

接口版本管理是多服务协作的必备能力，能给出具体实践规范是加分项。

参考回答

微服务各服务独立部署，不能假设所有消费方都同时升级。接口升级必须向后兼容：

  • ① 新增字段请求/响应新增可选字段时，旧消费方不会传/解析这个字段，完全兼容。JSON 序列化天然容忍多余字段（@JsonIgnoreProperties(ignoreUnknown=true)）
  • ② 废弃字段先标注 @Deprecated，保留至少一个版本（或一个发布周期），给消费方足够时间升级，再删除
  • ③ 不兼容变更修改字段类型、删除字段、修改接口语义这类不兼容变更，必须新建接口版本（/v2/user/{id}），旧接口保留一段时间并行运行，等消费方迁移完毕后下线旧接口
  • ④ 接口契约测试引入 Pact 等契约测试框架，消费方和提供方都维护接口契约，CI 中自动验证接口兼容性，防止意外破坏

原则：宁可保留废弃接口多一个版本，也不要强制所有消费方同时升级（分布式系统中这是不可能的）。

Q32 微服务拆分有哪些原则？如何避免拆得太细（过度微服务化）？ 高频 ▾
考察点

拆分原则是架构设计终极题，能说出"两个披萨原则"和过度拆分的反模式是成熟架构师的体现。

参考回答

拆分六大原则：

  • 单一职责每个服务只负责一个业务域，一个服务被频繁修改多个不相关功能说明职责混乱
  • DDD 限界上下文按业务边界拆，而不是按技术层拆。订单、用户、库存是天然边界
  • 数据库独立每个服务只能操作自己的数据库，不允许跨库直接访问
  • 团队自治一个服务由一个团队负责。"两个披萨原则"：两个大披萨能喂饱负责这个服务的团队（约 5~8 人）
  • 高内聚低耦合服务内部功能紧密相关；服务间只通过 API 交互，不共享代码库
  • 可独立部署每个服务能独立构建、测试、部署，不依赖其他服务一起发布

过度拆分的反模式（避免）：

  • NanoService每个方法一个服务，网络调用比业务逻辑还多，大量分布式事务，维护地狱
  • 技术层拆分拆成 DAO 服务、Service 服务、Controller 服务——每次业务操作要跨 3 个服务调用
  • 共享数据库多个服务共享同一个库——这是单体数据库，不是微服务

拆分的时机判断：当一个模块的 QPS/资源需求与整体差异明显、多团队频繁在同一模块冲突、需要独立技术栈时，才是拆分的时机。不要提前过度设计。
