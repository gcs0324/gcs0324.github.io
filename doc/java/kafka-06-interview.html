01架构原理类
Q1 ARCH Kafka 为什么吞吐量这么高？请从多个维度回答。

Kafka 的高吞吐来源于多项设计的叠加：

  • 顺序写磁盘（Append-Only）：Kafka 只追加写，磁盘顺序写速度接近内存随机写（600 MB/s），远高于数据库 B+Tree 的随机写（几十 MB/s）。
  • OS Page Cache：写入直接打到 Page Cache，由 OS 异步刷盘，消费也优先命中 Cache，消费者甚至不需要读磁盘。
  • 零拷贝（sendfile）：消费者拉取时，内核通过 DMA 直接将数据从 Page Cache 传到网卡，跳过"内核→用户态→内核"的两次拷贝，减少 CPU 上下文切换。
  • 批量发送 + 压缩：RecordBatch 打包多条消息一次发送，Snappy/LZ4/ZSTD 压缩减少网络传输量，极大降低网络往返次数。
  • Partition 并行：Topic 拆分为多个 Partition 分散在不同 Broker，Producer 和 Consumer 可并行读写，水平扩展吞吐量。
Q2 ARCH Partition 的作用是什么？Partition 数量设多少合适？

作用：Partition 是 Kafka 并行和水平扩展的基础单元。一个 Topic 的 Partition 可以分布在不同 Broker 上，实现负载均衡；Consumer Group 内每个 Partition 只能被一个 Consumer 消费，Partition 数决定消费并行度的上限。

数量设计原则：分区数越多并行度越高，但 Leader 选举开销、文件句柄消耗也随之增加（每个 Partition 在 Broker 上至少 3 个文件句柄）。

  • 经验公式：目标吞吐量 / 单 Partition 吞吐上限（通常 10~50 MB/s）
  • 通常不超过 100 个分区，结合实际 Consumer 实例数来定
  • 一旦 Partition 数增加，Key 路由结果改变，需谨慎评估对顺序消费的影响
Q3 ARCH ISR 机制是什么？Follower 什么情况下会被移出 ISR？

ISR（In-Sync Replicas） 是与 Leader 保持同步的副本集合。AR（全部副本）= ISR + OSR（落后副本）。

移出 ISR 的条件：Follower 在 replica.lag.time.max.ms（默认 30s）内没有向 Leader 发送 Fetch 请求，或拉取进度落后超过此时间，则被 Controller 从 ISR 中移除，进入 OSR。当 Follower 追上 Leader 后重新加入 ISR。

意义：acks=all 要求 ISR 中所有副本都写入才确认。ISR 动态收缩保证了即使部分 Follower 落后，也不会无限阻塞 Producer。

Q4 ARCH HW 和 LEO 的区别？HW 如何推进？
  • LEO（Log End Offset）：每个副本自己的下一条待写入消息的 Offset，即当前日志末尾 + 1，每个副本各自维护。
  • HW（High Watermark）：消费者可见的最大 Offset，等于 ISR 中所有副本 LEO 的最小值。HW 之前的消息才能被消费者读取。

HW 推进流程：Follower 向 Leader 发送 Fetch 请求时携带自己的 LEO。Leader 收到后更新该 Follower 的 LEO 记录，重新计算 ISR 中的 min(LEO)，更新 HW，并在下一次 Fetch 响应中将新 HW 告知所有 Follower。

例：Leader LEO=10，Follower1 LEO=8，Follower2 LEO=9 → HW = min(10,8,9) = 8，消费者只能看到 offset 0~7。

Q7 PRODUCER Producer 幂等的原理？只能保证哪个范围内的幂等？

原理：开启 enable.idempotence=true 后，Broker 为每个 Producer 分配唯一的 ProducerID（PID），Producer 为每个 Partition 的每条消息分配单调递增的 SequenceNumber。Broker 记录每个（PID, Partition）对应的最大已接受 SequenceNumber，若收到重复消息（相同 PID + 相同 SequenceNumber）则直接丢弃，不重复写入。

局限性：

  • 只能保证单个 Partition、单次 Session（Producer 重启后 PID 变更，之前的 SequenceNumber 记录失效）内的幂等
  • 跨多个 Partition 的原子写入需要事务 Producer（transactional.id），PID 与 transactional.id 绑定，重启后可恢复
Q8 PRODUCER Kafka 事务消息怎么实现？Exactly-Once 的完整方案？

事务 Producer 核心流程：

  • 设置 transactional.id，Broker 端用于跨 Session 恢复事务状态
  • 调用链：initTransactions() → beginTransaction() → send()（可跨多个 Partition）→ commitTransaction() / abortTransaction()
  • 事务日志存储在 __transaction_state Topic（50 个 Partition）

Exactly-Once 完整方案（CTP 模式）：

  • Consumer 端设置 isolation.level=read_committed，过滤未提交事务的消息
  • Consumer 消费 → 处理 → Producer 发送新消息 + 提交 Offset，三步在同一 Kafka 事务内原子完成
  • 事务提交 ↔ Offset 提交同步，宕机重启后消费位置和消息发送都能正确恢复
Q9 PRODUCER 消息发送链路中 RecordAccumulator 的作用？

RecordAccumulator 是 Producer 的内存缓冲区，位于业务线程和 Sender 线程之间，实现批量发送和线程解耦：

  • 业务线程调用 send() 后，消息不立即发网络，而是按 Partition 追加到对应的 Deque<ProducerBatch> 中
  • Sender 线程轮询 Accumulator，当批次大小达到 batch.size（默认 16KB）或等待时间超过 linger.ms 时，将批次通过 NetworkClient 发送给 Broker
  • 总缓冲区大小由 buffer.memory（默认 32MB）控制，满时 send() 阻塞，超过 max.block.ms 抛异常
03Consumer 类
Q10 CONSUMER Rebalance 的触发条件有哪些？如何避免频繁 Rebalance？

触发条件：

  • Consumer 加入 Group（新实例启动）
  • Consumer 离开 Group（正常关闭或崩溃）
  • 心跳超时（超过 session.timeout.ms，默认 45s，Coordinator 认为 Consumer 宕机）
  • 消费处理超时（超过 max.poll.interval.ms，默认 5min，Consumer 被踢出）
  • Topic Partition 数变更
  • Consumer 订阅的 Topic 数量变化

避免措施：

  • 调大 session.timeout.ms（如 60s）和 heartbeat.interval.ms（session 的 1/3，如 20s），减少误判
  • 调大 max.poll.interval.ms 或减小 max.poll.records，防止处理超时被踢出
  • 使用 CooperativeStickyAssignor（Kafka 2.4+）实现增量 Rebalance，减少全停影响
  • 避免消费处理逻辑中有长时间阻塞（DB 慢查询、HTTP 调用），必要时异步化
Q11 CONSUMER 手动提交 Offset 和自动提交的区别？各有什么风险？
方式配置语义风险
自动提交 enable.auto.commit=true，每隔 auto.commit.interval.ms（5s）提交 at-most-once（可能丢消息） 消息拉取后提交，但处理前宕机 → 消息丢失；或处理完但还未到提交时间点 → 重复消费
手动同步提交 commitSync()，阻塞直到提交成功 at-least-once 处理完再提交，宕机时重新消费（重复），需业务幂等；提交阻塞会降低吞吐量
手动异步提交 commitAsync(callback)，不阻塞 at-least-once 提交失败不重试（避免乱序），需在 callback 中记录失败告警；关闭时需改用 commitSync 兜底

生产推荐：异步提交（高吞吐）+ 关闭时同步提交（保证最终提交）+ 业务幂等（处理重复）。

Q12 CONSUMER Cooperative Rebalance 和 Eager Rebalance 的区别？
  • Eager Rebalance（默认）：Rebalance 触发时，所有 Consumer 立即停止消费，撤销全部 Partition 分配，等待 GroupCoordinator 重新分配完成后再恢复消费。"全停止"期间服务完全不可用，Rebalance 时间越长影响越大。
  • Cooperative Rebalance（CooperativeStickyAssignor）：增量式 Rebalance，只撤销需要迁移的 Partition。Consumer 继续消费其他 Partition，只停止迁移中的部分，大幅缩短服务中断时间。通常需要两轮协商（Two-Phase）完成迁移。
推荐：Kafka 2.4+ 新项目使用 CooperativeStickyAssignor，配合 partition.assignment.strategy=CooperativeStickyAssignor。从 Eager 迁移到 Cooperative 需要滚动重启。
Q13 CONSUMER Consumer Lag 怎么监控？积压了怎么处理？

Lag = HW − CurrentOffset（该 Partition 已写入但未消费的消息数）

监控方式：

  • 命令行：kafka-consumer-groups.sh --describe --group my-group，查看每个 Partition 的 LAG 列
  • JMX 指标：kafka.consumer:type=consumer-fetch-manager-metrics,records-lag-max
  • 接入 Prometheus + kafka-exporter，配合 Grafana 看板可视化 Lag 趋势告警

积压处理：确认根因 → 扩容 Consumer（≤ Partition 数）→ 批量消费（调大 max.poll.records）→ 极端情况临时扩分区（详见 → 04 · §04）

Q15 RELIABLE 如何实现幂等消费？业务层幂等有哪些方案？

Kafka at-least-once 语义决定消息可能被重复消费，业务层需自行保证幂等（即同一条消息处理多次结果不变）。

  • 数据库唯一键：以消息 ID 或业务主键建 UNIQUE KEY，重复 INSERT 触发唯一键冲突直接忽略。最简单可靠，适合 Insert 类操作。
  • Redis SETNX 去重：消费前 SET msgId NX EX TTL，已存在跳过。高并发场景常用，但 Redis 和 DB 操作非原子，需配合 DB 幂等。
  • 状态机判断：业务对象有明确状态流转（CREATED→PAID→SHIPPED），只在合法状态下执行变更，"查状态 + 变状态"必须在同一事务内。
  • 乐观锁版本号：UPDATE ... WHERE id=? AND version=?，重复操作版本号不匹配自动失败，适合 Update 类操作。
Q16 RELIABLE 如何保证消息顺序？全局顺序和局部顺序有什么区别？
  • 全局顺序：Topic 只有 1 个 Partition + Consumer Group 内只有 1 个 Consumer。所有消息严格有序，但吞吐量受限，且单点可用性低。
  • 局部顺序（推荐）：相同业务 Key（如订单 ID）通过 murmur2 哈希固定落到同一 Partition，该 Partition 内严格有序。不同 Key 可并行消费，吞吐量高。
  • 多线程消费保序：若需要多线程提升吞吐，可按 Key hashCode % 线程数 路由到固定线程处理，保证同 Key 在同一线程内有序。
⚠ 扩分区破坏顺序：增加 Partition 数后，相同 Key 可能路由到不同 Partition，顺序保证失效。需在业务低峰期操作，并处理过渡期的顺序问题。
Q17 RELIABLE 消息积压了如何紧急处理？

分四步处理，从快到慢：

  • ① 确认根因：区分是消费速率低还是生产速率暴增，检查业务处理耗时、下游 DB/Redis 响应时间、Consumer Lag 趋势。
  • ② 快速扩容 Consumer：新增 Consumer 实例（不超过 Partition 数），触发 Rebalance 后立即提升并行消费能力。Consumer 数量上限 = Partition 数。
  • ③ 批量消费优化：增大 max.poll.records，改为批量入库代替逐条处理，减少数据库 IO 次数。
  • ④ 临时扩分区（极端情况）：若 Consumer 已扩到 Partition 上限仍不够，停止原 Topic 写入 → 消费原 Topic 并转发到多分区新 Topic → 用更多 Consumer 并行消费新 Topic。

Q18 COMPARE Kafka vs RocketMQ — 延迟消息、事务消息、消费模型有什么区别？
⚡ Kafka
延迟消息：原生不支持，需借助延迟 Topic 或 Redis 时间轮
事务消息：支持，基于 Producer 两阶段提交，适合 CTP 流处理
消费模型：Consumer Group 竞争消费；不同 Group 各自消费（广播）
消费方式：Pull 模式，Consumer 主动拉取
吞吐量：极高（百万 TPS），日志/流处理首选

延迟消息：原生支持 18 个级别（1s ~ 2h），4.x 商业版支持任意精度
事务消息：支持半消息（Half Message）+ 事务回查机制，更适合业务事务

消息回查：Broker 主动回查 Producer 事务状态，更易实现最终一致
Q19 COMPARE Kafka vs RabbitMQ — 吞吐量、路由能力、适用场景有何差异？
⚡ Kafka
吞吐量：极高（百万 TPS），磁盘顺序写 + 零拷贝
路由：按 Topic + Partition，通过 Key 路由，简单但高效
持久化：消息保留 7 天（默认），可回溯重消费
延迟：毫秒级（配置 linger.ms=0）
场景：日志收集、流计算、事件溯源、大数据管道
🐰 RabbitMQ
吞吐量：万级 TPS，基于 AMQP 协议，有更多协议开销
路由：Exchange + Binding Key，支持 Direct/Fanout/Topic/Headers 多种路由模式
持久化：消费后即删除（默认），不支持回溯
延迟：微秒级（内存队列）
场景：任务队列、RPC 模式、复杂路由分发、低延迟通知
Q20 COMPARE 什么场景选 Kafka？什么场景不适合用 Kafka？

✅ 选 Kafka 的场景：

  • 高吞吐日志收集、用户行为埋点（百万 TPS 以上）
  • 实时流处理管道（Kafka Streams / Flink 消费 Kafka）
  • 事件溯源（Event Sourcing），需要回溯历史消息
  • 微服务解耦，多消费方订阅同一主题（不同 Consumer Group）
  • 数据库变更数据捕获（CDC，Debezium + Kafka）

❌ 不适合 Kafka 的场景：

  • 延迟消息：原生不支持，需额外实现，不如 RocketMQ 直接
  • 复杂路由：需要 fanout、topic 匹配等复杂分发逻辑，RabbitMQ 更合适
  • 极低延迟（微秒级）：Kafka 最低毫秒级，对延迟极敏感的场景不适用
  • 消息量很小的业务：Kafka 运维成本较高，小规模业务用 RabbitMQ 或 Redis 更轻量

Q22 ~ BONUS 补充：Kafka 消息可以保证 Exactly-Once 吗？怎么做到的？

Kafka 在特定条件下可以实现 Exactly-Once：

  • Producer 幂等（单 Partition）：enable.idempotence=true，依靠 PID + SequenceNumber，单 Partition 单 Session 内不重复。
  • 事务 Producer（跨 Partition）：开启 transactional.id，Producer 两阶段提交保证跨 Partition 原子写入。
  • Consumer 端 Exactly-Once：需要 isolation.level=read_committed，只消费已提交事务的消息。
  • 端到端 Exactly-Once（CTP）：消费 + 处理 + 发布 + Offset 提交在同一 Kafka 事务内，Kafka Streams 原生支持此语义（通过配置 processing.guarantee=exactly_once_v2）。
⚠ 注意：Kafka Exactly-Once 仅保证"消息在 Kafka 管道内不重复"，不保证消费者的外部操作（如写 DB）精确一次。外部操作的幂等需要业务层自己保证。
