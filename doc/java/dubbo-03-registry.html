1. ZooKeeper 注册中心

节点结构

/dubbo
  └── com.example.UserService
        ├── providers
        │   ├── dubbo://192.168.1.1:20880/...  （临时节点）
        │   └── dubbo://192.168.1.2:20880/...
        ├── consumers
        │   └── consumer://192.168.2.1/...
        ├── configurators  （动态配置）
        └── routers        （路由规则）

工作原理

  • Provider 注册：创建临时节点（Ephemeral），Session 断开节点自动删除
  • Consumer 订阅：Watch providers 节点，节点变化时收到通知（推送）
  • ZK 高可用：奇数节点集群（3/5/7），ZAB 协议保证一致性
⚠️ ZooKeeper 保证 CP（一致性 + 分区容忍性），Leader 选举期间注册中心不可用（约 30s），Dubbo Consumer 有本地缓存兜底。

2. Nacos 注册中心

Nacos = 服务注册发现 + 动态配置中心，阿里开源，Dubbo 3.x 推荐。

特性说明
服务注册支持 AP/CP 两种模式切换（临时实例=AP，持久实例=CP）
健康检查临时实例：心跳（默认5s）；持久实例：主动探测
推拉结合订阅推送 + 定期拉取（30s），比 ZK Watch 更灵活
配置管理内置动态配置，支持灰度发布
命名空间环境隔离（dev/test/prod）
集群基于 Raft 协议（CP 模式）

3. ZooKeeper vs Nacos

ZooKeeperNacos
CAP 侧重CP（强一致）AP（默认临时实例）/ CP 可选
通知机制Watch（一次性，需重新注册）长轮询 + Push
健康检查临时节点+Session心跳 + 主动探测
配置中心弱（需额外封装）内置，功能丰富
运维难度较低（成熟）较低（一站式）
Dubbo 推荐Dubbo 2.x 默认Dubbo 3.x 推荐
适用场景强一致需求，分布式锁高可用优先，微服务

4. 负载均衡策略

策略类名算法适用
随机（默认）RandomLoadBalance按权重随机选择通用，Provider 性能相近
轮询RoundRobinLoadBalance按权重平滑轮询Provider 性能相近
最少活跃调用数LeastActiveLoadBalance选当前活跃请求最少的 Provider性能差异大，慢节点自动减少流量
一致性哈希ConsistentHashLoadBalance相同参数打到同一 Provider有状态服务（缓存热点）
最短响应时间ShortestResponseLoadBalance选平均响应最快的 ProviderDubbo 2.7+，性能敏感
// 配置负载均衡
@Reference(loadbalance = "leastactive")  // Consumer 级别
UserService userService;

@Service(loadbalance = "roundrobin")     // Provider 级别
public class UserServiceImpl implements UserService { ... }

// 方法级别
@Reference(methods = {
    @Method(name = "getUser", loadbalance = "consistenthash")
})
💡 一致性哈希通过虚拟节点解决节点分布不均问题，Dubbo 默认 160 个虚拟节点。

5. 路由规则

路由规则在负载均衡前过滤 Provider 列表，支持条件路由、脚本路由、标签路由。

# 条件路由示例（Dubbo Admin 配置）
# Consumer IP 为 10.20.x.x 的流量 → Provider IP 为 10.20.x.x
host = 10.20.153.10 => host = 10.20.153.11

# 服务分组（灰度发布）：tag=gray 的 Consumer → tag=gray 的 Provider
[conditions]
"~tag=gray" => "tag=gray"

标签路由（Dubbo 2.7+）

# 金丝雀发布：10% 流量打到 v2 版本
@Reference(tag = "v2")  // Consumer 带标签请求
// Provider 打标签：application.yml
dubbo:
  provider:
    tag: v2

6. 服务目录

Directory 是 Consumer 侧维护的 Provider 列表容器，负责动态更新和过滤。

实现说明
StaticDirectory静态地址列表，直连场景
RegistryDirectory从注册中心动态获取，订阅变化自动更新
// RegistryDirectory 工作流程
1. 订阅注册中心 providers 节点
2. 节点变化时 notify() 回调
3. 将 URL 列表转换为 Invoker 列表（创建 TCP 连接）
4. Router 过滤（路由规则）
5. LoadBalance 选择（负载均衡）
6. 发起调用
