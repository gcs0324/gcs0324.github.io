1. CAP 定理 / BASE 理论

CAP 定理

分布式系统中只能同时满足以下三点中的两点：

特性说明典型系统
Consistency（一致性）所有节点读到相同数据ZooKeeper（CP）
Availability（可用性）每个请求都有响应（成功/失败）Eureka（AP）
Partition Tolerance（分区容忍）网络分区时系统继续运行几乎所有分布式系统必须满足
💡 网络分区是不可避免的，所以分布式系统实际选择是 CP 或 AP。ZooKeeper 选 CP（Leader 挂掉时短暂不可用）；Eureka 选 AP（节点挂掉后其他节点继续服务，但数据可能不一致）。

BASE 理论（AP 系统的补充）

  • Basically Available：基本可用（允许响应时间延长或部分功能降级）
  • Soft State：软状态（允许数据中间状态，不要求时刻一致）
  • Eventually Consistent：最终一致（经过一段时间后达到一致）

3. 限流算法

算法原理优缺点适用
固定窗口时间窗口内计数，超出拒绝简单；边界突刺（窗口切换瞬间2倍流量）简单场景
滑动窗口细粒度时间格，滑动计数解决边界突刺；内存略大精确限流
漏桶请求入桶，固定速率出桶流量平滑；无法应对突发平滑输出（如消息发送）
令牌桶（推荐）固定速率往桶加令牌，请求取令牌允许突发（桶满时），平均速率限制API 限流（Guava RateLimiter）
// Guava 令牌桶
RateLimiter limiter = RateLimiter.create(100.0); // 每秒 100 个令牌
if (limiter.tryAcquire()) {
    // 处理请求
} else {
    // 限流：返回 429 Too Many Requests
}

// Redis 分布式限流（Lua 脚本保证原子性）
String script = """
    local count = redis.call('incr', KEYS[1])
    if count == 1 then
        redis.call('expire', KEYS[1], ARGV[1])
    end
    return count
""";
Long count = redisTemplate.execute(script, List.of("limit:userId:123"), "60");
if (count > MAX_COUNT) throw new RateLimitException();

4. 缓存策略

常见问题与解决方案

问题描述解决方案
缓存穿透查询不存在的 key，每次都打到 DB缓存空值（TTL短）、布隆过滤器（前置拦截）
缓存击穿热点 key 过期瞬间，大量并发打 DB互斥锁（仅一个线程回源）、逻辑过期（不设 TTL）
缓存雪崩大量 key 同时过期，DB 压力骤增TTL 加随机值、多级缓存、限流+熔断
缓存一致性DB 更新后缓存未及时更新Cache Aside（旁路缓存）、延迟双删
// Cache Aside 模式（最常用）
// 读：先读缓存，缓存 miss 则读 DB 并回填缓存
public User getUser(Long id) {
    User user = cache.get("user:" + id);
    if (user == null) {
        user = db.findById(id);
        if (user != null) cache.set("user:" + id, user, 30, MINUTES);
    }
    return user;
}
// 写：先更新 DB，再删除缓存（不更新，避免并发问题）
public void updateUser(User user) {
    db.update(user);
    cache.delete("user:" + user.getId()); // 删除而非更新
}
// 延迟双删：更新 DB 前删缓存，更新后再延迟删一次（防并发读脏数据）

5. 分库分表

策略说明优缺点
水平分表同一库内，按行拆分到多张表解决单表数据量大；不解决连接压力
水平分库按行拆分到多个库（不同实例）解决连接/IO压力；跨库查询复杂
垂直分库按业务模块拆分（用户库/订单库）低耦合；跨库事务复杂
垂直分表大宽表拆为核心表+扩展表减少 IO，提高查询效率

分片键选择原则

  • 数据分布均匀（避免热点）
  • 业务查询维度匹配（按用户ID分则查询要带用户ID）
  • 范围查询友好（取模 vs 范围分片）

分库分表中间件

中间件类型特点
ShardingSphere-JDBC客户端无中心，轻量，Spring Boot 集成友好
MyCat代理数据库层代理，语言无关
TiDB分布式 DB兼容 MySQL，自动分片，HTAP

7. 典型场景设计

短链系统

  • 长 URL → MD5 取前 6位 → Base62 编码（0-9A-Za-z）→ 短码
  • 哈希冲突：追加随机数或自增序列
  • 短码 → 长 URL 映射存 Redis（TTL）+ MySQL（持久化）
  • 302 重定向（浏览器缓存）vs 301（无法统计点击）

秒杀系统

  • 前端：答题/验证码过滤机器人；页面静态化到 CDN
  • 网关层：限流（用户级 + 接口级），重复下单拦截
  • 库存：Redis 预扣库存（DECRBY，原子操作），成功才入队
  • MQ：异步创建订单，削峰，Consumer 写 DB
  • DB：乐观锁（version）防超卖，最终校对

分布式 ID 生成

方案优点缺点
UUID简单无依赖无序，索引性能差，128bit 较长
数据库自增有序，简单单点，性能瓶颈
Redis INCR高性能，有序依赖 Redis，持久化有风险
Snowflake（雪花）趋势递增，64bit，高性能时钟回拨问题
美团 Leaf号段模式 + Snowflake 双模式有一定复杂度
