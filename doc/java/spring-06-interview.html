Q1 Spring Bean 的完整生命周期是什么？每个阶段做了什么？ 高频 ▼
面试官视角

Spring 面试必考第一题。考察你对 IoC 容器内部工作机制的理解深度。期望听到完整的 7 个阶段，加分点：区分 BeanPostProcessor 的 before/after 调用时机，说明 AOP 代理在哪个阶段生成。

参考回答

Spring Bean 生命周期分为 7 个阶段：

①
实例化（Instantiation）
容器通过反射调用构造器创建 Bean 原始对象，此时属性均为默认值
②
属性填充（Populate Properties）
依赖注入，填充 @Autowired、@Value 等注解标注的属性（三级缓存解循环依赖发生在此阶段）
③
Aware 回调
若实现了 BeanNameAware、BeanFactoryAware、ApplicationContextAware 等接口，此时注入容器内置对象
④
BeanPostProcessor#before
postProcessBeforeInitialization() — 初始化前处理，可在此修改 Bean
⑤
初始化（Initialization）
先执行 @PostConstruct，再执行 InitializingBean#afterPropertiesSet()，最后执行 init-method
⑥
BeanPostProcessor#after ← AOP 代理在此生成
postProcessAfterInitialization() — AOP 代理对象在此阶段由 AbstractAutoProxyCreator 包装生成，放入容器的是代理对象而非原始对象
⑦
销毁（Destruction）
容器关闭时：先执行 @PreDestroy，再执行 DisposableBean#destroy()，最后执行 destroy-method

Q2 Spring 如何解决循环依赖？三级缓存分别存什么？为什么需要三级而不是两级？ 高频 ▼
面试官视角

高频难题，考察对容器内部数据结构的深度理解。很多人知道"三级缓存"，但说不清为什么需要第三级、它和 AOP 的关系。能说清楚第三级缓存（ObjectFactory）延迟代理生成的原因，可以拿高分。

参考回答

Spring 通过三个 Map 解决单例 Bean 之间的 setter 注入循环依赖（构造器注入的循环依赖无法解决）：

缓存层Map 名称存储内容作用
一级缓存singletonObjects完整 Bean（含代理）正常使用的单例池
二级缓存earlySingletonObjects早期暴露的 Bean（可能是代理）防止同一 Bean 被重复代理
三级缓存singletonFactoriesObjectFactory（Lambda）按需生成代理的工厂，延迟代理时机

为什么需要三级而不是两级？核心原因是 AOP 代理：如果 A 和 B 循环依赖，且 A 需要被 AOP 代理，若只有二级缓存，注入给 B 的 A 必须立即是代理对象；但 Spring 的设计是代理在 BeanPostProcessor#after 阶段生成（生命周期末尾），用三级缓存存 ObjectFactory，B 需要 A 时才通过工厂按需生成早期代理，这样代理生成时机与正常流程保持一致。

⚠️ 注意：构造器注入的循环依赖无法解决，因为实例化阶段就需要依赖，此时三级缓存都还没有该 Bean。同理，prototype 作用域的循环依赖也不支持。

Q4 BeanFactory 和 FactoryBean 的区别？FactoryBean 的使用场景？ 重点 ▼
面试官视角

名字很像，容易混淆，是考察细心度的经典题。核心考点：BeanFactory 是容器接口，FactoryBean 是一种特殊 Bean，通过它可以控制 Bean 的创建逻辑。MyBatis 的 MapperFactoryBean 是典型应用。

参考回答
  • ▸BeanFactory：Spring IoC 容器的顶层接口，负责管理所有 Bean 的定义、创建、获取。ApplicationContext 是其子接口，扩展了 AOP、事件、国际化等功能。
  • ▸FactoryBean：一种特殊的 Bean，实现该接口后容器调用 getObject() 方法获取真正要注册的对象，而不是 FactoryBean 本身。通过 &beanName（加 & 前缀）可以获取 FactoryBean 本身。

使用场景：当 Bean 的创建逻辑复杂（无法通过简单构造器完成）时使用，典型案例：

  • ①MyBatisMapperFactoryBean — 通过动态代理生成 Mapper 接口实现
  • ②Spring AOP 的 ProxyFactoryBean — 生成代理对象
  • ③Dubbo / Feign 的服务代理 — 远程调用代理
Q5 Spring 容器的 refresh() 方法做了哪些事？核心步骤是什么？ 高频 ▼
面试官视角

进阶题，考察对容器启动机制的深度掌握。能说出 12 步 refresh() 流程，尤其是 invokeBeanFactoryPostProcessors、registerBeanPostProcessors、finishBeanFactoryInitialization 三个核心步骤，即为加分答案。

参考回答

AbstractApplicationContext#refresh() 是 Spring 容器启动的核心方法，12 个关键步骤：

  • 1prepareRefresh() — 记录启动时间，校验必要属性
  • 2obtainFreshBeanFactory() — 创建 DefaultListableBeanFactory，加载 BeanDefinition
  • 3prepareBeanFactory() — 配置类加载器、注册内置 BeanPostProcessor
  • 4postProcessBeanFactory() — 子类扩展钩子
  • 5invokeBeanFactoryPostProcessors() ★ — 执行 BeanFactoryPostProcessor（配置类解析、@ComponentScan 在此执行）
  • 6registerBeanPostProcessors() ★ — 注册所有 BeanPostProcessor（AOP 的 AnnotationAwareAspectJAutoProxyCreator 在此注册）
  • 7-11消息源、事件广播、子类扩展、监听器注册
  • 12finishBeanFactoryInitialization() ★ — 实例化所有非懒加载单例 Bean（触发完整生命周期）

Q6 Spring Bean 的作用域有哪些？singleton Bean 是线程安全的吗？ 重点 ▼
面试官视角

作用域是基础题，但线程安全是拓展点。很多人直接说"singleton 不安全"而没有分析场景，实际上无状态的 singleton Bean（如 Service、Dao）是安全的，有状态的才不安全。

参考回答
作用域说明适用场景
singleton默认，容器内唯一实例无状态的 Service/Dao
prototype每次 getBean() 新建实例有状态的工具类
request每个 HTTP 请求新建Web 层请求上下文
session每个 HTTP Session 新建用户会话数据
applicationServletContext 级别全局共享数据

singleton 线程安全性：取决于 Bean 是否有可变状态字段。

  • ✅无状态 Bean 线程安全：如 @Service、@Repository 内只有不可变字段和方法局部变量
  • ❌有状态 Bean 不安全：若有 private int count 等可变成员变量，多线程并发修改会出问题，应使用 prototype 或 ThreadLocal
Q7 @Configuration 的 Full 模式和 Lite 模式区别？为什么要加 @Configuration？ 重点 ▼
面试官视角

进阶考点。很多人不清楚 @Configuration 和 @Component 的区别，实际上差别就在 CGLIB 代理，即 Full 模式保证 @Bean 方法间调用返回同一个单例对象。

参考回答
  • ▸Full 模式（加 @Configuration）：Spring 对配置类进行 CGLIB 代理，确保 @Bean 方法内部直接调用其他 @Bean 方法时返回容器中的单例，而不是新建对象。
  • ▸Lite 模式（只加 @Component 或 proxyBeanMethods=false）：配置类不被代理，@Bean 方法被当作普通方法，互相调用时每次都会创建新对象，违反单例语义。但启动速度更快（跳过 CGLIB 代理生成）。
// Full 模式：b() 调用 a() 返回容器中同一个 Bean
@Configuration
public class Config {
    @Bean public A a() { return new A(); }
    @Bean public B b() { return new B(a()); // 返回单例 A
    }
}

Spring Boot 的 AutoConfiguration 类通常加 proxyBeanMethods=false 使用 Lite 模式，因为自动配置类之间不需要方法间单例保证，换取更快启动速度。

Q9 JDK 动态代理和 CGLIB 代理的区别？Spring 什么时候用哪种？ 高频 ▼
面试官视角

AOP 基础必问题。核心考点在选择策略（有接口 vs 无接口），以及 Spring Boot 2.x 默认改为 CGLIB 的原因。加分：说出两者的性能差异和局限性。

参考回答
维度JDK 动态代理CGLIB
代理方式基于接口，实现同一接口基于继承，生成子类
要求目标类必须实现接口目标类不能是 final
性能创建快，调用慢（反射）创建慢，调用快（直接方法调用）
依赖JDK 内置需引入 cglib 依赖（Spring 已内置）

Spring 选择策略：

  • ▸Spring 5.x（Boot 2.x）起：默认使用 CGLIB（即使有接口），可通过 spring.aop.proxy-target-class=false 切换为 JDK
  • ▸原因：JDK 代理要求注入时必须用接口类型接收，CGLIB 更灵活，减少因用实现类注入导致的启动失败
  • ▸强制 CGLIB 条件：目标类无接口，或注解 @EnableAspectJAutoProxy(proxyTargetClass=true)
Q10 AOP 自调用（this.method()）为什么会失效？有哪些解决方案？ 高频 ▼
面试官视角

高频陷阱题，结合 @Transactional 失效场景一起考。原理考察：理解代理对象是容器管理的，this 指向原始对象，所以绕过了代理。解决方案的好坏体现编码规范意识。

参考回答

失效原因：Spring AOP 通过代理对象拦截方法调用。当类内部用 this.method() 调用时，this 指向的是原始对象（未被代理），所以切面逻辑不会执行。

三种解决方案：

  • ①注入自身代理（推荐）：@Autowired 注入自身 Bean，通过代理 Bean 调用。Spring Boot 需开启 spring.main.allow-circular-references=true
  • ②AopContext 获取代理：((MyService) AopContext.currentProxy()).method()，需开启 @EnableAspectJAutoProxy(exposeProxy=true)
  • ③重构代码（最优）：将被调用方法抽取到另一个 Bean 中，从根本上避免自调用

Q11 多个切面作用于同一方法时，执行顺序如何控制？ 重点 ▼
参考回答

通过 @Order(n) 注解或实现 Ordered 接口控制，数值越小优先级越高（先进后出，类似栈结构）：

  • ▸@Order(1) 的切面：先执行 Before，最后执行 After
  • ▸@Order(2) 的切面：后执行 Before，先执行 After
// 执行顺序示意（Order=1 优先级高）
Order1.before → Order2.before → [目标方法] → Order2.after → Order1.after

不指定 @Order 时，顺序不确定（取决于 Spring 扫描顺序）。同一切面内多个 @Around 方法按声明顺序执行。

Q12 Spring AOP 和 AspectJ 的区别？各自适用场景？ 重点 ▼
参考回答
维度Spring AOPAspectJ
实现方式运行时动态代理编译时/类加载时织入
织入时机运行期编译期 / 类加载期
切点范围仅 Spring Bean 方法任意 Java 代码（字段、构造器等）

Q13 @Around、@Before、@After、@AfterReturning、@AfterThrowing 的执行顺序？ 重点 ▼
参考回答
Around(before) → Before → [目标方法执行]
  ↓ 正常返回
  AfterReturning → After → Around(after)
  ↓ 异常返回
  AfterThrowing → After → (Around 不执行 proceed 后代码)

关键点：@Around 包裹所有其他通知，@After 相当于 finally（无论是否异常都执行），@AfterReturning 和 @AfterThrowing 互斥只执行一个。

Q14 Spring AOP 的底层实现原理？AnnotationAwareAspectJAutoProxyCreator 的作用？ 重点 ▼
参考回答

AnnotationAwareAspectJAutoProxyCreator 是 Spring AOP 的核心，它是一个 BeanPostProcessor：

  • ①在 registerBeanPostProcessors 阶段被注册到容器
  • ②在每个 Bean 初始化完成后（postProcessAfterInitialization），检查是否有切面匹配该 Bean
  • ③若匹配，使用 JDK 代理或 CGLIB 生成代理对象，将 Advice 编织进去
  • ④容器中注册的是代理对象，后续注入给其他 Bean 的也是代理对象

通过 @EnableAspectJAutoProxy 注解（或 Spring Boot 自动装配）触发 AspectJAutoProxyRegistrar 向容器注册该 Creator。

Q15 @Transactional 失效的场景有哪些？如何排查？ 高频 ▼
面试官视角

事务面试必考，能列举 5+ 种场景且说清楚原因的候选人都不多。建议分类记忆：代理问题、异常问题、传播问题、线程问题。

参考回答

共 7 类失效场景：

  • ①方法非 public — Spring AOP 无法代理非 public 方法（CGLIB 子类覆盖限制）
  • ②同类自调用 — this.method() 绕过代理，同 AOP 自调用失效原理
  • ③异常被 catch 吞掉 — 事务感知不到异常，正常提交
  • ④异常类型不匹配 — 默认只回滚 RuntimeException 和 Error，checked 异常需配置 rollbackFor=Exception.class
  • ⑤多线程操作 — 事务绑定在 ThreadLocal 上，子线程无法继承父线程的事务
  • ⑥数据库引擎不支持 — MySQL MyISAM 不支持事务（InnoDB 支持）
  • ⑦传播行为配置错误 — 如配置了 PROPAGATION_NOT_SUPPORTED 挂起事务

Q18 readOnly=true 只读事务有什么作用？一定不能写数据吗？ 重点 ▼
参考回答

@Transactional(readOnly=true) 的作用：

  • ①数据库优化：MySQL InnoDB 跳过 undo log 生成，减少锁资源，优化读性能
  • ②一致性读：在同一事务内多次查询看到一致的快照（防止不可重复读）
  • ③不强制禁止写：readOnly 是建议性的，驱动层可能不检查，但 ORM 框架（如 Hibernate）可能抛异常

适用场景：查询方法、报表生成、批量读取，可与 PROPAGATION_SUPPORTS 组合使用。

Q19 Spring 事务隔离级别和数据库隔离级别的关系？DEFAULT 是什么？ 重点 ▼
参考回答

Spring 的 Isolation 枚举对应数据库标准隔离级别，多了一个 DEFAULT：

Spring 枚举说明
DEFAULT使用数据库默认隔离级别（MySQL 默认 REPEATABLE_READ）
READ_UNCOMMITTED读未提交（脏读、不可重复读、幻读都可能发生）
READ_COMMITTED读已提交（Oracle/PgSQL 默认，解决脏读）
REPEATABLE_READ可重复读（MySQL 默认，解决脏读+不可重复读）
SERIALIZABLE串行化（性能最差，完全隔离）

推荐生产使用 DEFAULT，让数据库自行管理，避免代码和数据库配置不一致导致的问题。

Q20 编程式事务和声明式事务各自的优缺点？什么场景适合编程式？ 重点 ▼
参考回答
维度声明式（@Transactional）编程式（TransactionTemplate）
侵入性低（注解）高（代码级别）
粒度方法级别（粗粒度）代码块级别（细粒度）

Q21 分布式事务有哪些解决方案？各自适用什么场景？ 重点 ▼
参考回答
  • ①2PC（两阶段提交）：强一致，性能差，阻塞风险。场景：XA 协议，多数据库操作
  • ②TCC（Try-Confirm-Cancel）：业务侵入高，无锁，高性能。场景：资金扣减、库存占用等
  • ③Saga：长事务，每步补偿。场景：订单流程等长链路
  • ④消息最终一致性：通过本地消息表 + MQ 保证最终一致。场景：跨服务异步操作
  • ⑤Seata：阿里开源，支持 AT/TCC/Saga/XA 模式。AT 模式通过 undo_log 实现自动回滚，对业务无侵入

实际项目推荐：高性能场景 → TCC；普通微服务 → Seata AT 模式；异步场景 → 消息最终一致性。

Q22 TransactionSynchronizationManager 是什么？如何在事务提交后执行操作？ 重点 ▼
参考回答

TransactionSynchronizationManager 是 Spring 事务的 ThreadLocal 存储中心，维护当前线程的事务状态（Connection、事务名、是否只读等）。

事务提交后执行操作的典型场景（如发送 MQ 消息，需确保数据库提交后才发）：

TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronizationAdapter() {
        @Override
        public void afterCommit() {
            // 事务成功提交后执行，如发 MQ 消息
            mqProducer.send(message);
        }
    }
);

或使用 Spring 4.2+ 的 @TransactionalEventListener(phase = AFTER_COMMIT) 注解更优雅地监听事务提交事件。

Q25 Spring MVC 全局异常处理有哪些方式？@ControllerAdvice 的原理？ 重点 ▼
参考回答

三种全局异常处理方式：

  • ①@ControllerAdvice + @ExceptionHandler（推荐）：统一处理所有 Controller 异常，可返回 JSON 或视图
  • ②HandlerExceptionResolver：实现该接口，注册为 Bean，更底层的异常处理机制
  • ③@ResponseStatus：在异常类上标注，简单场景的异常 → HTTP 状态码映射

@ControllerAdvice 原理：本质是一个特殊的 Component，被 ExceptionHandlerExceptionResolver 扫描并缓存 @ExceptionHandler 方法。当 Controller 抛出异常时，DispatcherServlet 调用 HandlerExceptionResolver 链依次处理，ExceptionHandlerExceptionResolver 找到最匹配的 @ExceptionHandler 方法执行。

Q26 @RequestBody 是如何将 JSON 转为 Java 对象的？HttpMessageConverter 原理？ 重点 ▼
参考回答

@RequestBody 由 RequestResponseBodyMethodProcessor 处理，流程：

  • ①读取请求头 Content-Type（如 application/json）
  • ②遍历注册的 HttpMessageConverter 列表，找到支持该 Content-Type 和目标类型的转换器
  • ③默认使用 MappingJackson2HttpMessageConverter，调用 Jackson ObjectMapper 反序列化
  • ④返回值序列化同理：读取 Accept 头 → 内容协商 → 找到合适 Converter → 写入响应体

自定义 Converter：实现 HttpMessageConverter 接口并注册到 WebMvcConfigurer#configureMessageConverters 即可。

Q30 Spring Boot 3.x 相比 2.x 有哪些重要变化？ 新题 ▼
参考回答
  • ①最低 Java 版本：要求 Java 17+（Spring 6 / Boot 3 基线）
  • ②Jakarta EE 9+：javax.* 包全面替换为 jakarta.*（javax.servlet → jakarta.servlet），迁移成本较高
  • ③AutoConfiguration 加载方式：spring.factories 中的 EnableAutoConfiguration 配置废弃，改用 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
  • ④原生镜像支持（GraalVM Native Image）：AOT 编译支持，大幅减少启动时间和内存占用
  • ⑤Actuator 优化：新增 /actuator/sbom 等端点，Prometheus 指标改为 OpenTelemetry
  • ⑥HTTP 接口声明：新增 @HttpExchange 替代 Feign，原生支持声明式 HTTP 客户端
