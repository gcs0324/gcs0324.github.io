Q2 #{ } 和 ${ } 的区别是什么？ 高频 ▾
考察点

MyBatis 最基础也最容易考的题。重点是 SQL 注入风险，能给出反例加分。

参考回答

#{} 是预编译参数占位符，最终生成 PreparedStatement 的 ?；${} 是字符串直接替换，把值原样拼进 SQL。

对比#{ }${ }
底层PreparedStatement ?字符串拼接
SQL 注入风险无（参数被转义）有（直接拼接，用户输入可注入）
类型处理由 TypeHandler 处理，字符串加引号原样替换，不加引号
常用场景绝大多数参数传入表名、列名、ORDER BY 列（不能用 ?）

反例（${ } 导致 SQL 注入）：

-- 用户传入 name = "' OR '1'='1"
SELECT * FROM user WHERE name = '${name}'
-- 实际执行：SELECT * FROM user WHERE name = '' OR '1'='1'  → 绕过验证

结论：只有表名/列名这种 PreparedStatement 不支持的场景才用 ${}，且必须做白名单校验，绝不能直接拼用户输入。

Q3 resultType 和 resultMap 的区别？什么时候用 resultMap？ 重点 ▾
考察点

结果映射是 MyBatis 核心功能，考察对两种方式的理解和使用边界。

参考回答

resultType 指定返回的 Java 类型，MyBatis 自动把列名映射到同名（驼峰转下划线时需开启 mapUnderscoreToCamelCase）字段。resultMap 是手动定义的映射规则，精确控制每一列对应哪个字段。

以下几种情况必须用 resultMap：

  • ▸ 列名和字段名不一致（且不符合下划线转驼峰规则）
  • ▸ 结果中有嵌套对象（association，多对一）
  • ▸ 结果中有集合（collection，一对多）
  • ▸ 需要标注主键列（<id>）用于对象去重

Q4 MyBatis 动态 SQL 的实现原理是什么？ 高频 ▾
考察点

考察对框架原理的理解深度，不只是"会用 if/where/foreach"。

参考回答

MyBatis 解析 XML 时把动态 SQL 标签转成节点树（SqlNode 接口的实现类），每个标签对应一个节点：IfSqlNode、ForeachSqlNode、ChooseSqlNode 等。

执行时，DynamicSqlSource 遍历节点树，用 OGNL 表达式引擎求值各节点条件，把满足条件的 SQL 片段拼接进 DynamicContext（一个 StringBuilder）。最终生成一个带 ? 占位符的静态 SQL 交给 PreparedStatement。

关键点：<where> 和 <set> 本质上是带裁剪逻辑的 <trim>——自动去掉多余的 AND/OR/逗号，避免拼接错误。

Q5 什么是 N+1 问题？MyBatis 怎么解决？ 重点 ▾
考察点

ORM 典型性能陷阱，考察对嵌套查询开销的认知和解法。

参考回答

N+1 问题是说：查询 N 条主记录，再为每条主记录查一次关联数据，发出 1+N 条 SQL，而不是 1 条 JOIN 查询。

例子：查 100 个用户（1条SQL），再为每个用户查订单（100条SQL）= 101 条 SQL。随着数据量增大，性能急剧下降。

MyBatis 有两种解法：

  • 方法 1 — 嵌套结果（推荐）：用 JOIN 一次性查出所有数据，通过 resultMap + collection/association 把扁平结果合并成嵌套对象。只发 1 条 SQL
  • 方法 2 — 延迟加载：在 collection/association 上设 fetchType="lazy"，只有真正访问关联字段时才触发查询。适合不一定需要关联数据的场景，但仍是 N+1 SQL，只是延迟了时机

首选方法 1，减少数据库往返。只有关联数据访问频率极低时才考虑方法 2。

Q6 association 和 collection 的区别？ 重点 ▾
考察点

考察对嵌套映射的掌握，理解多对一和一对多的不同处理方式。

参考回答

两者都用于嵌套结果映射，区别是关联关系的方向：

associationcollection
关系多对一 / 一对一一对多
Java 类型单个对象（javaType）集合（ofType 指定元素类型）
典型场景订单 → 用户（一个订单属于一个用户）用户 → 订单列表（一个用户有多个订单）

MyBatis 在合并一对多结果时，通过 <id> 标签的主键值判断是否同一条主记录，相同则把关联行追加到 collection，不同则创建新的主对象。所以一对多查询必须在 resultMap 里标注主键的 <id>，否则合并会出错。

Q7 Mapper 接口没有实现类，调用方法时是怎么执行的？ 高频 ▾
考察点

考察 JDK 动态代理的应用，以及 MyBatis 框架原理。能讲出 MapperProxy 的核心流程加分。

参考回答

MyBatis 用 JDK 动态代理为 Mapper 接口创建代理对象。调用 sqlSession.getMapper(UserMapper.class) 实际返回的是 MapperProxy 实例。

调用 userMapper.selectById(1L) 时的链路：

  • ① 进入 MapperProxy.invoke()，获取被调用的方法对象
  • ② 从缓存中取出对应的 MapperMethod（封装了 MappedStatement 的 id 和方法签名）
  • ③ 判断操作类型（SELECT / INSERT / UPDATE / DELETE），调用 SqlSession 对应方法
  • ④ SqlSession → Executor → StatementHandler → JDBC，走完整执行链路

关键：Mapper 接口的全限定名 + 方法名 组合成 statementId，和 XML 里的 namespace + id 对应，这就是接口和 XML 绑定的原理。

Q8 XML 文件和 Mapper 接口是怎么绑定的？ 重点 ▾
考察点

MyBatis 基础原理题，考察对 namespace 机制的理解。

参考回答

绑定规则很直接：XML 里的 namespace 必须等于接口的全限定名，XML 里每个 SQL 语句的 id 必须等于接口里对应的方法名。

<!-- namespace = 接口全限定名 -->
<mapper namespace="com.example.mapper.UserMapper">
  <!-- id = 方法名 -->
  <select id="selectById" resultType="User">
    SELECT * FROM user WHERE id = #{id}
  </select>
</mapper>

MyBatis 启动时扫描所有 Mapper XML，按 namespace.id 为 key 把每条 SQL 解析成 MappedStatement 对象存入 Configuration。运行时通过同样的 key 取出对应的 SQL 配置执行。

两个常见报错：namespace 写错（找不到接口）、id 和方法名不一致（调用方法时找不到 MappedStatement）。

参考回答
维度一级缓存二级缓存
作用域同一个 SqlSession同一个 Mapper namespace（跨 SqlSession）

Q10 二级缓存有什么问题？为什么实际项目几乎不开？ 重点 ▾
考察点

考察对缓存实际使用风险的认知，不止是会配置。能讲出脏读场景加分。

参考回答

二级缓存最大的问题是跨表操作的脏读：

假设 OrderMapper 里有一个 JOIN 查询，结果涉及 order 和 user 两张表，缓存存在 OrderMapper 的 namespace 下。当 UserMapper 更新了用户姓名，OrderMapper 的缓存不会失效，下次查订单时带出的仍是旧的用户姓名——这就是脏读。

MyBatis 的缓存失效只能感知到同一 namespace的 DML，无法感知其他 Mapper 的写入。

另外，分布式环境下默认的 PerpetualCache（单机内存）在多实例部署时还会出现各实例缓存不一致的问题。即使用 Redis / Ehcache 等外置缓存，和业务缓存双写的一致性维护也很麻烦。

结论：二级缓存适合数据极少更新、单机部署、查询量大的场景（如数据字典）。多数业务场景直接用 Redis 做应用层缓存，逻辑更清晰可控。

MyBatis 插件基于 JDK 动态代理实现拦截。MyBatis 初始化时，对每个注册的 Interceptor，把四大对象（Executor、StatementHandler、ParameterHandler、ResultSetHandler）包一层代理。方法调用时先进代理的 invoke()，再由插件决定是否调用 invocation.proceed() 继续原方法。

Q12 PageHelper 的分页原理是什么？有什么注意事项？ 高频 ▾
考察点

PageHelper 几乎每个项目都用，考察原理和坑点。

参考回答

PageHelper 是 MyBatis 插件，拦截 Executor.query()，在 SQL 执行前做以下操作：

  • ① PageHelper.startPage(1, 10) 把分页参数写入 ThreadLocal
  • ② 插件拦截到下一条 query，取出 ThreadLocal 里的分页参数
  • ③ 用 JSqlParser 把原 SQL 改写为 SELECT ... LIMIT 0, 10
  • ④ 另外执行一条 SELECT COUNT(*) FROM (...) 统计总条数
  • ⑤ 返回 Page 对象（继承 ArrayList），同时包含 total / pages 等分页信息

两个主要坑：

  • ▸ startPage() 之后必须紧接着是要分页的查询，中间不能穿插其他查询，否则分页参数会被错误消费
  • ▸ startPage() 后的查询如果在 try-finally 里未被执行（抛异常跳过），ThreadLocal 里的参数不会被清除，影响下一次请求（推荐用 PageHelper.clearPage() 清理）

Q14 SqlSession 是线程安全的吗？为什么？ 高频 ▾
考察点

高频基础题，考察并发意识。能说明 SqlSessionTemplate 怎么解决这个问题更好。

参考回答

SqlSession 不是线程安全的。它内部持有一个数据库 Connection 和一级缓存（HashMap），多线程共用同一个 SqlSession 会导致：

  • ▸ Connection 并发使用，读写交错，产生不可预知的 SQL 顺序
  • ▸ 一级缓存 HashMap 并发读写，产生 ConcurrentModificationException

因此原生使用时，SqlSession 应该在方法内创建、使用、关闭，不能作为成员变量。

Spring 通过 SqlSessionTemplate 解决了这个问题：它是线程安全的代理，每次方法调用时从 Spring 事务上下文取线程绑定的 SqlSession，不跨线程共享。这也是为什么在 Spring 里可以把 Mapper 注入为 Bean 单例——实际上是注入了 SqlSessionTemplate 代理，而不是真正的 SqlSession。

Q15 MyBatis 延迟加载的原理是什么？ 重点 ▾
考察点

考察对动态代理在延迟加载中的应用，能说出 CGLIB 代理加分。

参考回答

延迟加载（Lazy Loading）是指关联对象不在主查询时加载，只有当真正访问关联属性时才执行额外的 SQL。

MyBatis 的实现原理：用 CGLIB（或 Javassist）动态代理生成结果对象的子类，在代理类里记录哪些关联属性还未加载。当外部代码调用 order.getUser() 时，代理拦截到 getter 调用，判断 user 字段未加载，触发一次额外 SQL 查询，再把结果填充到字段并返回。

需要注意：

  • ▸ 延迟加载要求 SqlSession 在使用关联对象时仍然处于打开状态，Spring 的"延迟加载 + 事务外访问"容易触发 org.apache.ibatis.executor.ExecutorException: Executor was closed
  • ▸ 全局配置 lazyLoadingEnabled=true 或在 association/collection 里单独设 fetchType="lazy"

Q16 Spring 中 MyBatis 的事务是怎么管理的？和 @Transactional 怎么配合？ 重点 ▾
考察点

Spring 事务和 MyBatis 整合是面试必考，考察对 SqlSessionTemplate 和 DataSourceTransactionManager 协作的理解。

参考回答

Spring + MyBatis 的事务管理由 DataSourceTransactionManager 负责，它和 MyBatis 通过 Connection 绑定协作：

  • ① @Transactional 方法被 AOP 拦截，Spring 从连接池获取 Connection，设置 autoCommit=false，绑定到当前线程（ThreadLocal）
  • ② 方法内所有 MyBatis 操作通过 SqlSessionUtils.getSqlSession() 取到同一个 Connection（因为 Spring 事务把 Connection 绑定在线程上），共享同一个事务
  • ③ 方法正常返回 → Spring 调用 connection.commit()；抛出异常 → connection.rollback()

关键结论：同一 @Transactional 方法内的所有 Mapper 操作共用一个 SqlSession 和 Connection，保证了事务原子性；没有事务时每次 Mapper 调用独立 SqlSession，互不干扰。

Q17 LambdaQueryWrapper 相比 QueryWrapper 有什么优势？ 高频 ▾

Q18 MP 逻辑删除是怎么实现的？有什么坑？ 高频 ▾
考察点

考察对 MP 逻辑删除原理和唯一索引冲突坑的认知。

参考回答

MP 逻辑删除通过 @TableLogic 注解实现。原理是 MP 在全局 SQL 拦截器里：

  • ▸ 删除操作改写为 UPDATE table SET deleted=1 WHERE id=?
  • ▸ 查询 / 更新操作自动追加 AND deleted=0 条件，过滤已删除数据

主要坑：

  • 坑 1 唯一索引冲突：手机号/邮箱字段有唯一索引，逻辑删除后值还在，新用户注册同手机号会报唯一冲突。解法：改成联合唯一索引 (phone, deleted)，或删除时把 phone 改写成随机字符串
  • 坑 2 原生 XML SQL 不生效：自己写的 XML Mapper 查询不会自动追加 deleted=0，需要手动加
  • 坑 3 统计类 SQL 遗漏：COUNT(*) 等聚合 SQL 如果走 XML 写，也要记得加 deleted=0

Q19 MP 乐观锁的 CAS 流程是什么？失败了怎么处理？ 高频 ▾
考察点

考察乐观锁原理和业务处理方式。能对比悲观锁的适用场景加分。

参考回答

MP 乐观锁通过 @Version 注解实现 CAS（Compare And Swap）。完整流程：

  • ① 查询：SELECT id, name, version FROM user WHERE id=1 → 返回 version=3
  • ② 修改业务逻辑
  • ③ 更新：UPDATE user SET name=?, version=4 WHERE id=1 AND version=3
  • ④ 若影响行数为 0，说明其他线程已修改（version 已不是 3），本次更新失败

失败处理方式（按业务场景选）：

  • ▸ 重新查询最新数据 + 重试（适合冲突概率低、重试代价小的场景）
  • ▸ 抛出业务异常 + 提示用户刷新重试（适合后台管理系统）
  • ▸ 放弃乐观锁改用悲观锁（适合高并发冲突率高的场景，如秒杀扣库存）

Q20 MP 分页插件是怎么对 COUNT 做优化的？ 重点 ▾
考察点

考察对分页插件底层优化策略的了解，适合有性能调优意识的面试官。

参考回答

分页查询通常需要两条 SQL：一条带 LIMIT 的主查询 + 一条 COUNT 查询（统计总条数）。MP 对 COUNT 做了以下优化：

  • 优化 1 — 去除 ORDER BY：COUNT 不需要排序，MP 自动去掉 ORDER BY 子句，减少数据库排序开销
  • 优化 2 — 去除多余列：COUNT 只需要行数，主查询里 SELECT a, b, c 的列可以简化为 SELECT 1 或 COUNT(*)
  • 优化 3 — GROUP BY 包装：原 SQL 带 GROUP BY 时，直接改写 COUNT 会语义错误，MP 会包一层 SELECT COUNT(*) FROM (原SQL) AS tmp
  • 优化 4 — 关闭 COUNT：new Page<>(1, 10, false) 第三个参数传 false，完全不执行 COUNT 查询，适合不需要总页数的下拉加载场景

Q21 MP 自动填充的时机和原理是什么？什么情况下不生效？ 重点 ▾
考察点

自动填充是高频实际开发场景，考察原理和生效边界。

参考回答

MP 自动填充依赖 MetaObjectHandler，在 BaseMapper.insert() 和 BaseMapper.update() 执行前，MP 调用 Handler 的 insertFill / updateFill 方法，通过反射把值设置到对应字段。

触发条件：字段上有 @TableField(fill = FieldFill.INSERT / INSERT_UPDATE / UPDATE) 注解，且通过 MP 的方法操作（不是原生 MyBatis XML）。

不生效的情况：

  • ▸ 用 UpdateWrapper / LambdaUpdateWrapper 的 .set("update_time", ...) 直接设 SET 字段，不走实体字段填充
  • ▸ XML 里写的 <insert> / <update>，不走 MP 插件体系
  • ▸ 字段已有非 null 值时，strictInsertFill 不会覆盖（用 setFieldValByName 可强制覆盖）

Q22 MP 多租户是怎么实现 SQL 隔离的？超级管理员怎么查全量数据？ 重点 ▾
考察点

考察对多租户实现方案的掌握，能讲出"管理员绕过"设计加分。

参考回答

MP 多租户通过 TenantLineInnerInterceptor 实现，拦截所有 SQL，在 WHERE 子句里自动追加 AND tenant_id = ?（由 getTenantId() 提供当前租户 ID）。不需要每条 SQL 手写租户条件。

超级管理员查全量数据：在 getTenantId() 里判断当前登录用户角色，是超级管理员时返回 null，MP 会跳过追加条件。

@Override
public Expression getTenantId() {
    User user = SecurityContext.getCurrentUser();
    if (user.isAdmin()) return null;  // 管理员不追加 tenant_id 条件
    return new LongValue(user.getTenantId());
}

ignoreTable：系统字典、配置表等不需要租户隔离的表，在 ignoreTable(tableName) 里返回 true，MP 跳过该表的 tenant_id 追加。

我的判断标准是两个维度：SQL 复杂度和团队背景。

场景选型建议理由
复杂查询多（报表、多表 JOIN、分页筛选）MyBatis / MPSQL 可控，便于 DBA 介入，慢查询好定位
业务以简单 CRUD 为主，领域模型清晰JPA / Hibernate减少重复代码，Schema 变更后代码自动适应

Q24 大批量数据插入如何优化？saveBatch 为什么不够快？ 高频 ▾
考察点

性能优化实战题，考察对 JDBC 批量插入机制的深度理解。能说出 rewriteBatchedStatements 加分。

参考回答

saveBatch() 的默认实现是循环单条 INSERT，每条 SQL 单独发送到数据库，网络往返 N 次，性能差。优化分三个层次：

  • 层次 1 — 批量值 INSERT：用 MyBatis XML 的 <foreach> 拼接 INSERT INTO user VALUES (?,?),(?,?),... 一条 SQL 多行，减少网络往返。注意每批控制在 500~1000 条（避免超过 max_allowed_packet）
  • 层次 2 — JDBC Batch + rewriteBatchedStatements：JDBC URL 加 ?rewriteBatchedStatements=true，再用 BatchExecutor 或 JDBC addBatch() / executeBatch()。MySQL 驱动会把多条 PreparedStatement 改写成一条多值 INSERT，效果同层次 1 但更通用
  • 层次 3 — LOAD DATA INFILE：极大数据量（百万级）直接用 MySQL LOAD DATA INFILE，跳过 SQL 解析，是最快方式，但需要文件权限且不支持事务回滚

日常推荐：foreach 批量 INSERT 每批 500 条 + 开启 rewriteBatchedStatements=true，覆盖 99% 的场景需求。
