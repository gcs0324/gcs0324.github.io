01发送全流程
Producer 发送链路总览

调用 producer.send(record) 后，消息并非直接发往 Broker，而是经过一条完整的本地处理链路：

🟢 业务线程（调用 send() 的线程）

→

→

→

⇄
buffer.memory
32 MB 限额

←

业务线程只负责把消息放入缓冲区即返回；Sender 线程异步批量发送，两者通过 RecordAccumulator 解耦，互不阻塞。

各环节详解
1
拦截器链（ProducerInterceptor）
按配置顺序依次执行 onSend(record)，可修改消息内容或做埋点统计。发送完成（成功或失败）后触发 onAcknowledgement()。拦截器链中任意一个抛出异常不会中断后续拦截器的执行。
2
序列化器（Serializer）
将 Key 和 Value 从 Java 对象转换为字节数组。内置 StringSerializer、ByteArraySerializer；业务常用 JsonSerializer（spring-kafka 提供）或 Avro（配合 Schema Registry）。Key 和 Value 可分别配置不同的序列化器。
3
分区器（Partitioner）
决定消息写入哪个 Partition。详见下一节。分区确定后，消息被路由到 RecordAccumulator 中对应 Partition 的 Deque（双端队列）。
4
RecordAccumulator — 消息缓冲区
每个 Partition 对应一个 Deque<ProducerBatch>。新消息被追加到队尾最新的 ProducerBatch；若当前 Batch 已满（超过 batch.size）或等待时间超过 linger.ms，Sender 线程将其取出发送。缓冲区总大小受 buffer.memory（默认 32 MB）限制。
5
Sender 线程 — 后台 I/O 线程
独立于业务线程的守护线程，不断轮询 RecordAccumulator，将就绪的 ProducerBatch 按目标 Broker 归组，封装为 ProduceRequest 交给 NetworkClient 发送。同时负责处理响应、触发重试和回调。
6
NetworkClient — NIO 网络层
基于 Java NIO Selector 管理与各 Broker 的 TCP 长连接池。维护 in-flight 请求队列（max.in.flight.requests.per.connection 控制每个连接的最大未响应请求数，默认 5）。收到 Broker 响应后触发 Sender 处理。
三种发送模式
模式写法特点适用场景
发后即忘
Fire-and-Forget		 producer.send(record) 不关心结果，最高吞吐，可能丢消息 日志采集、可丢弃的统计埋点
异步发送
Async		 producer.send(record, callback) Callback 在 Sender 线程回调，不阻塞业务线程；可感知成功/失败 绝大多数业务场景推荐写法
同步发送
Sync		 producer.send(record).get() 阻塞等待 Broker 确认，延迟最高，吞吐最低 强一致要求的支付/核心交易 
// 异步发送（推荐）
producer.send(record, (metadata, exception) -> {
    if (exception != null) {
        log.error("Send failed: topic={} partition={}", metadata.topic(), metadata.partition(), exception);
    } else {
        log.info("Send ok: offset={}", metadata.offset());
    }
});

// 同步发送（强一致）
try {
    RecordMetadata meta = producer.send(record).get(3, TimeUnit.SECONDS);
    log.info("Delivered to partition={} offset={}", meta.partition(), meta.offset());
} catch (TimeoutException e) {
    // 超时，可重试
} catch (ExecutionException e) {
    // 发送失败，处理异常
}
02分区策略
内置分区策略
场景策略算法特点
指定 Partition 直接写入 new ProducerRecord(topic, partition, key, value) 最高优先级，绕过分区器
有 Key，未指定 Partition Key 哈希取模 murmur2(keyBytes) % numPartitions 相同 Key 必落同一 Partition，保证局部有序
无 Key，未指定 Partition
（Kafka 2.4+）		 粘性分区
Sticky Partitioner		 同一批次内所有消息发往同一 Partition，批次发完后随机换一个 凑满 batch 后再换分区，减少小批次，显著提升吞吐
无 Key，未指定 Partition
（Kafka 2.3 及以前）		 轮询
Round Robin		 每条消息依次轮询到下一个 Partition 分区均衡但每条消息单独成批，效率低
⚠ 扩 Partition 后 Key 路由失效：若后期增加 Partition 数量，murmur2(key) % newNumPartitions 的结果会改变，导致同一 Key 的历史消息与新消息落到不同 Partition，打破顺序性。业务上需提前规划好 Partition 数量，或在应用层处理路由。
自定义分区器

实现 Partitioner 接口，按业务规则控制路由，例如按 VIP 等级优先写入低序号 Partition（消费者优先消费）：

public class VipFirstPartitioner implements Partitioner {

    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        int numPartitions = cluster.partitionCountForTopic(topic);
        // VIP 用户写 partition 0，普通用户轮询其余分区
        if (key != null && key.toString().startsWith("VIP_")) {
            return 0;
        }
        // murmur2 哈希兜底，保证其余 Key 均匀分布
        return (Utils.murmur2(keyBytes) & Integer.MAX_VALUE) % (numPartitions - 1) + 1;
    }

    @Override public void close() {}
    @Override public void configure(Map<String, ?> configs) {}
}

// 配置使用
props.put(ProducerConfig.PARTITIONER_CLASS_CONFIG, VipFirstPartitioner.class.getName());
03acks 与可靠性配置
acks — 消息确认级别

acks 控制 Producer 认为消息发送成功的条件，是可靠性与吞吐量权衡的核心参数：

acks = 0
○ Leader 写入
○ Follower 1 同步
○ Follower 2 同步
发完即认为成功，不等任何确认
丢消息风险最高 / 吞吐最高
acks = 1
✓ Leader 写入
○ Follower 1 同步
○ Follower 2 同步
Leader 落盘后返回确认
Leader 宕机时 Follower 未同步则丢
acks = all（-1）
✓ Leader 写入
✓ Follower 1 同步
✓ Follower 2 同步
ISR 全部写入后返回确认
最可靠 / 需配合 min.insync.replicas
值含义丢消息风险吞吐适用场景
acks=0 不等待任何确认，发完即认为成功 最高（Broker 未收到就可能丢） 最高 日志采集、可接受丢失的监控埋点
acks=1 Leader 写入本地日志后确认 中（Leader 写入后宕机，Follower 未同步则丢） 高 允许极少量丢失的一般业务
acks=all
（-1）		 ISR 中所有副本写入后确认 最低（需配合 min.insync.replicas） 低 订单、支付、核心业务
⚠ acks=1 的隐患：Leader 收到消息并返回确认后立刻宕机，而此时 Follower 还未同步。新选出的 Leader（原 Follower）没有这条消息，Producer 也不会重发（已收到确认），消息就此丢失。
重试参数三件套

网络抖动、Leader 切换等临时错误可通过重试恢复，三个参数协同控制重试行为：

参数默认值作用
retries Integer.MAX_VALUE 最大重试次数。实际由 delivery.timeout.ms 兜底，超时后不再重试
retry.backoff.ms 100 ms 两次重试之间的等待时间，避免立即重试加剧 Broker 压力
delivery.timeout.ms 120,000 ms（2 min） 消息从 send() 调用到最终确认（或放弃）的最大总时间，含重试时间。超过后触发回调并抛出 TimeoutException
⚠ 重试与消息顺序：当 max.in.flight.requests.per.connection > 1（默认 5）时，若批次 A 发送失败触发重试，批次 B 已成功写入，A 重试后将排在 B 之后，造成乱序。
解决方案：开启幂等（enable.idempotence=true），框架会自动将 in-flight 限制为 1，同时提供去重保证。
04幂等 Producer
为什么需要幂等 — 重试导致的重复写入

网络超时时，Broker 可能已写入消息但 ACK 丢失，Producer 误以为失败进行重试，导致同一条消息被写入两次。幂等 Producer 解决这个问题。

// 开启幂等，一行配置
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
// 开启幂等后框架自动设置：
// acks = all
// max.in.flight.requests.per.connection = 5（幂等下允许最多 5 个 in-flight）
// retries = Integer.MAX_VALUE
幂等实现原理 — PID + Sequence Number

Broker 端通过两个标识符识别重复消息并丢弃：

标识全称生命周期作用
PID Producer ID 每次 Producer 实例启动时由 Broker 分配，重启后重新分配 唯一标识一个 Producer 会话
Seq Sequence Number 每个 <PID, Partition> 维护独立的单调递增序列号，从 0 开始 标识同一 Producer 会话内的消息顺序

Broker 对每个 <PID, Partition> 记录最近写入的 Seq。收到消息时：

✓
Seq == lastSeq + 1 → 正常写入
符合预期，接受消息并更新 lastSeq。
✓
Seq ≤ lastSeq → 重复，直接丢弃
Broker 已写过此消息，判定为重试重复，丢弃并返回成功（Producer 认为正常）。
✗
Seq > lastSeq + 1 → 乱序，拒绝
消息乱序到达，返回 OutOfOrderSequenceException，Producer 需重建连接。
⚠ 幂等的局限性：
· 仅保证单个 Partition 内的幂等（PID + Partition 维度）
· 仅保证单次会话（单次 Producer 实例生命周期）内幂等，Producer 重启后 PID 改变，Broker 无法识别为同一 Producer
· 跨多个 Partition 的原子写入需使用事务
05事务 Producer — Exactly-Once
什么是 Kafka 事务

Kafka 事务（Kafka 0.11+）提供跨多个 Partition、跨多个 Topic 的原子写入能力：要么全部写入成功，要么全部回滚，消费者只能看到已提交的事务消息（需设置 isolation.level=read_committed）。

典型场景：Consume-Transform-Produce 模式（从 Topic A 消费 → 处理 → 写入 Topic B + 提交 Offset），三个动作要么全成功要么全回滚，实现 Exactly-Once 语义。

事务 API 完整用法
// 1. 配置 transactional.id（全局唯一，跨 Producer 实例标识同一业务逻辑）
props.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "order-producer-001");
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true); // 事务依赖幂等，自动开启

KafkaProducer<String, String> producer = new KafkaProducer<>(props);

// 2. 初始化事务（仅调用一次）
producer.initTransactions();

try {
    // 3. 开启事务
    producer.beginTransaction();

    // 4. 正常发送消息（可跨多个 Topic / Partition）
    producer.send(new ProducerRecord<>("orders", orderId, orderJson));
    producer.send(new ProducerRecord<>("inventory", itemId, decreaseJson));

    // 5. 若结合消费，原子提交 Offset（代替 consumer.commitSync()）
    producer.sendOffsetsToTransaction(offsetsMap, consumerGroupMetadata);

    // 6. 提交事务
    producer.commitTransaction();

} catch (ProducerFencedException | OutOfOrderSequenceException e) {
    // 不可恢复异常，直接关闭 Producer
    producer.close();
} catch (KafkaException e) {
    // 可恢复异常，回滚事务后可继续
    producer.abortTransaction();
}
事务实现原理 — 事务协调器

Kafka 事务由事务协调器（Transaction Coordinator）管理，每个 Broker 都可充当协调器角色，由 transactional.id 哈希到 __transaction_state Topic 的某个 Partition 的 Leader 担任。

1
initTransactions() — 获取 PID 并注册事务
Producer 向 Transaction Coordinator 注册 transactional.id，Coordinator 分配 PID（事务 PID，跨重启保持）并返回 epoch 值，使旧版 Producer 失效（Fencing）。
2
beginTransaction() — 本地标记
仅在 Producer 本地标记事务开始，Coordinator 此时不感知。
3
send() — 写入消息并注册参与 Partition
每次向新的 Partition 发消息时，Producer 通知 Coordinator 将该 Partition 加入事务参与列表（写入 __transaction_state）。消息本身带有事务标记，消费者持有 read_committed 时跳过未提交消息。
4
commitTransaction() — 两阶段提交
Phase 1：Producer 通知 Coordinator 准备提交，Coordinator 将状态写入 __transaction_state（PREPARE_COMMIT）。
Phase 2：Coordinator 向所有参与 Partition 写入 Transaction Marker（提交标记），通知 Broker 此事务已提交，最后将状态更新为 COMPLETE_COMMIT。
5
abortTransaction() — 回滚
写入 PREPARE_ABORT → 向各 Partition 写入 Abort Marker → 更新为 COMPLETE_ABORT。消费者收到 Abort Marker 后丢弃该事务内的所有消息。
幂等 vs 事务 vs Exactly-Once 对比
能力幂等 Producer事务 Producer
去重范围单 Partition、单 Session跨多 Partition、跨 Session（靠 transactional.id）
原子写入✗ 不支持✓ 多 Partition 原子提交或回滚
消费者隔离无隔离，消息即时可见需 isolation.level=read_committed 才可见已提交消息
性能开销小（仅序列号校验）大（两阶段提交，延迟增加）
Exactly-Once单 Partition 内可实现配合 sendOffsetsToTransaction 实现端到端 Exactly-Once
配置enable.idempotence=truetransactional.id=xxx（自动开启幂等）
实践建议：绝大多数业务用 acks=all + enable.idempotence=true + 业务层幂等 即可满足需求，性能损耗小。只有 Consume-Transform-Produce 模式下需要端到端 Exactly-Once 时才引入事务，权衡好延迟代价。
