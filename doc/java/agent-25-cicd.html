01Prompt 作为可发布制品
Prompt 需要跟代码一样被管理

传统应用的发布制品是编译后的代码，Agent 系统多了一类同样重要、却常被当成"配置随便改"的制品——Prompt（提示词）。改一版 System Prompt 对 Agent 行为的影响，不亚于改一版核心业务代码，理应纳入同样严格的版本管理和发布流程。

  • 版本化：Prompt 存入代码仓库，每次修改走 Code Review，而不是在某个后台配置页面直接改了就生效
  • 与代码解耦但同步发布：Prompt 可以独立于业务代码存放（方便非工程角色参与编写），但发布时要和对应的 Agent 逻辑版本绑定，避免"代码是新的、Prompt 是旧的"这类不一致
  • 变更可追溯：每次 Prompt 变更都要能追溯到是谁改的、为什么改、对应哪次评估结果，这是排查线上问题的关键线索
常见反模式：把 Prompt 存在数据库里，运营或产品同学在后台直接改了立即生效，不经过评估和 Review。这种"看起来灵活"的做法，实际上是把生产环境变成了没有测试保护的实验场。
02评估门禁接入流水线
发布前自动跑评估集

Agent 的 CI/CD 流水线和传统服务的核心区别在于多了一道评估门禁（Eval Gate）——单元测试和集成测试只能验证代码逻辑没错，验证不了"模型的回答是否还是那么准确"，这一层必须靠 评估体系 补上。

①
代码 / Prompt 变更提交
开发者提交 Prompt 或 Agent 逻辑的变更，触发 CI 流水线
②
单元测试 + 集成测试
跑传统测试，验证工具调用逻辑、参数解析等确定性代码没有回归
③
评估集回归
跑离线评估集，对比本次变更后的评估分数与基线分数，参见 评估体系
④
门禁判断
评估分数低于基线一定容忍度时，流水线自动拦截，不允许合并/发布
人工审批（可选）
高风险变更（涉及安全 Guardrails、支付类工具）额外要求人工审批才能发布
最佳实践：评估门禁的阈值不是一成不变的——初期可以设得宽松一些防止评估集不完善导致误拦截，随着评估集覆盖度提高，逐步收紧阈值。
03灰度发布
先给一小部分流量验证

即使评估集回归通过，也不能完全代表线上真实流量的表现——评估集覆盖不到的长尾场景，只有在真实流量中才会暴露。灰度发布（Canary Release）让新版本先承接一小部分流量，观察在线指标正常后再逐步放量。

阶段流量比例观察指标
内测0%，仅内部测试账号核心功能是否正常，人工抽查回答质量
灰度1%-10%任务完成率、用户满意度、人工介入率、成本，与旧版本对比
放量10%-100% 逐步提升持续监控在线指标，异常时立即暂停放量
A/B 对比：灰度阶段最好让新旧版本同时承接流量做 A/B 对比，而不是只看新版本自己的绝对指标——很多问题只有跟旧版本对比才能看出是退化还是正常波动。
04版本回滚
出问题时能快速切回旧版本
  • Prompt 版本与代码版本同时可回滚：回滚机制要同时覆盖 Prompt 和 Agent 逻辑代码，只回滚一边会造成新的不一致
  • 回滚要快：理想情况下应该是配置切换级别的操作（切换到上一个已知稳定的版本号），而不需要重新走一遍完整发布流程
  • 保留多个历史版本：至少保留最近几个稳定版本可供快速回滚，而不只是"上一个版本"
血泪教训：没有快速回滚能力的 Agent 系统，一旦线上出现严重问题（比如新 Prompt 导致大量幻觉或误触发高危工具），修复时间可能长达数小时。回滚速度应该被当成和成本控制中的预算熔断同等优先级的上线前必备能力。
05部署架构
Agent 服务的部署形态
  • 无状态化部署：Agent 服务本身尽量做成无状态的，会话状态存在外部存储（Redis / 数据库），这样才能水平扩容和随意重启
  • 与模型服务解耦：Agent 编排逻辑和底层 LLM 调用（无论是调用外部 API 还是自建推理服务）分层部署，模型可以独立升级、切换供应商，不影响 Agent 业务逻辑
  • 多环境隔离：开发 / 预发 / 生产环境的 Prompt 版本、工具权限配置要严格隔离，防止预发环境的测试 Prompt 意外影响生产
  • 配置中心管理：模型参数（温度、最大 Token 数）、工具开关、限流阈值等运行时配置放到配置中心，支持动态调整而不需要重新部署
06Java 实现
CI 流水线中的评估门禁骨架

结合评估体系的 AgentEvaluator，在 CI 阶段自动跑评估集并做门禁判断，接入 GitHub Actions / Jenkins 等流水线工具。

// 1. CI 阶段调用的评估门禁入口
public class EvalGateRunner {

    private final AgentEvaluator evaluator;
    private static final double BASELINE_SCORE = 0.85;
    private static final double TOLERANCE = 0.02;

    public static void main(String[] args) {
        EvalReport report = evaluator.evaluate(loadEvalCases("eval-cases/regression.json"));

        System.out.println("本次评估分数：" + report.avgScore());
        System.out.println("基线分数：" + BASELINE_SCORE);

        if (report.avgScore() < BASELINE_SCORE - TOLERANCE) {
            System.err.println("评估分数低于基线，拦截本次发布");
            System.exit(1);   // 非零退出码，CI 流水线据此判定失败
        }
        // 分数达标：写入本次结果作为下一次对比的基线候选
        baselineRepository.save(currentVersion(), report.avgScore());
    }
}

// 2. 灰度发布中的版本路由（简化示例）
public class AgentVersionRouter {

    private final double canaryPercentage; // 灰度流量比例，来自配置中心，可动态调整

    public AgentRuntime resolve(String userId) {
        boolean inCanary = hashUserId(userId) % 100 < canaryPercentage * 100;
        return inCanary ? agentRegistry.get("canary") : agentRegistry.get("stable");
    }
}
  • 非零退出码触发流水线失败：这是评估门禁接入通用 CI 工具（GitHub Actions、Jenkins、GitLab CI）最简单直接的方式，不需要为每个 CI 平台单独定制
  • 灰度比例从配置中心读取：不写死在代码里，运维可以在不发版的情况下调整灰度比例，快速放量或紧急收缩
  • 按用户 ID 哈希分流：保证同一用户在灰度期间稳定命中同一版本，避免同一用户体验反复横跳，便于问题排查
最佳实践：把评估门禁、灰度发布、快速回滚这三件事在系统设计的第一个版本就规划进去，而不是等第一次线上事故之后才补——Agent 行为的不确定性决定了这套发布护栏比传统服务更不可或缺。
