01 运行时数据区
整体结构

JVM 规范将运行时内存划分为 5 个区域，其中 3 个线程私有、2 个线程共享。

区域 线程 OOM？ 核心职责 / 关键点
程序计数器 私有 无 记录当前线程执行字节码的行号；执行 Native 方法时值为 undefined
JVM 虚拟机栈 私有 StackOverflow / OOM 每个方法对应一个栈帧，栈帧包含：局部变量表、操作数栈、动态链接、方法返回地址
本地方法栈 私有 StackOverflow / OOM 为 Native 方法服务；HotSpot 将虚拟机栈与本地方法栈合二为一
堆 共享 Java heap space 几乎所有对象实例存放于此（逃逸分析后少数在栈上分配）；分代：新生代 + 老年代
方法区 / 元空间 共享 Metaspace OOM 存储类结构、常量池、静态变量、JIT 代码；JDK8 用 Metaspace（本地内存）替代 PermGen
直接内存 共享 Direct buffer memory NIO ByteBuffer.allocateDirect() 分配；不受 -Xmx 管辖，默认受物理内存限制
栈帧结构详解
  • ①局部变量表 — 存放方法参数和局部变量，以 Slot（槽位）为单位，long/double 占 2 个 Slot；this 引用在实例方法 Slot[0]
  • ②操作数栈 — JVM 的"计算草稿纸"，字节码指令 push/pop 操作数进行运算
  • ③动态链接 — 指向运行时常量池中该栈帧所属方法的引用，用于支持方法调用的动态分派
  • ④方法返回地址 — 正常返回时恢复上层调用者 PC；异常退出时通过异常表确定处理入口
02 对象创建过程
五步创建流程（new 指令触发）
①
类加载检查
检查 new 指令的参数能否在常量池中找到类的符号引用，且该类已完成加载、解析、初始化。否则先触发类加载流程。
②
内存分配
在堆上为对象分配内存，大小在类加载完成后即可确定。两种分配方式：
• 指针碰撞（Bump-the-Pointer）— 堆内存规整时（Serial/ParNew + 整理型收集器），维护一个分界指针，向空闲区移动对象大小的距离
• 空闲列表（Free List）— 堆内存不规整时（CMS 使用标记-清除），维护可用内存块列表
并发安全：使用 TLAB（Thread-Local Allocation Buffer）— 每个线程在 Eden 预分配一块私有缓冲，避免 CAS 竞争；TLAB 用尽才加锁扩展
③
零值初始化
将分配的内存空间（不含对象头）初始化为零值：int=0、boolean=false、reference=null。这保证了字段不赋初始值也能直接使用。
④
设置对象头
设置 Mark Word（哈希码、GC 分代年龄、锁标志位）和 Klass Pointer（指向类元数据）。如果是数组对象还要记录数组长度。
⑤
执行 <init> 方法
按照程序员意愿初始化对象（构造方法体）。此时对象才算真正"初始化完毕"。注意与 JVM 的零值初始化（步骤③）区分。
03 对象内存布局
三部分组成

一个 Java 对象在堆中由三部分组成：对象头 + 实例数据 + 对齐填充。

Mark Word 状态变化（64位 JVM）
锁状态 存储内容 锁标志位
无锁 对象 hashCode（31位）+ GC分代年龄（4位）+ 是否偏向锁（1位=0） 01
偏向锁 线程 ID（54位）+ Epoch（2位）+ GC分代年龄（4位）+ 是否偏向（1位=1） 01
轻量级锁 指向栈中锁记录的指针（62位） 00
重量级锁 指向 Monitor 对象的指针（62位） 10
GC 标记 空（GC 使用） 11
面试考点：hashCode 和偏向锁不能共存 — 一旦对象调用了 System.identityHashCode()，偏向锁会被撤销，因为 Mark Word 没有空间同时存储 threadId 和 hashCode。
04 对象访问方式
两种定位方式

Java 程序通过栈上的 reference 引用找到堆中的对象。主流实现有两种：

句柄池（Handle Pool）
✓ GC 移动对象后只需更新句柄内的指针，reference 本身稳定
✗ 每次访问需两次指针追踪，速度较慢
✗ 需额外堆空间存句柄池
直接指针（HotSpot 默认）
✓ 减少一次指针间接跳转，访问对象字段更快
✗ GC 移动对象后需更新所有持有该对象引用的地方
05 OOM 类型与排查
引用类型速查

GC 回收对象时会考虑引用类型：

强引用
Object obj = new Object()
只要引用存在，永不被回收
软引用 SoftRef
内存不足时才回收，适合做缓存（图片缓存）
弱引用 WeakRef
下次 GC 时必定回收，ThreadLocal 的 Entry key 即为弱引用
虚引用 PhantomRef
不影响生命周期，仅用于对象回收时收到通知（DirectByteBuffer 清理）
java.lang.OutOfMemoryError: Java heap space
原因：堆内存不足，最常见的 OOM。可能是内存泄漏（对象无法被 GC）或堆设置过小。
排查：①先看 GC 日志确认是否频繁 Full GC 后依然 OOM ②用 jmap 导出 dump 文件 ③用 MAT（Eclipse Memory Analyzer）分析大对象、引用链
# 发生 OOM 时自动 dump -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/dump.hprof # 手动 dump jmap -dump:format=b,file=/tmp/dump.hprof <pid> # 查看对象直方图（不 dump，更快） jmap -histo <pid> | head -30
java.lang.OutOfMemoryError: Metaspace
原因：动态代理（CGLIB / ASM）不停生成新类，类元数据撑爆元空间。常见于 Spring AOP、Groovy 脚本动态加载场景。
排查：监控 MetaspaceSize、检查 ClassLoader 数量是否持续增长
# 设置元空间上限（默认无限制，会吃光本地内存） -XX:MaxMetaspaceSize=256m # 查看元空间使用 jcmd <pid> VM.metaspace
java.lang.StackOverflowError
原因：递归调用无终止条件，或单个栈帧的局部变量表过大，超过了 -Xss 设置的栈容量。
排查：查看异常堆栈，定位重复调用的方法链；适当增大 -Xss（默认 512k~1m）
-Xss1m # 设置每个线程栈大小为 1MB
java.lang.OutOfMemoryError: Direct buffer memory
原因：NIO 的 DirectByteBuffer 分配的堆外内存耗尽。Netty、Kafka Client 重度使用直接内存。
排查：通过 -XX:MaxDirectMemorySize 限制直接内存上限；检查 DirectByteBuffer 是否及时 release
-XX:MaxDirectMemorySize=512m
java.lang.OutOfMemoryError: GC overhead limit exceeded
原因：JVM 花费超过 98% 的时间做 GC，但每次 GC 后只释放不到 2% 的内存，循环往复。说明系统已无法正常运行。
排查：本质是堆 OOM 的前兆，处理方式与 Java heap space 相同 — 分析对象存活情况，找内存泄漏点
# 若想关闭该检查（不推荐，会掩盖问题） -XX:-UseGCOverheadLimit
内存泄漏排查工具速查
工具命令 / 用法适用场景
jmap jmap -histo <pid>
jmap -dump:format=b,file=x.hprof <pid>		 快速看对象直方图；导出 heap dump 供 MAT 分析
MAT 加载 .hprof 文件，查看 Dominator Tree、Leak Suspects 深度分析大对象、引用链，找内存泄漏根因
jstat jstat -gcutil <pid> 1000 实时监控各区 GC 频率和使用率，判断内存是否持续上涨
Arthas dashboard、memory 在线诊断，无需重启，查看实时内存分布
