01从单机事务到分布式事务
ACID 在分布式下为何失效

单库事务靠 MySQL 的 redo log + undo log + 锁，就能轻松做到 ACID。一旦跨库或跨服务，事情立刻变难 —— 因为参与方各有自己的事务日志，互相看不到，谁都不能单独决定"提交还是回滚"。

  • A原子性破裂：A 库提交成功、B 库网络超时不知道结果，事务无法整体回滚
  • C一致性破裂：扣了用户余额、加库存失败，两库数据对不上
  • I隔离性破裂：跨库事务的中间状态会被其他事务读到（看到扣款但未到账的诡异状态）
  • D持久性还在：每个本地库的持久性仍然成立，但全局视图可能"持久化了一个错的状态"
两类典型场景
场景表现常用方案
跨库事务分库分表后，订单表和订单明细表在不同分片；账户和流水在不同库XA、Seata AT
跨服务事务订单服务下单 → 库存服务扣减 → 支付服务记账，三个服务三个独立数据库TCC、Saga、MQ 事务消息
分布式事务从来不是"完美方案"，而是"在一致性、性能、复杂度之间做权衡"。下面每个方案都有它擅长和不擅长的场景，看到面试题时第一步永远是先问业务。
022PC 两阶段提交
2PC 的两个角色
Coordinator 协调者
事务的指挥官，决定整体提交还是回滚
Participant 参与者
实际持有数据的节点（各分库），执行本地事务，向协调者汇报投票
事务日志
协调者和参与者都要把投票/决议持久化到日志，宕机重启后能恢复
两阶段流程
1
阶段 1：Prepare（准备阶段）
协调者向所有参与者发送 prepare 请求。参与者执行本地事务（写 undo / redo log），但不提交，持有锁；执行成功回 YES，失败回 NO
2
阶段 2：Commit / Rollback（提交阶段）
协调者收齐所有投票：① 全部 YES → 发 commit，参与者提交事务释放锁；② 任一 NO 或超时 → 发 rollback，参与者按 undo log 回滚
2PC 两阶段时序 — Coordinator + 2 Participants
2PC 的三大缺陷
  • ①同步阻塞：阶段 1 结束后，所有参与者都在等协调者的指令，期间一直持有锁。如果协调者慢，整个事务持锁时间很长，吞吐被锁死
  • ②单点故障：协调者本身是单点。如果协调者在阶段 1 之后宕机，参与者只能死等，事务无法推进（除非引入额外的协调者选主机制）
  • ③数据不一致：阶段 2 协调者发送 commit 时，如果只有部分参与者收到（网络故障），就会出现"部分提交、部分未提交"的不一致状态
真实使用很少：原生 2PC 因为这三个缺陷，生产环境几乎不用。MySQL 内部的 binlog 与 redo log 协同其实就是 2PC，但那是单机内的"2PC"。跨库的 2PC 一般要配合改良协议（如 XA、Seata XA 模式）使用。
033PC 三阶段提交
3PC 怎么改进 2PC

3PC 把 2PC 的"准备 + 提交"拆成三步，并引入超时机制，让参与者在协调者掉线时也能自己做决定。

1
CanCommit（询问阶段）
协调者问参与者"你能不能 commit"。参与者只做轻量检查（资源是否就绪），不真正执行事务，回 YES / NO。这一步本质是提前试探，避免后续白做工
2
PreCommit（预提交阶段）
收齐 YES 后，协调者发 PreCommit。参与者真正执行本地事务（写 undo/redo），持锁，但仍然不提交，回 ACK
3
DoCommit（提交阶段）
协调者发 DoCommit，参与者提交事务释放锁。如果参与者在 PreCommit 之后超时没收到 DoCommit，默认自动提交（赌一把：能走到 PreCommit 说明大家都准备好了，协调者大概率发的是 commit）
3PC 没解决根本问题：超时自动提交看似减少阻塞，但如果实际上协调者发的是 rollback、只是网络丢了，参与者就会自动错误地提交，依然产生不一致。3PC 在工程上几乎没人用 —— 复杂度上升一档，可靠性没本质提升。
04XA 协议 & JTA
XA 是什么

XA 是 X/Open 组织在 1991 年定的分布式事务接口规范，本质就是 2PC 的标准化实现。它定义了"事务管理器（TM）"和"资源管理器（RM）"之间的接口，让不同数据库厂商的产品都能接入同一个全局事务。

名词角色对应实物
AP — Application Program业务应用你的 Java 服务
TM — Transaction Manager事务管理器（协调者）Atomikos、Narayana、Seata（XA 模式）
RM — Resource Manager资源管理器（参与者）MySQL、Oracle、PostgreSQL 等支持 XA 的数据库
JTA 与 XA 的关系

JTA（Java Transaction API）是 Java 给 XA 包了一层标准接口。Java 应用通过 JTA 调用，底层由 TM 实现具体的 XA 协议交互。

// 典型 JTA 调用（Atomikos）
UserTransaction tx = new UserTransactionImp();
tx.begin();
try {
    // 操作 DB1（MySQL）和 DB2（Oracle）
    jdbcTemplate1.update("UPDATE account SET balance=balance-100 WHERE id=1");
    jdbcTemplate2.update("UPDATE inventory SET stock=stock-1 WHERE sku='A'");
    tx.commit(); // TM 走 XA 两阶段
} catch (Exception e) {
    tx.rollback();
}
XA 在 MySQL 里怎么开启：MySQL InnoDB 默认支持 XA 接口。需要在SET autocommit=0后用XA START / XA END / XA PREPARE / XA COMMIT命令。生产中一般通过 Atomikos、Narayana 自动管理，应用层不直接写 XA 命令。
性能差是硬伤：XA 全程持锁，多次网络往返。压测下吞吐通常只有本地事务的 1/5 ~ 1/10。互联网公司很少用 XA，传统金融行业还在用。
05TCC 模式
TCC 是什么

TCC = Try / Confirm / Cancel，是把"一个业务操作"拆成三个方法，由业务自己实现，而不是依赖数据库的事务能力。它不用 XA、不用锁数据库行，本质是用业务层的"预留资源 + 显式确认/取消"换取了高并发能力。

Try
预留业务资源（冻结余额、占用库存），写中间表，不真正扣减
Confirm
所有 Try 成功后调用：把冻结的资源真正扣掉。必须幂等
Cancel
任一 Try 失败时调用：释放预留的资源。必须幂等
TCC 代码示例
// 扣余额服务
public class AccountService {
    // Try：把可用余额减 100，冻结余额加 100
    public boolean tryDeduct(Long uid, BigDecimal amount, String txId) {
        // 写一行冻结记录（txId 做幂等键）
        return accountDao.freeze(uid, amount, txId);
    }
    // Confirm：删冻结记录，余额真正扣掉
    public boolean confirm(String txId) {
        return accountDao.confirmFrozen(txId);
    }
    // Cancel：把冻结的金额释放回可用余额
    public boolean cancel(String txId) {
        return accountDao.releaseFrozen(txId);
    }
}
TCC 三大经典坑
  • ①空回滚：Try 因为网络问题没执行，但事务协调器超时了，直接调 Cancel。此时 Cancel 收到的是一个"自己根本没 Try 过"的 txId，要能识别并什么都不做
  • ②幂等：Confirm 和 Cancel 可能因为重试被调多次，必须保证多次调用结果一致。一般用 txId 作为唯一键去重
  • ③悬挂：Cancel 先到（因为网络乱序），Try 后到。如果 Cancel 已经"假装回滚"了，Try 又来冻结资源，就再也没人 Cancel 这一笔了，资源永远悬挂。解决：Cancel 时记录"已被取消"标志，Try 看到标志直接拒绝
业务侵入大：TCC 要求每个服务都拆成三个方法，原本一行 SQL 现在变成三套表 + 三个接口。适合一致性要求高、性能要求高、且团队有能力维护的核心业务（支付、账务），不适合普通 CRUD。
06Saga 模式
Saga 是什么

Saga 把一个长事务拆成一连串本地事务 T1, T2, ..., Tn，每个本地事务对应一个补偿事务 C1, C2, ..., Cn。任一步失败时，按逆序调用前面已成功步骤的补偿事务。和 TCC 的区别：Saga直接执行业务，没有 Try 阶段的"预留"。

// 订单流程
T1 创建订单 → T2 扣库存 → T3 扣余额 → T4 加积分

// 假设 T3 扣余额失败，按逆序补偿
C2 加回库存 → C1 取消订单
（C3 因为 T3 没成功不需要补偿，C4 因为 T4 没执行也不需要）
两种实现风格
Choreography 编排式
服务之间通过事件互相驱动，没有中央协调器。T1 完成发"订单已创建"事件，库存服务订阅这个事件触发 T2，依此类推。优点：去中心化、低耦合；缺点：链路看不见、调试难、循环依赖风险
Orchestration 协调式
有一个中央协调器（Saga Coordinator）按预定流程显式调用每个服务，决定何时进入下一步、何时触发补偿。优点：流程清晰、易追踪；缺点：协调器是中心化组件，要保证它本身的高可用
补偿事务的设计要点
  • ▸幂等：补偿可能被重试多次，要能识别"已经补偿过"
  • ▸允许"语义补偿"而非"数据回滚"：发出去的短信无法撤回，但可以发"上一条信息作废"的修正短信。补偿是业务概念，不是 undo log
  • ▸隔离性差：Saga 的中间状态对外可见（订单已创建但还没扣款），需要在业务层加状态字段隔离
  • ▸补偿可能失败：补偿本身也是个 RPC 调用，可能失败。需要重试 + 人工兜底
Saga 比 TCC 业务侵入小（不需要预留阶段，原有业务方法稍加改造即可），适合流程长、参与方多、一致性要求不极致的场景，比如订单履约、机票出票。Seata 的 Saga 模式、Apache ServiceComb Pack 都是典型实现。
07本地消息表 / 最大努力通知
核心思路

把"业务操作"和"要发的消息"放在同一个本地事务里。业务表 + 消息表同库同事务，要么都成功要么都失败，就把"分布式事务"问题降级为"本地事务 + 异步重试"。

1
业务库写入业务表 + 消息表（同事务）
订单服务在事务内：① 插入订单 ② 插入一条 status=待发送 的消息记录。两个写操作同生同死
2
异步发送消息
独立线程/定时任务扫消息表，把 status=待发送 的消息发到 MQ，发成功后更新为 status=已发送
3
消费者处理 + 回执
下游服务消费消息执行自己的业务，处理成功后通过另一个回执通道告知。失败则不断重试
最大努力通知是本地消息表的近亲：扫描表里"未确认成功"的消息，按递减频率不断重试（1s → 5s → 30s → 5min → 1h），直到收到下游回执或超过最大次数转人工。常用于跨公司接口（支付通知商户、银行通知客户）。
优缺点
  • ✅实现简单，不依赖任何分布式事务框架
  • ✅性能高，主流程只是本地事务 + 一行 insert
  • ✅可靠性好，消息表是兜底，不发完不停止
  • ❌只能最终一致，中间状态对外可见
  • ❌消息表与业务库耦合，分库分表时要每个分片都有消息表
08MQ 事务消息（RocketMQ）
为什么需要事务消息

本地消息表需要业务表 + 消息表同库。如果不想耦合一张消息表，就需要 MQ 本身提供"消息发送和本地事务的原子性"。RocketMQ 通过"半消息 + 二次确认 + 事务回查"做到了这一点。

1
发送 half message（半消息）
生产者先发一条"半消息"到 Broker。半消息已经被存储，但对消费者不可见
2
执行本地事务
生产者收到 Broker 的半消息确认后，执行自己的本地事务（写订单库）。根据本地事务结果，向 Broker 发送二次确认：commit 或 rollback
3
Broker 处理二次确认
收到 commit → 半消息转为正常消息，消费者可见。收到 rollback → 删除半消息
4
事务回查（兜底）
如果生产者执行本地事务后宕机，二次确认丢了。Broker 一段时间未收到确认，会主动回查生产者："这笔事务到底成没成？" 生产者根据本地状态告诉 Broker commit 还是 rollback
事务回查的实现成本：生产者必须能根据"事务 ID"查询本地事务最终状态。这意味着业务需要把事务状态持久化、提供查询接口。Spring Cloud Stream / RocketMQ Spring Boot 都封装了模板代码，但业务逻辑还得自己写。
RocketMQ 事务消息 — 半消息 + 二次确认 + 回查兜底
09Seata 框架
Seata 的三个角色

Seata 是阿里开源的分布式事务框架，对外提供 AT / TCC / Saga / XA 四种模式，全部基于同一套角色模型。

TC — Transaction Coordinator
事务协调器，独立部署的 Seata Server，负责维护全局事务状态、驱动分支事务的提交或回滚
TM — Transaction Manager
事务管理器，业务应用中的"事务发起方"。开启 / 提交 / 回滚全局事务
RM — Resource Manager
资源管理器，业务应用中的"事务参与方"。注册分支事务，向 TC 上报结果，接受 TC 指令做提交或回滚
AT 模式（无侵入）

AT = Automatic Transaction，是 Seata 的默认且最易用的模式。业务代码只需加一个@GlobalTransactional注解，框架自动接管。

1
一阶段：业务 SQL + 自动写 undo_log
Seata 拦截业务 SQL，在执行前后分别查询数据快照，把"修改前镜像 + 修改后镜像"写入 undo_log 表（与业务表同库）。本地事务直接提交，立即释放行锁
2
二阶段：异步提交或回滚
全局事务成功 → TC 通知 RM 异步删除 undo_log；失败 → RM 读 undo_log 中的"修改前镜像"反向生成 SQL 回滚数据
AT 模式的隔离性问题：一阶段就提交本地事务释放行锁，意味着其他事务能立刻看到"未最终提交"的脏数据。Seata 通过 SELECT ... FOR UPDATE 改写 + 全局锁来解决，但仍有性能折损。AT 适合 CRUD 中等并发场景，不适合高并发热点账户。
四种模式选型
模式业务侵入性能一致性适用
AT无（注解）中最终一致简单 CRUD、跨库事务
TCC大（三方法）高强一致核心账务、高并发
Saga中（补偿方法）高最终一致长流程、跨组织
XA无低强一致传统行业、低并发

四维对比
方案一致性性能复杂度业务侵入

常见业务场景的推荐方案
  • ▸支付扣款（强一致 + 高并发）：TCC。资源预冻结模型天然适合账务
  • ▸下单扣库存（最终一致即可）：MQ 事务消息 / 本地消息表，性能好实现简单
  • ▸订单履约（长流程、多服务）：Saga，每一步有明确补偿
  • ▸配置中心、注册中心（CP 系统）：直接走 Raft/ZAB 共识，不需要传统分布式事务
  • ▸异构数据源（MySQL + Oracle）的金融场景：XA / Seata XA，传统行业能接受性能损失
  • ▸普通 CRUD 跨库（既不想写 TCC 又对性能不敏感）：Seata AT，业务无侵入
选型口诀：先问一致性要求—— 能接受最终一致就别用强一致方案。再问业务侵入承受度—— 不想改业务就 Seata AT、本地消息表，能改就 TCC、Saga。最后看团队能力—— Seata 部署成本、TCC 三个坑、Saga 补偿设计，都是真实门槛。
