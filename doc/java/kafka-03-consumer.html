01消费流程
Consumer 基础结构与 poll() 循环

Kafka Consumer 是单线程设计（非线程安全），通过 poll() 主动向 Broker 拉取消息（Pull 模式）。核心循环结构：

Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092");
props.put("group.id",          "order-consumer-group");
props.put("key.deserializer",  StringDeserializer.class.getName());
props.put("value.deserializer",StringDeserializer.class.getName());
props.put("auto.offset.reset", "earliest"); // 无历史 offset 时从最早开始消费
props.put("enable.auto.commit","false");    // 关闭自动提交，手动控制

KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(List.of("orders", "payments")); // 订阅 Topic

try {
    while (true) {
        // poll() 触发心跳、Rebalance 处理、消息拉取，超时返回空集合
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));

        for (ConsumerRecord<String, String> record : records) {
            processRecord(record); // 业务处理
        }

        consumer.commitSync(); // 处理完一批后手动提交
    }
} finally {
    consumer.close(); // 触发正常 Rebalance，将 Partition 移交其他 Consumer
}
pull() 核心参数详解
参数默认值作用
fetch.min.bytes 1 B Broker 累积到至少这么多数据才返回响应。增大可减少请求次数，但会增加延迟
fetch.max.wait.ms 500 ms Broker 等待 fetch.min.bytes 满足的最大时间，超时后无论数据量多少都返回
max.poll.records 500 单次 poll() 最多返回的消息条数，控制每批处理量
max.poll.interval.ms 300,000 ms（5 min） 两次 poll() 之间的最大间隔。超过此时间未 poll，Broker 认为 Consumer 已死，触发 Rebalance
fetch.max.bytes 50 MB 单次 Fetch 响应的最大字节数上限
⚠ max.poll.interval.ms 踩坑：若业务处理逻辑耗时较长（如批量写 DB），可能在下次 poll() 前超过此阈值，导致 Consumer 被踢出 Group 并触发 Rebalance。解决方案：减小 max.poll.records（减少单批量）或增大 max.poll.interval.ms，或将耗时处理异步化。
subscribe() vs assign() — 两种订阅方式
方式API特点适用场景
自动分配
subscribe()		 consumer.subscribe(List.of("topic")) 加入 Consumer Group，由 GroupCoordinator 自动分配 Partition；支持 Rebalance 绝大多数生产场景
手动指定
assign()		 consumer.assign(List.of(new TopicPartition("topic", 0))) 绕过 Group 机制，直接指定消费哪些 Partition；不触发 Rebalance，没有 Group 概念 数据回放、精确消费特定分区、测试
⚠ subscribe() 和 assign() 不能混用，否则抛 IllegalStateException。
02Rebalance 机制
什么是 Rebalance & 触发条件

Rebalance 是 Consumer Group 内 Partition 分配关系的重新协商过程。触发后，Group 内所有 Consumer 暂停消费，等待分配结果后重新开始（Eager 模式）。

触发 Rebalance 的条件：

触发原因说明
Consumer 加入 Group新 Consumer 启动并 subscribe() 后，向 GroupCoordinator 发送 JoinGroup 请求
Consumer 离开 GroupConsumer 正常调用 close()，或心跳超时（超过 session.timeout.ms）被判定宕机
心跳超时Consumer 长时间未发送心跳（后台 HeartbeatThread 负责），Broker 移除该成员
poll() 超时两次 poll() 间隔超过 max.poll.interval.ms，Consumer 主动离开 Group
Topic 分区数变更增加 Topic 的 Partition 数，触发 Group 重新分配
订阅 Topic 变更Consumer 修改 subscribe() 的 Topic 列表

GroupCoordinator — Rebalance 协调者

GroupCoordinator 是 Broker 端负责管理 Consumer Group 的组件，每个 Consumer Group 对应唯一一个 Coordinator（由 __consumer_offsets Topic 的某个 Partition Leader 承担）。

职责说明
成员管理维护 Group 成员列表，处理加入 / 离开请求
Offset 存储接收 commitOffset 请求，将 Offset 写入 __consumer_offsets
Rebalance 协调发起 Rebalance，主持 JoinGroup 和 SyncGroup 两阶段流程
心跳检测接收 Consumer 心跳，超时则移除成员并触发 Rebalance
Rebalance 协议 — JoinGroup + SyncGroup 两阶段
Phase 1
JoinGroup
所有 Consumer 向 Coordinator 发送 JoinGroup 请求。Coordinator 等待所有成员到齐后，选出Group Leader（第一个加入的 Consumer），并把成员列表下发给 Leader。
Phase 2
SyncGroup
Group Leader（不是 Coordinator）根据分配策略计算出每个成员的 Partition 分配方案，通过 SyncGroup 请求上报给 Coordinator。Coordinator 再将各成员的分配结果下发给对应 Consumer。

Group Leader ≠ Coordinator：分区分配计算由 Consumer 端的 Group Leader 完成，Coordinator 只是中转站。这样设计的好处是分配算法可以在客户端扩展，Broker 不需要感知具体算法。
Eager vs Cooperative — 两种 Rebalance 协议
协议行为停顿时长代表分配策略
Eager（激进） Rebalance 开始时，所有 Consumer 立即撤销全部 Partition，停止消费，等待新分配结果后重新开始 全量停顿（短则几秒，长则十几秒） RangeAssignor、RoundRobinAssignor、StickyAssignor
Cooperative（协作） 只撤销需要移交的 Partition，其余 Partition 继续消费不中断，通过多轮 Rebalance 增量调整 极短（仅移交的 Partition 短暂停顿） CooperativeStickyAssignor（Kafka 2.4+ 推荐）
生产推荐：Kafka 3.x 中将 CooperativeStickyAssignor 设为默认分配策略，新项目应直接使用。存量项目从 Eager 迁移到 Cooperative 需要经过一次中间态 Rebalance（先配 StickyAssignor,CooperativeStickyAssignor 双策略滚动升级）。
减少 Rebalance 的实践
手段配置 / 做法原理
调大心跳超时 session.timeout.ms=45000
heartbeat.interval.ms=15000（约为 session 的 1/3）		 给网络抖动更多容忍空间，避免短暂延迟被误判为宕机
调大 poll 间隔 max.poll.interval.ms=600000 业务处理耗时较长时，避免 poll() 超时触发主动离组
减小单批处理量 max.poll.records=100 减少单次处理耗时，更容易在 max.poll.interval.ms 内完成
使用 Cooperative 协议 partition.assignment.strategy=CooperativeStickyAssignor 增量分配，减少因 Rebalance 导致的消费停顿影响面
避免频繁重启 滚动升级时控制节奏，避免短时间内大量 Consumer 反复加入/离开 每次成员变更都会触发 Rebalance
03Offset 提交策略
三种消费语义

Offset 提交的时机决定了消费语义，理解语义是选择提交策略的前提：

at-most-once
poll()
先提交 Offset
处理消息…
宕机→消息丢失
at-least-once
poll()
处理消息…
再提交 Offset
宕机→重新消费
exactly-once
poll()
处理消息…
原子：写DB + 提交Offset
宕机点（未提交 Offset，消息丢失）
宕机点（已处理，重启后重复消费）
原子提交（处理与提交不可分割）
语义含义实现方式
at-most-once 最多消费一次，可能丢消息 拉到消息后先提交 Offset，再处理。若处理失败，消息不会重新消费
at-least-once 至少消费一次，可能重复 处理完成后再提交 Offset。若提交前 Consumer 宕机，重启后重新消费，需业务幂等
exactly-once 精确消费一次 Kafka 事务（sendOffsetsToTransaction）+ 幂等消费，或外部存储原子提交 Offset
自动提交 — enable.auto.commit=true

Consumer 后台线程每隔 auto.commit.interval.ms（默认 5000 ms）自动提交当前已拉取的最大 Offset。

props.put("enable.auto.commit",      "true");
props.put("auto.commit.interval.ms", "5000");
优点缺点
代码简单，无需手动管理 · 语义是 at-least-once：poll() 后、处理完成前宕机，重启后会重复消费
· 5s 内消费的消息，若 Consumer 宕机则全部重新消费
· 无法精确控制提交时机
生产环境建议关闭自动提交，改用手动提交以精确控制消费语义，避免消息处理中途宕机后的大范围重复消费。
手动提交 — 三种粒度
// ① 同步提交 — 阻塞等待 Broker 确认，可靠但影响吞吐
// 每批处理完后提交
consumer.commitSync();

// 带重试的同步提交（异常时手动重试）
try {
    consumer.commitSync();
} catch (CommitFailedException e) {
    log.error("Commit failed", e);
    // Rebalance 期间提交会失败，通常忽略或告警
}

// ② 异步提交 — 不阻塞，回调中感知结果，吞吐高
// 不要在异步回调中重试（可能因乱序导致回退 Offset）
consumer.commitAsync((offsets, exception) -> {
    if (exception != null) {
        log.error("Async commit failed: {}", offsets, exception);
    }
});

// ③ 精确提交指定 Offset — 按 Partition 精细控制
// 适合消费到一半时需要定点提交的场景
Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
for (ConsumerRecord<String, String> record : records) {
    processRecord(record);
    // 提交当前消息的下一个 Offset（已消费的 +1）
    offsets.put(
        new TopicPartition(record.topic(), record.partition()),
        new OffsetAndMetadata(record.offset() + 1)
    );
}
consumer.commitSync(offsets);
提交方式语义吞吐适用场景
commitSync()at-least-once低强可靠，每批必须确认提交
commitAsync()at-least-once高正常消费链路，关闭时补一次 commitSync
commitSync(offsets)at-least-once低精确到消息级别的 Offset 控制
最佳实践 — 混合提交：正常循环用 commitAsync() 保证吞吐；在 finally 块或 ConsumerRebalanceListener.onPartitionsRevoked() 中用 commitSync() 兜底，确保 Rebalance 或关闭时 Offset 不丢失。
auto.offset.reset — 无历史 Offset 时的起点
值行为适用场景
earliest从 Partition 最早可用消息开始消费（等同于 --from-beginning）新 Group 第一次接入，需要处理全量历史数据
latest（默认）从 Partition 末尾开始，只消费启动后新写入的消息只关心实时消息，不需要历史数据
none找不到 Offset 时直接抛出异常明确要求 Offset 必须已存在，防止意外从头消费
04分区分配策略
四种内置分配策略对比

Consumer Group 成员如何瓜分 Topic 的 Partition，由 partition.assignment.strategy 决定（Group Leader 执行具体计算）：

策略算法优点缺点Rebalance 协议
Range
（旧默认）		 按 Partition 序号范围切分，每个 Consumer 分到连续的一段 同一 Consumer 能得到多 Topic 相同编号的 Partition（便于 Topic 联合消费） Topic 多时前几个 Consumer 分到的 Partition 更多，负载不均 Eager
RoundRobin 将所有 Topic 的所有 Partition 排成一列，依次轮询分给各 Consumer 分配最均匀 要求 Group 内所有 Consumer 订阅相同的 Topic 列表 Eager
Sticky 尽量保持上次 Rebalance 的分配结果，只移动必须移动的 Partition 减少 Rebalance 后的 Partition 迁移量，降低重复消费 实现复杂，首次分配与 RoundRobin 相同 Eager
CooperativeSticky
（新默认，推荐）		 在 Sticky 基础上改用 Cooperative 协议，增量分配 Rebalance 期间大部分 Partition 可继续消费，停顿影响最小 需 Kafka 2.4+；多轮 Rebalance 才能完成调整 Cooperative
示例：3 Consumer 消费 7 Partition 的分配结果
Topic: orders，Partition: P0 P1 P2 P3 P4 P5 P6
Consumer: C0  C1  C2

── RangeAssignor ──────────────────────────────────────
C0 → P0 P1 P2   (7/3=2余1，第一个多分1个)
C1 → P3 P4
C2 → P5 P6

── RoundRobinAssignor ─────────────────────────────────
C0 → P0 P3 P6
C1 → P1 P4
C2 → P2 P5

── StickyAssignor (首次，等同 RoundRobin) ──────────────
C0 → P0 P3 P6
C1 → P1 P4
C2 → P2 P5

  若 C1 宕机，Sticky 重新分配（尽量保留已有分配）：
C0 → P0 P3 P6 P1   (从 C1 接管 P1)
C2 → P2 P5 P4      (从 C1 接管 P4)
05Lag 监控与调优
Consumer Lag — 消息积压的核心指标
Lag = HW（Partition 末尾）− CurrentOffset（Consumer 当前消费位置）

Lag 代表 Consumer 落后 Broker 多少条消息。Lag 持续增长说明消费速度跟不上生产速度，需要扩容或优化。

查看 Lag 的方式命令 / 工具
命令行（实时查看） kafka-consumer-groups.sh --bootstrap-server host:9092 --describe --group my-group
JMX 指标 kafka.consumer:type=consumer-fetch-manager-metrics,client-id=xxx 中的 records-lag-max
Kafka Manager / CMAK 图形化展示各 Group 各 Partition 的 Lag 趋势
Prometheus + kafka-exporter 采集 kafka_consumergroup_lag 指标，配合 Grafana 告警
消费积压处理方案
1
紧急扩容 Consumer（最快见效）
增加 Consumer 实例数（不超过 Partition 数），触发 Rebalance 后新实例立即分担消费。注意：Consumer 数超过 Partition 数的部分会闲置，没有意义。
2
增大 max.poll.records + 批量入库
将 max.poll.records 从 500 调大到 1000~2000，配合数据库批量写入（batchInsert），减少 IO 次数，显著提升消费吞吐。
3
扩 Partition（需停写或新建 Topic）
若 Consumer 已达 Partition 数上限，需先扩 Partition 再加 Consumer。注意扩分区后有 Key 哈希路由变化问题。若不能停写，可新建一个多分区 Topic，将原 Topic 的积压消息用临时 Consumer 转发过去，再切流量。
4
异步化消费（解耦 IO 密集型处理）
poll() 主线程快速拉取，将消息投递到内存队列（如 LinkedBlockingQueue），线程池异步处理。注意此时 Offset 提交需要协调机制，防止处理未完成就提交。
多线程消费模式对比

Kafka Consumer 本身非线程安全，多线程消费需在 Consumer 层面或处理层面做设计：

模式结构优点注意点
多 Consumer 实例 每个线程独立持有一个 KafkaConsumer，各自 poll() 隔离性好，Offset 提交独立，实现简单 线程数受 Partition 数限制；每个实例都有独立 TCP 连接开销
单线程 poll + 线程池处理 主线程 poll()，消息投入线程池异步处理 单 Consumer 可充分利用多核，处理吞吐高 Offset 提交需等所有处理线程完成才能提交，否则可能丢消息；实现复杂 
// 单线程 poll + 线程池处理（简化版）
ExecutorService pool = Executors.newFixedThreadPool(8);

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
    List<Future<?>> futures = new ArrayList<>();

    for (ConsumerRecord<String, String> record : records) {
        futures.add(pool.submit(() -> processRecord(record)));
    }

    // 等待本批所有任务完成后再提交 Offset
    for (Future<?> f : futures) f.get();
    consumer.commitSync();
}
⚠ 异步处理 + Offset 提交的陷阱：若不等线程池完成就提交 Offset，Consumer 宕机时已提交但未处理的消息会丢失（变为 at-most-once）。必须在所有处理线程完成后再提交，或使用精确位置提交跟踪每条消息的处理状态。
