前五阶段合称类连接过程（验证+准备+解析），解析阶段可以在初始化后才进行（支持动态绑定）。

主动使用（触发初始化的 6 种场景）
  • ①new 实例化对象、读取或设置类的静态字段（非 final 常量）、调用类的静态方法
  • ②使用反射（Class.forName()、Method.invoke()）
  • ③初始化一个类时，如果其父类还未初始化，先触发父类初始化
  • ④JVM 启动时的主类（包含 main() 的类）
  • ⑤JDK7+ 动态语言支持：MethodHandle 解析的方法所属类
  • ⑥接口定义了 default 方法，实现类初始化时触发接口初始化
被动使用（不触发初始化的 3 种典型）
  • ①子类引用父类的静态字段— 只触发父类初始化，子类不初始化
    System.out.println(Sub.staticFieldFromParent)
  • ②定义数组类型引用— MyClass[] arr = new MyClass[10]，不触发 MyClass 初始化
  • ③引用编译期常量— static final int X = 100 在编译时直接内联，不触发类加载
面试高频：子类引用父类 static 字段，子类会被加载（字节码验证需要）但不会初始化；JVM 参数 -XX:+TraceClassLoading 可验证。
02 五个加载阶段详解
加载（Loading）

通过类的全限定名，找到 .class 文件的字节流，完成三件事：

  • ①获取定义此类的二进制字节流（可来自文件、网络、动态生成、加密解密等）
  • ②将字节流代表的静态存储结构转化为方法区运行时数据结构（类元数据）
  • ③在堆中生成一个代表此类的 java.lang.Class 对象（作为方法区数据的入口）
验证（Verification）

确保字节码符合 JVM 规范，防止恶意代码破坏 JVM。四重验证：

  • ①文件格式验证— 魔数 0xCAFEBABE、版本号范围、常量池合法性
  • ②元数据验证— 语义合法性：类是否继承了 final 类、是否缺少父类等
  • ③字节码验证— 数据流和控制流分析，确保方法体不会产生危害 JVM 的行为
  • ④符号引用验证— 在解析阶段发生，检查符号引用能否定位到具体目标（类/方法/字段存在且可访问）
优化：若代码可信（自己编译的代码），可用 -Xverify:none 关闭验证加快启动（不推荐生产使用）。
准备（Preparation）

为类的静态变量分配内存并设置初始零值（在方法区/元空间），注意两个重要细节：

  • •public static int value = 123; → 准备阶段 value = 0，不是 123（123 在初始化阶段的 <clinit> 中赋值）
  • •public static final int VALUE = 123; → 因有 ConstantValue 属性，准备阶段直接赋值 123
面试考点：准备 vs 初始化的区别。static 变量在准备阶段赋零值，static final 基本类型/字符串常量在准备阶段赋真实值，其余赋值均在初始化阶段。
解析（Resolution）

将常量池中的符号引用替换为直接引用（内存地址）。包括：

  • ①类/接口的解析— 符号引用指向的类名 → 类的直接引用
  • ②字段解析— 类名.字段名 → 字段的内存偏移量
  • ③类方法 / 接口方法解析— 方法的符号引用 → 方法表中的指针

解析可以在初始化之后进行（invokedynamic 指令），支持 Java 的动态语言特性。

初始化（Initialization）

执行类构造器 <clinit>() 方法：编译器自动收集所有静态变量赋值动作和static 代码块，按源文件顺序合并生成。

  • ①JVM 保证父类的 <clinit> 先于子类执行
  • ②若类没有静态变量赋值和 static 块，则不生成 <clinit>
  • ③<clinit> 由 JVM 加锁，线程安全，多线程并发时只有一个线程执行，其余阻塞等待 —— 单例模式静态内部类利用了这一特性
  • ④与实例构造器 <init> 区分：<clinit> 是类级别（static），<init> 是实例级别（new 时调用）

各加载器详解
加载器实现负责加载父加载器
Bootstrap C++（JVM内部） $JAVA_HOME/lib/rt.jar（java.lang, java.util 等核心类） null（无父）
Extension / Platform Java（sun.misc.Launcher$ExtClassLoader） $JAVA_HOME/lib/ext/ 目录所有 jar Bootstrap
Application Java（sun.misc.Launcher$AppClassLoader） 用户 -classpath 指定的 jar 和目录 Extension
自定义 Java（继承 ClassLoader） 自定义来源（网络/加密jar/数据库） 默认 Application
类的唯一性：在 JVM 中，两个类相等的条件是：类本身相同 AND 加载它的 ClassLoader 相同。同一字节码被不同 ClassLoader 加载，是两个不同的类（instanceof 返回 false，equals() 返回 false）。
自定义 ClassLoader 核心代码
public class MyClassLoader extends ClassLoader {
    private String classPath;

    public MyClassLoader(String classPath) {
        this.classPath = classPath;
    }

    // ★ 重写 findClass，不要重写 loadClass（否则破坏双亲委派）
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] classData = loadClassData(name);
        if (classData == null) {
            throw new ClassNotFoundException();
        }
        // 将字节数组转为 Class 对象
        return defineClass(name, classData, 0, classData.length);
    }

    private byte[] loadClassData(String className) {
        // 将类名转为路径，从文件/网络/加密jar读取字节码
        String fileName = classPath + File.separator
                + className.replace('.', File.separatorChar) + ".class";
        try (InputStream in = new FileInputStream(fileName);
             ByteArrayOutputStream out = new ByteArrayOutputStream()) {
            byte[] buf = new byte[1024];
            int len;
            while ((len = in.read(buf)) != -1) out.write(buf, 0, len);
            return out.toByteArray();
        } catch (IOException e) {
            return null;
        }
    }
}
04 双亲委派模型
工作原理

当一个类加载器收到类加载请求时，先把请求委派给父加载器，只有父加载器无法完成（在搜索范围内找不到该类），才由子加载器自己尝试加载。

loadClass() 源码分析（核心逻辑）
protected Class<?> loadClass(String name, boolean resolve)
        throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 1. 检查是否已加载（缓存）
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                // 2. 委派父加载器（递归）
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    // 父为 null 说明父是 Bootstrap
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器找不到，捕获异常继续
            }

            if (c == null) {
                // 3. 父加载器失败，自己尝试加载
                c = findClass(name);  // ← 子类应重写此方法
            }
        }
        if (resolve) resolveClass(c);
        return c;
    }
}
关键：双亲委派逻辑在 loadClass() 中实现。子类应重写 findClass()，而不是 loadClass()，否则会破坏双亲委派。
双亲委派的核心作用
  • ①防止核心类被篡改— 自己写的 java.lang.String 类永远不会被加载（Bootstrap 已先加载了官方 String），保证了 JVM 安全性
  • ②避免类重复加载— 同一个类被父加载器加载后缓存，子加载器直接复用，不会出现多份 Class 对象
破坏双亲委派的场景

破坏① SPI 机制（JDBC / JNDI）

JDBC 的 java.sql.Driver 接口定义在 Bootstrap 加载的 rt.jar 中，但具体实现（com.mysql.jdbc.Driver）在用户 classpath。Bootstrap 无法加载用户代码。

解决：引入线程上下文类加载器（Thread Context ClassLoader）。父加载器通过 Thread.currentThread().getContextClassLoader() 获取 Application ClassLoader，委托其加载 SPI 实现，实现了"子加载器加载，父加载器调用"的逆向委派。

破坏② Tomcat — 类隔离

多个 WebApp 可能依赖同一库的不同版本（如 Spring 4.x 和 Spring 5.x）。Tomcat 为每个 Web 应用创建独立的 WebAppClassLoader，优先自己加载（先 findClass，再委派父），实现应用间类隔离。

破坏③ OSGi — 网状委派

OSGi 实现热插拔模块化，每个 Bundle 有独立 ClassLoader，ClassLoader 间形成网状（非树状）委派结构，类查找走模块导入/导出规则。

JDK9+ 模块化（Module）

JDK9 引入 JPMS（Java Platform Module System），类加载首先按模块查找，Bootstrap/Platform/Application 三层加载器职责重新划分为 Bootstrap → Platform → System（Application），不再纯靠类路径委派。

05 热部署原理
类的卸载条件

JVM 中类可以被卸载，但需同时满足三个苛刻条件：

  • ①该类的所有实例对象均已被 GC
  • ②加载该类的 ClassLoader 实例已被 GC
  • ③该类对应的 java.lang.Class 对象没有任何地方引用
注意：由 Bootstrap / Extension / Application 三个内置加载器加载的类永远不会被卸载（这三个 ClassLoader 实例不会被回收），只有自定义 ClassLoader 加载的类才可能卸载。
热部署的实现方式
  • ①新 ClassLoader 加载新版本— 创建新的自定义 ClassLoader 加载新版本字节码；旧 ClassLoader 与其加载的所有类等待满足卸载条件后被 GC。这是实现热部署的通用方式。
  • ②Arthas redefine— 基于 Java Instrumentation API（Instrumentation.redefineClasses()）。限制：不允许修改类结构（不能增删字段、方法、改继承关系），只能替换方法体。
  • ③Arthas retransform— 与 redefine 类似，但支持后续恢复原始字节码（retransform --classPattern）。
  • ④Spring DevTools— 双 ClassLoader 机制：base ClassLoader 加载不变的依赖（第三方 jar），restart ClassLoader 加载用户代码。代码修改后，只重建 restart ClassLoader，比完整重启快 10 倍以上。
  • ⑤JRebel（商业）— 通过 Java Agent 进行字节码增强，支持修改类结构（增删字段/方法），无需重启即可生效，是最完整的热部署方案。
Arthas 热修复示例
# 1. 修改 Java 文件，编译得到新 .class 文件
javac -cp . com/example/OrderService.class

# 2. 连接 Arthas
java -jar arthas-boot.jar

# 3. 用 redefine 替换线上类（不改变方法签名）
redefine /tmp/com/example/OrderService.class

# 4. 验证类是否生效（反编译）
jad com.example.OrderService

# 5. 若要恢复原始字节码
retransform --deleteAll
retransform -c <classLoaderHash> --classPattern com.example.OrderService
