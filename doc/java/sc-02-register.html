01为什么需要注册中心
没有注册中心，微服务怎么找到对方？

最简单的方式是硬编码 IP：order-service 调用 user-service 时，直接写死 http://192.168.1.10:8082/user/info。这在小规模系统中勉强可以用，但立即暴露三个问题：

  • 动态扩容user-service 新增一个实例（192.168.1.11），order-service 不知道，新实例永远不会被调用
  • 故障下线192.168.1.10 宕机了，order-service 还在调它，持续报错
  • 运维噩梦50 个服务互相调用，IP 变一次就要改大量配置，还要重启

注册中心解决方案：服务注册 + 服务发现。服务启动时把自己的 IP+端口注册到注册中心，消费方通过服务名查询注册中心获取实例列表，再通过负载均衡选一个调用。

02Nacos 架构原理
Nacos 是什么？做了什么？

Nacos（Dynamic Naming and Configuration Service）是阿里开源的注册中心 + 配置中心一体化产品。相比需要单独部署注册中心（Eureka）+ 配置中心（Spring Cloud Config）的方案，Nacos 一个组件全覆盖，运维简单很多。

Nacos 数据模型：Namespace / Group / Service / Cluster / Instance

Nacos 用五层数据模型组织服务，理解这个模型对多环境、多机房部署非常重要：

  • Namespace最顶层隔离，通常用来区分环境（dev / test / staging / prod）。不同 Namespace 的服务互不可见。默认 Namespace 是 public。
  • Group在 Namespace 内进一步分组，通常用来区分业务域（order-group / user-group）。同一 Namespace 不同 Group 的服务也互不可见（需显式跨 Group 查询）。
  • Service服务名，如 order-service。一个 Service 可以有多个实例。
  • Cluster服务的分集群，通常用来区分机房/可用区（beijing / shanghai）。LoadBalancer 优先选同集群的实例（就近访问）。
  • Instance一个具体的服务进程，包含 IP、端口、权重、健康状态、元数据等。
spring:
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        namespace: dev-namespace-id   # Namespace ID（不是名称）
        group: order-group
        cluster-name: BJ              # 当前实例所属集群
Nacos 集群部署与 Raft 共识

生产环境 Nacos 需要至少 3 节点集群（奇数，同 Raft 要求）。Nacos 2.x 默认在 CP 模式（一致性优先）下使用 Raft 协议选举 Leader，所有写操作通过 Leader 再同步到 Follower，保证数据一致性。

Nacos 使用的持久化存储：

  • 单机模式内嵌 Derby 数据库（仅用于测试/开发，不可用于生产）
  • 集群模式外置 MySQL，所有节点共享同一个 MySQL，通过 Raft 保证写操作串行
03AP vs CP 模式选择
同一个 Nacos，临时实例用 AP，永久实例用 CP

Nacos 的一大亮点：在同一注册中心内，临时实例和永久实例使用不同的一致性协议，可以按需选择。

模式实例类型协议适用场景配置
AP 模式临时实例（Ephemeral）Distro（自研最终一致性）Spring Boot 微服务（需要高可用，允许短暂不一致）默认行为（ephemeral: true）
CP 模式永久实例（Persistent）Raft需要强一致的场景（如 DNS 服务、服务配置）ephemeral: false

AP 模式下的行为：客户端实例宕机后，Nacos 在心跳超时（默认 15s）后将其标记为不健康，30s 后从列表中删除。宕机期间其他实例依然可以正常注册和发现（AP 优先可用性）。

CP 模式下的行为：Raft Leader 不可用时，整个注册中心暂停写操作（新注册 / 注销），直到选出新 Leader。已注册的实例列表仍可读（不影响服务发现），但新服务无法注册。

04健康检查机制
客户端心跳 vs 服务端探测
客户端心跳（临时实例，AP 模式）
服务实例定期（默认每 5 秒）向 Nacos 发送心跳（PUT /nacos/v1/ns/instance/beat）。

· 超过 15 秒未收到心跳 → 标记为不健康（unhealthy）
· 超过 30 秒未收到心跳 → 从实例列表删除

消费方缓存了实例列表，Nacos 会主动 Push 变更通知（UDP），消费方收到后更新本地缓存。
服务端主动探测（永久实例，CP 模式）
Nacos 主动向注册的实例发起健康检查请求（HTTP 或 TCP）。

· HTTP 探测：Nacos 对实例的某个 URL 发 GET 请求，200 则健康
· TCP 探测：建立 TCP 连接，成功则健康

适用于非 Spring Boot 服务（如传统 Java 服务、第三方服务），不能自己发心跳的场景。
消费方的本地缓存与推拉结合

消费方不会每次调用都去 Nacos 查询（否则 Nacos 成为请求热点）。Spring Cloud LoadBalancer 在本地缓存实例列表，更新策略是推拉结合：

  • PushNacos 服务端感知到实例变化（注册/注销/健康状态变化），主动通过 gRPC（Nacos 2.x）推送给所有订阅该服务的消费方，延迟约 1~2 秒
  • Pull消费方定期（默认 30 秒）主动拉取一次，防止 Push 漏掉的情况

Nacos 2.x 把 HTTP 轮询改成了 gRPC 长连接，推送延迟从秒级降到毫秒级，是相比 Nacos 1.x 最大的架构改进。

05Nacos 配置中心
配置文件的三个维度：Namespace / Group / DataId

Nacos 配置中心用三个维度定位一个配置文件：

  • Namespace环境隔离，与注册中心的 Namespace 一一对应
  • Group业务分组，默认 DEFAULT_GROUP
  • DataId配置文件名，格式通常是 {spring.application.name}-{spring.profiles.active}.{file-extension}，如 order-service-prod.yaml
spring:
  config:
    import: nacos:order-service-prod.yaml   # Spring Boot 2.4+ 写法
  cloud:
    nacos:
      config:
        server-addr: 127.0.0.1:8848
        namespace: prod-namespace-id
        group: order-group
        file-extension: yaml
动态刷新：@RefreshScope

Nacos 配置变更后，服务不需要重启即可生效，但需要在 Bean 上添加 @RefreshScope：

@RestController
@RefreshScope   // 配置变更时，Spring 会销毁并重新创建这个 Bean
public class OrderController {

    @Value("${order.maxRetry:3}")
    private int maxRetry;   // 配置变更后，这里的值会自动更新

    // 使用 @ConfigurationProperties 更推荐，自动支持刷新
}

// 推荐方式：@ConfigurationProperties + @RefreshScope
@Component
@RefreshScope
@ConfigurationProperties(prefix = "order")
public class OrderProperties {
    private int maxRetry = 3;
    private String paymentUrl;
    // getter/setter
}

刷新原理：Nacos 客户端监听配置变更（长轮询，默认 30 秒），收到变更后发布 RefreshEvent，Spring 的 ContextRefresher 接收事件，重新绑定所有 @RefreshScope Bean 的配置。

配置分级与共享配置

实际项目中，常见三层配置结构：

  • 公共配置common.yaml：所有服务共享（数据库连接池参数、公共超时配置）
  • 服务配置order-service.yaml：该服务所有环境通用的配置
  • 环境配置order-service-prod.yaml：该服务特定环境的配置（DB 密码、第三方 API Key）
# 加载多个配置文件（shared-configs）
spring:
  config:
    import:
      - nacos:common.yaml
      - nacos:order-service.yaml
      - nacos:order-service-prod.yaml  # 同名 key 以最后加载的为准
敏感配置（密码、密钥）不应该放 Nacos 明文存储。应使用 Nacos 的加密插件或对接 HashiCorp Vault / 阿里云 KMS，在应用启动时自动解密。
06Nacos vs Eureka
全面对比
维度NacosEureka
一致性协议AP（Distro）/ CP（Raft）可切换AP（自研，最终一致性）
健康检查客户端心跳 + 服务端主动探测，两种均支持仅客户端心跳
服务下线支持主动注销 + 心跳超时自动剔除心跳超时自动剔除（90s）
配置中心✅ 内置，无需额外组件❌ 不支持，需单独部署 Spring Cloud Config
推送机制gRPC 长连接推送（Nacos 2.x），毫秒级定时拉取，秒级延迟
维护状态✅ 阿里持续维护，社区活跃⚠ Netflix 已停止维护（2022 年）
UI 控制台功能丰富，支持服务管理/配置编辑/权重调整简单，仅展示服务列表
权重/路由✅ 实例权重、集群就近路由❌ 不支持
新项目直接选 Nacos，无需考虑 Eureka。Nacos = 注册中心 + 配置中心，减少一个中间件的部署和运维。Eureka 已停止维护，Spring Cloud 官方也逐渐减少对它的支持。
