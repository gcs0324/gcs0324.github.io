01 RPC 原理 Q1–Q6
Q1 什么是 RPC？它和本地调用有什么区别？ 高频▼
面试官视角

考查对 RPC 本质的理解，以及对网络调用和本地调用差异的认知。能说出"部分失败"这个分布式特有问题是加分项。

参考回答

RPC（Remote Procedure Call）让调用远程服务像调用本地方法一样，屏蔽网络通信细节。核心组件：序列化 + 网络传输 + 动态代理 + 服务发现。

  • 本地调用JVM 内方法调用，栈帧传参，无网络开销，失败即异常，简单可靠
  • RPC 调用涉及序列化、网络传输（延迟/超时/丢包）、服务发现、容错重试，需要处理部分失败等分布式特有问题
核心挑战：RPC 的本质难题不是性能，而是对网络分区、超时、部分失败的处理。

Q4 TCP 的粘包/半包问题是什么？RPC 如何解决？ 重点▼
面试官视角

网络编程基础，体现对 TCP 流协议本质的理解。能说出 Netty LengthFieldBasedFrameDecoder 的候选人更优秀。

参考回答

TCP 是流协议，无消息边界。粘包：多个消息被合并成一个 TCP 包；半包：一个消息被拆分成多个 TCP 包。

RPC 解决方案：定长 Header + Body

Dubbo 协议帧格式（16 字节 Header）：
Magic(2B) | Flag(1B) | Status(1B) | RequestID(8B) | DataLength(4B) | Body(变长)
│ 魔数    │ 标志位  │ 响应状态  │ 请求唯一ID     │ Body 字节数    │ 序列化数据
先读 16 字节 Header，再按 DataLength 读 Body
→ Netty LengthFieldBasedFrameDecoder 实现帧解码

其他方案：固定分隔符（HTTP 用 \r\n）、固定包长（简单但浪费空间）。

Q5 RPC 的动态代理是如何工作的？ 重点▼
参考回答

Consumer 调用的接口是动态代理生成的 Stub。代理拦截方法调用，将调用信息（接口名、方法名、参数类型、参数值）序列化，通过 TCP 发送到 Provider，等待响应后反序列化返回。

  • ①Dubbo 默认用 Javassist 生成代理（比 JDK 动态代理快，避免反射调用）
  • ②也支持 JDK 动态代理（兼容性好）
  • ③异步调用时代理返回 null 或 CompletableFuture，通过 RequestID 匹配响应

综合题，考查对 Dubbo 全链路的掌握深度。能流利说出 10 步流程，并能说出每步对应的 Dubbo 组件，是高分回答。

参考回答
Consumer                              Provider
   │                                      │
1. 调用本地 Stub                          │
2. 序列化请求（Hessian/Protobuf）         │
3. 建立 TCP 连接（Netty）                 │
4. 发送网络请求 ─────────────────────────>│
                                       5. 解码帧/反序列化
                                       6. 找到 Invoker

02 Dubbo 架构 Q7–Q12
Q7 Dubbo 的四大角色各自的职责？ 高频▼
面试官视角

入门题，考查对 Dubbo 基础架构的了解。能说出"注册中心挂掉后 Consumer 可以继续调用"是加分项。

参考回答
  • Provider服务提供者：启动时向注册中心注册服务信息（接口、IP、端口、版本），监听端口等待 Consumer 调用
  • Consumer服务消费者：启动时从注册中心订阅服务，缓存 Provider 地址列表，发起调用
  • Registry注册中心（ZK/Nacos）：服务注册发现中枢，Provider 挂掉时通知 Consumer 更新列表
  • Monitor监控中心：统计调用次数、耗时、成功率，可选组件（Dubbo Admin）
关键：注册中心挂掉后 Consumer 可以继续调用（已缓存 Provider 列表），但无法感知新 Provider 上线或已有 Provider 下线。

Q11 Dubbo Filter 的作用和实现原理？如何自定义 Filter？ 重点▼
参考回答

Dubbo Filter 是责任链模式，通过 SPI Wrapper 机制实现，在 Invoker 外层包装多个 Filter 形成调用链。

  • Provider 侧TimeoutFilter（超时检测）、TokenFilter（鉴权）、ExceptionFilter（异常统一处理）
  • Consumer 侧ActiveLimitFilter（并发控制）、CacheFilter（结果缓存）、MonitorFilter（统计）
@Activate(group = CommonConstants.CONSUMER)  // 仅 Consumer 侧激活
public class TraceFilter implements Filter {
    public Result invoke(Invoker<?> invoker, Invocation inv) throws RpcException {
        RpcContext.getContext().setAttachment("traceId", UUID.randomUUID().toString());
        return invoker.invoke(inv);  // 传递到下一个 Filter
    }
}
// 在 META-INF/dubbo/org.apache.dubbo.rpc.Filter 配置：
// trace=com.example.TraceFilter
Q12 Dubbo 的配置优先级规则是什么？ 高频▼
面试官视角

实际配置问题，配置不生效是最常见的 Dubbo 使用困惑。能背出优先级规则并说出常见误区是满分回答。

参考回答

优先级（高→低）：

  • ①方法级 Consumer 配置（@Reference method 级别）
  • ②接口级 Consumer 配置（@Reference 级别）
  • ③接口级 Provider 配置（@Service 级别）
  • ④全局 Consumer 配置（dubbo.consumer.*）
  • ⑤全局 Provider 配置（dubbo.provider.*）

核心原则：Consumer 侧 > Provider 侧；方法级 > 接口级 > 全局。

常见误区：Consumer 未配置 timeout，以为会用 Provider 的配置，实际上 Consumer 全局有默认值（1000ms）会覆盖 Provider 的设置。

Q15 注册中心宕机后 Dubbo 还能正常调用吗？ 高频▼
参考回答

可以继续调用，因为 Dubbo 有多重保障：

  • ①内存缓存：Consumer 启动后将 Provider 列表缓存在 RegistryDirectory 内存中
  • ②本地文件缓存：Dubbo 将 Provider 地址持久化到本地文件（~/.dubbo/），重启时读取
  • ③TCP 长连接：已有的长连接不受注册中心影响，可继续正常请求
但：注册中心宕机期间，新 Provider 上线或 Provider 下线都无法被感知，调用可能路由到已下线的 Provider，需配合熔断/心跳处理。

Q17 一致性哈希算法的原理？虚拟节点解决什么问题？ 重点▼
参考回答

一致性哈希：将 0~2³² 映射成环，每个 Provider 映射到环上某点，请求按 key 哈希后顺时针找最近 Provider。好处：新增/删除节点只影响相邻节点（迁移数据最小化）。

虚拟节点：每个真实节点映射为多个虚拟节点（Dubbo 默认 160 个），解决节点分布不均导致的热点问题，使流量更均匀。

适用场景：相同 userId 或商品 ID 的请求打到同一 Provider，利用本地缓存提高命中率（有状态服务）。

Q19 Dubbo 超时机制是怎样的？Provider 和 Consumer 超时有何不同？ 高频▼
参考回答
  • Consumer 超时timeout 参数控制，默认 1000ms。超时抛 TimeoutException，Consumer 放弃等待结果
  • Provider 侧TimeoutFilter 检测执行时间，超时打印警告日志，但不中断方法执行（Java 无法安全中断执行中的线程）
  • 关键认知超时 ≠ 取消。Provider 可能仍在执行，Consumer 超时后若 Failover 重试，可能导致重复执行！
最佳实践：非幂等接口设 retries=0 + Failfast；幂等接口可设合理的 retries 和 timeout。

Q21 如何在 Dubbo 中实现限流和熔断？ 高频▼
参考回答

Dubbo 内置限流：executes（Provider 并发执行数）、actives（Consumer 并发调用数）。简单场景够用。

Sentinel 集成（推荐）：通过 dubbo-sentinel-adapter，Dubbo 的每次调用自动成为 Sentinel 的资源，支持：

  • QPS 限流令牌桶/滑动窗口算法，超阈值直接拒绝
  • 熔断降级错误率 > 阈值或慢调用比例高时自动熔断，半开探测恢复
  • 热点参数限流对某个 userId/商品 ID 的异常流量单独限流
  • 动态规则实时控制台动态修改规则，无需重启服务
Q22 Failover 重试和幂等性的关系？如何保证幂等？ 重点▼
面试官视角

分布式系统的经典问题，考查对幂等设计的掌握。能说出多种幂等方案并分析适用场景是满分回答。

参考回答

Failover 重试时切换到不同 Provider，第一次调用可能已在 Provider 执行完毕（只是响应丢失），重试导致重复执行。

幂等保证方案：

  • 唯一 ID 去重客户端生成唯一 requestId，服务端用 Redis 记录已处理的 ID，重复请求直接返回已有结果
  • 数据库唯一约束对 bizId 加唯一索引，重复插入 catch DuplicateKeyException 返回已有记录
  • 乐观锁update ... where version = #{version}，只有一次能成功
  • 状态机只有特定状态才能触发操作（如只有"待支付"状态才能扣款）

Q23 Dubbo 异步调用的两种方式？ 重点▼
参考回答
// 方式1：接口直接返回 CompletableFuture（推荐，Dubbo 2.7+）
public interface UserService {
    CompletableFuture<User> getUserAsync(Long id);
}
// Consumer 侧
userService.getUserAsync(1L)
    .thenAccept(u -> System.out.println(u.getName()))
    .exceptionally(e -> { log.error("failed", e); return null; });

// 方式2：@DubboReference async=true（旧方式，不推荐）
@DubboReference(async = true)
UserService userService;
userService.getUser(1L); // 立即返回 null
CompletableFuture<User> f = RpcContext.getContext().getCompletableFuture();
推荐方式1：类型安全，IDE 友好，与 CompletableFuture 生态无缝集成。
Q24 什么是泛化调用？有什么应用场景？ 重点▼
参考回答

泛化调用：Consumer 不需要引入 Provider 的接口 jar，直接通过接口名 + 方法名 + 参数调用服务，返回 Map 格式结果。

应用场景：API 网关（将 HTTP 请求转成 Dubbo 调用）、测试工具（Dubbo Admin 在线测试接口）、服务监控、Mock 服务

ReferenceConfig<GenericService> ref = new ReferenceConfig<>();
ref.setInterface("com.example.UserService");
ref.setGeneric("true");
GenericService gs = ref.get();
Object result = gs.$invoke(
    "getUser",
    new String[]{"java.lang.Long"},
    new Object[]{1L}
);
// result 是 Map<String, Object>
Q25 Dubbo 的版本（version）和分组（group）有什么区别？ 高频▼
参考回答
  • version（版本）同一接口的不同版本实现，用于接口升级。Consumer 可指定版本，version="*" 随机调用任意版本（金丝雀发布）
  • group（分组）同一接口的不同实现分组，用于功能分组或 A/B 测试。group="*" 或配置 MergeableCluster 可合并多组结果
// 蓝绿部署
@DubboService(version = "1.0")  // 当前稳定版
@DubboService(version = "2.0")  // 新版本（金丝雀）
@DubboReference(version = "2.0") // 指定调用新版（只有部分 Consumer 配置）
Q26 Dubbo 如何实现灰度发布？ 重点▼
参考回答
  • 权重灰度新版 Provider 配低权重（如 10），老版配高权重（90），随机负载均衡按比例分流
  • 标签路由Consumer 携带 tag 标签（通过 RpcContext 传递），匹配带相同 tag 的 Provider（按用户/环境隔离）
  • 条件路由在 Dubbo Admin 配置路由规则，如特定 IP 或用户的请求路由到灰度节点
  • version 金丝雀部分 Consumer 指定新版 version 测试，其他继续用旧版
Q27 Dubbo 3.x 的主要新特性是什么？ 重点▼
参考回答
  • Triple 协议基于 HTTP/2 + Protobuf，完全兼容 gRPC，支持跨语言、流式调用（Server/Client/Bi-Stream）、浏览器直连
  • 应用级服务发现以应用为粒度注册（而非接口），大幅减少注册中心数据量（10x+），解决大规模集群下注册中心压力
  • 云原生 & 服务网格原生支持 Kubernetes，可与 Istio 集成，支持 Proxyless Service Mesh
  • 性能提升序列化优化，启动速度提升，Nacos 成为默认推荐注册中心
Q28 什么是服务网格（Service Mesh）？和 Dubbo 有何关系？ 重点▼
参考回答

服务网格（如 Istio）：将服务通信能力（负载均衡、限流、熔断、可观测性）下沉到基础设施层（Sidecar 代理），业务代码无感知，语言无关。

  • 传统 DubboSDK 模式，治理逻辑在应用内，升级需重新部署业务服务
  • Dubbo ProxylessDubbo 3.x 支持不用 Sidecar，直接与控制平面（Istio xDS）通信，获得服务网格能力，减少网络跳转开销
  • 未来趋势两者融合，SDK 负责编程模型，Mesh 负责流量治理
Q29 Dubbo 和 Spring Cloud 的对比与选型建议？ 高频重点▼
面试官视角

微服务技术选型题，考查对两大生态的整体认知。能提到 Spring Cloud Alibaba 整合两者的候选人，体现出对业界实践的了解。

参考回答
维度DubboSpring Cloud
通信协议Dubbo Protocol（TCP 二进制）HTTP/REST（Feign）
性能高（二进制协议）中（HTTP JSON）
服务治理内置（负载均衡/容错/降级）依赖 Netflix OSS / Alibaba 组件
跨语言弱（Dubbo3 Triple 改善）强（HTTP 天然跨语言）

两者不是竞争关系：Spring Cloud Alibaba 将 Dubbo 集成到 Spring Cloud 体系（Nacos + Dubbo + Sentinel + Gateway），兼顾两者优势，是目前国内主流方案。
