01InnoDB 整体架构
三层结构：连接层 · 内存层 · 磁盘层

InnoDB 的架构可以分为三层。连接层（MySQL Server）负责 SQL 解析、优化和权限验证，存储引擎以下是 InnoDB 的范畴。内存层是性能的核心，所有读写都先经过内存。磁盘层保证数据持久化。

02Buffer Pool 深度
Buffer Pool 是 InnoDB 性能的核心

Buffer Pool 是 InnoDB 在内存中维护的页缓存（默认页大小 16 KB）。所有读写操作都必须先把磁盘上的页加载到 Buffer Pool，在内存中修改，再异步刷回磁盘。Buffer Pool 命中率直接决定了 IO 次数：命中率 99% 和 95% 在高并发下差距是数量级的。

-- 推荐配置：物理内存的 70%~80%（单实例）
innodb_buffer_pool_size = 12G      -- 16G 物理内存时
innodb_buffer_pool_instances = 8   -- 减少锁竞争，建议 ≥ 8（当 size > 1G 时）

-- 查看命中率（应 > 99%）
SHOW STATUS LIKE 'Innodb_buffer_pool_read%';
-- Innodb_buffer_pool_reads       = 从磁盘读的次数（miss）
-- Innodb_buffer_pool_read_requests = 总请求次数
-- 命中率 = 1 - reads / read_requests
改良 LRU：young 区 + old 区防止缓存污染

经典 LRU 有一个问题：全表扫描或批量预读会把大量"只读一次"的冷页塞进 LRU 头部，把真正的热页挤出去，这叫缓存污染。InnoDB 把 LRU 链表分成两段来解决这个问题：

  • young区链表前 5/8，存放真正的热页。只有在 old 区停留超过 1 秒后再次被访问的页，才会移到 young 区头部。
  • old区链表后 3/8，新读入的页先插到 old 区头部（midpoint insertion），不直接进 young 区。

全表扫描读入的页放在 old 区，扫描完后如果没有在 1 秒内被再次访问，不会进入 young 区，不污染热数据缓存。

innodb_old_blocks_pct  = 37    -- old 区占比，默认 37%（≈ 3/8）
innodb_old_blocks_time = 1000  -- 在 old 区停留多少毫秒后才允许晋升，默认 1000ms
三条链表：free / flush / LRU
free 链表
存放所有空闲页描述符。读新页时先从 free 链表取页；free 链表为空则从 LRU 链表尾部淘汰最久未使用的页。
flush 链表
存放所有脏页（被修改但尚未刷回磁盘的页）。Page Cleaner Thread 按一定策略从 flush 链表选页刷盘，刷完后页回到 free 链表。
LRU 链表
冷热分离的改良 LRU，管理页的淘汰顺序。一个页可以同时在 LRU 链表和 flush 链表中（脏页）。
03Change Buffer
写入非唯一二级索引时的缓冲优化

修改一条记录时，除了修改聚簇索引叶节点，还需要更新所有相关的二级索引。如果二级索引页不在 Buffer Pool 里，需要先从磁盘读进来，才能修改，这产生一次随机 IO。

Change Buffer 的思路：延迟合并——把对不在 Buffer Pool 里的二级索引页的修改操作缓存起来（不立即读入该页），等到该页因为其他原因被读入 Buffer Pool 时，再把缓冲的操作合并（merge）进去，消灭了写入时的随机 IO。

条件能否用 Change Buffer原因
非唯一二级索引（INSERT / UPDATE / DELETE）✅ 能无需立即判断唯一性，可以缓存
唯一二级索引（UNIQUE INDEX）❌ 不能插入必须立即读入页验证唯一性，无法缓存
聚簇索引（主键）❌ 不能查询经常读聚簇索引页，命中率高，无需 change buffer
全文索引 / 空间索引❌ 不能有专门的处理机制
Change Buffer 的 merge 时机
  • ①页被读入 Buffer Pool 时：读操作把该二级索引页加载进来，触发 merge，把 change buffer 里对该页的所有变更合并
  • ②后台线程定期 merge：Master Thread 每秒检查，选择一部分 change buffer 里的操作批量 merge
  • ③数据库正常关闭时：全量 merge change buffer
innodb_change_buffer_max_size = 25  -- change buffer 最多占 buffer pool 的比例，默认 25%
                                     -- 写多读少场景可适当调大（最大 50）
Change Buffer 不是银弹。如果数据库刚写入后立即有大量读操作来读这些二级索引页（写后读场景，如电商下单后立即查询），merge 触发非常频繁，change buffer 的好处完全抵消，反而增加了 merge 的开销。写多读少（如日志、数据导入）才是 change buffer 的适用场景。
04Redo Log 原理
为什么需要 Redo Log？

设想一个没有 Redo Log 的 InnoDB：每次 UPDATE 都必须把修改过的 16 KB 数据页从内存写回磁盘。这意味着——

  • 随机 IO一条 UPDATE 可能修改多个分散在磁盘各处的页（数据页 + 多个二级索引页），每个页都要定位磁盘物理位置写入，这是随机写，HDD 上耗时毫秒级，极慢。
  • 写放大严重哪怕只改了一行中的一个字段，也要把整个 16 KB 的页写回磁盘。IO 量远超实际修改量。
  • 并发瓶颈高并发下大量小写操作对应大量随机 IO，磁盘 IOPS 迅速成为瓶颈，TPS 上不去。

Redo Log 的解法：把随机写变成顺序写。不立即刷脏页，而是先把"做了什么修改"这条记录顺序追加到 redo log 文件里，脏页可以在之后批量异步写回。只要 redo log 落盘，即使数据库崩溃，重启时也能用 redo log 把内存中未来得及刷盘的修改重放一遍（crash recovery），数据不丢。

WAL —— Write-Ahead Logging

这就是 WAL（Write-Ahead Logging，先写日志）的核心思想：先写 redo log，再修改内存中的页，只要 redo log 落盘，事务就算提交成功，脏页可以在之后异步刷盘。

redo log 是物理日志（记录"某个数据页某个偏移量写了什么字节"），顺序追加到固定大小的文件，是顺序 IO，比随机写脏页快一个数量级。

innodb_log_file_size      = 1G   -- 单个 redo log 文件大小（8.0.30+ 改为 innodb_redo_log_capacity）
innodb_log_files_in_group = 2    -- redo log 文件组数量，循环写，默认 2 个（即 ib_logfile0 + ib_logfile1）
innodb_log_buffer_size    = 16M  -- log buffer 大小，默认 16 MB
innodb_flush_log_at_trx_commit — 三种模式
值行为数据安全性能适用场景
0每秒由后台线程刷一次 log buffer → OS cache → 磁盘⚠ 崩溃丢 ≤ 1 秒数据最快允许少量丢失（如日志表）
1（默认）每次提交：log buffer → fsync() → 磁盘✅ 不丢数据（ACID D）最慢生产环境，资金/订单类业务
2每次提交：log buffer → OS cache；每秒 fsync() 到磁盘⚠ MySQL 崩溃不丢；OS 崩溃丢 ≤ 1 秒中允许 OS 崩溃丢失的非关键业务
Checkpoint 机制

redo log 是循环覆盖的固定大小文件，写满后必须覆盖旧内容。但被覆盖的 redo log 对应的脏页必须先刷到磁盘，否则 crash 后无法用 redo log 恢复这些页。Checkpoint 就是这个推进脏页刷盘的机制：InnoDB 不断把 checkpoint_lsn 向前推进，checkpoint_lsn 之前的 redo log 对应的页都已刷盘，可以安全覆盖。

当 redo log 写速度追上 checkpoint 时（"redo log 快写满了"），InnoDB 会强制触发 checkpoint，同步刷脏页，这会产生明显的写停顿（write stall）。调大 innodb_log_file_size 可以延缓这个问题。

Group Commit（BLGC — Binlog Group Commit）

高并发下，多个事务的 redo log fsync() 可以合并成一次系统调用，大幅提升吞吐。MySQL 5.6+ 的 BLGC 将提交过程分为三个有序阶段，同阶段的多个事务排队批量处理：

  • Flush各事务把 binlog cache 写到 binlog 文件（OS cache）
  • Sync合并多个事务，一次 fsync() 把 binlog 从 OS cache 刷到磁盘
  • Commit按顺序对各事务调用存储引擎的 commit，更新 redo log 状态为 commit

组的大小由 binlog_group_commit_sync_delay（等待多少微秒）和 binlog_group_commit_sync_no_delay_count（等多少事务）控制。

05Binlog 日志
Binlog 是什么，解决什么问题？

Binlog（Binary Log，二进制日志）是 MySQL Server 层的日志，与存储引擎无关（InnoDB、MyISAM 都会写 binlog）。它记录的是所有对数据产生变更的 SQL 语句或行变化，以追加写的方式写入一系列二进制文件（mysql-bin.000001、mysql-bin.000002…），不循环覆盖（与 redo log 循环覆盖相反）。

主从复制
主库的 Binlog Dump Thread 把 binlog 事件流推送给从库。从库的 IO Thread 接收后写入 relay log，SQL Thread 重放 relay log 上的事件，使从库数据与主库保持同步。
PITR（时间点恢复）
全量备份 + 增量 binlog，可以把数据库恢复到任意时间点。例如误 DELETE 后，用全量备份还原，再重放 binlog 到删除操作前一秒，数据完整找回。
三种 Binlog 格式
格式 记录内容 优点 缺点 典型场景
STATEMENT 原始 SQL 语句 日志量小；可读性强 非确定性函数（NOW()、UUID()、RAND()）主从结果不一致 旧版本、低风险简单 DML
ROW 每行的前镜像（before image）和后镜像（after image） 精确，主从强一致；可做数据订阅（Canal/Debezium） 大批量 DML 日志量暴增（每行一条） MySQL 5.7+/8.0 默认，生产推荐
MIXED 默认 STATEMENT，遇到不确定性函数自动切换为 ROW 折中方案，安全性有保障 判断逻辑复杂，调试难度高 5.1–5.6 过渡时期 
-- 查看当前格式
SHOW VARIABLES LIKE 'binlog_format';
-- 推荐配置（MySQL 8.0 默认已是 ROW）
binlog_format = ROW
binlog_row_image = FULL   -- full / minimal / noblob，默认 full（完整前后镜像）
Binlog Cache 与 sync_binlog

事务执行期间，binlog 事件先写入 binlog cache（每个 session 独立，内存中），事务提交时才 flush 到 binlog 文件。这个设计避免了事务中途产生不完整的 binlog 记录。

sync_binlog 值行为数据安全性能
0由 OS 决定何时 fsync，MySQL 不主动调用⚠ OS 崩溃丢多个事务最快
1（推荐）每次事务提交都 fsync binlog 到磁盘✅ 最安全，不丢数据最慢
N（N>1）累积 N 次提交后才 fsync 一次⚠ 崩溃丢最多 N 个事务较快
sync_binlog          = 1       -- 生产环境强烈推荐
binlog_cache_size    = 32K     -- 单个 session 的 binlog cache 大小，超出则写临时文件
max_binlog_size      = 1G      -- 单个 binlog 文件最大大小，超出后自动 rotate
Binlog vs Redo Log —— 关键区别
维度BinlogRedo Log
所属层MySQL Server 层（引擎无关）InnoDB 存储引擎层
日志类型逻辑日志（SQL 或行变化）物理日志（页偏移量 + 字节内容）
写入方式追加写，不覆盖，文件 rotate循环写，固定大小，覆盖旧日志
主要用途主从复制 · PITR · 数据订阅Crash Recovery（实例崩溃恢复）
写入时机事务提交时统一 flush事务执行中持续追加（prepare 阶段落盘）
保留时间由 binlog_expire_logs_seconds 控制，默认 30 天固定文件大小，循环覆盖
sync_binlog=1 且 innodb_flush_log_at_trx_commit=1 才是双重安全保障。只设其中一个，另一个出问题时数据仍会丢失。生产关键业务（资金、订单）必须两者都设为 1，代价是每次提交都要等两次 fsync（binlog + redo log），可用 Group Commit 缓解吞吐损失。
06Undo Log 原理
两个核心用途：回滚 + MVCC

undo log 是逻辑日志（记录"把这条记录改回去"的逆操作），与 redo log 的物理日志形成对比。undo log 有两个独立用途：

事务回滚
事务执行过程中，每次修改前把原始值写入 undo log。如果事务回滚，按 undo log 逆向执行，把数据恢复到修改前的状态。
MVCC 版本链
每次修改都生成一个新版本，旧版本保留在 undo log 里，用 DB_ROLL_PTR 指针串成版本链。读操作通过 ReadView 沿版本链找到对自己可见的版本，实现无锁读。
版本链结构

InnoDB 每行记录有两个隐藏列：DB_TRX_ID（最后修改该行的事务 ID）和 DB_ROLL_PTR（指向 undo log 的指针）。每次 UPDATE 产生一条 undo log，链接在前一版本后面，形成版本链。

当前行（trx_id=100）→ undo log（trx_id=80）→ undo log（trx_id=60）→ 最原始版本
           ↑ DB_ROLL_PTR             ↑ DB_ROLL_PTR

读操作创建 ReadView，按事务可见性规则沿版本链找到第一个对自己可见的版本返回，整个过程不加锁。

Purge 线程：版本链的清理

版本链会不断增长。当所有活跃事务都不再需要某个旧版本时（即该版本对任何当前事务都不可见），Purge Thread 可以安全地删除这条 undo log，释放空间。

长事务导致 undo log 膨胀。一个长事务开启后，它的 ReadView 会一直"保留"着事务开始时的活跃事务列表。只要这个长事务不结束，Purge Thread 就无法清理其 ReadView 开始时刻之后产生的所有旧版本，undo log 持续膨胀，可能占用数 GB 磁盘空间，并拖慢 Purge 速度影响所有事务。
排查：SELECT * FROM information_schema.INNODB_TRX WHERE time_to_sec(timediff(now(), trx_started)) > 60;
07一条 UPDATE 语句的完整执行流程
以 UPDATE orders SET status=2 WHERE id=1001 为例

这是 MySQL 最核心的执行路径，涉及 Server 层、InnoDB 内存层、磁盘层和两套日志系统。理解这个流程，才能真正理解 InnoDB 的数据安全保证从何而来。

UPDATE 完整执行路径 · 两阶段提交（2PC）
两阶段提交（2PC）保证了什么

redo log 和 binlog 是两套独立的日志系统（redo 在 InnoDB 内，binlog 在 Server 层）。如果没有 2PC，可能出现：

  • →写了 redo 但崩溃在写 binlog 前：redo 能恢复数据，但 binlog 里没有这条记录，主从复制的从库会丢这条更新
  • →写了 binlog 但 redo 没写完：binlog 有记录，但 InnoDB 内部数据未持久化，主库崩溃恢复后数据不一致

2PC 流程：① redo log 写 prepare 状态并 fsync → ② binlog 写入并 fsync → ③ redo log 写 commit 状态。Crash Recovery 规则：若 redo log 有 prepare 但 binlog 里有对应 xid → 提交；若 binlog 里没有 → 回滚。这保证了 redo 和 binlog 的最终一致性。

Crash Recovery 的关键判断依据是 binlog 里是否存在对应的 xid。redo log 记录了 XID，binlog 的每个事务结尾也有 XID_LOG_EVENT。恢复时 InnoDB 扫描 redo log 找到 prepare 状态的事务，去 binlog 里对应位置核查 xid 是否存在，以此决定提交还是回滚。
08一条 SELECT 语句的完整执行流程
以 SELECT * FROM orders WHERE user_id=1001 ORDER BY created_at DESC LIMIT 10 为例

SELECT 的路径比 UPDATE 长，涉及的层次更多。理解这个流程，是优化慢查询的基础。

①
连接器（Connector）
验证用户名密码，检查权限，从连接池取连接（或新建）。连接建立后，权限信息缓存在连接对象中，直到连接断开才失效。
②
Parser — 词法分析 + 语法分析
词法分析：把 SQL 字符串拆成 token（SELECT、*、FROM、orders…）。语法分析：按 SQL 语法规则构建 AST（抽象语法树）。若 SQL 语法有误，在此报错：You have an error in your SQL syntax。
③
Analyzer — 语义分析
检查表名是否存在、列名是否合法、权限是否足够。语法正确但语义错误在此报：Table 'db.orders' doesn't exist。
④
Optimizer — 基于代价的优化
核心工作：估算各执行路径的代价（IO 次数 + CPU 消耗），选择最优方案。主要决策：
· 选哪个索引：user_id 上的索引 vs (user_id, created_at) 联合索引 vs 全表扫描
· 是否需要回表：如果联合索引覆盖了所有 SELECT 列，直接从索引返回
· ORDER BY 能否用索引排序：若索引已按 created_at 排好序，跳过 filesort
· 是否用 ICP / MRR：根据 optimizer_switch 开关决定

代价估算依赖统计信息（mysql.innodb_table_stats），统计信息过期可能导致错误执行计划，需 ANALYZE TABLE 更新。
⑤
Executor — 驱动存储引擎
再次检查查询权限，调用 InnoDB 的 handler API，按执行计划逐行或逐批获取数据。Executor 是存储引擎无关的抽象层，可以驱动 InnoDB、MyISAM 等任何引擎。
⑥
InnoDB — 创建 ReadView（MVCC）
开启 MVCC 快照读。ReadView 包含四个关键字段：
· m_ids：ReadView 创建时所有活跃（未提交）的事务 ID 列表
· min_trx_id：m_ids 的最小值
· max_trx_id：ReadView 创建时下一个将分配的事务 ID（比当前最大已分配 ID 大 1）
· creator_trx_id：创建此 ReadView 的事务自身 ID

RC（Read Committed）：每次 SELECT 都创建新的 ReadView，能看到每次 SELECT 前已提交的最新数据（不可重复读）
RR（Repeatable Read，默认）：同一事务内只在第一次 SELECT 时创建 ReadView，整个事务看到的数据快照不变（可重复读）
⑦
InnoDB — B+树索引遍历
按执行计划，在二级索引（如 idx_user_id）的 B+树上定位到 user_id=1001 的第一个叶节点，然后沿叶节点链表顺序扫描，直到 user_id 不等于 1001 为止。
⑧
InnoDB — Buffer Pool 查找 + 磁盘读
对每个需要访问的数据页：
· Buffer Pool 命中：直接从内存读，更新 LRU 链表（young 区热数据）
· 未命中（page miss）：IO Thread 从 .ibd 文件读入 16 KB 页，通过 LRU midpoint 插入 old 区，不污染 young 区热数据
同时，InnoDB 会触发线性预读（连续读了同一 extent 中的若干页时，预读剩余页）或随机预读（同一 extent 被读的页达到阈值时预读）。
⑨
InnoDB — MVCC 版本可见性判断
对每一行，通过 ReadView 判断可见性：
· DB_TRX_ID < min_trx_id：该版本由更早的已提交事务写入 → 可见
· DB_TRX_ID >= max_trx_id：该版本由 ReadView 创建后才开始的事务写入 → 不可见，沿 undo log 找旧版本
· DB_TRX_ID in m_ids：该版本由创建 ReadView 时仍活跃的事务写入，尚未提交 → 不可见，沿 undo log 找旧版本
· 否则（已提交且在 ReadView 范围内）→ 可见
沿 undo log 版本链不断往旧找，直到找到第一个可见版本。
⑩
InnoDB — ICP 过滤 + MRR 优化回表
· ICP（Index Condition Pushdown）：若 WHERE 中有二级索引包含的列但不是定位列（如 created_at 范围），在引擎层先过滤，减少回表次数
· 回表：用二级索引叶节点里的主键，再去聚簇索引取完整行
· MRR：若回表行数多，先收集所有主键值排序，再批量顺序回表
11
Server 层 — 排序 / 分组 / 裁剪
从 InnoDB 拿到满足 WHERE 条件的行集后：
· ORDER BY created_at DESC：若执行计划选了 (user_id, created_at) 联合索引且方向一致 → 无 filesort；否则在 sort_buffer 内排序
· LIMIT 10：截取前 10 行，若用了索引排序，读满 10 行后立即停止扫描（early termination）
· GROUP BY / HAVING / JOIN 在此处理
12
返回结果集
结果集按网络协议（MySQL Client/Server Protocol）分包发回客户端。大结果集分批发送，不会一次性放入内存。连接保持直到所有数据发送完毕或客户端关闭连接。
MySQL 8.0 彻底移除了 Query Cache。Query Cache 在 5.x 时代存在于 Server 层，命中则直接返回缓存结果。但因为任何对表的写操作都会使该表所有缓存失效，高并发写入场景下 Query Cache 的锁竞争反而成为性能瓶颈，最终在 8.0 中被移除。应用层缓存（Redis）才是正解。
09Doublewrite Buffer
解决 Partial Write 问题

InnoDB 的页大小是 16 KB，而操作系统的文件系统块通常是 4 KB（或更小）。刷脏页时需要写 4 次 4 KB 的块才能完成一个 16 KB 的页写入。如果数据库在写入过程中崩溃（比如写到第 2 个块时断电），这个页会变成部分写（Partial Write）——页头写了新内容，页尾还是旧内容，整个页损坏，无法通过 redo log 恢复。

redo log 里记录的是增量变更（某偏移写了什么字节），它的 apply 前提是原始页是完整的。一个损坏的页无法直接 apply redo log。

Doublewrite 的写入流程
①
写入共享表空间的 doublewrite 区
Page Cleaner 准备刷脏页时，先把这批脏页顺序写入 ibdata1（或独立 doublewrite 文件，8.0.20+）中的 doublewrite 区域。这是顺序 IO，代价小。
②
fsync 确认落盘
调用 fsync 确保 doublewrite 区的数据已真正写到磁盘。
③
写入各自的 .ibd 文件
把脏页写到它们在 .ibd 数据文件中的真实位置（随机 IO）。若此时崩溃，.ibd 里的页可能损坏，但 doublewrite 区里有完整备份。

Crash Recovery：InnoDB 启动时检测到 .ibd 里的页损坏（checksum 校验失败），直接用 doublewrite 区的备份还原该页，然后 apply redo log，恢复完整数据。

-- 控制 doublewrite（默认开启，生产环境不建议关）
innodb_doublewrite = ON

-- MySQL 8.0.20+ 独立 doublewrite 文件，不再污染 ibdata1
innodb_doublewrite_dir  = ./
innodb_doublewrite_files = 2
在使用 ZFS / Btrfs 等具备原子写能力的文件系统时，可以关闭 doublewrite（innodb_doublewrite=OFF）消除约 5%~10% 的写放大，因为这类文件系统本身保证写操作原子性，不存在 partial write 问题。
10后台线程职责
四类核心后台线程
Master Thread
InnoDB 的总调度线程，每秒或每 10 秒执行一次循环：
· 每秒：flush log buffer → redo log（无论事务是否提交）；合并 change buffer（视 IO 压力）；刷脏页（视脏页比例）
· 每 10 秒：批量刷脏页；合并剩余 change buffer；删除无用 undo log；checkpoint
IO Thread
处理 AIO（Async IO）请求，负责实际的磁盘读写：
· Read Thread（默认 4 个）：处理异步读请求（预读、缺页读）
· Write Thread（默认 4 个）：处理异步写请求（脏页刷盘）
· Log Thread：redo log 的异步 IO
· Insert Buffer Thread：change buffer 合并的 IO
Purge Thread
清理已提交事务不再需要的 undo log，回收 undo tablespace 空间。事务提交后，undo log 并不立即删除，Purge Thread 异步判断哪些版本已无活跃事务依赖，然后批量清理。

默认 4 个 Purge Thread，高并发写入场景可调大：innodb_purge_threads=4
Page Cleaner Thread
专门负责刷脏页，5.6+ 从 Master Thread 中分离出来。从 flush 链表中选出脏页，写入 doublewrite 区后刷到 .ibd。

刷脏策略受 innodb_io_capacity（正常刷脏速率）和 innodb_io_capacity_max（紧急刷脏速率）控制。
默认 1 个，可增加：innodb_page_cleaners=4
InnoDB 架构理解要点总结：
· 写性能来自 WAL（顺序写 redo log）+ Change Buffer（缓存二级索引写入）+ 脏页异步刷盘
· 读性能来自 Buffer Pool（内存命中）+ AHI（热点索引 Hash 加速）+ MRR（顺序化回表 IO）
· 数据安全来自 redo log 持久化 + 两阶段提交 + doublewrite
· MVCC 无锁读来自 undo log 版本链 + ReadView 可见性判断
· 空间回收来自 Purge Thread 异步清理 undo log
