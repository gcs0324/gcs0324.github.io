01MyBatis 是什么
半自动 ORM

MyBatis 是一个持久层框架，负责把 Java 对象和 SQL 结果之间的转换处理掉，但 SQL 本身由开发者写。这和 Hibernate 的"全自动 ORM"（框架自动生成 SQL）不同。

称它"半自动"的原因：开发者负责写 SQL，MyBatis 负责参数绑定和结果映射。SQL 可以完全手控，适合复杂查询、慢查询优化场景。

对比维度JDBC（原生）MyBatisHibernate / JPA
SQL 由谁写开发者开发者框架自动生成（也可自定义）
结果映射手动 rs.getString()自动映射到 POJO自动映射
动态 SQL字符串拼接XML / 注解 标签Criteria API / JPQL
适用场景极简单或追求零依赖复杂 SQL、报表、分库分表简单 CRUD、领域驱动设计
学习曲线低（但重复代码多）低到中高（Proxy、Session、缓存复杂）
MyBatis 更准确的名字应该叫 SQL 映射框架（SQL Mapper Framework）。它不试图隐藏 SQL，而是让 SQL 写起来更优雅、参数绑定更安全、结果解析更方便。
02完整执行流程
从方法调用到 SQL 返回

一次 userMapper.selectById(1L) 的完整链路分为三段：初始化阶段（启动时完成，只走一次）、代理拦截阶段（每次调用时触发）、SQL 执行阶段（每次调用时执行）。

  • ①启动时：读取 mybatis-config.xml + 所有 Mapper XML，解析成 MappedStatement 对象，缓存进 Configuration。每个 SQL 片段对应一个 MappedStatement，key 是 接口全限定名.方法名
  • ②获取 SqlSession：通过 SqlSessionFactory.openSession() 创建，每个 SqlSession 独立持有一份连接和一级缓存
  • ③Mapper 代理：sqlSession.getMapper(UserMapper.class) 返回 JDK 动态代理对象；调用方法时进入 MapperProxy.invoke()
  • ④查 MappedStatement：从 Configuration 按 id 取出目标 SQL 的所有配置（参数类型、结果映射、SQL 模板）
  • ⑤Executor 执行：调用 Executor.query() 或 update()；先查一级缓存，命中则直接返回
  • ⑥StatementHandler：创建 JDBC PreparedStatement，调用 ParameterHandler 设置 ? 参数
  • ⑦执行 SQL：JDBC 发出查询，拿到 ResultSet
  • ⑧ResultSetHandler：将 ResultSet 按 resultMap 规则映射成 Java 对象，存入一级缓存，返回给调用方

03四大核心对象
Executor / StatementHandler / ParameterHandler / ResultSetHandler

MyBatis 把 SQL 执行拆成四个独立对象，每个对象负责一件事。插件（Interceptor）只能拦截这四个对象的方法，不能拦截其他。

Executor
最顶层的执行器，负责调度整个查询/更新流程。三种实现：
· SimpleExecutor：每次都创建新 Statement，用完即关
· ReuseExecutor：复用相同 SQL 的 Statement
· BatchExecutor：批量 update，多条 SQL 攒在一起发送
StatementHandler
负责创建 JDBC Statement，三种实现：
· SimpleStatementHandler：对应 JDBC Statement（无 ?）
· PreparedStatementHandler：对应 PreparedStatement（有 ?，默认）
· CallableStatementHandler：调用存储过程
ParameterHandler
把 Java 方法的入参设置到 PreparedStatement 的 ? 占位符上。底层通过 TypeHandler 做 Java 类型 → JDBC 类型的转换，比如 LocalDate → DATE。
ResultSetHandler
把 JDBC ResultSet 映射成 Java 对象。先按 resultMap 规则找列映射，再通过 TypeHandler 做类型转换，最后填充到 POJO 字段。嵌套结果（association/collection）也在这里合并。
记忆口诀：Executor 调度 → StatementHandler 创建语句 → ParameterHandler 设参数 → SQL 执行 → ResultSetHandler 映射结果。插件可拦截这四个的任意方法。
04XML 映射文件
resultMap — 精确控制列到字段的映射

resultType 只适合列名和字段名完全一致的简单查询。一旦有别名、嵌套对象、一对多关系，就需要 resultMap。

<resultMap id="userMap" type="User">
  <id     column="user_id"   property="id"/>
  <result column="user_name" property="name"/>
  <result column="create_time" property="createTime"/>
</resultMap>
  • id<id> 标注主键列，MyBatis 用它做对象去重（在嵌套查询里很关键）
  • result<result> 标注普通列，column 是 SQL 列名，property 是 Java 字段名
association — 多对一（嵌套单个对象）

查询订单时顺带把用户信息也带出来，用户是"单个对象"，用 association。

<resultMap id="orderMap" type="Order">
  <id column="order_id" property="id"/>
  <result column="amount" property="amount"/>
  <!-- 多对一：一个订单对应一个用户 -->
  <association property="user" javaType="User">
    <id     column="user_id"   property="id"/>
    <result column="user_name" property="name"/>
  </association>
</resultMap>
collection — 一对多（嵌套集合）

查询用户时顺带把他的所有订单带出来，订单是"集合"，用 collection。

<resultMap id="userWithOrders" type="User">
  <id column="user_id" property="id"/>
  <result column="user_name" property="name"/>
  <!-- 一对多：一个用户有多个订单 -->
  <collection property="orders" ofType="Order">
    <id     column="order_id" property="id"/>
    <result column="amount"   property="amount"/>
  </collection>
</resultMap>
N+1 问题：如果先查出 N 条用户，再为每个用户单独查订单，就会发 N+1 条 SQL。解决方法：用 JOIN 一次性查出（嵌套结果 resultMap），或开启懒加载（fetchType="lazy"）只在真正访问 orders 字段时才查。
05动态 SQL
根据运行时条件拼接 SQL

动态 SQL 解决的是 JDBC 时代常见的"字符串拼接漏洞"问题——根据参数是否为空决定是否加 WHERE 条件。MyBatis 用 OGNL 表达式 + XML 标签在框架层完成拼接，生成的永远是合法 SQL。

标签作用常见场景
<if>条件判断参数不为空才加条件：AND name = #{name}
<where>智能 WHERE包裹多个 if，自动处理开头多余的 AND/OR
<set>智能 SETUPDATE 时自动去掉末尾多余的逗号
<foreach>循环IN 查询、批量 INSERT
<choose/when/otherwise>多选一（like switch）根据传入参数类型决定用哪个条件
<trim>通用裁剪自定义要去掉的前缀/后缀，where/set 底层就是 trim 实现的
<select id="list" resultType="User">
  SELECT * FROM user
  <where>
    <if test="name != null and name != ''">
      AND name LIKE CONCAT('%', #{name}, '%')
    </if>
    <if test="status != null">
      AND status = #{status}
    </if>
  </where>
</select>
foreach — IN 查询与批量插入
<!-- IN 查询 -->
<select id="listByIds" resultType="User">
  SELECT * FROM user WHERE id IN
  <foreach collection="ids" item="id" open="(" separator="," close=")">
    #{id}
  </foreach>
</select>

<!-- 批量插入（单条 SQL，效率远高于循环单插）-->
<insert id="batchInsert">
  INSERT INTO user(name, age) VALUES
  <foreach collection="list" item="u" separator=",">
    (#{u.name}, #{u.age})
  </foreach>
</insert>
foreach 批量插入要注意 MySQL 单条 SQL 大小限制（默认 max_allowed_packet = 4MB），列表超大时建议每次 500 条分批提交。
06缓存机制
一级缓存（SqlSession 级，默认开启）

一级缓存的作用域是单个 SqlSession。同一个 SqlSession 内，相同的 SQL + 相同的参数，第二次查询直接返回缓存里的对象，不再发 SQL。

  • 命中条件同一 SqlSession + 相同 statementId + 相同参数 + 相同 RowBounds（分页偏移量）
  • 失效时机执行了 insert/update/delete（任何写操作都会清空本 SqlSession 的一级缓存）；调用 sqlSession.clearCache()；SqlSession 关闭
  • Spring 整合后Spring 每次方法调用都会创建新的 SqlSession（通过 SqlSessionTemplate），一级缓存实际上在大多数场景下失效。除非当前方法在同一事务内
二级缓存（Mapper 级，需手动开启）

二级缓存的作用域是同一个 Mapper（namespace），跨 SqlSession 共享。SqlSession 关闭/提交后，数据才会从一级缓存写入二级缓存。

  • 开启方式mybatis-config.xml 开 cacheEnabled=true（默认 true），再在 Mapper XML 加 <cache/> 标签
  • 失效时机同 namespace 下任意 insert/update/delete 操作，整个 namespace 的二级缓存全部清空
  • 脏读风险多表 JOIN 查询时，若结果涉及 B 表，但缓存在 A 的 namespace 下，当 B 表更新后 A 的缓存不会失效，导致脏读。实际项目中二级缓存很少开启

07插件机制
Interceptor — 拦截四大对象

MyBatis 插件基于 JDK 动态代理，在四大对象的方法上套一层代理。可以在 SQL 执行前后插入自定义逻辑，最典型的是分页插件（PageHelper）和 SQL 审计日志。

  • 可拦截目标Executor（query/update/commit 等）、StatementHandler（prepare/query）、ParameterHandler（setParameters）、ResultSetHandler（handleResultSets）
  • 声明方式实现 Interceptor 接口，加 @Intercepts + @Signature 注解声明要拦截哪个类的哪个方法
  • 执行顺序多个插件按注册顺序依次套代理，形成调用链（类似 Servlet Filter）
@Intercepts({
  @Signature(type = StatementHandler.class,
             method = "prepare",
             args = {Connection.class, Integer.class})
})
public class SqlPrintPlugin implements Interceptor {
  @Override
  public Object intercept(Invocation invocation) throws Throwable {
    // 在 SQL 执行前打印
    StatementHandler handler = (StatementHandler) invocation.getTarget();
    System.out.println("SQL: " + handler.getBoundSql().getSql());
    return invocation.proceed(); // 继续执行
  }
}
PageHelper 分页原理

PageHelper 是最常用的 MyBatis 分页插件。它拦截 Executor.query()，在 SQL 执行前把原 SQL 改写成带 LIMIT offset, size 的分页 SQL，同时执行一条 COUNT(*) 查询总条数。

  • 使用方式PageHelper.startPage(pageNum, pageSize) 先设置分页参数（存入 ThreadLocal），紧接着的第一条查询自动应用分页
  • 底层拦截拦截 StatementHandler.prepare()，取出 ThreadLocal 里的分页参数，用 JSqlParser 改写 SQL
  • 注意事项startPage 之后必须紧跟查询，中间不能有其他查询，否则分页参数会被错误的查询消费
08Spring 整合
SqlSessionTemplate — 线程安全的 SqlSession

原生 SqlSession 不是线程安全的，不能作为单例 Bean 注入。SqlSessionTemplate 是 MyBatis-Spring 提供的代理类，每次调用时从 Spring 事务上下文里取当前线程绑定的 SqlSession，没有则创建新的，使用完自动关闭。

  • 线程安全原理每个方法调用都通过 SqlSessionUtils.getSqlSession() 获取 Session，该方法先检查 Spring 事务同步器里是否已绑定，有则复用，无则新建
  • 事务一致性在 @Transactional 方法内，多个 Mapper 操作共享同一个 SqlSession（同一个 Connection），保证同一事务
MapperScannerConfigurer — 自动扫描注册 Mapper

@MapperScan("com.example.mapper") 背后的原理：Spring 启动时扫描指定包下所有接口，为每个接口创建一个 MapperFactoryBean，注册到 BeanFactory。运行时 getBean(UserMapper.class) 实际返回的是 JDK 动态代理对象（MapperProxy），调用方法时走 MyBatis 执行流程。

  • MapperFactoryBean实现了 FactoryBean，getObject() 返回 sqlSession.getMapper(mapperInterface) 的代理对象
  • @Mapper vs @MapperScan@Mapper 标注单个接口；@MapperScan 批量扫描，两者效果相同，不要重复使用
Spring Boot 已自动配置 SqlSessionFactory 和 MapperScannerConfigurer，只需加 mybatis-spring-boot-starter 依赖 + 配置数据源即可，无需手动写 XML 配置。
