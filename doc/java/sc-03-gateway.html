01Spring Cloud Gateway 核心架构
Gateway 是什么，解决什么问题

API 网关是所有外部请求的统一入口，把原本各服务自己处理的横切关注点（认证、限流、日志、监控、路由）统一在网关层处理，服务内部只专注业务逻辑。

网关承担的职责
· 路由转发（按规则转发到对应服务）
· 身份认证（JWT 解析 / Token 验证）
· 权限校验（角色/资源权限）
· 限流（防止服务被打垮）
· 请求日志 / 链路 Trace ID 注入
· 协议转换（HTTP → gRPC）
· 灰度发布 / 金丝雀路由
Gateway vs Zuul
Gateway 基于 Spring WebFlux + Reactor + Netty，全异步非阻塞，一个线程可以处理大量并发请求，吞吐远高于 Zuul（同步 Servlet 模型）。

Zuul 2.x 虽然也改用异步，但 Spring 官方未集成，实际生产中 Gateway 已是默认选择。

02路由配置与断言（Predicate）
路由三要素：id / predicates / filters

Gateway 的路由配置由三部分组成：id（唯一标识）、predicates（断言，决定哪些请求匹配）、filters（过滤器，对匹配的请求做处理）。

spring:
  cloud:
    gateway:
      routes:
        - id: order-service-route
          uri: lb://order-service          # lb:// 表示从 Nacos 负载均衡获取实例
          predicates:
            - Path=/api/order/**           # 路径断言：匹配 /api/order/ 开头
            - Method=GET,POST              # 方法断言
            - Header=X-Request-Version,v2  # Header 断言
          filters:
            - StripPrefix=1                # 去掉路径前缀 /api，转发 /order/**
            - AddRequestHeader=X-Service-Name, order-service
            - RequestRateLimiter=...       # 限流过滤器

        - id: user-service-route
          uri: lb://user-service
          predicates:
            - Path=/api/user/**
          filters:
            - StripPrefix=1
常用内置断言（Predicate Factory）
断言示例说明
Path- Path=/api/**最常用，按请求路径匹配（支持 Ant 风格通配符）
Method- Method=GET,POST按 HTTP 方法匹配
Header- Header=X-Token, \d+Header 名 + 正则值匹配
Query- Query=version, v2URL 查询参数匹配（灰度发布常用）
Host- Host=**.example.com按 Host 域名匹配
Weight- Weight=group1, 80按权重分流（灰度：80% 旧版 + 20% 新版）
Before/After/Between- After=2024-01-01T00:00:00+08:00时间范围匹配
03Filter 过滤器链
Global Filter vs GatewayFilter
GlobalFilter（全局过滤器）
对所有路由生效，无需在每个路由上配置。通过实现 GlobalFilter 接口自定义：

· 认证 Filter（解析 JWT，设置用户上下文）
· 日志 Filter（记录请求/响应日志）
· Trace Filter（注入 TraceId 到 Header）

用 @Order 或 Ordered 接口控制执行顺序，数字越小优先级越高。
GatewayFilter（路由过滤器）
只对特定路由生效，在路由配置的 filters 下声明：

· StripPrefix=1：去掉路径前 1 段
· AddRequestHeader：添加请求 Header
· AddResponseHeader：添加响应 Header
· RewritePath：重写请求路径
· RequestRateLimiter：限流（需配 Redis）
· Retry：失败重试配置
自定义全局认证 Filter 示例
@Component
@Order(-100)   // 最高优先级，最先执行
public class AuthGlobalFilter implements GlobalFilter {

    private static final String TOKEN_HEADER = "Authorization";
    // 白名单：不需要认证的路径
    private static final List<String> WHITE_LIST = List.of("/api/user/login", "/api/user/register");

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String path = exchange.getRequest().getPath().value();

        // 白名单放行
        if (WHITE_LIST.stream().anyMatch(path::startsWith)) {
            return chain.filter(exchange);
        }

        // 获取 Token
        String token = exchange.getRequest().getHeaders().getFirst(TOKEN_HEADER);
        if (token == null || !token.startsWith("Bearer ")) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }

        // 解析 JWT，验证合法性
        try {
            String userId = JwtUtil.parseUserId(token.substring(7));
            // 把用户 ID 放入 Header 传给下游服务
            ServerHttpRequest mutatedRequest = exchange.getRequest().mutate()
                .header("X-User-Id", userId)
                .build();
            return chain.filter(exchange.mutate().request(mutatedRequest).build());
        } catch (Exception e) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }
    }
}
04OpenFeign 原理与使用
OpenFeign 是什么？解决了什么痛点？

服务间调用最原始的方式是用 RestTemplate，需要手动拼 URL、序列化/反序列化、处理错误。OpenFeign 让你像调用本地接口一样调用远程服务：

// 1. 定义 Feign 接口（只写接口，不写实现）
@FeignClient(name = "user-service",   // 对应 Nacos 注册的服务名
             fallback = UserFeignFallback.class)  // Sentinel 降级
public interface UserFeignClient {

    @GetMapping("/user/{id}")
    UserDTO getUserById(@PathVariable("id") Long id);

    @PostMapping("/user/batch")
    List<UserDTO> getUsersByIds(@RequestBody List<Long> ids);
}

// 2. 注入使用（像调本地方法）
@Service
public class OrderService {
    @Autowired
    private UserFeignClient userFeignClient;

    public OrderDetailDTO getOrderDetail(Long orderId) {
        Order order = orderRepo.findById(orderId).orElseThrow();
        UserDTO user = userFeignClient.getUserById(order.getUserId()); // 远程调用
        return OrderDetailDTO.of(order, user);
    }
}
OpenFeign 的底层原理

Feign 的核心是动态代理：

①
扫描 @FeignClient 接口
Spring Boot 启动时，@EnableFeignClients 触发扫描，找到所有 @FeignClient 注解的接口。
②
生成动态代理对象
Feign 通过 JDK 动态代理为每个接口生成代理类，注册到 Spring IOC 容器。调用接口方法时，实际执行代理的 invoke 方法。
③
方法元数据解析
代理的 invoke 根据方法上的 @GetMapping/@PostMapping 等注解，构建 HTTP 请求（方法、路径、参数、请求体）。
④
LoadBalancer 选实例
从 Nacos 获取 user-service 的实例列表，Spring Cloud LoadBalancer 按策略（轮询/权重）选一个实例，得到真实的 IP:Port。
⑤
发起 HTTP 请求 → 响应反序列化
通过 HTTP Client（默认 JDK URLConnection，推荐换成 OkHttp3 或 Apache HttpClient5）发起请求，响应 JSON 通过 Jackson 反序列化成返回类型。
推荐配置：超时 + OkHttp3 + 日志
spring:
  cloud:
    openfeign:
      client:
        config:
          default:                          # 全局配置
            connect-timeout: 2000           # 连接超时 2s
            read-timeout: 5000              # 读超时 5s
            logger-level: BASIC             # NONE/BASIC/HEADERS/FULL
          user-service:                     # 针对特定服务单独配置
            read-timeout: 3000
      httpclient:
        ok-http:
          enabled: true                     # 启用 OkHttp3（需引入 feign-okhttp 依赖）

logging:
  level:
    com.example.feign: DEBUG                # 开启 Feign 调用日志
05负载均衡策略
Spring Cloud LoadBalancer（取代 Ribbon）

Spring Cloud 2020.x 起，内置 Spring Cloud LoadBalancer 作为客户端负载均衡的默认实现，替代了已废弃的 Ribbon。LoadBalancer 从 Nacos 获取服务实例列表后，按策略选择一个实例转发请求。

RoundRobinLoadBalancer（默认）
轮询策略：按顺序依次选择实例。所有实例权重相同时，流量均匀分布。简单高效，适合实例配置相同的场景。
RandomLoadBalancer
随机策略：随机选一个实例。在实例数较多时与轮询效果接近，优点是实现简单无状态（轮询需要维护计数器）。
// 自定义负载均衡策略（针对特定服务）
@Configuration
@LoadBalancerClient(name = "user-service", configuration = UserLBConfig.class)
public class GatewayConfig {}

public class UserLBConfig {
    @Bean
    public ReactorLoadBalancer<ServiceInstance> randomLB(
            Environment env, LoadBalancerClientFactory factory) {
        String name = env.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
        return new RandomLoadBalancer(factory.getLazyProvider(name, ServiceInstanceListSupplier.class), name);
    }
}

Nacos 的权重负载均衡：Nacos 控制台可以调整每个实例的权重（0~1），LoadBalancer 会按权重比例分配流量。权重为 0 时该实例不接收任何流量（优雅下线）。

06超时、重试与灰度发布
Gateway 层的重试配置
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/order/**
          filters:
            - name: Retry
              args:
                retries: 2                 # 最多重试 2 次（加上首次共 3 次）
                statuses: BAD_GATEWAY,SERVICE_UNAVAILABLE  # 502/503 时重试
                methods: GET               # 只对 GET 请求重试（POST 不能轻易重试，可能重复提交）
                backoff:
                  firstBackoff: 50ms       # 第一次重试等 50ms
                  maxBackoff: 500ms        # 最大等待 500ms
                  factor: 2               # 指数退避倍数
POST/PUT 请求不要配置重试，除非服务实现了幂等性。非幂等接口重试会导致重复创建订单、重复扣款等严重问题。
灰度发布（金丝雀发布）实现方案

灰度发布让新版本先接受小比例流量，验证无误后再全量。在 Spring Cloud Gateway 中有两种常见实现：

Weight 断言分流（简单灰度）
routes:
  - id: order-v1
    uri: lb://order-service
    predicates:
      - Path=/api/order/**
      - Weight=order-group, 90  # 90% 流量
  - id: order-v2
    uri: lb://order-service-v2
    predicates:
      - Path=/api/order/**
      - Weight=order-group, 10  # 10% 灰度
Header/Cookie 定向灰度
特定用户（内测用户、员工）收到灰度版本： 
routes:
  - id: order-v2-gray
    uri: lb://order-service-v2
    predicates:
      - Path=/api/order/**
      - Header=X-Gray-User, true
    # 灰度用户请求头带 X-Gray-User: true
    # 其余用户走默认路由（order-v1）
Gateway 性能调优要点：
· 基于 WebFlux/Netty，不要在 Filter 中做同步阻塞操作（如同步调用 Redis/DB），必须用响应式 API（Mono/Flux）
· 限流过滤器（RequestRateLimiter）需要 Redis 支撑，确保 Redis 高可用
· 大流量场景下适当调大 Netty 的 workerThreads（默认 CPU 核数 × 2）
