01 JMM / volatile Q1–Q7
Q1 什么是 JMM？主内存和工作内存的关系是什么？ 高频▼
面试官视角

并发基础必问，考察候选人是否真正理解多线程可见性问题的根源。期望听到主内存/工作内存的抽象模型，以及它如何导致可见性问题。

参考回答

JMM（Java Memory Model）是 Java 虚拟机规范定义的一种内存模型，用于屏蔽不同操作系统和硬件平台的内存访问差异，使 Java 程序在各平台上能得到一致的并发行为。

核心模型：所有共享变量（实例字段、静态字段）存储在主内存中；每个线程有自己的工作内存（对应 CPU 缓存/寄存器的抽象），只能操作主内存变量的副本。

  • 读：主内存 → 工作内存（load）→ 执行引擎（use）
  • 写：执行引擎（assign）→ 工作内存 → 主内存（store+write）

正是这种"缓冲"机制导致了可见性问题：线程 A 修改了工作内存中的变量，未及时刷新主内存，线程 B 读到的是旧值。volatile、synchronized 等机制用于解决此问题。

Q2 volatile 的两个核心语义是什么？底层如何实现？ 高频▼
面试官视角

volatile 是并发高频题，很多人只知道"可见性"，能说出"禁止指令重排"以及底层 lock 前缀指令的，层次明显更高。DCL 单例的原理要在这里说清楚。

参考回答

volatile 有两个核心语义：

  • ①可见性：写 volatile 变量时，CPU 发出 lock 前缀指令，触发缓存行写回主内存，并通过 MESI 缓存一致性协议使其他 CPU 的该缓存行失效。其他线程下次读该变量时强制从主内存加载最新值。
  • ②禁止指令重排序：通过内存屏障实现。volatile 写前插入 StoreStore 屏障，写后插入 StoreLoad 屏障；volatile 读后插入 LoadLoad 和 LoadStore 屏障，禁止编译器和处理器将 volatile 操作前后的指令重排到屏障另一侧。
注意：volatile 不保证原子性，volatile int i; i++ 仍然是读-改-写三步，非原子操作。

Q3 volatile 为什么不保证原子性？i++ 在多线程下有什么问题？如何解决？ 高频▼
参考回答

i++ 看似一条语句，字节码层面是三步：① 读取 i 的值（getstatic/getfield）② 加 1（iadd）③ 写回（putstatic/putfield）。这三步不是原子的，多线程下可能：

线程A读到 i=0，线程B也读到 i=0
线程A执行 +1 写入 i=1
线程B也执行 +1 写入 i=1  ← 丢失了一次更新
// 期望 i=2，实际 i=1

volatile 只保证每次读到最新值，但无法阻止"读-改-写"过程中其他线程的插入。解决方案：

  • ①AtomicInteger.getAndIncrement() — CAS 原子操作，推荐
  • ②synchronized 块 — 锁住三步操作
  • ③LongAdder — 高并发场景性能更好
Q4 happens-before 原则有哪些？它和 volatile、synchronized 的关系？ 重点▼
参考回答

happens-before 是 JMM 定义的可见性保证：操作 A happens-before 操作 B，意味着 A 的执行结果对 B 可见。JMM 定义了 8 条规则，常考的有：

  • ①程序顺序规则：同一线程内，前面的操作 hb 后面的操作
  • ②监视器锁规则：unlock hb 后续对同一锁的 lock（synchronized 可见性的理论基础）
  • ③volatile 变量规则：volatile 写 hb 后续对该变量的读（volatile 可见性的理论基础）
  • ④线程启动规则：Thread.start() hb 被启动线程的任何操作
  • ⑤传递性：A hb B，B hb C，则 A hb C

volatile 和 synchronized 分别对应规则③和②，是实现 happens-before 的具体机制。

Q5 DCL（双重检查锁定）单例模式为什么必须加 volatile？ 高频▼
面试官视角

综合考察 volatile 和指令重排序的理解。能说出"半初始化对象"和"指令重排"的候选人，面试官会认为其对 JMM 有深刻理解。

参考回答

instance = new Singleton() 在 JVM 层面分三步：① 在堆上分配内存 ② 调用构造函数初始化对象 ③ 将 instance 引用指向该内存。

由于指令重排序，JVM 可能将执行顺序变为 ①③②（先将引用指向内存，再初始化），此时：

线程A执行到步骤③（instance 已非 null，但对象未初始化）
线程B执行第一次检查：instance != null → 直接返回
线程B使用了半初始化的 instance → NPE 或数据错误

volatile 通过内存屏障禁止 ②③ 重排序，确保引用赋值时对象一定已完全初始化。

// 正确写法
private static volatile Singleton instance;
public static Singleton getInstance() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) {
                instance = new Singleton(); // volatile 禁止重排
            }
        }
    }
    return instance;
}
Q6 指令重排序有哪几种？as-if-serial 语义是什么？ 重点▼
参考回答

三种重排序：① 编译器重排序（JIT 在不改变单线程语义下调整顺序）② 处理器重排序（CPU 乱序执行，流水线优化）③ 内存系统重排序（Store Buffer、Invalid Queue 导致写操作可见延迟）。

as-if-serial 语义：在单线程内，无论怎么重排序，最终执行结果必须与顺序执行结果一致。编译器和 CPU 的底线保证。但多线程下 as-if-serial 只保证各自线程内部，跨线程可见性需要 JMM 的 happens-before 规则。

Q8 创建线程有几种方式？各自区别和推荐度？ 高频▼
参考回答

严格来说创建线程只有一种方式：new Thread()，其他都是 Runnable/Callable 的不同封装。实际开发中有 4 种写法：

  • ①继承 Thread：最简单，但 Java 单继承限制，不推荐
  • ②实现 Runnable：解耦，可共享数据，但无返回值
  • ③实现 Callable + FutureTask：有返回值，可抛异常，推荐
  • ④线程池（首选）：复用线程，统一管理，可监控，生产环境必用

Q11 ThreadLocal 的实现原理是什么？为什么会内存泄漏？如何解决？ 高频▼
面试官视角

ThreadLocal 高频题，能说清楚弱引用 key 导致泄漏原因，以及线程池场景下必须 remove() 的道理，是进阶工程师的标志。

参考回答

实现原理：每个 Thread 内部有一个 ThreadLocalMap，key 是 ThreadLocal 对象的弱引用，value 是存储的值。ThreadLocal.get/set 实际是操作当前线程的 ThreadLocalMap。

内存泄漏原因：当 ThreadLocal 对象不再被强引用时，弱引用 key 被 GC 回收变为 null，但 value 是强引用，无法被 GC。如果线程（线程池中长期存活），这些"key=null"的 Entry 就一直占用内存，即内存泄漏。

解决方案：使用完毕后显式调用 threadLocal.remove()，最佳实践是 try-finally 保证执行：

try {
    userCtx.set(user);
    doWork();
} finally {
    userCtx.remove(); // 必须！
}

Q12 wait() 必须在 while 循环中使用，为什么不能用 if？ 重点▼
参考回答

因为虚假唤醒（Spurious Wakeup）：线程可能在没有被 notify()/notifyAll() 的情况下从 wait() 返回（操作系统和 JVM 规范都允许此行为），此时条件可能仍未满足。

用 if：唤醒后不重新检查条件，直接往下执行，可能在队列空时仍执行 take()，导致 NPE 或数据错误。

用 while：唤醒后重新检查条件，若条件不满足继续 wait()，确保安全。Java 官方文档明确要求："Always invoke wait inside a loop that tests the condition being waited for."

Q13 如何优雅地停止一个线程？stop() 为什么被废弃？ 重点▼
参考回答

Thread.stop() 被废弃原因：强制停止会立即解锁所有 Monitor，导致对象在不一致状态（如只完成了一半的数据修改），破坏线程安全性。

优雅停止方案：

  • ①interrupt() 协作中断（推荐）：调用 interrupt() 设置中断标志，线程自行检查 isInterrupted() 并退出。sleep/wait 等可中断方法会抛 InterruptedException。
  • ②volatile 标志位：设置 volatile boolean running = false，线程在循环中检查该标志。适合没有阻塞调用的场景。
// 正确的 interrupt 处理
while (!Thread.currentThread().isInterrupted()) {
    try {
        doWork();
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt(); // 恢复标志
        break; // 响应中断，退出
    }
}
Q14 守护线程是什么？与用户线程有什么区别？ 重点▼
参考回答

守护线程（Daemon Thread）是为其他线程服务的后台线程。当所有用户线程结束后，JVM 会强制退出，所有守护线程随之终止（不管是否执行完毕）。

设置方式：thread.setDaemon(true)，必须在 start() 前调用。

典型守护线程：GC 线程、JVM 心跳线程。注意：守护线程的 finally 块在 JVM 强制退出时不保证执行，不应在守护线程中进行需要保证完成的操作（如写文件、释放资源）。

Q17 AQS（AbstractQueuedSynchronizer）的实现原理是什么？ 高频▼
面试官视角

AQS 是 JUC 的核心，能讲清楚 state + CLH 队列 + acquire/release 流程的候选人，对并发框架有较深理解，是中高级工程师的分水岭。

参考回答

AQS 通过两个核心数据结构实现同步：

  • ①volatile int state：同步状态变量，子类定义其语义（ReentrantLock：重入次数；Semaphore：剩余许可；CountDownLatch：倒计数）
  • ②CLH 变体双向链表：等待获取锁的线程封装为 Node 节点排队；head 是虚节点，首个真实等待节点是 head.next

独占锁（ReentrantLock）核心流程：

acquire(1):
  tryAcquire(1)       // 子类实现：CAS 尝试将 state 0→1
  → 失败则 addWaiter  // 当前线程封装为 Node 入队
  → acquireQueued    // 循环检查前驱是否为 head，是则尝试 tryAcquire；否则 park 挂起

release(1):
  tryRelease(1)       // state 减 1，减到 0 时返回 true
  → unparkSuccessor(head) // 唤醒 head.next 的线程

Q18公平锁和非公平锁的区别？为什么非公平锁吞吐量更高？重点▼
参考回答

公平锁：严格按 AQS 等待队列顺序（FIFO）获取锁，每次唤醒都需要线程从阻塞到运行（上下文切换）。

非公平锁：线程获取锁时先 CAS 尝试抢锁，失败才入队。若此时锁刚好释放，新来的线程可能立即抢到锁（插队），避免了唤醒等待线程的上下文切换开销，吞吐量更高。

代价：可能导致等待队列中的线程长时间饥饿（极端情况）。ReentrantLock 默认非公平，可通过 new ReentrantLock(true) 设为公平锁。

Q19死锁的四个必要条件是什么？如何预防和检测？高频▼
参考回答

死锁的四个必要条件：① 互斥（资源只能被一个线程持有）② 持有并等待（持有资源同时等待其他资源）③ 不可抢占（资源不能被强制夺取）④ 循环等待（线程间形成等待环路）。

预防：破坏任意一条即可。最常用：破坏④ — 对所有锁统一排序，按固定顺序申请；破坏③ — tryLock() 超时放弃。

检测：jstack <pid> 输出线程堆栈，JVM 会标注 "Found N deadlock"；或用 ThreadMXBean.findDeadlockedThreads() 编程检测。

Q20ReentrantReadWriteLock 的读写规则？写锁饥饿如何解决？重点▼
参考回答

读写规则：读读不互斥（多个读线程并发）/ 读写互斥 / 写写互斥。适合读多写少场景。

底层用 AQS state 的高 16 位表示读锁数量，低 16 位表示写锁重入次数。

写锁饥饿：高并发读时，读锁不断被获取，写锁长期等待。解决：

  • ①使用公平锁 new ReentrantReadWriteLock(true)，保证 FIFO 顺序
  • ②使用 StampedLock（JDK 8+）的乐观读模式，不阻塞写

Q22synchronized 是可重入锁吗？可重入锁的实现原理是什么？重点▼
参考回答

是的，synchronized 是可重入锁。可重入锁允许同一个线程多次获取同一把锁，避免自己把自己锁死。

实现原理：Monitor 对象内有一个计数器和持有线程记录。线程获取锁时，若当前持有者就是自己则计数器+1，无需等待；释放锁时计数器-1，减到 0 才真正释放。

ReentrantLock 同理：AQS 的 state 存储重入次数，获取时+1，释放时-1，减到 0 才唤醒等待线程。

Q25CAS 的 ABA 问题是什么？如何解决？高频▼
参考回答

ABA 问题：线程 1 读到值为 A，线程 2 将其改为 B 再改回 A，线程 1 此时执行 CAS 看到值仍是 A，认为没变化而成功，但中间发生了变化。对大多数场景无影响，但在某些特殊场景（如链表指针操作）会有问题。

解决方案：

  • ①AtomicStampedReference：带版本号（stamp）的引用，CAS 同时校验引用和版本号，A→B→A 时版本号不同则 CAS 失败
  • ②AtomicMarkableReference：带布尔标记的引用，适合只需标记"是否被修改过"的场景
Q26LongAdder 为什么比 AtomicLong 在高并发下性能更好？重点▼
参考回答

AtomicLong 所有线程竞争同一个 volatile long 变量，高并发时 CAS 频繁失败，自旋消耗 CPU。

LongAdder 采用分散热点策略：维护一个 base 值和 Cell 数组，低并发时直接 CAS 更新 base；高并发时，不同线程映射到不同 Cell 上各自累加（减少竞争）；sum() 时再汇总 base + 所有 Cell。

代价：sum() 时读取结果不是实时精确的（读 sum 期间可能有其他线程在写 Cell）。所以 LongAdder 适合统计（如 QPS）而非需要精确读取的场景。

Q27CopyOnWriteArrayList 的原理是什么？有什么优缺点？重点▼
参考回答

读操作无锁，直接读 volatile 数组。写操作（add/remove/set）加 ReentrantLock，复制整个数组，在副本上修改，完成后将 volatile 引用指向新数组。

优点：读完全无锁，并发读性能极好。缺点：① 写时全量复制，内存开销大，GC 压力大 ② 弱一致性（读操作读的是快照，写操作完成前读不到新数据）。适合读多写极少的场景（配置列表、白名单等）。

Q28BlockingQueue 有哪些实现？SynchronousQueue 有什么特点？重点▼
参考回答

常用实现：ArrayBlockingQueue（有界，数组，单锁）/ LinkedBlockingQueue（可选有界，链表，读写双锁）/ PriorityBlockingQueue（无界，优先队列）/ DelayQueue（延迟出队）/ SynchronousQueue（零容量，直接传递）。

SynchronousQueue：容量为 0，put() 必须有线程在 take()（直接传递），否则阻塞。用于 CachedThreadPool：每个任务必须立即被线程接收，无线程则创建新线程，这解释了 CachedThreadPool 线程数量无上限。

Q29CompletableFuture 使用时有哪些常见陷阱？重点▼
参考回答
  • ①默认线程池陷阱：不指定 executor 时用 ForkJoinPool.commonPool()，与并行流共享，可能相互影响。生产环境始终指定自定义线程池
  • ②异常吞噬：链式调用中间步骤的异常如果不处理，join() 才会抛出，难以定位。应使用 exceptionally() 或 handle() 显式处理
  • ③阻塞主线程：在 Reactive/Netty 事件循环线程上调用 get()/join() 会阻塞事件循环，导致性能问题
  • ④thenApply vs thenApplyAsync：thenApply 在上一步完成的线程中执行（可能是主线程）；thenApplyAsync 提交到线程池异步执行。IO 操作应用 Async 版本

Q30ThreadPoolExecutor 的 7 个核心参数分别是什么？高频▼

Q31提交任务到线程池的完整执行流程是什么？高频▼
参考回答

提交任务时，ThreadPoolExecutor 按以下顺序判断：

  • ①当前线程数 < corePoolSize → 创建核心线程执行任务（即使有空闲线程）
  • ②当前线程数 ≥ core → 尝试放入工作队列（offer）
  • ③队列已满，且线程数 < maximumPoolSize → 创建非核心线程执行
  • ④队列满且线程数 = max → 执行拒绝策略
常见误区：不是"先扩到 max 线程再入队"，而是"先入队，队满才扩"。只有有界队列满了，才会创建超过 core 的线程。
Q32线程池核心线程数应该如何设置？有什么参考公式？高频▼
参考回答
  • CPU 密集N+1（N=CPU核数）。+1 是为了当线程因偶发中断导致暂停时，有额外线程接替，避免 CPU 空转。多了增加上下文切换开销
  • IO 密集2N 或 N / (1 - 阻塞系数)。IO 时间占比越高，阻塞系数越大，需要更多线程充分利用 CPU 空闲时间
  • 混合型按实际 IO/CPU 比例计算，且必须通过压测验证，观察 CPU 利用率和响应时间综合判断
公式只是起点，实际应结合压测结果、机器配置、任务特性动态调整。有条件推荐使用动态线程池（美团 DynamicTp）实现运行时调参。
Q33阿里规范为什么禁止使用 Executors 工厂方法创建线程池？高频▼
参考回答

四种内置线程池的问题：

  • ①FixedThreadPool / SingleThreadExecutor：使用 LinkedBlockingQueue（无界队列），任务积压无上限，可能堆积数百万任务导致 OOM
  • ②CachedThreadPool / ScheduledThreadPool：maximumPoolSize 为 Integer.MAX_VALUE，可创建近 21 亿个线程（实际 OOM 在数千线程时）导致 OOM

正确做法：始终使用 ThreadPoolExecutor 构造函数，明确指定有界队列和 maximumPoolSize，清楚每个参数的含义和风险。

Q35如何优雅关闭线程池？shutdown 和 shutdownNow 的区别？重点▼
参考回答
方法行为场景
shutdown()不接受新任务，等待已提交任务（队列+执行中）全部完成正常关闭，推荐
shutdownNow()不接受新任务，中断执行中线程（interrupt），返回未执行的任务列表需要立即停止时
// 优雅关闭最佳实践
executor.shutdown(); // 停止接收新任务
try {
    // 等待最多 30 秒让已有任务完成
    if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
        executor.shutdownNow(); // 超时则强制中断
        // 再等 5 秒确保响应中断
        executor.awaitTermination(5, TimeUnit.SECONDS);
    }
} catch (InterruptedException e) {
    executor.shutdownNow();
    Thread.currentThread().interrupt();
}
