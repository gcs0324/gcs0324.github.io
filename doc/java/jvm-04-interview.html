01 必背高频题 Q1 – Q8
Q1 JVM 运行时数据区有哪些？线程共享 vs 线程私有的区别？ 高频 ▼
面试官视角

JVM 所有问题的基础。考察你对内存模型的系统性理解。期望听到线程私有/共享的分类、各区域的职责和 OOM 类型。加分点：提到直接内存、JDK8 用 Metaspace 替换 PermGen 的原因。

参考回答

JVM 运行时内存划分为 5 个区域：

  • ①线程私有（3个）：程序计数器（唯一不会 OOM 的区域，记录当前线程字节码行号）、JVM 虚拟机栈（每个方法对应一个栈帧，含局部变量表/操作数栈/动态链接/返回地址，可 StackOverflow）、本地方法栈（服务 Native 方法，HotSpot 将两者合并）
  • ②线程共享（2个）：堆（几乎所有对象实例，分新生代+老年代，OOM: Java heap space）、方法区/元空间（类元数据/运行时常量池/静态变量，JDK8 起用本地内存的 Metaspace 替代 PermGen，OOM: Metaspace）

另外还有直接内存，不属于 JVM 规范，NIO 的 DirectByteBuffer 分配于此，不受 -Xmx 限制，可 OOM: Direct buffer memory。

Q2 堆和栈的区别是什么？什么情况下对象会在栈上分配？（逃逸分析） 重点 ▼
面试官视角

很多人只会说"堆存对象，栈存基本类型"，这只能得基础分。考察点在于逃逸分析和标量替换——能说出这两个点，说明你了解 JIT 优化，是高级 Java 工程师应有的知识。

参考回答

堆和栈的核心区别：

  • ①存储内容：栈存基本类型变量和对象引用，堆存对象实例本身
  • ②生命周期：栈随方法调用/返回自动分配/释放；堆中对象靠 GC 回收
  • ③线程归属：栈是线程私有，堆是线程共享
  • ④大小：栈空间小（默认 512k~1m），堆由 -Xmx 指定

关于栈上分配，JVM 通过逃逸分析（JDK7+ 默认开启）判断对象作用域，若对象未逃逸出方法（不被外部引用/返回/传参），JVM 会做三种优化：

  • ①栈上分配：直接在栈帧分配，方法返回后随栈帧销毁，不需 GC
  • ②标量替换（-XX:+EliminateAllocations）：把对象拆散成基本类型存局部变量表，彻底消除对象分配
  • ③同步消除：锁对象不逃逸则直接消除 synchronized 块

Q3 Minor GC / Major GC / Full GC 的区别和触发条件？ 高频 ▼
面试官视角

GC 类型是必考题。重点在触发条件是否清晰，以及是否能区分 Major GC 和 Full GC（很多人混用）。加分点：说出 Full GC 的多种触发原因，以及 Full GC 为什么要尽量避免。

参考回答
  • ①Minor GC（Young GC）：只回收新生代（Eden + Survivor）。触发：Eden 区满。速度快（几ms~几十ms），因为新生代存活对象少，标记-复制算法效率高。
  • ②Major GC：回收老年代。往往伴随至少一次 Minor GC（非绝对）。速度比 Minor GC 慢 10 倍以上。CMS 的并发清除阶段就是 Major GC。
  • ③Full GC：回收整个堆 + 元空间。触发条件：老年代空间不足 / 元空间不足 / 调用 System.gc() / CMS 并发模式失败 / Minor GC 晋升失败（Promotion Failed）。停顿时间最长，生产要尽力避免。
注意：Major GC 和 Full GC 有时混用。严格来说 Major GC 仅老年代，Full GC 包含全堆+元空间。不同收集器对这两个术语的界定略有差异。

Q4 CMS 和 G1 的核心区别？生产上如何选择？ 高频 ▼
面试官视角

生产选型题，是对 GC 原理掌握深度的综合考察。期望听到 Region 设计、SATB、停顿预测模型等关键词，而不只是"G1 更好"。最后能给出版本差异化的选择建议更佳。

参考回答

核心区别有五点：

  • ①内存模型：CMS 是传统新生代/老年代分区；G1 把堆切成等大小 Region（1~32MB），Region 可动态扮演 E/S/O/H 角色
  • ②内存碎片：CMS 用标记-清除，长期运行产生碎片；G1 基于 Region 复制，基本无碎片
  • ③可预测停顿：G1 有停顿预测模型，在 -XX:MaxGCPauseMillis 约束内优先回收垃圾最多的 Region；CMS 停顿不可控
  • ④并发漏标处理：CMS 用增量更新；G1 用 SATB，重新标记阶段更短
  • ⑤失败退化：CMS 退化为 Serial Old（极慢）；G1 退化为 Full GC

选择建议：JDK8 堆 <6GB → Parallel GC（吞吐优先）；堆 ≥6GB 或延迟敏感 → G1。JDK9+ 默认 G1 直接用。JDK15+ 毫秒级停顿要求 → ZGC。不建议新项目用 CMS（JDK14 已删除）。

Q5 什么是 Stop-The-World？哪些 GC 阶段会触发 STW？ 高频 ▼
面试官视角

考察对 GC 停顿的底层理解。大多数人知道 STW 是暂停，但不知道是通过 Safepoint 实现的。能说出各收集器 STW 的具体阶段和 ZGC 如何缩短 STW，是加分答案。

参考回答

Stop-The-World（STW）：JVM 暂停所有用户线程，只有 GC 线程工作的状态。STW 期间应用完全停止响应。

各收集器 STW 阶段：

  • ①初始标记（Initial Mark）：所有并发 GC 都需要，标记 GC Roots 直接关联对象，时间极短但必须 STW
  • ②重新标记 / 最终标记（Remark / Final Mark）：修正并发标记期间的变化，较短但需 STW
  • ③G1 的转移阶段（Evacuation Pause）：复制存活对象到新 Region，全程 STW
  • ④Full GC：全程 STW，停顿最长

ZGC 把对象转移也并发化，STW 只剩初始标记和最终标记，通常 <10ms。

实现原理：STW 通过 Safepoint 机制实现。JVM 在字节码特定位置插入安全点检查，GC 触发时所有线程需在下一个安全点暂停，全部暂停后 STW 才正式开始。

Q6 如何排查 CPU 飙高问题？（top -Hp + jstack 线程 dump） 高频 ▼
面试官视角

经典生产实战题，几乎每场面试必考。不仅要说出标准 5 步流程，还要能说出常见根因（死循环/频繁 GC/正则回溯）。加分：提到 Arthas 的 thread -n 命令一键搞定。

参考回答

CPU 飙高排查标准 5 步：

  • ①找进程：top 找到 CPU 最高的 Java 进程 PID
  • ②找线程：top -Hp <PID> 查看进程内各线程 CPU 占用，找到最高线程 TID（十进制）
  • ③转十六进制：printf "%x\n" <TID> 得到 nid
  • ④抓线程栈：jstack <PID> | grep -A 30 "<nid>"
  • ⑤分析根因：看调用栈定位具体代码
top                        # 找到 Java 进程 PID=12345
top -Hp 12345              # 找到 CPU 最高线程 TID=12399
printf "%x\n" 12399        # 输出 305f（十六进制 nid）
jstack 12345 | grep -A 30 "305f"

# 或用 Arthas 一步搞定（推荐）
thread -n 5                # 直接列出 CPU 最高的 5 个线程及调用栈

常见根因：① 死循环（while true / 递归溢出）② GC 线程占用高（频繁 Full GC）③ 正则表达式回溯 ④ 大量锁竞争自旋 ⑤ 序列化/反序列化大对象。若是 GC 线程 CPU 高（线程名含 GC task thread），转向 GC 排查。

Q7 如何排查内存泄漏？（jmap -histo + MAT dump 分析） 高频 ▼
面试官视角

实战排查题，考察工具熟练度。能说出 MAT 的 Leak Suspects 和 Dominator Tree，以及 ThreadLocal 未 remove 是高频泄漏场景，是加分答案。预防措施（HeapDumpOnOutOfMemoryError）也要提。

参考回答

内存泄漏特征：堆持续增长，Full GC 后无法回落。排查 5 步：

  • ①确认泄漏：jstat -gcutil <pid> 5000 观察 Old 区（OU/OC）是否持续增长、GC 后不下降
  • ②快速看对象分布：jmap -histo:live <pid> | head -30，看哪些类实例数量异常多
  • ③导出 heap dump：jmap -dump:format=b,live,file=/tmp/heap.hprof <pid>
  • ④MAT 分析：看 Leak Suspects（自动分析疑似泄漏）和 Dominator Tree（哪个对象持有内存最多）
  • ⑤找引用链：对大对象执行 "Path to GC Roots"，找到哪个根引用阻止了 GC

常见泄漏场景：① ThreadLocal 未 remove（key 弱引用，value 强引用）② static 集合无限增长 ③ 监听器/回调未注销 ④ 数据库连接/流未关闭 ⑤ 缓存未设过期

生产建议：提前配置 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/，OOM 时自动 dump，不错过现场。

Q8 双亲委派模型是什么？Tomcat 为什么要破坏它？ 高频 ▼
面试官视角

类加载必考题，分两层：基础层（双亲委派规则和作用）+ 进阶层（为什么 Tomcat 要破坏，实现方式）。只会背规则拿基础分，能解释 Tomcat 多 WebApp 类隔离需求才得满分。

参考回答

双亲委派：收到类加载请求时，先委派父加载器，只有父加载器找不到才自己加载。层次：Bootstrap → Extension → Application → 自定义。

核心作用：① 防止用户自定义 java.lang.String 等核心类替换官方实现 ② 避免同一类被重复加载。

Tomcat 为什么要破坏：多个 Web 应用可能依赖同一个库的不同版本（如应用 A 用 Spring 4.x，应用 B 用 Spring 5.x）。若遵循双亲委派，同名类只能加载一次，无法隔离。Tomcat 为每个 WebApp 创建独立的 WebAppClassLoader，优先自己加载（先 findClass 再委派父），打破委派顺序实现隔离。

Q9 对象一定在堆上分配吗？逃逸分析和标量替换原理？ 重点 ▼
面试官视角

进阶题，区分"背了面试题"和"真正理解 JVM 优化"的分水岭。能解释逃逸分析的判断标准，以及标量替换为何比栈上分配更彻底，说明有 JIT 实践经验。

参考回答

不一定。JVM 通过逃逸分析（JDK7+ 默认开启 -XX:+DoEscapeAnalysis）判断对象作用域，若对象没有逃逸出方法，JVM 可做三种优化：

  • ①栈上分配：对象直接在栈帧分配，方法返回后销毁，不需 GC
  • ②标量替换（-XX:+EliminateAllocations，默认开启）：把对象拆散成多个基本类型字段存入局部变量表，根本不创建对象。这是最彻底的优化。
  • ③同步消除：锁对象不逃逸则去掉 synchronized

实践中标量替换效果最显著，可大量减少短命对象的堆分配，降低 Minor GC 频率。用 -XX:-DoEscapeAnalysis 关闭后 GC 日志中 Minor GC 频率会明显升高。

Q10 G1 的 Region 如何工作？Mixed GC 的触发条件？ 重点 ▼
面试官视角

G1 是生产主流 GC，深度考察。能说清 Region 动态角色、Mixed GC 与并发标记周期的关系、RSet 解决跨 Region 引用，是标准水平。

参考回答

G1 把堆切成等大小的 Region（1~32MB，2 的幂），每个 Region 可动态扮演 E（Eden）/ S（Survivor）/ O（Old）/ H（Humongous 大对象）角色，没有固定的新老代边界。

Mixed GC 触发条件：

  • ①老年代占堆比例超 -XX:InitiatingHeapOccupancyPercent（默认 45%），触发一轮并发标记周期
  • ②并发标记完成后，G1 知道哪些 Old Region 垃圾最多，接下来若干次 GC 进入 Mixed GC 模式：回收所有 Young Region + 部分垃圾最多的 Old Region
  • ③持续到老年代占比降到安全水位（-XX:G1HeapWastePercent，默认 5%）为止

关键技术：每个 Region 维护 RSet（Remembered Set）记录外部引用，Card Table 精确定位修改位置，SATB 写屏障防止并发漏标。

Q11 ZGC 的着色指针是什么？为什么停顿时间极短？ 重点 ▼
面试官视角

ZGC 在 JDK11 以后越来越被生产采用。能说出着色指针和读屏障的原理，以及"停顿时间不随堆大小增长"的核心原因，是加分答案。

参考回答

着色指针（Colored Pointers）：在 64 位指针的高 4 位（bit 40~43）存储 GC 状态元数据（Finalizable / Remapped / Marked1 / Marked0），把对象状态信息嵌入指针本身。

ZGC 停顿极短的原因：

  • ①并发转移：对象移动不再需要 STW。通过读屏障（Load Barrier）在用户线程读取指针时检查颜色位，若对象已转移自动修正，实现"边使用边整理"
  • ②STW 极短：只有初始标记（标记 GC Roots）和最终标记需要 STW，其余全部并发
  • ③停顿不随堆大小增长：STW 阶段工作量只与 GC Roots 数量有关，与堆大小无关，TB 级堆也能保持毫秒级停顿

Q14 方法区在 JDK8 前后有何变化？为什么用 Metaspace 替换 PermGen？ 重点 ▼
面试官视角

考察对 JVM 内存演进历史的了解。能说清"PermGen OOM 是痛点 → JDK8 用本地内存 Metaspace 替代"这条主线，以及内容迁移方式，是加分答案。

参考回答

JDK7 及之前：方法区的实现是 PermGen（永久代），位于 JVM 托管内存，由 -XX:MaxPermSize 限制（默认 64~128MB）。

JDK8：用 Metaspace（元空间）替代，主要变化：

  • ①存储位置：Metaspace 使用本地内存（Native Memory），不占用 JVM 堆空间
  • ②大小限制：默认无上限，需用 -XX:MaxMetaspaceSize 主动限制
  • ③内容迁移：类元数据移到 Metaspace；运行时常量池和 static 变量移到堆（JDK7 已迁移一部分）

为什么替换：PermGen 大小固定，CGLIB/动态代理大量生成类时频繁 OOM（PermGen space）；用本地内存更灵活，消除 PermGen OOM 问题。

Q15 JVM 内存屏障是什么？与 volatile 有什么关系？ 重点 ▼
面试官视角

并发编程底层原理题。很多人知道 volatile 保证可见性和有序性，但不知道底层是靠内存屏障指令实现的。能说清四种屏障类型 + volatile 读写各插入哪些屏障，是高分答案。

参考回答

内存屏障（Memory Barrier）是 CPU 指令，用于禁止指令重排序和强制内存可见性，分四类：LoadLoad / StoreStore / LoadStore / StoreLoad（最重量级，全能屏障）。

volatile 的实现：

  • 写volatile 写之前插入 StoreStore（前面的写不重排到 volatile 写后）；写之后插入 StoreLoad（保证写立即对其他线程可见）
  • 读volatile 读之后插入 LoadLoad + LoadStore（后面的读写不重排到 volatile 读前）

效果：① 可见性：volatile 写刷新到主内存，volatile 读使本地缓存失效 ② 有序性：禁止 volatile 读写与前后指令重排序。但 volatile 不保证原子性（i++ 等复合操作仍不安全）。

Q16 如何自定义类加载器实现类隔离？核心代码是什么？ 重点 ▼
面试官视角

实操能力考察题。考察点在于：为什么重写 findClass 而不是 loadClass，以及如何用两个不同 ClassLoader 加载同名类实现隔离。这是框架开发、中间件开发的基础能力。

参考回答

类隔离核心：为每个隔离域创建独立的 ClassLoader。同一字节码被不同 ClassLoader 加载，产生两个 Class 对象，JVM 视为两个不同的类。

public class IsolatedClassLoader extends ClassLoader {
    private final String baseDir;

    public IsolatedClassLoader(String baseDir) {
        super(ClassLoader.getSystemClassLoader());
        this.baseDir = baseDir;
    }

    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = loadClassBytes(name);
        if (bytes == null) throw new ClassNotFoundException(name);
        return defineClass(name, bytes, 0, bytes.length);
    }

    private byte[] loadClassBytes(String name) {
        String path = baseDir + "/" + name.replace('.', '/') + ".class";
        try { return Files.readAllBytes(Paths.get(path)); }
        catch (IOException e) { return null; }
    }
}

// 使用：两个 ClassLoader 加载同名类，互相隔离
IsolatedClassLoader clA = new IsolatedClassLoader("/deploy/app-v1/classes");
IsolatedClassLoader clB = new IsolatedClassLoader("/deploy/app-v2/classes");
Class<?> sa = clA.loadClass("com.example.OrderService");
Class<?> sb = clB.loadClass("com.example.OrderService");
System.out.println(sa == sb); // false！两个不同的 Class 对象
关键：重写 findClass() 不要重写 loadClass()，否则破坏双亲委派，导致 JDK 核心类也被自定义加载器尝试加载。

Q17 -Xms 和 -Xmx 为什么建议设成相同值？ 重点 ▼
面试官视角

JVM 基础配置题，考察对堆动态扩缩容副作用的理解。不仅要说"避免扩展触发 GC"，还要能解释收缩时也会触发 GC，以及生产环境内存可预测的重要性。

参考回答

-Xms 是堆初始大小，-Xmx 是堆最大大小。建议设为相同值，原因：

  • ①避免堆扩展触发 GC：若 Xms < Xmx，堆不足时 JVM 动态扩展，扩展本身会触发 Full GC
  • ②避免堆收缩触发 GC：GC 后内存充裕时 JVM 可能收缩堆，收缩时也触发 GC
  • ③内存可预测：生产环境内存固定，避免 JVM 意外占用额外内存影响其他进程
-Xms4g -Xmx4g   # 推荐：Xms = Xmx
# 通常建议堆 = 物理内存 × 60%~70%（给 OS 和堆外内存留空间）

Q18 -XX:NewRatio 和 -Xmn 如何配合设置？ 重点 ▼
面试官视角

GC 调优参数题，考察是否实际操作过 JVM 调优。关键点：两个参数的区别、G1 场景下不需要手动设置新生代大小，以及 SurvivorRatio 的配合。

参考回答
  • ①-XX:NewRatio=2：Old:New = 2:1，新生代占堆 1/3。动态，跟随堆大小变化。

-Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200  # G1 场景（让 G1 自动调）

Q19 -XX:MaxGCPauseMillis 设太小会有什么副作用？ 重点 ▼
面试官视角

G1 调优反直觉考点。很多人以为把停顿目标设越小越好，但实际上会适得其反。考察是否理解 G1 停顿目标的本质是"尽力而为"，以及 GC 频率和停顿时间之间的权衡。

参考回答

-XX:MaxGCPauseMillis 是 G1 的停顿时间目标（不是硬性保证），设太小会带来副作用：

  • ①GC 频率增加：G1 每次只回收少量 Region 来缩短停顿，导致 GC 轮次增多，总体 GC 开销变大
  • ②吞吐量下降：更多 CPU 时间花在 GC 上，业务线程时间减少
  • ③Mixed GC 推迟：老年代回收不及时，反而可能触发 Full GC（停顿更长）
  • ④新生代被强制缩小：G1 为缩短 Young GC 时间会减少 Eden Region，导致 Minor GC 更频繁
实践：普通 Web 服务 200ms（默认）通常足够；需要更低可设 100ms；追求毫秒级应考虑 ZGC。

Q20 元空间溢出如何配置上限？-XX:MaxMetaspaceSize 设多少合适？ 重点 ▼
面试官视角

考察对 Metaspace 的理解。Metaspace 默认无上限这点很多人不知道，这是生产隐患。关键：先排查根因（ClassLoader 泄漏/动态类过多），再设合理上限。

参考回答

Metaspace 默认无上限（使用本地内存），动态类生成过多时可能耗尽系统内存，生产环境必须设上限：

-XX:MetaspaceSize=128m       # 初始大小（首次触发 GC 的阈值，默认约 20MB）
-XX:MaxMetaspaceSize=256m    # 上限（超过则 OOM: Metaspace）

合适的值：普通 Spring Boot 应用 128~256m；大量 AOP 代理 256~512m。最佳实践：先不设上限，用 jcmd <pid> VM.metaspace 观察预生产峰值，设为峰值 1.5~2 倍。

注意：仅靠调大上限是掩盖问题。若 Metaspace 持续增长，先排查是否存在 ClassLoader 内存泄漏（ClassLoader 不断创建但未释放）。

Q22 线上发生 OOM，第一时间怎么处理？如何保留现场？ 高频 ▼
面试官视角

高频实战题，考察应急处理的系统性思维。两条线并行：保留现场（dump）+ 快速恢复服务。面试官想听到你把"保留现场"放在优先位置，而不是立刻重启。

参考回答

保留现场（优先）：

  • ①若已配置 -XX:+HeapDumpOnOutOfMemoryError，OOM 时 JVM 自动 dump，直接取文件
  • ②进程还活着时立即手动 dump：jmap -dump:format=b,live,file=/tmp/heap.hprof <pid>
  • ③同时抓线程快照：jstack <pid> > /tmp/thread.txt
  • ④保存 GC 日志，记录 OOM 前后 GC 状态

快速恢复服务：重启进程；若内存泄漏短期无法修复，临时扩大 -Xmx 买时间；流量突增则限流降级。

事后分析：用 MAT 打开 .hprof，看 Leak Suspects 和 Dominator Tree，找持有最多内存的对象和引用链。

预防：提前配置 HeapDumpOnOutOfMemoryError；监控堆趋势（Prometheus + JVM Exporter），内存持续上升及时告警。

Q23 频繁 Full GC 的常见原因和完整排查步骤？ 高频 ▼
面试官视角

生产故障排查高频题。考察你能否说出多种根因（而不只是"内存泄漏"），以及是否掌握 jstat/GC 日志等排查工具的具体用法。说出 System.gc() 这个容易被忽视的原因是加分项。

参考回答

常见原因（6类）：

  • ①内存泄漏：老年代对象持续增加，GC 后不下降
  • ②大对象直接进老年代：超过 -XX:PretenureSizeThreshold 的对象绕过新生代
  • ③Promotion Failed：Minor GC 时对象晋升，老年代空间不足
  • ④元空间不足：动态生成类过多，Metaspace 超限
  • ⑤CMS 触发过晚：CMSInitiatingOccupancyFraction 设太高，并发清理来不及
  • ⑥显式 System.gc()：代码或框架中调用，用 -XX:+DisableExplicitGC 禁用

排查步骤：

  • ①jstat -gcutil <pid> 2000 30 观察 Old 区（OU/OC）是否持续增长
  • ②查 GC 日志中 Full GC 触发原因字符串
  • ③若 Old 持续增长 → 疑内存泄漏，jmap -histo <pid> 看实例数量异常的类
  • ④CMS 触发过晚 → 降低 CMSInitiatingOccupancyFraction（如 60%）
  • ⑤搜索代码中是否有 System.gc() 调用

02 · 常见问题排查表 Q24 · Promotion Failed
Q24 GC 日志中看到 Promotion Failed 是什么问题？如何解决？ 重点 ▼
面试官视角

GC 日志诊断题，考察对 CMS 碎片问题的深度理解。能说清"Promotion Failed 的根本原因是老年代没有足够连续空间（不是总量不足）"，并给出升级 G1 这个最优解，是高分答案。

参考回答

Promotion Failed：Minor GC 时存活对象需晋升到老年代，但老年代没有足够的连续空间（内存碎片导致总量够但分不出大块），JVM 被迫触发 Full GC 整理内存。

根本原因：CMS 使用标记-清除算法，长期运行产生大量碎片；Survivor 区满导致对象提前晋升。

解决方案：

  • ①CMS 开启碎片整理：-XX:+UseCMSCompactAtFullCollection + -XX:CMSFullGCsBeforeCompaction=N
  • ②提前启动 CMS：降低 -XX:CMSInitiatingOccupancyFraction（如 60%）
  • ③增大老年代空间
  • ④最佳方案：升级到 G1，G1 基于 Region 复制，基本消除碎片问题

Q25 Arthas 实战：dashboard / jad / trace / watch / redefine 各自的使用场景？ 重点 ▼
面试官视角

工具实战题，考察线上诊断经验。能说出每个命令的典型场景（不只是功能描述），尤其是 trace 定位接口慢和 watch 拦截参数这两个最常用的，体现了真实的生产排查经验。

参考回答
  • ①dashboard：实时总览 CPU/内存/线程/GC，快速判断 JVM 健康状态。memory 命令看详细内存分区。
  • ②jad：反编译线上 class，排查"发布了新版本但代码未生效"、确认线上代码版本。
  • ③trace：输出方法调用树 + 各步耗时，定位接口慢的根因（哪个子调用最耗时）。
  • ④watch：实时拦截方法的入参/返回值/异常，不用加日志就能看到线上实际数据。
  • ⑤redefine / retransform：热修复线上代码，无需重启。不能修改类结构（增删方法/字段）。
thread -n 5                     # CPU 最高的 5 个线程
trace com.example.OrderService pay   # 方法调用树 + 耗时
watch com.example.OrderService pay "{params,returnObj,throwExp}" -e -x 3
jad com.example.OrderService    # 反编译
redefine /tmp/OrderService.class # 热修复
