01 可达性分析
判断对象存活：可达性分析算法

JVM 不使用引用计数法（无法解决循环引用），而是以 GC Roots 为起点，向下搜索，无法到达的对象即为"不可达"，可被回收。

GC Roots 包括：

  • ①虚拟机栈中引用的对象（本地变量表中的引用）
  • ②方法区静态变量引用的对象（static 字段）
  • ③方法区常量引用的对象（final static 字段）
  • ④JNI（Native 方法）引用的对象
  • ⑤持有同步锁的对象（synchronized 锁定的对象）
  • ⑥JVM 内部引用（基本类型的 Class 对象、常驻的异常对象 NullPointerException 等）
三色标记算法（并发标记）

在并发垃圾回收中（CMS / G1），标记与用户线程同时进行，引入三色标记保证正确性：

  • ⬛黑色（Black）— 对象本身及所有引用均已扫描，绝对存活，不会再扫描
  • 🔘灰色（Gray）— 对象本身已标记，但其字段还未全部扫描（待处理队列）
  • ⬜白色（White）— 未被访问到，若标记结束后仍为白色则被判定为垃圾
并发漏标问题：用户线程在标记期间将白色对象挂到黑色对象下（黑色不再扫描），且原来灰色→白色的引用被切断，导致存活对象被误回收。
解决方案：① 增量更新（CMS）— 记录黑色对象新增的引用，重新标记时再扫一遍。② SATB（G1）— 在引用被删除时记录旧值，重新标记时扫描旧引用。
对象"二次标记"与 finalize()

对象不可达后不立即回收，而是经过两次标记才被真正回收：

  • ①第一次标记：发现不可达，若对象未重写 finalize() 或已被调用过，直接进入"即将回收"集合
  • ②否则，加入 F-Queue 队列，由低优先级 Finalizer 线程异步执行 finalize()
  • ③若 finalize() 中对象重新与 GC Root 建立关联（"自救"），则移出"即将回收"集合
注意：finalize() 机制不可靠（不保证执行完毕）、代价高、易产生 Bug，JDK9 已标记为 @Deprecated，应避免使用。推荐用 try-with-resources 或 PhantomReference 替代。
02 基础 GC 算法
三种基础算法对比
算法优点缺点使用场景
标记-清除 实现简单，不需移动对象 产生内存碎片；标记清除均需STW CMS 老年代（并发清除阶段）
标记-复制 无碎片；存活对象少时效率极高 空间利用率 50%；存活对象多时复制开销大 新生代（Eden:S0:S1 = 8:1:1）
标记-整理 无碎片；空间利用率高 需移动存活对象，更新引用，暂停时间长 老年代（Serial Old, G1 Mixed GC）
分代收集理论
  • ①弱分代假说（Weak Generational Hypothesis）— 绝大多数对象朝生夕灭，生命周期极短
  • ②强分代假说（Strong Generational Hypothesis）— 熬过越多次 GC 的对象越难被回收
  • ③跨代引用假说（Intergenerational Reference Hypothesis）— 跨代引用相对于同代引用来说仅占少数

基于这三个假说，JVM 将堆分为新生代和老年代，分别采用不同的 GC 策略和频率，并用 Remembered Set（记忆集）解决跨代引用扫描问题。

03 经典垃圾收集器
收集器搭配关系
Serial / Serial Old 单线程 Client模式
最基础的收集器，单线程执行，GC 时必须暂停所有用户线程（STW）。优点：没有线程切换开销，在单 CPU 场景下效率反而最高。Serial 用于新生代（复制算法），Serial Old 用于老年代（整理算法），也是 CMS 失败后的后备。
ParNew 多线程 STW
Serial 的多线程版本，是 CMS 的唯一搭档（JDK9 后两者合并废弃）。多 CPU 环境下 GC 吞吐比 Serial 更高，但仍需 STW。
Parallel Scavenge / Parallel Old 吞吐量优先
目标是达到可控的吞吐量（= 运行用户代码时间 / 总时间）。提供 -XX:MaxGCPauseMillis（停顿时间上限）和 -XX:GCTimeRatio（吞吐量目标）两个参数，支持自适应调节策略（-XX:+UseAdaptiveSizePolicy）自动调整堆参数。
CMS（Concurrent Mark Sweep） 低停顿 老年代
STW
① 初始标记（Initial Mark）
仅标记 GC Roots 直接关联的对象，速度极快，STW 时间很短
并发
② 并发标记（Concurrent Mark）
从 GC Roots 开始遍历整个对象图，与用户线程并发执行，耗时最长但不影响业务
STW
③ 重新标记（Remark）
修正并发标记期间用户线程导致的标记变动（增量更新方式），STW，但远短于全量标记
并发
④ 并发清除（Concurrent Sweep）
与用户线程并发清除垃圾对象（标记-清除算法，不移动对象）
CMS 三大痛点：
① 浮动垃圾— 并发清除阶段新产生的垃圾只能下次收集，需预留内存（-XX:CMSInitiatingOccupancyFraction 默认 68%）
② 并发模式失败（Concurrent Mode Failure）— 浮动垃圾过多或内存碎片导致 CMS 来不及工作，退化为 Serial Old，Stop-the-World 全量清理，极慢
③ 内存碎片— 标记-清除算法不整理内存，长期运行后 Full GC 频繁
04 G1 收集器（重点）
核心设计：Region 化堆

G1 将整个堆划分为若干大小相等的 Region（1~32MB，2 的幂），每个 Region 可动态扮演不同角色：E（Eden）/ S（Survivor）/ O（Old）/ H（Humongous 大对象）。GC 时优先回收垃圾最多的 Region，在可控停顿时间内最大化释放内存。

G1 四种 GC 模式
模式触发条件回收范围STW？
Young GC Eden Region 用满 所有 Eden + Survivor Region 是（短暂）
Concurrent Cycle 老年代占堆比例超 InitiatingHeapOccupancyPercent（默认45%） 并发标记，不回收；只统计垃圾分布 初始标记 + 重新标记 STW
Mixed GC Concurrent Cycle 完成后触发 所有 Young Region + 垃圾最多的 Old Region（可配置比例） 是（可控停顿）
Full GC Mixed GC 来不及或 Humongous 分配失败 全堆标记-整理（单线程 Serial Old 方式） 是（极慢，应尽力避免）
关键技术点
  • ①Remembered Set（RSet）— 每个 Region 维护一个 RSet，记录哪些外部 Region 引用了本 Region 的对象，避免全堆扫描跨 Region 引用
  • ②Card Table— 将堆划分为 512 字节的 Card，写屏障时将被修改对象所在 Card 标记为 Dirty，扫描 RSet 时只需扫 Dirty Card
  • ③SATB 写屏障— 并发标记时若删除灰→白引用，将旧引用（白色对象）记录下来，重新标记时再扫，防止漏标
  • ④停顿预测模型— G1 统计每个 Region 的回收耗时，用衰减均值预测，在 -XX:MaxGCPauseMillis 限制内选择回收价值最高的 Region 集合（Garbage First 命名由来）
G1 vs CMS 选择：内存 ≥ 6GB 或对停顿敏感优先选 G1；JDK8 默认仍是 Parallel GC，JDK9+ 默认 G1。
05 ZGC / Shenandoah
ZGC 设计目标

ZGC（Z Garbage Collector）是 JDK11 引入（JDK15 正式产品化）的低延迟 GC，设计目标：

  • ①停顿时间 < 10ms（JDK16+ 优化到 <1ms），且不随堆大小增长
  • ②支持 TB 级别的堆（最大 16TB）
  • ③吞吐量损耗相对 G1 控制在 15% 以内
着色指针（Colored Pointers）

ZGC 的核心创新。在 64 位指针的高位借用 4 个 bit 存储 GC 状态元数据（仅 Linux/x86-64 支持）：

优势：GC 元数据直接嵌入指针，无需额外内存存放对象状态；通过读屏障（Load Barrier）在读取指针时检查颜色位，触发必要的修正（重映射/重标记），从而在用户线程执行期间完成对象转移，实现真正并发，极大缩短 STW。
ZGC vs G1 vs Shenandoah
收集器STW 停顿吞吐量适用堆大小核心技术
G1 几十~几百ms 高 6GB~几十GB Region + SATB + RSet
ZGC <10ms（几乎恒定） 中等（~15%损耗） GB~TB 级 着色指针 + 读屏障
Shenandoah <10ms 中等 中大型堆 Brooks 转发指针 + 读写屏障
06 GC 调优实战
核心 JVM 参数速查
# 堆大小（建议 Xms = Xmx，避免动态扩展导致 Full GC）
-Xms4g -Xmx4g

# 新生代大小（或用 NewRatio）
-Xmn1g                          # 直接指定新生代大小
-XX:NewRatio=2                  # Old:New = 2:1（即新生代占 1/3）
-XX:SurvivorRatio=8             # Eden:S0:S1 = 8:1:1

# 选择收集器
-XX:+UseG1GC                    # G1（JDK9+ 默认）
-XX:+UseZGC                     # ZGC（JDK15+ 生产就绪）
-XX:+UseConcMarkSweepGC         # CMS（JDK9 废弃，JDK14 删除）
-XX:+UseParallelGC              # Parallel（JDK8 默认）

# G1 调优
-XX:MaxGCPauseMillis=200        # 期望最大停顿时间（ms），默认200
-XX:G1HeapRegionSize=4m         # Region 大小，1~32m，建议2的幂
-XX:InitiatingHeapOccupancyPercent=45  # 触发并发标记的老年代占比

# 元空间
-XX:MetaspaceSize=128m          # 初始元空间大小（首次触发GC的阈值）
-XX:MaxMetaspaceSize=256m       # 元空间上限（防止无限增长）

# OOM 时自动 dump
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/tmp/heap.hprof

# GC 日志（JDK9+ 格式）
-Xlog:gc*:file=/var/log/gc.log:time,uptime:filecount=5,filesize=20m
调优思路：五步法
  • ①明确目标— 是追求高吞吐（批处理）还是低延迟（在线服务）？对停顿时间要求多少？
  • ②分析 GC 日志— 开启 -Xlog:gc*，用 GCEasy / GCViewer 分析 GC 频率、停顿时间、每次 GC 前后内存变化
  • ③选合适收集器— JDK8 低延迟选 CMS + ParNew，JDK11+ 选 G1 或 ZGC
  • ④调整参数— 先调堆大小，再调新老比例，最后精调收集器参数（如 MaxGCPauseMillis）
  • ⑤验证— 通过压测 + 监控（Prometheus + JVM micrometer）验证调优效果
常见问题排查
现象常见原因排查命令
频繁 Full GC 老年代过小 / 内存泄漏 / 大对象直接进老年代 jstat -gcutil <pid> 1000 观察 OU 增长
Promotion Failed Minor GC 时老年代没有连续空间容纳晋升对象（CMS碎片） 查看 GC 日志中 "promotion failed"，增大 Old 或提前 CMS
Concurrent Mode Failure CMS 并发清理来不及，老年代满，退化 Serial Old 降低 CMSInitiatingOccupancyFraction（如 60%）
G1 退化 Full GC Mixed GC 回收速度跟不上老年代增长 降低 InitiatingHeapOccupancyPercent，增加 Mixed GC 轮次
STW 时间过长 堆太大 / 跨代引用多 / Survivor 区对象未晋升 jstat -gccause 确认 GC 类型，考虑换 ZGC
