01为什么需要多 Agent
单 Agent 的瓶颈

单个 Agent 把所有职责（理解需求、规划步骤、调用工具、检查结果）塞进同一个 System Prompt 和同一段上下文里。任务简单时没问题，但当任务需要多种专业能力（比如既要写 SQL 又要写前端代码，还要做安全审查）时，单 Agent 会遇到明显瓶颈。

  • Prompt 膨胀：单个 System Prompt 要覆盖所有职责的规则，越写越长，LLM 容易"顾此失彼"——记住了写代码规范，忘了安全审查要求
  • 上下文污染：不相关任务的中间产物（比如调研阶段的搜索结果）会一直留在上下文里，干扰后续步骤的判断，也白白消耗 Token
  • 专业度打折：一个"万能" Agent 在每个细分领域的表现，通常不如针对该领域单独调优 Prompt 的专用 Agent
  • 缺乏并行：单 Agent 只能顺序执行，即使子任务之间没有依赖关系，也只能一步步排队做完
类比理解：单 Agent 像一个人身兼产品经理、程序员、测试、运维四个角色；多 Agent 是把这四个角色拆给四个专人，每人只需要精通自己的领域，配合一个"项目经理"来协调。
多 Agent 协作解决什么问题
  • 职责分离：每个 Agent 只负责一个领域（代码 Agent、检索 Agent、审查 Agent），System Prompt 更短更聚焦，指令遵循更准确
  • 上下文隔离：每个子 Agent 有自己独立的上下文窗口，只保留跟自己任务相关的信息，不会被无关内容干扰
  • 并行执行：互不依赖的子任务可以分给不同 Agent 同时跑，缩短整体耗时
  • 可组合、可替换：某个子 Agent 效果不好，可以单独换模型或调 Prompt，不影响其他 Agent
不是万能药：多 Agent 会引入协调开销——Agent 之间传递结果需要额外的 LLM 调用，整体延迟和成本通常比单 Agent 更高。任务简单、步骤少于 5 步时，先用单 Agent，不要一上来就上多 Agent。
02协作模式：中心化 vs 去中心化
两种基本协作拓扑

多 Agent 系统按"谁来决定下一步该谁做"分成两大类：中心化（Centralized）由一个统一的调度者分配任务；去中心化（Decentralized）由 Agent 之间直接互相传递任务，没有固定的"总指挥"。

维度中心化（Orchestrator）去中心化（Peer-to-Peer）
决策方式一个 Orchestrator Agent 统一分配任务、汇总结果Agent 之间直接对话，动态决定交给谁处理
可控性高，流程可预测，容易加日志和熔断低，Agent 间的交接路径可能不固定
扩展性新增 Agent 只需注册给 Orchestrator新增 Agent 需要教会所有相关 Agent 何时把任务转给它
失败排查容易定位是哪个环节出错（看 Orchestrator 的分配记录）较难，需要还原整条 Agent 间的交接链路
典型场景客服工单分诊、代码生成 + 审查流水线多角色头脑风暴、开放式协作探索
选型建议：绝大多数生产场景优先选中心化模式。它的可观测性和可控性远好于去中心化，出问题时能快速定位到具体环节，这在工程落地中比"更灵活的协作"更重要。
03Orchestrator-Worker（主从模式）
主从模式的核心角色

Orchestrator-Worker（也叫 Supervisor 模式）是工程落地中最常见的多 Agent 架构：一个 Orchestrator（调度者）负责理解用户目标、拆分子任务、决定交给哪个 Worker（执行者）处理，Worker 只管把分到的子任务做好，不需要理解全局目标。

①
接收用户目标
Orchestrator 拿到用户的完整需求，例如"帮我写一个用户注册接口，包含参数校验和单元测试"
②
拆分子任务
Orchestrator 判断需要哪些专业能力：写代码 → Code Agent，写测试 → Test Agent，检查安全性 → Security Agent
③
分发给 Worker
把子任务和必要的上下文（不是全部历史，只给该 Worker 需要的部分）传给对应 Worker Agent 执行
④
Worker 独立执行
每个 Worker 在自己独立的上下文里完成任务，不感知其他 Worker 的存在，返回结果给 Orchestrator
⑤
汇总与判断
Orchestrator 收集所有 Worker 的结果，判断是否需要再次分发（比如 Security Agent 发现漏洞，打回给 Code Agent 修复）
生成最终结果
所有子任务完成后，Orchestrator 汇总输出给用户
关键点：Worker 不需要知道自己在一个多 Agent 系统里，也不需要知道其他 Worker 的存在——这种"信息隔离"正是多 Agent 相对单 Agent 的核心优势之一。
串行 vs 并行分发
分发方式适用场景示例
串行（Sequential）后一个 Worker 依赖前一个的输出Code Agent 写完代码 → Test Agent 才能针对这份代码写测试
并行（Parallel）多个 Worker 互不依赖，可同时执行同时让三个 Research Agent 分别调研三个候选方案，再汇总对比
条件分发根据前一步结果决定分发给谁Security Agent 发现高危漏洞才触发 Fix Agent，否则直接结束
面试要点：面试常问"Orchestrator 怎么知道该并行还是串行"——答案是这是 Orchestrator Prompt 里显式设计好的策略（或者由 Orchestrator 的 LLM 根据任务描述动态判断依赖关系），不是框架自动推导的黑魔法。
04通信机制
消息传递 vs 共享状态

Agent 之间怎么交换信息，直接决定了系统的耦合度和可调试性。主流做法有两种：消息传递（Message Passing）——Agent 之间显式传结构化消息；共享状态（Shared State）——所有 Agent 读写同一份共享的状态对象（也叫 Blackboard 模式）。

方式数据流向优点缺点
消息传递点对点，A 的输出结构化后作为 B 的输入耦合低，每个 Agent 只关心自己的输入输出格式需要为每对 Agent 定义消息格式，Agent 一多容易组合爆炸
共享状态 / Blackboard所有 Agent 读写同一个共享对象新增 Agent 不需要改动已有 Agent，直接读写共享状态即可容易出现"谁改了这个字段"难排查，需要良好的状态 Schema 约束
工程落地建议：给共享状态定义严格的 Schema（哪些字段谁能写、谁只能读），并且每次状态变更都落一条日志。这样既保留了 Blackboard 模式的低耦合优势，又不丢可观测性。
Handoff：Agent 间的任务交接

Handoff（交接）指一个 Agent 主动把当前任务转交给另一个 Agent 处理的动作。实现上通常把"转交"包装成一种特殊的工具调用——Agent 输出"我要交给 XX Agent"，由框架层负责切换上下文和执行者。

  • 交接信息最小化：转交时只传递必要的上下文摘要，而不是把当前 Agent 的完整对话历史全部转发过去，否则下一个 Agent 的上下文会迅速膨胀
  • 交接可追溯：每次 Handoff 都要记录"谁转交给谁、为什么转交"，方便事后排查是哪一步决策出了问题
  • 避免循环交接：A 转给 B，B 又转回 A，如果没有终止条件会形成死循环，需要设置最大交接次数
05常见陷阱与工程实践
生产环境中的典型问题
  • 成本失控：每个 Agent 都是一次独立的 LLM 调用，N 个 Agent 协作一次任务，成本约等于 N 倍单 Agent 调用。上线前要估算最坏情况下的调用次数上限
  • 死循环 / 无限交接：Orchestrator 反复在两个 Worker 之间转发（比如 Test Agent 一直报错，Code Agent 一直"修复"却没修对），必须设置全局最大步数（通常 10-20 步）强制终止
  • 结果不一致：并行执行的多个 Worker 各自输出的结果格式不统一，汇总阶段解析困难。需要在分发子任务时就约定好统一的返回 Schema
  • 上下文丢失：Handoff 时如果传递的摘要遗漏了关键信息，下一个 Agent 会"凭空"做决策，导致结果偏离预期
  • 调试困难：多 Agent 系统的执行路径是动态的，同样的输入两次运行可能走完全不同的 Agent 组合。必须给每次运行打全链路 Trace ID，记录每个 Agent 的输入输出
先问自己一个问题：这个任务真的需要多 Agent 吗？很多"看起来复杂"的任务，用一个写得足够好的单 Agent + 更细致的 Prompt 就能搞定，且成本、延迟、可调试性都更好。多 Agent 应该是解决"单 Agent 已经优化到位但仍然不够"的最后手段，不是默认选项。
工程实践清单
  • 设最大步数：Orchestrator 的分发循环必须有硬上限，超过就强制终止并返回当前最优结果
  • 每步落日志：记录每次分发/交接的输入、输出、耗时、Token 消耗，用于事后排查和成本分析
  • Worker 无状态化：Worker 尽量设计成无状态的——每次调用只依赖传入的上下文，不依赖上一次调用留下的隐藏状态，这样才能安全地并行和重试
  • 超时与降级：单个 Worker 超时时，Orchestrator 要有降级策略（跳过该步骤 / 换个 Worker 重试 / 直接向用户报告部分结果），不能让整个流程卡死
06Java 实现
Orchestrator-Worker 的 Java 骨架

不依赖特定框架，用 CompletableFuture 实现一个最简单的 Orchestrator-Worker 结构：并行分发独立子任务，串行处理有依赖的子任务。

// 1. Worker 接口：每个 Worker 只关心自己的输入输出
public interface AgentWorker {
    String name();
    String execute(String taskContext);
}

// 2. Orchestrator：负责拆分任务、分发、汇总
public class Orchestrator {

    private final ChatClient plannerLlm;
    private final Map<String, AgentWorker> workers;
    private static final int MAX_STEPS = 15;

    public String run(String userGoal) {
        List<SubTask> plan = planTasks(userGoal);   // ① LLM 拆分子任务
        Map<String, String> results = new HashMap<>();
        int steps = 0;

        for (SubTask task : plan) {
            if (steps++ > MAX_STEPS) break;           // 防止无限循环

            if (task.dependsOn() == null) {
                results.put(task.id(), dispatch(task, results)); // 无依赖：直接执行
            } else {
                // 有依赖：等前置任务结果就绪后再执行（串行）
                results.put(task.id(), dispatch(task, results));
            }
        }
        return summarize(userGoal, results);           // ⑤ Orchestrator 汇总
    }

    // 并行分发一组互不依赖的子任务
    private Map<String, String> dispatchParallel(List<SubTask> independentTasks,
                                                    Map<String, String> ctx) {
        Map<String, CompletableFuture<String>> futures = independentTasks.stream()
            .collect(Collectors.toMap(SubTask::id,
                t -> CompletableFuture.supplyAsync(() -> dispatch(t, ctx))));
        futures.values().forEach(CompletableFuture::join);
        return futures.entrySet().stream()
            .collect(Collectors.toMap(Map.Entry::getKey, e -> e.getValue().join()));
    }

    private String dispatch(SubTask task, Map<String, String> ctx) {
        AgentWorker worker = workers.get(task.workerName());
        String minimalContext = buildHandoffContext(task, ctx); // 只传必要摘要，不传全部历史
        return worker.execute(minimalContext);
    }
}
  • Worker 接口最小化：只暴露 execute(context)，Worker 内部各自维护自己的 System Prompt 和工具集，Orchestrator 不关心其实现细节
  • buildHandoffContext：Handoff 时只截取任务相关的字段，不是把 results 整个 Map 全部转发，避免下游 Worker 上下文膨胀
  • 并行用 CompletableFuture：Spring AI / LangChain4j 场景下同样可以用这个模式包装多个 ChatClient 调用，实现互不依赖子任务的并发执行
  • MAX_STEPS 硬编码上限：无论 Orchestrator 的 LLM 怎么"决策"，代码层面的步数上限必须存在，这是最后一道防线
最佳实践：先用最朴素的 Java 代码把 Orchestrator-Worker 骨架跑通、加好日志和步数上限，再考虑要不要引入 LangChain4j / Spring AI 的多 Agent 编排能力。框架能省样板代码，但步数上限、成本监控、Trace 这些工程护栏永远需要自己把关。
