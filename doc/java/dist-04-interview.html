Q1 CAP 定理是什么？所谓"三选二"的真实含义？ 高频重点 ▾
考察点

CAP 是分布式入门题，但市面上的"三选二"说法有误导性。能讲清"P 是必选"加分。

参考回答

CAP 是说一致性（C）、可用性（A）、分区容忍性（P）三者不可兼得：

  • ▸ C：所有节点同一时刻看到相同数据，读必读到最新写
  • ▸ A：非故障节点都能在合理时间返回非错误响应
  • ▸ P：网络分区时系统继续工作

真实的取舍不是三选二，而是 P 必选。因为在真实分布式系统里网络分区一定会发生，放弃 P 就退化成单机。所以选择只发生在分区时选 C 还是选 A：

类型分区时行为代表
CP少数派拒绝服务，宁可不可用也不返回旧数据ZK、etcd、HBase
AP各分区继续服务，可能返回旧数据，事后收敛Eureka、Cassandra、Dynamo

Q2 BASE 理论和 ACID 有什么区别？ 高频 ▾
考察点

常和 CAP 一起考。重点是"BASE 是 AP 的工程落地，与 ACID 是取舍关系而非对立"。

参考回答

BASE 是 Basically Available（基本可用）、Soft state（软状态）、Eventually consistent（最终一致），是 eBay 工程师对 CAP 中 AP 一侧的落地总结。

维度ACIDBASE
一致性强一致：写完立即可见最终一致：可能短暂看到旧值
可用性故障时宁可不可用故障时降级保响应
性能跨节点协调开销大异步复制，吞吐高
典型场景银行转账、库存扣减商品浏览、社交评论

实际系统几乎都是"局部 ACID + 全局 BASE"：单库内用事务保强一致，跨库跨服务用消息/补偿走最终一致。

Q3 说说你理解的"一致性"等级？强一致和最终一致区别？ 重点 ▾
考察点

分布式系统里"一致性"有多种精细划分，能讲出 4~5 档基本到位。

参考回答
等级含义
线性一致所有操作像在全局时钟下原子按真实时间执行。读必读到最新写
顺序一致所有节点看到的操作顺序一致，但不要求和真实时间一致。ZK 是这一档
因果一致有因果关系的操作所有节点看到顺序一致，无因果不要求
读己之写用户能读到自己刚写的（避免发完朋友圈刷不到自己）
最终一致停止写入后，足够长时间后所有副本收敛一致

线性一致 vs 顺序一致的小例子：A 在 10:00 写 x=1，B 在 10:01 读 x。线性一致要求 B 必读到 1；顺序一致只要求"全集群先看到写、再看到读"这个顺序，具体时间可以滞后，B 可能读到 0。

Q4 Paxos 算法的核心流程？为什么工程上很少直接用？ 重点 ▾
考察点

不要求复述完整证明，能讲两阶段流程 + Multi-Paxos 工程难点即可。

参考回答

Basic Paxos 让多个节点对一个值达成一致，分两阶段：

  • ① Prepare：Proposer 选递增编号 N，向 Acceptor 发 Prepare(N)。Acceptor 承诺"不再接受 < N 的提案"，回复已接受的最大提案
  • ② Accept：Proposer 收到多数派回复后，从回复里挑"已接受的最大编号"对应的值（没有就用自己想提的），发 Accept(N, v)。多数派接受即达成共识

工程上很少直接用的原因：

  • ▸ 只能对单个值达成共识，实际要 Multi-Paxos 选 Leader 跳过 Prepare 才能复制日志
  • ▸ 论文只给核心证明，不给完整工程实现，每家公司的 Paxos 长得都不一样
  • ▸ Leader 选举、日志补洞、配置变更等都要自己设计，正是因为难懂难落地才催生了 Raft

Q5 Raft 怎么选 Leader？怎么保证日志一致？ 高频重点 ▾
考察点

共识算法里最常考的。能说出"随机超时"和"日志至少和我一样新"这两个关键点加分。

参考回答

选 Leader：节点有 Follower / Candidate / Leader 三态。Follower 在随机选举超时（150~300ms）没收到心跳就变 Candidate，term + 1 给自己投一票，向其他节点拉票。投票规则：① 本 term 还没投过 ② 候选人日志至少和我一样新（按 last log term，相同比 last log index）。赢得多数派即变 Leader。

日志复制：Leader 收到写请求 → 追加本地日志 → 并行发 AppendEntries 给 Follower → 多数派写入后推进 commitIndex → 应用到状态机 → 返回客户端。

关键安全约束：

  • ▸ Election Restriction：日志比候选人新的节点不会投票给他，保证 Leader 一定有最新的已提交日志
  • ▸ Log Matching：相同 (term, index) 位置内容相同，则之前所有日志都相同。Leader 用 prevLogIndex/prevLogTerm 强制 Follower 对齐

这两条加起来，保证已提交的日志永远不会被覆盖。

Q6 ZAB 协议和 Raft 有什么区别？ 重点 ▾
考察点

容易混淆，能说清两个关键差异（提交方式、读策略）就到位。

参考回答

ZAB 是 ZooKeeper 专用的原子广播协议，本质和 Multi-Paxos / Raft 解决同一类问题，主要差异：

维度ZABRaft
提交方式两阶段 propose + commit一阶段 AppendEntries 携带 commitIndex
选主标准zxid 最大者优先(last log term, last log index) 大者优先

典型实现ZooKeeperetcd、TiKV、Consul

本质上都是基于多数派共识 + 选主 + 日志复制的同一类协议，差异在工程细节。

Q7 ZooKeeper 是 CP 还是 AP？为什么？ 高频 ▾
考察点

CAP 落地题，常和 Eureka 对比。

参考回答

ZK 是 CP。原因有两点：

  • ① 写操作必须走 ZAB 共识，由 Leader 协调所有 Follower 达成多数派一致才返回成功
  • ② 发生网络分区时，少数派分区因为凑不齐多数派，拒绝服务。整个集群对外表现为"不可用"，但保证不会返回不一致数据

对比 Eureka（AP）：分区时每个节点都继续提供服务，宁可返回过期的服务列表也要响应，事后收敛。两者代表 CAP 的两种典型取舍。

面试加分：① ZK 严格说是"顺序一致"而非"线性一致"，但分区时少数派不可用，整体属于 CP；② Nacos 同时提供 CP 模式（基于 Raft）和 AP 模式（基于 Distro 协议），可选择。

Q8 什么是拜占庭将军问题？CFT 和 BFT 有什么区别？ 基础 ▾
考察点

偏理论。日常工作几乎不用，能点到核心区别即可，深挖 PBFT 是加分项。

参考回答

拜占庭将军问题描述的是节点可能作恶的共识场景：发假消息、给不同人发不同消息。Paxos / Raft / ZAB 都假设所有活节点诚实，只容忍宕机，属于 CFT；要容忍作恶就需要 BFT。

对比CFTBFT
故障模型宕机 / 丢包，但不撒谎节点可能任意作恶
节点数要求≥ 2f+1 容忍 f 个故障≥ 3f+1 容忍 f 个作恶
性能高低，消息复杂度 O(n²)
场景公司内网集群公链、跨组织联盟链
代表Paxos、Raft、ZABPBFT、HotStuff、Tendermint

日常工作接触的中间件（ZK / etcd / Kafka / Redis）几乎全是 CFT。BFT 只在区块链和跨机构联盟系统里需要。

Q9 为什么需要分布式事务？说说你了解的常见方案？ 高频 ▾
考察点

开放题，主要看能不能把方案分类讲清楚，并说出各自适用场景。

参考回答

单库事务靠 MySQL 的 redo/undo log + 锁就能保证 ACID。一旦跨库（分库分表）或跨服务（订单 → 库存 → 支付），各方有自己的事务日志互相看不到，谁都不能单独决定提交还是回滚。常见方案按一致性强度分两类：

类型方案特点
强一致2PC / XA同步阻塞，性能低，金融行业常用
强一致TCC资源预留，业务侵入大，性能高

最终一致本地消息表业务表 + 消息表同事务，简单可靠
最终一致MQ 事务消息RocketMQ 半消息 + 二次确认 + 回查
最终一致Seata AT业务无侵入，自动写 undo_log 回滚

面试时先反问"业务一致性要求多强"，再给方案。盲目套 2PC / TCC 会被认为缺乏经验。

Q10 2PC 协议是什么？有哪些经典问题？ 高频重点 ▾
考察点

必考。流程要熟，三大缺陷必背。

参考回答

2PC = Two-Phase Commit。协调者 + 参与者，分两阶段：

  • ① Prepare：协调者问所有参与者"能提交吗"，参与者执行本地事务（写 undo/redo log），但不提交持锁等待，回 YES / NO
  • ② Commit / Rollback：协调者收齐投票，全 YES 发 commit，任一 NO 或超时发 rollback

三大缺陷：

  • ▸ 同步阻塞：阶段 1 后所有参与者持锁等待，锁定时间长，吞吐被锁死
  • ▸ 单点故障：协调者宕机，参与者不知道该 commit 还是 rollback，只能死等
  • ▸ 数据不一致：阶段 2 commit 时若部分参与者收到、部分没收到（网络故障），就会出现部分提交、部分未提交

正是因为这三个缺陷，生产环境几乎不直接用原生 2PC。MySQL 内部 binlog 与 redo log 的协同其实就是 2PC，但那是单机内的。

Q11 3PC 比 2PC 好在哪里？真的解决问题了吗？ 进阶 ▾
考察点

3PC 是经典反面教材：解决了部分问题但没解决根本问题。能讲清这一层即到位。

参考回答

3PC 把 2PC 的两阶段拆成三阶段，引入超时机制 + 询问阶段：

  • ① CanCommit：协调者问参与者"能不能提交"，只做轻量检查（资源是否就绪），不真正执行事务
  • ② PreCommit：收齐 YES 后正式执行本地事务，写 undo/redo，持锁
  • ③ DoCommit：协调者发提交。若参与者 PreCommit 后超时没收到 DoCommit，默认自动提交（赌大家都准备好了，协调者大概率发的是 commit）

3PC 没解决根本问题：超时自动提交看似减少阻塞，但如果协调者实际发的是 rollback 只是网络丢了，参与者就会自动错误地提交，依然产生不一致。3PC 工程上几乎没人用，复杂度上升一档但可靠性没本质提升。

Q12 TCC 是什么？空回滚、幂等、悬挂分别是什么？ 高频重点 ▾
考察点

TCC 三大坑是高频深挖题，能讲清成因 + 解决方案才算通过。

参考回答

TCC = Try / Confirm / Cancel，把业务操作拆成三个方法：

  • ▸ Try：预留资源（冻结余额、占用库存），不真正扣减
  • ▸ Confirm：全部 Try 成功后，把冻结的资源真正扣掉
  • ▸ Cancel：任一 Try 失败，释放预留资源

三大经典坑：

  • ① 空回滚：Try 因为网络问题没执行，但协调器超时了直接调 Cancel。Cancel 收到一个自己根本没 Try 过的 txId。
    解决：Cancel 时先查"是否有 Try 过的痕迹"，没有则空操作
  • ② 幂等：Confirm 和 Cancel 可能因为重试被调多次。
    解决：用 txId 做唯一键去重，已处理的直接返回成功
  • ③ 悬挂：Cancel 先到（网络乱序），Try 后到。如果 Cancel 已"假装回滚"，Try 又来冻结资源，就再也没人 Cancel 这一笔了，资源永远悬挂。
    解决：Cancel 时记录"已被取消"标志，Try 看到标志直接拒绝

所以 TCC 业务侵入大，适合一致性要求高、性能要求高的核心业务（支付、账务），不适合普通 CRUD。

Q13 Saga 模式是什么？编排式和协调式有什么区别？ 重点 ▾
考察点

长流程业务场景下的常见方案，能讲清和 TCC 的区别加分。

参考回答

Saga 把长事务拆成一连串本地事务 T1, T2, ..., Tn，每个本地事务对应一个补偿事务 C1, C2, ..., Cn。任一步失败，按逆序调用前面已成功步骤的补偿。

和 TCC 的核心区别：Saga 直接执行业务，没有 Try 阶段的预留。中间状态对外可见。

风格原理优缺点
Choreography 编排式服务通过事件互相驱动，T1 完成发事件，下游订阅事件触发 T2去中心化、低耦合；但链路看不见、调试难、循环依赖风险
Orchestration 协调式中央协调器按预定流程显式调用每个服务流程清晰、易追踪；协调器是中心化组件，要保证它本身高可用

补偿设计要点：① 幂等 ② 允许"语义补偿"而非"数据回滚"（短信无法撤回，发修正短信） ③ 补偿失败要重试 + 人工兜底。

Q14 本地消息表和最大努力通知怎么实现？ 高频 ▾
考察点

互联网常用方案，实现简单但要讲清"为什么把业务表和消息表放同库"。

参考回答

核心思路：把"业务操作"和"要发的消息"放在同一个本地事务里。业务表 + 消息表同库同事务，要么都成功要么都失败，就把"分布式事务"问题降级为"本地事务 + 异步重试"。

  • ① 业务库写入业务表 + 消息表（同事务，消息 status=待发送）
  • ② 独立线程/定时任务扫消息表，把待发送的消息发到 MQ，发成功后改为已发送
  • ③ 消费者处理 + 回执确认。失败则不断重试

最大努力通知是本地消息表的近亲：扫描表里"未确认成功"的消息，按递减频率不断重试（1s → 5s → 30s → 5min → 1h），直到收到下游回执或超过最大次数转人工。常用于跨公司接口（支付通知商户、银行通知客户）。

优点：实现简单、性能高、可靠性好；缺点：只能最终一致、消息表与业务库耦合（分库分表时每片都要有）。

Q15 RocketMQ 事务消息是怎么实现的？为什么需要回查？ 高频重点 ▾
考察点

RocketMQ 特色功能，能讲全四个步骤 + 回查作用即到位。

参考回答

RocketMQ 通过"半消息 + 二次确认 + 事务回查"做到"消息发送与本地事务的原子性"：

  • ① 生产者发半消息到 Broker，半消息已存储但对消费者不可见
  • ② 生产者收到 Broker 确认后，执行本地事务（写订单库）
  • ③ 根据本地事务结果，向 Broker 发二次确认：commit → 半消息转正常消息可见；rollback → 删除半消息
  • ④ 事务回查：如果生产者执行本地事务后宕机，二次确认丢了，Broker 一段时间未收到确认会主动回查生产者"这笔事务到底成没成"，生产者根据本地状态告诉 Broker commit 还是 rollback

为什么需要回查：第 ② 步和第 ③ 步之间生产者可能宕机，二次确认永远不会到达。如果没有回查，半消息会永远挂在 Broker 里。回查是兜底机制，保证最终一致性。

实现成本：业务方必须根据事务 ID 能查询本地事务最终状态。这意味着事务状态要持久化，并提供查询接口。

Q16 Seata 有几种模式？AT 模式怎么回滚？ 重点 ▾
考察点

Seata 是阿里开源框架，AT 模式是默认且最常用的，重点考"自动写 undo_log 回滚"。

参考回答

Seata 有四种模式：AT（默认）、TCC、Saga、XA。架构都是 TC（事务协调器，独立部署）+ TM（事务管理器，发起方）+ RM（资源管理器，参与方）三角色。

AT 模式回滚流程：

  • ① 一阶段：Seata 拦截业务 SQL，在执行前后分别查询数据快照，把"修改前镜像 + 修改后镜像"写入 undo_log 表（与业务表同库）。本地事务直接提交，立即释放行锁
  • ② 二阶段：全局事务成功 → TC 通知 RM 异步删除 undo_log；失败 → RM 读 undo_log 中"修改前镜像"反向生成 SQL 回滚数据

AT 模式的隔离性问题：一阶段就提交本地事务释放行锁，意味着其他事务能立刻看到"未最终提交"的脏数据。Seata 通过 SELECT ... FOR UPDATE 改写 + 全局锁解决，但仍有性能折损。AT 适合 CRUD 中等并发，不适合高并发热点账户。

Q19 释放 Redis 分布式锁为什么要用 Lua 脚本？ 高频重点 ▾
考察点

常和 Q18 一起考。要能讲清"误删别人的锁"这个场景。

参考回答
// ❌ 直接 DEL 有风险
if (get(lock) == myUuid) {  // 第 1 步：判 value
    del(lock);              // 第 2 步：删 key
}
// 问题：① app-1 GC 卡顿 30s，锁已自动过期
//      ② app-2 抢到新锁
//      ③ app-1 醒来执行 del → 把 app-2 的锁误删

// ✅ Lua 脚本：判 + 删 原子
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end

Redis 单条命令是原子的，但多条命令组合不是原子的。Lua 脚本在 Redis 中作为一个整体执行，中间不会被其他命令打断，保证"判 value → 删 key"必然连续。

面试时常被追问"为什么 Redis 事务 MULTI/EXEC 不行"：MULTI 不能在事务中根据中间结果决策，没法做 if 判断；Lua 才能写控制流。

Q20 Redlock 是什么？为什么有争议？ 重点 ▾
考察点

进阶题。能说出 Martin Kleppmann 的质疑加分。

参考回答

单 Redis 节点的锁有隐患：主节点宕机切到从时，如果主从没完成同步，新主可能丢失这把锁，导致两个客户端同时持锁。Redis 作者 antirez 为此提出Redlock：

  • ① 向 N 个独立 Redis 节点（通常 5 个）依次申请锁，记录起始时间 T0
  • ② 如果 ≥ ⌈N/2⌉+1 个节点抢锁成功，且总耗时 < 锁有效期，视为获锁成功
  • ③ 真正可用有效期 = 原有效期 − 申请阶段总耗时

著名争议：Martin Kleppmann（《DDIA》作者）撰文指出，Redlock 在 GC 暂停、时钟漂移等场景下仍可能两个客户端同时持锁，本质上是因为它依赖"墙上时间"判断锁有效性。antirez 撰文回应，争议至今没有定论。

实践建议：

  • ▸ 普通业务用单节点 + Redisson 看门狗已经够用
  • ▸ 对正确性要求极高（金融）应该用 ZooKeeper / etcd 的 CP 锁，不要用 Redlock

Q21 ZooKeeper 怎么实现分布式锁？为什么只监听前一个节点？ 高频重点 ▾
考察点

"避免惊群"是关键考点，没说到这一层算没答完。

参考回答

ZK 锁基于两个核心特性：临时节点（会话断开自动删）+ 顺序节点（ZK 自动给名字加递增后缀）。

  • ① 客户端在 /lock 下创建临时顺序节点，比如 /lock/req-0001
  • ② 看自己是不是最小的节点，是 → 获锁
  • ③ 不是最小 → 只监听前一个节点的删除事件，挂起等待
  • ④ 收到 watch 通知 → 再检查自己是否最小 → 是则获锁

为什么只监听前一个：如果所有等待者都监听 /lock 整个目录，锁释放时会"惊群"——N 个客户端同时被唤醒抢锁，但只有一个能成功，其余 N-1 个白醒。只监听前驱，每次释放只唤醒紧接着的下一个，避免惊群效应。

客户端宕机：会话超时（默认 30s）后临时节点自动删，后继自动获锁。比 Redis 锁的 TTL 更可靠（TTL 是估算业务耗时，会话超时是探测真实存活）。

Q23 Redisson 的看门狗机制是怎么实现的？ 重点 ▾
考察点

常被问的细节题。能讲出"自动续期 + 客户端宕机自动失效"加分。

参考回答

SET NX PX 的最大痛点：TTL 怎么定？设短了业务还没干完就过期；设长了宕机后别人等太久。Redisson 用看门狗自动续期解决：

// 不显式指定 TTL → 开启看门狗
RLock lock = redisson.getLock("order:123");
lock.lock();  // 默认 30 秒锁，每 10 秒续期一次
try {
    // 业务代码...
} finally {
    lock.unlock();
}

// 显式指定 TTL → 不开看门狗
lock.lock(10, TimeUnit.SECONDS); // 10 秒后必释放
  • ▸ 续期周期 = lockWatchdogTimeout / 3，默认 30s/3 = 10s 续一次
  • ▸ 客户端宕机 → 后台续期任务不再运行 → 30s 后锁自动释放
  • ▸ 底层实现：每次续期都是一个 Lua 脚本，先检查是不是自己的锁，再 PEXPIRE 续到 30s

可重入也基于 Hash 实现：field=客户端ID，value=重入次数，加一次 +1，释放时 -1 减到 0 才真正 DEL。

Q26 雪花算法的时钟回拨问题怎么解决？ 重点 ▾
考察点

能讲出几种典型应对方案即可。

参考回答

Snowflake 严重依赖本机时钟。如果机器时钟被回拨（NTP 同步、运维误操作），同一时间戳 + 同一序列号会生成相同 ID。常见解决方案：

  • ① 等待：检测到小幅回拨（< 几秒），等待时钟追上来再发号
  • ② 拒绝：回拨幅度大直接抛异常拒绝发号，等运维介入
  • ③ 扩展 bit：百度 UidGenerator 用额外字段记录"回拨次数"，回拨时给这个字段 +1 规避冲突
  • ④ 外部校验：美团 Leaf 的 leaf-snowflake 模式，启动时去 ZK 比对时间，确认未回拨才发号
  • ⑤ 绕开时钟：彻底放弃雪花，改用号段模式（Leaf-segment）

生产中常用组合：检测到回拨小幅就等待，大幅就拒绝并告警，运维介入处理时钟问题。

Q27 号段模式是什么？Leaf 的双 Buffer 是怎么优化的？ 进阶 ▾
考察点

号段切换抖动是关键考点，能讲清"为什么需要双 Buffer"加分。

参考回答

号段模式：每次从 DB 批量取一段 ID 到内存，比如 step=1000 就一次取 1000 个，内存里分配完了再去 DB 取下一段。QPS 直接放大 1000 倍。

// 号段表
CREATE TABLE id_segment (
    biz_tag VARCHAR(64) PRIMARY KEY,
    max_id BIGINT,
    step INT
);
// 取号段：UPDATE max_id = max_id + step

问题：当前号段用完时去 DB 取下一段，这一瞬间会卡几毫秒，并发请求堆积。

Leaf 双 Buffer 优化：服务端维护两个号段 Buffer（current + next）。当 current 用了 10% 时异步预取 next，等 current 真正用完时直接切到 next，几乎无感知。next 用了 10% 又异步预取下一段。

  • ▸ 平时：current 用 90%、next 待命
  • ▸ current 用尽：切到 next（瞬时），同时异步取下一个 next
  • ▸ DB 短暂不可用：靠 next 撑过去，期间不阻塞业务

Q28 为什么 UUID 不适合做 MySQL 主键？ 高频 ▾
考察点

InnoDB 聚簇索引底层知识。能说出"页分裂"和"索引膨胀"加分。

参考回答

UUID 是 36 字符随机字符串，作为 InnoDB 主键有三个硬伤：

  • ① 无序导致页分裂：InnoDB 主键是聚簇索引，数据按主键顺序存储。新插入的 UUID 是随机的，会插到 B+ 树中间，导致频繁页分裂和数据移动，写性能大幅下降
  • ② 索引体积大：UUID 36 字符（即使去掉横线也 32 字符），而 bigint 只占 8 字节。MySQL 所有二级索引都包含主键，主键大 → 二级索引也膨胀 → 内存放下的索引页减少 → 查询变慢
  • ③ 不可读：日志里看 UUID 没业务意义，不像数字 ID 能看出大致下单时间

正确做法：

  • ▸ 主键用趋势递增的数字 ID（雪花算法、Leaf）
  • ▸ UUID 适合做"对外暴露的非主键 ID"——用户 token、文件名、trace ID、分享链接，这些不进聚簇索引

Q31 你怎么权衡分布式系统中的一致性和性能？ 重点 ▾
考察点

开放设计题，看架构思维。能从业务出发讲取舍加分。

参考回答

核心原则：不是技术决定一致性等级，是业务决定。我会按业务分层来设计：

  • ▸ 金钱、库存、账务：强一致优先。本地事务能解决就单库 ACID；跨库跨服务上 TCC 或 Seata AT
  • ▸ 订单状态、用户基础信息：读多写少，加 Redis 缓存做读扩散，写时同步双删保证缓存一致
  • ▸ 评论、点赞、动态、推荐：最终一致即可。先入 MQ 异步落库、异步同步到搜索引擎，用户感知不到
  • ▸ 日志、监控、统计：最弱一致，丢一点没关系，用 Kafka + Flink 流处理

每层都对应不同的存储和处理模式。把所有业务一律按强一致设计是新手最常见的过度设计，会浪费性能预算并把简单问题变复杂。

另一个常用技巧：把"看似的强一致"降级为"最终一致 + 用户侧补偿"。比如下完订单立即显示"已下单成功"（其实只写了主库，库存异步扣），后台再异步处理后续动作，体验上是即时的，但底层是最终一致。

Q32 在你做过的项目里，分布式事务方案是怎么选的？为什么？ 高频 ▾
考察点

典型项目经验题。要结合具体业务场景讲，避免空谈方案。

参考回答

我会按下面这个顺序问自己（也是回答这种题的模板）：

  • ① 业务一致性强度：能接受秒级最终一致 → 走 MQ / 本地消息表；不能接受 → 走 TCC / Seata
  • ② 是否高并发：高 QPS（> 1000）就别用 XA / Seata AT 这种持锁方案
  • ③ 业务能否改造：原有业务代码不能动 → Seata AT 注解式；能改造 → TCC / Saga
  • ④ 团队能力：Seata 部署成本、TCC 三大坑、Saga 补偿设计，都需要团队真有人能扛

  • ▸ 下单扣库存场景：用 RocketMQ 事务消息。下单是写订单库 + 发"扣库存"消息，业务可以接受库存秒级延迟。RocketMQ 半消息 + 二次确认保证订单和消息原子，库存服务异步消费。性能好，业务侵入小
  • ▸ 支付扣款场景：用 TCC。资金账户要求强一致，且高并发（活动期 QPS 几万）。Try 阶段冻结余额、Confirm 阶段真正扣减，配合幂等表防重复，业务侵入大但性能和正确性都满足

面试加分：能讲出"为什么没选另一种方案"——比如"为什么下单没用 TCC"（TCC 拆三方法成本太高，库存只是普通业务不值得）——说明真做过取舍。
