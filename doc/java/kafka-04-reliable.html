01消息不丢失
消息丢失的三个环节

Kafka 消息从 Producer 发出到 Consumer 处理完，任何一环都可能丢失消息，必须三端联动配置：

P
生产者侧丢失
发送消息后 Leader 宕机，或 acks=0/1 配置过低，Leader 确认后 Follower 还未同步即宕机，消息丢失。
B
Broker 侧丢失
Leader 宕机后，unclean.leader.election=true 导致落后的 OSR 副本成为新 Leader，已确认的消息被覆盖丢失。
C
消费者侧丢失
自动提交或处理前提交 Offset，消费者拉取消息后宕机，Offset 已提交但消息实际未处理完，下次重启不再消费该消息。
三端联动 — 最强可靠性配置清单
🟢 PRODUCER 端
acks=all — 等全部 ISR 副本写入确认
retries=Integer.MAX_VALUE — 无限重试，配合超时兜底
enable.idempotence=true — 避免重试导致重复
delivery.timeout.ms=120000 — 整体 2min 超时兜底
捕获 send() 回调异常，失败时告警或写重发队列
🔵 BROKER 端
replication.factor≥3 — 至少 3 副本，容忍单节点宕机
min.insync.replicas=2 — ISR 至少 2 副本写入才确认
unclean.leader.election=false — 禁止 OSR 副本成 Leader
log.flush.interval.messages — 一般不配（依赖副本，强刷盘性能差）
🟡 CONSUMER 端
enable.auto.commit=false — 关闭自动提交
业务处理完成后手动 commitSync()
处理失败时不提交 Offset，允许重消费
结合幂等设计，消除重消费带来的副作用
黄金三件套：acks=all + min.insync.replicas=2 + unclean.leader.election.enable=false，生产环境必须同时配置这三项。
⚠ 强刷盘的代价：log.flush.interval.messages=1 每条消息强制 fsync，吞吐量骤降 10x+。绝大多数场景依靠副本机制保证持久性即可，无需强刷盘。
02幂等消费（不重复）
为什么会重复消费
场景原因
消费者处理中宕机Offset 未提交，重启后重新消费同一批消息
Rebalance 触发新 Consumer 从上次提交的 Offset 开始，与上一消费者有重叠
commitSync() 异常提交失败未处理，下次 poll 重新消费
处理超过 max.poll.interval.msConsumer 被踢出 Group，Partition 被重分配，消息再次消费
业务层幂等方案对比
方案原理适用场景注意点
数据库唯一键 以消息 ID / 业务唯一键作 UNIQUE KEY，重复 INSERT 触发唯一键冲突，忽略异常 Insert 类操作，数据量不大 需捕获 DuplicateKeyException，UPDATE 场景不适用
Redis SETNX 消费前 SET msgId NX EX 86400，已存在则跳过 高并发去重，Redis 可用性高 Redis 与 DB 操作非原子，极端情况下仍可能重复，需配合 DB 幂等
状态机判断 只在允许状态下执行变更（订单只能从 CREATED → PAID），重复操作被状态拦截 有明确状态流转的业务（订单、审批） 需在事务内"查状态 + 变状态"，防止并发下多次执行
乐观锁版本号 UPDATE … WHERE id=? AND version=?，重复操作版本号不匹配自动失败 UPDATE 类操作，业务对象有 version 字段 更新失败需判断是幂等（已处理）还是真正冲突
①
Consumer 拉到消息 msgId = abc123
②
Redis.get("processed:abc123") — 是否已处理？ 已存在 → 跳过，提交 Offset
③
↓ 不存在 — 执行业务逻辑（写 DB）
④
Redis.set("processed:abc123", 1, EX 86400) 成功
⑤
commitSync() 提交 Offset
⚠ ③④ 非原子性：若步骤 ③ 写库成功，步骤 ④ Redis 写入前宕机，下次 Redis 中无记录会再次执行 ③。因此写库本身也需保证幂等（如唯一键），不能单纯依赖 Redis 去重。
03消息顺序消费
全局顺序 vs 局部顺序（Key 级别）
🌐 全局顺序
Topic 只有 1 个 Partition
Consumer Group 内只有 1 个 Consumer
✅ 所有消息严格按发送顺序消费
❌ 吞吐量受单 Partition 限制
❌ Consumer 宕机时不可用
🔑 局部顺序（Key 级别）
按业务 Key 路由到固定 Partition
相同 Key 的消息保证有序
✅ 高吞吐，不同 Key 可并行消费
⚠️ 同一 Partition 内 Consumer 单线程处理
⚠️ 扩分区后 Key 路由结果改变
⚠ 扩分区破坏 Key 路由一致性：Partition 数变化后，murmur2(key) % partitionCount 结果改变，相同 Key 可能落不同 Partition 导致顺序混乱。扩分区应在业务低峰期操作，并处理迁移期间的顺序问题。
多线程消费与顺序保证
模式顺序保证吞吐量说明
单线程 poll + 单线程处理 ✅ 严格顺序低 默认模式，一个 Consumer 单线程顺序处理 Partition
单线程 poll + 线程池处理 ❌ 无法保证高 线程调度导致乱序，不推荐顺序敏感场景
按 Key 路由线程 ✅ 相同 Key 有序中高 poll 后按 key.hashCode() % poolSize 路由到固定线程，相同 Key 始终同一线程
多 Consumer 实例（数量=Partition 数） ✅ Partition 内严格顺序高 每个 Consumer 独占一个 Partition，最常用方案 
// 按 Key 路由到固定线程 — 保证相同 Key 有序
ExecutorService[] workers = new ExecutorService[THREAD_NUM];
for (int i = 0; i < THREAD_NUM; i++) {
    workers[i] = Executors.newSingleThreadExecutor();
}

for (ConsumerRecord<String, String> record : records) {
    int idx = Math.abs(record.key().hashCode()) % THREAD_NUM;
    workers[idx].submit(() -> process(record)); // 相同 key → 相同线程 → 顺序保证
}
// 注意：提交 Offset 时需等待对应线程处理完毕，否则可能丢失
04消息积压处理
积压应急处理 — 四步方案
STEP 01
确认根因
检查 Consumer Lag 趋势、消费速率、业务处理耗时、下游 DB/Redis 响应时间
STEP 02
快速扩容
新增 Consumer 实例（≤ Partition 数），触发 Rebalance，立即提升并行消费能力
STEP 03
批量消费
增大 max.poll.records，批量入库代替逐条处理，大幅减少数据库 IO 次数
STEP 04
临时扩分区
极端情况：停止原 Topic 写入，消费后转发到多分区新 Topic，用更多 Consumer 处理
积压根因排查与对策
现象可能原因解决方向
消费速率持续低于生产速率业务处理耗时长（DB 慢查询、外部服务超时）优化处理逻辑，引入异步化、批量、连接池
Lag 突然暴增流量突发（大促、秒杀活动）Consumer 扩容，对非核心逻辑降级
部分 Partition 积压，其他正常热点 Key 导致单 Partition 消息量远高于其他打散热点 Key（加随机后缀），热点 Topic 单独处理
Consumer 频繁 Rebalance处理耗时超过 max.poll.interval.ms，Consumer 被踢出 Group调大 max.poll.interval.ms，减小 max.poll.records，异步化处理
Consumer 已达 Partition 数上限无法再增加 Consumer 实例先增加 Partition 数（注意 Key 路由一致性），再增加 Consumer
监控命令：kafka-consumer-groups.sh --bootstrap-server xxx --describe --group my-group
重点关注 LAG 列（= HW − CurrentOffset），以及 CONSUMER-ID 是否有空行（有 Partition 没有 Consumer 分配）。
05延迟消息与消息回溯
延迟消息 — Kafka 原生不支持，替代方案
方案原理优点缺点
延迟 Topic 分级 预建多个延迟 Topic（delay_1s / delay_5s / delay_30s），消息先发到对应 Topic，延迟 Consumer 到期后转发到目标 Topic 纯 Kafka 实现，无外部依赖 延迟精度粗，时间级别有限，Consumer 持续 poll
Redis Sorted Set 消息存入 ZSet（score = 执行时间戳），定时任务扫描到期消息发到 Kafka 实现简单，精度取决于扫描频率 Redis 容量限制，扫描间隔有误差
时间轮（HashedWheelTimer） 消息持久化 + 内存时间轮定时调度，到期后发 Kafka 延迟精度高（毫秒级） 需持久化支持宕机恢复，内存占用
使用 RocketMQ 原生支持 18 个延迟级别（1s ~ 2h），复杂延迟场景更合适 开箱即用，语义完整 引入新 MQ 组件，运维成本增加
消息回溯 — 重置消费位置

Kafka 数据在 retention.ms（默认 7 天）内可随时重新消费：

// 代码方式：seek 到指定位置
consumer.subscribe(Arrays.asList("my-topic"));
consumer.poll(Duration.ofMillis(0));  // 触发 partition 分配

// 回溯到 Partition 起始
consumer.seekToBeginning(consumer.assignment());

// 回溯到指定 Offset
TopicPartition tp = new TopicPartition("my-topic", 0);
consumer.seek(tp, 12345L);

// 按时间戳回溯（找指定时间之后的第一条消息）
Map<TopicPartition, Long> tsMap = new HashMap<>();
tsMap.put(tp, Instant.parse("2024-06-01T00:00:00Z").toEpochMilli());
Map<TopicPartition, OffsetAndTimestamp> result = consumer.offsetsForTimes(tsMap);
consumer.seek(tp, result.get(tp).offset());
# 命令行方式：重置整个 Consumer Group 的 Offset
# 回到最早 Offset
kafka-consumer-groups.sh --bootstrap-server xxx \
  --group my-group --reset-offsets --to-earliest \
  --topic my-topic --execute

# 按时间戳回溯
kafka-consumer-groups.sh --bootstrap-server xxx \
  --group my-group --reset-offsets \
  --to-datetime 2024-06-01T00:00:00.000 \
  --topic my-topic --execute
⚠ 重置前必须停止 Consumer：Consumer Group 中有活跃成员时无法重置 Offset，需先停止所有实例，再执行重置，最后重启 Consumer。
Dead Letter Topic — 失败消息兜底

消息多次重试仍失败时，不应无限重试阻塞后续消息，应转入死信队列：

步骤说明
1. 记录重试次数Redis 记录 retry:${msgId} 计数器，每次失败 +1
2. 超阈值转发 DLT重试 ≥ N 次（通常 3~5 次），将消息发送到 ${topic}.DLT
3. 提交 Offset提交当前消息的 Offset，不阻塞后续消息的消费
4. 告警 + 人工介入DLT Consumer 触发告警，人工分析修复后可重新消费 DLT
try {
    process(record);
} catch (Exception e) {
    long retryCount = redisTemplate.opsForValue()
        .increment("retry:" + record.key());
    if (retryCount >= 3) {
        // 转入死信队列
        kafkaTemplate.send(record.topic() + ".DLT", record.key(), record.value());
        log.error("消息已转入死信队列 key={}", record.key(), e);
        // 不再抛出异常，让 Offset 正常提交
    } else {
        throw e;  // 重新抛出，不提交 Offset，下次重试
    }
}
Spring Kafka 内置了 DeadLetterPublishingRecoverer，配合 DefaultErrorHandler 可自动实现上述逻辑，详见 → 05 · Spring Kafka · §04 错误处理
