Q1 MySQL 为什么用 B+树做索引？和 B树、跳表相比有什么优势？ 高频重点 ▾
考察点

数据结构基础 + 磁盘 IO 模型的理解，能说出"IO 次数"和"范围查询"两个核心原因就能拿分，再说出为什么非叶节点不存数据会加分。

参考回答

B+树选择的核心原因是最小化磁盘 IO 次数。

  • vs B树B树非叶节点既存 key 又存 data，导致每个节点能存的 key 数少，树更高，IO 次数多。B+树非叶节点只存 key 不存 data，同样 16 KB 的页能放更多 key，树更矮（3 层 B+树能索引千万行），IO 次数更少。此外 B+树所有叶节点用双向链表相连，范围查询只需在叶层顺序扫描，B树要回溯，效率差很多。
  • vs 跳表跳表是链表结构，物理上不连续，磁盘 IO 代价高（每次跳跃可能跨页）。B+树页内连续，一次 IO 读入整页，局部性好。跳表在内存结构（Redis ZSet）中表现优秀，不适合磁盘存储引擎。
  • vs Hash 索引Hash 只支持等值查询，不支持范围查询和 ORDER BY，无法用于 LIKE 'xxx%'，InnoDB 不支持显式 Hash 索引（仅 AHI 是内部自动管理的）。

一句话总结：B+树矮胖（减少 IO 层次）+ 叶链表（高效范围扫描），完美契合磁盘数据库的访问模式。

Q2 聚簇索引和非聚簇索引的区别？为什么 InnoDB 建议用自增主键？ 高频重点 ▾
考察点

聚簇索引概念本身是基础，能答出为什么用自增主键（页分裂问题）是进阶加分点。

参考回答

聚簇索引（Clustered Index）：索引的叶节点直接存放整行数据，数据行的物理顺序和索引顺序一致。InnoDB 每张表必须有且只有一个聚簇索引，默认用主键。

二级索引（Secondary Index / 非聚簇索引）：叶节点存的是主键值而非行数据。通过二级索引找到主键后，再去聚簇索引查完整行，这一步叫回表。

为什么推荐自增主键：

  • ①自增 ID 顺序插入，新行永远追加到 B+树最右边叶节点，不会触发页分裂，写入性能好。
  • ②UUID 或随机主键的插入位置随机，频繁导致已满页分裂成两个半满页，浪费空间 + 降低写性能。
  • ③自增 ID 占 4~8 字节，二级索引叶节点存储主键值时更紧凑；UUID 36 字节，所有二级索引都变大。

如果业务必须用业务 ID（如雪花 ID），选择趋势递增的方案（Snowflake、UUID v7）而非完全随机的 UUID v4。

Q3 什么是覆盖索引？如何用它消除回表？ 高频 ▾
考察点

覆盖索引是索引优化最常用的手段，面试中能结合 EXPLAIN Extra 字段（Using index）说明识别方法会大加分。

参考回答

当 SELECT 需要的所有列（包括 WHERE、ORDER BY、SELECT 列表中的列）都包含在某个索引里，MySQL 就能直接从索引叶节点返回数据，不需要回表，这叫覆盖索引（Covering Index）。

识别方式：EXPLAIN 的 Extra 列显示 Using index（不是 Using index condition）。

-- 表：orders(id PK, user_id, status, amount, created_at)
-- 索引：idx_user_status(user_id, status)

-- 查询1：需回表（amount 不在索引中）
SELECT amount FROM orders WHERE user_id=1 AND status=1;

-- 查询2：覆盖索引（只查 user_id 和 status，都在索引里）
SELECT user_id, status FROM orders WHERE user_id=1 AND status=1;
-- → Extra: Using index

-- 优化方案：若经常查 amount，可建联合索引覆盖它
CREATE INDEX idx_cover ON orders(user_id, status, amount);

注意：覆盖索引不是一种特殊索引类型，而是查询能被索引"覆盖"的状态，是联合索引的常见优化技巧。

Q4 联合索引的最左前缀原则是什么？哪些情况会导致部分失效？ 高频重点 ▾
考察点

高频考点，核心是能说清联合索引的排序方式，以及范围条件之后的列为何失效。能答出"索引跳跃扫描"（MySQL 8.0+）是加分项。

参考回答

联合索引 (a, b, c) 的 B+树按 a 排序，a 相同时按 b 排序，b 相同时按 c 排序。查询只有从最左列开始，索引才能定位范围。

查询条件索引使用情况原因
WHERE a=1 AND b=2 AND c=3✅ 全部用到完整最左前缀
WHERE a=1 AND b=2✅ 用到 a,b前缀匹配
WHERE a=1✅ 用到 a前缀匹配
WHERE b=2 AND c=3❌ 失效跳过 a，无法定位
WHERE a=1 AND c=3⚠ 仅用 ab 中断，c 无法用
WHERE a>1 AND b=2⚠ a 范围，b 失效a 是范围条件，之后的列无序
WHERE a=1 AND b LIKE 'x%'✅ a,b 均用前缀 LIKE 等同范围，b 后无更多列时没影响

关键原则：范围条件（>、<、BETWEEN、LIKE 'x%'）之后的列无法继续走索引。设计联合索引时，等值条件的列放前面，范围条件的列放最后。

MySQL 8.0 新增索引跳跃扫描（Index Skip Scan）：在某些情况下可以跳过最左列，但代价较高，有限制条件（最左列 distinct 值少时才触发），不能依赖。

Q6 ORDER BY 一定会走索引吗？什么情况会产生 filesort？ 高频重点 ▾
考察点

ORDER BY 与索引是综合考点，很多人只知道"走索引就不排序"，但不知道什么条件下才走。能说出 filesort 的两种算法是加分项。

参考回答

ORDER BY 能走索引的前提：ORDER BY 的列要和索引的排序方向完全匹配，且 WHERE 的等值条件要在联合索引中位于 ORDER BY 列之前。

场景（索引 idx(a,b)）是否走索引
WHERE a=1 ORDER BY b✅ 走，b 在 a 确定后有序
WHERE a=1 ORDER BY b DESC✅ 走（反向扫描）
ORDER BY a, b✅ 走，和索引顺序一致
WHERE a>1 ORDER BY b❌ filesort，a 是范围，b 不连续有序
ORDER BY a ASC, b DESC❌ filesort，方向不一致（8.0 支持降序索引可解决）
ORDER BY 非索引列❌ filesort

filesort 两种算法（EXPLAIN Extra 显示 Using filesort）：

  • 单路把 SELECT 的所有列都放入 sort_buffer 排序，直接输出，省一次回表，但占内存多
  • 双路sort_buffer 只放排序列+主键，排好序后再回表取其他列，内存用量少但多一次 IO

当 sort_buffer_size 不够时，MySQL 分批排序后用磁盘归并（Using filesort + 临时文件），性能大幅下降。调大 sort_buffer_size 可缓解，但更根本的是设计合适的联合索引消除 filesort。

Q7 ICP（索引条件下推）和 MRR（多范围回表读）分别解决了什么问题？ 重点 ▾
考察点

ICP 和 MRR 是 MySQL 5.6 引入的两个重要优化，能说出各自针对的问题场景说明对索引执行过程有深刻理解。

参考回答

ICP（Index Condition Pushdown，索引条件下推）：

原来：引擎只负责定位索引，WHERE 中非定位列的过滤条件由 Server 层在回表取到完整行后才执行，每行都要回表。

ICP 后：把 WHERE 中能用索引列判断的条件下推到引擎层，在读索引叶节点时就先过滤，减少回表次数。EXPLAIN Extra 显示 Using index condition。

-- 索引 idx(age, name)，查询：WHERE age BETWEEN 20 AND 30 AND name LIKE 'a%'
-- 无 ICP：按 age 范围扫描索引，每条都回表，Server 层再过滤 name
-- 有 ICP：在索引层就检查 name LIKE 'a%'，不满足的直接跳过，不回表

MRR（Multi-Range Read Optimization，多范围回表读）：

回表时，二级索引叶节点的主键值顺序和 .ibd 文件中数据的物理顺序不一致，导致大量随机 IO。MRR 的做法：先收集所有需要回表的主键值，按主键排序后批量回表，把随机 IO 变成顺序 IO。EXPLAIN Extra 显示 Using MRR。

MRR 在返回行数多时效果显著，少量行时额外排序开销可能得不偿失，MySQL 会根据代价决定是否启用。

Q8 如何设计索引？给一个订单表说说你会建哪些索引？ 高频 ▾
考察点

开放式实战题，考察对业务理解和索引权衡的综合判断，没有标准答案，重点是说清楚决策依据。

参考回答

索引设计五步法：

  • ①分析查询场景：梳理高频 SQL 的 WHERE/ORDER BY/GROUP BY 列
  • ②选择性优先：选择区分度高的列建索引（用 SELECT COUNT(DISTINCT col)/COUNT(*) 衡量）
  • ③联合索引合并：多个查询共用字段时建联合索引，遵循最左前缀，等值列靠前，范围列靠后
  • ④覆盖索引优先：高频查询能否不回表？把 SELECT 列加入索引
  • ⑤控制索引数量：每增一个索引，写入时多维护一棵 B+树。索引不是越多越好，通常单表不超过 5 个

以订单表 orders(id, user_id, merchant_id, status, amount, created_at) 为例：

-- 场景1：用户查自己的订单列表，按时间倒序，支持状态筛选
CREATE INDEX idx_user_status_time ON orders(user_id, status, created_at);
-- WHERE user_id=? AND status=? ORDER BY created_at DESC → 全走索引，无 filesort

-- 场景2：商家查自己店铺的订单
CREATE INDEX idx_merchant_time ON orders(merchant_id, created_at);

-- 场景3：运营后台按时间范围统计金额（全量分析，少量，不建索引或用分析型 DB）

Q9 Buffer Pool 的作用？LRU 为什么要分成 young/old 两区？ 高频重点 ▾
考察点

Buffer Pool 是 InnoDB 性能核心，能说清改良 LRU 的"缓存污染"问题是深度理解的标志。

参考回答

Buffer Pool 是 InnoDB 的内存页缓存，所有读写都先经过内存（默认页 16 KB）。命中率直接决定磁盘 IO 次数，生产环境应保持 >99%。

为什么改良 LRU：全表扫描或 mysqldump 会把大量"只读一次"的冷页塞入 LRU 头部，把真正的热页挤出，叫缓存污染。

解法：把 LRU 分成 young 区（前 5/8）和 old 区（后 3/8）：

  • 新页读入时先插到 old 区头部（midpoint insertion），不直接进 young 区
  • 晋升只有在 old 区停留超过 1 秒（innodb_old_blocks_time=1000）后再次被访问，才移到 young 区头部
  • 效果全表扫描读入的页在 old 区一扫而过，1 秒内没有第二次访问，永远不进 young 区，热数据缓存不受影响

Q10 Redo Log 是什么？WAL 原理是什么？innodb_flush_log_at_trx_commit 三个值怎么选？ 高频重点 ▾
考察点

WAL 是 InnoDB 最核心的设计，三个 flush 值的选择是生产配置题，考察对数据安全和性能权衡的理解。

参考回答

Redo Log 解决的问题：InnoDB 无法在每次写操作后立即把脏页刷回磁盘（随机 IO 慢、写放大严重），所以用顺序写日志代替随机写磁盘。

WAL（Write-Ahead Logging）：先把"做了什么修改"顺序追加到 redo log，再修改内存页。只要 redo log 落盘，事务就算提交成功，脏页可以之后批量刷盘。崩溃后 redo log 重放，数据不丢。

Redo log 是物理日志（记录某页某偏移量写了什么字节），循环覆盖固定文件，顺序 IO。

innodb_flush_log_at_trx_commit行为数据安全适用
0每秒刷一次（后台线程）⚠ 崩溃丢 ≤1s允许少量丢失的场景
1（默认）每次提交都 fsync 到磁盘✅ 不丢数据生产金融/订单类
2提交写 OS cache，每秒 fsync⚠ OS 崩溃丢 ≤1s非关键业务

维度BinlogRedo Log

Q12 两阶段提交（2PC）是怎么保证 Redo Log 和 Binlog 一致的？ 高频重点 ▾
考察点

2PC 是 InnoDB 最精妙的设计之一，能说清"为什么需要 2PC"和 Crash Recovery 的判断规则，是区分中级和高级的分水岭。

参考回答

为什么需要 2PC：Redo log（InnoDB）和 Binlog（Server）是两套独立系统。若没有协调：写了 redo 但崩溃在写 binlog 前，主库 crash 恢复后有数据，但 binlog 里没记录，从库会丢这次更新 → 主从不一致。

2PC 流程：

  • 第一阶段InnoDB 写 redo log，标记为 prepare 状态，fsync 到磁盘
  • 第二阶段Server 层写 binlog 到文件并 fsync
  • 完成InnoDB 把 redo log 标记为 commit 状态，释放行锁

Crash Recovery 判断规则：重启时扫描 redo log，找到 prepare 状态的事务，去 binlog 里查对应的 XID 是否存在：

  • 存在binlog 已写入 → 提交事务（redo log 标记 commit）
  • 不存在binlog 未写入 → 回滚事务

这保证了无论在哪个时刻崩溃，redo log 和 binlog 最终都是一致的。

Q13 Undo Log 有什么用？MVCC 是如何实现的？ 高频重点 ▾
考察点

MVCC 是 InnoDB 最复杂的特性，能说清版本链和 ReadView 四字段的考生属于上层水平。

参考回答

Undo Log 是逻辑日志，记录"如何把修改回滚回去"，有两个独立用途：

  • 回滚事务执行中每次修改前把原始值写入 undo log，回滚时按 undo log 逆向恢复
  • MVCC每次 UPDATE 产生新版本，旧版本留在 undo log，通过 DB_ROLL_PTR 指针串成版本链

MVCC 读的过程：快照读时创建（或复用）ReadView，包含四字段：

  • m_ids创建时所有活跃事务 ID 列表
  • min_trx_idm_ids 最小值
  • max_trx_id下一个待分配事务 ID
  • creator_trx_id当前事务自身 ID

对每行记录的 DB_TRX_ID，按规则判断可见性：小于 min_trx_id 可见；大于等于 max_trx_id 不可见；在中间看是否在 m_ids 里。不可见则沿版本链找上一版本。整个过程不加锁。

Q14 一条 UPDATE 语句的完整执行流程是什么？ 重点 ▾
考察点

这道题能把 InnoDB 所有核心机制串联起来，是综合能力的终极考验。能按步骤完整说出并说清每步的作用即可拿满分。

参考回答

以 UPDATE orders SET status=2 WHERE id=1001 为例，完整 9 步：

  • ①Parser 词法/语法分析，Optimizer 生成执行计划（选主键索引）
  • ②Executor 权限校验，调用 InnoDB handler API
  • ③InnoDB 查 Buffer Pool，命中直接用；未命中从 .ibd 读入 16 KB 页
  • ④对该行加 X 锁（Record Lock 或 Next-Key Lock）
  • ⑤写 undo log（记录原始值，用于回滚和 MVCC 版本链）
  • ⑥修改 Buffer Pool 内存页，标记 dirty，加入 flush 链表
  • ⑦写 redo log（prepare 状态），从 log buffer 写入 redo log file 并 fsync，这是 2PC 第一阶段
  • ⑧Server 层写 binlog cache，flush 到 binlog 文件并 fsync，2PC 第二阶段
  • ⑨redo log 标记 commit，释放行锁；脏页由 Page Cleaner 异步刷盘，与事务提交无关

整个流程的安全保证：redo log 保证 crash recovery，binlog 保证主从一致，2PC 保证两者一致，doublewrite 防止刷盘时 partial write。

Q15 Doublewrite Buffer 解决了什么问题？为什么 redo log 无法直接解决？ 重点 ▾
考察点

能说清"partial write 问题"和"为什么 redo log 不够"是真正理解 InnoDB 写路径的标志。

参考回答

Partial Write（部分写）问题：InnoDB 页 16 KB，OS 文件系统块 4 KB，刷一个页需要写 4 次。断电发生在中途时，.ibd 里的页会损坏（一半新一半旧）。

为什么 redo log 无法单独解决：redo log 记录的是增量变更（某偏移量写了什么字节），apply 的前提是原始页是完整且正确的。损坏的页无法 apply redo log，会产生错误结果。

Doublewrite 的解法：

  • ①刷脏页前，先把这批页顺序写入 ibdata1 的 doublewrite 区（顺序 IO，代价小），fsync
  • ②再把页写入 .ibd 各自的位置（随机 IO）；此时崩溃 .ibd 里页损坏，但 doublewrite 区有完整备份
  • ③Crash Recovery 时，发现 .ibd 页损坏（checksum 失败），用 doublewrite 区的备份还原，再 apply redo log

代价是约 5%~10% 的写放大，使用 ZFS/Btrfs 等支持原子写的文件系统可以关闭。

Q16 Change Buffer 是干什么的？什么场景下适用，什么场景下不适用？ 重点 ▾
考察点

Change Buffer 的适用场景经常被误解，能说清"写后立即读"场景反而有害，是深度理解的体现。

参考回答

Change Buffer 缓存对不在 Buffer Pool 里的非唯一二级索引页的修改，避免写入时把该页从磁盘读入（省一次随机 IO）。等到该页被其他操作读入 Buffer Pool 时，再把缓存的修改合并（merge）进去。

只有非唯一二级索引能用：唯一索引需要立即读入页验证唯一性，无法缓存；主键（聚簇索引）不适用。

适用场景：写多读少，如日志写入、批量数据导入，写入后长时间不读，merge 压力小。

不适用场景：写后立即读，如电商下单后立即查询该订单，merge 频繁触发，change buffer 的好处完全抵消，还增加了 merge 开销，反而不如直接读入页。此时应考虑减小 innodb_change_buffer_max_size 或直接关闭。

Q19 RC 和 RR 在 MVCC ReadView 上有什么区别？ 高频重点 ▾
考察点

这是 MVCC 最精华的考点，区别就在 ReadView 生成时机，能用一句话说清楚就满分了。

参考回答

核心区别只有一条：ReadView 的创建时机不同。

  • RC每次执行 SELECT 都创建一个新的 ReadView。因此每次 SELECT 都能看到该 SELECT 执行前已提交的最新数据，同一事务内两次读同一行可能结果不同（不可重复读）。
  • RR同一事务内第一次执行 SELECT 时创建 ReadView，后续所有 SELECT 都复用这同一个 ReadView，整个事务看到的数据快照不变（可重复读）。
-- RR 可重复读示意
BEGIN;
SELECT age FROM t WHERE id=1;  -- 第一次 SELECT，创建 ReadView，得到 age=25
-- 此时另一事务把 age 改成 30 并提交
SELECT age FROM t WHERE id=1;  -- 复用同一 ReadView，仍得到 age=25（可重复读）

-- RC 不可重复读示意
BEGIN;
SELECT age FROM t WHERE id=1;  -- 创建 ReadView，得到 age=25
-- 另一事务提交 age=30
SELECT age FROM t WHERE id=1;  -- 新 ReadView，得到 age=30（不可重复读）

Q20 RR 隔离级别下幻读真的被完全解决了吗？ 高频重点 ▾
考察点

很多人答"RR 用 Gap Lock 解决了幻读"——这个答案只对一半。能说出"快照读 + 当前读混用"仍会产生幻读是真正的加分点。

参考回答

没有完全解决。分三种情况：

  • 纯快照读同一事务多次普通 SELECT，MVCC 复用同一 ReadView，不会出现幻行 → ✅ 无幻读
  • 纯当前读UPDATE/SELECT FOR UPDATE 加 Next-Key Lock 锁住行和间隙，阻止并发插入 → ✅ 无幻读
  • 快照读+当前读混用先普通 SELECT（不加锁），另一事务 INSERT + COMMIT，再 UPDATE（当前读，能看到新行，更新成功）→ ❌ 幻读出现
-- 幻读复现（RR 级别）
BEGIN;
SELECT * FROM t WHERE age>20;     -- 快照读，返回 2 行，不加锁
-- 事务 B: INSERT INTO t VALUES(3,25); COMMIT;
UPDATE t SET name='x' WHERE age>20;  -- 当前读，扫到 3 行（含 B 插入的行），更新 3 行！
SELECT * FROM t WHERE age>20;     -- 此时也看到 3 行（自己修改了 B 的行使其可见）

根本防范：读后写的业务场景，SELECT 就应该用 FOR UPDATE，一开始就加 Next-Key Lock 阻止并发插入。

Q22 Record Lock、Gap Lock、Next-Key Lock 分别是什么？RC 和 RR 加锁有什么区别？ 高频重点 ▾
考察点

InnoDB 行锁类型是事务考点必问，能说清 Next-Key Lock 的区间定义和 RC 无 Gap Lock 是核心。

参考回答
  • Record Lock锁住索引树上的单个叶节点（一条具体记录）。精确匹配（WHERE id=5）时加此锁。RC 和 RR 都有。
  • Gap Lock锁住两个索引值之间的开区间间隙，只阻止在该间隙内 INSERT，不阻止读。仅 RR 级别有，RC 没有 Gap Lock，并发写入能力更强。
  • Next-Key Lock= Record Lock + 左侧 Gap Lock，锁住左开右闭区间。InnoDB 的默认行锁类型。例如 id 有值 (3, 7, 10)，对 id=7 的 Next-Key Lock 锁住 (3, 7]。

RC vs RR 加锁对比：RC 只有 Record Lock（仅锁已有行），RR 有完整的 Next-Key Lock（锁行 + 锁间隙），所以 RR 下死锁概率更高但幻读更少。无索引的 UPDATE 在 RC 下锁全表所有行，RR 下锁全表所有行和所有间隙，两者都很危险，需确保 WHERE 命中索引。

Q23 死锁是如何产生的？InnoDB 如何检测和处理？如何避免？ 高频 ▾
考察点

死锁是每家公司都会遇到的生产问题，能给出排查命令和实际避免方案是工程实战加分点。

参考回答

死锁产生：多个事务以不同顺序请求同一组资源，形成循环等待。典型场景：事务 A 持有 id=1 的锁等 id=2，事务 B 持有 id=2 的锁等 id=1。

-- 查看最近一次死锁
SHOW ENGINE INNODB STATUS\G;
-- 找 LATEST DETECTED DEADLOCK 段，看每个事务 HOLDS 什么锁、等待什么锁

避免策略：

  • ①固定加锁顺序：多事务操作同一组行，约定按 id 从小到大顺序，消灭循环等待
  • ②缩短事务：持锁时间越短，与其他事务冲突概率越低
  • ③索引优化：避免全表扫描触发大范围加锁
  • ④业务重试：捕获 1213 错误，自动重试事务（指数退避）

ORDER BY sec DESC;

Q27 多表 JOIN 如何优化？驱动表选择有什么原则？ 高频 ▾
考察点

JOIN 优化是后端必备知识，能说清 NLJ/BNLJ 原理和小表驱动大表的原因是加分点。

参考回答

InnoDB JOIN 两种算法：

  • NLJNested-Loop Join：驱动表每一行，去被驱动表用索引查匹配行。被驱动表有索引时高效。EXPLAIN 的 Extra 显示 Using join buffer 说明没用 NLJ，而是 BNLJ。
  • BNLJBlock Nested-Loop Join：驱动表分批读入 join_buffer，被驱动表全扫，和 buffer 里所有行匹配。被驱动表无索引时使用，效率差。

优化原则：

  • ①小表驱动大表：驱动表扫描一次，被驱动表扫描 N 次（N=驱动表行数）。驱动表越小，外层循环越少。MySQL 优化器通常自动选，也可用 STRAIGHT_JOIN 强制指定。
  • ②被驱动表 JOIN 列必须有索引：无索引 → BNLJ → 全表扫描 × 驱动表行数，性能极差
  • ③超过 3 张表的 JOIN 要慎重，考虑拆成多次查询后在应用层组合
  • ④调大 join_buffer_size 可缓解 BNLJ，但根本是加索引

复制原理（异步三线程模型）：

  • Dump Thread主库上的线程，监控 binlog 变化，把 binlog event 推送给从库
  • IO Thread从库上的线程，接收主库 Dump Thread 推来的 binlog，写入本地 relay log
  • SQL Thread从库上的线程，读取 relay log，重放 SQL 执行，应用到从库数据

主从延迟排查：

-- 从库执行，查看延迟秒数
SHOW SLAVE STATUS\G;
-- 关键字段：Seconds_Behind_Master（延迟秒数，0 表示无延迟）
-- IO 延迟：Master_Log_File vs Relay_Master_Log_File 不一致
-- SQL 延迟：Relay_Log_File vs Exec_Master_Log_Pos 不一致

常见延迟原因和解法：

  • 大事务主库大事务 binlog 大，从库 SQL Thread 单线程顺序执行，耗时长 → 拆小事务
  • 单线程回放MySQL 5.6 之前 SQL Thread 只有一个线程 → 升级 5.7+ 开启并行复制（slave_parallel_workers=8）
  • 从库压力过大从库承担大量读请求，IO/CPU 竞争 → 读写分离 + 增加只读从库
  • 网络问题主从网络延迟 → 检查网络，确保在同一机房

Q31 分库分表的方案如何选择？分片键怎么设计？有哪些坑？ 高频重点 ▾
考察点

分库分表是架构必问，能说出分片键选择标准和跨分片问题（跨库 JOIN、分布式事务）是高分回答。

参考回答

两种策略对比：

策略方式优点缺点
Range 范围分片按 id/时间范围切分（1~100w，100w~200w…）范围查询高效，扩容简单热点问题（新数据集中在最新片）
Hash 取模分片id % N 决定落哪个库/表数据均匀分布，无热点扩容需迁移数据（一致性 Hash 可缓解）

分片键设计原则：

  • ①选查询最高频的维度（电商用 user_id，SaaS 用 tenant_id），避免跨分片查询
  • ②分片键不能是随机 UUID（热点均匀但排序困难），趋势递增 ID（雪花 ID）是更好选择

主要坑：

  • 跨库 JOIN禁止，改为应用层组合（多次查询 + 内存 join）或数据冗余
  • 分布式事务跨库事务需要 Seata/TCC 等方案，复杂度剧增
  • 跨分片分页/排序需要从所有分片取数据后在内存里汇总排序，性能差
  • 全局唯一 ID不能用数据库自增，需要雪花算法、Segment 号段、Redis 原子递增等方案

方案原理故障切换数据丢失风险适用
主从 + MHA异步主从，MHA 监控主库，故障时选最新从库提升为主手动或自动（30s~60s）⚠ 可能丢失 binlog传统自建 MySQL，RTO 中等
