01核心概念
Kafka 是什么

Kafka 是由 LinkedIn 开源的分布式流处理平台，本质是一个基于发布/订阅模型的持久化消息队列。核心设计目标：高吞吐（单机百万级 TPS）、低延迟、持久化、水平扩展。

L = Leader（负责读写），F = Follower（只同步），RF=2 表示每个 Partition 有 2 个副本

Producer
  • 消息生产者，向指定 Topic 发送消息
  • 可指定 Partition 或由分区器决定
  • 支持同步、异步、发后即忘三种发送模式
Broker / Cluster
  • Kafka 服务节点称为 Broker
  • 多个 Broker 组成 Cluster，共享元数据
  • 每个 Broker 承载若干 Partition 的 Leader / Follower
Consumer
  • 消费者，从 Topic 拉取消息（Pull 模式）
  • 同一 Consumer Group 内，一个 Partition 只能被一个成员消费
  • 不同 Group 之间互不影响，各自维护 Offset
Topic · Partition · Offset — 三个最重要的概念
概念定义关键点
Topic 消息的逻辑分类，类似数据库中的表 一个 Topic 由多个 Partition 组成，分散存储在不同 Broker 上
Partition Topic 的物理分片，每个 Partition 是一个有序、不可变的消息序列 Partition 是 Kafka 并行消费和水平扩展的基础单元；Partition 内有序，Partition 间无序
Offset 消息在 Partition 内的唯一递增编号，从 0 开始 Consumer 通过 Offset 标记消费进度，存储在 __consumer_offsets Topic 中
Partition 数量设计原则：分区数越多，并行度越高，但也会增加 Leader 选举开销和文件句柄消耗。经验值：吞吐目标 / 单 Partition 吞吐上限（通常 10~50 MB/s），结合 Consumer 实例数来定，一般不超过 100 个分区。
Consumer Group — 并行消费模型

Consumer Group 是 Kafka 实现消息队列语义（竞争消费）和发布订阅语义（广播）的核心机制：

场景做法效果
消息队列（竞争消费）多个 Consumer 属于同一 Group每条消息只被 Group 内一个 Consumer 处理
发布订阅（广播）每个 Consumer 属于不同 Group每条消息被所有 Group 各消费一次
⚠ Consumer 数量上限：同一 Group 内有效 Consumer 数不能超过 Topic 的 Partition 数，多出的 Consumer 会闲置无法分配到 Partition。
02消息存储原理
日志文件结构 — LogSegment 三件套

每个 Partition 对应磁盘上的一个目录（如 topic-0/），目录内由多个 LogSegment 组成，每个 Segment 包含三个文件：

文件作用说明
.log 消息数据文件 顺序追加写入，消息按 Offset 顺序存储，文件名即该 Segment 起始 Offset
.index 偏移量索引（稀疏索引） 记录 Offset → 物理位置的映射，每隔 log.index.interval.bytes（默认 4KB）写一条，通过二分查找定位消息
.timeindex 时间戳索引 记录时间戳 → Offset 的映射，支持按时间回溯消费（--reset-offsets --to-datetime） 
topic-orders-0/
├── 00000000000000000000.log        ← Segment 1，起始 offset=0
├── 00000000000000000000.index
├── 00000000000000000000.timeindex
├── 00000000000001000000.log        ← Segment 2，起始 offset=1000000
├── 00000000000001000000.index
└── 00000000000001000000.timeindex
📁 topic-orders-0/（Partition 目录）
Segment 1 · 起始 offset=0
📄 00000000000000000000.log 消息数据
🔍 00000000000000000000.index 稀疏偏移索引
🕐 00000000000000000000.timeindex 时间戳索引
Segment 2 · 起始 offset=1,000,000（活跃写入）
📄 00000000000001000000.log 顺序追加写
🔍 00000000000001000000.index 每 4KB 一条
🕐 00000000000001000000.timeindex 支持按时间回溯

Segment 滚动条件（满足其一即新建）：大小超过 log.segment.bytes（默认 1 GB）或时间超过 log.roll.hours（默认 168h / 7 天）。

为什么 Kafka 这么快 — 顺序写 + Page Cache + 零拷贝
1
顺序写磁盘
Kafka 只追加写（Append-Only），磁盘顺序写速度接近内存随机写（600 MB/s vs 100 MB/s），远超随机写（~100 MB/s vs 数据库 B+Tree 随机写几十 MB/s）。
2
Page Cache — 操作系统级缓存
Kafka 写消息时直接写 OS Page Cache，由操作系统异步刷盘（pdflush），读消息时优先从 Page Cache 命中。即使 Kafka 进程重启，Page Cache 依然有效，不像 JVM 堆内存会被清空。
3
零拷贝 — sendfile() 系统调用
消费者拉取消息时，Kafka 使用 sendfile() 将数据从 Page Cache 直接通过 DMA 传输到网卡，跳过「内核→用户态→内核」的两次拷贝，减少 CPU 上下文切换。
4
批量处理 + 压缩
Producer 端将多条消息打包成 RecordBatch 发送，Broker 端批量写入，Consumer 端批量拉取，极大减少网络往返次数和序列化开销。
消息查找流程 — 二分查找 + 顺序扫描

Consumer 通过 Offset 查找消息的完整路径：

1
定位 Segment
根据目标 Offset，在 Segment 文件列表（按起始 Offset 命名）中二分查找，找到包含该 Offset 的 Segment。
2
查 .index 稀疏索引
在该 Segment 的 .index 文件中二分查找，找到不超过目标 Offset 的最近索引条目，得到对应的物理文件位置（position）。
3
顺序扫描 .log
从第 2 步得到的 position 开始，在 .log 文件中顺序扫描，直到找到目标 Offset 的消息。由于稀疏索引间距不大，扫描量极小。
03副本机制 — ISR · HW · LEO
AR / ISR / OSR — 三个副本集合
集合全称含义
AR Assigned Replicas 该 Partition 的全部副本集合，包括 Leader 和所有 Follower
ISR In-Sync Replicas 与 Leader 保持同步的副本集合。Follower 若在 replica.lag.time.max.ms（默认 30s）内没有跟上 Leader，会被移出 ISR
OSR Out-of-Sync Replicas 落后于 Leader 的副本集合，AR = ISR + OSR。OSR 中的副本正在追赶，追上后重新加入 ISR
⚠ unclean.leader.election.enable：默认 false，禁止 OSR 中的副本在 ISR 为空时成为 Leader。若设为 true，可提升可用性但会丢失数据，生产环境不建议开启。
HW 与 LEO — 消费边界与副本进度
概念全称定义
LEO Log End Offset 每个副本自己的下一条待写入消息的 Offset，即当前日志末尾位置 + 1。每个副本各有自己的 LEO。
HW High Watermark 消费者可见的最大 Offset，等于 ISR 中所有副本 LEO 的最小值。HW 以下的消息才能被消费者读取。

HW 推进时机：Follower 向 Leader 发送 Fetch 请求时，会带上自己的 LEO。Leader 收到后更新该 Follower 的 LEO 记录，重新计算 ISR 中的最小 LEO，更新 HW 并在下次 Fetch 响应中告知 Follower。
min.insync.replicas — 可用性与持久性的权衡

当 acks=all 时，Broker 要求 ISR 中至少有 min.insync.replicas 个副本写入才算成功。

配置组合效果
replication.factor=3
min.insync.replicas=2
acks=all		允许 1 个副本宕机仍可写入；若同时 2 个副本不可用，Producer 会收到 NotEnoughReplicasException，写入阻塞
min.insync.replicas=1退化为只需 Leader 写入，等同于 acks=1，不推荐
min.insync.replicas=replication.factor最强持久性，任何一个副本宕机都会导致写入失败，可用性最低
04Controller 与元数据
Kafka Controller — 集群大脑

Controller 是 Kafka 集群中一个特殊的 Broker，负责集群级别的管理工作：

职责说明
Partition Leader 选举当 Leader 副本所在 Broker 宕机时，从 ISR 中选出新 Leader
ISR 变更监控 Follower 同步进度，将落后副本移出 ISR，追上后重新加入
Topic / Partition 管理处理 Topic 创建/删除、分区数变更，向各 Broker 下发元数据变更
Broker 上下线监听 Broker 的加入与退出，触发相应的 Leader 重新选举和副本再分配
Controller 选举 — ZooKeeper 模式

在传统 ZooKeeper 模式下，Controller 通过抢占临时节点的方式选出：

1
所有 Broker 启动时竞争注册
每个 Broker 启动后尝试在 ZooKeeper 的 /controller 路径创建临时节点（Ephemeral ZNode），写入自己的 broker.id。
2
第一个创建成功的 Broker 成为 Controller
ZooKeeper 保证只有一个 Broker 能创建成功，其余 Broker 注册 Watch 监听 /controller 节点。
3
Controller 宕机后重新选举
Controller Broker 宕机时，/controller 临时节点自动删除，其余 Broker 通过 Watch 感知，再次竞争创建节点，第一个成功的成为新 Controller。
KRaft 模式 — Kafka 3.x 去除 ZooKeeper

Kafka 3.3 起 KRaft 模式正式 GA，Kafka 4.0 完全移除 ZooKeeper 依赖。KRaft 将元数据管理内置到 Kafka 自身，通过 Raft 协议在专用的 Controller 节点之间同步：

对比维度ZooKeeper 模式KRaft 模式
元数据存储存在 ZooKeeper 中存在 Kafka 内部 @metadata Topic 中
Controller 角色1 个 Active Controller + ZooKeeper多个 Controller 节点组成 Raft 组（奇数个，如 3）
选举机制ZooKeeper 临时节点抢占Raft 协议 Leader 选举（多数派投票）
扩展性ZooKeeper 节点数限制，百万 Partition 有瓶颈元数据处理能力大幅提升，支持百万级 Partition
运维复杂度需额外维护 ZooKeeper 集群只需部署 Kafka，架构更简单
启动速度慢（需与 ZooKeeper 同步大量元数据）快（Controller 直接持有最新元数据快照）
生产建议：新项目直接用 Kafka 3.x KRaft 模式；存量项目按官方迁移工具逐步切换（kafka-storage.sh 支持在线迁移）。
05压缩与批量发送
压缩算法对比

Kafka 支持对消息批次（RecordBatch）进行压缩，Producer 端压缩后发送，Broker 直接存储压缩数据，Consumer 端解压：

算法压缩比CPU 开销速度推荐场景
GZIP高高慢带宽极贵、对延迟不敏感的批量归档场景
Snappy中低快平衡压缩比与速度，Google 内部广泛使用
LZ4中极低极快延迟敏感场景，Kafka 官方推荐默认选择
ZSTD高低快Kafka 2.1+ 支持，压缩比接近 GZIP，速度接近 LZ4，综合最优
NONE无无最快消息本身已压缩（如图片/视频二进制），或内网带宽充裕
⚠ Broker 端重压缩：若 Producer 压缩算法与 Broker 的 compression.type 配置不一致，Broker 会先解压再重新压缩，消耗额外 CPU。建议 Producer、Broker 配置保持一致，或 Broker 设置为 producer（透传 Producer 的压缩格式）。
batch.size 与 linger.ms — 吞吐与延迟的平衡

Producer 端的批量发送由两个参数共同控制，两者满足其一即触发发送：

参数默认值作用
batch.size16 KB单个批次的最大字节数。批次凑满后立即发送，不等待 linger.ms 超时
linger.ms0批次等待时间。0 表示消息到达即发送（低延迟），增大后允许更多消息凑批（高吞吐）
// 高吞吐场景推荐配置（日志采集、埋点上报）
props.put("batch.size",   65536);    // 64 KB，加大批次
props.put("linger.ms",    10);       // 等待最多 10ms 凑批
props.put("compression.type", "lz4"); // 开启压缩

// 低延迟场景推荐配置（支付、交易类）
props.put("batch.size",   16384);    // 默认 16 KB
props.put("linger.ms",    0);        // 立即发送
props.put("acks",         "1");      // 适当降低可靠性换延迟
buffer.memory（默认 32 MB）：Producer 端消息缓冲区总大小。若消息发送速度超过发送速度，缓冲区满后 send() 会阻塞，超过 max.block.ms（默认 60s）则抛出异常。高吞吐场景可适当调大。
