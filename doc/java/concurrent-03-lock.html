01synchronized
三种使用方式
// 1. 修饰实例方法 — 锁是当前实例对象（this）
public synchronized void instanceMethod() { ... }

// 2. 修饰静态方法 — 锁是当前 Class 对象
public static synchronized void staticMethod() { ... }

// 3. 修饰代码块 — 锁是括号内指定对象
public void blockMethod() {
    synchronized (this) { ... }       // 锁 this
    synchronized (MyClass.class) { }  // 锁 Class 对象
    synchronized (lockObj) { }        // 锁任意对象
}

字节码层面：同步方法通过 ACC_SYNCHRONIZED 标志；同步代码块通过 monitorenter / monitorexit 指令实现。两者底层都依赖 Monitor（监视器）。

Mark Word 结构（64位 JVM）

对象头中的 Mark Word 随锁状态变化存储不同内容：

轻量级锁指向栈中锁记录的指针（62bit）00

锁状态适用场景实现机制性能
偏向锁只有一个线程访问Mark Word 记录线程ID，下次进入无需 CAS最快，几乎无开销
轻量级锁多线程交替访问（无竞争）CAS 将 Mark Word 复制到栈帧的 Lock Record快，CAS 操作
重量级锁多线程激烈竞争OS Mutex，线程挂起/唤醒，涉及用户态/内核态切换慢，有上下文切换开销
JDK 15 废弃偏向锁：现代多核 CPU 下，启用偏向锁的 JVM 维护成本（撤销偏向锁的 STW）高于收益。JDK 15 中默认禁用，JDK 18 彻底删除。新项目无需考虑偏向锁优化。
JDK 6 其他锁优化
  • ①自旋锁 / 自适应自旋：竞争失败时不立即挂起，而是 CAS 循环尝试（默认 10 次）。JDK 6 引入自适应自旋，根据历史成功率动态调整自旋次数
  • ②锁消除：JIT 通过逃逸分析发现锁对象不可能被共享，直接消除锁（如方法内的 StringBuffer 操作）
  • ③锁粗化：连续多次对同一对象加解锁，JIT 将其合并为一次更大范围的锁（减少加解锁开销）
03ReentrantLock
核心特性与用法
ReentrantLock lock = new ReentrantLock(true); // true=公平锁

// 标准用法：必须在 finally 中 unlock
lock.lock();
try {
    // 临界区
} finally {
    lock.unlock(); // 必须！
}

// 可中断锁（响应 interrupt()）
lock.lockInterruptibly();

// 超时尝试获取锁
if (lock.tryLock(500, TimeUnit.MILLISECONDS)) {
    try { ... } finally { lock.unlock(); }
} else {
    // 获取超时，处理降级
}

// Condition（更精确的等待/通知）
Condition notFull  = lock.newCondition();
Condition notEmpty = lock.newCondition();
notFull.await();    // 类似 wait()，释放锁
notFull.signal();   // 类似 notify()，唤醒等待 notFull 的线程
公平锁 vs 非公平锁
维度公平锁（fair=true）非公平锁（默认）
获取顺序严格按等待队列顺序（FIFO）先 CAS 抢锁，失败再入队
吞吐量低（线程切换多）高（减少线程切换）
饥饿风险无极端情况可能饥饿
适用场景等待时间敏感吞吐量优先（绝大多数场景）

05AQS（AbstractQueuedSynchronizer）
AQS 核心数据结构

AQS 是 JUC 锁框架的基础，通过一个 volatile int state 变量和一个 CLH 变体双向队列实现同步：

  • state同步状态，不同锁语义不同：ReentrantLock 中是重入次数；Semaphore 中是剩余许可数；CountDownLatch 中是倒计数值
  • 队列等待获取锁的线程以 Node 结点形式排列在双向链表中，head 为虚节点，首个真实等待结点为 head.next
  • Node包含：等待线程引用、waitStatus（CANCELLED/-1=SIGNAL/-2=CONDITION/-3=PROPAGATE）、prev/next 指针
// 独占模式（ReentrantLock）核心流程
acquire(1):
  if (!tryAcquire(1))           // 子类实现：CAS 尝试设置 state
    addWaiter(Node.EXCLUSIVE)   // 入队
    acquireQueued(node, 1)      // 自旋+park 等待

release(1):
  if (tryRelease(1))            // 子类实现：state 减 1，=0 则释放成功
    unparkSuccessor(head)       // 唤醒后继结点
基于 AQS 的实现
类模式state 含义
ReentrantLock独占0=未锁定，>0=重入次数
Semaphore共享剩余许可数
CountDownLatch共享倒计数，减到 0 全部唤醒
ReentrantReadWriteLock独占+共享高16位=读锁数，低16位=写锁重入次数
CyclicBarrier（基于 ReentrantLock）count 剩余等待数
06读写锁
ReentrantReadWriteLock

读写互斥规则：读读不互斥 / 读写互斥 / 写写互斥。适合读多写少场景：

ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
Lock readLock = rwLock.readLock();
Lock writeLock = rwLock.writeLock();

// 读操作（共享）：允许多个读线程并发
readLock.lock();
try { return cache.get(key); }
finally { readLock.unlock(); }

// 写操作（独占）：排它
writeLock.lock();
try { cache.put(key, value); }
finally { writeLock.unlock(); }
写锁饥饿风险：高并发读场景下，读锁不断被获取，写锁可能长期等待。StampedLock 的乐观读可缓解此问题。
StampedLock（JDK 8+）

提供乐观读（不阻塞写），解决 ReadWriteLock 写饥饿问题：

StampedLock sl = new StampedLock();

// 乐观读（不加锁，需验证）
long stamp = sl.tryOptimisticRead();
int x = this.x, y = this.y;
if (!sl.validate(stamp)) { // 期间有写操作，升级为悲观读
    stamp = sl.readLock();
    try { x = this.x; y = this.y; }
    finally { sl.unlockRead(stamp); }
}

// 写锁
long stamp = sl.writeLock();
try { this.x = newX; }
finally { sl.unlockWrite(stamp); }
StampedLock 不可重入：同一线程不能重复获取写锁，且不支持 Condition，使用场景比 ReadWriteLock 受限。
07死锁
死锁的四个必要条件
  • ①互斥：资源同一时刻只能被一个线程占用
  • ②持有并等待：线程持有资源的同时等待其他资源
  • ③不可抢占：已持有的资源不能被强制剥夺
  • ④循环等待：存在线程间循环等待资源的环路

破坏任意一个条件即可预防死锁：

  • 破②一次性申请所有资源（原子获取）
  • 破③tryLock 超时放弃，释放已持有资源重试（ReentrantLock）
  • 破④对所有资源统一排序，按固定顺序申请（最常用方法）
// 死锁检测：jstack 查看线程堆栈
$ jstack <pid> | grep -A 30 "deadlock"

// 或使用 ThreadMXBean
ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] ids = bean.findDeadlockedThreads(); // 返回死锁线程ID
