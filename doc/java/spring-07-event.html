01为什么需要事件机制
问题：强耦合的业务代码

假设用户注册成功后，需要：发送欢迎邮件、初始化积分账户、推送欢迎消息。直接写在 UserService.register() 里：

public void register(User user) {
    userDao.save(user);         // 核心业务
    mailService.sendWelcome();  // 耦合 ①
    pointService.initAccount(); // 耦合 ②
    pushService.sendMessage();  // 耦合 ③
}

问题：每增加一个后续动作都要改 UserService，违反开闭原则；某个下游服务异常会影响注册主流程；无法按需异步执行。

解决：观察者模式 + Spring Event

Spring 事件机制基于观察者模式，将"发生了什么"（Event）和"做什么响应"（Listener）彻底分离：

// 发布者只关心"注册完成"这个事实
public void register(User user) {
    userDao.save(user);
    eventPublisher.publishEvent(new UserRegisteredEvent(user)); // 解耦
}

// 各模块各自监听，互不感知
@EventListener
public void onRegister(UserRegisteredEvent event) { mailService.sendWelcome(); }

@EventListener
public void onRegister(UserRegisteredEvent event) { pointService.initAccount(); }

核心价值：发布者不依赖任何监听者；新增功能只需新增 Listener，无需改动发布方。

02核心组件与原理
四个核心角色
角色接口 / 类职责
事件ApplicationEvent携带事件数据的载体，继承自 EventObject；Spring 4.2+ 支持任意 POJO 作为事件
发布者ApplicationEventPublisher调用 publishEvent() 发布事件；ApplicationContext 实现了此接口
多播器ApplicationEventMulticaster容器内部组件，负责将事件路由到所有匹配的监听器；默认实现 SimpleApplicationEventMulticaster
监听器ApplicationListener<E> / @EventListener响应特定类型事件；支持接口和注解两种方式
publishEvent() 内部调用链
①
调用 publishEvent(event)
AbstractApplicationContext.publishEvent() 将 POJO 自动包装为 PayloadApplicationEvent（若不是 ApplicationEvent 子类）
②
交给 ApplicationEventMulticaster
调用 multicastEvent(event)，获取所有匹配该事件类型的监听器列表
③
判断是否异步
若多播器配置了 Executor，则每个监听器在线程池中异步调用；否则在调用线程中同步顺序执行
④
逐一调用 Listener
对每个 ApplicationListener 调用 onApplicationEvent()；@EventListener 方法由 EventListenerMethodProcessor 在 Bean 初始化时包装为 ApplicationListenerMethodAdapter
两种监听方式
// ── 方式一：实现接口（传统，泛型明确类型）──
@Component
public class WelcomeMailListener implements ApplicationListener<UserRegisteredEvent> {
    @Override
    public void onApplicationEvent(UserRegisteredEvent event) {
        mailService.sendWelcome(event.getUser());
    }
}

// ── 方式二：@EventListener（Spring 4.2+，推荐）──
@Component
public class PointListener {
    @EventListener
    public void onRegister(UserRegisteredEvent event) {
        pointService.initAccount(event.getUser());
    }

    // 同一个方法监听多种事件
    @EventListener({OrderCreatedEvent.class, OrderPaidEvent.class})
    public void onOrder(ApplicationEvent event) { ... }
}
03@EventListener 注解
条件过滤：condition

用 SpEL 表达式过滤，只在特定条件下响应：

@EventListener(condition = "#event.user.vip == true")
public void onVipRegister(UserRegisteredEvent event) {
    // 只有 VIP 用户注册时才触发
    vipService.initVipBenefits(event.getUser());
}
返回值：触发链式事件

@EventListener 方法可以有返回值，Spring 会将返回值自动发布为新事件，实现事件链：

@EventListener
public PointInitializedEvent onRegister(UserRegisteredEvent event) {
    pointService.initAccount(event.getUser());
    return new PointInitializedEvent(event.getUser()); // 自动发布
}

@EventListener
public void onPointInitialized(PointInitializedEvent event) {
    // 接收链式事件
    couponService.grantWelcomeCoupon(event.getUser());
}
监听器排序：@Order

同一事件有多个监听器时，用 @Order 控制执行顺序（数值越小越先执行）：

@EventListener
@Order(1)
public void saveAuditLog(UserRegisteredEvent event) { ... }   // 先执行

@EventListener
@Order(2)
public void sendWelcomeMail(UserRegisteredEvent event) { ... } // 后执行
⚠ 注意：@Order 只在同步事件下有意义；异步场景中执行顺序由线程调度决定，无法保证。
04异步事件
两种异步实现方式
方式一：@Async + @EventListener
  • 单个监听器异步，其他监听器不受影响
  • 需要 @EnableAsync 启用
  • 线程池隔离，主线程不阻塞
  • 推荐：细粒度控制哪个监听器异步
方式二：配置全局异步多播器
  • 所有事件都走异步
  • 配置 SimpleApplicationEventMulticaster 的 Executor
  • 影响 Spring 内置事件（如 Boot 启动事件）
  • 慎用：可能破坏框架内部事件顺序
// ── 方式一（推荐）：@Async 修饰单个 Listener ──
@Component
public class AsyncMailListener {
    @Async
    @EventListener
    public void onRegister(UserRegisteredEvent event) {
        // 在独立线程池中执行，不阻塞注册流程
        mailService.sendWelcome(event.getUser());
    }
}

// ── 方式二：全局异步多播器（谨慎使用）──
@Bean(name = "applicationEventMulticaster")
public ApplicationEventMulticaster eventMulticaster() {
    SimpleApplicationEventMulticaster m = new SimpleApplicationEventMulticaster();
    m.setTaskExecutor(Executors.newFixedThreadPool(4));
    return m;
}
异步事件的异常处理
⚠ 陷阱：@Async 方法中抛出的异常不会传播到调用方，必须配置 AsyncUncaughtExceptionHandler，否则异常会被默默吞掉。
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {
    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) ->
            log.error("Async listener [{}] threw: {}", method.getName(), ex.getMessage(), ex);
    }
}
05TransactionSynchronizationManager
TSM 与事件机制的关系

TransactionSynchronizationManager（TSM） 是 Spring 事务体系的 ThreadLocal 存储中枢，提供 registerSynchronization() API，允许向当前事务注册生命周期回调——@TransactionalEventListener 的底层正是自动调用此 API 完成的。

// 手动写法（@TransactionalEventListener 的等价底层）
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronizationAdapter() {
        @Override
        public void afterCommit() {
            mqProducer.sendOrderCreated(order); // 事务提交后才执行
        }
    }
);
完整原理 → TSM 的 ThreadLocal 内容、全部四个回调时机（beforeCommit / beforeCompletion / afterCommit / afterCompletion）及注意事项，详见 03 · 事务管理 · §08 TransactionSynchronizationManager。
06@TransactionalEventListener
什么是 @TransactionalEventListener

@TransactionalEventListener（Spring 4.2+）是 @EventListener 的增强版，它将事件监听与事务生命周期绑定：只在特定的事务阶段才真正触发监听器，是 TSM 手动注册 TransactionSynchronization 的声明式替代方案。

本质：底层仍然调用 TransactionSynchronizationManager.registerSynchronization()，只是由框架自动完成。

四个 phase 详解
AFTER_COMMIT
事务成功提交后触发（默认值） 最常用。典型场景：发 MQ 消息、清除 Redis 缓存、发送通知邮件。确保只有数据真正落库才执行后续动作，避免数据不一致。
BEFORE_COMMIT
事务提交前触发 此时数据尚未提交，仍在事务中。可以在此阶段做额外的校验，或把内存中的数据 flush 到数据库。若抛出异常，事务会回滚。
AFTER_ROLLBACK
事务回滚后触发 用于补偿操作或告警。例如：订单创建事务回滚后，释放已占用的库存锁、记录失败日志。
AFTER_COMPLETION
事务完成后触发（无论提交还是回滚） 用于统一资源清理，如关闭文件句柄、清理临时数据。不关心事务成功与否的场景。 
// AFTER_COMMIT（默认）：提交成功后发 MQ
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onOrderCreated(OrderCreatedEvent event) {
    mqProducer.sendOrderCreated(event.getOrder());
}

// BEFORE_COMMIT：提交前校验
@TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)
public void validateBeforeCommit(OrderCreatedEvent event) {
    if (!inventoryService.checkStock(event.getOrder())) {
        throw new InsufficientStockException(); // 触发回滚
    }
}

// AFTER_ROLLBACK：回滚后补偿
@TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
public void onOrderFailed(OrderCreatedEvent event) {
    inventoryService.releaseReservation(event.getOrder());
    alertService.notifyOrderFailure(event.getOrder().getId());
}

// AFTER_COMPLETION：统一清理
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMPLETION)
public void cleanup(OrderCreatedEvent event) {
    tempStorage.remove(event.getOrder().getId());
}
fallbackExecution：无事务时也执行

默认情况下，若发布事件时没有激活的事务，@TransactionalEventListener 的监听器不会被调用（事件被丢弃）。设置 fallbackExecution = true 可改变此行为：

@TransactionalEventListener(
    phase = TransactionPhase.AFTER_COMMIT,
    fallbackExecution = true   // 无事务时也立即执行
)
public void onUserRegistered(UserRegisteredEvent event) {
    mailService.sendWelcome(event.getUser());
}
⚠ 谨慎使用 fallbackExecution：若方法设计上依赖"数据已提交"这个前提，无事务时立即执行可能读不到预期数据（数据还未写入）。
@TransactionalEventListener vs TSM 手动注册 对比
维度@TransactionalEventListenerTSM.registerSynchronization()
代码量注解声明，极简匿名类/Lambda，稍繁琐
与业务代码耦合Listener 与 Service 完全解耦回调代码写在 Service 方法内，有耦合
可复用性可被多个发布者触发每次需要手动注册
fallback 支持有 fallbackExecution 参数需自行判断 isActualTransactionActive()
适用场景通用优先选择动态决定是否注册回调、需要细粒度控制时
07实战：业务解耦
完整示例：用户注册后触发多个动作
// ── 1. 定义事件（POJO 即可，Spring 4.2+ 无需继承 ApplicationEvent）──
public record UserRegisteredEvent(User user, Instant registeredAt) {}

// ── 2. 发布者：只关心核心业务 ──
@Service
@RequiredArgsConstructor
public class UserService {
    private final UserDao userDao;
    private final ApplicationEventPublisher publisher;

    @Transactional
    public void register(UserRegisterDTO dto) {
        User user = userDao.save(dto.toUser());
        publisher.publishEvent(new UserRegisteredEvent(user, Instant.now()));
        // 发布后立即返回，不等待任何监听器
    }
}

// ── 3. 监听器们（各自独立，互不感知）──

// 同步监听：积分初始化（需要在同一事务中）
@Component
public class PointListener {
    @EventListener
    @Order(1)
    public void initPoint(UserRegisteredEvent e) {
        pointService.initAccount(e.user().getId());
    }
}

// 事务提交后发 MQ（避免事务回滚导致消息误发）
@Component
public class MqListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Async  // 异步，不阻塞
    public void sendMq(UserRegisteredEvent e) {
        mqProducer.send("user.registered", e.user().getId());
    }
}

// 事务提交后发邮件（异步，容忍延迟）
@Component
public class MailListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Async
    @Order(2)
    public void sendWelcomeMail(UserRegisteredEvent e) {
        mailService.sendWelcome(e.user().getEmail());
    }
}
✅ 最佳实践：需要在同一事务中执行的操作 → 用 @EventListener（同步）；需要确保数据提交后再执行的操作 → 用 @TransactionalEventListener(AFTER_COMMIT)；耗时操作（邮件、MQ）→ 额外加 @Async。
常见陷阱汇总
陷阱原因解决
@TransactionalEventListener 没触发发布时没有激活的事务加 fallbackExecution=true 或确保在 @Transactional 方法中发布
AFTER_COMMIT 里读不到刚写的数据在同一事务中读，事务已提交但新连接缓存加 @Async 换新线程，或用新事务 REQUIRES_NEW
@Async 异常被吞掉异步线程异常不传播到主线程配置 AsyncUncaughtExceptionHandler
同一 Bean 内 publishEvent 无法触发本 Bean 的 @EventListener事件是同步的，不存在代理问题；但若 publishEvent 和 listener 在同一方法调用栈中可能导致栈溢出避免在 listener 中再发布同类型事件
TSM.registerSynchronization 报 IllegalStateException当前线程没有激活的事务先调用 isActualTransactionActive() 判断
