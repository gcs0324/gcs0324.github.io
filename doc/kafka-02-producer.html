Pipeline · 发送链路全流程
Producer 完整发送链路（用户线程 + Sender 线程）
STEPS 发送链路五步详解
1
拦截器（ProducerInterceptor）
可在发送前修改消息，可在 ack 回调后做统计。支持链式调用，异常不阻断发送，单个拦截器抛出异常会被捕获并跳过，后续拦截器仍继续执行。
2
序列化器（Serializer）
将 Key 和 Value 对象序列化为 byte[]。内置 StringSerializer / IntegerSerializer，可自定义实现 org.apache.kafka.common.serialization.Serializer 接口。
3
分区器（Partitioner）
决定消息写入哪个 Partition。默认策略：
Key 非空：murmur2(key) % numPartitions，hash 路由，保证同 key 落同分区；
Key 为空：黏性分区（Sticky Partitioner，Kafka 2.4+），batch 填满或 linger.ms 到期后随机切换，减少小 batch 碎片化。
4
RecordAccumulator
内存缓冲区，按 TopicPartition 维度组织 ProducerBatch 队列（Deque）。Sender 线程异步从中取批次发送，实现用户线程与网络 I/O 解耦。
5
Sender + NetworkClient
Sender 线程从 RecordAccumulator 拉取 ready 的 batch，通过 NetworkClient（NIO 封装）批量发送给 Broker Leader，处理响应后触发 Callback 并释放内存。
Memory · RecordAccumulator 与 BufferPool
RecordAccumulator 内存结构与 BufferPool 复用机制
ProducerBatch
批次写入缓冲
按 TopicPartition 分组，写满或超时发送
  • 大小由 batch.size 控制（默认 16KB）
  • batch 满 or linger.ms 到期 → 标记 ready → Sender 取走
  • 底层使用 MemoryRecordsBuilder 追加写，支持压缩
  • 发送完毕后，ByteBuffer 归还到 BufferPool 复用
BufferPool
固定大小内存池
ByteBuffer 复用，大幅降低 GC 压力
  • 维护固定大小的 ByteBuffer 复用池（buffer.memory 默认 32MB）
  • 内存不足时 send() 阻塞最多 max.block.ms（默认 60s）
  • 超时抛 TimeoutException，不会无限阻塞
  • 相比直接分配/回收，显著降低 Full GC 频率
WARN

buffer.memory 耗尽不代表 Kafka Broker 出问题，而是本地发送速率 > Broker 消费速率，需检查：网络带宽、Broker 负载、batch 配置，以及是否有大量消息堆积在 Accumulator 中。

Sender · Sender 线程工作机制
LOOP Sender 线程循环逻辑
1
ready() 检查
遍历 RecordAccumulator，找出可以发送的 TopicPartition：batch 已满、linger.ms 到期、有等待中的请求超时、或 Accumulator 内存压力大。返回可发送的 Broker Node 集合。
2
drain() 拉取 batch
按照 Node（Broker） 维度组织 batch，每个 Node 对应一个 List<ProducerBatch>，受 max.request.size 限制单次请求的总大小。
3
构造 ProduceRequest
将 batch 封装为 ProduceRequest，通过 NetworkClient.send() 放入发送队列。底层 Selector（Java NIO） 非阻塞，不等待响应即可继续处理下一轮循环。
4
poll() 处理响应
调用 NetworkClient.poll() 处理 I/O 事件，收到 Broker Response 后触发用户 Callback；成功则释放内存到 BufferPool；失败则根据 retries 配置决定重试或回调异常。
INFO

max.in.flight.requests.per.connection（默认 5）控制每个连接最多允许多少个未确认请求同时在途。设为 1 可严格保序，但吞吐下降明显（约 40%）；开启幂等后 Kafka 自动限制 ≤ 5 且通过 Sequence Number 保证最终有序。

Acks · 确认机制与可靠性权衡
acks 值 含义 可靠性 吞吐 适用场景
0 不等待 Broker 确认，直接返回 最低，可能丢失 最高 日志收集、埋点上报等允许少量丢失的场景
1 等待 Leader 写入本地日志后确认 中等，Leader 宕机前 Follower 未同步则丢 均衡 大多数业务场景的默认选择
-1 (all) 等待所有 ISR 副本都确认 最高，配合 min.insync.replicas=2 才真正不丢 最低 金融、订单等核心链路
WARN

acks=-1 不等于绝对不丢，还需 min.insync.replicas ≥ 2，否则 ISR 只剩 Leader 时退化为 acks=1，Leader 宕机时消息仍可能丢失。

GOOD

推荐生产配置：acks=-1 + min.insync.replicas=2 + replication.factor=3，三者缺一不可，共同构成不丢消息的安全网。

Idempotence · 幂等 Producer 原理
幂等机制：PID + Sequence Number 去重
STEPS 幂等 Producer 四步原理
1
开启配置
enable.idempotence=true（Kafka 3.0+ 默认开启）。Kafka 自动强制设置 acks=-1、retries=MAX_INT、max.in.flight.requests.per.connection ≤ 5，无需手动设置这些参数。
2
PID 分配
Producer 启动时向 Broker 申请全局唯一的 Producer ID（PID）。PID 在 Producer 重启后会变化，这是幂等只在单 session 内有效的根本原因。
3
Sequence Number 单调递增
每个 <PID, TopicPartition> 维护独立的序列号，每发一条消息 +1，序列号写入 RecordBatch header 随消息一起发送给 Broker。
4
Broker 去重
Broker 在内存中维护每个 <PID, Partition> 的最大已接受序列号。收到重传时对比序列号：重复则 ACK 不写盘；乱序则抛 OutOfOrderSequenceException。
WARN

幂等只保证单 Producer 单 Session 单 Partition 内不重复。跨 Partition 或 Producer 重启后 PID 变化，需要用事务 Producer（transactional.id）来保证端到端的 Exactly Once。

Transaction · 跨分区原子写入
API 事务 Producer API 用法
producer.initTransactions(); try { producer.beginTransaction(); producer.send(new ProducerRecord<>("order-topic", key, value)); producer.send(new ProducerRecord<>("inventory-topic", key, value)); producer.commitTransaction(); } catch (Exception e) { producer.abortTransaction(); }
PHASES 事务执行五阶段
1
initTransactions()
向 Transaction Coordinator（TC） 注册 transactional.id，获取对应的 epoch（防止僵尸 Producer）。TC 将事务元数据存储在内部 topic __transaction_state。
2
beginTransaction()
仅在本地标记事务开始，不发网络请求。Producer 内部将事务状态设为 IN_TRANSACTION，后续 send() 操作会自动附加事务语义。
3
send()（写数据）
Producer 将数据写入各 Partition，同时通知 TC 记录参与的 Partition 列表（AddPartitionsToTxn RPC）。消息带 PID + epoch + sequence，但对消费者不可见（受隔离级别控制）。
4
commitTransaction()
发送 EndTxn(COMMIT) 给 TC → TC 写 Commit 到 __transaction_state → TC 向各参与 Partition 写 Transaction Marker（Control Batch）→ 消费者在 read_committed 模式下才能看到这批消息。
5
abortTransaction()
TC 写 Abort Marker，已写入的消息对 read_committed 消费者永久不可见（不是物理删除，而是消费者根据 Control Batch 标记跳过这些消息）。
INFO

transactional.id 相同的新 Producer 启动时，TC 会将旧 Producer 的 epoch +1 使其失效（Zombie Fencing），避免网络分区恢复后两个 Producer 实例同时写入造成脑裂。

Tuning · 关键参数与调优
参数 默认值 作用 调优建议
batch.size 16384（16KB） 单个 ProducerBatch 最大字节数，满了立即发 高吞吐场景可调大到 64KB~1MB，注意内存总占用
linger.ms 0 batch 等待时间，到期强制发送 生产通常设 5~20ms，换取更大批次，降低请求数
compression.type none 消息压缩算法 推荐 lz4（平衡）或 zstd（高压缩比），CPU 换带宽
max.in.flight.requests.per.connection 5 单连接最大在途请求数 不开幂等时设 1 保序；开幂等时保持 ≤5
buffer.memory 33554432（32MB） RecordAccumulator 总内存上限 根据消息量和网络延迟调整，通常 64~256MB
max.block.ms 60000 send() 阻塞等待内存的最大时间 内存不够时的熔断阈值，不宜设置过大
retries MAX_INT（幂等开启后） 失败重试次数 开幂等则无需手动设；关闭时建议设 3~5
HIGH-THROUGHPUT 高吞吐配置
适用：日志采集、埋点上报、监控指标
batch.size=524288 # 512KB linger.ms=20 compression.type=lz4 buffer.memory=134217728 # 128MB acks=1

适用：订单、支付、核心业务链路

Interview · 5 道高频面试题
Q1 Kafka Producer 发送消息的完整流程？
拦截器 → 序列化 → 分区器 → 写入 RecordAccumulator（按 TopicPartition 的 Deque 组织）→ Sender 线程异步批量拉取 → NetworkClient NIO 发送 → 等待 Broker ACK → 回调用户 Callback。

关键点：用户线程和 Sender 线程通过 RecordAccumulator 解耦，内存由 BufferPool 复用，避免频繁 GC。
Q2 acks=-1 就一定不丢消息吗？
不一定。还需要 min.insync.replicas ≥ 2。若 ISR 中只剩 Leader 一个副本，即使 acks=-1，Broker 也只等 Leader 写入就 ACK，效果退化为 acks=1。Leader 宕机时消息仍可能丢失。正确姿势：acks=-1 + min.insync.replicas=2 + replication.factor=3 三者组合。
Q3 幂等 Producer 能保证跨 Partition 不重复吗？
不能。幂等只在单 <PID, Partition> 维度去重，且 Producer 重启后 PID 变化，新旧 PID 的 Sequence 独立，原先的去重记录失效。跨 Partition 或跨 Session 的 Exactly Once 需要用事务 Producer（transactional.id）实现。
Q4 max.in.flight.requests.per.connection 为什么影响消息顺序？
当 max.in.flight > 1 时，多个 Request 同时在途。若 Request-1 失败重试而 Request-2 已成功，重试后 Request-1 的消息排在 Request-2 之后，导致乱序。设为 1 可避免此问题，但吞吐降低约 40%。开启幂等后，Broker 通过 Sequence Number 检测乱序并拒绝（OutOfOrderSequenceException），保证最终写入有序。
Q5 生产环境 Producer 频繁报 TimeoutException 怎么排查？
排查链路：
① 检查 buffer.memory 是否耗尽（发送速率 > Broker 消费速率，可通过 JMX 监控 buffer-available-bytes）
→ ② 检查 request.timeout.ms 与网络延迟是否匹配（跨机房延迟高时需调大）
→ ③ 检查 Broker Leader 是否正常（ISR 收缩、Full GC 暂停、磁盘 IO 瓶颈）
→ ④ 检查 linger.ms 设置过大导致 batch 长时间积压，触发 max.block.ms
→ ⑤ 检查序列化性能是否有瓶颈导致消息产生速率过快
