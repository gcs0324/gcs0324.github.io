Consumer Group 负载均衡
Topic · 4 Partitions — Consumer Group A · 3 Consumers
核心规则
Partition 分配约束
同 Group 内消费互不重叠
  • 同 Group 内每个 Partition 只被一个 Consumer 消费
  • Consumer 数 > Partition 数：多余的 Consumer 空闲，浪费资源
  • Consumer 数 < Partition 数：部分 Consumer 负责多个 Partition
  • 不同 Group 之间相互独立，同一 Partition 可被多 Group 各自消费
分配策略
Partition Assignor
通过 partition.assignment.strategy 配置
  • RangeAssignor（默认）：按 Topic+Partition 范围切分，可能不均匀
  • RoundRobinAssignor：轮询分配，均匀但 Rebalance 后变动大
  • StickyAssignor：尽量保持上次分配，减少 Rebalance 迁移
  • CooperativeStickyAssignor：增量式 Rebalance，Kafka 2.4+ 推荐
Rebalance 全流程
WARN

Stop-the-World 代价：Rebalance 期间所有 Consumer 停止消费，直到新分配方案下发完毕。大规模集群（数百个 Consumer）可能持续数十秒，期间消费完全中断，消息积压快速增长。

FLOW Rebalance 完整流程（6 步）
1
触发事件发生
任意一个条件触发：Consumer 加入或退出 Group；心跳超时（session.timeout.ms，默认 45s）；处理时间过长（max.poll.interval.ms，默认 5min）；Topic 分区数变化；Consumer 调用 subscribe() 更改订阅。GroupCoordinator 感知到成员变化。
2
GroupCoordinator 发起 Rebalance
向所有 Consumer 发送 RebalanceInProgress 错误。所有 Consumer 收到后停止消费，提交当前 Offset，准备重新加入。
3
JoinGroup 阶段
所有 Consumer 向 GroupCoordinator 发送 JoinGroup 请求，携带自己支持的分配策略列表。GroupCoordinator 选出 Leader Consumer（第一个加入的），并将所有成员列表返回给 Leader。
4
SyncGroup 阶段
Leader Consumer 根据分配策略计算每个 Consumer 负责的 Partition，通过 SyncGroup 请求上报给 GroupCoordinator。GroupCoordinator 将分配结果下发给所有 Consumer。
5
Consumer 开始消费
每个 Consumer 按分配结果，从上次提交的 Offset 开始消费（或 auto.offset.reset 配置的位置）。消费恢复，积压开始消化。
6
心跳维持
Consumer 定期发送 Heartbeat（heartbeat.interval.ms，建议为 session.timeout.ms 的 1/3）告知存活，GroupCoordinator 据此判断成员是否需要踢出。
INFO

CooperativeStickyAssignor 实现增量式 Rebalance：只暂停需要重新分配的 Partition，其余 Partition 继续消费不中断，大幅降低 Rebalance 对业务的影响。Kafka 2.4+ 强烈推荐切换。

静态成员减少 Rebalance
动态成员（默认）
每次重启都触发 Rebalance
Consumer 重启被视为新成员加入
  • Consumer 重启 → 触发第 1 次 Rebalance（成员退出）
  • Consumer 恢复上线 → 触发第 2 次 Rebalance（成员加入）
  • 滚动部署 N 个实例 → 触发 2N 次 Rebalance
  • 每次 Rebalance 可能导致数秒消费中断，代价极高
静态成员（group.instance.id）
重启不触发 Rebalance
Consumer 配置唯一固定 ID
  • Consumer 配置唯一的 group.instance.id
  • 重启后在 session.timeout.ms 内重连，Coordinator 直接恢复之前分配，不触发 Rebalance
  • 超过超时时间才真正触发 Rebalance
  • 适合：滚动重启、短暂网络抖动等场景
BEST

生产环境建议为每个 Consumer 实例配置稳定的 group.instance.id（如 ${hostname}-${partition}），配合适当的 session.timeout.ms，可将 Rebalance 频率降低 80% 以上。

Pull 模式详解
PUSH 推模式
Broker 主动推消息
代表：RabbitMQ
  • 速率由 Broker 控制，Consumer 被动接收
  • Consumer 处理慢时消息在 Consumer 侧快速积压，甚至 OOM
  • 不同 Consumer 消费能力不同，统一推送速率难以兼顾
  • 需要 Broker 维护每个 Consumer 的状态，复杂度高
PULL 拉模式
Consumer 主动拉取
代表：Kafka、RocketMQ
  • Consumer 自控速率，按自身能力拉取，不会被推爆
  • 可批量拉取（max.poll.records），提高吞吐
  • 可按需控制 Fetch 大小，灵活适配不同场景
  • 劣势：无消息时需轮询，通过 fetch.max.wait.ms 长轮询缓解
CONFIG Kafka Poll 循环关键参数
1
max.poll.records（默认 500）
单次 poll() 最多返回的消息条数。调小可减少单批处理时间（降低 max.poll.interval.ms 超时风险），调大可提高吞吐。处理逻辑重时建议调小到 50~100。
2
fetch.min.bytes（默认 1 字节）
Broker 至少积累多少字节才返回响应，减少空响应次数。调大（如 64KB）可减少网络往返，适合高吞吐低延迟要求不高的场景。
3
fetch.max.wait.ms（默认 500ms）
Broker 等待数据满足 fetch.min.bytes 的最长时间（长轮询）。超时后无论数据量多少都返回。控制消费延迟的关键参数。
4
max.partition.fetch.bytes（默认 1MB）
每个 Partition 单次返回的最大字节数。总 Fetch 大小约为 Partition 数 × max.partition.fetch.bytes，需根据内存合理配置。
Offset 提交方式
提交方式 API 触发时机 风险 适用场景
自动提交 enable.auto.commit=true 每隔 auto.commit.interval.ms（5s），在 poll() 时触发 可能重复消费（消费成功但提交前崩溃）或漏消费（提交后处理失败） 日志采集等允许少量重复的场景
手动同步提交 commitSync() 处理完消息后手动调用，阻塞直到 Broker 确认 提交失败会抛异常，吞吐略低于异步提交 需要精确控制、不允许丢失的业务场景
手动异步提交 commitAsync(callback) 非阻塞提交，结果通过 callback 异步通知 重试可能导致旧 Offset 覆盖新 Offset，需自行处理重试逻辑 高吞吐场景，配合关闭时 commitSync 兜底
精确提交指定 Offset commitSync(Map<TopicPartition, OffsetAndMetadata>) 手动指定每个 Partition 的精确 Offset 实现复杂，需自行维护 Offset Map 精确一次语义、批次内部分成功场景
WARN

最佳实践：先处理消息，再提交 Offset（At-least-once）。如果先提交再处理（At-most-once），Consumer 崩溃后该消息的 Offset 已提交，重启后不会再消费，消息永久丢失。

__consumer_offsets 存储原理
STORAGE __consumer_offsets 内部机制
1
Topic 结构
__consumer_offsets 是 Kafka 内置 Topic，默认 50 个 Partition，replication.factor=3。每个 Consumer Group 的 Offset 被路由到固定的 Partition：
Math.abs(groupId.hashCode()) % 50
2
消息格式
Key：<GroupId, Topic, Partition> 三元组唯一标识一个消费位点。Value：OffsetAndMetadata，包含 offset 值、提交时间戳、可选自定义 metadata 字符串。
3
GroupCoordinator 负责
每个 Consumer Group 对应一个 GroupCoordinator（管理该 Group Offset 所在 Partition Leader 的 Broker）。Consumer 提交 Offset 直接发给 GroupCoordinator，不经过 ZooKeeper（Kafka 0.9+ 后迁移至内部 Topic）。
4
Log Compaction 清理
__consumer_offsets 使用 Log Compaction 策略，只保留每个 Key 的最新 Offset 记录。过期 Group 数据（offsets.retention.minutes，默认 7 天）会被自动删除。

消费语义与幂等设计
AT-MOST-ONCE
最多一次
  • 先提交 Offset，再处理消息
  • 处理失败后不重试，消息可能丢失
  • 实现最简单，无需幂等
  • 适合：日志统计、监控打点等允许丢失的场景
AT-LEAST-ONCE
至少一次
  • 先处理消息，再提交 Offset
  • 提交失败重启后重新消费，消息可能重复
  • Kafka 默认语义，需要下游做幂等
  • 适合：大多数业务场景配合幂等处理
EXACTLY-ONCE
精确一次
  • 事务 Producer + Consumer read_committed
  • 或下游系统幂等写入保证
  • 复杂度高，有性能开销
  • 适合：金融支付、库存扣减等核心场景
PATTERN 4 种幂等设计实践
1
方案1 — 数据库唯一键
消息中携带唯一业务 ID（如订单号），使用数据库唯一索引 INSERT。重复消息触发 duplicate key error，catch 后直接返回成功。简单可靠，适合写入量不大的场景。
2
方案2 — Redis 去重
消费前用 SET key NX EX 86400 尝试占位，成功才处理，失败说明已处理直接跳过。注意：Redis 重启可能导致去重失效，适合处理时间短、允许极低概率重复的场景。
3
方案3 — 状态机去重
通过业务状态机保证同一操作不会被重复执行（如订单状态 PENDING → PAID，重复支付请求检查状态后直接返回成功）。最符合业务语义，需要完善的状态设计。
4
方案4 — Kafka 事务 + 原子写
Producer 事务保证 Consume-Transform-Produce 的原子性。Consumer 配置 isolation.level=read_committed 只读已提交事务的消息。适合流处理管道（Kafka to Kafka）场景。
面试速答
Q&A Consumer 核心面试题（6 道）
Q1
Rebalance 的触发条件和完整流程？
触发：成员变化（加入/退出/心跳超时）、订阅变化、分区数变化。流程：所有 Consumer 停止消费 → 提交 Offset → JoinGroup（GroupCoordinator 选出 Leader Consumer，下发成员列表）→ SyncGroup（Leader 计算分配方案，通过 Coordinator 下发给所有 Consumer）→ Consumer 按新分配继续消费 → 维持心跳。
Q2
如何减少 Rebalance？
① 配置 group.instance.id 启用静态成员；② 合理调大 session.timeout.ms 减少误判；③ 合理设置 max.poll.interval.ms 避免处理超时；④ 使用 CooperativeStickyAssignor 实现增量式 Rebalance；⑤ 减少 Consumer 实例的频繁重启。
Q3
自动提交和手动提交的区别？什么时候用哪个？
自动提交简单但有重复/丢失风险；手动提交精确但实现复杂。生产建议：先处理再 commitSync()，或 commitAsync() + 关闭时 commitSync() 兜底。日志采集可用自动提交，订单支付必须手动提交。
Q4
消费了消息但没提交 Offset，重启后会怎样？
重启后从最近一次提交的 Offset 开始消费，即重新消费那些处理过但未提交的消息（At-least-once 语义）。如果下游处理没有幂等设计，会导致重复处理，产生脏数据。
Q5
Kafka Pull 模式相比 Push 模式有什么优势？
① 消费者自控速率，不会被 Broker 推爆；② 可批量拉取，提高吞吐；③ 灵活控制 Fetch 大小和等待时间；④ Offset 由 Consumer 维护，支持任意位置重置消费。劣势：无消息时需轮询，通过 fetch.max.wait.ms 长轮询优化。
Q6
__consumer_offsets 是什么？提交失败怎么办？
__consumer_offsets 是 Kafka 内置 Topic，存储所有 Consumer Group 的提交 Offset，默认 50 个 Partition，使用 Log Compaction 策略。commitSync() 失败会抛异常，必须捕获后重试或报警，不能忽略。commitAsync() 失败通过 callback 处理，注意避免重试导致旧 Offset 覆盖新 Offset（可在回调中只记录日志，由下次提交自然覆盖）。
