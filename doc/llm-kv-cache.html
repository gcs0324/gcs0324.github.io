01 KV Cache — 推理加速的核心
是什么

Transformer 生成每个 Token 时，需要对所有历史 Token 做 Attention 计算：Q × K → Attention Score → × V → 输出。其中历史 Token 的 K 和 V 不会变，可以缓存下来，下次直接复用，不用重新算。这个缓存就叫 KV Cache。

没有 KV Cache

生成第 N 个 Token 时，要把前面 N-1 个 Token 全部重新过一遍 Attention 层。生成越到后面越慢，复杂度 O(n²)，长文本几乎不可用。

有 KV Cache

历史 Token 的 K/V 已经存在显存里，每次只算新 Token 的 Q，然后和缓存的 K/V 做 Attention。复杂度降到 O(n)，生成速度基本恒定。

KV Cache 的生命周期：只在单次生成过程中有效，存在 GPU 显存里。会话结束、进程重启、显存不足时全部失效。和下面讲的 Prompt Cache 是两个不同层次的缓存。
02 Prompt Cache — 跨请求的前缀缓存
是什么

Prompt Cache（也叫前缀缓存）是跨请求级别的缓存。如果两次请求的 Prompt 前缀完全相同，服务端可以复用上次已经计算好的 KV 结果，不用从头算。

比喻：你每天开会前都要翻一遍同一份 100 页背景材料。没有缓存的话每天都要重新读；有缓存的话，材料内容没变，KV 结果直接用上次的，只需要处理今天新增的那几页议程。

命中条件
  • ① Prompt 前缀和上次请求完全一致（逐 Token 匹配）
  • ② 缓存还在有效期内（Anthropic API 约 5 分钟 TTL）
  • ③ 相同的模型版本（不同模型不共享缓存）
命中收益（Anthropic API）
  • · 首 Token 延迟明显降低（无需重新计算前缀）
  • · 输入 Token 费用降低约 90%
  • · 吞吐量提升，适合 System Prompt 巨大的 Agent 场景
前缀必须完全一致：哪怕在 System Prompt 里加一个空格，缓存就全部失效。这就是为什么 Claude Code 的 CLAUDE.md 内容一旦稳定就不要频繁改动。
03 压缩 Context 对缓存的影响
压缩做了什么

当对话历史过长（接近上下文窗口限制），Claude Code 会触发 Context Compaction：把旧的对话历史替换成一段 AI 生成的摘要，从而腾出空间继续对话。

从 Prompt Cache 角度看：Messages 部分整体被改写了，前缀从某个位置起完全不同。之前为这段历史计算并缓存的 KV 全部作废。

✓ 压缩后仍然命中的部分
  • System Prompt（没变）
  • Tools 定义（没变）
  • CLAUDE.md 注入的项目上下文（没变）
✗ 压缩后必然 Cache Miss 的部分
  • 原始对话历史（已被摘要替换）
  • Tool Use 循环记录（已清除）
  • 压缩后第一条新消息（前缀已变）
表现：压缩后第一条回复会明显比平时慢（首 Token 延迟升高）。服务端要重新处理 Messages 部分的 KV，System + Tools 因为没变仍然命中，所以不是完全冷启动，只是比命中时慢。
压缩时机：默认在上下文剩余空间不足时自动触发。Claude Code 也支持手动执行 /compact 命令提前压缩。无论哪种方式，对缓存的影响相同。
04 Claude Code Agent 的消息结构
发给大模型的完整结构

Claude Code 使用 Anthropic Messages API，每次请求由三部分拼成：

System Prompt — CLAUDE.md · 权限配置 · 行为规则 · 项目上下文
数千–数万 Token 命中 ✓
Tools — Read / Edit / Bash / MCP 等所有工具的 JSON Schema
大量结构化 JSON 命中 ✓
Messages（历史） — 用户消息 · Assistant 回复 · Tool Use 循环
随对话增长 部分命中
Messages（最新一条） — 当前用户输入
每次都不同 必定 Miss
为什么 Tools 这么大：Claude Code 默认加载几十个工具（文件读写、bash、MCP 工具等），每个工具的 JSON Schema 描述都很详细，Tools 部分加起来可达数千 Token，比普通 AI 应用的 Tools 大很多。
05 哪些部分容易命中缓存
部分 变化频率 缓存命中 原因
System Prompt 会话级别固定 高 CLAUDE.md、权限、行为规则基本不变
Tools 定义 会话级别固定 高 工具列表启动后不变
Messages 前半段 随对话稳定增长 中 前缀匹配，越靠前越稳定
Messages 后半段 每次请求都在变 低 新 Tool Use 结果不断追加
Context 压缩后 一次性大改动 Messages 全 Miss 历史被摘要替换，前缀完全不同

为什么 System + Tools 是 Claude Code 速度的关键

Claude Code 的 System Prompt + Tools 通常占整个请求 Token 的 40–70%。这部分如果稳定命中 Prompt Cache，相当于每次请求的大头都直接跳过计算，首 Token 延迟从几秒降到零点几秒。一旦这部分失效（比如修改 CLAUDE.md 后），会明显感觉第一条回复变慢。

实践建议：CLAUDE.md 内容稳定后不要频繁小改。每次修改都会导致 System Prompt 前缀改变，缓存完全失效，下一条回复明显变慢。批量修改一次比多次零散修改对缓存更友好。
