Scale — Broker 扩缩容与分区再均衡
WORKFLOW Broker 扩缩容流程
1
扩容 Broker
新 Broker 配置 broker.id + log.dirs 启动，自动加入集群，Controller 感知新节点上线。此时新 Broker 上没有任何分区副本，不会自动分配，需手动触发迁移计划。
2
生成迁移计划
用 kafka-reassign-partitions.sh --generate 生成迁移 JSON 文件，指定 topics-to-move 和 broker-list（包含新 Broker ID），工具自动计算最优分区分布。
3
执行迁移
kafka-reassign-partitions.sh --execute --reassignment-json-file plan.json。Kafka 后台开始复制数据到新 Broker，通过 --throttle 限速（单位 bytes/s）避免影响正常业务流量。
4
验证迁移
kafka-reassign-partitions.sh --verify --reassignment-json-file plan.json，确认所有 Partition 迁移完成且 ISR 恢复正常，再进行下一步操作。
5
缩容 Broker
先将目标 Broker 上的所有 Partition 迁移走（同上流程），确认 ISR 正常后，再优雅关闭：kafka-server-stop.sh，触发 Controlled Shutdown，Leader 会提前转移，大幅减少不可用时间。
# 生成迁移计划 kafka-reassign-partitions.sh \ --bootstrap-server localhost:9092 \ --topics-to-move-json-file topics.json \ --broker-list "0,1,2,3" \ --generate > plan.json # 执行（限速 50MB/s，保护业务） kafka-reassign-partitions.sh \ --bootstrap-server localhost:9092 \ --reassignment-json-file plan.json \ --throttle 52428800 \ --execute
WARN

迁移时务必设置 --throttle 限速（建议不超过网卡带宽的 30%），否则大量数据复制会打满网络，影响正常的 Producer / Consumer 流量，严重时导致消费超时和消息堆积。

KRaft — KRaft 模式部署（Kafka 3.x）
ZOOKEEPER MODE
ZooKeeper 模式
传统部署方式，Kafka 4.0 已移除
  • 需额外部署 ZK 集群（建议 3~5 节点）
  • Broker 启动强依赖 ZooKeeper 可用
  • 元数据变更需经过 ZK 再通知 Broker
  • 集群分区数上限约 20 万
  • 运维复杂度高，两套系统需分别监控
KRAFT MODE
KRaft 模式
Kafka 3.3+ 生产可用，Kafka 4.0 移除 ZK
  • Broker 内置 Raft 协议，无外部依赖
  • 3~5 个 Controller 节点组成 Quorum
  • 元数据存储在 @metadata 内部 Topic
  • 启动更快，支持百万级分区
  • 运维简单，只需维护一套系统
DEPLOY KRaft 部署流程
1
格式化存储
每个节点执行 kafka-storage.sh format -t <cluster-id> -c server.properties，生成集群唯一 ID，所有节点必须使用相同的 cluster-id，否则节点无法加入同一集群。
2
配置节点角色
process.roles=controller（仅控制节点）/ process.roles=broker（仅 Broker）/ process.roles=broker,controller（合并模式，适合小集群或开发环境，生产大集群建议角色分离）。
3
配置 Quorum 选举地址
controller.quorum.voters=1@host1:9093,2@host2:9093,3@host3:9093，所有节点配置相同的列表，格式为 nodeId@host:port，Controller 监听端口与 Broker 端口分开。
4
启动与验证
先启动所有 Controller 节点，再启动 Broker 节点。通过 kafka-metadata-quorum.sh --describe 验证 Quorum 状态和 Leader 选举结果。
# server.properties（KRaft Controller+Broker 合并模式） process.roles=broker,controller node.id=1 controller.quorum.voters=1@host1:9093,2@host2:9093,3@host3:9093 listeners=PLAINTEXT://host1:9092,CONTROLLER://host1:9093 log.dirs=/data/kafka-logs # 格式化并启动 kafka-storage.sh format -t $(kafka-storage.sh random-uuid) -c server.properties kafka-server-start.sh server.properties
MM2 — MirrorMaker 2 跨集群同步
REPLICATION MirrorMaker 2 配置与使用
1
架构概览
MM2 基于 Kafka Connect 框架，通过 MirrorSourceConnector 将源集群的 Topic 数据实时同步到目标集群。支持多集群拓扑：主主双向同步、主备灾备、多源聚合扇入等。
2
最小配置示例
clusters = primary, secondary primary.bootstrap.servers = primary-broker:9092 secondary.bootstrap.servers = secondary-broker:9092 primary->secondary.enabled = true primary->secondary.topics = .* replication.factor = 3
3
Offset 同步与故障切换
MM2 通过 MirrorCheckpointConnector 将消费者 Offset 从源集群映射到目标集群，故障切换后 Consumer 可通过 RemoteClusterUtils.translateOffsets() 从正确位置继续消费，避免重复消费或数据丢失。
4
Topic 命名规则
同步到目标集群的 Topic 会加前缀（如 primary.order-topic），可通过 replication.policy.class 自定义命名规则（实现 ReplicationPolicy 接口），也可使用 IdentityReplicationPolicy 保持原名。
INFO

MM2 适合多数据中心灾备、数据聚合、集群迁移等场景。相比旧版 MirrorMaker 1，MM2 支持 Exactly-Once 语义、自动同步 Topic 配置变更和 ACL。

WARN

MM2 同步有延迟（通常 100ms~几秒），不适合需要强一致同步的场景；消息在跨集群同步后顺序可能改变（Partition 映射非一一对应时）。

Broker Params — Broker 关键参数调优
参数 默认值 作用 调优建议
num.network.threads 3 处理网络请求的线程数 建议 = CPU 核数，高并发场景可调到 8~16
num.io.threads 8 处理磁盘 IO 的线程数 建议 = 2×磁盘数，SSD 集群可适当减小
socket.send.buffer.bytes 102400 网络发送缓冲区大小 高吞吐场景调大到 4MB（4194304）
socket.receive.buffer.bytes 102400 网络接收缓冲区大小 同上，调大到 4MB，与 OS 的 rmem_max 协调
socket.request.max.bytes 104857600 单个请求最大字节数（100MB） 根据实际最大消息大小调整，不建议过大
log.flush.interval.messages Long.MAX_VALUE 强制刷盘前最多缓存的消息数 依赖 OS Page Cache 异步刷盘，不建议手动设置（会显著降低吞吐）
replica.fetch.max.bytes 1048576 (1MB) Follower 单次 Fetch 最大字节数 需大于最大消息大小，否则 Follower 无法复制大消息，ISR 永久缩水
message.max.bytes 1048588 (~1MB) Broker 接受的最大消息大小 需与 Producer 的 max.request.size 和 Consumer 的 fetch.max.bytes 三方协调一致
JVM — JVM GC 调优
JVM Kafka JVM GC 调优实践
1
堆大小设置
建议 Heap 设 6GB（-Xms6g -Xmx6g），不超过 8GB（避免 GC 停顿过长）。Kafka 大量使用 Page Cache，JVM 堆不需要很大；剩余内存留给 OS 做 Page Cache 才是关键——Page Cache 直接决定读写性能。
2
使用 G1GC（官方推荐）
Kafka 官方推荐 G1GC（JDK 9+ 默认），相比 CMS GC 停顿更可预测，适合大堆场景。
-XX:+UseG1GC -XX:MaxGCPauseMillis=20 -XX:InitiatingHeapOccupancyPercent=35 -XX:G1HeapRegionSize=16m -XX:MinMetaspaceFreeRatio=50 -XX:MaxMetaspaceFreeRatio=80
3
避免 Full GC
若 GC 频繁触发，逐步排查：① 消息过大导致大量临时对象；② Connector 插件内存泄漏；③ 增大 InitiatingHeapOccupancyPercent（默认 45，可调到 70）；④ 升级 JDK 版本（JDK 17+ ZGC 更低停顿）。
4
完整 JVM 参数示例
# KAFKA_JVM_PERFORMANCE_OPTS 推荐配置 export KAFKA_JVM_PERFORMANCE_OPTS="\ -server \ -XX:+UseG1GC \ -XX:MaxGCPauseMillis=20 \ -XX:InitiatingHeapOccupancyPercent=35 \ -XX:G1HeapRegionSize=16m \ -XX:MinMetaspaceFreeRatio=50 \ -XX:MaxMetaspaceFreeRatio=80 \ -XX:+ExplicitGCInvokesConcurrent \ -XX:+PrintGCDateStamps \ -XX:+PrintGCDetails \ -Xloggc:/data/kafka-gc.log" export KAFKA_HEAP_OPTS="-Xms6g -Xmx6g"
OS — OS 层调优
FILE DESCRIPTOR
文件描述符
每个 Partition 打开 3 个文件
  • 每个 Partition 打开 .log / .index / .timeindex 三个文件
  • 1000 个分区 = 3000 个 fd，默认 1024 限制极易耗尽
  • ulimit -n 1000000 临时修改
  • 永久生效：/etc/security/limits.conf 设置 nofile = 1000000
  • systemd 服务需设 LimitNOFILE=1000000
NETWORK BUFFER
网络缓冲区
调大内核 Socket 缓冲区
  • 写入 /etc/sysctl.conf 后 sysctl -p 生效
  • net.core.rmem_max = 134217728
  • net.core.wmem_max = 134217728
  • net.ipv4.tcp_rmem = 4096 65536 134217728
  • net.ipv4.tcp_wmem = 4096 65536 134217728
PAGE CACHE & DISK
Page Cache 与磁盘
Kafka 性能最关键的 OS 参数
  • 关闭 swap：vm.swappiness=1（不能设 0）
  • 文件系统推荐 XFS（性能优于 ext4）
  • 挂载加 noatime 减少无效磁盘写入
  • vm.dirty_ratio=80（Page Cache 脏页上限）
  • vm.dirty_background_ratio=5（后台刷盘触发点）
Metrics — 关键 JMX 监控指标
指标名 类型 含义 告警阈值
UnderReplicatedPartitions Broker ISR 不足的分区数（副本未全部同步） >0 立即告警，持续增加说明 Broker 过载或网络异常
ActiveControllerCount Broker 当前活跃 Controller 数（全集群应恰好为 1） ≠1 立即告警：0 = 无 Controller（集群瘫痪），>1 = 脑裂
OfflinePartitionsCount Broker 无 Leader 的 Partition 数（完全不可用） >0 立即告警，需紧急介入恢复
RequestHandlerAvgIdlePercent Broker 请求处理线程（IO 线程池）平均空闲率 <0.2 告警，IO 线程饱和，考虑增大 num.io.threads 或扩容
NetworkProcessorAvgIdlePercent Broker 网络处理线程平均空闲率 <0.3 告警，网络线程饱和，增大 num.network.threads
BytesInPerSec Topic 每秒写入字节数 接近网卡带宽时告警（通常设 70% 作为预警线）
BytesOutPerSec Topic 每秒读出字节数（含副本复制流量） 同上，注意出方向流量 = 消费流量 + 副本复制流量
MessagesInPerSec Topic 每秒写入消息条数 容量规划参考指标，结合消息大小评估 TPS 上限
records-lag-max Consumer 消费者组中最大 Lag 值（最慢分区的积压量） 根据业务 SLA 设阈值，持续增大说明消费能力不足
fetch-rate Consumer Consumer 拉取速率（次/秒） 突然下降说明消费端出现瓶颈（DB 慢查询、GC 等）
Lag — Consumer Lag 监控与告警
Consumer Lag 示意图 — LEO vs Committed Offset
MONITOR Consumer Lag 监控与告警
1
获取 Lag 数据
kafka-consumer-groups.sh \ --bootstrap-server localhost:9092 \ --group my-group --describe # 输出：GROUP / TOPIC / PARTITION / CURRENT-OFFSET / LOG-END-OFFSET / LAG / CONSUMER-ID
2
Prometheus + kafka-exporter
部署 kafka-exporter（danielqsj/kafka-exporter）暴露 JMX 指标为 Prometheus 格式，配置 scrape job，在 Grafana 创建 kafka_consumergroup_lag 面板实时展示各 Group 的 Lag 趋势。
3
分级告警规则
P2：Lag 持续 5 分钟增大 → Slack 通知；
P1：Lag 超过阈值（如 10 万条）持续 10 分钟 → PagerDuty 升级告警；
P0：Lag 极大且消费者数 = 0 → Consumer 全部宕机，立即介入。
4
Lag 增大的根因排查
① 消费者处理耗时增加：下游 DB 慢查询、外部接口超时，导致每条消息处理时间拉长；
② Consumer 频繁 Rebalance：Rebalance 期间所有消费者暂停消费，Lag 快速增大；
③ 消费者实例不足：Partition 数 > Consumer 数，部分 Consumer 处理多个 Partition；
④ 消息量突增：活动大促、上游业务波峰，写入速率远超消费能力；
⑤ 消费者 OOM 重启：内存不足反复崩溃，消费中断。
