事务与 Exactly-Once

幂等 Producer · Transaction Coordinator · 2PC · EOS · 隔离级别 · Flink 集成

概览 幂等 Producer 事务 API 执行全流程 两阶段提交 端到端 EOS 隔离级别 面试速答
三层保障体系概览
LAYER 01 · AT-LEAST-ONCE
至少一次
  • acks=-1 + retries 保证消息不丢
  • 网络抖动重传时可能产生重复消息
  • 默认配置，适合大多数业务场景
  • 消费端需要做幂等处理
LAYER 02 · 幂等（单分区 EOS）
精确一次（单分区）
  • enable.idempotence=true
  • 单 Producer + 单 Session + 单 Partition
  • 实现：PID + Sequence Number Broker 端去重
  • 性能开销约 5%
LAYER 03 · 事务（跨分区 EOS）
精确一次（端到端）
  • transactional.id + 事务 API
  • 跨多个 Partition 的原子写入
  • 支持 Consume-Transform-Produce 模式
  • 性能开销约 20%
INFO

三层是递进关系：开启幂等自动满足 at-least-once，开启事务自动开启幂等。代价也依次增加：性能开销约 5%（幂等）→ 约 20%（事务）。根据业务对一致性的实际要求选择合适层次，不要过度设计。

幂等 Producer 原理
幂等机制 — PID + Sequence Number 去重
STEPS 幂等 Producer 工作机制
1
开启配置
enable.idempotence=true（Kafka 3.0+ 默认开启）。Kafka 自动强制：acks=-1、retries=Integer.MAX_VALUE、max.in.flight.requests.per.connection≤5，不符合则启动时报错。
2
PID 分配
Producer 启动时向 Broker 的 InitProducerId 接口申请全局唯一的 ProducerID（PID）。PID 在 Producer 重启后重新申请，因此幂等只在单次 Session 有效（这是幂等 vs 事务的核心区别）。
3
Sequence Number
每个 <PID, TopicPartition> 维护独立的序列号（从 0 开始，单调递增），写入每条 RecordBatch 的 header 中。
4
Broker 去重
Broker 内存中为每个 <PID, Partition> 记录最近 5 个 batch 的序列号范围。重传时比较序列号：等于已记录则 ACK 不写盘（去重），小于则丢弃，跳跃则报错（乱序检测）。
WARN

幂等只保证单 Producer + 单 Session + 单 Partition 内不重复。Producer 重启后 PID 变化，跨 Partition 写入没有原子性。需要跨 Partition 原子写或跨 Session 保证幂等，必须使用事务。

事务 API 使用
CODE Producer 事务 API 完整示例
▶
// 配置 Properties props = new Properties(); props.put("bootstrap.servers", "localhost:9092"); props.put("transactional.id", "order-producer-001"); props.put("enable.idempotence", "true"); KafkaProducer<String, String> producer = new KafkaProducer<>(props); // 初始化事务（只调用一次） producer.initTransactions(); try { producer.beginTransaction(); // 跨多个 Partition 原子写入 producer.send(new ProducerRecord<>("order-topic", orderId, orderJson)); producer.send(new ProducerRecord<>("inventory-topic", itemId, stockJson)); producer.send(new ProducerRecord<>("payment-topic", payId, payJson)); // 提交事务（Consumer 在 read_committed 模式下才能看到以上消息） producer.commitTransaction(); } catch (ProducerFencedException e) { // 被新 Producer 实例 Fence 掉（epoch 过期），直接关闭 producer.close(); } catch (Exception e) { // 其他异常，中止事务 producer.abortTransaction(); }
INFO

transactional.id 是业务层面的唯一标识，相同 ID 的新 Producer 启动会使旧 Producer 失效（epoch+1），防止僵尸 Producer（Zombie Fencing）。生产中建议绑定业务实例 ID，如 order-service-${instanceId}。

事务执行全流程
事务五阶段流程
PHASE 五阶段详细说明
1
initTransactions()
Producer 向 Transaction Coordinator（TC） 发送 InitProducerIdRequest，携带 transactional.id。TC 查询 __transaction_state，若是新 ID 则分配 PID+epoch=0；若已存在则 epoch+1（Zombie Fencing 旧 Producer）。将 PID+epoch 返回给 Producer。
2
beginTransaction()
仅在 Producer 本地设置一个 transactionState = IN_TRANSACTION 标志，不发网络请求。轻量操作。
3
send()（写数据）
Producer 发送消息到各 Partition（消息带 PID+epoch+sequence），同时通过 AddPartitionsToTxnRequest 通知 TC 记录本次事务涉及的 Partition 列表（存入 __transaction_state）。此时消息已写入 Partition Log，但 Consumer 在 read_committed 模式下不可见（LSO 未推进）。
4
commitTransaction()
Producer 向 TC 发送 EndTxnRequest（COMMIT）→ TC 在 __transaction_state 写入 COMMIT 标记 → TC 向每个参与的 Partition 发送 WriteTxnMarkersRequest，写入 Transaction Marker（Control Batch，isTransactionCommit=true）→ Consumer 的 LSO 推进，消息变为可见 → TC 清理 __transaction_state 中的事务记录。
5
abortTransaction()
流程同 commit，但写入 ABORT Marker（isTransactionCommit=false）。Consumer 遇到 Abort Marker 后跳过该事务的所有消息，消息物理上仍然存储在 Log 中，只是 Consumer 层面过滤。
两阶段提交实现
2PC Kafka 两阶段提交过程
P1
Prepare（准备阶段）
Producer 向 TC 发送 EndTxnRequest（COMMIT）。TC 将事务状态从 ONGOING 写为 PREPARE_COMMIT（持久化到 __transaction_state）。此时即使 TC 宕机，重启后也能继续完成提交（幂等性保证）。
P2
Commit（提交阶段）
TC 向各参与 Partition 的 Leader 发送 WriteTxnMarkersRequest。每个 Partition Leader 写入 Transaction Marker 到本地 Log。所有 Partition 确认后，TC 将事务状态改为 COMPLETE_COMMIT，清理记录。
传统 2PC
经典分布式事务
协调者 + 参与者模型，prepare 后持锁等待
  • 协调者单点故障可能导致事务悬挂
  • Participant 在 prepare 后持有锁等待协调者
  • 任一 Participant 宕机可能阻塞整个事务
  • 同步阻塞严重影响系统吞吐
  • 网络分区时可能出现数据不一致
Kafka 2PC
改进的两阶段提交
TC 通过 __transaction_state 持久化，无锁设计
  • TC 持久化状态，宕机自愈，无单点阻塞
  • Participant（Partition Leader）不持有锁
  • 消息已写入 Log，commit 只写 Control Batch
  • Marker 写入异步，不阻塞正常写入
  • 宕机重启后 TC 继续完成剩余 Marker 写入
KEY

Kafka 的 2PC 相比传统 2PC 的关键改进：无锁设计。消息在 prepare 阶段已经写入了 Partition（只是 Consumer 看不到），commit 阶段只是写一个 Control Batch 的 Marker，不需要锁，也不阻塞写入。

端到端 Exactly-Once（EOS）
Consume-Transform-Produce 模式 — EOS 事务边界
STEPS Consume-Transform-Produce EOS 实现步骤
1
Consumer 消费
Consumer 以 isolation.level=read_committed 消费 Source Topic，只读已提交的事务消息，避免处理中间状态。
2
开启事务
处理前 producer.beginTransaction()，标记事务开始。
3
处理 + 生产
业务逻辑处理消费到的消息，将结果写入 Sink Topic（producer.send()）。同时将 Consumer 的 Offset 提交到 __consumer_offsets，作为事务的一部分（通过 producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata)）。
4
原子提交
producer.commitTransaction() 原子提交：Sink 消息 + Offset 提交同时对外可见（或同时回滚）。若事务 abort，消费的 offset 不会提交，Consumer 重启后会重新消费，实现精确一次。
KEY

sendOffsetsToTransaction 是 EOS 的关键：将 Consumer Offset 的提交纳入 Producer 事务，使消费进度和写出结果强一致。没有这步，即使 Producer 事务成功，Offset 已经提交的情况下重启仍然会重复消费。

Consumer 事务隔离级别
read_uncommitted
读未提交（默认）
读取所有消息，包括进行中的事务消息和已 abort 的消息
  • 性能最高，没有额外过滤开销
  • 可能读到后来被 abort 的"脏数据"
  • 消费边界基于 HW（High Watermark）
  • 适合：不涉及事务的普通场景
  • 适合：日志消费、监控数据采集
read_committed
读已提交
只读已提交事务的消息，基于 LSO 推进消费边界
  • 等到 Commit Marker 到达后消息才可见
  • 自动过滤 Abort 事务的所有消息
  • 消费边界基于 LSO（Last Stable Offset）
  • 适合：参与 EOS 的下游消费者
  • 适合：财务对账、订单状态同步
维度 read_uncommitted read_committed
可见消息范围 所有消息，含进行中事务、已 abort 事务 仅已提交事务消息，abort 消息被过滤
性能开销 无额外开销 需要缓冲未完成事务消息，略有开销
Lag 计算基准 基于 HW（High Watermark） 基于 LSO（Last Stable Offset）
适用场景 普通消费、日志采集、监控 EOS 下游、财务、订单、对账
WARN

使用 read_committed 时，Consumer Lag 监控需要基于 LSO 而非 HW 计算，否则会虚报 Lag。进行中的长事务会让 LSO 远低于 HW，看起来 Lag 很大，实际上是正常的事务等待。

面试速答
Q&A 高频面试题 · 事务与 Exactly-Once
Q1
Kafka 幂等和事务的区别？
幂等（enable.idempotence=true）：单 Producer + 单 Session + 单 Partition 级别去重，通过 PID+Sequence Number 实现，性能开销约 5%。事务（transactional.id）：跨 Partition 原子写入，跨 Session 保证（同 transactional.id 的新实例可接续），支持 Consume-Transform-Produce 的端到端 EOS，性能开销约 20%。事务包含幂等，是超集。
Q2
Kafka 事务是如何实现原子性的？
通过两阶段提交（2PC）：① Producer 向 TC 发 commit 请求，TC 持久化 PREPARE_COMMIT 状态；② TC 向所有参与 Partition 发 WriteTxnMarkers 请求，写入 Commit Marker；③ Consumer 在 read_committed 模式下遇到 Commit Marker 后才对外暴露该事务的所有消息。关键：消息在 Phase 1 已经写入 Partition（无锁），Phase 2 只写一个 Control Batch，极轻量。
Q3
什么是 Zombie Fencing？为什么需要？
Zombie Producer 是指：某个 Producer 因网络分区等原因以为自己挂了，重启后以相同 transactional.id 起了一个新实例，此时旧实例可能还在运行，两个 Producer 同时写同一个 Topic 会导致数据混乱。Zombie Fencing 机制：TC 为每个 transactional.id 维护 epoch，新 Producer 启动时 epoch+1，旧 Producer 收到任何请求时 TC 校验 epoch，epoch 过低则返回 ProducerFencedException，旧 Producer 必须关闭。
Q4
Consume-Transform-Produce（CTP）模式如何实现 EOS？
关键是将 Consumer Offset 的提交纳入 Producer 事务（sendOffsetsToTransaction）：① Consumer 消费 Source Topic（read_committed）；② 开启 Producer 事务；③ 业务处理，结果写入 Sink Topic；④ 将 Consumer Offset 作为事务一部分提交（而非单独 commitSync）；⑤ commitTransaction：Sink 消息和 Offset 同时提交或同时回滚。若事务 abort，Offset 回滚，Consumer 重启后重新消费并重新处理，保证精确一次。
Q5
开启 Kafka 事务对性能有多大影响？应该怎么评估？
事务开销来源：① initTransactions 额外网络请求（启动时一次）；② AddPartitionsToTxn 请求（每次 beginTransaction 后第一次写新 Partition 时）；③ Transaction Marker 写入（commit/abort 时写 Control Batch）；④ Consumer 过滤 abort 消息（read_committed 有额外开销）。整体吞吐下降约 20%。评估方式：在 staging 环境用与生产相同的消息大小和 QPS 压测，对比事务开启前后的 P99 延迟和吞吐，结合业务的一致性要求决定是否值得。
