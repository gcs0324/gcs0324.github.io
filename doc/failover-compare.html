Redis 哨兵 · Redis 集群 · Kafka ISR — 三种主流方案的触发条件、选举方式、数据安全取舍，以及 Kafka Controller 三种典型宕机场景

对比总览 Redis 哨兵 Redis 集群 Kafka ISR Controller 三场景
Overview · 对比总览
面试官视角

这三种机制都解决"主节点挂了谁来接管"的问题，但思路完全不同。Redis 哨兵是外置监控进程投票，专门盯着一主多从；Redis 集群把监控内置进每个节点，用 gossip 协议互相探活；Kafka 则依赖一个"总控制器" Controller，由它统一触发分区 Leader 切换。三者在故障检测时间、脑裂防护、数据丢失风险上各有取舍。

面试高频追问：异步复制会丢数据吗？ ——三种方案底层复制都是异步，主库提交后才向 Slave 同步，主库宕机瞬间未同步的写入都会丢失。Redis 可用 min-replicas-to-write 降低风险，Kafka 用 acks=all + ISR 提供更强保证（但也只是"至少送达 ISR 中的副本"，不是"零丢失"）。

Redis Sentinel · 哨兵故障转移
面试官视角

哨兵的核心思路：用一组独立进程（Sentinel）专门监控 Redis 主从。单个 Sentinel 看到主库不响应只是"主观下线（SDOWN）"，只有 ≥ quorum 个 Sentinel 都认为主库不可达，才升级为"客观下线（ODOWN）"，防止网络抖动误判。

经典追问："Sentinel 自己也可能宕机，谁来协调故障转移？"——Sentinel 之间会用 类 Raft 投票选出一个 Leader Sentinel 来执行提升动作，其余 Sentinel 只负责监控，不插手。这个过程需要 超过半数 Sentinel 的投票，即使 quorum 设置较小也无法绕过。

SENTINEL 哨兵故障转移 — 5 步流程
①
SDOWN — 主观下线
Sentinel 每隔 1 s 向 Master 发 PING；若连续 down-after-milliseconds（默认 30 000 ms）无响应，该 Sentinel 单方面标记 Master 为 SDOWN（Subjectively Down）。
# sentinel.conf sentinel monitor mymaster 192.168.1.10 6379 2 # quorum = 2 sentinel down-after-milliseconds mymaster 30000 # 30 s 超时
②
ODOWN — 客观下线
该 Sentinel 向其他 Sentinel 发送 SENTINEL is-master-down-by-addr 查询；当 收到 ≥ quorum 个确认时，Master 被标记为 ODOWN（Objectively Down），触发故障转移流程。
注意：quorum 只决定 ODOWN 门槛，Leader Sentinel 选举仍需 majority（超半数）投票。
③
Leader Sentinel 选举（类 Raft）
任何一个检测到 ODOWN 的 Sentinel 都可以发起"请投我一票"请求（带自增 epoch）。Sentinel 遵守先到先得原则，每个 epoch 只投一票。第一个拿到超半数票的 Sentinel 成为 Leader，负责执行后续步骤。
# 选举结果示例日志 +elected-leader master mymaster 192.168.1.10 6379 +failover-state-select-slave master mymaster ...
④
筛选最优 Slave
Leader Sentinel 按以下优先级依次筛选 Slave，排除不可用候选后取最优：
排除规则（任一满足即排除）： 断线时间 > down-after-milliseconds × 10 数据滞后量过大（INFO replication 中 slave_repl_offset 差距） 选择优先级（依次比较）： 1. slave-priority 越小越优先（0 = 永不晋升） 2. replication offset 越大越优先（数据最新） 3. runID 字典序越小越优先（兜底决胜）
⑤
执行故障转移
Leader Sentinel 向选中的 Slave 发送 SLAVEOF NO ONE 使其独立为新 Master；等待其就绪后，向其余 Slave 发送 SLAVEOF <新Master>，并更新配置文件（CONFIG REWRITE）。最后通知客户端新主地址（通过 pub/sub 频道 +switch-master）。
# 客户端监听切换事件 SUBSCRIBE __sentinel__:hello # 收到 +switch-master mymaster 旧IP 旧Port 新IP 新Port
⚠ 数据丢失

Slave 晋升后，原 Master 宕机期间未同步的写入永久丢失。min-replicas-to-write 1 + min-replicas-max-lag 10 可在无 Slave 可用时让 Master 拒绝写入，降低脑裂期间的数据丢失窗口。

Redis Cluster · 分片集群故障转移
面试官视角

集群模式不依赖外部哨兵，监控逻辑内置于每个节点。节点通过 gossip 协议互相交换集群状态，当某个 Master 对超半数 Master 不可达时，集群内部自动触发 Slave 的晋升竞选。

与哨兵的关键区别：集群中 Slave 是"自己发起选举"而非被外部指派。复制偏移量最大（数据最新）的 Slave 会比其他 Slave 等待更短的随机延迟，因此通常率先发起投票请求，自然获得优先晋升权。

经典追问："cluster-require-full-coverage 是什么？"——默认 yes，任意一个 slot 范围无 Master 提供服务时，整个集群停止对外服务。设为 no 则允许部分 slot 不可用时其余 slot 继续服务，适合容忍局部故障的业务场景。

CLUSTER 分片集群故障转移 — 5 步流程
①
PFAIL — 疑似故障
每个节点每隔 cluster-node-timeout / 10 向随机节点发 PING；若某 Master 在 cluster-node-timeout（默认 15 000 ms）内没有回复 PONG，当前节点标记其为 PFAIL（Possible Failure），并通过 gossip 广播给其他节点。
# cluster.conf（自动维护，示例） cluster-node-timeout 15000 # 15 s 超时 → PFAIL
②
FAIL — 确认故障广播
当某节点收到关于同一 Master 的 PFAIL gossip，累计超过集群中 Master 数量的半数时，将其状态升级为 FAIL，并向全集群广播 CLUSTER FAIL 消息，通知所有节点停止向该 Master 路由请求。
③
Slave 发起竞选（延迟机制）
该 Master 的所有 Slave 检测到 FAIL 后，等待随机延迟后发起选举请求。延迟计算：
延迟 = 500ms + random(0~500ms) + (MAX_OFFSET - slave_offset) × 系数 # 复制偏移量越大（数据越新）→ 延迟越短 → 越先发起投票 # 保证数据最新的 Slave 通常率先获得投票权
④
Master 投票，超半数者胜
Slave 向全集群的 Master 节点发送 FAILOVER_AUTH_REQUEST（携带当前 configEpoch）；Master 在同一 epoch 只投一票（先到先得）。第一个收到超半数 Master 赞成票的 Slave 赢得选举，晋升为新 Master。
# 命令交互示例 Slave → Masters : FAILOVER_AUTH_REQUEST (epoch=42) Master → Slave : FAILOVER_AUTH_ACK (epoch=42) # 收到 > N/2 个 ACK → 晋升
⑤
接管 Slot，更新集群状态
新 Master 广播 CLUSTER UPDATE 消息，宣告自己接管原 Master 负责的所有 slot 范围，并将 configEpoch 加一。其他节点更新路由表，客户端下次请求时收到 MOVED 重定向，感知到新拓扑。
⚠ 数据丢失

与哨兵相同：异步复制导致未同步到 Slave 的写入丢失。此外，若某个 Master 的所有 Slave 都宕机，且 cluster-require-full-coverage yes，则整个集群停止对外服务。

Kafka ISR · Partition Leader 故障转移
面试官视角

Kafka 的"主从切换"概念粒度更细——不是节点级，而是 Partition 级。每个 Partition 有一个 Leader 和若干 Follower，Leader 处理所有读写，Follower 持续追赶复制。当 Leader 所在 Broker 宕机，Controller（集群总调度节点）负责从 ISR（In-Sync Replicas）中选出新 Leader，并通知所有 Broker 更新 MetaData。

Kafka 与 Redis 的最大区别：Kafka 有 acks=all + min.insync.replicas 的写入确认机制，可以确保消息被至少 N 个副本持久化后才向 Producer 返回成功，大幅降低数据丢失窗口（但不能保证零丢失，因为极端场景下 ISR 可能只剩 Leader 本身）。

KAFKA · ISR Partition Leader 故障转移 — 核心流程
①
Follower 脱离 ISR
Follower 若超过 replica.lag.time.max.ms（默认 30 s）没有追上 Leader 的 LEO，将被 从 ISR 中摘除，降级为普通副本。ISR 实时反映"当前与 Leader 保持同步"的副本集合。
# broker 配置 replica.lag.time.max.ms = 30000 # 超时则踢出 ISR min.insync.replicas = 2 # ISR < 2 时 acks=all 的写入报错
②
Controller 感知 Broker 宕机
ZK 模式：Leader Broker 的 ZooKeeper session 超时（~18 s），临时节点 /brokers/ids/<id> 自动消失，Controller 的 Watch 触发。
KRaft 模式：Broker 心跳超时（<1 s），Active Controller 直接感知，无需 ZK。
③
Controller 从 ISR 选新 Leader
Controller 遍历该 Broker 承担 Leader 的所有 Partition，对每个 Partition 从其 ISR 列表中取第一个存活 Follower 作为新 Leader，并更新 ZK / KRaft 元数据，随后向所有 Broker 广播 LeaderAndIsrRequest。
ISR = [Broker-1(宕), Broker-2, Broker-3] ↓ Broker-1 宕机 新 Leader = Broker-2（ISR 中第一个存活） LeaderEpoch 自增，防止旧 Leader 幽灵写入
ISR 耗尽时

unclean.leader.election.enable = false（默认，推荐）：等待 ISR 中至少一个副本恢复，期间 Partition 不可用 → CP，保数据一致，牺牲可用性。
unclean.leader.election.enable = true：允许 ISR 外落后的副本当 Leader → AP，保可用性但已提交的消息可能丢失。
金融、订单类业务保持 false；日志、监控类可酌情设 true。配合 acks=all + min.insync.replicas=2 可降低 ISR 耗尽的概率。

Producer 配置

Leader 切换期间 Producer 会短暂收到 NOT_LEADER_FOR_PARTITION 错误。配置重试后客户端会自动等待新 Leader 上位，业务无感知：acks=all、retries=Integer.MAX_VALUE、delivery.timeout.ms=120000、enable.idempotence=true（幂等，防重复写入）。

Controller Scenarios · 三种典型宕机场景
面试官视角

很多人以为"Controller 宕机 = 先选 Controller 再选 Partition Leader"，其实两种选举是相互独立的，触发条件不同，发生与否取决于宕机的节点扮演什么角色。理解这三个场景，面试时可以精准回答"什么情况下会同时触发两种选举"。

前提：ZK 模式中，Controller 本身也是一个普通 Broker，可能同时担任某些 Partition 的 Leader。KRaft Isolated 模式下 Controller 是专用节点，不持有任何 Partition，因此场景 C 在 KRaft Isolated 下不会出现。

场景 A
普通 Broker 宕机
非 Controller 节点宕机，仅触发 Partition Leader 选举
1
ZK 临时节点 /brokers/ids/N 消失，Controller 的 Watch 触发
2
不涉及 Controller 选举，Controller 仍正常运行
3
Controller 找出该 Broker 担任 Leader 的所有 Partition，逐一从 ISR 选新 Leader
4
广播 LeaderAndIsrRequest，通知全集群更新 Metadata
✓
只有 Partition Leader 选举，耗时约数秒（Partition 数量 × 单次元数据操作）
场景 B
Controller 宕机（无 Leader 分区）
Controller 宕机，但该节点未担任任何 Partition 的 Leader
1
ZK 临时节点 /controller 消失，所有 Broker 监听到变化
2
存活 Broker 竞相抢占 /controller 临时节点，写入成功者成为新 Controller
3
新 Controller 从 ZK 加载全量 Metadata，重建内存状态
4
不需要 Partition Leader 选举：原 Controller 不持有任何 Leader，所有 Partition 仍正常服务
✓
只有 Controller 选举，ZK 模式约 18 s（session 超时）；KRaft 模式 <1 s
场景 C
Controller 宕机（有 Leader 分区）
最复杂：Controller 同时担任部分 Partition 的 Leader，两种选举都触发
1
ZK 临时节点 /controller 消失 + /brokers/ids/N 消失，同时触发
2
先完成 Controller 选举：存活 Broker 抢占 /controller 临时节点
3
再触发 Partition Leader 选举：新 Controller 就位后才能执行，为原 Controller 持有的 Leader 分区选出新 Leader
4
两阶段串行完成，总不可用时间 = Controller 选举时间 + Partition Leader 选举时间
✓
两种选举都发生，顺序：Controller 选举 → Partition Leader 选举；ZK 模式总耗时可能超 30 s；KRaft 模式大幅缩短
面试连环问

Q：KRaft 模式下场景 C 还会发生吗？
A：取决于部署方式。Isolated 模式（生产推荐）：Controller 节点专用，不承载 Partition，场景 C 不会出现；Combined 模式（开发/测试）：Controller 节点同时是 Broker，仍可能触发场景 C，但选举耗时已从 ~18 s 降至毫秒级。
