INFO

Kafka 的核心定位是分布式流平台，不仅是 MQ，还支持流处理（Kafka Streams）和数据管道（Kafka Connect）。它把消息持久化为有序日志，任何消费者都可以在任意时刻从任意 Offset 开始消费，这是传统 MQ 无法比拟的能力。

Components · 核心组件
Kafka 整体架构 — Producer / Broker Cluster / Consumer Group / ZooKeeper
BROKER
Broker
Kafka 服务进程，一个节点部署一个 Broker
  • 接收 Producer 写入的消息，追加到本地 Log
  • 响应 Consumer 的 Fetch 请求，返回消息数据
  • 维护 Partition 的 Leader / Follower 状态
  • Controller Broker 负责集群元数据管理和分区再均衡
TOPIC
Topic
消息的逻辑分类，生产者写入、消费者订阅的单元
  • 一个 Topic 可以有多个 Partition，跨 Broker 分布
  • Producer 指定 Topic 写入；Consumer 订阅 Topic 消费
  • 可配置 保留策略：按时间（默认 7 天）或按大小
  • 支持按 key 路由到固定 Partition（保证局部有序）
PARTITION
Partition
Topic 的物理分片，并发和顺序的基本单位
  • 每个 Partition 是一段只追加的有序日志
  • Partition 数决定消费并发度上限
  • 消息在 Partition 内按 Offset 严格有序
  • 跨 Partition 不保证顺序，按需用 key 路由同一 Partition
REPLICA
Replica
Partition 的副本，保证高可用
  • Leader Replica：承担所有读写请求
  • Follower Replica：从 Leader 同步数据，不对外服务
  • ISR（In-Sync Replicas）：与 Leader 保持同步的副本集合
  • Leader 挂掉后，从 ISR 中选举新 Leader，保证数据不丢
Roles · Producer / Consumer / Consumer Group
PRODUCER
生产者
  • 指定 Topic 写入消息
  • acks 控制持久性：0 / 1 / all
  • 可指定 key，key 相同的消息路由到同一 Partition
  • 不指定 key 时轮询（Round Robin）分配 Partition
  • 支持批量发送（linger.ms + batch.size）
  • 幂等 Producer：enable.idempotence=true
CONSUMER
消费者
  • 订阅一个或多个 Topic
  • 主动 Pull 拉取消息（非 Push）
  • 维护自己的消费 Offset
  • Offset 提交到 __consumer_offsets Topic
  • 支持手动提交 / 自动提交（enable.auto.commit）
  • 可随时从任意 Offset 重置消费位置（回放）
CONSUMER GROUP
消费者组
  • 多个 Consumer 的逻辑分组，共用一个 group.id
  • 组内负载均衡：Partition 按策略分配给成员
  • 分配策略：RangeAssignor / RoundRobinAssignor / StickyAssignor
  • Consumer 加入 / 退出触发 Rebalance
  • 不同 Group 之间独立，互不影响
  • GroupCoordinator（Broker）管理组内成员状态
RULE Consumer Group 核心规则
1
同 Group 内：每个 Partition 只被一个 Consumer 消费
实现组内负载均衡，避免重复消费。这是 Kafka 实现点对点模式的基础。
2
不同 Group 之间：同一条消息各 Group 独立消费
实现发布订阅模式。N 个 Group 订阅同一 Topic，每个 Group 都能收到完整的消息流。
3
Consumer 数量 > Partition 数量时，多余的 Consumer 空闲
扩容 Consumer 超过 Partition 数没有意义，增加 Partition 数才能提升并发度上限。
4
两种模式统一实现
所有消费者同一 Group → 点对点（每条消息只消费一次）；每个消费者不同 Group → 发布订阅（每条消息每个 Group 各消费一次）。
ZooKeeper & KRaft · 元数据管理
ZK ZooKeeper 承担的 5 个职责
1
Broker 注册与存活检测
每个 Broker 启动时在 ZK 的 /brokers/ids 节点注册临时节点，宕机后节点自动删除，触发 Controller 感知。
2
Controller 选举
所有 Broker 抢占 ZK 的 /controller 节点，抢到的成为 Controller，负责 Leader 选举和分区再均衡。
3
Topic 分区元数据存储
Topic 的分区数、副本分配方案、ISR 列表存储在 ZK 的 /brokers/topics 路径下。
4
Consumer Group Offset 存储（旧版）
Kafka 0.9 之前，Offset 存储在 ZK 的 /consumers 下。新版改为内部 Topic __consumer_offsets，减少 ZK 压力。
5
ACL 权限配置
访问控制列表（ACL）配置持久化在 ZK 的 /kafka-acl 路径，Broker 启动时加载。
ZOOKEEPER ZooKeeper 模式
─
外部依赖
需要单独部署 ZooKeeper 集群（通常 3 或 5 节点），增加运维负担。
─
元数据操作有额外网络跳转
Controller 先读写 ZK，再通知其他 Broker，链路长，延迟高。
─
Controller 单点瓶颈
全集群只有一个 Active Controller，大规模集群下成为性能瓶颈。
─
扩展性瓶颈
ZK 节点数量有限，单集群 Partition 数超过 20 万时元数据变更明显变慢。
KRAFT KRaft 模式
✓
内置 Raft 共识协议
Controller 节点自行通过 Raft 选举，无需外部协调服务。
✓
元数据存储在 @metadata Topic
元数据以事件日志形式存储，Broker 通过 Fetch 同步，一致性更强。
✓
无外部依赖
Kafka 3.3 起生产可用，Kafka 4.0 完全移除 ZooKeeper 支持。
✓
集群规模可扩展到 100 万+ 分区
Controller Quorum 直接管理元数据，去掉中间层后扩展性大幅提升。
KRAFT

KRaft 的核心优势：启动更快（无需等待 ZK 连接）、元数据变更延迟更低（少一跳网络）、集群规模可扩展到 100 万+ 分区。从 Kafka 3.3 起可在生产环境使用 KRaft，Kafka 4.0 已完全移除 ZooKeeper。

Message Model · 点对点 vs 发布订阅
QUEUE 点对点模式
Q
所有消费者在同一个 Consumer Group
Kafka 实现：设置 group.id=same-group，所有实例共用一个组 ID。
A
每条消息只被消费一次
Partition 在组内唯一分配，保证同一消息不会被两个 Consumer 重复消费。
B
横向扩展消费能力
增加组内 Consumer 实例数（不超过 Partition 数）即可线性提升吞吐。
TOPIC 发布订阅模式
Q
每个消费者（或服务）使用独立的 Consumer Group
Kafka 实现：不同服务配置不同 group.id，各自维护独立 Offset。
A
每条消息被每个 Group 各消费一次
N 个 Group 订阅同一 Topic，每个 Group 都能独立消费完整的消息流。
B
新增订阅者无需改动 Producer
只需创建新的 Consumer Group 从头消费，已有 Producer 和 Consumer 完全不感知。
INFO

Kafka 通过 Consumer Group 机制同时支持两种模式：所有消费者同 Group → 点对点；每个消费者不同 Group → 发布订阅。两种模式可以混用，同一个 Topic 可以同时被点对点消费的 Group 和独立订阅的多个 Group 消费。

Offset · 消息定位机制
Partition 日志 Offset 示意 — Committed Offset / Current Offset / HW / LEO
OFFSET Offset 关键概念
①
消息定位三要素：Topic + Partition + Offset
在 Kafka 中唯一定位一条消息，需要同时指定 Topic 名称、Partition 编号和 Offset 值。
②
Offset 由 Consumer 自己维护
提交到内部 Topic __consumer_offsets，Broker 不主动推进。Consumer 可以随时重置 Offset 实现消息回放。
③
Offset 只在 Partition 内单调递增，不跨 Partition 比较
HW（High Watermark）是消费者可见的最大 Offset，只有 ISR 中所有副本都同步的消息才能超过 HW 被消费；LEO（Log End Offset）是日志末尾下一条消息的 Offset。
Log Segment · 文件结构
FILES Log Segment 三类文件
1
.log — 实际消息数据文件
顺序写入，每个 RecordBatch 追加到文件末尾。只追加写，不修改，充分利用磁盘顺序 IO 性能。文件名即该 Segment 的基础 Offset（20 位零填充）。
2
.index — 稀疏 Offset 索引
每隔 N 字节写一条索引，存储 offset → position（文件物理偏移）的映射。查找时先二分查找 .index 定位大致位置，再顺序扫描 .log。
3
.timeindex — 时间戳索引
存储 timestamp → offset 的映射，支持按时间查找（如回溯到某个时间点）。与 .index 配合使用，先找 Offset 再找 Position。
/data/kafka-logs/order-topic-0/ 00000000000000000000.log # 基础 offset = 0 00000000000000000000.index 00000000000000000000.timeindex 00000000000001048576.log # 滚动后的新 segment，基础 offset = 1048576 00000000000001048576.index 00000000000001048576.timeindex
ROLL

Segment 滚动条件（满足任意一个即创建新 Segment）：文件大小超过 log.segment.bytes（默认 1 GB）；或距上次滚动时间超过 log.roll.hours（默认 7 天）。旧 Segment 在保留期满后由后台线程统一删除。

RecordBatch · 消息格式 V2
RecordBatch 消息格式 V2 — 字段结构示意
V2

RecordBatch V2 相比 V1 的三大优势：批量压缩（整个 Batch 作为整体压缩，比 V1 的单条压缩效率高得多，压缩比更好）；支持事务（ProducerId + ProducerEpoch + BaseSequence 字段组合实现 Exactly-Once 语义）；变长编码 Varint，减少小整数的空间占用，整体消息格式更紧凑。

Interview · 面试速答
Q1 Kafka 与 RabbitMQ 的核心区别？
架
架构差异
RabbitMQ 是传统 AMQP Broker，消息存在内存 / 磁盘队列，消费后删除；Kafka 是分布式追加日志系统，消息持久化到磁盘，保留到期后才删。
溯
消息回溯
RabbitMQ 消费后即删，不支持回溯；Kafka 保留到期（默认 7 天），Consumer 可以重置 Offset 随时重放历史消息。
序
顺序保证
RabbitMQ 单队列有序，集群下无法保证；Kafka 在单 Partition 内严格有序，跨 Partition 不保证。
量
吞吐对比
Kafka 顺序 IO + 批量写入 + 零拷贝，百万级 msg/s；RabbitMQ 每条消息 ack 一次，万级 msg/s。
Q2 Kafka 为什么用 Partition 而不是整个 Topic 存储？
扩
水平扩展
Partition 可以分布在不同 Broker 上，单个 Topic 的数据量可以突破单机磁盘限制，线性扩展存储和读写能力。
并
并发消费
Consumer Group 按 Partition 分配，多个 Consumer 可以并行消费不同 Partition，消费吞吐随 Partition 数线性扩展。
序
有序性成本
在 Partition 内保证顺序比全局有序成本低得多——全局有序需要全局锁或单点写入，而 Partition 内顺序只需追加写。按 key 路由到同一 Partition 即可实现业务级有序。
Q3 ZooKeeper 在 Kafka 中做了什么？KRaft 如何替代？
ZK
ZooKeeper 三大职责
Broker 注册（临时节点，宕机自动感知）、Controller 选举（抢占 /controller 节点）、元数据存储（Topic 分区、ISR、ACL 等持久化在 ZK 中）。
KR
KRaft 替代方案
内置 Raft 共识协议，Controller 节点（通常 3 个）自行选举；元数据写入内部 @metadata Topic，其他 Broker 通过 Fetch 同步。无需外部 ZooKeeper。
优
KRaft 优势
去掉外部依赖，降低运维复杂度；元数据变更少一跳网络，延迟更低；支持 100 万+ Partition，扩展性更强。Kafka 4.0 已完全移除 ZooKeeper。
