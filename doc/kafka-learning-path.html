Stage 1 · 核心概念 & 架构（第 1 周）
Kafka 整体架构 — Producer / Broker Cluster / Consumer Group / Controller
WEEK 1 核心概念 & 架构基础 入门必须掌握
1
Topic · Partition · Replica · Broker
Broker（服务器节点）：Kafka 集群中的一台服务器就是一个 Broker，负责接收 Producer 发来的消息、存储到磁盘、响应 Consumer 的拉取请求。
Topic（主题）：消息的逻辑分类，类似数据库中的一张表或一个队列名。Topic 本身不存数据，真正存数据的是它下面的 Partition。
Partition（分区）：每个 Topic 被物理拆分成一个或多个 Partition，分布到不同的 Broker 上。
   ① 不同 Partition 在不同 Broker 上 → 水平扩展
   ② 多个 Consumer 可同时消费不同 Partition → 并行消费
   每个 Partition 是只追加（Append-Only）的日志文件，每条消息有唯一编号 Offset（从 0 递增）。Partition 内部有序，Partition 之间无序。
   比喻：Topic 是一本书，Partition 是拆出的多卷，每卷分别放在不同书架（Broker）上，读者可以同时取不同卷来读。
Replica（副本）：每个 Partition 的备份，防止单点故障丢数据。有一个 Leader Replica（负责所有读写），其余是 Follower Replica（只从 Leader 同步，不对外服务）。
关键约束：同一 Partition 的 Leader 和 Follower 必须在不同 Broker 上，否则 Broker 宕机会同时失去 Leader 和全部副本。
Topic my-topic (replication.factor=3, partitions=3) Partition 0 → Leader(Broker-0) Follower(Broker-1) Follower(Broker-2) Partition 1 → Leader(Broker-1) Follower(Broker-2) Follower(Broker-0) Partition 2 → Leader(Broker-2) Follower(Broker-0) Follower(Broker-1) // Leader 打散到不同 Broker，负载均衡
2
ISR（In-Sync Replicas）机制
ISR 是与 Leader 保持同步的副本集合。Follower 落后超过 replica.lag.time.max.ms（默认 30s）就被踢出 ISR。Leader 挂掉后只从 ISR 内选举新 Leader，保证不丢已提交数据。

关键公式：min.insync.replicas ≤ ISR 大小 ≤ replication.factor
当 ISR 大小 < min.insync.replicas 时，Broker 拒绝 acks=all 的写请求（抛 NotEnoughReplicasException），牺牲可用性换数据安全。
3
HW · LEO · Leader Epoch
LEO（Log End Offset）：副本日志中下一条消息即将被写入的位置，即当前最后一条消息的 offset + 1。比如副本已存了 offset 0～99 共 100 条消息，LEO 就是 100。
HW（High Watermark，高水位）：ISR 所有副本中最小的 LEO，Consumer 只能读到 HW 之前的消息——确保读到的都是所有副本都已同步的"安全数据"。

Leader Epoch（Kafka 0.11+）：解决 HW 的两个经典 Bug —— 数据丢失（Follower 重启后截断到旧 HW）和数据不一致（两个副本先后宕机导致 divergence）。每次 Leader 切换时 epoch+1，Follower 重启后先向 Leader 查询自己 epoch 对应的结束 offset 再截断，而非依赖 HW。
Broker-0 (Leader): LEO=100, HW=97 epoch=5 Broker-1 (Follower): LEO=98 epoch=5 Broker-2 (Follower): LEO=97 epoch=5 ↑ HW = min(100,98,97) = 97 // Consumer 最多可消费到 offset 96（< HW） // Follower 重启 → OffsetsForLeaderEpoch 请求 → 精确截断
4
Controller 角色 & 选举
Controller 是集群里一个特殊的 Broker，负责三件事：
• Partition Leader 选举：某台 Broker 宕机时，找到受影响的 Partition，从 ISR 里选一个新 Leader
• 分区重分配：Broker 上下线时调整各 Partition 的副本分布
• 元数据管理：维护分区 Leader、ISR 等集群信息，并推送给所有 Broker

ZooKeeper 模式：各 Broker 抢占 ZK 上的 /controller 临时节点，抢到的就是 Controller。KRaft 模式（3.3+ 正式可用）：Broker 内置 Raft 协议自己选出 Controller，去掉了外部 ZooKeeper 依赖，故障切换从秒级降至毫秒级，新集群推荐使用。
5
消息存储：分段日志 + 稀疏索引
每个 Partition 在磁盘上是一组 Segment 文件（.log + .index + .timeindex）。文件名是该 Segment 起始 offset。.index 是稀疏索引（每隔 index.interval.bytes 默认 4KB 记录一条映射），查消息流程：
① 二分查找定位 Segment 文件 → ② 在 .index 中二分找到最近的索引条目 → ③ 从该位置顺序扫 .log 定位精确 offset。
data/my-topic-0/ 00000000000000000000.log ← 消息体（Record Batch 格式） 00000000000000000000.index ← offset → 物理位置 稀疏索引 00000000000000000000.timeindex ← 时间戳 → offset 索引 00000000000000174580.log ← 新 Segment（满 1GB 或 7 天滚动） 00000000000000174580.index leader-epoch-checkpoint ← Leader Epoch → Start Offset 映射
6
高性能原理：零拷贝 + 顺序写 + Page Cache + 批量压缩
Kafka 能达到百万级 TPS 的四大支柱：
传统 IO vs Kafka 零拷贝 — 数据搬运路径对比
SEQUENTIAL WRITE
顺序写磁盘
Append-only log，磁盘顺序写速度 600MB/s+，接近内存随机写
  • 消息只追加到 Segment 末尾，永不修改已写入数据
  • 磁头无需寻道，充分利用磁盘预读（read-ahead）和操作系统的写后合并（write-behind）
  • 与 SSD 随机写相比：HDD 顺序写 200MB/s vs SSD 随机写 50-100MB/s
  • Kafka 不依赖 SSD，HDD 即可达到高吞吐，成本大幅降低
PAGE CACHE
利用操作系统缓存
Kafka 不自己管缓存，全交给 OS Page Cache 管理
  • 写消息：写入 Page Cache 即返回，OS 异步刷盘
  • 读消息：如果还在 Page Cache 中（热数据），无磁盘 IO
  • Broker JVM 堆不需要很大（6-8G 足够），剩余内存全给 Page Cache
  • Broker 重启后 Page Cache 仍在（进程级 vs OS 级），热数据不丢失
ZERO COPY
零拷贝传输
sendfile() 跳过用户空间，4次拷贝 → 2次
  • 传统路径：磁盘 → 内核缓冲 → 用户空间 → Socket 缓冲 → NIC（4次拷贝 + 4次上下文切换）
  • sendfile()：磁盘 → Page Cache → NIC（2次 DMA拷贝，0次 CPU拷贝）
  • Java 层通过 FileChannel.transferTo() 调用
  • Consumer 读取热数据时几乎纯内存操作，延迟极低
BATCHING
批量 + 压缩
减少网络往返，压缩后传输数据量降低 60-80%
  • Producer: batch.size + linger.ms 凑批发送，单次 RPC 携带数千条消息
  • 压缩在 Producer 端做，Broker 原样存储（不解压），Consumer 解压
  • Snappy 适合低延迟，LZ4 适合高吞吐，Zstd 压缩比最高
  • 端到端压缩：一批消息只压缩一次，网络 + 磁盘双重受益
ELECTION 集群选举 — Controller 选举 & Partition Leader 选举 高频面试
①
Controller 是什么，做什么
Controller 是集群里一个负责"调度决策"的 Broker，它不直接存消息，专门负责三件事：

① Broker 上下线感知 — 监听所有 Broker 的存活状态，某台挂了立刻感知
② Partition Leader 选举 — 宕机的 Broker 上的所有 Leader 分区，由 Controller 统一触发重新选主
③ 元数据管理 — 维护并广播分区副本分配、Leader 信息等集群元数据

面试开场白：被问到"Controller 的作用"时，用这三点回答就能打 80 分，再说清楚选举机制就 100 分了。
②
ZooKeeper 模式 — Controller 选举流程（逐步理解，不要死背）
ZK 模式下，所有 Broker 都知道谁是 Controller，因为它们都盯着同一个 ZooKeeper 节点：
ZooKeeper 中存在一个临时节点：/controller 内容：{"version":1, "brokerid":2, "timestamp":"..."} // 这个节点由当前 Controller（假设是 Broker-2）创建 // 临时节点的特性：创建者的 Session 断开，节点自动删除
① 正常状态：/controller 节点存在，所有 Broker 注册了对该节点的 Watcher 监听（ZK 的事件通知机制）。

② Controller（Broker-2）宕机：与 ZK 的 TCP 连接断开 → ZK 等待 zookeeper.session.timeout.ms（默认 18s）确认超时 → 自动删除 /controller 临时节点。

③ 所有 Broker 收到 Watcher 通知：/controller 节点消失了！Broker-0、Broker-1 同时知道 Controller 没了。

④ 抢占注册（先到先得）：所有存活 Broker 同时尝试 create /controller。由于 ZK 的原子性保证，只有一个能成功，其他的拿到 NodeExistsException，乖乖退出再注册 Watcher 等下次机会。

⑤ 新 Controller 接管：胜出者（假设 Broker-0）写入 /controller 节点，Controller Epoch 自增。然后从 ZK 中读取全量集群元数据，开始触发所有受影响 Partition 的 Leader 重新选举。

耗时：ZK session 超时（最长 18s）+ 选举时间 ≈ 秒级，期间 Controller 职能暂停，所有 Partition Leader 选举被积压。
③
KRaft 模式 — 为什么更好（和 ZK 模式的本质区别）
KRaft 是 Kafka 3.3 GA 的新模式，去掉了 ZooKeeper 依赖，Controller 选举改用 Raft 共识协议：
KRaft 架构：部署若干专用 Controller 节点（通常 3 或 5 个），组成 Raft Quorum 当前 Controller = Raft Leader 其余 Controller 节点 = Raft Follower，实时同步集群元数据 // 当 Controller 宕机时： // 1. 其他 Controller 节点检测到心跳超时（毫秒级，不需要等 ZK session 超时） // 2. 自增 term（类比 ZK 的 epoch），向其他节点发 RequestVote 请求 // 3. 先拿到多数票（n/2 + 1）的节点成为新 Controller // 4. 元数据持久化到 __cluster_metadata 内部 Topic（Raft Log） // Failover 时间：毫秒级
和 ZK 模式的关键差异：
• Failover 速度：秒级 → 毫秒级（心跳超时远小于 ZK session 超时）
• 架构复杂度：去掉 ZK，少维护一套中间件
• Partition 上限：ZK 模式约 20 万 Partition；KRaft 可支持 百万级（元数据不走 ZK 了）
• 元数据存储：ZK 存在外部 ZooKeeper → KRaft 存在 Kafka 自身的 __cluster_metadata Topic（Raft Log 形式）
对比项ZooKeeper 模式KRaft 模式（3.3+ GA）
选举机制 抢占 ZK 临时节点 /controller（先到先得） Raft 共识，多数派投票（n/2+1）
Failover 时间 秒级（受 ZK session 超时影响，默认 18s） 毫秒级（心跳超时检测，无 session 等待）
元数据存储 ZooKeeper 的 ZNode 树（外部依赖） Kafka 内置 __cluster_metadata Topic（Raft Log）
支持的 Partition 规模 约 20 万（ZK 性能瓶颈） 百万级（官方验证）
Controller epoch 作用 防脑裂：旧 Controller 的命令携带旧 epoch，Broker 收到后直接拒绝，保证同时只有一个有效 Controller

④
完整流程（5 步）
Broker 宕机后，Controller 触发受影响分区的 Leader 重选，流程如下：

Step 1 · Controller 检测到 Broker-2 下线
ZK 模式：/brokers/ids/2 临时节点消失；KRaft 模式：心跳超时，Raft 标记为不可达。

Step 2 · 找出所有"受害"分区
Controller 遍历元数据，找到 Leader 在 Broker-2 上的所有 Partition（可能有几十上百个）。

Step 3 · 从 ISR 中选新 Leader
对每个分区：取其 ISR 列表，去掉已下线的 Broker-2，从剩余 ISR 中选第一个。顺序按副本列表顺序（AR 列表），优先选 Preferred Replica。非 ISR 副本没有资格（除非开启 unclean election，下面说）。

Step 4 · Leader Epoch + 1，写元数据
每次 Leader 切换 epoch 必须自增，目的是让 Follower 在重启时能按 epoch 精确截断日志（防止老数据污染新 Leader，下面 Leader Epoch 详解）。

Step 5 · 广播 LeaderAndIsrRequest
Controller 把新的 Leader/ISR 信息推送给集群所有 Broker。Broker 更新本地元数据缓存，Producer/Consumer 下次刷新 Metadata 就能路由到新 Leader。
⑤
Unclean Leader Election — 面试常考的两难题
问题场景：某分区的 所有 ISR 副本全挂了，只有落后很多的 out-of-sync 副本还活着，这时怎么办？

这是一个 可用性 vs 数据完整性 的经典权衡，由 unclean.leader.election.enable 控制：
unclean.leader.election.enable=false // 默认值，推荐 // 效果：ISR 全空 → 该 Partition 持续 offline，拒绝所有读写 // 优点：绝对保证已提交数据不丢 // 代价：该分区不可用，生产者收到 NotEnoughReplicasException unclean.leader.election.enable=true // 效果：允许 out-of-sync 副本成为 Leader // 代价：这个副本落后的那部分消息（HW 到 LEO 之间）永久丢失 // 场景：日志类业务，宁丢部分消息也要维持可用性
面试答法：两个选择各自牺牲 CAP 中的不同属性：false 选 CP（一致性+分区容忍），true 选 AP（可用性+分区容忍）。大多数金融/订单业务选 false，日志/埋点业务可以接受 true。
⑥
Leader Epoch — 解决 HW 时代的两个 Bug
这是 Kafka 0.11 引入的机制，面试被追问"数据一致性如何保证"时很加分。先理解为什么需要它：

Bug 1：数据丢失
旧机制：Follower 重启后会把 log 截断到 HW 位置再开始同步。问题是，如果这个 Follower 恰好在截断完之后成为了新 Leader，而旧 Leader 在 HW 之后还写了消息——那些消息就永久消失了。

Bug 2：数据不一致（幽灵消息）
两个副本先后宕机、恢复的时序配合，可能导致两个副本在同一 offset 上存了不同的内容，形成"分叉"。

Leader Epoch 如何修复：每次 Leader 切换 epoch 自增。Follower 重启后不再直接截断到 HW，而是先发 OffsetsForLeaderEpoch(epoch=N) 给新 Leader，新 Leader 返回"epoch N 结束的 offset"，Follower 只截断到这个精确位置，而非盲目按 HW 截断。
Follower 重启后的对话： Follower → Leader: OffsetsForLeaderEpoch(leaderEpoch=5) Leader → Follower: endOffset=100 // epoch 5 的最后一条是 offset 100 Follower: 将 log 截断到 offset 100，然后继续从 101 拉数据 // 结果：精确截断，不会截太多也不会留脏数据 // 无论 Leader 换了多少次，每个 epoch 的边界都有据可查
⑦
选举期间你的代码会发生什么（开发视角）
选举不是抽象的，它直接影响你写的 Producer 和 Consumer：

Producer 侧：向已经失去 Leader 的 Partition 发消息，会收到 NotLeaderOrFollowerException。配置了 retries=Integer.MAX_VALUE + retry.backoff.ms 的 Producer 会自动等待并重试，直到新 Leader 上位。选举完成后发送自动恢复，业务无感知（KRaft 毫秒级恢复，ZK 模式秒级）。

Consumer 侧：Fetch 请求同样会收到 NotLeaderOrFollowerException，Consumer 自动刷新 Metadata 找到新 Leader 并重连，几乎无需任何代码改动。

Metadata 刷新机制：客户端（Producer/Consumer）本地缓存了 Topic 的 Partition → Leader Broker 映射，当请求出错时会触发 Metadata 重新请求（向任意 bootstrap broker），拿到最新 Leader 信息后重发。这就是为什么 retries 要设大的原因。
// 配置 Producer 使其在 Leader 选举期间自动等待恢复 props.put("retries", Integer.MAX_VALUE); // 无限重试 props.put("delivery.timeout.ms","120000"); // 总超时 2min，兜底 props.put("retry.backoff.ms", "200"); // 每次重试间隔 200ms props.put("request.timeout.ms", "30000"); // 单次请求超时 30s
面试连环追问

Q：ZK 模式 Controller 选举为什么是秒级？ → 因为要等 ZK session 超时（默认 18s），这个时间无法绕过，是 ZK 用来确认连接真的断了而不是网络抖动的保护机制。

Q：Controller 和 Partition Leader 的区别是什么？ → Controller 是管理者，负责协调谁当 Leader；Partition Leader 是具体分区的读写入口，实际处理 Producer/Consumer 请求。Controller 选举影响的是"谁来决策"，Partition Leader 选举影响的是"谁来服务流量"。

Q：Partition Leader 选举一定选 ISR 中的第一个吗？ → 默认优先选 Preferred Replica（AR 列表中的第一个副本），但它必须在 ISR 中且存活。如果 Preferred Replica 不在 ISR 或者已宕机，才在剩余 ISR 中按顺序选。

Q：Leader Epoch 和 HW 的区别？ → HW 是数据可见性边界（Consumer 只读 HW 以内），Leader Epoch 是日志截断的基准（Follower 按 epoch 截断，解决 HW 机制的 Bug）。两者解决不同问题，0.11 之前只有 HW，0.11 之后两者并存。

Stage 2 · Java Producer & Consumer 深度解析（第 2-3 周）
Producer 消息发送全链路 — Main Thread → Sender Thread → Broker
PRODUCER 生产者核心机制 重点
1
发送链路 6 个阶段
send() → Interceptor（可选，用于埋点/增强） → Serializer（Key/Value 序列化） → Partitioner（决定目标 Partition） → RecordAccumulator（按 Partition 分桶的内存缓冲区） → Sender 线程（独立线程，按 batch.size/linger.ms 触发发送） → NetworkClient（NIO 非阻塞发送到 Broker Leader）。

Main Thread 和 Sender Thread 之间通过 RecordAccumulator 解耦。send() 是异步的，返回 Future<RecordMetadata>，可以 get() 阻塞等待或注册 Callback。
2
批量发送 & 核心参数
Sender 线程按两个条件触发发送：① batch.size 达到（默认 16KB） ② linger.ms 到期（默认 0ms，即立即发）。生产环境建议调大两者：
props.put("batch.size", "65536"); // 64KB，高吞吐场景调大 props.put("linger.ms", "5"); // 等 5ms 凑批 props.put("compression.type", "lz4"); // LZ4 高吞吐，zstd 高压缩比 props.put("buffer.memory", "67108864"); // 64MB 发送缓冲区 props.put("max.in.flight.requests.per.connection", "5"); // 管道化，允许5个未确认请求
注意：max.in.flight.requests.per.connection > 1 时，如果前一批重试、后一批先成功，会导致消息乱序。开启幂等（enable.idempotence=true）后 Kafka 会用 Sequence Number 保证单 Partition 内顺序，此时允许设为 5（上限）。
3
Partitioner 策略
有 Key：默认 murmur2(key) % partitionCount，相同 key 始终路由到同一 Partition，保证单 key 顺序。
无 Key：Kafka 2.4+ 改为 Sticky Partitioner（黏性策略），一个 batch 凑满或 linger.ms 到期才换分区，比 RoundRobin 更利于凑大批量。
自定义：实现 Partitioner 接口，常见场景是按租户/地区路由，或解决数据倾斜（热点 Key 打散到多个分区再在消费端聚合）。
4
acks · 重试 · 幂等发送
acks=all + retries=Integer.MAX_VALUE + enable.idempotence=true 是生产三件套。幂等发送原理：每个 Producer 启动时获得唯一 PID，每条消息携带 Sequence Number（Partition 级别递增），Broker 检测到 Seq 重复则丢弃并返回成功，保证单 Partition 精确一次。
// 幂等保证范围：单 Producer 实例 + 单 Partition + 单 Session // Producer 重启 PID 变化 → 需要事务 API 扩展保证 Producer PID=1001 send(topic-0, seq=0, msg_A) → Broker 写入 ✓ send(topic-0, seq=1, msg_B) → 网络超时，重试 send(topic-0, seq=1, msg_B) → Broker 检测 seq=1 已存在，丢弃，返回成功
5
事务 API（跨 Partition 原子写）
通过 transactional.id 实现跨 Partition 原子写入。底层引入 Transaction Coordinator（Broker 上运行）和 __transaction_state Topic（存事务状态）。流程：initTransactions → beginTransaction → send × N → sendOffsetsToTransaction → commitTransaction。

配合 Consumer isolation.level=read_committed 实现端到端 Exactly-Once：Consumer 只能看到已 commit 的事务消息。

Consumer Group Rebalance 流程 — Group Coordinator 协调分区分配
CONSUMER 消费者核心机制 重点
1
Consumer Group & Group Coordinator
同一 Group 内，每个 Partition 只分配给一个 Consumer（消费者数 > 分区数 → 多余 Consumer 空闲）。

Group Coordinator 是特定 Broker 上的组件，负责管理 Consumer Group 的生命周期。每个 Group 通过 hash(group.id) % __consumer_offsets分区数 确定 Coordinator 所在的 Broker。Coordinator 管理成员注册、心跳检测、触发 Rebalance、存储 offset（到 __consumer_offsets Topic）。
2
Rebalance 流程 & 5 步协议
① 所有 Consumer 向 Coordinator 发 JoinGroup
② Coordinator 选出 Leader Consumer（通常是第一个 Join 的）
③ Leader Consumer 拿到所有成员的订阅信息，执行分配策略
④ Leader 把分配方案通过 SyncGroup 发给 Coordinator
⑤ Coordinator 把方案广播给所有 Consumer

Rebalance 期间 全组暂停消费（Eager 协议的 Stop-The-World）。Kafka 2.4+ 推荐 CooperativeStickyAssignor：增量 Rebalance，只迁移受影响的分区，不全组暂停。
3
分区分配策略对比
策略原理优缺点推荐场景
RangeAssignor 按 Topic 维度，Partition 范围等分给 Consumer 实现简单；多 Topic 时 容易不均匀（余数总分给前面的 Consumer） 默认策略，单 Topic 可用
RoundRobin 所有 Topic 的 Partition 放一起轮询分配 更均匀；但 Rebalance 时所有分区重分配，迁移量大 多 Topic 且对均匀性要求高
StickyAssignor 尽量保留上次分配，只迁移必要的分区 均匀 + 最小迁移；但仍是 Eager 协议（全组暂停） 生产推荐（如不支持 Cooperative）
CooperativeSticky 两轮 Rebalance：先撤回待迁移分区，再分配到新 Consumer 增量 Rebalance，不全组暂停；Kafka 2.4+ 推荐 生产首选
OFFSET Offset 提交 & 消费语义
1
Offset 存储机制
Consumer 消费进度（offset）存储在 __consumer_offsets 内部 Topic（默认 50 个 Partition），key 是 group.id + topic + partition，value 是 offset + metadata。这是一个 Log Compaction Topic，只保留每个 key 的最新值，不会无限膨胀。
2
三种提交方式 & 语义
自动提交（enable.auto.commit=true）：每隔 auto.commit.interval.ms（默认 5s）自动提交。简单但语义不精确 —— 处理失败也会提交，或处理完但还没到提交时间就宕机导致重复消费。
手动同步：commitSync() 阻塞直到提交成功。最安全，保证 at-least-once。
手动异步：commitAsync(callback) 不阻塞，配合回调处理失败。吞吐更高但回调顺序可能乱。

最佳实践：正常循环用 commitAsync()（高吞吐），关闭前最后一次用 commitSync()（保证提交成功）。
try { while (running) { ConsumerRecords<?,?> records = consumer.poll(Duration.ofMillis(100)); process(records); // 先处理 consumer.commitAsync(); // 异步提交，高吞吐 } } finally { consumer.commitSync(); // 关闭前同步提交，保证不丢进度 consumer.close(); }
3
消费速度调优 & 避免 Rebalance
① 增加 Partition 数 + Consumer 数（横向扩展）
② 加大 max.poll.records（默认 500）批量处理
③ 耗时操作放线程池异步处理，主循环只负责 poll + 提交
④ max.poll.interval.ms（默认 5min）内必须完成处理并再次 poll，否则触发 Rebalance
⑤ 设置 group.instance.id（静态成员），Consumer 重启不触发 Rebalance（在 session.timeout.ms 内）
常见坑

Consumer 线程内做耗时操作（如调外部 API）很容易超过 max.poll.interval.ms 导致反复 Rebalance，表现为消费停滞、日志大量 Rebalancing。解法：① 消息扔线程池异步处理 ② 适当调大 max.poll.interval.ms ③ 减小 max.poll.records 降低单次处理量。

Fetch 长轮询机制 — fetch.min.bytes + fetch.max.wait.ms 的权衡
ADVANCED Consumer 高级控制 — Fetch · Seek · Offset Reset
1
Fetch 长轮询机制（Long Poll）
Consumer 的 poll() 底层是 FetchRequest。Broker 不是立即返回，而是按以下规则：
• 若已有数据 ≥ fetch.min.bytes（默认 1B）→ 立即返回
• 否则挂起请求，直到数据够了 or fetch.max.wait.ms（默认 500ms）超时
• 配合 max.partition.fetch.bytes（默认 1MB）控制单分区单次最大拉取量

调优思路：高吞吐场景调大 min.bytes 凑批降低 RPC 次数；低延迟场景调小 max.wait.ms 减少等待。
2
subscribe() vs assign() — 两种消费模式
subscribe()：声明式订阅 Topic，由 Coordinator 自动分配分区，支持 Rebalance，适合标准消费组场景。
assign()：手动指定具体分区，跳过 Consumer Group 机制，不参与 Rebalance，不提交到 __consumer_offsets。适合数据回放、单分区独占消费、自定义负载均衡场景。

两者互斥，同一 Consumer 实例只能用其一。
// subscribe 模式（常规） consumer.subscribe(List.of("orders")); // assign 模式（手动控制） TopicPartition p0 = new TopicPartition("orders", 0); TopicPartition p1 = new TopicPartition("orders", 1); consumer.assign(List.of(p0, p1)); // 只消费 P0 P1
3

三种 seek 方式实现"时间旅行"：
// 1. 按 offset 跳转 consumer.seek(new TopicPartition("orders", 0), 12345L); // 2. 跳到分区开头/末尾 consumer.seekToBeginning(List.of(partition)); consumer.seekToEnd(List.of(partition)); // 3. 按时间戳查找 offset（最常用 — 回放某天的数据） Map<TopicPartition, Long> query = Map.of(partition, LocalDate.of(2026,5,1).atStartOfDay() .toInstant(ZoneOffset.UTC).toEpochMilli()); Map<TopicPartition, OffsetAndTimestamp> result = consumer.offsetsForTimes(query); consumer.seek(partition, result.get(partition).offset());

Consumer 内部线程模型（Kafka 0.10+ 重要变化）
Kafka 0.10 之前，心跳是在 poll() 调用内部发送的 —— 如果消息处理耗时过长，心跳就停了，Coordinator 会误判 Consumer 死亡并触发 Rebalance。

Kafka 0.10 之后引入独立的 Heartbeat 线程（后台守护线程），与 poll() 线程完全解耦：
• Heartbeat Thread：每隔 heartbeat.interval.ms（默认 3s）向 Coordinator 发心跳，维持 Consumer 存活状态
• Poll Thread（主线程）：执行 poll() → 处理消息 → commitAsync()

两个超时参数容易混淆：
• session.timeout.ms（默认 45s）：Heartbeat Thread 多久没发心跳 → Coordinator 认为 Consumer 死亡 → 触发 Rebalance
• max.poll.interval.ms（默认 5min）：Poll Thread 两次 poll() 之间的最大间隔 → 超时 → Consumer 主动离组（即使心跳正常也触发 Rebalance）

实际意义：即使消息处理很慢（超过 session.timeout），只要 Heartbeat Thread 还在跳，Coordinator 就不会剔除你；但如果 poll() 间隔超过 max.poll.interval.ms（通常是业务处理太慢），Consumer 会被剔除。
策略含义典型场景风险
latest 默认 从分区最新位置开始消费 实时消费，不关心历史数据 新增 Consumer Group 会丢失启动前的所有消息
earliest 从分区最早位置开始消费 全量数据消费，离线数仓导入 误删 Consumer Group 后重启会重新消费全部历史
none 找不到 offset 直接抛异常 严格控制场景，要求外部管理 offset 需要应用代码捕获 NoOffsetForPartitionException
消费失败处理 — 重试 Topic + 死信队列 (DLQ) 分级隔离
DLQ 消费失败处理 — 重试 Topic + 死信队列 生产必备
1
为什么不能简单"重试或丢弃"
原生 Kafka 没有重试 / 死信队列（不像 RocketMQ/RabbitMQ）。如果不设计好失败处理，会陷入两难：
• 不重试直接 commit：消息丢失（业务异常被吞）
• 原地无限重试：毒丸消息（poison pill）阻塞整个 Partition，后面消息全卡住
• 抛异常不 commit：Rebalance 后另一个 Consumer 接手还是同样异常，最终消费停滞
2
分级重试 + DLQ 标准方案
业界主流：主 Topic → 延迟重试 Topic（多个等级）→ 死信 Topic。
• 消费失败 → 写入 orders-retry-5m（带未来时间戳）
• 专门的 Retry Consumer 拉取后 sleep 到时间再处理（或用 ScheduledExecutor 延迟）
• 重试 N 次仍失败 → 升级到 orders-retry-30m
• 最终失败 → 写入 orders-DLQ，告警通知人工介入

关键：主 Topic 始终向前 commit，不被失败消息阻塞，保证消费速度。
3
DLQ 消息必须携带的元信息（Header）
DLQ 消息要能被排查根因，写入时在 Header 加上：
ProducerRecord<String, String> dlqRecord = new ProducerRecord<>( "orders-DLQ", record.key(), record.value()); dlqRecord.headers() .add("x-original-topic", record.topic().getBytes()) .add("x-original-partition", String.valueOf(record.partition()).getBytes()) .add("x-original-offset", String.valueOf(record.offset()).getBytes()) .add("x-exception-class", e.getClass().getName().getBytes()) .add("x-exception-message", e.getMessage().getBytes()) .add("x-stack-trace", getStackTrace(e).getBytes()) .add("x-retry-count", String.valueOf(retryCount).getBytes()) .add("x-failed-at", Instant.now().toString().getBytes()); dlqProducer.send(dlqRecord); consumer.commitSync(); // 主 Topic offset 向前推进
4
Spring Kafka 的 DefaultErrorHandler
Spring Kafka 2.7+ 内置 DefaultErrorHandler + DeadLetterPublishingRecoverer，几行代码搞定分级重试：
@Bean DefaultErrorHandler errorHandler(KafkaTemplate<?, ?> template) { var recoverer = new DeadLetterPublishingRecoverer(template, (record, ex) -> new TopicPartition(record.topic() + "-DLQ", -1)); var backOff = new ExponentialBackOff(1000L, 2.0); // 1s → 2s → 4s → 8s ... backOff.setMaxElapsedTime(60000L); // 最多重试 60s var handler = new DefaultErrorHandler(recoverer, backOff); handler.addNotRetryableExceptions(IllegalArgumentException.class); // 直接进 DLQ 不重试 return handler; }

Exactly-Once Semantics（EOS）三层递进模型
ADVANCED Exactly-Once · Schema Registry · Log Compaction
1
Exactly-Once 三层模型
Layer 1 幂等 Producer：单 Partition 去重，PID + Sequence Number，范围最窄但零配置（Kafka 3.0 默认开启）。
Layer 2 事务消息：跨 Partition 原子写，需要 transactional.id，底层是 Transaction Coordinator + __transaction_state Topic 实现的 2PC。Consumer 需设置 isolation.level=read_committed。
Layer 3 Streams EOS：read-process-write 三步原子化 —— Consumer 读取 + 处理 + Producer 写出 + offset 提交打包成一个事务，实现端到端 Exactly-Once。
processing.guarantee = "exactly_once_v2" // Kafka Streams 2.5+，推荐 // v2 改进：一个 Producer 管全部 Task，减少 Coordinator 压力 // v1（exactly_once）：每个 Task 一个 Producer，资源开销大
2
Schema Registry（Confluent）
集中管理 Avro / Protobuf / JSON Schema，解决 Producer/Consumer Schema 不兼容导致的反序列化失败。
• Producer 注册 Schema → 拿到 schema-id → 消息头只放 id（5字节 magic+id）
• Consumer 按 id 从 Registry 拉 Schema 反序列化，本地缓存避免重复拉取
• 兼容性策略：BACKWARD（新 Schema 可读旧数据）/ FORWARD（旧 Schema 可读新数据）/ FULL（双向兼容）/ NONE（不检查）

面试要点：Schema Registry 是 独立服务（非 Broker 组件），Schema 存储在 _schemas Topic 中。
3
Log Compaction（日志压缩）& 关键参数
针对 相同 key 只保留最新 value 的场景（数据库变更日志、配置中心、KTable 底层、__consumer_offsets）。设置 cleanup.policy=compact，Cleaner 线程后台合并 Segment。
# Topic 级别关键参数 cleanup.policy=compact # 也可设 compact,delete 双策略 min.cleanable.dirty.ratio=0.5 # 脏数据比例 ≥ 50% 才触发压缩 min.compaction.lag.ms=0 # 消息至少存活多久才能被压缩（默认 0） max.compaction.lag.ms=Long.MAX # 消息最多多久必须被压缩（GDPR 合规场景调小） segment.ms=604800000 # 7 天滚动 Segment（active segment 不参与压缩） delete.retention.ms=86400000 # tombstone 标记保留 1 天（防消费者错过删除）
关键概念：
• Active Segment 不压缩：只压缩已 roll 的旧 Segment，所以高频写入但 segment.ms 太大会导致压缩滞后
• Tombstone：发送 value=null 标记删除该 key，Cleaner 处理后从日志中真正移除
• 状态恢复场景：Consumer 从头消费 compact Topic 就能拿到所有 key 的最终状态快照
4
消息格式：Record Batch（V2）
Kafka 0.11+ 使用 V2 消息格式（RecordBatch），一个 Batch 包含多条 Record，Header 中包含：
• baseOffset：Batch 中第一条消息的 offset
• PID + epoch + baseSequence：幂等和事务的基础
• 压缩：整个 Batch 压缩，而非单条消息，压缩比更高
• 每条 Record 支持 Header（key-value 元数据），可用于链路追踪 traceId 传递

时间语义 — Event Time / Processing Time / Ingestion Time
流处理三种时间，决定窗口归属：
• Event Time：业务事件发生时间（订单下单时间），最准确，但有乱序问题
• Ingestion Time：消息进入 Kafka 的时间（Broker 打的时间戳）

Streams 内置状态由 RocksDB（本地嵌入式 K/V 库）+ Changelog Topic（自动创建的 compact Topic）保证：
• 每次更新状态 → 写 RocksDB（本地） + 写 Changelog Topic（持久化）
• 实例宕机重启 → 从 Changelog Topic replay 重建 RocksDB
• 实例迁移到其他节点 → 同样从 Changelog 重建（Standby Replica 可加速恢复）

Broker 网络线程模型 — Reactor 多线程 + 请求队列 + IO 线程池
TUNING Broker & OS 关键配置调优
1
Broker 线程模型 & 请求处理流程
Kafka Broker 使用 Reactor 多线程模型：
• Acceptor（1个）：接受 TCP 连接，轮询分配给 Network Thread
• Network Threads（num.network.threads 默认 3）：NIO 读写请求/响应，解析协议
• Request Queue：共享阻塞队列，Network Thread 放入，IO Thread 取出
• IO Threads（num.io.threads 默认 8）：执行实际业务逻辑（写日志、更新索引、验证 CRC）
• Purgatory（延迟操作炼狱）：acks=all 时请求在此等待副本同步完成

调优关键：看 RequestHandlerAvgIdlePercent（IO Thread 空闲率）和 NetworkProcessorAvgIdlePercent（Network Thread 空闲率），低于 30% 就要扩线程。
2
OS & JVM 关键认知（开发视角）
Kafka Broker 对 OS 和 JVM 配置非常敏感，作为开发者需要理解这些原理，以便在问题排查和调参时有正确的判断：
• 禁 Swap（vm.swappiness=1）：一旦 Kafka 进程内存被换出到磁盘，Page Cache 失效，GC 时间暴增，直接触发 Heartbeat 超时和 Rebalance
• 脏页刷盘策略：适当放宽（dirty_ratio=60）让 OS 多缓冲写，但太大在服务器宕机时丢的数据更多；acks=all 保证的是"写入副本 ISR"，而非"落盘"，OS 崩溃时 Page Cache 中的数据会丢失（生产必须 2+ 副本）
• 文件系统：XFS 优于 ext4（删 Segment 文件时不阻塞写，Kafka 大量频繁滚动日志时差距明显）
• JVM 堆不要太大：Broker JVM 堆建议 6-8G，64G 内存服务器剩余 ~56G 全给 OS Page Cache。GC STW > 10s 会导致 Controller Failover；G1GC 是当前最佳选择
4
Broker & Topic 核心配置
不同业务场景用不同配置，不要全用默认值：

OPS-ADV Preferred Leader Election & 副本流量管理 运维必知
1
Preferred Replica & 失衡问题
每个 Partition 的 Replica 列表中第一个副本就是 Preferred Replica（首选 Leader）。理想状态下 Leader 应该都是 Preferred，分布均匀。

但 Broker 重启后 Leader 会切到其他副本，不会自动切回。多次滚动重启后，Leader 全堆到几个 Broker 上，流量倾斜 —— 这是 90% Kafka 集群运维都遇到过的问题。
2
触发方式 & 策略选择
自动触发（auto.leader.rebalance.enable=true）：每 5min 检查失衡率，超 10% 自动触发。小集群用，大集群建议关闭。
手动触发：通过 kafka-leader-election.sh --election-type preferred 在运维窗口执行，可分批进行。

为什么大集群禁用自动：选举瞬间 Broker 会短暂拒绝部分写请求 → 客户端重试 → 流量抖动。手动触发可以在低峰期分批操作（先选 1/3 观察，无异常再选剩余），可控性更高。
3
副本重分配 & 限流原理（开发需理解）
扩容新 Broker 后，已有分区不会自动迁移 —— 需要通过 kafka-reassign-partitions.sh 或管理界面触发迁移计划。

核心要点（开发必须懂）：
• 数据迁移本质是 Follower 副本复制数据，会消耗 Broker 间网络带宽
• 必须设置 throttle 限流（--throttle <bytes/s>），不限流会瞬间打满千兆网卡，挤占正常 Producer/Consumer 流量导致消息积压
• 迁移期间 ISR 会短暂缩小，如果同时有大量写入且 ISR < min.insync.replicas，会触发写失败
• 建议在低峰期执行，并预留 30%+ 带宽给正常业务流量
MirrorMaker 2 — 跨集群 / 跨 Region 复制架构
MM2 MirrorMaker 2 — 跨集群复制 / 异地容灾
1
使用场景
异地容灾：北京集群挂了，上海集群无缝接管 —— 应用切流到上海集群即可。
就近消费：用户分布在多 Region，每个 Region 部署独立集群但数据同步，降低延迟。
数据汇聚：多个业务集群 → 数据中心集群做统一离线分析。
集群迁移：从老集群 / 老 Kafka 版本平滑迁移到新集群，迁移期间双写双读。
2
MM2 架构 — 三个 Connector
MM2 基于 Kafka Connect，由三个 Connector 协作：
• MirrorSourceConnector：核心，从源集群拉数据 → 目标集群，自动重命名 Topic（加前缀防回环）
• MirrorCheckpointConnector：同步 Consumer Group offset，切流时消费者能从原位置继续
• MirrorHeartbeatConnector：发心跳消息，测量端到端复制延迟

命名规则：默认 {源集群别名}.{原 Topic 名}，比如源集群叫 beijing 的 orders → 目标集群上叫 beijing.orders。这样双向复制不会回环。
3
关键设计决策 & 监控指标
Topic 命名规则：{源集群别名}.{原 Topic}（如 beijing.orders），命名前缀防止双向复制时数据回环 —— 目标集群的 Topic 带有源集群前缀，不会被 MM2 当成源数据再复制回去。

Offset 映射（切流关键）：MirrorCheckpointConnector 会把源集群的 Consumer offset 映射到目标集群等价位置，存到 {源集群}.checkpoints.internal Topic。切流时通过 RemoteClusterUtils.translateOffsets() 获取映射，消费者无需从头消费。

核心监控指标：replication-latency-ms（端到端复制延迟，超 5s 告警）、record-count（复制速率）。MM2 本身是 Connect 集群，也需要监控 Connect Worker 的 connector-task-metric。
Stage 5 · 架构设计 & 最佳实践（第 9-10 周）
Event-Driven Architecture — 以 Kafka 为事件总线的电商订单解耦
ARCHITECTURE 大厂级架构模式 面试加分项
1
Event-Driven Architecture（EDA）
以 Kafka 为事件总线，服务间通过事件异步解耦，而非直接 RPC 调用。
核心原则：事件是不可变的事实记录，发布后不修改，消费方各自处理。
• 每个下游服务用独立 Consumer Group，互不影响
• 新增下游服务零改动（只需新建 Group 订阅）
• 事件可回溯重放（设置 offset 回到任意时间点）
• 天然削峰填谷：高峰期消息堆在 Kafka，下游按自身速度消费
2
CQRS + Event Sourcing
CQRS（命令查询分离）：写操作走命令模型改 DB，读操作走 Kafka Consumer 维护的物化视图（ES / Redis）。读写分离，各自优化。
Event Sourcing：系统状态 = 初始状态 + 事件日志 Replay。Kafka 的 Log Compaction Topic 天然适合做 Event Store。

适用场景：审计追溯（金融交易）、复杂查询优化（多维度搜索用 ES）、时间旅行（回放到任意时刻）。
3
Saga 模式（分布式事务替代方案）
拒绝 2PC（性能差、可用性低），改用 Saga：每步操作发一个事件，下游监听执行，失败时发补偿事件回滚。
• Choreography Saga（编排式）：各服务自行监听事件，去中心化，Kafka 原生支持，适合简单流程
• Orchestration Saga（协调式）：中央协调器控制流程，适合复杂流程，更易追踪和调试

关键难点：补偿操作设计（如何回滚已完成步骤）、幂等保证（补偿/重试不出错）、状态追踪（Saga 执行到哪一步）。
4
CDC 数据管道 & 实时数仓
CDC（Change Data Capture）：用 Debezium 捕获 MySQL binlog 变更 → Kafka Topic → 下游消费。
• MySQL → Kafka → Elasticsearch（全文搜索）
• MySQL → Kafka → ClickHouse/StarRocks（OLAP 分析）
• MySQL → Kafka → Redis（缓存预热/更新）

优势：业务代码零侵入（读 binlog 不改业务），准实时（秒级延迟），数据一致性（binlog 是 DB 的 ground truth）。

SKEW 数据倾斜 — 热点 Key & 分区不均 实战难点
1
现象 & 诊断
"为什么集群整体不忙，但消费就是积压？" —— 大概率是数据倾斜。
• 几个 Partition 的写入 / 消费速率远高于其他（比如 99% 流量打到 1 个分区）
• 对应 Consumer 实例 CPU/网络打满，其他 Consumer 几乎空闲
• 整体 consumer-lag 表面正常，但分 Partition 看就是单点积压

诊断命令：
kafka-consumer-groups.sh --describe --group my-group # 看每个 Partition 的 LAG 列，是否极度不均（如 P3 有 100w，其他 0） kafka-run-class.sh kafka.tools.GetOffsetShell \ --broker-list xxx:9092 --topic orders --time -1 # 看每个 Partition 的当前 offset，速率高的分区 offset 增长快
2
根因 — Key 选择不当
默认 hash(key) % partitionCount 分区，如果 Key 分布严重不均，就会倾斜。常见反例：
• 用 userId 当 Key，但有 1 个超级 VIP 用户（如直播间）操作量是普通用户 1000 倍
• 用 tenant_id 当 Key，但某个大客户的流量是其他客户总和
• 用 商品 ID 当 Key，但秒杀爆款流量占 80%
• 用 状态字段（status=PAID）当 Key，只有几种值导致大量消息挤同一 Partition
3
解决方案 — 加盐打散 + 消费端聚合
核心思路：牺牲单 Key 严格顺序，换分区均匀。
// 方案 A：识别热点 Key 加盐打散 String key = order.getUserId(); if (isHotUser(key)) { int salt = ThreadLocalRandom.current().nextInt(10); // 0-9 随机 key = key + "_" + salt; // 热点 user 散到 10 个分区 } producer.send(new ProducerRecord<>("orders", key, order)); // 方案 B：完全弃用业务 Key，用复合 Key String key = order.getUserId() + "#" + order.getOrderId(); // 牺牲了"同一用户必到同一分区"，但保证均匀 // 方案 C：消费端二次分流（适合 stateful 处理） // 一级 Consumer Group 只做分流：按 hash(userId+salt) 写入下一级 Topic // 下一级 Consumer Group 做实际处理
方案对比：A 适合偶尔热点（如有限的几个 VIP）；B 牺牲同 user 顺序性，业务能接受才用；C 引入中转 Topic，复杂但灵活，适合实时大数据场景。
4
分区数量不均的情况
另一种倾斜：Partition 在 Broker 上分布不均（比如新 Broker 上线后没有分区迁过去）。
• 表现：某 Broker CPU / 网络打满，其他 Broker 闲置
• 解法：用 kafka-reassign-partitions.sh（见 Stage 4）把分区迁过去，带 throttle 限流
• 预防：扩容 Broker 后立即生成迁移计划，不要等问题暴露
Stage 6 · 面试冲刺 & 实战项目
INTERVIEW 大厂高频面试题清单 必背
Q1
Kafka 如何保证消息不丢失？
三端配置缺一不可：Producer（acks=all + retries + 幂等）→ Broker（replication.factor=3 + min.insync.replicas=2 + unclean.leader.election=false）→ Consumer（手动提交 offset，先消费再提交）。→ 详细版本
Q2
消息积压了怎么办？
紧急扩容（新建 10 倍分区临时 Topic + Relay Consumer 转发），同时分析根因（消费太慢 or 发送暴增），处理完再缩回。→ 详细版本
Q3
Kafka 怎么保证消息顺序？
同 Partition 内有序。业务层用 业务 Key hash 到固定 Partition，Consumer 单线程消费。多线程时用 Key hash 路由到固定 Worker Thread。Producer 端注意 max.in.flight.requests.per.connection + 幂等保证重试不乱序。→ 详细版本
Q4
Kafka 为什么快？
四大核心：① 顺序写磁盘（append-only，HDD 顺序写 600MB/s+）→ ② Page Cache（热数据在内存，读写都快）→ ③ 零拷贝（sendfile() 跳过用户空间，省 2 次 CPU copy）→ ④ 批量 + 压缩（端到端压缩，网络 + 磁盘双重受益）。详见上方 Stage 1 分析。
Q5
Rebalance 的触发原因 & 如何避免？
触发：Consumer 上下线 / session.timeout 超时 / max.poll.interval 处理超时 / Topic 分区变化。
避免：① 合理设置超时参数 ② 耗时操作用线程池 ③ CooperativeStickyAssignor（增量 Rebalance） ④ group.instance.id（静态成员，重启不触发 Rebalance）。详见上方 Stage 2 分析。
Q6
ISR 是什么？Leader Epoch 解决什么问题？
ISR = 与 Leader 保持同步的副本集合。HW = ISR 中所有副本最小 LEO，Consumer 只能消费 < HW 的消息。
Leader Epoch 解决两个 HW 截断 Bug：① Follower 重启截断到旧 HW 导致数据丢失 ② 两副本先后宕机导致数据不一致。Epoch+1 后 Follower 向新 Leader 查询精确截断点，不再依赖本地 HW。
Q7
Producer 幂等和事务的区别？
幂等（enable.idempotence=true）：PID + Seq 保证单 Partition + 单 Session 不重复，Producer 重启 PID 变化失效。
事务（transactional.id）：跨 Partition + 跨 Session 原子写，底层通过 Transaction Coordinator + __transaction_state 实现 2PC，Consumer 需 read_committed 配合。
Q8
Kafka Controller 的作用？ZK vs KRaft？
Controller 负责 Partition Leader 选举、分区重分配、metadata 管理。
ZK 模式：依赖 ZooKeeper 选举和存储 metadata，Controller Failover 秒级，Partition 上限约 20 万。
KRaft 模式：Controller 内嵌 Raft 共识，metadata 存 __cluster_metadata Topic，Failover 毫秒级，支持百万 Partition。3.3+ GA，新集群必选 KRaft。
Q9
消费失败怎么处理？毒丸消息怎么避免阻塞？
原生 Kafka 没有重试 / DLQ 机制，需业务层实现分级重试 + 死信队列：消费失败 → 写延迟 Topic（5min / 30min 多级）→ 仍失败 → 写 DLQ + 告警。
关键：主 Topic 始终向前 commit offset，绝不阻塞 Partition。DLQ 消息要在 Header 带上原 topic/offset/异常栈，便于排查。Spring Kafka 用 DefaultErrorHandler + DeadLetterPublishingRecoverer 几行代码搞定。详见上方 Stage 2 实现。
Q10
Broker 重启后流量倾斜怎么办？
Broker 重启时 Leader 切到其他副本，恢复后不会自动切回，多次重启后 Leader 全堆到几个 Broker 上 —— 这是 Preferred Replica 失衡。
解决：① auto.leader.rebalance.enable=true 自动定时检查（小集群） ② 大集群关闭自动，运维窗口手动执行 kafka-leader-election.sh --election-type preferred。
扩容新 Broker 后用 kafka-reassign-partitions.sh 迁移分区，必须带 throttle 限流否则会打爆网卡。
Q11
如何做数据回放 / 时间旅行消费？
两种方式：
• seek() 方式：用 subscribe 订阅后，在 ConsumerRebalanceListener.onPartitionsAssigned 中调 seek(partition, offset) 或 offsetsForTimes() 按时间戳定位
• assign() 方式：手动指定分区，跳过 Consumer Group，独立消费不影响其他 Consumer
典型场景：补数据、Bug 修复后重新处理、订单异常的离线排查。
Q12
异地多活 / 跨集群同步怎么做？
用 MirrorMaker 2（基于 Kafka Connect 实现），三个 Connector：MirrorSourceConnector（同步数据）、MirrorCheckpointConnector（同步 Consumer offset，切流时不丢进度）、MirrorHeartbeatConnector（测量端到端延迟）。
命名规则 {源集群名}.{Topic} 防止双向复制回环。监控核心指标 replication-latency-ms。详见 Stage 4。
