Redis Sentinel · 哨兵选举
面试这样说

Redis 哨兵的选举分两个阶段。第一阶段是判断主库是否真的下线，分主观下线和客观下线。主观下线是单个哨兵自己认为主库挂了，客观下线是超过 quorum 数量的哨兵都认为主库挂了才触发后续流程。之所以要两阶段，是为了防止网络抖动导致误判，毕竟一次切换代价很高。

第二阶段是选 Leader 哨兵。所有哨兵基于 Raft 变体互相投票，每个哨兵每轮只能投一票，先到先得，拿到超过半数票的哨兵成为 Leader。这个 Leader 是一次性的，只负责这一次切换，执行完毕身份自动失效，和 Raft 里持久存在的 Leader 不一样，更像临时指挥官。

选新主库由 Leader 哨兵按三级优先级决定：slave-priority 最小的优先，然后是复制偏移量最大的，最后用 run_id 打平局。确定后发 SLAVEOF NO ONE 给新主，发 SLAVEOF 新主地址 给其他从库，通知客户端切换完成。

PHASE 1
主库下线判定（SDOWN → ODOWN）
两阶段判定，防止误判
1
主观下线 SDOWN
单个哨兵在 down-after-milliseconds（默认 30s）内未收到 PING 响应，单方面标记为 SDOWN。可能是网络抖动，不能作为切换依据。
2
客观下线 ODOWN
向所有哨兵发送 SENTINEL is-master-down-by-addr，收到 ≥ quorum 个认同后升级为 ODOWN，触发 Leader 选举。
PHASE 2
Leader Sentinel 选举 + Failover
Raft 变体，先到先得，一次性 Leader
3
发起投票（epoch +1）
确认 ODOWN 的哨兵将配置纪元 epoch 加 1，向所有哨兵广播投票请求。每个哨兵每个 epoch 只能投一票，先到先得。若无人获得多数票，等待随机时间重新选举。
4
获得 ≥ N/2+1 票成为一次性 Leader
Leader Sentinel 是临时角色，只负责本次 Failover，执行完毕身份自动失效，所有哨兵恢复平等状态。
5
选出新主库（三级优先）
① slave-priority 最小 → ② 复制偏移量最大（数据最新）→ ③ run_id 字典序最小（打平局）
6
执行 Failover
向新主发 SLAVEOF NO ONE，向其他从库发 SLAVEOF 新主地址，通过 Pub/Sub 通知客户端新主地址。
脑裂

网络分区时旧主库可能仍接受写入，恢复后数据丢失。配置 min-replicas-to-write 1 + min-replicas-max-lag 10 可缓解。

Redis Cluster · 主节点选举
面试这样说

Redis Cluster 的故障切换不依赖外部哨兵，完全靠节点自治。故障检测用的是 Gossip 协议，节点间互发心跳，超时未响应先标记 PFAIL，超过半数主节点都认为 PFAIL 了才升级为 FAIL。

故障主节点的从节点发起竞选，向其他主节点拉票。关键点是：复制偏移量越大的从节点，发起投票的等待时间越短，所以它天然先拿到票。这个设计很巧妙，通过时间差自然筛选出数据最新的候选人，不需要集中比较。

获得超过半数主节点投票后，从节点晋升为主节点，接管原主节点负责的哈希槽，广播给整个集群。和 Sentinel 最大的区别是：Cluster 没有独立的协调者，从节点直接向其他主节点拉票，是纯去中心化设计。

PHASE 1
故障检测（Gossip 协议）
PFAIL → FAIL，多数主节点确认
1
PFAIL（可能下线）
节点在 cluster-node-timeout（默认 15s）内未收到 PONG，标记对方为 PFAIL，通过 Gossip 扩散。
2
FAIL（确认下线）
当 ≥ N/2+1 个主节点都报告 PFAIL，任意主节点将其升级为 FAIL 并广播，触发从节点选举。
PHASE 2
从节点竞选主节点
偏移量大者时间差优先，去中心化投票
3
发起时间差异化（天然优先权）
每个从节点发起延迟 = 固定 500ms + 随机量 + 偏移量惩罚。偏移量最大的从节点延迟最小，最先发起，自然先拿到票，无需集中评估。
delay = 500ms + random(0~500ms) + (MAX_OFFSET - my_offset) × 系数 # 偏移量越大 → 延迟越小 → 最先发起 → 先拿票
4
epoch +1，广播 FAILOVER_AUTH_REQUEST
每个主节点每 epoch 只投一票，先到先得。
5
获得 ≥ N/2+1 票晋升
执行 CLUSTER FAILOVER，接管原主节点的所有哈希槽，广播 PONG 通知全集群。
关键区别

Redis Cluster 没有独立协调者，从节点直接向其他主节点拉票，纯去中心化。只要存活主节点不足 N/2+1，选举失败，集群整体不可用。

Kafka Controller · 控制器选举
面试这样说

Kafka 的 Controller 是整个集群的"大脑"，所有分区 Leader 的选举、ISR 的变更、Broker 上下线处理都由它协调。

旧版依赖 ZooKeeper：所有 Broker 启动时都去抢一个 ZooKeeper 临时节点，第一个写入成功的就是 Controller。ZK 保证写入原子性，Controller 宕机后临时节点自动删除，Broker 重新竞争。问题是依赖 ZK 运维复杂，分区数量有上限，元数据一致性也有短暂窗口。

新版 KRaft 去掉了 ZooKeeper，改用内置 Raft 协议。预先配置几个节点组成 Controller Quorum，它们之间跑标准 Raft 选出 Active Controller，元数据变更写入 Raft 日志多数确认后才生效。强一致，支持百万级分区，运维也简单了很多。

Controller 失联后，所有存活 Broker 同时向 ZK 抢写 /controller 临时节点，写入自己的 broker_id 和 controller_epoch。

2

Follower ─(timeout)→ Candidate ─(RequestVote)→ 其他节点 其他节点 ─(多数票)→ Active Controller ─(心跳)→ Follower

所有元数据变更写入 Raft 日志，多数节点确认后才生效，强一致，支持百万级分区。
KRaft 优势

去除 ZooKeeper 后启动速度提升 2-3 倍，分区数量上限从约 20 万提升至百万级，运维大幅简化，元数据一致性更强。

Kafka Partition Leader · 分区领导者选举
面试这样说

Kafka 的 Partition Leader 选举其实不算真正的选举，更准确地说是 Controller 的任命。Controller 不需要让副本之间投票，而是直接从 ISR 列表里按顺序找第一个存活的副本，发一条 LeaderAndIsr 命令指定它为新 Leader，整个过程毫秒级完成。

核心是 ISR（In-Sync Replicas），只有 ISR 里的副本才能成为 Leader，保证新 Leader 数据是最新的，不会丢失已确认的消息。

有一个 Unclean Leader Election（不洁选举）的概念，ISR 为空时可以从非同步副本里选 Leader 保持可用性，但代价是可能丢数据。生产默认关闭，这是 CAP 中 CP 和 AP 的取舍。另外，acks=all 配合 min.insync.replicas=2 是保证消息不丢失的标准组合。

LEADER ELECTION
Partition Leader 任命（Controller 直接指定）
ISR 保障数据安全，毫秒级切换

分区全部副本列表，创建时固定，顺序决定优先副本（Preferred Replica）。

C

长期运行后 Leader 可能漂移，执行 preferred-replica-election 工具将 Leader 迁回 AR[0]，实现负载均衡。

Q&A
Redis Sentinel 面试题
Q1为什么要分主观下线和客观下线两个阶段？

单个哨兵的网络可能异常，只靠自己判断主库是否下线容易误判，误触发 Failover 代价很高（主从切换、数据同步、客户端重连）。客观下线要求超过 quorum 个哨兵都认同，相当于多人表决，可靠性大幅提升。这是典型的多数派思想，用分布式共识防止单点误判。

Q2Sentinel Leader 和新主库是怎么选出来的？有什么区别？

选 Leader Sentinel：哨兵间互相投票，Raft 变体，每个 epoch 只能投一票，先到先得，≥ N/2+1 票成为 Leader。目的是确保只有一个哨兵执行 Failover，避免并发操作冲突。这个 Leader 是一次性的，执行完自动失效。

选新主库：由 Leader Sentinel 单独决定，不投票。按三级优先级：slave-priority 最小 → 复制偏移量最大 → run_id 最小。

Q3为什么建议哨兵节点数量为奇数？

选举需要 ≥ N/2+1 票。3 个节点能容忍 1 个宕机（需 2 票），4 个节点也只能容忍 1 个宕机（需 3 票），两者容错能力一样，但 4 节点多一台机器浪费资源。奇数节点在相同容错能力下更经济。

Q4如何缓解 Sentinel 模式的脑裂问题？

脑裂：网络分区时旧主库仍接受写入，恢复后数据丢失。

min-replicas-to-write 1 # 至少 1 个从库确认才写入 min-replicas-max-lag 10 # 从库延迟超过 10s 则主库拒绝写入

分区期间旧主无从库可用，拒绝写入，缩小丢失窗口。是缓解而非根除。

Q&A
Redis Cluster 面试题
Q1Cluster 选举和 Sentinel 选举最大的区别是什么？

Sentinel：哨兵之间选 Leader 哨兵，再由 Leader 评估从库；有外部监控进程，从库偏移量由 Leader 集中比较。

Cluster：故障主节点的从节点直接向其他主节点拉票，没有独立协调者；通过延迟发起时间实现偏移量大者优先，完全去中心化，更自治。

Q2什么情况下 Redis Cluster 整体不可用？

① 某个主节点下线且没有从节点：该主节点的哈希槽无人接管，集群进入 FAIL 状态；② 存活主节点不足 N/2+1：选举需要多数主节点投票，不足则选举失败，集群整体不可用。这是 Cluster 的可用性边界。

Q3epoch 在 Cluster 中起什么作用？

① 唯一性：每个主节点每 epoch 只投一票，同一轮不可能出现两个候选人都获得多数票；② 防脑裂：旧主恢复后 epoch 过期，其命令被其他节点忽略，防止数据回滚；③ 配置收敛：节点交换配置时 epoch 大的覆盖 epoch 小的，集群最终一致。

Q&A
Kafka Controller 面试题
Q1旧版 ZK 选举 Controller 有什么问题？KRaft 怎么解决？

ZK 模式问题：① 运维复杂，需要单独维护 ZK 集群；② 约 20 万分区后性能下降；③ 大集群启动慢；④ ZK 与 Broker 间存在短暂元数据不一致。

KRaft 解决：元数据存入 Kafka 内部 Raft 日志，Controller 即 Raft Leader，变更多数确认才生效，强一致；去掉 ZK 依赖，启动提速 2-3 倍，支持百万级分区。

Q2Controller 频繁切换（抖动）会有什么影响？

每次选举触发大量分区 Leader 重选和元数据同步：① 服务抖动：分区短暂不可写，Producer 重试；② 性能下降：新 Controller 加载全量元数据，CPU/网络负载高；③ 大集群影响更重：数万分区批量重选可能持续数十秒。常见原因：Controller 所在 Broker GC 过长、zookeeper.session.timeout.ms 设置过小。

Q&A
Kafka Partition Leader 面试题
Q1ISR 是什么？什么情况下副本被踢出 ISR？

ISR 是与 Leader 保持同步的副本集合，Kafka 数据可靠性的核心保障，只有 ISR 内的副本才能成为 Leader。

Follower 在 replica.lag.time.max.ms（默认 30s）内未追上 Leader 最新 offset，自动移出 ISR。追上后重新加入，无需人工干预。

Q2acks=0/1/all 区别？生产环境如何选择？

acks=0：不等确认，吞吐最高，可能丢数据，适合日志等。acks=1（默认）：Leader 写入即确认，Follower 未同步时 Leader 宕机数据丢失。acks=all：ISR 内所有副本确认，最安全。

生产推荐：核心业务用 acks=all + min.insync.replicas=2 + replication.factor=3，在可接受延迟内最大化数据安全。

Q3Unclean Leader Election 是什么？为什么默认关闭？

ISR 为空时从非同步副本（OSR）选 Leader，代价是已确认消息可能丢失，违反持久性保证。这是 CAP 的取舍：关闭 = 优先 CP（一致性），开启 = 优先 AP（可用性）。金融/订单等核心业务保持关闭，日志收集等允许丢失的场景可以开启。

Q&A
综合 & 设计类面试题
Q1这几套机制都用"多数派"原则，为什么？

多数派是防脑裂的数学基础：任意两个多数派集合必然有交集，所以不可能同时产生两个都获得多数认可的 Leader。N 个节点中，多数派 = N/2+1，两个多数派之和 = N+2 > N，必然重叠，重叠节点不可能同时投两票。这是 Raft、Paxos、ZAB 等共识算法的数学基础。

Q2Kafka 和 Redis 选举机制最核心的区别是什么？

Redis：节点间对等投票，无中心协调者，秒级切换，解决主库不可用时的快速切换问题。

Kafka Controller：先选出唯一 Controller 集中管理，KRaft 用标准 Raft，解决元数据一致性和集群管理问题。

Kafka Partition Leader：不是"选举"而是 Controller 的"任命"，毫秒级，代价是需要维护 ISR 候选人名单。

总结：Redis 去中心化投票，Kafka 中心化任命，都用 epoch/term 防脑裂。

Q3Kafka 消息不丢失需要哪些配置？和选举有什么关联？
# Broker 端（与选举直接相关） replication.factor=3 # 3副本，允许1个节点故障 min.insync.replicas=2 # ISR最少2个，防退化为单点 unclean.leader.election=false # 禁止不洁选举，保证一致性 # 生产者端 acks=all # 等ISR全部确认 enable.idempotence=true # 幂等，防重试重复 # 消费者端 enable.auto.commit=false # 手动提交offset

min.insync.replicas 控制 ISR 门槛，影响选举能否找到合法候选人；unclean=false 确保只有 ISR 副本才能成为 Leader，从根本上保证已确认消息不因选举而丢失。
