顺序写与 Page Cache
顺序写
Append-Only
  • 所有消息只追加到文件末尾，从不随机写
  • 磁盘顺序写吞吐约 600 MB/s
  • 磁盘随机写仅约 100 MB/s，差距 6×
  • 顺序写性能接近内存随机读写
Page Cache
OS 级缓存
  • OS 将磁盘文件缓存在物理内存中
  • Kafka 不在 JVM 堆维护消息缓存
  • 读写优先命中 Page Cache，不落磁盘
  • Broker 重启后 Page Cache 依然有效
零拷贝
sendfile
  • Consumer 拉取时调用 sendfile(2)
  • 数据从 Page Cache 直接传到网卡
  • 不经过用户空间，节省 2 次 CPU 拷贝
  • 配合 DMA scatter-gather 效率更高
顺序写 vs 随机写 — 吞吐对比
INFO

Kafka 刻意不在 JVM 堆内缓存消息，而是依赖 OS 的 Page Cache。好处：① 不受 JVM GC 影响，避免 Full GC 导致的停顿；② Broker 重启后 Page Cache 仍然有效，不需要预热；③ 读写共享同一份 Cache，刚写入的消息马上可被 Consumer 从缓存命中，延迟极低。

Log Segment 文件结构
Partition 目录结构示意
/data/kafka-logs/order-topic-0/ 00000000000000000000.log ← Segment 1：offset 0 ~ 1048575 00000000000000000000.index 00000000000000000000.timeindex 00000000000001048576.log ← Segment 2：offset 1048576 ~ 2097151 00000000000001048576.index 00000000000001048576.timeindex 00000000000002097152.log ← Active Segment（当前写入） 00000000000002097152.index 00000000000002097152.timeindex
.log
消息数据文件
顺序追加 RecordBatch，不可修改，文件名即该 Segment 的起始 offset
  • 存储实际消息内容（RecordBatch 格式）
  • 支持压缩：GZIP / Snappy / LZ4 / ZSTD
  • 每个 RecordBatch 有 baseOffset、size、crc 等头部
  • Append-Only，写完即不可变
.index
稀疏 Offset 索引
每隔 index.interval.bytes（默认 4KB）写一条索引项
  • 记录 relativeOffset → position 映射
  • 每条索引 8 字节（4B offset + 4B position）
  • 用 mmap 映射进内存，支持二分查找
  • 文件小，可全量常驻内存
.timeindex
稀疏时间戳索引
支持按时间点定位消息，如消费指定时间之后的消息
  • 记录 timestamp → relativeOffset 映射
  • 每条索引 12 字节（8B timestamp + 4B offset）
  • Consumer 按时间 reset offset 时使用
  • 同样用 mmap 映射，二分查找
ROLL Segment 滚动条件
1
log.segment.bytes（默认 1 GB）
当前 Active Segment 的 .log 文件大小达到上限，立即触发滚动，创建新 Segment。
2
log.roll.hours（默认 168h / 7 天）
Segment 存在时间超过阈值，即使未达到大小上限也触发滚动，防止单个 Segment 持续过长时间。
3
log.roll.ms（精确时间）
毫秒级滚动时间阈值，优先于 log.roll.hours。同时配置时以 ms 为准。
4
管理员手动触发
通过 kafka-log-dirs.sh 或 Admin API 可手动触发 Segment 滚动，常用于维护场景。
稀疏索引查找流程
LOOKUP 根据 Offset 定位消息 — 完整流程
1
定位 Segment
将所有 Segment 文件名（BaseOffset 列表）加载到内存并排序。对列表做二分查找，找到满足 BaseOffset ≤ targetOffset 的最大那个 Segment。时间复杂度 O(log S)，S 为 Segment 数量。
2
在 .index 中二分查找
.index 文件已通过 mmap 映射到进程地址空间，直接当作内存数组访问。在索引数组中二分查找不超过 targetOffset 的最大索引项，得到 (relativeOffset, position) 对，即对应的 .log 文件字节偏移量。
3
在 .log 中顺序扫描
从 Step 2 得到的 position 开始，在 .log 文件中顺序读取 RecordBatch，逐条比较 offset，直到找到等于 targetOffset 的消息。最多扫描约 4KB（一个索引间隔），磁盘顺序读速度极快。
4
返回消息
读取到目标 RecordBatch 后，如有压缩则解压缩，返回对应 Record 给调用方。整体查找近似 O(log N) 复杂度，N 为消息总数。
INFO

稀疏索引的权衡：索引项不是每条消息都写一个，而是每隔 4KB（index.interval.bytes）写一条。好处是索引文件极小，可全量 mmap 进内存做二分查找；代价是最后一步需要顺序扫描最多 4KB 的 .log 数据。但磁盘顺序读速度极快（~600 MB/s），扫描 4KB 的耗时可忽略不计。

零拷贝原理
传统 IO vs 零拷贝 sendfile — 数据路径对比
GOOD

Kafka 的 Consumer 拉取消息时，Broker 调用 FileChannel.transferTo()，底层是 Linux 的 sendfile(2) 系统调用。现代内核还支持 scatter-gather DMA，数据只在内核空间流动，完全不进入用户空间。Producer 写入时仍是写 Page Cache，OS 异步刷盘（由 log.flush.interval.messages 等参数控制，但通常依赖 OS 自动刷盘）。

mmap 在索引文件中的应用
普通文件读取
read() 系统调用
每次访问都需要系统调用 + 一次内核到用户空间的拷贝
  • 调用 read(fd, buf, size) 触发系统调用
  • 数据从 Page Cache 拷贝到用户空间 buffer
  • 程序访问 buffer 中的数据
  • 频繁随机访问时系统调用开销显著
  • 每次访问至少 1 次上下文切换 + 1 次内存拷贝
mmap 内存映射
MappedByteBuffer
文件直接映射到进程虚拟地址空间，访问如同操作内存数组
  • 调用 mmap() 建立文件到内存的映射
  • 程序直接通过指针/数组下标访问文件内容
  • OS 按需将页面加载到 Page Cache（缺页中断）
  • 零拷贝，无需用户空间 buffer
  • 随机访问效率极高，适合频繁二分查找
MMAP Kafka 如何使用 mmap 加速索引访问
1
索引文件 mmap 映射
Broker 启动时，将所有 Segment 的 .index 和 .timeindex 文件通过 Java 的 MappedByteBuffer（底层 mmap）映射到进程虚拟地址空间。文件内容按定长结构体紧密排列：每条 offset 索引 8 字节（4B relativeOffset + 4B position），每条时间戳索引 12 字节（8B timestamp + 4B offset），直接当作结构体数组访问。
2
二分查找（无系统调用）
对 MappedByteBuffer 中的索引数组做二分查找，计算元素下标 i = mid * 8，直接读 MappedByteBuffer 的对应位置。不需要 read() 系统调用，速度接近纯内存数组的二分查找，O(log M) 其中 M 为索引条数。
3
写入索引（OS 后台刷盘）
写新索引条目时，直接修改 MappedByteBuffer 对应位置（buffer.putInt(offset, value)），不需要 write() 系统调用。OS 的虚拟内存子系统会在后台将脏页异步刷回磁盘（也可调用 force() 主动 fsync）。
日志保留策略
策略类型 配置参数 默认值 触发条件 说明
时间保留 log.retention.hours 168h（7天） Segment 最后修改时间超过阈值 以 Segment 为单位删除，不会切分 Segment；Active Segment 不删除
大小保留 log.retention.bytes -1（不限） Partition 总大小超过阈值 从最旧的 Segment 开始删除，直到总大小低于阈值
检查间隔 log.retention.check.interval.ms 300000（5min） LogCleaner 线程定期触发 清理检查的间隔时间，不是实时清理
日志压缩 log.cleanup.policy=compact delete Key 相同时只保留最新 Value 适合 KV 语义数据；可与 delete 组合使用
WARN

保留策略以 Segment 为最小粒度，不会删除 Active Segment（当前正在写入的那个）。如果最后一个 Segment 非常大且持续写入，即使其中的消息早已超过保留时间，也不会被删除，需要等该 Segment 滚动为封存状态后，下次检查才能触发清理。生产环境要注意合理设置 log.segment.bytes 和 log.roll.hours，避免 Active Segment 过大。

Log Compaction
Log Compaction 前后对比
COMPACT Log Compaction 机制详解
1
适用场景
changelog 流（数据库变更同步 CDC）、配置存储（每次更新配置只关心最新值）、用户状态（最新的用户画像/积分）。不适合需要完整消息历史的场景（如订单流水）。
2
Cleaner 线程工作流程
LogCleaner 后台线程选择"污染率"（dirty/total 比率）最高的 Partition 进行 Compaction。读取 dirty 部分（上次 Compact 之后新写入的数据），在内存中建立 key → 最新 offset 的 HashMap，然后重写 log 文件，跳过不是最新版本的消息。
3
Tombstone（墓碑消息）
发送 Value 为 null 的消息即为墓碑消息，表示逻辑删除该 Key。Compaction 时，其他旧版本会被删除，但墓碑消息本身会保留一段时间（delete.retention.ms，默认 24h），让所有 Consumer 都能感知到删除事件，之后才被物理删除。
4
混合策略 compact + delete
设置 log.cleanup.policy=delete,compact 可同时启用两种策略：先 compact（每个 Key 保留最新值），再 delete（删除超时的 Segment）。适合需要"最新快照 + 有限历史"的场景，如保留最近 7 天的状态变更，同时每个 Key 只保留最新状态。
面试速答
Q & A Broker 存储机制高频面试题
Q1
Kafka 为什么这么快？从存储层面回答
① 顺序写：所有消息只追加到文件末尾，磁盘顺序 IO 性能接近内存（~600 MB/s vs 随机写 ~100 MB/s）。② Page Cache：利用 OS 缓存，不走 JVM 堆，不受 GC 影响，且读写共享同一份缓存。③ 零拷贝：Consumer 拉取时 sendfile 系统调用，数据不经用户空间，减少 2 次 CPU 拷贝和 2 次上下文切换。④ 批量处理：消息批量写入（RecordBatch），减少 IO 次数和系统调用开销。
Q2
Kafka 如何根据 Offset 快速定位消息？
三步：① 二分查找 Segment 文件名（O(log S)，S = Segment 数，从 BaseOffset 列表定位目标 Segment）→ ② mmap 稀疏索引二分查找得到 .log 文件的字节偏移 position（O(log M)，M = 索引条数）→ ③ 从 position 顺序扫描 .log 文件（最多扫描 4KB，磁盘顺序读）。总体接近 O(log N)，N 为消息总数。
Q3
Log Segment 什么时候滚动？滚动影响写入吗？
触发条件：大小超过 log.segment.bytes（1GB）或时间超过 log.roll.hours（7天）。滚动时新建一组 .log/.index/.timeindex 文件，原 Segment 封存。滚动操作很轻量（新建文件 + 元数据更新），不会暂停写入，对消费者和生产者影响极小，基本透明。
Q4
零拷贝中，DMA 是什么？为什么还需要它？
DMA（Direct Memory Access）是允许外设直接与内存传输数据的机制，不需要 CPU 参与每个字节的搬运。sendfile 流程中：磁盘 → Page Cache 是 DMA 传输（磁盘控制器直接写内存），Page Cache → 网卡也是 DMA 传输（网卡直接读内存）。CPU 只需设置传输参数，数据移动由 DMA 控制器完成，大幅降低 CPU 占用率，释放 CPU 处理其他任务。
Q5
Log Compaction 和 delete 策略可以同时用吗？有什么效果？
可以，设置 log.cleanup.policy=compact,delete。效果：先 compact（对数据去重，每个 Key 只保留最新值），同时 delete（根据时间/大小删除过期 Segment）。适合需要"最新快照 + 有限历史"的场景：例如保留最近 7 天的用户行为轨迹，同时每个用户只保留最新状态。Tombstone 消息也会在 delete.retention.ms（默认 24h）后被物理清除。
