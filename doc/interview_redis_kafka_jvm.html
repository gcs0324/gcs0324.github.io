底层原理高频
▾
核心答案
数据类型底层编码切换条件
Stringint / embstr / raw长度≤44字节用embstr，否则raw

缓存穿透、缓存击穿、缓存雪崩的区别与解决方案？
缓存设计高频必考核心
▾
三者区分
问题原因解决方案
穿透 查询不存在的数据，每次都打到DB ① 布隆过滤器前置拦截
② 缓存空值（TTL短，防内存膨胀）
击穿 热点Key过期，大量并发同时回源DB ① 互斥锁（SETNX）重建
② 逻辑过期（不设TTL，异步重建）
雪崩 大量Key同时过期 / Redis宕机 ① TTL加随机抖动
② 集群+哨兵保高可用
③ 降级熔断限流
互斥锁方案代码
// 缓存击穿 - 互斥锁方案 public String getData(String key) { String val = redis.get(key); if (val != null) return val; String lockKey = "lock:" + key; if (redis.setnx(lockKey, "1", 30)) { // 获取锁 try { val = db.query(key); // 回源DB redis.set(key, val, ttl); // 写缓存 } finally { redis.del(lockKey); // 释放锁 } } else { Thread.sleep(50); // 等待重试 return getData(key); } return val; }

Redis 分布式锁如何实现？Redisson 的看门狗机制是什么？
分布式锁高频核心
▾
SETNX方案痛点
  • 锁超时但业务未完成 → 锁被其他线程误释放（需在释放时验证UUID）
  • 释放锁时 GET+DEL 非原子 → 必须用 Lua脚本 保证原子性
  • 主从切换时主节点已写锁但未同步从节点 → 发生锁丢失
Redisson 看门狗机制
Redisson 加锁默认 TTL 30秒，同时启动一个后台线程（WatchDog），每 10秒（TTL/3）检查锁是否仍被当前线程持有，若是则自动续期 30秒。业务结束主动 unlock 后 WatchDog 停止。
// Redisson 可重入锁 RLock lock = redisson.getLock("order:lock:" + orderId); try { // 尝试获取锁，等待10s，锁定30s（WatchDog自动续期） boolean ok = lock.tryLock(10, 30, TimeUnit.SECONDS); if (ok) { /* 业务逻辑 */ } } finally { if (lock.isHeldByCurrentThread()) lock.unlock(); }
RedLock 方案：向 N（奇数≥5）个独立 Redis 节点分别加锁，超过半数成功才视为加锁成功，解决单点和主从切换问题。但争议较大（Martin 论文指出时钟漂移问题），生产中视场景选用。

RDB 和 AOF 的区别？如何选择？
持久化
▾
维度RDBAOF
原理fork子进程，全量快照二进制文件追加写命令日志，可 always/everysec/no
数据安全可能丢失最后一次快照后的数据everysec 最多丢1秒数据
文件大小小，压缩二进制大，文本命令；AOF重写可压缩
恢复速度快慢（需回放命令）
适用场景可接受少量数据丢失、恢复快对数据完整性要求高
生产推荐：两者同时开启（Redis 4.0+ 混合持久化），重启时优先用 AOF 恢复，AOF 文件前半段是 RDB 快照，大幅提升恢复速度。

Redis 主从、哨兵、Cluster 集群的区别与选型？
高可用高频
▾
模式特点局限适用
主从复制主写从读，读扩展手动故障转移，主挂服务不可写读多写少简单场景
哨兵模式自动故障转移，客户端透明仍是单主写入，数据量受限于单机高可用要求，数据量不大
Cluster集群数据分片（16384槽位），横向扩展事务/多key操作受限，运维复杂海量数据、高并发写
Cluster 分片原理：对 key 做 CRC16 % 16384 得到槽位号，槽位分配给各节点。跨槽操作需用 Hash Tag（{user:1}:order）保证路由到同一节点。

Redis 的过期策略和内存淘汰策略？
内存管理
▾
过期策略（两者结合）
  • 惰性删除：访问时才检查是否过期，CPU友好，但内存可能积压
  • 定期删除：每隔100ms随机抽取20个带TTL的key检测，若过期比例>25%则继续扫描
内存淘汰策略（maxmemory-policy）
策略说明
noeviction不淘汰，内存满时写操作报错（默认）
allkeys-lru全key中淘汰最近最少使用 ★推荐
volatile-lru仅在设了TTL的key中淘汰LRU
allkeys-lfu全key中淘汰访问频率最低（Redis4.0+）
allkeys-random随机淘汰，不推荐

热Key 问题如何发现和解决？
性能优化高频
▾
发现方式
  • redis-cli --hotkeys：需开启 maxmemory-policy 为 LFU 策略
  • monitor 命令：实时抓取命令，分析高频 key（有性能开销，慎用）
  • 业务侧埋点：在应用层统计 key 访问频次
解决方案
  • 本地缓存（L1）：Caffeine/Guava，减少 Redis 请求；注意一致性问题
  • Key拆分：将热Key复制为 key_0、key_1...key_N，随机读其中一个
  • 读写分离：热Key从从节点读取，分散压力
  • 限流降级：Sentinel 或 Hystrix 对热Key做限流兜底

为什么 Lua 脚本在 Redis 中能保证原子性？
Lua脚本
▾
Redis 是单线程处理命令的（网络IO多线程，命令执行单线程）。Lua 脚本通过 EVAL 命令执行时，整个脚本被当做一条命令原子执行，执行期间不会被其他命令打断。
-- 分布式锁释放的原子Lua脚本 if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end

如何保证 Redis 缓存与数据库数据一致性？
数据一致性核心高频
▾
主流方案对比
方案做法问题
先更新DB后删缓存写DB → 删 Redis★ 推荐，极小概率不一致（并发读写）
先删缓存后更新DB删 Redis → 写DB并发读会重建旧值，不一致窗口长

BigKey 问题有哪些危害？如何处理？
性能优化
▾
  • 危害：单次操作耗时长，阻塞其他命令；序列化/反序列化慢；内存不均导致集群倾斜；DEL大key会导致长时间阻塞
  • 发现：redis-cli --bigkeys 或 SCAN + MEMORY USAGE
  • 删除：Hash/Set/ZSet 用 HSCAN/SSCAN 分批删；String 直接 UNLINK（异步删除，Redis 4.0+）
  • 预防：禁止把大对象存 String，拆分为多个小 Key；List 分页存储

Redis 为什么单线程还这么快？Redis 6.0 多线程改了什么？
线程模型
▾
  • 纯内存操作：所有数据在内存，微秒级读写
  • 单线程无锁竞争：无上下文切换，无死锁风险
  • IO多路复用：epoll 非阻塞监听多个连接，高并发不阻塞
  • 高效数据结构：SDS、跳表、压缩列表等针对场景优化
Redis 6.0 多线程：仅网络 I/O（读取解析请求、写回响应）使用多线程，命令执行依然单线程。解决的是网络带宽瓶颈，不是计算瓶颈。

Kafka 为什么能做到百万级 TPS？核心高性能原理是什么？
高性能原理核心高频
▾
  • 顺序写磁盘：Partition 只追加写，磁盘顺序 IO（600MB/s）远快于随机 IO（100MB/s）
  • 零拷贝（Zero-Copy）：sendfile 系统调用，数据直接从 PageCache 到网卡，跳过用户态，减少2次数据拷贝和2次上下文切换
  • PageCache：消息先写 OS PageCache 再刷盘，异步刷盘提升写吞吐
  • 批量压缩发送：Producer 批量聚合消息后压缩（snappy/lz4/zstd）发送，减少网络 IO
  • 分区并行：多 Partition 并行消费，水平扩展吞吐

如何保证 Kafka 消息不丢失？三个层面分别怎么做？
可靠性高频必考核心
▾
层面配置/做法说明
Producer acks=all（-1）
retries=Integer.MAX_VALUE
enable.idempotence=true		 等待所有ISR副本确认后才视为发送成功；幂等避免重试引起重复
Broker replication.factor≥3
min.insync.replicas=2
unclean.leader.election.enable=false		 至少2个ISR副本确认；禁止非ISR副本当选Leader（否则会丢消息）
Consumer 关闭自动提交Offset
业务处理完再手动提交		 避免消费未完成就提交Offset导致消息"丢失"

Kafka 如何实现幂等消费和事务消息？
幂等 & 事务高频
▾
Producer幂等（exactly-once发送）
开启 enable.idempotence=true，Broker 为每个 Producer 分配 PID，每条消息附带 SequenceNumber。Broker 检测到重复序号直接丢弃，保证单分区精确一次写入。
Kafka 事务消息
  • 设置 transactional.id，Producer 获得全局唯一事务ID
  • Consumer 设置 isolation.level=read_committed，只消费已提交事务的消息
  • 跨 Partition、跨 Topic 的原子写保证：要么全提交，要么全回滚
消费幂等由业务保证：数据库唯一索引 / Redis SETNX 记录消息ID / 状态机幂等检查，三选一。

消费者组（Consumer Group）机制？Rebalance 触发条件和影响？
消费者组高频
▾
  • 同一 Group 内：一个 Partition 只能被一个 Consumer 消费（独占），实现负载均衡
  • 不同 Group：同一消息可以被多个 Group 各消费一次，实现广播/扇出
Rebalance 触发条件
  • Consumer 加入或离开 Group（包括崩溃/超时）
  • Topic 分区数变更
  • 订阅的 Topic 变更
Rebalance 影响：期间所有 Consumer 停止消费（Stop-The-World），大量消费者的 Group 可能几十秒不可用。
优化：① 设置合理的 session.timeout.ms 和 heartbeat.interval.ms；② 使用 StickyAssignor 减少分区迁移；③ Kafka 2.4+ 支持 静态成员（static membership），Consumer 重启不触发 Rebalance。

消息积压了几百万条，如何快速处理？
故障处理高频核心
▾
紧急处理步骤
  • 定位瓶颈：是 Consumer 处理慢？网络瓶颈？还是下游DB/服务拖慢？
  • 扩 Consumer 数量：临时加消费者（不超过 Partition 数），触发 Rebalance 后并行消费
  • 扩 Partition 数：提高并行度上限（注意：Partition 只能增不能减）
  • 消费者端批量处理：增大 max.poll.records，批量写DB代替逐条写
  • 临时跳过非关键消息：业务允许时，将 Offset 直接重置到最新，丢弃历史积压（慎用）
事后预防：设置告警阈值（lag监控），Consumer 处理时间超过 max.poll.interval.ms 会被踢出 Group，需适当调大或优化处理逻辑。

ISR 是什么？Leader 选举规则？
副本机制高频
▾
ISR（In-Sync Replicas） 是与 Leader 保持同步的副本集合。Follower 在 replica.lag.time.max.ms（默认30s）内持续拉取消息则在 ISR 内，否则被踢出。
  • Leader 选举：从 ISR 中按优先级（AR 列表顺序）选第一个存活的副本
  • unclean.leader.election.enable=false：禁止非ISR副本选主（防止数据丢失），推荐生产配置
  • HW（High Watermark）：消费者只能消费 HW 以下的消息（ISR中所有副本都已同步的位置），保证消费一致性

如何保证 Kafka 消息的顺序消费？
顺序消费
▾
  • 全局顺序：Topic 只设 1 个 Partition，1 个 Consumer，吞吐极低，不推荐
  • 分区内顺序（推荐）：同一业务 Key（如 userId、orderId）发到同一 Partition（指定相同 Key，Kafka 对 Key 取 hash 路由），Consumer 单线程消费该分区
  • Consumer 端：每个 Partition 对应一个内存队列，单线程按序处理，多 Partition 并行但各自有序

Kafka Controller 是什么？选主机制是什么？
集群管理高频
▾
Controller 是 Kafka 集群中一个特殊的 Broker，负责管理 Partition Leader 选举、ISR 变更、Broker 上下线通知等集群元数据协调工作。
  • Kafka 2.8 之前：所有 Broker 抢占 ZooKeeper 的 /controller 临时节点，抢到的成为 Controller；Controller 宕机后节点消失，其余 Broker 重新抢占
  • Kafka 3.3+ KRaft 模式：移除 ZooKeeper 依赖，元数据存储在 Kafka 自身的 Raft 日志中（__cluster_metadata Topic），通过 Raft 共识选主，延迟更低，运维更简单

JVM 内存区域划分？Java 8 元空间和永久代的区别？
内存模型
▾
区域线程内容OOM
程序计数器私有当前字节码行号，唯一不会OOM的区域❌
虚拟机栈私有栈帧（局部变量/操作数栈/返回地址）StackOverflow / OOM
本地方法栈私有Native方法OOM
堆共享对象实例、数组；GC主战场✅ 最常见
方法区/元空间共享类信息、常量池、静态变量✅
永久代 vs 元空间：永久代在 JVM 堆内，大小固定，易 OOM；元空间（Java 8+）使用本地内存（Native Memory），默认无上限，降低 OOM 概率。但无限增长也会耗尽物理内存，需用 -XX:MaxMetaspaceSize 设上限。
02
GC 算法有哪些？分代收集是如何工作的？
GC算法高频
▾
基础算法
  • 标记-清除：标记可达对象，清除不可达。产生内存碎片
  • 标记-复制：存活对象复制到另一半，清空原区域。无碎片但浪费一半内存（新生代用）
  • 标记-整理：存活对象移向一端，清理边界外。无碎片，适合老年代
分代收集
区域算法触发GC
Eden + S0 + S1（新生代）复制算法（Eden:S0:S1 = 8:1:1）Minor GC（频繁、快速）
Old Gen（老年代）标记-整理Major GC / Full GC（慢）
元空间—类卸载时
对象晋升老年代条件：① 年龄≥15（可配置）；② 动态年龄判断（Survivor中相同年龄对象超过空间一半）；③ 大对象直接进老年代（-XX:PretenureSizeThreshold）；④ Minor GC后存活对象Survivor放不下。

CMS、G1、ZGC 分别适用什么场景？核心区别？
垃圾收集器高频核心

线上服务 OOM 了，你的排查思路是什么？
故障排查高频必考核心
▾
排查步骤
  • 1. 确认OOM类型：看错误日志，Java heap space / GC overhead / Metaspace / Direct buffer memory / Unable to create thread
  • 2. 获取Heap Dump：启动参数加 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/oom.hprof，或 jmap -dump:live,format=b,file=oom.hprof <pid>
  • 3. 分析Dump文件：MAT（Memory Analyzer Tool）或 VisualVM 打开，查看 "Leak Suspects" 报告，找最大对象占用者
  • 4. 常见根因：① 内存泄漏（静态集合持有大量对象）② 缓存无限增长 ③ 大对象分配（读整个文件到内存）④ 线程数过多（每线程1MB栈）
  • 5. 临时处置：重启服务恢复，同时保留Dump和GC日志

类加载机制？双亲委派模型的作用？如何打破？
类加载高频
▾
类加载过程：加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
双亲委派模型
  • 加载时先委派给父加载器，父加载器无法加载才自己加载
  • 层级：Bootstrap（JDK核心） → Extension（ext目录） → Application（classpath）
  • 作用：防止核心类被覆盖（java.lang.String 不会被自定义替换），保证类唯一性和安全
何时打破双亲委派
  • SPI机制（JDBC等）：线程上下文类加载器，由子加载器加载接口实现
  • OSGi / 热部署：每个模块有独立类加载器，实现类隔离和热替换
  • Tomcat：WebApp 类加载器优先加载自己的类（不委派给父），实现 War 包隔离

JIT 即时编译是什么？什么是编译热点？
JIT编译
▾
  • JVM 先解释执行字节码（慢），对热点代码触发 JIT 编译为本地机器码（快）
  • 热点判断：方法调用次数 > 阈值（C1=1500次，C2=10000次）
  • C1（Client）编译器：快速编译，少量优化，适合启动时
  • C2（Server）编译器：深度优化（内联、逃逸分析、锁消除），适合长期运行
  • GraalVM：可替换 C2，支持 AOT（提前编译），适合 Serverless 场景

Full GC 频繁触发，如何排查？
GC调优高频核心
▾
常见原因
  • 老年代空间不足：对象晋升速度 > 老年代回收速度，需增大堆或减少晋升
  • 元空间不足：动态类生成过多（CGLib、Groovy脚本），设置 MaxMetaspaceSize
  • System.gc() 显式调用：代码/第三方库调用，加 -XX:+DisableExplicitGC
  • 大对象直接进老年代：大文件/报表查询，改用分批处理或流式读取
  • CMS Concurrent Mode Failure：并发收集期间老年代用完，触发Full GC，需提前触发CMS（-XX:CMSInitiatingOccupancyFraction=70）

对象一定分配在堆上吗？什么是逃逸分析？
对象分配
▾
不一定。JIT 的逃逸分析（-XX:+DoEscapeAnalysis，默认开启）会判断对象是否逃逸出方法或线程。
  • 栈上分配：未逃逸的小对象直接在栈帧分配，方法结束自动销毁，无GC压力
  • 标量替换：对象被拆解为基本类型存在栈，彻底避免对象分配
  • 锁消除：未逃逸对象上的同步锁被 JIT 直接去掉（如对局部 StringBuilder 加锁）
  • TLAB（线程本地分配缓冲）：Eden区为每个线程预分配一小块空间，避免多线程竞争分配指针

volatile 的内存语义？happens-before 规则？
并发内存模型高频核心
▾
volatile 两大语义
  • 可见性：写 volatile 变量时强制刷新到主内存，读时从主内存重新加载，保证各线程读到最新值
  • 有序性（禁止指令重排）：写前不能重排到写后，读后不能重排到读前（通过内存屏障实现）
  • 不保证原子性：i++ 依然线程不安全，需用 AtomicInteger 或 synchronized
Happens-Before 核心规则（JMM）
  • 程序顺序规则：同线程内，前面的操作 happens-before 后面的操作
  • 监视器锁规则：unlock happens-before 后续的 lock
  • volatile规则：volatile写 happens-before 后续的 volatile读
  • 线程启动规则：Thread.start() happens-before 线程内任何操作
  • 传递性：A hb B，B hb C → A hb C
