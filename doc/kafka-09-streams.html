KStream / KTable / GlobalKTable 区别
类型 语义 存储 分区感知 适用场景
KStream 无限事件流，每条记录独立，不聚合 无本地状态（除非 groupBy 后） 按分区并行处理 日志流、点击流、事件序列
KTable 变更日志，相同 Key 的新值覆盖旧值，快照语义 本地 RocksDB 存储最新值 与输入 Topic 分区数一致 用户资料、配置、数据库变更同步
GlobalKTable 全局 KTable，每个实例加载全量数据 每个实例本地存储全量数据（内存/RocksDB） 不按分区，所有实例数据一致 小维度表广播（地区码、品类信息）
KSTREAM
事件流
每条消息独立处理，无状态覆盖
StreamsBuilder builder = new StreamsBuilder(); KStream<String, Order> orders = builder.stream("order-topic"); orders.filter((key, order) -> order.getAmount() > 100) .to("big-order-topic");
KTABLE
变更日志表
相同 Key 新值覆盖旧值，RocksDB 存储
KTable<String, UserProfile> users = builder.table("user-profile-topic", Materialized.as("user-store"));
GLOBALKTABLE
全局广播表
每个实例持有全量数据，适合小维度表
GlobalKTable<String, Region> regions = builder.globalTable("region-table");
有状态处理：聚合与窗口
STATEFUL 聚合、窗口与流表 Join
1
分组聚合（aggregate）
结果存储在本地 RocksDB State Store，可通过 Interactive Queries 直接查询。
orders.groupByKey() .aggregate( () -> 0L, (key, order, total) -> total + order.getAmount(), Materialized.<String, Long, KeyValueStore<...>> as("order-total-store") .withValueSerde(Serdes.Long()) );
2
时间窗口（Tumbling Window）
Tumbling（固定不重叠）/ Hopping（固定重叠）/ Sliding（基于事件时间滑动）/ Session（基于活跃度的会话窗口）。
orders.groupByKey() .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofMinutes(5))) .count(Materialized.as("order-count-5min"));
3
流表 Join
支持：KStream-KStream Join（双流 Join，需窗口）/ KStream-KTable Join（流表 Join，无窗口）/ KStream-GlobalKTable Join（广播 Join，无需 co-partition）。
KStream<String, EnrichedOrder> enriched = orders.join( users, (order, user) -> new EnrichedOrder(order, user.getName()) );
4
时间语义
Event Time（消息中的业务时间戳，最准确，需处理乱序）/ Processing Time（Broker 处理时间，简单但可能不准）/ Ingestion Time（消息进入 Kafka 的时间）。Kafka Streams 默认 Event Time，通过 TimestampExtractor 自定义提取逻辑。
RocksDB 状态存储与容错
LOCAL STATE
本地状态存储
LSM Tree 结构，写入高效，延迟极低
  • Kafka Streams 将有状态算子的中间结果存储在本地 RocksDB，避免每次都远程查询
  • RocksDB 采用 LSM Tree 结构，顺序写入效率极高，读取通过布隆过滤器加速
  • State Store 的数据同时写入内置的 Changelog Topic（Kafka Topic），作为持久化备份
  • 支持通过 Interactive Queries API 直接对外暴露 State Store 查询接口
FAULT TOLERANCE
容错恢复
Changelog Topic 重放，热备减少恢复时间
  • 实例崩溃重启后，框架从 Changelog Topic 重放数据到本地 RocksDB，恢复 State Store
  • 恢复时间取决于积压量，可能需要数分钟
  • Standby Replicas（num.standby.replicas）：在其他实例上预热 State Store
  • 故障时热备实例快速接管，无需从头重放 Changelog
CHANGELOG Changelog Topic 机制
1
Changelog Topic 命名
自动创建，命名规则：${application.id}-${store-name}-changelog，由 Kafka Streams 框架管理生命周期。
2
压缩策略
Changelog Topic 默认配置 cleanup.policy=compact，只保留每个 Key 的最新值，避免无限增长。
3
Standby Replicas
在其他实例上预热 State Store，持续消费 Changelog Topic 保持同步。故障时快速接管，无需从头重放，大幅减少恢复时间。
Topology 构建与并发度
Topology 数据流示意
TOPOLOGY Sub-topology 与并发度控制
1
Sub-topology
Kafka Streams 将 Topology 自动分割为多个 Sub-topology（以 Repartition Topic 为边界），每个 Sub-topology 独立并行执行，互不阻塞。
2
并发度控制
num.stream.threads（默认 1）：单个实例内并行的流处理线程数。多个 Streams 实例（横向扩展）通过消费者组机制自动分配 Partition，最大并发度 = 输入 Topic 的 Partition 数。
3
查看 Topology
调用 topology.describe() 可输出 Sub-topology 列表和处理器依赖关系，便于调试和优化。
Topology topology = builder.build(); System.out.println(topology.describe()); // 输出 Sub-topology 列表和处理器依赖关系
Kafka Connect 框架
SOURCE CONNECTOR
Source Connector
从外部系统拉取数据写入 Kafka Topic
  • 从 DB、文件、API 拉取数据写入 Kafka Topic
  • Debezium MySQL Source：CDC 变更捕获，实时同步数据库变更
  • FileStream Source：读取文件内容写入 Topic
  • JDBC Source：定期轮询数据库表，支持增量同步
SINK CONNECTOR
Sink Connector
从 Kafka Topic 读取数据写入外部系统
  • 从 Kafka Topic 读取数据写入 DB、ES、HDFS、S3
  • JDBC Sink：写入关系型数据库，支持 upsert
  • Elasticsearch Sink：实时索引 Kafka 消息到 ES
  • S3 Sink：按时间分区写入 S3，适合数据湖场景
CONNECT 部署与运行机制
1
启动 Connect
Standalone 模式（单节点，开发用）或 Distributed 模式（多节点，生产用）。Distributed 模式下多个 Worker 组成集群，通过内置 Topic 协调任务分配与 Offset 存储。
2
部署 Connector（REST API）
POST /connectors { "name": "mysql-source", "config": { "connector.class": "io.debezium.connector.mysql.MySqlConnector", "database.hostname": "mysql", "database.port": "3306", "database.user": "debezium", "database.password": "dbz", "database.server.name": "mydb" } }
3
Task 并行
每个 Connector 分解为多个 Task（tasks.max 配置），Task 是实际执行的单元，由 Worker 线程运行，支持横向扩展提高吞吐。
4
容错
Distributed 模式下 Worker 宕机后，Task 自动重新分配给存活 Worker；Offset 存储在 Kafka 内部 Topic，重启后从上次位置继续，保证 At-Least-Once 语义。
Schema Registry + Avro / Protobuf
SCHEMA Schema Registry 工作原理与兼容性策略
1
问题背景
Kafka 消息是 byte[]，无内置 Schema。当 Producer 和 Consumer 的消息格式不一致时（字段增减、类型变化），Consumer 反序列化失败。Schema Registry 提供集中式 Schema 管理和兼容性校验。
2
工作原理
Producer：发送前向 Schema Registry 注册 Schema（返回 Schema ID），消息头写入 Magic Byte(0x0) + Schema ID(4字节) + 序列化数据。
Consumer：解析消息头中的 Schema ID，从 Registry 拉取 Schema（带本地缓存），再反序列化数据。
3
Schema 兼容性策略
策略 含义 适用场景
BACKWARD 新 Schema 可读旧数据（可删字段，可加可选字段） Consumer 先升级
FORWARD 旧 Schema 可读新数据（可加字段，可删可选字段） Producer 先升级
FULL 双向兼容 严格场景，要求最高
NONE 不检查兼容性 开发阶段
4
Avro vs Protobuf vs JSON Schema
Avro：Schema 随数据存储，压缩好，Hadoop 生态友好。
Protobuf：IDL 驱动，跨语言支持好，Google 生态。
JSON Schema：可读性强，但序列化效率低。
生产推荐 Avro 或 Protobuf。
与 Flink / Spark 集成
FLINK Flink + Kafka
1
KafkaSource（新版 Source API）
自动管理 Offset，支持 Exactly-Once（通过 Flink Checkpoint 将 Offset 保存到 Flink State）。
2
KafkaSink
支持 Exactly-Once（通过 Kafka 事务，DeliveryGuarantee.EXACTLY_ONCE），Checkpoint 时提交事务。
3
代码示例
KafkaSource<String> source = KafkaSource.<String>builder() .setBootstrapServers("localhost:9092") .setTopics("input-topic") .setGroupId("flink-group") .setStartingOffsets(OffsetsInitializer.latest()) .setValueOnlyDeserializer(new SimpleStringSchema()) .build(); env.fromSource(source, WatermarkStrategy.noWatermarks(), "Kafka Source");
SPARK Spark Structured Streaming + Kafka
1
readStream 从 Kafka 读取
DataFrame API，每行包含 key、value、topic、partition、offset、timestamp 字段。
2
写入 Kafka
writeStream + kafka sink，指定 topic 和 bootstrap.servers，配置 checkpointLocation 保证容错。
3
代码示例（Scala）
val df = spark.readStream .format("kafka") .option("kafka.bootstrap.servers", "localhost:9092") .option("subscribe", "input-topic") .load() df.selectExpr("CAST(key AS STRING)", "CAST(value AS STRING)") .writeStream.format("kafka") .option("kafka.bootstrap.servers", "localhost:9092") .option("topic", "output-topic") .option("checkpointLocation", "/tmp/checkpoint") .start()
INFO

Kafka Streams vs Flink 选型：轻量流处理（无复杂 State，业务简单）→ Kafka Streams（无需额外集群）；复杂 CEP、多流 Join、大 State → Flink（更强的有状态计算能力）；批流统一、SQL 查询 → Spark Structured Streaming。

Spring Kafka 核心使用
SPRING Spring Kafka 核心用法
1
依赖（Maven）
<dependency> <groupId>org.springframework.kafka</groupId> <artifactId>spring-kafka</artifactId> </dependency>
2
Producer（KafkaTemplate）
@Autowired private KafkaTemplate<String, String> kafkaTemplate; public void send(String topic, String message) { kafkaTemplate.send(topic, message) .whenComplete((result, ex) -> { if (ex != null) log.error("Send failed", ex); }); }
3
Consumer（@KafkaListener）
@KafkaListener(topics = "order-topic", groupId = "order-group", concurrency = "3") public void consume(ConsumerRecord<String, String> record, Acknowledgment ack) { // 处理消息 processOrder(record.value()); // 手动提交（需配置 ack-mode: manual） ack.acknowledge(); }
4
关键配置（application.yaml）
spring: kafka: bootstrap-servers: localhost:9092 consumer: group-id: my-group auto-offset-reset: earliest enable-auto-commit: false listener: ack-mode: manual concurrency: 3
WARN

concurrency 不能超过 Topic 的 Partition 数，否则多余的线程会空闲（同 Consumer Group 规则）。生产建议关闭 enable-auto-commit，使用 ack-mode: manual 配合 Acknowledgment.acknowledge() 手动提交，避免消息未处理完就提交 Offset 导致丢失。
