01 CLAUDE.md 配置
CLAUDE.md 是什么

CLAUDE.md 是 Claude Code 的项目级配置文件，放在项目根目录。每次启动 Claude Code 时自动读取，相当于给 Agent 注入一份"项目上下文"。写得好的 CLAUDE.md 能让 Claude 理解项目架构、编码规范、常用命令，减少重复解释。

类比：CLAUDE.md 就是你给新同事的"项目上手指南"，写得越清楚，同事干活越靠谱。
推荐结构
# CLAUDE.md

## Project Overview
一句话说清楚项目是什么、用什么技术栈。

## Architecture
关键目录结构、核心模块职责。

## Commands
- 构建：`mvn clean package`
- 测试：`mvn test`
- Lint：`./mvnw spotless:check`

## Code Conventions
编码规范、命名约定、重要约束。

## Common Patterns
项目中反复出现的模式（如错误处理、API 风格）。
最佳实践：保持 CLAUDE.md 精简（200-500 行以内）。太长反而让 Claude 抓不住重点。用 ## 分节，每节 3-5 条关键信息。
多级配置
文件位置作用域用途
~/.claude/CLAUDE.md全局个人偏好、通用规范（所有项目生效）
项目根目录/CLAUDE.md项目级项目架构、构建命令、团队规范
子目录/CLAUDE.md模块级特定模块的上下文（如 doc/、src/）
加载顺序：全局 → 项目根 → 子目录。子目录配置会补充而非覆盖全局配置。
02 自定义 Skills NEW
什么是 Skills

Skills 是 Claude Code 的可复用指令模板，把一套固定的工作流封装成一个 skill 文件。当你触发某个 skill 时，Claude 会按照预定义的步骤执行，保证每次做同一件事质量一致。

  • ▸ 本质是一个 SKILL.md 文件，包含角色定义、步骤清单、输出格式
  • ▸ 可以引用项目中的脚本、模板、配置文件
  • ▸ 支持参数化，同一个 skill 可用于不同场景
Skill 文件示例
# SKILL.md — code-review

## 角色
你是一个严格的代码审查员，专注于发现 bug 和安全隐患。

## 步骤
1. 读取 git diff 的变更
2. 检查每个变更文件的：
   - 边界条件处理
   - 资源泄漏风险
   - 并发安全性
3. 输出审查报告，格式：
   - 🔴 严重问题
   - 🟡 建议改进
   - 🟢 做得好的地方

## 约束
- 只评论变更的代码，不评论未改动的部分
- 每个问题给出具体的修复建议
常用内置 Skills
Skill用途触发方式
Code编码工作流（规划→实现→验证）编写代码时自动匹配
brainstorming需求探索与设计讨论创建功能前自动匹配
security-auditor安全审查涉及认证/加密时匹配
frontend-design前端界面设计构建 UI 组件时匹配
03 MCP 集成
MCP（Model Context Protocol）

MCP 是 Claude Code 连接外部工具和数据源的标准协议。通过 MCP Server，Claude 可以读写数据库、调用 API、操作文件系统、访问浏览器——能力边界大幅扩展。

  • ▸ MCP Server 是一个独立进程，通过 stdio 或 HTTP 与 Claude Code 通信
  • ▸ Claude Code 内置支持 MCP，无需额外插件
  • ▸ 配置在 .mcp.json 或 ~/.claude/mcp.json
MCP 配置示例
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "postgresql://localhost/mydb"]
    },
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/allowed/dir"]
    }
  }
}
安全注意：只暴露必要的目录和数据库给 MCP Server。生产环境不要把数据库凭据硬编码在配置文件中。
常用 MCP Server
Server功能适用场景
postgres / mysql数据库查询查数据、改 schema、写 SQL
filesystem文件读写操作非项目目录的文件
githubGitHub API管理 Issue、PR、Release
brave-search网络搜索查找最新文档、Stack Overflow
puppeteer浏览器控制自动化测试、截图、爬取页面
04 多文件编辑
Edit vs Write vs Patch
工具用途最佳场景
Edit精确替换文件中的某段文本修改已有文件的特定部分
Write创建新文件或完全重写新建文件、大规模重构
Read读取文件内容编辑前先理解上下文
核心原则：Claude Code 每次编辑都基于 Read 获取的真实内容。先 Read → 理解上下文 → 再 Edit，而不是凭猜测修改。
高效编辑模式
  • ▸ 先读后改：每次 Edit 前必须 Read 过目标文件，确保 oldString 精确匹配
  • ▸ 小步迭代：一次 Edit 改一小段，比一次改整个文件更可靠
  • ▸ 并行读取：需要看多个文件时，一次性 Read 所有文件，减少轮次
  • ▸ replaceAll：批量重命名变量时用 replaceAll: true，比逐个替换快
批量操作技巧
# 批量重命名：把所有 MyOldService 替换为 MyNewService
Edit(filePath, oldString="MyOldService", newString="MyNewService", replaceAll=true)

# 跨文件一致性：同时修改接口和实现
Read 接口文件 → Read 实现文件 → Edit 接口 → Edit 实现
05 记忆管理
Memory 系统

Claude Code 有持久化记忆能力，可以跨会话记住项目上下文、你的偏好、过去的决策。记忆存储在 .claude/memory/ 目录下。

  • ▸ Project Memory：项目级知识，所有会话共享（架构决策、技术选型）
  • ▸ Session Memory：当前会话的工作状态、任务进度
  • ▸ Global Memory：跨项目的个人偏好（编码风格、常用工具）
如何利用记忆
  • ▸ 让 Claude 在关键决策时自动写入记忆，下次会话直接引用
  • ▸ 用 memory search 查询过去的技术决策，避免重复讨论
  • ▸ 在 CLAUDE.md 中告诉 Claude 什么信息值得记住
实用技巧：在 CLAUDE.md 中加一句"每次做完重要决定后，把原因写入 project memory"，这样团队新成员（或未来的你）能快速了解历史背景。
06 Git 工作流
Claude Code 的 Git 行为准则
  • ▸ 绝不自动 commit：除非你明确要求，Claude 不会执行 git commit
  • ▸ 绝不 force push：破坏性操作必须人工确认
  • ▸ 精确 add：只 git add 涉及的文件，不用 git add -A
  • ▸ 新建 commit 而非 amend：除非你明确要求修改上一次 commit
常用 Git 指令
commit 并推送告诉 Claude "commit 并 push"，它会自动 add → commit → push，commit message 按项目风格生成
创建 PR说 "创建一个 PR"，Claude 会 diff 所有变更、写 PR description、用 gh 命令创建
review 代码说 "review 一下最近的改动"，Claude 会 git diff HEAD~N 并逐文件审查
解决冲突遇到 merge conflict 时，Claude 可以读取冲突文件并给出解决建议
07 并行与子代理
Subagent（子代理）

Claude Code 可以派生子代理并行处理多个独立任务。子代理是独立的 Claude 实例，有自己的上下文，完成后把结果返回给主代理。

  • ▸ explore：快速搜索代码库，找定义、找调用者、查签名
  • ▸ general：执行复杂多步任务（写代码、分析、审查）
并行场景
场景做法收益
同时改 3 个独立文件派 3 个子代理并行编辑3x 速度
大范围代码探索派 explore 子代理搜索主代理不被阻塞
写代码 + 写测试一个子代理实现，另一个写测试并行推进
多模块重构每个模块一个子代理模块间互不干扰
注意：子代理看不到主代理的完整上下文，派发时必须在 prompt 中给足背景信息。
08 成本优化
Token 消耗分析

Claude Code 的成本主要来自上下文窗口——每次请求都会带上完整对话历史。上下文越长，token 消耗越大。

操作估算 Token优化建议
读一个小文件（~100行）~800 tokens用 offset/limit 只读需要的部分
读一个大文件（~500行）~4000 tokens先 grep 定位再精确读取
一次 Edit 操作~500 tokens小步迭代，避免反复修改同一处
子代理搜索~2000 tokens只在真正需要时派子代理
省钱技巧
💡
用 Sonnet 而不是 Opus
80% 的任务 Sonnet 就够了。只在复杂推理、架构设计时切换 Opus。用 /model 命令随时切换。
💡
精确读取而非全量读取
用 Read(offset=100, limit=50) 只读 50 行，而不是读整个 500 行文件。省 90% token。
💡
Grep 定位后再 Read
先 Grep 找到行号，再精确 Read 那几行。比直接读整个文件省很多。
💡
及时开新会话
对话超过 30 轮后，上下文膨胀严重。开一个新会话，用 CLAUDE.md 和 memory 恢复上下文，比继续长对话更省。
09 调试技巧
让 Claude 帮你 Debug
  • ▸ 贴错误日志：直接粘贴报错信息，Claude 会定位到出错的文件和行号
  • ▸ 描述复现步骤：告诉 Claude "做了 X 操作，期望 Y，实际 Z"
  • ▸ 让它跑测试：说 "跑一下测试看看哪些失败"，Claude 会执行并分析结果
  • ▸ 让它加日志：说 "在这里加几行日志"，Claude 会帮你加 debug log
调试工作流
1
描述问题
给 Claude 完整的错误信息、堆栈跟踪、复现步骤
2
Claude 定位
Claude 读取相关文件，分析根因，给出修复方案
3
应用修复
Claude 修改代码，你 review 变更
4
验证
跑测试确认修复有效，没有引入新问题
10 实战工作流
从 0 到 1 开发新功能
① 需求探索"我要做一个 X 功能，帮我分析需求和技术方案" → Claude 会提问题、给方案
② 写计划"写一个实现计划" → Claude 会生成分步计划，你确认后开始执行
③ 实现"按计划执行" → Claude 逐步实现，每步完成后自动验证
④ 测试"写测试" → Claude 生成单元测试/集成测试，跑通后提交
⑤ 提交"commit 并创建 PR" → Claude 按规范 commit + 推送 + 建 PR
日常开发快捷指令
你说Claude 做什么
"解释一下这个文件"读取文件，逐模块解释用途和逻辑
"这个函数有什么问题"分析函数逻辑，找 bug 和改进建议
"帮我重构这段代码"分析代码坏味道，给出重构方案并执行
"写一个 API 接口"按项目风格生成 Controller + Service + DTO
"跑一下 lint"执行项目的 lint 命令，修复报错
"看看最近 5 个 commit 改了什么"git log + git diff，总结变更
"这个 PR 改了什么，有没有问题"拉取 PR diff，逐文件审查
高效使用的核心原则
🎯
明确 > 模糊
说"在 UserService 的 login 方法里加一个参数校验"，而不是"帮我加个校验"。越具体，Claude 做得越准。
🎯
分步 > 一大坨
复杂任务拆成小步骤，每步确认后再下一步。一次扔 10 个需求容易出错。
🎯
验证 > 盲信
Claude 改完代码后，跑一下测试、看一眼 diff。不要假设"它肯定改对了"。
🎯
CLAUDE.md > 重复解释
每次都要解释的项目规范，写进 CLAUDE.md。一次投入，永久省时间。
