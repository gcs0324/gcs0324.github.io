01 · 高性能三驾马车原理串联
三驾马车综合示意 — Producer 写入 → Broker 处理 → Consumer 拉取
01 · 顺序写
Append-Only 日志
  • 磁盘顺序写吞吐 600MB/s，随机写仅 100MB/s
  • Partition 日志只追加不修改，天然适配顺序 IO
  • OS 对顺序 IO 有 预读（readahead）优化，进一步提速
  • 无需 B-Tree 索引维护，写放大极低
02 · Page Cache
OS 托管内存层
  • Broker 写入只写 OS Page Cache，异步刷盘，写入即返回
  • Consumer 读取先查 Page Cache，命中则 零延迟（纯内存读）
  • Kafka 故意不在 JVM 堆缓存消息，避免 GC 停顿影响延迟
  • OS 负责 Cache 淘汰（LRU），比应用层更高效
03 · 零拷贝
sendfile 系统调用
  • Page Cache → 网卡仅 2 次 DMA 拷贝，0 次 CPU 拷贝
  • 传统路径：4 次拷贝（2 CPU + 2 DMA），涉及用户空间切换
  • 减少约 50% 数据搬运，CPU 占用显著降低
  • DMA 直接操作内存，CPU 全程不参与数据复制
02 · 批量读写与消息压缩
BATCH 批量发送
1
RecordBatch 打包
Producer 将多条消息打包成 RecordBatch，由 batch.size（容量上限）和 linger.ms（等待时间上限）共同控制触发条件。
2
一次请求多条消息
一个网络请求携带一个或多个 RecordBatch，大幅降低请求次数和连接开销。量化：单条发送 QPS 约 5~10 万/s，批量后可达 100~200 万/s，提升 10~20 倍。
3
推荐均衡配置
linger.ms=5 + batch.size=65536（64KB）是常见的均衡配置，兼顾吞吐与延迟。高吞吐场景可调大 batch.size=1048576（1MB）。
# Producer 关键配置 batch.size=65536 linger.ms=5 buffer.memory=67108864
COMPRESS 消息压缩
1
批粒度压缩
压缩在 RecordBatch 粒度进行（一批压缩），比逐条压缩效率高得多，压缩比也更高（重复字段可跨消息去重）。
2
Producer 压缩，Consumer 解压
压缩在 Producer 端完成，Broker 存储压缩数据（不解压），Consumer 拉取后解压。Broker 几乎不承担压缩 CPU 开销。
3
算法对比
根据场景选择合适的压缩算法：
算法 压缩比 速度 CPU 推荐场景
none 1x — 无 低延迟优先，消息本身已压缩
gzip 3~5x 慢 高 带宽受限，CPU 充足
snappy 2~3x 快 低 均衡选择（Google 推荐）
lz4 2~3x 极快 极低 生产推荐，Kafka 默认支持
zstd 3~5x 中 中 高压缩比且速度优于 gzip（Kafka 2.1+）
03 · Reactor 网络模型
Kafka Broker 网络线程模型 — Acceptor / Processor / Handler 三层分工
REACTOR 三层线程模型详解
1
Acceptor — 单线程连接分发
唯一的 Acceptor 线程负责 accept() 新连接，通过 Round-Robin 将连接分配给各 Processor。Acceptor 不做任何 IO 操作，只负责连接分发，永远不会成为瓶颈。
2
Processor — NIO 多路复用网络 IO
每个 Processor 线程通过 NIO Selector 同时管理多个客户端连接，只负责网络读写和请求解析，不做任何业务逻辑。解析完的请求放入 RequestChannel，收到响应后发回客户端。默认 num.network.threads=8，网络密集场景可适当调大。
3
KafkaRequestHandler — 业务处理线程
从 RequestChannel 取请求，执行实际的磁盘读写、日志追加等业务逻辑，是 性能瓶颈所在。响应写回 Processor 的 ResponseQueue。建议线程数 = 磁盘数 × 2（IO 密集型），配置项 num.io.threads=16。
# server.properties 核心线程配置 num.network.threads=8 # Processor 数量 num.io.threads=16 # Handler 数量，建议 = 磁盘数×2 queued.max.requests=500 # RequestChannel 最大队列长度
04 · 多副本 + ISR 高可用
ISR · HA 多副本高可用配置与策略
1
基础配置三件套
replication.factor=3（3 副本）、min.insync.replicas=2、acks=-1。这三个参数的组合才是真正的高可用保障，单独配置任何一项都不够。
# Topic 级别配置 replication.factor=3 min.insync.replicas=2 # Producer 配置 acks=-1 (all)
2
故障容忍能力
3 副本可容忍 1 个 Broker 宕机（ISR 还剩 2 个，满足 min.insync.replicas=2），消息不丢、服务不中断。2 个 Broker 同时宕机时写入失败（但已有数据不丢，不会丢消息）。
3
副本分布策略
Kafka 自动将 Partition 的不同副本分配到不同 Broker。建议配置机架感知（broker.rack），确保副本跨机架分布，抵御整机架故障。新增 Broker 后执行 kafka-reassign-partitions.sh 重新均衡。
# broker.rack 配置（每个 Broker 节点设置） broker.rack=rack-1 # Broker1 broker.rack=rack-2 # Broker2 broker.rack=rack-3 # Broker3
4
核心监控指标
持续监控以下指标，任何异常立即告警：
UnderReplicatedPartitions > 0：有 Partition 副本不足，紧急处理
IsrShrinksPerSec：ISR 收缩频率，频繁收缩说明 Follower 追不上
IsrExpandsPerSec：ISR 扩展频率，应与收缩频率基本持平（健康状态）
05 · min.insync.replicas 深度解析
配置组合 数据可靠性 可用性 说明
acks=1（不配置 min.isr） 中 高 Leader 写入即 ACK，Follower 未同步时 Leader 宕机则丢数据
acks=-1 + min.isr=1 中 高 等同于 acks=1，ISR 只剩 Leader 时仍然 ACK，无保护
acks=-1 + min.isr=2 + rf=3 高 中 真正的高可靠配置，同时宕机 2 个 Broker 时写入失败（保护数据）
acks=-1 + min.isr=3 + rf=3 极高 低 任一 Broker 异常即写入失败，可用性过低，不推荐
BEST PRACTICE

黄金配置：replication.factor=3 + min.insync.replicas=2 + acks=-1，在可靠性和可用性之间取得最佳平衡。这是生产环境核心 Topic 的标配。同时建议设置 unclean.leader.election.enable=false，防止非 ISR 成员被选为 Leader 导致数据丢失。

06 · Broker 宕机恢复流程
RECOVERY Broker 宕机到完全恢复的完整流程
1
宕机检测
Controller 通过 ZooKeeper Session 超时（默认 30s）或心跳超时检测到 Broker 宕机。KRaft 模式（Kafka 3.3+）通过 Raft 心跳机制检测，无需 ZooKeeper，检测速度更快（通常 <10s）。
2
Leader 切换
Controller 为该 Broker 上所有 Partition（担任 Leader 的）从 ISR 中选举新 Leader，批量发送 LeaderAndIsrRequest 给存活 Broker 通知 Leader 变更。整个过程通常在 数秒内完成（Partition 数量越多耗时越长）。
# 查看 Controller 当前状态 kafka-metadata-quorum.sh --bootstrap-server :9092 describe --status
3
客户端感知新 Leader
Producer/Consumer 遇到请求失败（NotLeaderOrFollowerException）后，通过 metadata.max.age.ms（默认 5min，建议调小到 30s）触发元数据刷新，获取新的 Partition Leader 信息，自动重连到新 Leader 继续工作，无需人工干预。
4
宕机 Broker 恢复
Broker 重启后，以 Follower 身份重新加入集群，向新 Leader 发送 Fetch 请求追赶数据（Catch-up）。追上 HW（High Watermark）后重新加入 ISR，此时 IsrExpandsPerSec 指标会出现一次增长。
5
Preferred Leader 选举（恢复均衡）
Broker 恢复后，集群可能处于非均衡状态（原 Preferred Leader 已变成 Follower）。auto.leader.rebalance.enable=true（默认开启）会定期（leader.imbalance.check.interval.seconds=300）触发 Preferred Leader 选举，恢复均衡分布，避免热点。
# 手动触发 Preferred Leader 选举 kafka-leader-election.sh --bootstrap-server :9092 \ --election-type preferred --all-topic-partitions
07 · 跨机房双活 / 灾备方案
主备模式
Active-Standby
一主一备，MirrorMaker 2 异步同步，故障时 DNS 切换
  • 主机房：正常处理所有流量，Producer/Consumer 全部连接主集群
  • 备机房：通过 MirrorMaker 2 异步同步数据（延迟 100ms~秒级）
  • 故障切换：DNS 切换到备机房，Consumer 通过 RemoteClusterUtils.translateOffsets() 恢复 Offset
  • RPO：秒级（可能丢失最近几秒的数据）
  • RTO：分钟级（DNS 生效 + Consumer 重启时间）
  • 缺点：切换有延迟，可能重复消费或少量丢失；备机房资源利用率低
双活模式
Active-Active
两机房各自处理流量，双向 MirrorMaker 2 同步
  • 架构：两机房各部署独立 Kafka 集群，各自处理部分流量（按用户 / 请求路由）
  • 同步：双向 MirrorMaker 2 同步，需用 Topic 前缀过滤避免无限循环（如 dc1. 前缀的 Topic 不回同步到 dc1）
  • 优点：无单点故障，任一机房故障另一个接管，资源利用率高
  • 挑战：消息可能在两机房重复，下游需幂等处理
  • 挑战：跨机房写入延迟高（通常 10~50ms RTT）
  • RPO：准零（同步延迟内）
FAILOVER 机房切换注意事项
1
Offset 映射
源集群和目标集群的 Offset 不同（MirrorMaker 2 不保证 Offset 一致）。使用 MM2 的 Checkpoint 文件（__consumer_offsets 中的映射记录）做 Offset 转换，确保从正确位置开始消费。
# 使用 MM2 工具查询 Offset 映射 RemoteClusterUtils.translateOffsets(adminClient, "source-cluster", groupId, timeout)
2
Consumer Group 迁移
告知 Consumer 连接新集群的 bootstrap.servers，并从映射后的 Offset 开始消费（不能直接 seek 到旧 Offset，需先 translate）。建议提前在目标集群创建好相同的 Consumer Group。
3
Schema 兼容
确保两端的 Schema Registry 同步（或共用同一个），避免切换后反序列化失败。如果是 Avro/Protobuf 消息，Schema ID 在两个集群中必须一致。
4
监控双集群
两个集群都需要完整的监控体系（JMX + Prometheus + Grafana），切换后重点验证：Consumer Lag 是否正常下降、吞吐是否恢复到预期水平、是否有大量重复消费（幂等性验证）。
08 · 面试速答（系统设计题）
INTERVIEW 4 道高频系统设计面试题
Q1
Kafka 为什么能实现百万级 TPS？
五个维度逐一回答：
① 顺序写：磁盘顺序写 600MB/s，接近内存随机写，Append-Only 设计避免寻址开销
② Page Cache：写入即写内存，OS 异步刷盘，完全不受 JVM GC 影响
③ 零拷贝：sendfile 系统调用，0 次 CPU 拷贝，2 次 DMA 拷贝，减少 50% 数据搬运
④ 批量处理：RecordBatch 批量发送，减少 10~20 倍网络请求次数
⑤ 分区并行：多 Partition 线性扩展，多 Consumer 并行消费，横向扩展能力强
Q2
如何保证 Kafka 消息不丢失？三端分析
Producer 端：acks=-1 + 异常处理（Callback 中捕获失败并重试）+ 幂等重试（enable.idempotence=true）
Broker 端：replication.factor=3 + min.insync.replicas=2 + unclean.leader.election.enable=false（禁止脏选举）
Consumer 端：关闭自动提交（enable.auto.commit=false），先处理消息再手动提交 Offset，业务逻辑幂等

三端缺一不可，最容易忽视的是 Consumer 端的幂等设计（先提交再处理 = 可能丢消息，先处理再提交 = 可能重复消费，需业务幂等兜底）。
Q3
设计一个支持 100 万 TPS 的 Kafka 集群，如何规划？
分区规划：单分区写入约 10~20MB/s（100 字节消息约 10~20 万/s），100 万/s 需要约 5~10 个分区。考虑冗余和扩展性，设 50~100 个分区（过多分区会增加 Controller 和 ZooKeeper 负担）
Broker 规模：每个 Broker 约 100~200MB/s 吞吐，replication.factor=3 下实际写入约 300MB/s（100 万/s × 100 字节 × 3 副本 = 300MB/s），需要约 10 个 Broker（每个承载 30MB/s，留有余量）
硬件规格：每个 Broker 配 12 核 CPU、64GB 内存、RAID10 SSD 或多块独立 HDD（建议 JBOD 模式）
网络：万兆网卡（10GbE），避免网络成为瓶颈（300MB/s 复制流量 × 节点数）
# 容量估算公式 每秒总字节 = 消息数/s × 平均消息大小 × replication.factor 所需 Broker 数 = 每秒总字节 / 单 Broker 吞吐上限 × 安全系数(1.5)
Q4
Broker 磁盘打满了怎么紧急处理？
① 立即定位：du -sh /data/kafka-logs/*/ 找出占用最大的 Topic 目录
② 触发快速清理：临时减小该 Topic 的 log.retention.hours 或 log.retention.bytes，触发快速清理（不需要重启 Broker，热更新生效）
③ 检查 Compaction：若有 Log Compaction Topic，检查 Cleaner 线程是否正常（kafka-log-dirs.sh 查看每个 Partition 的 Dirty ratio）
④ 紧急扩容：挂载新磁盘，在 log.dirs 中追加新路径（热更新），Kafka 会自动将新 Partition 分配到新磁盘
⑤ 长期方案：启用 Tiered Storage（Kafka 3.6+）将冷数据归档到对象存储（S3/OSS），本地只保留热数据
# 动态修改 Topic 保留策略（不需要重启） kafka-configs.sh --bootstrap-server :9092 \ --entity-type topics --entity-name my-topic \ --alter --add-config retention.ms=3600000 # 改为 1 小时 # 追加新磁盘（热更新，修改后 SIGHUP 或等待配置刷新） log.dirs=/data/kafka-logs1,/data/kafka-logs2
