Leader / Follower 副本同步
Partition-0 副本分布 · ISR 与 OSR 示意
LEADER
Leader 副本
处理所有 Producer 写入与 Consumer 读取
  • 处理所有 Producer 写入和 Consumer 读取请求
  • 维护 ISR 列表和 HW（High Watermark）
  • 选举时唯一候选来源为 ISR 成员
  • 宕机后 Controller 从 ISR 中选出新 Leader
FOLLOWER
Follower 副本
主动 Pull，维护自身 LEO，被动接受踢出 / 回归 ISR
  • 主动向 Leader 发 FetchRequest（类似 Consumer Pull 模式）
  • 维护自己的 LEO（Log End Offset）
  • 落后超过 replica.lag.time.max.ms（默认 30s）则被踢出 ISR
  • 追上 Leader HW 后重新加入 ISR
ISR 动态维护
ISR In-Sync Replicas 全生命周期
1
ISR 定义
与 Leader 保持同步的副本集合，包括 Leader 自身。只有 ISR 成员才有资格成为新 Leader，是 Kafka 可靠性的核心保障。
2
判断标准
Follower 在 replica.lag.time.max.ms（默认 30000ms）内曾向 Leader 发送过 FetchRequest，即认为同步正常，留在 ISR。旧版本按消息数（replica.lag.max.messages）判断已废弃，因为批量写入容易误判。
3
踢出 ISR
Follower 超时未 Fetch，Leader 将其移出 ISR，通知 Controller 更新元数据。Follower 仍继续从 Leader 拉数据，只是不参与 acks 和选举。
4
重新加入 ISR
Follower 追上 Leader 的 HW（即自身 LEO ≥ Leader HW）后，Leader 重新将其加入 ISR。
5
ISR 收缩的影响
ISR 数量低于 min.insync.replicas 时，acks=-1 的 Producer 请求会收到 NotEnoughReplicasException。这是 Kafka 故意设计的安全保护：宁可写入失败，也不降低数据可靠性。
WARN

生产必须监控 UnderReplicatedPartitions JMX 指标，>0 立即告警。ISR 频繁收缩通常说明 Follower 有性能瓶颈（GC、磁盘 IO、网络带宽）。

LEO / HW / LSO 水位线
水位线示意 · LEO / HW / LSO
LEO
Log End Offset
  • 每个副本独立维护，指向下一条待写入位置
  • Leader LEO 随 Producer 写入实时增长
  • Follower LEO 随 Fetch 进度更新
  • Leader 用各 ISR 成员 LEO 计算 HW
HW
High Watermark
  • Leader 维护，等于 ISR 中所有副本 LEO 的最小值
  • HW 以下的消息 Consumer 可见（已被所有 ISR 副本持久化）
  • HW 以上的消息 Consumer 不可见，防止读到后续可能被截断的数据
LSO
Last Stable Offset
  • 事务场景专用，read_committed 的 Consumer 只能读到 LSO
  • 跳过进行中的事务消息，保证事务一致性
  • 无事务场景下 LSO = HW
  • 关系：LSO ≤ HW ≤ Leader LEO
WARN

HW 截断问题（Kafka 2.6 前）：Leader 宕机 Follower 晋升新 Leader，若新 Leader 的 HW 低于旧 Leader 已确认的消息，可能出现消息"回退"。Kafka 2.6 引入 Leader Epoch 解决：Follower 重启时对比 Leader Epoch，不一致则截断本地日志到安全位置。

Follower Fetch 流程
FETCH Follower 拉取数据完整链路
1
FetchRequest
Follower 向 Leader 发送请求，携带 TopicPartition、fetchOffset（自身当前 LEO）、maxBytes、maxWait。
2
Leader 读取数据
Leader 从 fetchOffset 开始读取 Log（走 Page Cache），同时更新该 Follower 在内存中记录的 LEO 值，用于 HW 计算。
3
更新 HW
Leader 根据所有 ISR 成员最新的 LEO 重新计算 HW，在 FetchResponse 中将新 HW 一并返回。
4
Follower 更新
Follower 写入数据到本地 Log（更新自身 LEO），然后更新自身 HW = min(自身 LEO, Response 中的 Leader HW)。
5
长轮询等待
若 Leader 暂无新数据，不立即返回空响应，等待最多 replica.fetch.wait.max.ms（默认 500ms）或有新数据到达，再响应。减少无效轮询，降低 CPU 和网络开销。
Leader 选举
TRIGGER
触发时机
以下情况会触发 Partition Leader 重新选举
  • Broker 宕机或网络隔离
  • Broker 优雅关闭（kafka-server-stop.sh）
  • Controller 执行分区平衡（preferred replica election）
  • 管理员手动执行 kafka-leader-election.sh
RULE
选举规则
Controller 按优先级依次执行
  • ① 优先从 ISR 中选 Preferred Replica（AR 列表第一个）
  • ② ISR 为空且 unclean.leader.election.enable=false（默认）→ Partition 变 offline
  • ③ unclean.leader.election.enable=true → 从所有副本中选，可能丢数据
COMPARE unclean 选举对比：CP vs AP
✗
unclean=false（默认，推荐）
ISR 为空时 Partition offline，拒绝读写。保证不丢数据（CP）。适合：订单、支付、账务等核心业务，数据一致性高于可用性。
✓
unclean=true
ISR 为空时从 OSR 选 Leader，可能丢失未同步的消息。保证可用性（AP）。适合：日志收集、埋点统计（少量丢失可接受）。
Controller 职责与选举
CONTROLLER 集群调度中心的五大职责
1
监听 Broker 存活
监听 ZooKeeper 的 /brokers/ids 节点（ZK 模式）或 @metadata 日志（KRaft 模式），发现 Broker 下线后触发 Leader 重新选举。
2
批量选举 Leader
为宕机 Broker 上的所有 Partition 重新选举 Leader（从 ISR 中选），批量生成 LeaderAndIsrRequest 发给集群所有存活 Broker，避免逐一通知的开销。
3
管理 ISR 变化
接收各 Partition Leader 上报的 ISR 变更，更新元数据并广播给所有 Broker。
4
Topic 生命周期管理
处理 Topic 创建/删除/分区扩容，计算副本分配方案，更新元数据。
5
Controller 自身选举
ZK 模式：所有 Broker 竞争创建 /controller 临时节点，成功者成为 Controller；Controller 宕机时节点消失，其他 Broker 重新竞争。
KRaft 模式：专属 Controller 节点组通过 Raft 协议选举，无需 ZooKeeper，选举更快更稳定。
INFO

Controller 是 Kafka 集群的"调度中心"，但也是单点。KRaft 模式下可配置多个 Controller 节点（建议 3 或 5 个），通过 Raft 保证高可用，元数据管理延迟更低，集群规模可支持百万级 Partition。

分区策略
策略 触发条件 路由规则 优点 适用场景
Hash 路由 Key 非 null murmur2(key) % numPartitions 同 Key 必落同 Partition，保证顺序 用户 ID、订单 ID 路由，保证顺序
黏性分区 (Sticky) Key 为 null（Kafka 2.4+ 默认） 同 batch 粘在一个 Partition，batch 满或 linger 到期后随机切换 减少小 batch，提高吞吐 无顺序要求的高吞吐场景
轮询 (RoundRobin) 旧版 Key 为 null 时 依次分配到各 Partition 均匀分布 已被 Sticky 取代
自定义分区器 配置 partitioner.class 实现 Partitioner 接口 完全自定义路由逻辑 按地域、业务线、VIP 等级路由
SIZING 分区数规划四条原则
1
容量公式
分区数 = 目标吞吐 ÷ 单分区吞吐（单分区写约 10~100 MB/s，取决于消息大小和硬件）
2
集群上限
单集群总分区数建议不超过 10 万（每个分区在 Broker 内存和 Controller 各有开销）
3
只增不减
分区数只能增加不能减少（减少会导致 hash 路由错乱，数据混乱）
4
扩分区前评估下游
若 Consumer 依赖 Hash 顺序，扩分区后同一 Key 可能换 Partition，破坏顺序保证。操作前必须通知下游 Consumer。
PLAN

设计初期就规划充足的分区数，生产环境扩分区代价远大于预留。建议：预期最大分区数 × 1.5 倍预留，且为 2 的幂次方（方便路由计算）。

面试速答
Q&A 分区与副本机制高频面试题
Q1
ISR 是什么？什么时候副本会被踢出 ISR？
ISR 是与 Leader 保持同步的副本集合。踢出条件：Follower 在 replica.lag.time.max.ms（默认 30s）内未向 Leader 发 FetchRequest。踢出后副本仍继续拉数据，不影响数据存储；追上 Leader HW 后重新加入 ISR。ISR 为空时，acks=-1 的写入会失败（NotEnoughReplicasException）。
Q2
LEO、HW、LSO 的含义和区别？
LEO：副本日志末尾 Offset（各自独立维护）。HW：ISR 中所有副本 LEO 的最小值，Consumer 可见边界。LSO：最后一个已完成事务的 Offset，read_committed 消费者的可见边界。关系：LSO ≤ HW ≤ Leader LEO。
Q3
分区数增加会有什么问题？
① Hash 路由的消息换 Partition，同 Key 消息可能路由到不同 Partition，破坏顺序保证；② Rebalance 期间消费暂停；③ Broker 和 Controller 内存、元数据开销增加；④ 已有 Segment 的数据不会迁移。操作建议：低峰期进行，提前评估顺序依赖，必要时通知下游 Consumer 暂停。
Q4
unclean.leader.election.enable 应该设 true 还是 false？
默认 false，推荐保持。设 true 会在 ISR 为空时允许从未同步副本选 Leader，可能丢失消息（未同步到该副本的消息永久消失）。只在允许少量丢失的场景（日志、埋点）才考虑设 true，核心业务务必保持 false。
Q5
Controller 宕机后集群会怎样？
ZK 模式：Controller 宕机后其 ZK 临时节点消失，其他 Broker 监听到后竞争成为新 Controller，通常数秒内完成。期间新的 Leader 选举请求会积压，但已有的 Partition Leader 继续正常服务读写。恢复后新 Controller 处理积压任务。
KRaft 模式：通过 Raft 在 Controller Quorum 中选举，无需 ZK，速度更快，通常 1~2 秒内完成。
