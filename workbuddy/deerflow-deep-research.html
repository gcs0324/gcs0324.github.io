定位与背景

DeerFlow（Deep Exploration and Efficient Research Flow）是字节跳动于 2026 年 2 月 28 日开源的 Super Agent Harness。开源当天即登顶 GitHub Trending 第一，目前已获 47k+ Stars。与 v1 零代码复用的彻底重写，定位从"深度研究框架"升级为"能干几乎任何复杂任务的超级智能体运行时"。

它不是套壳聊天机器人，而是"给 AI 一台真正的计算机，让它自主完成从几分钟到数小时的任务"。

三大核心亮点

💻

给 Agent 配了台真电脑

每个任务跑在隔离沙箱里，有完整文件系统和 Bash，能读写文件、跑脚本、装依赖。底层是字节开源的 AIO Sandbox，支持本地 / Docker / K8s 三级隔离，会话间零污染。

⚡

动态子智能体并行

主智能体拆解任务后按需拉起多个上下文隔离的子代理并行执行再汇总——这是它能扛长任务的根因。

🧩

开箱即用 + 高度可扩展

基于 LangGraph 1.0 + LangChain，出厂自带文件系统、记忆、技能、沙箱。加一个 Markdown Skill 就能扩能力，支持技能按需渐进加载省 token。

第一章

范式：从 Framework 到 Harness

认知演进三段论

1

2023–2024：提示工程时代

核心问题是"怎么让模型说对的话"——few-shot、CoT、ReAct 等提示技巧是主战场。Agent 的概念还停留在单轮推理层面。

2

2025：上下文工程时代

核心问题变成"怎么让模型记住更多"—RAG、长上下文窗口、记忆管理、结构化输出。LangChain/LlamaIndex 等 Framework 崛起，但都停留在"帮模型拼积木"层面。

3

2026：Harness 时代

核心问题升级为"怎么让模型真正干完活"。Harness（马具）不提供动力，但牵住方向、稳住步伐——它包裹模型，提供预设 Prompt、工具标准化、生命周期钩子、规划、文件系统、子智能体管理等一切让模型"持续稳定输出"的基础设施。

关键区分：Framework 给你零件让你组装；Harness 给你一套能直接上马的完整鞍具。DeerFlow 的核心价值不在"提供新能力"，而在"让已有能力稳定、可靠地交付复杂任务"。

v1 → v2 的定位跃迁

理解 DeerFlow 2.0 的钥匙在于一件事：Deep Research（深度研究）从"唯一主打"降级为"内置的一个 Skill"。v1 的定位是"帮人做研究的工具"，但字节内部团队在使用过程中发现——社区把 LangManus（DeerFlow 的前身）玩成了数据管道、PPT 工厂、内容流水线。大家真正要的不是研究工具，而是底下那套"能真正做事的运行时"。

于是团队决定彻底重写。与 v1 零代码复用——这不是渐进升级，而是范式跃迁。v2 的名字里虽然还带着"Research"，但实际做的是一套通用 Super Agent Harness。

"我们意识到，大家想要的底层那套能让 Agent 持续、稳定、可靠地完成复杂任务的基础设施——于是我们把它抽出来，做成了 DeerFlow 2.0。"
— DeerFlow 团队
第二章

总体架构：Lead Agent + Middleware Chain + Dynamic Sub-agents

DeerFlow 采用三段式协同架构：一个 Lead Agent 负责理解意图和拆解任务，11 层中间件链负责横切关注点（沙箱、记忆、限流、上下文管理等），一个动态子代理调度器负责并行执行和汇总。底层基于 LangGraph 状态图，上层封装为开箱即用的运行时。

架构总览

严格分层的工程纪律

架构上最关键的设计决策是 deerflow-harness（核心层）与 App（应用层）的严格分离。Harness 可独立发布为 pip 包，依赖方向为单向：App 可 import Harness，Harness 绝不 import App。这种约束确保了核心运行时不会被应用层代码污染，也方便社区在此基础上构建自己的 Agent 应用。

Lead Agent 的三部分动态构建

Lead Agent 由三个独立可替换的组件在运行时动态组装：

  • 模型层：支持任何 OpenAI 兼容 API 的模型，含 supports_thinking / supports_vision 等能力标记
  • 工具层：包括文件系统、Bash、Web 搜索、代码执行、MCP 工具等
  • 中间件链：11 层中间件按严格顺序串联，覆盖沙箱、记忆、摘要、限流等横切关注点
第三章

核心拆解一：11 层中间件链（全文最硬核）

DeerFlow 最精妙的设计，是把上传、沙箱、记忆、摘要、限流等横切关注点与核心 Agent 逻辑彻底解耦，封装为 11 层有序中间件。加能力 = 插一层中间件，不碰核心代码——这是典型的 AOP（面向切面编程）思想在 Agent 工程中的落地。

中间件全链与触发时机

# 中间件 类型 职责
1ThreadDataMiddlewarebefore_model在模型调用前注入线程上下文（thread_id 等）
2SandboxMiddlewarebefore_model为当前线程创建/复用沙箱实例，挂载文件系统
3FileMiddlewarebefore_model处理文件上传，将用户文件映射到沙箱虚拟路径
4SystemPromptMiddlewarebefore_model注入系统级 Prompt（任务指令、能力描述、格式约束）
5SkillMiddlewarebefore_model按需渐进加载 Skill（Markdown），注入工具列表和能力描述
6MemoryMiddlewarewrap_model_call读写持久化记忆，在模型调用前后插入/提取长期记忆
7SummaryMiddlewareafter_model自动检测上下文用量，超标时触发摘要压缩
8SubagentLimitMiddlewarebefore_agent控制子代理并发数（默认 3），防止 API 调用洪水
9ToolCallLimitMiddlewarebefore_agent限制单次任务最大工具调用次数，防止死循环
10RateLimitMiddlewarebefore_model控制模型 API 调用频率（规划中/v2.x）
11ClarificationMiddlewarebefore_agent检测指令模糊度，必要时中断执行流请求用户澄清

四类钩子的触发时机

A

before_agent

在 Lead Agent 开始执行任务前触发。SubagentLimitMiddleware 在此检查并发上限，ClarificationMiddleware 在此判断是否需要请求用户澄清。

B

before_model

每次调用 LLM 前触发。ThreadData、Sandbox、File、SystemPrompt、Skill 等中间件在此注入上下文，RateLimit 在此控制调用频率。

C

after_model

每次模型返回后触发。SummaryMiddleware 在此检测上下文消耗并触发压缩。

D

wrap_model_call

包裹整个模型调用过程。MemoryMiddleware 在此实现调用前后的记忆读写。

顺序不是随意的：层间依赖关系

关键约束：ThreadDataMiddleware 必须在 SandboxMiddleware 之前——因为沙箱需要 thread_id 来定位或创建实例。ClarificationMiddleware 必须放在最后——因为它可能中断执行流（抛出 ClarificationNeededException），之后的中间件不应再执行。

源码解析：中间件注册与执行

Python deerflow-harness/middleware/__init__.py · 中间件链注册 
# 中间件注册表 - 顺序至关重要
MIDDLEWARE_CHAIN = [
    ThreadDataMiddleware(),       # 1. 注入线程上下文
    SandboxMiddleware(),          # 2. 创建/复用沙箱
    FileMiddleware(),             # 3. 文件上传处理
    SystemPromptMiddleware(),     # 4. 注入系统 Prompt
    SkillMiddleware(),            # 5. 渐进式加载技能
    MemoryMiddleware(),           # 6. 长期记忆读写
    SummaryMiddleware(),          # 7. 上下文压缩
    SubagentLimitMiddleware(),    # 8. 子代理并发限制
    ToolCallLimitMiddleware(),    # 9. 工具调用限制
    RateLimitMiddleware(),        # 10. API 速率限制
    ClarificationMiddleware(),    # 11. 歧义检测（必须在最后）
]

# 中间件执行器 - 洋葱模型
async def execute_middleware_chain(state: AgentState, hook: HookType):
    """按序执行所有注册中间件的指定钩子"""
    for middleware in MIDDLEWARE_CHAIN:
        if hasattr(middleware, hook.value):
            state = await getattr(middleware, hook.value)(state)
    return state

第四章

核心拆解二：动态子智能体调度与上下文隔离

如果说中间件链是 DeerFlow 的"脊柱"，那么动态子智能体调度就是它的"肌肉"。这是它能扛长任务、实现 3-5 倍加速的根因。

完整调度链路

1

指令输入与意图理解

用户输入自然语言任务描述，Lead Agent 做第一轮理解——"这是一份行业报告，需要搜索 + 整理 + 撰写 + 制图 + 审核"。

2

结构化任务拆解

Lead Agent 将任务拆解为 3-6 个可并行的子任务，每个子任务有明确的输入、工具集、终止条件，输出为结构化 JSON。

3

按需拉起子代理（并行）

SubagentExecutor 的调度池将子任务分发到执行池，每个子代理拥有独立的上下文窗口和工具集，互不污染。默认最多并行 3 个。

4

结果汇总与综合

所有子代理完成后，Lead Agent 收到各自的输出，进行交叉验证、去重、整合，生成最终交付物写入 outputs/ 目录。

双线程池架构

SubagentExecutor 采用 调度池 + 执行池 的双线程池设计：调度池负责任务分发而不执行，执行池负责实际运行子代理。这种分离确保调度逻辑本身不会阻塞执行，且调度策略可独立优化（例如根据子任务优先级动态分配）。

Python deerflow-harness/executor/subagent_executor.py · 核心调度逻辑 
class SubagentExecutor:
    """动态子智能体调度器 - 双线程池架构"""

    MAX_CONCURRENT = 3  # 字节内部高并发场景验证的最优值

    def __init__(self):
        self.schedule_pool = ThreadPoolExecutor(max_workers=1)
        self.execute_pool = ThreadPoolExecutor(max_workers=self.MAX_CONCURRENT)
        self.limit_middleware = SubagentLimitMiddleware(self.MAX_CONCURRENT)

    async def execute(self, subtasks: list[Subtask]) -> TaskResult:
        """
        subtasks: Lead Agent 拆解后的结构化子任务列表
        每个 subtask 包含: instruction, tools, context, termination_condition
        """
        # 1. 调度池分发
        scheduled = await self._schedule(subtasks)

        # 2. 执行池并行运行（受限流中间件控制）
        futures = []
        for task in scheduled:
            if self.limit_middleware.can_proceed():
                future = self.execute_pool.submit(self._run_subagent, task)
                futures.append((task.id, future))

        # 3. 收集结果 - 总耗时 ≈ 单个最慢子任务
        results = {}
        for task_id, future in futures:
            results[task_id] = await asyncio.wrap_future(future)

        # 4. 汇总：交叉验证 + 去重 + 整合
        return await self._synthesize(results)

上下文隔离：为什么并行不打架

每个子代理拥有独立的上下文窗口、独立的工具集和独立的终止条件。它们之间通过文件系统（沙箱的 workspace 目录）交换中间结果，但对话上下文完全不共享。这意味着：

  • 子代理 A 的幻觉不会污染子代理 B 的推理
  • 总 token 消耗 = 各子代理 token 之和（无交叉污染）
  • 总耗时 ≈ 最慢子任务耗时，而非串行累加
关键洞察：3-5 倍加速的数学原理不是魔法——假设 5 个子任务各需 10 分钟，串行 = 50 分钟，并行（限 3 并发）= 两轮，每轮 max(10,10,10) = 10 分钟，总计约 20 分钟。加速比取决于任务可并行度，上限由最慢子任务和并发上限共同决定。

调度策略深挖

  • 何时拆：Lead Agent 根据任务复杂度自动判断——简单问答不拆，多阶段研究/开发任务才拆。触发条件是任务步骤数 > 2 且步骤间无强数据依赖。
  • 拆几个：通常 3-6 个，由任务粒度决定。过细（> 8）会增加调度开销和综合难度，过粗（< 3）失去并行价值。
  • 如何限流：SubagentLimitMiddleware 默认限并发 = 3，这是字节内部在高并发场景验证的最优值——既保证并行收益，又避免 API 调用洪水。
  • 如何综合结果：Lead Agent 收到所有子代理输出后，进行新一轮推理：交叉验证事实一致性、去重、按章节结构整合。
第五章

执行环境：给 Agent 一台计算机

"会说话" vs "有自己的电脑"——这是 DeerFlow 与其他 Agent 框架最本质的区别。大多数 Agent 只在对话上下文中"模拟"执行，DeerFlow 给每个任务一个真实的隔离计算环境。

能力 说明
完整文件系统读写文件、创建目录、权限管理，与真实 Linux 环境一致

第六章

长时任务的上下文工程

为什么长任务必然爆上下文

一个典型的研究报告任务涉及数十次 Web 搜索、多次文件读写、多轮子代理交互——每次工具调用都会追加到上下文窗口。如果不加干预，即使 200K token 的窗口也会在 15-30 分钟内被填满。一旦上下文溢出，Agent 会丢失早期的搜索结果和推理过程，导致报告前后不一致甚至自相矛盾。

DeerFlow 的三层解法

📝

自动摘要与压缩

SummaryMiddleware 持续监控上下文消耗百分比，达到阈值（默认 70%）时触发 LLM 摘要，将对话历史压缩为结构化纪要，释放上下文空间。

💾

中间结果持久化

每个子任务的输出不仅返回给 Lead Agent，同时持久化到沙箱的 workspace/ 目录。Agent 可以像人类一样"打开文件回顾之前的工作"，而不依赖上下文记忆。

🔒

子任务限流 + 上下文隔离

每个子代理的上下文天然隔离（不共享对话历史），SubagentLimitMiddleware 限制并发量防止 API 洪水。子代理只需关注自己的子任务，上下文窗口压力远小于串行方案。

分水岭判断：这是区分"玩具"与"能干重活的系统"的关键分水岭。能跑一个 2 分钟任务的 Agent 遍地都是，能把 9 小时的任务稳定跑完而不崩溃的，才值得研究。
第七章

可扩展性：Skill 体系与生态

Skill 的本质

DeerFlow 中的 Skill 是结构化的 Markdown 文件，包含工具描述、执行指令、输出格式规范。内置了研究、报告、PPT、网页、图像、视频等标准 Skill。它的设计理念借鉴了 Claude Code 的 Custom Slash Commands，但更进一步——Skill 不仅定义指令，还定义工具组合和执行管道。

渐进式按需加载：对 Token 敏感的优化

设计亮点：Skill 不会一次性全部注入系统 Prompt（那会消耗数千 token）。SkillMiddleware 根据任务意图，只在需要时才加载相关 Skill 的描述和工具列表。对于 token 敏感的模型（如部分国产模型），这种渐进式加载策略显著降低了不必要的开销。

三种扩展方式

方式 门槛 适用场景
Gateway 安装 .skill 包 低 社区发布的标准化 Skill，支持 version/author/compatibility 等 YAML frontmatter
直接放置 Markdown 最低 自定义简单 Skill，写一段 Markdown 描述工具和指令即可
组合成复合工作流 中 将多个 Skill 编排为管道——例如"研究 Skill → 报告 Skill → PPT Skill"一键串联
第八章

连接能力：MCP、模型工厂与多渠道

DeerFlow 作为 MCP Host

DeerFlow 本身就是 MCP（Model Context Protocol）Host，可以像 Cursor 或 Claude Desktop 一样连接任意 MCP Server 来无限扩展工具能力。支持 HTTP/SSE 传输的 MCP Server 的 OAuth token 认证流程——这意味着你可以把企业内部的数据库、API、知识库通过 MCP 直接接入 DeerFlow 的工具链。

模型工厂：编排层与推理层解耦

兼容任何 OpenAI 兼容 API 的模型，每个模型配置带 supports_thinking 和 supports_vision 能力标记，供中间件链和任务拆解器在运行时做智能决策（例如：拆解任务优先用推理模型，常规搜索用快模型）。

模型 推荐场景 关键能力
豆包 Seed-2.0-Code 代码生成、子代理执行 代码能力 SOTA，推理强
DeepSeek v3.2 任务拆解、综合推理 推理深度强，性价比高
Kimi 2.5 长文撰写、报告生成 超长上下文，中文流畅
架构亮点：换模型时，系统的其余部分（中间件链、沙箱、子代理调度器）完全不关心。编排层与推理层彻底解耦——这是面向接口编程在 Agent 工程中的典型实践。

IM 多渠道接入

支持 Telegram、Slack、飞书/Lark 的消息接入，无需公网 IP——通过 webhook 回调机制实现，降低部署门槛。这对个人开发者和中小团队尤其友好。

执行闭环：补上"最后一公里"

传统研究 Agent 的问题在于——它们完成了认知工作（搜索、分析、总结），却把所有执行工作留给了人。DeerFlow 的不同在于：

  • 研究报告 → 直接输出 PPTX 到 outputs/ 目录
  • 数据分析 SQL → 直接在沙箱里跑，输出可视化图表
  • 网页原型 → 直接在沙箱里起 dev server 并部署
  • 代码项目 → 完整的前后端代码 + 依赖安装 + 运行验证

上手体验

  • 依赖安装：uv sync 一键搞定 Python 依赖，免手动配虚拟环境
  • 前端启动：nvm use && pnpm install && pnpm dev 一条命令
  • 云部署：火山引擎提供一键部署模板，省去运维配置
  • Docker：Docker Compose 启动实测顺畅，但纯新手可能有门槛
  • 人在回路：AI 先出研究计划，用户用自然语言直接改——"加一步技术实现分析""删掉背景介绍"——或一键接受

真实短板（保持客观）

注意：以下短板是全文脱离软文感的关键，请保持客观阅读。
  • 无原生速率限制与成本控制：每个子代理并行发几十次 API 调用时，云账单可能线性上涨。官方目前未提供内置的预算上限或调用频率控制面板。
  • 执行层仍有粗糙处：任务拆解质量高度依赖模型推理能力——用小模型做 Lead Agent 可能产生不合理的任务拆分，导致子代理空转或产出无关内容。
  • Docker 对新手有门槛：虽然本地模式可零依赖运行，但生产部署仍需 Docker。对纯前端或不熟悉容器的开发者有学习成本。
  • 文档与生态待完善：项目仍属早期，社区 Skill 数量和第三方 MCP 适配尚不如 LangChain/CrewAI 生态丰富。

结语

升维：两条 Harness 路线与 2026 的 Agent 工程化

纵观 2026 上半年的 Agent 工程化浪潮，呈现出两条鲜明的技术路线：

路线对比

维度 DeerFlow 路线 Hermes 路线
核心理念 多智能体编排 单体自进化
发力方向 练协作：子代理并行 + 沙箱把大任务干完 练内功：Skill 沉淀 + RL 越用越强
架构风格 "开分店"——拆分任务，多兵作战 "练独门功夫"——一个 Agent 持续精进
适用场景 一次性复杂任务（报告、MVP、数据管道） 持续型任务（客服、运维、个人助理）
Hermes 练内功，DeerFlow 练协作。一条路是让一个 Agent 越来越强（Skill 积累 + 强化学习反馈），一条路是让多个 Agent 分工协作、各司其职。两条路线并不互斥，真正的看点是——它们会不会融合？

收束题眼

回到开篇的核心论点：当模型能力趋于同质化，决定 Agent 能否稳定干重活的不再是模型，而是 Harness。DeerFlow 用沙箱、子代理调度、中间件链和技能体系，给出了一份"如何让 AI 真正交付复杂任务"的工程答卷。它不是终点，而是 Agent 工程化的一个重要路标。
