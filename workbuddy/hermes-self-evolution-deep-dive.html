00 引子

用一个场景把读者拉进来

同一个任务，两种命运

你让 AI Agent 执行一个看似简单的任务："把这个 Next.js 项目部署到 Vercel"。

普通 Agent · 第一次
摸索环境变量配置、踩 Node 版本不兼容的坑、试错 vercel deploy 参数……花了 15 分钟、30 次工具调用才成功。
→
普通 Agent · 第二次
同样的事从头来一遍。环境变量、Node 版本、参数——每一个坑都重新踩。没有记忆，没有积累。
Hermes · 第一次
同样摸索、同样踩坑、同样花 15 分钟。但在任务完成后，它自动复盘，把成功路径抽象成一条可复用的 Skill。
→
Hermes · 第二次
直接调用上次沉淀的 Skill，一气呵成完成部署。甚至顺手修正了 Skill 中过时的命令。30 秒搞定。

这个反差场景揭示了一个核心命题：这不是"AI 自己写代码改自己"的科幻叙事，而是一次关于"Agent 如何进化"的范式提案。

Hermes Agent 由 Nous Research 在 2026 年 2 月开源，它把"自我进化"做成了框架的底层第一性原则——不是附加功能，不是可选插件，而是整个架构设计的出发点。它与你见过的 AutoGPT、LangChain、CrewAI 乃至各类"Agent 框架"有一个根本性的分水岭：那些框架优化的是"执行效率"，而 Hermes 优化的是"从经验流中自主学习的能力"。

不改模型权重，只改"怎么用模型"的策略。
进化的不是"大脑"，而是"工作方法"。

—— 全文题眼

这句话是理解 Hermes 全部设计的钥匙。接下来，我们将逐层拆解它的三层进化引擎、四层记忆架构，以及它们如何构成一个自我加速的飞轮。

01 问题定义

为什么现有 Agent 无法进化

要理解 Hermes 为什么重要，先要看清它试图解决的痛点。当前主流的 Agent 框架——无论是 AutoGPT 的自主循环、LangChain 的链式编排、CrewAI 的多角色协作，还是更近期的各类"通用 Agent"——都共享一个根本性的瓶颈：它们优化的是"执行"效率，但没有突破"从经验流中自主学习"的壁垒。

三个致命痛点

痛点一：跨会话失忆

每次新对话开始，Agent 都是"失忆"的。你在上一个会话中花 20 分钟调通的环境配置、踩过的坑、摸索出的最佳实践，全部蒸发。它不会记住"上次我是怎么做的"，更不会从中学习"下次应该怎么做"。

痛点二：技能不可复用

即便 Agent 在一次会话中表现出色，这些"技能"也无法被提取、保存、复用。你无法把"部署到 Vercel 的完整流程"固化成一个可复用的模块——每次都要从头来过，相当于每次都雇佣一个新实习生。

痛点三：无法从失败中吸取教训

Agent 执行失败后，最多告诉你"出错了"，但不会分析"为什么出错"、不会总结"下次如何避免"。失败经验被白白浪费，同样的错误反复犯。

这三个痛点叠加的后果是：Agent 的能力不会随使用时间增长。用了一百次的 Agent 和用了一次的 Agent，表现没有本质区别。它是一个静态工具，而非一个成长型伙伴。

Hermes 的分水岭

Hermes 把"自进化"当作框架的第一性原则，而非补丁式的附加功能。这意味着从架构设计的第一天起，记忆、技能沉淀、经验复用就不是"以后可以加的功能"，而是整个系统的骨架。其他框架的典型路径是：先做一个能执行任务的 Agent，然后再考虑"能不能让它记住东西"。Hermes 的路径恰恰相反：先设计好记忆和进化的骨架，再往上面挂执行能力。

这个设计顺序的差异，决定了 Hermes 的进化能力是"内生的"而非"外挂的"。

本章小结

现有 Agent 框架的共同瓶颈是"跨会话失忆、技能不可复用、无法从失败中学习"。Hermes 把自进化作为第一性原则而非附加功能，从架构层面解决了这三个问题——这是它与其他框架的根本分水岭。

02 边界厘清

先祛魅："自进化"到底进化了什么

"自进化"这个词容易被误解为某种科幻场景——AI 在运行时自动修改自己的神经网络权重，变得越来越聪明。这个画面既不准确，也容易让人对 Hermes 的能力产生不切实际的期望。

本章的目的就是祛魅：厘清边界，明确它做什么、不做什么。

它不做什么

Hermes 不在运行时重训底层 LLM 的权重。无论你用了 Hermes 多少次、沉淀了多少技能、经历了多少进化循环，底层模型（无论你接的是 GPT-4、Claude 还是 Llama）的参数一个都不会变。它不是在"修改大脑"。

⚠️ 常见误解

"Hermes 会在使用过程中读取你的数据，实时修改模型权重，让模型变得越来越懂你。"——这是错误的。运行时的任何进化都发生在模型外部的策略层，与模型权重无关。

它做什么

Hermes 的"自进化"发生在模型外部的三个层次：

  • 提示层：优化系统提示、工具描述、技能文件的措辞和结构。
  • 记忆层：积累和检索跨会话的经验、偏好、上下文。
  • 工具编排层：优化"在什么场景下用什么工具、按什么顺序用"的策略。

用一个贯穿全文的类比来建立稳定的心智模型：

📝
Skill 沉淀 = 做笔记
把成功经验写成可复用的操作手册。解决的是"记得住"的问题——下次遇到类似任务，不用从头摸索。
运行时层 / 系统层
💪
RL 训练 = 刻意练习
把大量使用轨迹内化成模型的"肌肉记忆"。解决的是"做得好"的问题——模型本身的判断力和执行力变强。
模型层

这个类比非常精准：做笔记不需要改变你的大脑结构，它改变的是你"下次遇到类似问题时怎么处理"的策略。同样，Skill 沉淀不需要改变模型权重，它改变的是"下次模型遇到类似任务时，给它什么样的上下文和指令"。而 RL 训练则确实需要"改变大脑"（修改权重），但这是离线的、批量的、需要专门算力的——跟运行时的"做笔记"是完全不同的路径。

为什么这一章很重要

这是"防割韭菜"章节。在 AI 领域，"自进化""自我改进"这类术语经常被滥用。明确边界不仅是为了技术准确性，更是为了建立作者的可信度——你得先证明自己不会夸大其词，读者才愿意信任你后续的深度分析。

本章小结

Hermes 的自进化不触碰模型权重，而是在提示层、记忆层、工具编排层优化"使用模型的方式"。"做笔记 vs 刻意练习"的类比是理解全文的关键心智模型：Skill 沉淀解决"记得住"，RL 训练解决"做得好"。

03 地基

四层记忆架构：为什么进化必须先解决记忆

任何形式的"从经验中学习"，前提都是"能记住经验"。一个跨会话失忆的 Agent，不可能自进化——经验都留不住，何谈从经验中学习？因此，记忆架构是 Hermes 自进化体系的地基。

Hermes 将记忆刻意分为四层，每层有明确的职责、存储位置和读取时机：

⚡
工作记忆
Working Memory
当前对话的上下文窗口。存储即时任务状态、最近几轮对话。随会话结束而清除。对应 LLM 的 context window。
📖
情景记忆
Episodic Memory
跨会话的"经历日志"。记录"什么时候、做了什么、结果如何"。通过 FTS5 全文索引存入 SQLite，检索时先经 LLM 摘要再注入上下文。
🧠
语义记忆
Semantic Memory
从多次经历中提炼的"知识点"和"事实"。比如"用户偏好用 pnpm 而非 npm""项目用 Tailwind 而非 CSS Modules"。存储在 MEMORY.md 中。
🔧
技能记忆
Skill Memory
可复用的"操作手册"——即 Skill 文件。每个 Skill 是一个 SKILL.md，包含触发条件、执行步骤、注意事项。是程序性记忆的核心载体。

为什么要分层？

这是 Hermes 设计中最容易被忽略、但最为关键的决策。如果所有记忆混在一个存储里——一个大文件、一个大数据库——时间一长必然退化：

  • 检索变慢：存储越大，找到相关信息的成本越高。全量塞进上下文窗口既不现实也不经济。
  • 噪声淹没有用信息：无关的历史记录会干扰模型的判断。你需要的是"跟当前任务相关的经验"，而不是"所有历史经验"。
  • 不同类型的信息有不同的生命周期：工作记忆随会话清除，情景记忆长期保留但可能被新经验覆盖，语义记忆相对稳定，技能记忆则是持续迭代的。混在一起就无法实施差异化的管理策略。

实现细节：文件系统 + SQLite 的混合架构

Hermes 的记忆系统并非依赖某个复杂的向量数据库，而是采用了文件系统 + SQLite 的务实组合：

记忆层 存储位置 读取方式 控制策略
工作记忆 LLM 上下文窗口 直接注入 受 context window 限制，自动截断
情景记忆 SQLite + FTS5 全文索引 关键词检索 → LLM 摘要 → 注入 只带相关条目，非全量加载
语义记忆 MEMORY.md 文件 会话开始时注入 精炼长期事实，控制文件大小
技能记忆 SKILL.md 文件（技能库目录） 按需加载（You MUST load it） patch 式增量更新，单文件 ≤ 15KB

其中几个关键设计值得展开：

SOUL.md / MEMORY.md / USER.md 的角色分工。这三个文件构成了 Hermes 的"人格与偏好层"。SOUL.md 定义 Agent 的核心性格和价值观（"你是谁"），USER.md 记录用户的基本信息（"你在帮谁"），MEMORY.md 则是跨会话的长期记忆（"你们一起经历了什么"）。它们的共同目的是在不无限膨胀上下文的前提下，保持 Agent 的连续性和个性化。

FTS5 全文索引 + LLM 摘要注入。情景记忆不是简单地存日志、检索时全部塞回上下文。Hermes 的做法是：用 SQLite 的 FTS5 扩展做全文检索，找到与当前任务相关的历史条目，然后用 LLM 对这些条目做摘要，只把摘要后的关键信息注入上下文。这样既保证了相关性，又控制了上下文长度。

"只带相关内容"的纪律。这是整个记忆系统的核心原则。不是"记住所有"，而是"在需要时找到相关的，且只把相关的带进来"。这直接决定了系统能否在长期使用中保持性能不退化。

本章小结

记忆是自进化的地基。Hermes 将记忆刻意分为工作记忆、情景记忆、语义记忆、技能记忆四层，用文件系统 + SQLite 的混合架构实现差异化存储与检索。程序性记忆（技能）与情景记忆（经历）的刻意分离是关键设计选择——这确保了系统能在长期使用中保持检索效率和信号纯度。

04 引擎一 · 运行时进化

Skill 闭环：让经验自动沉淀为可复用的能力

如果说记忆架构是地基，那么 Skill 闭环就是 Hermes 运行时进化的核心引擎。它的工作是将"一次成功的执行经验"自动转化为"下次可直接复用的能力"。

完整闭环：六步循环

1
经验提取
从执行轨迹中识别可复用的模式
2
知识存储
写入 SKILL.md 技能文件
3
智能检索
下次遇到类似任务时匹配技能
4
上下文注入
将技能内容注入当前对话
5
执行验证
用技能指导执行，验证效果
6
自动改进
patch 式修正过时或出错的部分

这六步构成了一个自增强的闭环：每次使用都在验证和改进技能，每次改进都让下次执行更高效。关键在于，这个闭环是自动触发的，不需要用户手动操作。

触发时机：Nudge 机制

Hermes 不会在每次工具调用后都触发复盘——那样成本太高，也会打断执行流。它用一个叫 Nudge 的机制来判断"什么时候该把经验固化成技能了"。

Nudge 触发条件

大致的触发规则是：每完成约 15 次工具调用，或完成一个复杂任务后，系统会触发自我复盘。复盘时会回顾刚刚的执行轨迹，识别其中"值得固化为技能"的部分——比如一套反复验证有效的工具调用序列、一个解决特定问题的可靠流程。

"约 15 次"这个数字并非随意设定，而是成本-效果的权衡点。太频繁（比如每 3 次调用）会过度消耗 token 和时间；太稀疏（比如每 100 次）又会遗漏有价值的经验。15 次工具调用通常意味着一个"有一定复杂度、值得总结"的完整工作单元。

自我修正：patch 式而非整体重写

这是 Hermes Skill 系统中最精巧的设计之一。当后续使用中发现某个技能过时或出错时，Hermes 不会重写整个 SKILL.md 文件，而是用 patch 式的 find-and-replace，只修改需要变更的片段。

SKILL.md 的 patch 式更新（伪代码示意）
# 不是这样（整体重写——风险高、浪费 token）：
write_file("SKILL.md", regenerate_entire_skill(new_experience))

# 而是这样（patch 式——精准、低成本、可追溯）：
old = "使用 `vercel deploy --prod` 部署"
new = "使用 `vercel deploy --prod --yes` 部署（--yes 跳过确认提示）"
edit_file("SKILL.md", find=old, replace=new)

为什么这个设计如此重要？因为整体重写有两个致命问题：

第一，"越用越腐烂"。每次重写都可能引入回归——之前正确的部分可能被改错。而 patch 式更新只动需要动的地方，最大限度地保留了已经验证过的内容。这让技能"越用越准"而非"越用越烂"。

第二，token 浪费。重写一个可能 10KB 的 SKILL.md 需要先生成 10KB 的内容，而 patch 式更新只需要生成变更的那几行。在大量技能需要维护的场景下，这个成本差异是巨大的。

硬核深挖：注入机制背后的工程约束

对于想深入理解工程细节的读者，这里展开几个值得注意的设计决策：

[SYSTEM: ...] 前缀与"you MUST load it"强制措辞。当 Hermes 决定在当前会话中加载某个技能时，它会在消息流中注入一条以 [SYSTEM: ...] 为前缀的指令，并使用 "you MUST load it" 这样的强制措辞。这看似简单，背后其实是一个成本-效果的精密权衡：

  • 成本侧：每次注入技能都会占用上下文窗口，增加 token 消耗。不能无差别地注入所有可能相关的技能。
  • 效果侧：如果不强制加载，LLM 可能"偷懒"忽略技能——尤其是当技能内容较长时。强制措辞确保技能被实际使用和验证。

"Prompt Caching Must Not Break"约束。许多 LLM 提供商支持 Prompt Caching——如果连续请求的前缀相同，可以复用缓存的 KV 状态，大幅降低成本和延迟。Hermes 的技能注入必须放在不会破坏 Prompt Cache 的位置——通常是在缓存前缀之后。如果技能注入打断了前缀的一致性，每次请求都要重新计算整个前缀的 KV，成本会飙升。这是一个典型的"看起来不起眼、但做错了会让整个系统在经济上不可行"的工程约束。

技能注入的消息结构（简化示意）
# ---- 以下部分可被 Prompt Cache 复用 ----
system_prompt: "You are Hermes, a self-evolving agent..."
soul_md: "你的性格、价值观..."
user_md: "用户信息..."
memory_md: "长期记忆..."

# ---- 以下部分每次可能不同（Cache 边界） ----
skill_injection: "[SYSTEM: The following skill is relevant to the current task. You MUST load it and follow its instructions: ...]"
episodic_recall: "[SYSTEM: Relevant past experience summary: ...]"
user_message: "帮我把项目部署到 Vercel"
本章小结

Skill 闭环是运行时进化的核心引擎：Nudge 机制在约 15 次工具调用后触发复盘，将成功经验抽象为 SKILL.md；后续使用中通过 patch 式 find-and-replace 增量修正，让技能"越用越准"。注入机制背后的 Prompt Caching 约束是一个"做错了会让系统在经济上不可行"的关键工程决策。

05 引擎二 · 离线批量进化

GEPA/DSPy 系统级优化：让 Agent 在离线时"反思"自己

运行时的 Skill 闭环解决的是"即时经验沉淀"，但它有一个局限：只能优化"技能文件"这一个维度。Agent 的表现还取决于系统提示写得好不好、工具描述清不清楚、工具代码本身有没有 bug。这些维度的优化需要更系统的方法。

2026 年 3 月，独立项目 hermes-agent-self-evolution 应运而生。它用 DSPy + GEPA（Genetic-Pareto Prompt Evolution）自动进化技能文件、工具描述、系统提示，甚至工具代码本身。

GEPA 是什么？为什么它不同于普通提示优化

GEPA 是 ICLR 2026 论文提出的方法，核心思想是用遗传算法 + Pareto 前沿优化来进化提示词。但 Hermes 用它的方式有一个独到之处：

GEPA 的关键差异

普通的提示优化只看"成功还是失败"（二值信号），然后尝试随机变异。GEPA 的优化器会读取完整的执行轨迹，理解"为什么失败"——是哪个步骤出了问题、是什么原因导致的、修正哪个环节能改善。这意味着它生成的候选变体是有方向性的，而非盲目试错。

举个具体例子：假设一个"部署到 Vercel"的技能在执行中失败了，普通优化器只会知道"失败了，试试换个说法"。而 GEPA 会读取轨迹，发现失败是因为"技能中引用的 vercel-cli 命令已经在新版本中改名了"——然后它会针对性地修改那个过时的命令名，而不是随机重写整段技能。

安全设计：进化不能失控

自动修改系统提示和工具代码听起来很危险——如果进化出一条有害的指令怎么办？如果"优化"后的工具代码引入了安全漏洞怎么办？Hermes 用一套多层约束门控来兜底：

约束门控 规则 目的
测试门控 候选变体必须 100% 通过现有测试套件 防止回归——进化不能破坏已有功能
大小门控 技能文件不超过 15KB 控制上下文占用，防止技能膨胀
语义门控 变体的语义不能偏离原始目的 防止"优化"方向跑偏——部署技能不能进化成删除技能
审核门控 所有变体以 PR 形式提交人工审核 最后一道防线，确保人类把关
回滚门控 完整 Git 历史可追溯、可回滚 出问题时能快速恢复到上一个已知好的版本

这五层门控构成了一个"进化沙箱"：GEPA 可以自由探索优化空间，但任何变异都必须通过所有门控才能生效。这种设计让"自动化"和"安全性"取得了平衡——既不扼杀进化的效率，也不放弃人类对系统的最终控制权。

经济性：让"Agent 自我改进"平民化

GEPA 管道的一个重要特性是无需 GPU。它调用的是 LLM API（来做轨迹分析和变体生成），而不是在本地跑模型训练。这意味着：

成本结构

每次进化运行的成本大约在 2–10 美元之间——取决于优化的范围和使用的 LLM。这个成本意味着任何团队都用得起，而不只是拥有 GPU 集群的大公司。它大大降低了"Agent 自我改进"的门槛。

对比一下：一次完整的 RL 训练（下一章会讲）可能需要数百到数千美元的 GPU 算力。GEPA 的 2–10 美元让它成为"高频、低成本的渐进式优化"路径——你可以每周跑一次，持续改进系统提示和技能文件，而不需要等到攒够一大笔训练预算。

GEPA 进化管道（伪代码示意）
# 1. 收集执行轨迹
trajectories = collect_trajectories(agent, test_scenarios)

# 2. GEPA 分析"为什么失败"（而非仅看成功/失败）
for traj in trajectories:
    if not traj.success:
        failure_analysis = llm_analyze(
            "为什么这条轨迹失败了？哪个环节出了问题？",
            trajectory=traj
        )

# 3. 生成候选变体（有方向性，非盲目变异）
candidates = generate_variants(
    current_skill, failure_analyses, constraints
)

# 4. 约束门控过滤
survivors = []
for candidate in candidates:
    if passes_all_tests(candidate) \
       and size_ok(candidate, limit=15KB) \
       and semantic_aligned(candidate, original):
        survivors.append(candidate)

# 5. Pareto 前沿选择（多目标优化：成功率 vs 效率 vs 简洁性）
best = pareto_select(survivors)

# 6. 提交 PR 供人工审核
create_pull_request(best, reviewer="human")
本章小结

hermes-agent-self-evolution 用 DSPy + GEPA 实现离线批量进化：优化器读取执行轨迹理解"为什么失败"，生成有方向性的候选变体，经过五层约束门控（测试/大小/语义/审核/回滚）后以 PR 形式提交人工审核。每次成本 2–10 美元、无需 GPU，让"Agent 自我改进"平民化。

06 引擎三 · 模型级进化

RL 训练：把使用轨迹变成更强的模型

前两个引擎——Skill 闭环和 GEPA——都在模型外部工作，不改变模型本身。第三条路线则是最重、最根本的：把使用轨迹导出为训练数据，去 RL（强化学习）训练一个更强的 Hermes 模型。

轨迹如何变成训练数据

Hermes 的运行时会产生大量的执行轨迹——每一步工具调用、每一条 LLM 响应、每一次成功或失败的结果。这些轨迹通过 trajectory.py 模块被结构化记录，然后转换为训练所需的格式。

trajectory.py 结构化记录（简化示意）
# 每条轨迹记录完整的状态-动作-奖励序列
class Trajectory:
    task: str                    # "部署到 Vercel"
    steps: List[Step]          # 每一步的详情
    outcome: str               # "success" | "failure"
    reward: float              # 奖励信号
    tools_used: List[str]      # 使用的工具序列
    total_cost: float          # token 成本
    duration: float             # 耗时

这些轨迹随后被转换为 ShareGPT 格式——一种在开源社区广泛使用的对话数据格式。这里有一个有趣的叙事点值得展开：

"gpt 标签"背后的生态锁定

ShareGPT 格式中，消息的角色标签通常是 "gpt" 和 "human"——这是从 ShareGPT（一个分享 ChatGPT 对话的项目）继承来的命名。即使你用 Claude 或 Llama 生成的轨迹，在格式化时也可能被打上 "gpt" 标签。这个看似无害的命名惯例，实际上折射了 OpenAI 在 Agent 训练数据生态中的深远影响——格式标准、角色命名、甚至数据结构，都带着 ChatGPT 时代的烙印。这是一个"技术惯例演变为生态锁定"的典型案例。

batch_runner.py：数据工厂

要训练一个好的 RL 模型，需要大量多样化的轨迹数据。batch_runner.py 就是 Hermes 的"数据工厂"——它用线程池并行运行大量 Agent 对话，自动收集执行轨迹：

batch_runner.py 工作原理（伪代码示意）
# 并行运行 Agent 对话，批量收集轨迹
with ThreadPoolExecutor(max_workers=32) as executor:
    futures = []
    for scenario in test_scenarios:
        # 每个 scenario 是一个预定义的任务场景
        future = executor.submit(run_agent_dialogue, scenario)
        futures.append(future)

    # 收集所有轨迹
    all_trajectories = [f.result() for f in futures]

# 导出为 ShareGPT 格式训练数据
export_training_data(all_trajectories, format="sharegpt")

戳破最大的误解

⚠️ 关键澄清

关于 Hermes 的 RL 训练，有一个广泛流传的误解："Hermes 会读取用户的实时对话数据，用来实时训练/微调模型权重。"

这是错误的。RL 训练的数据源默认是用 claude-opus 这类顶级模型作为 Teacher Model 合成的"示范动作"——而非普通用户的实时对话。

这个误解的来源可能是对"使用轨迹训练模型"这个说法的字面理解。但实际流程是：

  1. 定义任务场景：预定义一批多样化的 Agent 任务。
  2. Teacher Model 生成示范：用 claude-opus 等顶级模型在这些场景中执行任务，产生高质量轨迹。
  3. 收集和格式化：batch_runner.py 并行收集这些轨迹，转为 ShareGPT 格式。
  4. RL 训练：用这些高质量轨迹做强化学习，训练更强的 Hermes 模型。

用户实时对话的轨迹可以被导出用于训练，但这不是默认行为，需要显式配置。而且即便使用用户轨迹，也是离线批量处理，而非"实时改权重"。

这个澄清的重要性在于：它划清了"从示范中学习"和"实时监控用户行为并改模型"的界限。前者是正常的模型训练流程，后者涉及隐私和安全问题——Hermes 做的是前者。

本章小结

RL 训练是三层进化中最重的路径：trajectory.py 结构化记录执行轨迹，batch_runner.py 用线程池并行收集数据，最终导出为 ShareGPT 格式用于强化学习。关键澄清：训练数据源默认是 Teacher Model（claude-opus）合成的示范动作，而非用户实时对话——这与"读取用户数据实时改权重"是截然不同的两码事。

07 全文高潮

合体：三层飞轮如何协同

前三章分别拆解了三层进化引擎。但 Hermes 的真正威力不在于任何单层，而在于三层构成的飞轮——它们互相喂养，形成正向循环。

图：三层飞轮——运行时技能积累 → 系统级批量优化 → 模型级 RL 训练 → 更强模型产出更高质量轨迹 → 回馈运行时层

飞轮如何转动

理解这个飞轮的关键，是看清楚三层之间的"喂养"关系：

第一圈：运行时层 → 模型层。用户在使用 Hermes 的过程中产生大量执行轨迹。这些轨迹——尤其是成功的、高效的轨迹——被导出为训练数据。轨迹越多、质量越高，RL 训练出来的模型就越强。

第二圈：模型层 → 运行时层。更强的 Hermes 模型意味着什么？意味着它在执行任务时会产生更高质量的轨迹——更少的试错、更优的工具调用序列、更高的成功率。这些更高质量的轨迹又会被导出为更好的训练数据……循环加速。

第三圈：系统层的加持。GEPA 在中间扮演"催化剂"角色。它从运行时轨迹中分析失败原因，优化技能文件和系统提示。优化后的技能和提示让运行时层的表现更好，产生更高质量的轨迹，进而让模型层的训练数据更好。GEPA 不直接参与模型训练，但它提升了飞轮每一圈的效率。

为什么要同时做三条路线？

这是最核心的问题。如果只做其中一条，会怎样？

只做一条 结果 局限
只做 Skill 闭环 能记住经验、复用流程 像一个"只会查手册的实习生"——手册再全，判断力和执行力受限于模型本身的智力。遇到手册没覆盖的新情况就抓瞎。
只做 RL 训练 模型本身变强 成本高、周期长，而且记不住你的具体偏好。每次 RL 训练都是"通用能力提升"，无法针对性地记住"你用 pnpm 不用 npm"这类个性化信息。
只做 GEPA 提示和工具描述变好 天花板受限于当前模型的智力。GEPA 优化的是"怎么用好当前模型"，但如果模型本身不够聪明，优化的边际收益会递减。

三者互补才闭环：

  • Skill 闭环解决"个性化记忆"——记住你的偏好、你的项目、你的工作流。
  • GEPA解决"使用效率"——让当前模型被用得更好，榨干每一分智力。
  • RL 训练解决"智力天花板"——让模型本身变强，突破当前能力上限。

缺任何一层，飞轮都会"漏气"：只做 Skill，模型智力是天花板；只做 RL，个性化记忆缺失；只做 GEPA，优化空间受限于模型。三者同时运转，才能形成真正的自加速循环。

开源框架中的独特性

据我们所知，没有其他开源 Agent 框架把运行时行为当作下一代模型的训练素材。大多数框架的运行时和训练是完全割裂的——你用 Agent 做的事，不会回馈到模型本身。Hermes 的飞轮设计打破了这堵墙，让"使用"和"训练"形成闭环。这在开源生态中是独创的。

本章小结

三层引擎构成自加速飞轮：运行时技能积累产出轨迹 → 轨迹导出为训练数据 → RL 训练更强模型 → 更强模型产出更高质量轨迹 → 回馈运行时层；GEPA 在中间催化每一圈的效率。只做任何单层都有致命局限——Skill 解决"记得住"、GEPA 解决"用得好"、RL 解决"变更强"，三者互补才闭环。这种"运行时行为喂养下一代模型"的设计在开源框架中是独创的。

08 批判性审视

冷静下来：局限与适用边界

前面的章节可能让人对 Hermes 的自进化能力充满期待。但一篇严肃的技术解读不能止步于赞美——客观性来自于对局限的诚实分析。这一章是让本文区别于营销软文的关键。

局限一：效果高度依赖使用模式

Hermes 的自进化机制——尤其是 Skill 闭环——本质上是从重复性工作流中提取模式。这意味着：

回报不均匀

重复性工作流回报最大：如果你每天部署 Vercel、每周跑 CI/CD、每月生成相同格式的报告——这些高频重复任务是 Skill 沉淀的理想场景，进化价值最大。

一次性任务进化价值有限：如果你用 Hermes 做的是"写一篇全新的营销文案""分析一个从未见过的数据集"这类高度非重复的任务，Skill 沉淀几乎没有用武之地——因为你不会第二次遇到完全相同的任务。

这不是 Hermes 的设计缺陷，而是"从经验中学习"这一范式的固有边界。人类也是如此：一个每天做同类手术的外科医生会越做越熟练，但一个每次面对全新病例的研究型医生，"经验积累"的杠杆效应就小得多。

局限二：对"约 40% 加速"数据保持审慎

Nous Research 在发布时提到 Hermes 在某些场景下能实现"约 40% 的执行加速"。这个数字很有传播力，但需要审慎看待：

  • 它来自单一案例：40% 的加速很可能是在特定任务类型（高重复性、已有技能沉淀）下的最优表现，不宜当作普遍结论。
  • 没有公开的基准测试：缺乏标准化的评估方法、对照组和统计显著性数据。在学术意义上，这个数字目前更接近"营销数据"而非"研究数据"。
  • "加速"的定义不明确：是减少了 40% 的工具调用次数？减少了 40% 的 token 消耗？还是减少了 40% 的墙钟时间？不同的定义对应完全不同的实际价值。

合理的做法是：把它当作"可能的上界"而非"典型表现"。在实际使用中，加速效果会因任务类型、使用频率、技能库成熟度等因素大幅波动。

局限三：评估数据集质量决定进化效果

无论是 GEPA 还是 RL 训练，进化的效果都取决于"用什么数据来评估和训练"。如果评估数据集本身有偏差——比如只覆盖了部分任务类型、只包含简单场景——那么进化出来的技能和模型也会带有同样的偏差。

Garbage in, garbage out. 这个古老的计算原则在 Agent 自进化中依然适用——进化算法再精巧，也无法从有偏差的数据中进化出无偏差的能力。

局限四：进化算法可能陷局部最优

GEPA 用遗传算法 + Pareto 前沿来探索优化空间。但遗传算法有一个已知的局限：可能陷入局部最优——找到一个"比当前好一点"的变体后就停止探索，错过"好很多"的全局最优解。尤其当搜索空间较大、评估样本较少时，这个风险更显著。

Hermes 的约束门控（测试 100% 通过、语义不偏移）在保证安全的同时，也可能过度收紧了搜索空间——一些"方向正确但暂时无法通过所有测试"的候选变体会被过滤掉，错失了潜在的更优解。

局限五：人工审核可能成为瓶颈

GEPA 的所有变体都需要以 PR 形式提交人工审核。这在项目初期是合理的——安全第一。但随着技能库增长、进化频率提升，人工审核的工作量会线性增长。如果审核速度跟不上进化速度，PR 积压会成为瓶颈，反而拖慢进化节奏。

这个问题可能的解决方向包括：自动审核（用另一个 LLM 做初审）、分级审核（低风险变更自动通过、高风险变更人工审核）、社区审核（开源社区共同审核 PR）。但这些方案目前都还在探索阶段。

本章小结

Hermes 自进化有明确的适用边界：重复性工作流回报最大，一次性任务价值有限；"约 40% 加速"来自单一案例，不宜当普遍结论；评估数据集质量、进化算法局部最优、人工审核瓶颈都是潜在风险。诚实面对这些局限，恰恰是技术成熟度的体现。

09 结语 · 升维

这代表 AI Agent 工程化的什么方向

从"被手动调教的静态工具"到"在实战中主动进化的数字资产"——这是 Hermes 所代表的 AI Agent 工程化方向。

传统 Agent 的能力曲线是平的：无论你用多久，它的表现不会随时间增长。Hermes 打破了这个天花板，让 Agent 的能力随使用经验持续增长。这不是通过修改模型权重实现的——进化的不是"大脑"，而是"工作方法"。

正因为进化发生在策略层而非模型层，Hermes 对模型选择不敏感、兼容任何提供商。你今天用 GPT-4，明天换成 Claude，后天换成开源 Llama——Skill 库、记忆系统、GEPA 优化的提示词都不受影响。这让 Hermes 的进化成果成为一种与模型解耦的数字资产，而非绑定在某个特定模型上的"一次性投资"。

回扣全文题眼：不改模型权重，只改"怎么用模型"。这句话既是 Hermes 的技术宣言，也是它的设计哲学——你不需要拥有模型的所有权来让 Agent 变强，你只需要让"使用模型的方式"持续进化。

🔮 留给读者的开放问题

当运行时行为持续喂养下一代模型，当每一次工具调用、每一次成功或失败都在塑造 Agent 的未来能力——Agent 的进化会走向何处？它会不会最终到达一个"自我改进的奇点"，还是会在某个能力平台期稳定下来？更重要的是：当 Agent 的进化深度依赖于用户的使用数据，谁真正"拥有"这些进化成果——是用户、是框架开发者、还是训练出来的模型本身？
